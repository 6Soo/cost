## 1. 사용자 확정 제품 방향

### 1.1 사이드메뉴·디자인

- 공통 다크·라이트 디자인을 모든 업무 화면에 적용한다. 사이드바도 별도의 밝은 고정색으로 남지 않아야 한다.
- 사이드바 스크롤바는 얇고 둥글며 hover·다크/라이트 대응을 갖춘다. Firefox/WebKit의 색상·넓이를 확인한다.
- 상단 '숲길여행 회계' 브랜드 링크는 적절한 녹색 계열로 조화롭게 강조한다. 높은 명도의 단색 버튼보다 공통 색상 토큰·테두리·hover·keyboard focus를 사용한다.
- 사이드바 하단 '전체 여행 보기' 링크는 /trips로 연결하고, 작은 안내 문구를 간결하게 배치한다. 여행 검색, 목록, 이전 여행 확장, 모바일 drawer를 보존한다.
- 근거: UI 통합 명세와 PR #120. 실제 코드 PR #120은 병합되었고 operations.md와 현재 인계 §0.19에 런타임 78cf8b8 확인이 기록되어 있다. 실로그인 브라우저 육안 수락은 NOT_RUN.

### 1.2 해·초승달 아이콘 한 개로 테마 수동 선택

- 모든 업무 화면 우상단의 버튼은 오직 아이콘 하나만. 라이트 모드에는 해, 다크 모드에는 초승달. 버튼을 누르면 반대 테마로 즉시 전환.
- 화면에 '라이트 모드', '다크 모드', '클릭하면 전환' 등 버튼 아래·옆 설명이나 캡션을 추가하지 않는다. 접근성용 aria-label과 44px 터치 영역은 반드시 유지한다.
- 최초에는 시스템 prefers-color-scheme을 적용하고, 사용자가 수동 전환하면 브라우저 localStorage의 light/dark 선택값을 우선한다. 페이지 이동·새로고침에도 보존하고 서버·Google·DB에는 저장하지 않는다.
- 모든 페이지, 사이드바·본문·카드·폼의 계산 색상이 같이 바뀌어야 한다. 375px/390px/759px/760px/1280px, 200% 확대 및 키보드 테스트를 포함한다.
- 세부: docs/card-all-transactions-and-ui-design-system-spec-v1.md §13. PR #116/#122는 명세 병합, 기능 구현과 실브라우저 수락은 아직 확인되지 않았다. 티켓 THEME-TOGGLE-01.

### 1.3 장부 스크롤/하단 빈 화면 결함

- 사용자가 제시한 0630_오제 화면에서 거래 목록 하단 이후 큰 어두운 빈 영역이 노출되고 전체 페이지가 아래로 움직이는 증상을 수정한다.
- 원인은 첨부 화면만으로 단정하지 않는다. 문서(body) 스크롤과 app(100dvh) 및 nav/main 개별 스크롤 경계를 나눠 조사한다. nav와 거래 목록은 각각 스크롤하되 앱 전체가 빈 영역까지 내려가면 안 된다.
- 모바일 drawer, 휠/터치/키보드 PageDown, 200% 확대, 끝 행 접근, sticky 요소, 다른 standalone 페이지 회귀를 검사한다.
- PR #117은 최소 CSS 변경과 명세 §14를 포함하나 현재 OPEN/CONFLICT. 최신 main에 이미 병합된 #120 메뉴 디자인과 #116의 테마 §13을 보존하여 별도 재조정해야 한다. 브라우저 테스트가 통과하지 않았다면 해결 완료라고 쓰지 않는다.

### 1.4 항공권 참가자 연결 → 항공권 예약 확인

- 2026-10-23 등장한 기존 참가자 연결은 영문 탑승자를 Reservation 참가자와 수동 연결하기 위한 보조 기능이었다. 사용자는 독립 메뉴의 활용도가 낮다고 판단해 업무 목적을 '항공권 예약 확인'으로 변경했다.
- 메뉴/타이틀 '항공권 예약 확인'. 첫 화면 필수 입력은 탑승객 이름 하나만. 예약번호나 여행 정본 ID를 먼저 요구하지 않는다.
- 한글·영문 이름 지원은 실제 원본의 확인된 이름 대응에 한정한다. 로마자 임의 변환, 동명이인 자동 합치기, 결과 첫 건 자동 선택 금지.
- 예약별 카드에 예약번호·탑승객·확인된 여정/상태/날짜 의미/증거 출처 표시. 항공권 예약일, 발권일, 결제일, 이메일 발송일은 서로 다르므로 정확히 구분.
- 정보 위계: 항공권 예약 정보 → 확정 연결된 카드 결제 → 미연결 카드 거래 후보. 연결된 카드라는 표시는 저장된 동일 예약·결제 사건의 실제 근거가 있을 때만 가능하다.
- **미연결 시 검증된 항공권 예약일의 모든 카드 원행을 후보로 조회한다.** 금액·가맹점으로 멋대로 필터링하지 않고 모든 기록(취소·환불·이미 다른 예약 연결 포함)을 표시하며 페이징으로 전수 접근한다. 후보는 결제 확정이 아니고 자동 연결·기장하지 않는다.
- 예약일이 확인되지 않으면 카드 거래 후보를 임의 날짜로 표시하지 않는다. 날짜 근거 부족을 명확히 알리고 사용자의 명시적 날짜 필터만 별도로 제공할 수 있다.
- 이전 참가자 수동 연결/owner·CSRF·revision 보호는 삭제하지 않고 상세 보조 기능으로 옮긴다. 기본 조회는 owner, no-store, 검색 이름의 URL 노출을 방지한 POST 경로 우선.
- 상세 정본: docs/flight-booking-verification-spec-20261026.md, 명세 PR #118. 코드 PR #119는 현재 OPEN/MERGEABLE로 이름 단독 조회·기본 예약 카드만 작업 중. 실제 카드 연결·예약일 원행 후보는 미구현. 새 렌더러를 검증하지 않고 과거 UI 테스트를 'legacy'로만 돌리는 것은 새 화면 수락 증거가 아니다.
- 티켓 순서: FLIGHT-VERIFY-DATA-01 → FLIGHT-VERIFY-API-01 및 FLIGHT-VERIFY-CARD-01 → FLIGHT-VERIFY-UI-01. 새 화면 실제 테스트 및 외부 출처/권한/보안 검증 후 병합·배포.

### 1.5 오제 수입·기존 장부 ↔ 웹 장부 대조

- 0625_아키타 = 회계 2분기 마지막. 0630_오제 = 회계 3분기 첫 여행. 6월 30일 시작을 달력 분기로 기계 분류하지 않는다.
- 수입 표시를 지출 검증 결과 하나로 전부 숨기지 않는다. 수입 자체의 근거와 전체 회계 경고는 별개.
- 같은 여행·같은 지출·통화/부호 포함 금액 일치, 추가로 날짜/가맹점/분류/예약번호 중 하나 이상 일치하면 COST 웹 거래 후보 행을 굵게 강조한다. 볼드는 단지 읽기 전용 시각 표시이며 거래 확정·중복 제거·Google 원본 쓰기가 아니다.
- 명세 PR #110 및 구현 PR #114는 병합되어 있고 운영 기록이 있으나, 과거 화면 표시 실패 원인과 전체 로그인 UI 수락은 별도 미검증 항목이다. 세부: docs/trip-income-visibility-and-ledger-match-spec-20261025.md.

### 1.6 지출 일괄 자동 정리

- 일반 지출 정리 화면의 '전체 지출 자동 정리'는 무심코 실행하면 위험하다. 일반 화면 버튼을 제거하고 owner 유지보수 화면에 읽기 전용 dry-run/미리보기, 명시적 실행, 재검증·감사·중복 방지를 분리한다.
- PR #105 명세와 #114 코드·운영 기록을 우선 재사용한다. 금융 기록이나 수동 여행 이동의 권위를 UI 변경으로 확대·약화하지 않는다.
