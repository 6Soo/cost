## 1. 현재 확인된 코드와 정확한 결함

2026-10-28 main `webapp/card_flow.py` 정적 확인:

1. `render_expense_cleanup(board, csrf, *, page=1)`는 `cleanup-breakdown` 아래 세 건수를 HTML `<span>`으로 렌더링한다. CSS `.cleanup-breakdown span`은 배경·둥근 모서리·여백으로 **버튼처럼 보이게** 하지만 클릭, 링크, role, keyboard, pressed/current 상태가 없다.
2. `/import` 핸들러는 `cleanup_page`만 파싱한다. 카테고리별 query parameter가 없다.
3. `_cleanup_card_where`는 미기록 카드 거래를 선별하고 `_cleanup_unassigned_where`는 `board_rows`의 여행 미배정 비용 행을 선별한다. 목록은 **카드 거래 먼저, 그 다음 장부 행** 순으로 합쳐져 20건 단위 페이지를 구성한다.
4. `_cleanup_card_breakdown`은 카드마다 `CASE WHEN`의 배타적 우선순위로 상태를 계산한다. 우선순위: 취소/원본충돌/파싱오류/리뷰보류→`protected`, 비용항목 없음→`no_item`, 여행 미배정→`no_trip`, **나머지→`protected`**. 즉 현재 `보류·오류` 숫자에는 실제 보류가 아닌 기타 검토 대상도 들어갈 수 있다. 이 마지막 `ELSE protected`를 근거 없이 “금융 보호 발생”으로 설명하면 안 된다.
5. 상단 총 53건(첨부 화면의 예시)은 `card_total + ledger_total`이다. 화면 표시 예시의 3/20/30은 실제 운영의 고정 수치가 아니며 변경 가능한 동적 결과다. `여행 미배정`에는 카드 `no_trip`과 장부 `ledger_total`이 함께 포함된다.
6. 페이지 내 저장 성공 시 `CLEANUP_SCRIPT`는 해당 `.cleanup-row`를 즉시 제거하고 전체 `cleanup-count`만 1 감소시킨다. 현재는 **카테고리 숫자 동기화가 없다.**
7. 기존 지출 검토 버튼/POST는 `/api/imports/<batch>/decision`, `/api/rows/<row_id>/save`로 각각 처리한다. 클릭 필터는 **조회 전용 GET**이어야 하며 금융 보호와 쓰기 API를 호출해서는 안 된다.

**따라서 단순히 span을 button으로 바꾸거나 현 페이지 DOM만 가리는 구현은 수락하지 않는다.** 서버에서 해당 상태의 전체 후보를 다시 선별하고, 카운트·페이지네이션·저장 후 갱신까지 일치해야 한다.

## 2. 확정된 제품/UX 동작

### 2.1 필터 칩

~~~text
지출 정리
근거 확인이 필요한 거래 53건

[전체 53건] [항목 미분류 3건] [여행 미배정 20건] [보류·오류 30건]
                    (선택된 필터 칩은 강조, 나머지는 기본 배경)

선택: 여행 미배정 (20건)
[여행 미배정 거래 카드 1]
[여행 미배정 거래 카드 2] ...
[1/1 페이지 | 이전 | 다음]
~~~

- 세 기존 칩을 **실제 동작하는 필터 컨트롤**로 만든다. `전체 N건` 칩(또는 ‘전체 보기’ 동일 위치)을 추가해 한 번에 원래 목록으로 돌아올 수 있어야 한다.
- 기본 URL `/import`에서는 `전체` 선택. `항목 미분류` 선택 시 해당 항목만, `여행 미배정` 선택 시 해당 항목만, `보류·오류` 선택 시 해당 항목만 반환.
- 하나의 주된 필터만 선택하는 **단일 선택 방식**이다. 다른 칩을 누르면 기존 선택을 대체한다. 여러 칩 조합 검색이나 금융 상태를 바꾸는 액션이 아니다.
- 선택 시 URL에 `cleanup_reason`를 유지해 새로고침, 뒤로가기, 공유 가능한 내부 링크에도 같은 조회 조건 적용. 새 필터 선택 시 페이지를 **1로 초기화**하고 `#expense-cleanup`에 위치를 유지.
- 필터 변경 시 해당 카테고리의 **전체 건수**가 리스트 위에 표시되어야 한다. 상단 원래 총건수는 전체 미결 건수로 유지하되, “여행 미배정 20건 중 1~20건 표시”처럼 필터 결과와 구분한다.
- 선택 항목이 0건이면 “여행 미배정 거래가 없습니다”처럼 **선택한 이유에 맞는 빈 상태**를 표시한다. 다른 분류의 거래나 전체 목록을 빈 상태로 대체하지 않는다.
- 클릭 후 선택 강조, keyboard focus, `aria-current` 또는 `aria-pressed`는 HTML 요소 의미에 맞춰 하나만 일관되게 적용. 새로고침 후에도 현재 필터가 유지돼야 한다.
- 상태별 건수는 필터 선택과 무관하게 **전체 모집단 기준**으로 유지한다. 현재 첫 페이지만 세어 숫자를 바꾸면 안 된다.
- 각 칩의 레이블은 항상 `텍스트 + 숫자 + 건`을 포함한다. 숫자 0건 칩도 클릭·조회 가능하며 잘못된 disabled 의미를 주지 않는다.
- 기존 OTA 보류 검토 `<details>`와 지출 정리 상단 칩은 **별도 기능**이다. OTA snapshot 갱신이나 모든 OTA 자료 로드를 단순 칩 클릭의 부수효과로 발생시키지 않는다.

### 2.2 권장 컴포넌트·스타일

- 기존 공통 `site_shell`/디자인 토큰/버튼·필터 배지 스타일을 재사용한다. 페이지 전용 새 테마 토글, 임의의 아이콘, 하드코딩된 새 색상 팔레트 금지.
- `<nav aria-label="지출 정리 상태 필터">` 안의 `<a href="/import?cleanup_reason=no_trip#expense-cleanup">...` 형태를 **권장**한다. 서버 렌더링·페이지 전환과 궁합이 맞고 JS 실패·새로고침/뒤로가기에도 동작한다. 시맨틱 link에서 `aria-pressed`를 쓰지 않고 현재 항목에 `aria-current="page"` 또는 `aria-current="true"`를 준다.
- 클릭 결과가 같은 문서에서 동적 전환하도록 AJAX를 추후 도입할 수는 있으나, 이 경우에도 **서버가 필터링한 실제 결과**만 불러오고 URL/history/로딩·오류/중복 요청 경쟁을 보호해야 한다. 1차 범위는 GET 링크 기반을 우선한다.
- 모바일 320/375/390px에서 칩이 자동 줄바꿈되며 터치 영역 최소 44px, 키보드 포커스 테두리, 라이트·다크 대비 충족. 긴 한글 상태명이나 큰 글씨 200%에서 가로 넘침 없음.
- 선택 칩은 배경색만으로 의미를 전달하지 않고 `선택됨`의 접근 가능한 상태와 테두리/강조를 제공한다.
- 기존 카드의 `원본 충돌`, `파싱 오류`, `취소·환불 확인`, `환불 상쇄 확인`, `여행 배정 필요` 등 **개별 거래 상태 배지는 읽기 전용 사실 표시**로 유지한다. 상단 필터 칩과 거래별 금융 상태를 혼동하거나 거래별 보류 배지를 전부 클릭 버튼으로 바꾸지 않는다.

## 3. 정확한 상태 분류와 숫자 계약

### 3.1 하나의 정본 분류 함수

새 단일 함수(예: `_cleanup_card_reason_sql()` 또는 독립 `app/cleanup_reason.py`의 공통 상태 DTO)를 정의하고 **건수 계산 / 목록 조회 / URL 필터 / 저장 후 재조회**에서 같은 조건·우선순위를 사용한다. 동일 CASE를 쿼리마다 손으로 복사하지 말 것.

**카드 거래 우선순위** (현재 결과의 의미를 보존하되 잘못된 레이블은 교정):

1. `protected`: 취소 거래, 충돌, 파싱 오류, 존재하는 `transaction_review_holds` 및 별도 금융 보호가 실제로 입증된 경우.
2. `no_item`: 실제 검토할 카드 중 항목이 비어 있고 1번에 해당하지 않는 거래.
3. `no_trip`: 위 경우가 아니고 `display_tab_id`가 비어 있거나 `unclassified`인 거래. 기존 유효성 오류를 보호 상태로 분류하는 규칙은 **현재 금융 코어 권한**을 따른다.
4. `other_review`: 이미 항목/여행이 있지만 아직 기장·대사·사용자 확정으로 정리되지 않아 전체 검토 모집단에 남은 거래. **이 거래를 실제 HOLD나 오류라고 표시하지 않는다.**

**장부 비용 행:** `_cleanup_unassigned_where()`로 선별된 행은 `no_trip`. 이후 신규 유형이 추가되면 기존 명시 상태와 호환되는 공통 enum으로 확장한다.

- **상태별 합계는 서로 겹치지 않아야 한다**: `all_total = no_item + no_trip + protected + other_review`.
- UI에서는 먼저 기존 세 상태 칩을 유지하고, `other_review>0`이면 `기타 검토 N건` 칩을 추가해 **모든 거래가 반드시 접근 가능**하게 한다. 기존의 `보류·오류` 숫자가 실제 금융 보호가 아닌 거래를 포함한다면 수정된 상태 count에 따라 바뀔 수 있다. 그 차이는 위 분류 근거/테스트로 설명한다.
- 금융 규칙 자체를 변경하지 않는다. `no_item/no_trip`은 **분류/배정 입력 상태**이고, `protected`는 **실제 보호 상태**, `other_review`는 **기타 검토 대기**다. OTA 예약 연결 여부와도 다른 축이다.
- 동일 거래에 항목 부족+여행 부족이 함께 있을 수 있지만, 상단 칩은 대표 사유 하나만 보여주는 **배타적 검토 큐**다. 추후 다중 태그 필터가 필요하면 별도 승인/명세로 확장한다.
- `카드 원결제 + 취소`는 금융 코어에서 연결되었어도 **각 원행 ID를 임의로 삭제·합치지 않는다**. 단일 항목의 그룹/상태와 기존 보호 규칙을 지킨다.

### 3.2 필수 불변조건

- 기존 `_cleanup_card_where`의 복제, 회사거래 제외, 기장/수동결정 제외, 미기록 검사 조건을 보존한다.
- 카드 원본 `transaction_id`는 DISTINCT; 여러 `import_batch_rows`에 매핑돼도 중복 표시·중복 count 금지.
- `ledger_total`은 `no_trip` 카테고리에만 포함한다. 카드 no_trip과 장부 no_trip은 합산해 표시하되 내부 `kind`는 그대로 두어 기존 쓰기 API 사용을 유지한다.
- 실제 protected 카드가 no_item/no_trip 조건에도 해당하면 protected로 **한 번만** 센다.
- 이전에 미기록 전체에 포함된 정상 상태 카드가 분류 상 `other_review`이더라도 전체 목록에서 사라지지 않는다.
- snapshot stale/error·금융 미확정은 실제 확인된 상태와 구별하며 “보류가 없으니 기록 가능”처럼 판단하지 않는다.

## 4. URL/HTTP 및 서버 쿼리 계약

### 4.1 GET /import

| Query | 값 | 동작 |
| --- | --- | --- |
| `cleanup_reason` | `all`(기본), `no_item`, `no_trip`, `protected`, `other_review` | 해당 분류의 전체 후보 중 현재 페이지 20건 |
| `cleanup_page` | 양의 정수, 기본 1 | 현재 선택 필터 내 페이지 |
| `#expense-cleanup` | URL fragment | 필터 컨트롤과 목록 위치 유지, 서버 입력 아님 |

예시:
- 전체: `/import#expense-cleanup`
- 항목 미분류: `/import?cleanup_reason=no_item#expense-cleanup`
- 여행 미배정 2페이지: `/import?cleanup_reason=no_trip&cleanup_page=2#expense-cleanup`
- 보류·오류: `/import?cleanup_reason=protected#expense-cleanup`

**검증:** 쿼리 필드는 enum allowlist; 악의적인 SQL/임의 문자열/매우 긴 입력은 허용하지 않는다. 잘못된 값은 400 오류 또는 안전한 `all` 복귀를 **명시적으로 결정하고 테스트**한다. 예측 불가 URL을 만든 채 화면에 다른 필터가 적용되는 모호한 상태는 금지. `cleanup_page`는 상한·정수 변환·음수/초대형 숫자에 대한 안전한 처리. 모든 데이터 조회는 기존 owner-only 접근 제어를 그대로 따른다.

### 4.2 서버 계산

**비권장 구현:** 전체 53건 혹은 수천 건을 한 번에 가져와 DOM `display:none`, `data-reason`만으로 필터링하는 방식, 20건 페이지에서 먼저 slice 후 현재 20건만 상태 분류하는 방식. 둘 다 전체 데이터 접근·페이지 정확성·성능이 잘못된다.

**권장**:
1. 기준 모집단의 card/ledger SQL selector를 재사용한다.
2. 카드 각 거래의 대표 분류 `reason`을 **공통 CASE/DTO 한 곳**에서 결정한다.
3. `counts`는 전체 모집단에서 `GROUP BY reason`으로 계산한다. `all_total`과 합계가 항상 같다.
4. 선택한 `cleanup_reason`으로 DB 서버에서 필터링하고 `COUNT(*)`와 `LIMIT 20 OFFSET ?`를 적용한다. `DISTINCT transaction_id`와 기존 stable sort (카드일자 DESC+거래 ID; 장부 일자 DESC+row ID) 보존. 카드+장부가 혼합된 `no_trip`도 한 페이지당 정확히 최대20건.
5. 카드/장부의 현재 목록 순서(기존 카드 먼저, 이후 장부)를 명확히 보존하거나 결정적 통합 정렬을 별도 테스트로 확정한다. 임의 sqlite 비결정 순서는 금지.
6. 상세 OTA 근거, 원결제/환불 분석, `flow.pipeline.preview`는 **선택된 페이지의 카드 ID만** 대상으로 조회한다. 필터·페이지 클릭 때문에 전체 OTA 대사/상세 이벤트 전체 읽기가 일어나면 불합격.
7. `nav 이전/다음` URL은 `cleanup_reason`과 `#expense-cleanup`을 항상 보존한다. 다른 카드 상세·파일 업로드·여행 조회 링크는 불필요한 필터 파라미터를 덧붙이지 않는다.
8. 상태 개수와 같은 순간의 목록을 계산하는 동안 일관된 읽기 snapshot/트랜잭션을 활용해 count/list 불일치 가능성을 낮춘다. 쓰기 권한이나 금융 코어의 기존 locking 순서를 무턱대고 변경하지 않는다.

**성능 목표:** 필터링에 의해 기존 첫 화면 20건 로딩·OTA 지연 조회 특성이 유지되고, 1페이지의 카드 상세 분석 수가 현재 전체 보기보다 증가하지 않음. 실제 p50/p95, SQL `EXPLAIN QUERY PLAN`, 100건/1만건 합성 응답 크기 비교를 기록한다. 병목 측정 없이 임의 인덱스를 운영 DB에 추가하지 않는다.

## 5. 저장/재분류 후 카운트·목록 최신성

기존 `CLEANUP_SCRIPT`는 성공 시 `item.remove()`와 전체 count 감소만 수행한다. 필터 구현은 여기까지 반드시 보완한다.

- 저장 성공 시 해당 거래의 **서버 권위 분류**가 바뀌었는지 확인한다. 가장 단순하고 안전한 1차 구현은 성공 뒤 `/import?cleanup_reason=<current>&cleanup_page=<current>#expense-cleanup`을 새로 GET해 count/페이지를 **정확히 재계산**하는 것이다. 이때 이미 처리한 항목이 없어진 마지막 페이지는 유효한 이전 페이지로 이동한다.
- 낙관적 DOM 제거를 유지하려면 같은 트랜잭션을 두 번 세지 않고 전체/상태별 count를 최신 서버 GET으로 동기화하고 현재 필터의 빈 페이지를 재채우는 동작까지 구현해야 한다. 서버 재조회 없는 숫자 임의 감소는 불합격이다.
- 저장 API의 revision·CSRF·멱등성·권한·보류/환불 보호 규칙을 **변경하지 않는다**. 필터 칩 클릭은 어떤 POST도 수행하지 않아야 한다.
- 새로고침/뒤로가기/다른 필터 선택·저장 후 필터 유지, stale revision·409·500 처리, 요청 중 버튼 중복 동작 및 focus를 검증한다.
- OTA 진행 중/오류/신선도 부족은 카드 UI에서 기존대로 표시한다. 목록 상태 필터가 금융 보류를 해제하거나 “원결제 상쇄 = 실제 환급 완료”로 변환하지 않는다.

## 7. 필수 테스트 매트릭스

### 7.1 데이터/필터

1. 화면 예시 53건(3/20/30)의 **합성** DB. 전체=53, `no_item`=3, `no_trip`=20, `protected`=30, page20. 각 칩 GET의 실제 `data-kind/data-transaction/data-row-id` 집합이 기대 사유와 정확히 같음. 동일 분류가 카드/장부 양쪽에 있으면 합산.
2. `item`과 `display_tab_id`가 둘 다 없지만 보호 사유가 없는 카드 → `no_item` 한 번만; 보류 사유까지 있으면 `protected` 한 번만.
3. `board_rows` 미배정 7 + 카드 미배정 13 → `no_trip`=20. 장부의 수동 교정 행은 기존 exclude 규칙대로 제외.
4. 카드의 `item` 및 `trip`이 있는데도 다른 검토 사유로 미기록 → `other_review`; `protected`로 거짓 표기하지 않음.
5. 한 거래가 여러 `import_batch_rows`에 연결돼도 count/list에서 1건만.
6. 서로 다른 상태 필터 각각 0건인 경우에도 전체 결과/분모/빈 화면 정확.
7. 취소/부분환불/초과환불, 이미 분류된 OTA, inference stale, 승인번호 없는 카카오, 사용자가 수동 설정한 trip을 보호하고 **필터 클릭이 데이터에 쓰지 않음**.

### 7.2 URL·페이지

8. `/import` = `cleanup_reason=all`; `?cleanup_reason=no_trip`은 1페이지에서 해당 20건 이내만.
9. `?cleanup_reason=protected&cleanup_page=2`의 이전/다음 링크가 필터를 보존. URL 뒤로가기·새로고침 시 같은 선택.
10. 필터 변경 시 기존 `cleanup_page=3`이 있더라도 1페이지부터. 마지막 항목을 저장했을 때 존재하지 않는 페이지로 고립되지 않음.
11. SQL injection용 문자열, 특수문자, page=-1, page=0, page=999999999 등 처리 안전. 로그인/owner 권한 그대로.
12. 상세 예약/OTA 내용을 클릭하지 않았는데 단순 필터 전환으로 전체 메일 재파싱·대사 백그라운드 강제 재실행·전체 OTA 상세 페이지 요청 0.

### 7.3 브라우저·디자인·저장

13. 세 버튼+전체/조건부 기타가 실제 `<a href>`(또는 접근 가능한 button)이며 Tab/Enter·포커스·현재 상태로 작동. 기존 `<span>`-only 화면으로 회귀하지 않음.
14. 320/375/390/760/1024/1440px, 라이트/다크, 200% 확대에서 가로 넘침·버튼 겹침 없음; 클릭 영역 최소44px.
15. 카드/장부 저장 후 전체/필터 숫자 갱신, 처리된 거래 재등장 없음, 다음 항목 노출 정상.
16. 보호된 거래의 분류 상태가 필터 전환에 의해 저장/해제되지 않으며 환급 완료로 표시되지 않음.
17. 기존 카드 파일 추가·자료별 상세 검토 `<details>`와 OTA 검토 `<details>`의 접힘 상태, 상단 메뉴/단일 테마 버튼, GET/POST 데이터 경로 회귀 없음.
18. 비용/여행 선택, 오류 문구, preview revision과 금융 보호 API에서 구형 카드 동작과 출력 계약 동등.
