# 하나카드 해외 이중수입 수정·정리 사본 예행 (2026-11-13)

정책: [SRC-005·SRC-009·SRC-013](../../policy/source.md). 운영 원본(`D:/WebLedgerHost/data/board.sqlite`)은 `mode=ro`로만 읽고, SQLite backup으로 만든 별도 사본에서만 예행했다. 원문·금액·개별 거래 식별값·가맹점·승인번호는 이 보고서에 없다(건수·비율만).

## 원인

하나카드 해외 구매가 두 번 수입되어 두 번 장부되었다. 매입 원본 뷰(`xls:hana_foreign`, 청구금액)와 승인 출처 다운로드(`csv:headered`/`xls:headered`, 승인금액)가 같은 승인번호를 서로 다른 앞자리 0으로 패딩한다(`00102256` 대 `102256`). `app/card_export_profiles.py`의 `existing_purchase`가 (1) 승인번호를 **원문 문자열 그대로** 비교하고 (2) 교차 뷰 매칭을 `hana_usage`·`hana_foreign`·`ibk_print` 레이아웃으로만 제한해서, `headered` 승인 출처 행은 매칭되지 않고 별개의 깨끗한 거래로 삽입·장부되었다. 금액은 승인 시점 원화 대 청구 원화(환율·수수료 차이)라 서로 다르지만 같은 구매다.

## 수정 (비교 전용 정규화)

- `app/normalize.py`에 `normalize_approval_number` 추가: 앞자리 0 제거, 전체 0·공백은 빈 키(매칭 불가). **저장 원문은 바꾸지 않는다.**
- `existing_purchase`가 정규화 키로 비교(`LTRIM(approval_number,'0')`)하고 `headered`+`하나`를 교차 뷰 매칭에 포함. 다른 발급사 `headered`는 그대로 제외.
- 금액 배수 가드(0.5~2.0배): 승인번호 재사용으로 인한 서로 다른 구매가 원본 충돌로 잘못 합쳐지지 않게 별개로 유지.
- 같은 구매가 두 번 장부되지 않는다(두 번째 뷰는 원본 충돌로 보호). 저장된 원문 승인번호·금액·부호·ID는 그대로.

## 정리 도구

`app/card_hana_duplicate_repair.py` (`python -m app.card_hana_duplicate_repair`). 카드 원본 행을 삭제하지 않고 기존 `duplicate_of` 구조로 승인 출처 행을 매입 행의 중복으로 표시하며, 열린 분기는 그 행의 장부·화면 투영만 제거해 한 번만 합산한다. 매입 원본(해외 청구금액)을 금융 정본으로 유지(SRC-005·SRC-009). 닫힌 분기(2025·2026 Q1·Q2, 세무사 제출 완료)는 표시만 하고 장부 금액을 바꾸지 않는다. 환불 짝·수동 교정·원본 보호 쌍은 옮기지 않고 사유별로 보고한다. 구조는 `closed_period_repair`와 같이 미리보기/digest/신선 백업·복원 게이트/단일 작성자 확인/감사 원복/재실행 변경0.

## 운영 반영 명령 (헤드 세션 수행)

병합·배포·운영 반영은 이 작업에서 하지 않았다. 운영 반영은 단일 작성자 정지 후 신선 백업·복원 검증 증거를 갖추고:

```
python -m app.card_hana_duplicate_repair --host-root D:/WebLedgerHost --request-id hana-double-import-20261113
python -m app.card_hana_duplicate_repair --host-root D:/WebLedgerHost --request-id hana-double-import-20261113 --apply --expected-digest <미리보기 digest> --backup-evidence <신선 증거 JSON>
```

원복은 `--restore`(미리보기) 후 `--restore --apply --expected-digest <원복 digest> --backup-evidence <신선 증거>`. 사본 예행 산출물은 `D:/WebLedgerHost/data/backups/hana-double-import-20261113/`에 있다.
