<a id="src-docs-target-workflow-google-authority-md--1-제품-목적과-최종-권위--확정"></a>
#### 1. 제품 목적과 최종 권위 — 확정

COST의 주목적은 **법인카드 지출 및 현지 영수증을 자동 추출·대사·분류하고, 사용자가 확인해 Google 스프레드시트에 그대로 복사·붙여넣을 수 있는 지출표를 완성하는 것**이다.

- **Google 스프레드시트가 여행별 수입·지출·결산에 대한 유일한 최종 회계 정본(source of truth)**이다.
- 사용자는 Google의 기존 여행별 시트를 계속 직접 관리하며, 최종 반영·수정·결산 마감의 주체다. COST는 Google에 회계 행을 자동 쓰기 하지 않는다.
- COST의 웹 지출표는 **Google 반영 전 작업물**이다. 준비·검토·복사를 모두 끝내더라도 Google에 기록됐다는 의미는 아니다.
- COST가 제3자에게 보여 주는 **확정 장부/최종 결산 화면은 Google을 읽어서 구성**한다. 아직 Google에 없는 지출 후보를 확정 실적으로 합산하지 않는다.
- **신규 여행 시트의 공식 기준은 메인 Google 장부의 `매출자료 양식_rev` 하나**이다(사용자 확정, 2026-10-11). 이 양식의 상단 수입/하단 지출과 열 순서·합계 수식을 유지한다. 과거 다른 레이아웃은 사용자 직접 수정 예정인 구형 잔재이며, 별도 호환 구현이나 자동 변환을 하지 않는다. 실제 열 계약/수식은 [실측 문서](google-ledger.md#src-docs-google-workbook-layout-md)를 따른다.
- Google은 영수증 이미지 저장소, 카드 raw transaction DB, AI 규칙 엔진, 검토 작업 DB가 아니다. 이런 비정본 데이터는 적절한 별도 저장소에 둔다.

##### 입력 방향의 비대칭 — 절대 뒤집지 않는다

| 회계 데이터 | 최초 작성·분류 | COST와 Google 사이 흐름 | 최종 권위 |
| --- | --- | --- | --- |
| **수입** | 사용자, Google 시트 **상단**에 직접 입력 | **Google → COST** 읽기 전용 | Google |
| **은행 이체 지출** | 사용자, Google 시트 지출 영역에 직접 입력; 증빙내용 **이체** | **Google → COST** 읽기 전용 | Google |
| **법인카드 지출** | 법인카드 매입 raw → COST 대사·분류 → 웹에서 사용자가 완성 | **COST → 복사 → 사용자 → Google**, 이후 Google → COST 조회 | Google |
| **현지 현금 영수증** | A4 다중 영수증 업로드 → OCR → COST 분류·검토 | **COST → 복사 → 사용자 → Google**, 이후 Google → COST 조회 | Google |
| **현지 개인카드 영수증** | 영수증 OCR → COST 분류·검토; 회사 비용 인정 여부는 사용자 결정 | **COST → 복사 → 사용자 → Google**, 이후 Google → COST 조회 | Google |
| **현지 법인카드 영수증** | 영수증 OCR 후 기존 법인카드 매입과 대사 | **기존 카드 지출 한 건**으로 통일; 영수증은 증빙으로 연결 | Google 카드 지출 기재 |

**중요:** COST의 카드 대사는 은행 이체를 수집하거나 자동 대사하는 기능이 아니다. 은행 이체는 사용자가 Google에 직접 쓰는 예외적 지출 경로다. **개인카드 경비를 회사에서 계좌이체로 사후 상환하더라도 사용자가 Google 기존 지출 내역을 직접 확인하고 중복 기입을 피한다(2026-10-11 사용자 확정).** COST가 개인카드 영수증과 상환 이체를 자동 대사·상계·수정하거나 별도 정산 기능을 만드는 것은 요구 범위 밖이다.

<a id="src-docs-target-workflow-google-authority-md--2-배치조회작업-구조--확정된-요구--배포는-계획"></a>
#### 2. 배치·조회·작업 구조 — 확정된 요구 / 배포는 계획

<a id="src-docs-target-workflow-google-authority-md--목표-컴포넌트"></a>
##### 목표 컴포넌트

1. **로컬 Windows PC**: 법인카드 XLS/CSV 및 보존 OTA 근거의 원본, 카드 중복·취소·환불·여행 귀속 검사, 분류 규칙과 AI 처리기. 원본 고객/카드 자료를 로컬에 유지하는 것이 기본 원칙.
2. **Render 상시 웹서버(목표)**: 로그인·권한, 카드·영수증 지출 검토 UI, 규칙 수정 메시지·대기 상태, Google에 복사할 지출표, Google 정본 읽기/제3자 확정 장부 표시. Render 이전은 **아직 승인·구현·배포 완료가 아니다**.
3. **Google 스프레드시트**: 사용자가 직접 작성하는 수입·이체 지출과, COST 검토 후 사용자가 붙여넣는 카드·영수증 지출의 최종 정본.

<a id="src-docs-target-workflow-google-authority-md--주기"></a>
##### 주기

- **Google 정본 읽기: 매시 정각(Asia/Seoul, 분 00) 1회**를 희망한다. 읽기 전용이며 Google 데이터 변경이 없으면 파싱·캐시 갱신·DB 쓰기를 불필요하게 반복하지 않는다. 실패하면 마지막 정상 스냅샷과 확인 시각을 표시하고 빈 장부로 덮어쓰지 않는다.
- **로컬 원본 수집/갱신:** 사용자는 매일 00:00 KST 1회를 희망한다. **현재 어떤 로컬 작업이 주기적으로 실행되는지는 미확인**이므로 실제 scheduler·파일 수집·OTA 스냅샷 지문 확인·웹 폴링을 조사한 뒤, 안전하게 늦출 수 있는 **원본 수집 작업만** 대상으로 결정한다.
- **로컬 AI 자연어 수정 요청:** 일일 배치와 독립적으로, 사용자 요청 시 응답 가능한 구조가 목표. 로컬 PC가 오프라인이면 대기·재개로 표시하며 작업이 성공했다고 주장하지 않는다.
- **사용자 수동 카드 업로드·웹 검토·원본 저장·보안 검사·결산 화면**을 자정까지 대기시키거나 서버를 하루 한 번만 켜는 구조로 바꾸지 않는다.
- Render로 이전해도 로컬 원본을 직접 읽을 수는 없다. 로컬 PC가 허가된 인증 채널을 통해 **검토에 필요한 최소 후보 필드만** 동기화하는 방법을 검토한다. 실제 원본이나 비밀값의 무단 외부 전송은 금지한다.

<a id="src-docs-target-workflow-google-authority-md--읽기쓰기-경계"></a>
##### 읽기·쓰기 경계

- Google → Render: **읽기 전용** (수입 + 사용자가 기입한 은행 이체 + 붙여넣기 완료 지출 + 여행별 결산).
- COST → Google API: **자동 쓰기 금지**. 복사 기능은 사람의 클립보드/붙여넣기 동작일 뿐.
- 로컬 → Render: 검토용 지출 후보/규칙 결과/상태를 인증·최소필드로 제공. 어떤 개인정보·원본 세부 필드가 필요한지는 별도 확정.
- Render → 로컬 AI: 규칙 수정 요청 전달 및 제안 결과 수신. 로컬 PC의 인터넷 포트를 임의 공개하지 않고 인증된 연결/작업 조회 방식으로 구성; 구체적 기술 선택은 구현 전 검증.

<a id="src-docs-target-workflow-google-authority-md--3-카드-지출-기존-안정화된-기능을-활용--확정"></a>
#### 3. 카드 지출: 기존 안정화된 기능을 활용 — 확정

- 법인카드의 **국내·해외 매입 확정 자료**만 회계 비용 근거다. 승인내역은 비용이 아닌 보조 증거다.
- 승인·매입이 겹치거나 동일한 파일을 다시 받아도 비용을 중복 계상하지 않는다.
- 지연 매입, 승인 취소와 매입 취소, 부분 환불, 완전 취소, 실제 다중 결제를 구별한다. 해외 카드의 실제 청구 KRW 원금·수수료·합계를 보존하고 영수증 고정 환율로 덮어쓰지 않는다.
- 검증된 OTA·여행 일정 권위와 사용자 확정을 보존한다. 모호한 귀속은 HOLD하며 원문 날짜·금액·거래 ID를 규칙으로 변경하지 않는다.
- 화면에서 웹 사용자가 **가맹점/항목/설명/여행 귀속/증빙 구분**을 검토하고 재사용 가능한 규칙의 적용 범위를 승인한다.
- 사용자 수정은 원본 변조가 아니라 **분류·귀속·회계 표시 결정**이다. 금액 일부만 비용 처리하는 사례는 원본을 그대로 보존하고 별도 회계 조정·사유·결정으로 취급한다.
- **사용자 확정(2026-10-11): C열 `항목`은 가맹점·결제처·지급처이고, D열 `내용`은 숙박비·항공료·식비 등 비용 분류**다. 규칙 적용/복사 출력에서도 두 값을 혼동하지 않는다.
- **사용자 확정(2026-10-11): 지출표는 실제 거래 한 건당 한 행으로 출력한다.** 같은 가맹점·비용 항목·날짜·금액을 공유해도 서로 다른 실제 거래는 합산/병합하지 않는다. 원결제와 별개로 발생한 취소·환불도 임의로 상계해 행을 없애지 않는다. 승인 증거는 지출 행이 아니며, 법인카드와 중복되는 영수증은 카드 거래 하나만 대표 지출로 출력하고 영수증은 증빙에 연결한다. 중복 업로드는 기존 멱등성 규칙을 따른다.
- 최종 출력은 공식 `매출자료 양식_rev`의 **B:H 지출 7열(거래일자·항목·내용·기간·예약번호·증빙유형·금액(원))** 계약을 따른다. **현재 여행/구간의 검토가 끝난 지출만** 선택해 TSV 등 다중 셀 붙여넣기 가능한 형태로 복사한다. 구형 B:I 비연속 양식에는 복사를 지원한다고 주장하지 않으며 사용자가 템플릿으로 정비한다.

- **새 목표 구조로 이전했다는 증거가 아니며**, 현행 SQLite 운영 정본의 과거 데이터·사용자 결정·환불·OTA 연결을 삭제/재작성할 근거도 아니다.

#### 4. 현지 영수증(A4 다중 OCR) — 신규 기능 요구 확정

<a id="src-docs-target-workflow-google-authority-md--입력과-원본"></a>
##### 입력과 원본

- 주된 대상은 **일본 현지 영수증**이다. 사용자가 **A4 한 장에 여러 장의 종이 영수증을 붙여 촬영/스캔**하여 업로드한다.
- 한 이미지/PDF 안의 **서로 다른 영수증을 자동 감지·분리**하여 개별 비용 후보로 만든다. 잘렸거나 겹쳤거나 경계가 불명확하면 사용자에게 분리/확인을 요청하고 누락 또는 중복 생성하지 않는다.
- 영수증별로 가능한 범위에서 **상호명, 일자, 최종 결제금액, 통화(JPY), 결제수단, 원본 이미지 위치**를 인식한다. 영수증의 합계/현금 지급/거스름돈/세금/할인/취소를 구별한다.
- OCR 신뢰도가 낮거나 총액이 불명확하면 HOLD. 개별 물품 목록 전체를 자동 비용 행으로 쪼개지 않는다(별도 사용자 지시가 없으면 **영수증 한 장당 비용 한 건**).
- 원본 이미지와 추출 텍스트/원화 환산값을 구분해 보존한다. 이력/재처리 시 같은 이미지를 다시 입력해도 중복 후보가 증가하지 않아야 한다.
- OCR 엔진·비용·개인정보 보관/학습 정책은 **미확정**. 별도 허가 없이 영수증 이미지나 개인정보를 외부 무료 AI/OCR 서비스로 전달하지 않는다.

<a id="src-docs-target-workflow-google-authority-md--결제수단과-중복-대사"></a>
##### 결제수단과 중복 대사

사용자가 예상한 월별 법인카드 중복은 **1~2건 수준**이다. 복잡한 자동 매칭 엔진을 새로 만들지 않는다.

- **현금(대부분):** 독립 영수증 지출 후보. 최종 Google 증빙내용 **영수증**.
- **개인카드(일부):** 사용자가 회사 경비로 인정하면 독립 영수증 지출 후보. 최종 Google 증빙유형 **영수증**. 나중에 상환 이체가 발생하더라도 **Google에 이미 기록한 경비와 중복되지 않는지 사용자가 직접 확인하고 기입 여부를 결정**한다. COST는 상환 이체의 자동 중복 탐지·대사·제외·상계 기능을 만들지 않고, Google의 수입·이체 지출은 그대로 읽기 전용으로 다룬다.
- **법인카드(일부):** **기존 법인카드 매입 거래가 대표 지출**, 영수증은 그 거래의 증빙/설명으로 연결한다. 카드 원화 청구액을 최종 금액 기준으로 사용하고 영수증의 단순 JPY 환율 금액을 추가 비용으로 기록하지 않는다. 매입 미도착, 후보 복수, 불일치 때는 HOLD.
- **결제수단 불명:** 함부로 현금/법인카드라고 확정하지 않는다. 사용자가 확인한다.

법인카드 거래의 날짜·상호·현지 통화·원금액·카드 여부를 참고하되 **유일성이 확보되지 않은 후보를 자동 병합하지 않는다**. 이 기능은 드문 중복을 사용자에게 보여 주고 정리하는 가벼운 경로여야 한다.

<a id="src-docs-target-workflow-google-authority-md--환산-간편한-내부-장부-작성-규칙"></a>
##### 환산: 간편한 내부 장부 작성 규칙

- **JPY 100엔 = KRW 1,000원**. 즉 내부 표에 복사할 금액은 **엔화 1엔당 원화 10원**이다.
- 적용 대상은 현금 및 사용자 승인 개인카드 **영수증 기반 경비**다. 엔화 원본 금액과 적용 환율(10 KRW/JPY), 산출 원화 금액을 각각 보존한다.
- **법인카드의 확정 청구 KRW는 카드 매입을 따르며 고정 환율을 적용하지 않는다.**
- 이 환율은 사용자가 정한 **간편 장부 환산 기준**이지 카드사 청구액·세무상 법정환율을 뜻하지 않는다.
- 원 단위 반올림/소수 엔화 처리 및 실제 세무 신고 사용 가능 범위는 별도 확인이 필요하다.

<a id="src-docs-target-workflow-google-authority-md--5-지출-검토-ui--로컬-ai에-자연어로-규칙-수정-요청--목표"></a>
#### 5. 지출 검토 UI + 로컬 AI에 자연어로 규칙 수정 요청 — 목표

- 여행별 지출 검토표는 **메인의 `매출자료 양식_rev`의 지출 7개 열과 동일한 의미·순서·표시 형식**으로 제공한다. 과거 레거시 양식의 서로 다른 열 배치까지 별도 지원하지 않는다.
- 각 지출 행에서 사용자가 **자연어 메시지**를 작성해 로컬 PC의 응답 가능한 AI에게 보낸다.
- 예: “이 편의점 결제는 식비가 아니라 현지 잡비야. 앞으로 같은 가맹점은 그렇게 분류해 줘.”
- AI는 허용된 규칙 스키마와 현재 사용자 결정/원본 근거를 조회해 **(a) 현재 거래만 수정, (b) 기존·미확정 거래에 적용할 재사용 규칙, (c) 추가 확인 필요**를 구분한 **제안**을 만든다.
- 사용자는 변경 전·후 및 **영향받을 거래/여행/금액**을 미리 본 후 명시적으로 적용한다. AI가 임의로 원본 카드 내역·구글 시트·확정된 거래를 변경하지 않는다.
- 같은 상호라는 이유만으로 임의 여행 전체를 자동 귀속하지 않는다. 원본 금액/일자/ID 변경 명령은 거부하거나 별도 표시 조정으로 안내한다. 기존 사용자 확정 우선.
- 적용 승인 후 영향을 받는 **미확정 지출표만** 다시 계산한다. 이미 한 번 통과한 전체 KB 대사·OTA 회귀는 반복하지 않는다.
- 로컬 PC/AI가 꺼져 있으면 메시지를 보존하고 **대기**로 표시한다. 외부 무료 모델로 임의 폴백하지 않는다.
- 로컬 AI가 실제 **로컬 추론 모델**인지, 로컬 PC에서 동작하는 클라우드 코딩 에이전트인지, 연결·호출·인증 방식은 아직 확인되지 않았다. 이와 무관하게 개인정보 최소 전달·명시적 승인·감사 이력은 유지한다.

<a id="src-docs-target-workflow-google-authority-md--6-google-복사붙여넣기-계약과-최종-웹장부--확정미확정-구분"></a>
#### 6. Google 복사/붙여넣기 계약과 최종 웹장부 — 확정/미확정 구분

> **2026-10-25 추가 제품 명세:** [0630_오제 수입 표시 진단 및 Google 기존 장부↔COST 웹 장부 지출 거래 볼드 강조](google-ledger.md#src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md). 같은 여행·동일 금액(부호/통화 포함) + 날짜/가맹점/분류/예약번호 하나 이상 일치 시 **웹 장부 행을 볼드 표시**한다. 이는 화면 대조 후보이지 Google 반영 확정·중복 병합 증명이 아니다. 수입/지출 검증 독립 표시 및 원인 진단도 해당 명세를 따른다. 아직 미구현이다.


<a id="src-docs-target-workflow-google-authority-md--복사-전"></a>
##### 복사 전

- 대상 여행과 지출 행, 총 건수·합계·원화 단위를 명확히 표시한다.
- **`매출자료 양식_rev`를 기반으로 신설·정비된 여행 시트의 지출 데이터 영역**으로 복사한다. 수식·합계·기존 수입·수기 이체 행은 침범하지 않는다. 대상 시트가 아직 레거시 양식이면 무리한 복사를 허용하지 않고 기준 템플릿 정비를 안내한다.
- 카드/영수증 구분과 시트 실제 증빙내용 값을 표시한다. **이체는 Google 수기 입력만**, **영수증은 현금/개인카드 기반 최종 증빙 표기**. 카드 지출의 기존 증빙 표기값은 실제 시트 확인 전까지 정하지 않는다.
- Google에 붙이기 전 규칙 수정과 지출 검토를 최대한 끝내어 Google 내 사후 수정·삭제를 최소화한다.

<a id="src-docs-target-workflow-google-authority-md--복사-후"></a>
##### 복사 후

- 복사 버튼 클릭 또는 사용자의 “붙여넣기 했음” 표시는 **Google 기록의 독립적 증명이 아니다**.
- 다음 Google 읽기에서 확인할 수 있는 **행/항목/금액/건수/합계**로 실제 반영 상태를 판단한다. 원본 거래 ID가 Google에 없으면 동명이액·삭제·재정렬·직접 수정이 결합된 경우 **1:1 거래 동일성을 입증할 수 없으므로 UNKNOWN/HOLD**한다.
- Google에 기입된 금액과 COST 원본 카드 금액이 다른 경우, 원본을 고치거나 조용히 역동기화하지 않는다. 사용자가 Google에서 수정한 최종 장부가 회계 정본이며 불일치를 표시한다.
- **여행 마감 완료는 여행 시트를 메인 Google 장부에서 보관 Google 장부로 이동한 시점으로 판정한다**(사용자 확정, 2026-10-11). 정상 동기화에서 보관본의 해당 실여행 탭이 확인되면 마감 완료이며, 메인에만 남은 여행은 종료일이나 장부 내 결산 수식 존재 여부와 무관하게 미마감이다. 여행 식별이 불확실하면 임의로 마감 처리하지 않는다. **동일 여행이 활성 메인과 보관 장부에 동시에 존재하면 마감 상태는 완료이며, 금액 정본은 메인을 기본 선택하고 `확인 대상`으로 표시한다**(사용자 확정, 2026-10-11). 사용자가 두 사본의 내용을 비교해 정본 선택을 수동 조정할 수 있어야 한다. 어떤 경우에도 수입·지출을 중복 집계하지 않고 **선택된 한 사본만** 조회·집계하며, 사용자 선택·수정 이력을 보존한다. 다른 사본은 비교·검토 자료로 보존하고 양쪽 일치 검증 완료로 속이지 않는다. COST가 Google의 어느 사본도 자동 수정하지 않는다. [장부 구조 및 중복 원본 규칙](google-ledger.md#src-docs-google-workbook-layout-md)을 따른다.
- Google 원본이 읽히지 않으면 마지막 정상 시각과 **동기화 지연**을 표시한다. 최신 장부라고 속이지 않는다.
- **결산 완료 여행**은 Google 여행 시트의 확정 수입·지출 행 및 계산된 합계를 COST 확정 장부 화면에서 일치시켜야 한다. 단순 합계만 맞는 것으로 성공 처리하지 않는다.
- Google 시트 마감 후 변경이 감지되면 웹에서도 마감 당시와 달라진 사실을 표시한다. 자동 재마감·자동 삭제·Google 쓰기는 하지 않는다.

<a id="src-docs-target-workflow-google-authority-md--웹장부의-두-화면상태를-섞지-않는다"></a>
##### 웹장부의 두 화면/상태를 섞지 않는다

1. **지출 작성·검토 작업 공간:** 아직 Google에 붙여넣지 않았거나 붙여넣기 확인 전인 카드·영수증 후보; AI 규칙 수정 가능.
2. **최종 장부/권한별 조회:** **Google에 실제 존재하는 수입·이체·카드·영수증 지출**과 결산을 표시하되, **기본은 owner 본인만 전체 열람**, owner가 승인한 계정은 **계정별 허용 여행만 읽기 전용**으로 제공한다.
3. **비로그인 공개 데모 — 사용자 확정(2026-10-11):** 인터넷 일반 방문자가 **로그인 없이** 열람할 수 있는 별도 데모 페이지를 제공한다. **마감 완료가 확인된 실제 여행 중 Google 확정 회사수익 금액 상위 3건**을 **성공한 Google 정본 동기화 시마다 자동으로 재선정**해 이름·닉네임 등 개인정보를 서버에서 제거하고, 실제 수입·지출·순수익 금액을 보여 준다. 두 장부의 메인 우선/수동 정본 조정과 중복 방지 규칙을 반영하며, 동기화 실패 시 잘못된 새 순위로 갱신하지 않는다. 새로 선정된 여행도 공개 전에 같은 서버 측 익명화 검증을 통과해야 한다. 원본 Google/owner·viewer API 접근은 인증 없이 허용하지 않는다. **마감 판단은 정상 동기화로 확인한 보관 Google 장부의 해당 실여행 탭 존재를 기준으로 하며, 단순 종료일이나 이름이 유사한 사본으로 마감 완료를 추정하지 않는다.** 같은 여행이 두 파일에 동시에 있으면 마감 완료 + 메인 정본 우선 + 확인 대상 정책을 함께 적용한다. 이 문서의 요구 확정은 실데이터 게시·배포를 뜻하지 않는다. 세부 명세는 [접근제어·데모 정책](google-ledger.md#src-docs-access-and-top3-demo-md)을 따른다.

예상 손익 계산에 아직 Google에 없는 미반영 지출을 포함한다면 **예상**이라고 별도 명시한다. 확정 순수익과 섞지 않는다.

<a id="src-docs-target-workflow-google-authority-md--7-안전복구인프라-제약"></a>
#### 7. 안전·복구·인프라 제약

- 현재 운영 DB는 로컬 SQLite **D:/WebLedgerHost/data/board.sqlite**로 설계돼 있고, 장부 수정/환불/사용자 확정/OTA 링크를 보존한다. **Google이 정본이 되는 것은 목표 구조 변경**이지 기존 SQLite 파일을 즉시 삭제하라는 뜻이 아니다.
- 목표 Render 서버는 24시간 접근을 지원하되, 이행 전에는 코드의 Linux 이식성, 지속 저장소, 예약 작업, OAuth 콜백, 시트 읽기 권한, 파일 의존성, 백업·복구, 비용/보존 정책, 개인정보/국외 이전을 조사한다. 서비스 규모에 맞춰 단순 구조를 우선하며 PostgreSQL 재작성은 기본 요구가 아니다.
- Render에 저장할 후보 필드와 이미지/고객정보/원본의 전송 범위를 정하기 전에는 실제 자료를 업로드하지 않는다.
- 원본 파일, 운영 DB, 비밀값, 사용자 결정, OTA 정확 연결과 환불 관계를 임의 삭제·초기화·덮어쓰지 않는다.
- 기존 역할을 바꾸는 작업은 **코드 변경+데이터 migration**으로 오해하기 쉽다. Google 권위로 전환하기 전에 현재 ledger_entries/board_rows와 Google 정본의 차이를 먼저 인식해 충돌 전략을 승인받는다. 양방향 자동 쓰기/무작정 일괄 재계산 금지.
- 문서만 고치면 코드 테스트/배포/운영 재시작을 하지 않는다. 코드 수정은 AGENTS.md의 표적 검증 최소화 원칙을 따른다.
- 사용자에게 확인받지 않은 “추정 시트 구조”나 “완료된 Render 배포”를 사실로 보고하지 않는다.

<a id="src-docs-target-workflow-google-authority-md--8-우선순위와-구현-경계--제안사용자-승인-전-자동-착수-금지"></a>
#### 8. 우선순위와 구현 경계 — 제안(사용자 승인 전 자동 착수 금지)

**P0 — 공식 `양식_rev` 계약 확정(진행 중)**  
Google 원본 두 개와 공식 `매출자료 양식_rev` B:H 수입·지출 열/합계 수식을 읽기 전용으로 확인했다. 사용자가 2027년 여행 `0206_하쿠산`·`0302_야쿠시마`의 연도를 확정했다. 남은 것은 **실제 최신 양식 기준의 붙여넣기 대상 범위·빈칸·합계 보호 확인**이며, 과거 양식별 호환 매핑이나 전수 재작성은 개발 범위 밖이다.

**P1 — Google 읽기 전용 최종 조회 경로**  
매시 정각 Google 읽기, 수입·이체·붙여넣기 지출 모두 정본으로 조회, 마지막 정상 시각/오류와 진행 중 지출 분리. 현재 운영 데이터는 건드리지 않는 격리 검증부터.

**P2 — `양식_rev`와 같은 웹 검토표 및 복사**  
기존 카드 분류·규칙·검토 엔진을 재사용하고, 공식 지출 7열에 맞춘 TSV/표 형식 복사만 제공. 과거 시트 양식별 별도 출력 기능을 만들지 않는다. Google 자동 쓰기 구현 금지.

**P3 — 행별 자연어 규칙 제안·적용**  
로컬 AI의 유효한 연결 경로를 확인 후, 제안/영향 미리보기/사용자 승인/미확정 행 재분류를 구현. 개인정보 외부 전송과 임의 DB 수정을 금지한다.

**P4 — A4 다중 일본 영수증 OCR**  
한 장에서 여러 영수증 인식, cash/private/corporate 분기, JPY×10, 법인카드 중복 수동 확인, 기존 검토/복사 재사용. 별도의 복잡한 매칭 엔진은 금지.

**P5 — Render 전환과 로컬 PC 전송 주기 조정**  
현재 서버·워커·동기화와 파일 의존성을 실측한 뒤 격리 Render 실행 및 데이터 보호 확인. Google 읽기 주기와 PC 원본 수집 주기를 분리. 도메인 전환은 기능/복구 검증 이후에만 수행.

각 단계는 작은 별도 PR과 직접 영향을 받는 검증 한 번으로 끝낸다. 하나의 대형 재구축 PR로 모든 단계를 동시에 진행하지 않는다.

<a id="src-docs-target-workflow-google-authority-md--9-구현-전-결정해야-할-미확정-사항--질문-목록"></a>
#### 9. 구현 전 결정해야 할 미확정 사항 — 질문 목록

Q1. **Google 원본/공식 양식/두 여행 연도 확정**: 과거 보관(26탭), 활성 메인(43탭)을 확인했다. **메인 `매출자료 양식_rev`가 유일한 신규 여행 기준**이며 B:H 지출 7열을 사용한다. `0206_하쿠산`, `0302_야쿠시마`는 2027년 여행이다. 과거의 비연속 B:I 시트들은 추후 사용자가 직접 정비하며 **호환 구현 대상이 아니다**. C열 `항목`(결제처/지급처), D열 `내용`(비용 분류)은 사용자 확인으로 확정됐다. 아직 확인할 것은 템플릿의 실제 복사 대상 범위와 마감 후 변경 이력/동기화 시점이다. **동일 여행이 두 파일에 있으면 메인 우선·`확인 대상` 표시·사용자 수동 정본 조정**으로 우선순위는 확정됐다. [실측 문서](google-ledger.md#src-docs-google-workbook-layout-md)를 따른다.

Q2. **지출 출력 단위 — 사용자 확정(2026-10-11)**: 카드·영수증은 **실제 지출 거래 한 건당 한 행**으로 출력한다. 동일 결제처/항목으로 묶어 합산하지 않는다. 원결제·취소·환불의 구분 및 법인카드 영수증의 증빙 연결은 기존 거래 무결성 규칙을 따른다. 이 사항은 더 이상 미결 질문이 아니다.

Q3. **개인카드 사후 상환 — 사용자 확정(2026-10-11)**: 개인카드 영수증의 비용 기입 후 회사가 이체 상환하더라도, 사용자가 Google에 이미 기입된 비용을 직접 확인하고 **중복 기입하지 않도록 수동 관리**한다. 별도 자동 이체 대사·정산·상계 개발은 하지 않는다. 기존 Google 수기 이체 입력 → COST 읽기 전용 원칙은 유지한다. 이 사항은 더 이상 미결 질문이 아니다.

Q4. **일본 영수증 세부 사항**: 대부분 JPY 영수증이지만 다른 통화도 있는가? 소수 금액·반올림·일본 세금계산 실무에서 100엔=1000원 가정의 예외가 있는가? A4 PDF/사진 지원 범위와 OCR 엔진 사용 동의/정책은 별도 확정.

Q5. **로컬 AI 구현체**: 응답 가능한 로컬 PC AI가 실제 온디바이스 추론인가, 로컬 PC의 Paseo/OpenCode·Codex와 연결된 클라우드 모델인가? 외부 모델에 허용하는 데이터/로그 범위 및 오프라인 시 대기 정책을 확정한다.

Q6. **권한·데모 — 사용자 확정(2026-10-11)**: 전체 장부 기본 열람은 owner 본인만, 별도 계정에는 owner가 **계정별로 여행 조회 권한을 부여**한다. 데모는 **로그인 없이 누구나 접근 가능한 공개 페이지**이며 Google에서 **마감 완료가 확인된 여행 중 수익금액 상위 3건을 성공한 정본 동기화 시마다 자동 재선정**하여 성명·닉네임 등 개인정보 마스킹 후 실제 회계 금액과 함께 공개하는 목표다. 자동 갱신마다 별도의 owner 승인을 요구하지 않지만 새 선정 여행도 개인정보 검증을 통과해야 한다. **마감 판정 근거는 메인→보관 장부 여행 시트 이동으로 확정**됐으며, **수익 동률 시 보조 정렬 규칙**은 아직 미정이다. 마감 미확인/진행 중 여행은 데모 후보에서 제외한다. 공개 데모용 서버-side 데이터와 인증된 전체 장부를 분리한다. [자세한 요구와 개인정보 검증 경계](google-ledger.md#src-docs-access-and-top3-demo-md)를 따른다.

Q7. **마감 기준 확정 / 갱신 동작 미정**: 여행의 마감 완료는 **사용자가 여행 시트를 메인 Google 장부에서 보관 Google 장부로 이동한 시점**으로 판정한다. COST는 정상 읽기에서 실제 보관 여행 탭을 확인해 마감을 인지한다. 보관본과 메인본이 동시에 있으면 **마감 완료**지만 재무 정본은 메인 우선 + 확인 대상/수동 조정이다. 매시 정각 읽기 외 마감 직후 수동 새로고침 허용 여부 및 마감 후 원본 수정 이력 표시의 세부 방식은 별도 결정한다.

Q8. **Render 이전 승인·데이터 보관**: 호스팅 지역/개인정보/백업·복구·비용, 후보 거래와 OCR 이미지를 서버에 얼마나 저장하는지, PC 오프라인 허용 지연.

<a id="src-docs-target-workflow-google-authority-md--10-변경-관리"></a>
#### 10. 변경 관리

2026-10-20 사용자가 보험가입 명단을 실제 참가 기록으로 인정하고 참가자와 기존 수입을 대조하는 시스템의 계획·명세 작성을 요청했다. [참가자 확정·수입 대조 명세](participants.md#src-docs-participant-income-reconciliation-spec-md)와 [작업 인덱스](../history/implementation-and-audits.md#src-docs-participant-income-task-index-md)에 전달 계약과 구현 계획을 기록한다. 기본 설계는 COST 대조표에 이름만 추가하거나 기존 수입 행에 참가 표시를 붙이는 방식이며 Google 수입 자동 쓰기를 허용하지 않는다. 계획 작성 완료이며 제품 구현·배포는 미실행이다.


이 명세는 **사업 흐름에 대한 요구사항**이며, 현재 코드·배포 상황과 분리되어 있다. 확정된 방향을 새 모델에 긴 프롬프트로 계속 복제하지 말고 이 문서를 먼저 읽게 한다. 미확정 사항은 확인 후 본 문서에서 ‘확정’으로 승격한다. 기존 운영 기록과 상충하면 과거 기록을 지우지 않고 **현재 운영 사실 vs 목표 정책**을 명시한다.

새 단계 작업 전: **목표 / 변경 동작 / 직접 영향 / 한 번의 필요한 검증 / 종료 조건**을 먼저 정하고 불필요한 전체 재검증을 피한다.

- 메인 문서: 3분기_기타비용, 프리랜서 지급대장, 0630_오제 및 7~12월 여행, 0206_하쿠산, 0302_야쿠시마, 행사경비총괄표, 매출자료 양식/개선판(일부 숨김).
- **2026-10-25 사용자 확정 회계 분기 경계:** `0625_아키타`가 **2분기 마지막 여행**, `0630_오제`가 **3분기 첫 여행**이다. 오제는 출발일이 6월 30일이어도 7월까지 이어지는 여행 기간과 회계 처리 때문에 **3분기**로 분류된다. 2026-10-11 실측에서 `0630_오제`는 활성 **메인** 장부에 있었다. 달력상 출발 분기를 보관 장부 선택이나 회계 분기에 자동 대입하지 않는다. 현재 원본과 운영 스냅샷 상태는 별도 재확인한다.

> **2026-10-25 수입 표시 조사:** [0630_오제 수입 표시 진단·Google ↔ 웹 장부 대조 시각화 명세](google-ledger.md#src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md). 위 정보는 2026-10-11 당시 실측이며 현재 운영 스냅샷에서의 누락 원인은 별도 판정해야 한다. Google 원본 자동 쓰기나 거래 확정은 범위 밖이다.
- **사용자 확정(2026-10-11): 메인의 `0206_하쿠산`, `0302_야쿠시마`는 모두 2027년 출발 여행이다.** 해당 탭의 “2026년 월 매출 확인자료_” 문구는 예전 템플릿의 잔재다. 이 두 여행은 2026년으로 잘못 연결하지 않는다. 다른 여행의 연도는 별도로 확인한다.
- 분기 기타비용, 프리랜서 지급대장, 총괄표, 숨김 양식 시트는 일반 여행별 개별 장부와 목적이 다르다. 여행으로 자동 등록·중복 집계하지 않는다.

<a id="src-docs-google-workbook-layout-md--2-실제로-확인한-여행-시트-구조"></a>
#### 2. 실제로 확인한 여행 시트 구조

**사용자 확정(2026-10-11): 메인 장부의 `매출자료 양식_rev`가 신규 여행 시트의 유일한 기준 템플릿이다.** 신규 기능 구현·복사 출력·검증은 이 양식 하나를 기준으로 한다. 과거에 관측된 상이한 레이아웃은 구형 양식의 잔재이며 사용자가 추후 직접 정비한다. **레거시 레이아웃을 위해 호환 파서/자동 변환기/별도 복사 경로를 만들지 않는다.**

기준 템플릿은 위쪽 **수입 내용**, 아래쪽 **지출 내용**, 맨 아래 **합계 및 회사수익인식**이다. 신설 시트에서는 데이터 행 추가/수식 범위 변경이 있을 수 있으므로 기준 **열 계약을 유지하되 절대 행 번호를 하드코딩하지 않는다**. 비표준 구형 시트가 그대로 남으면 임의로 매핑하지 않고 '구형 양식/확인 필요'로 표시하여 최종 장부 조회가 완전하다고 주장하지 않는다.

<a id="src-docs-google-workbook-layout-md--공식-기준-매출자료-양식_rev의-bh-연속-7열-구조"></a>
##### 공식 기준: `매출자료 양식_rev`의 B:H 연속 7열 구조

확인된 예:
- 메인 **0630_오제**: 수입 제목 B6/헤더 B7:H7, 지출 제목 B45/헤더 B46:H46.
- 메인 **1005_경주**: 수입 제목 B4/헤더 B5:H5, 지출 제목 B30/헤더 B31:H31.
- 보관 **0404_에히메의 사본**: 수입 제목 B6/헤더 B7:H7, 지출 제목 B25/헤더 B26:H26.
- **유일한 신규 여행 기준 템플릿 `매출자료 양식_rev`**: 수입 제목 B4/헤더 B5:H5, 지출 제목 B20/헤더 B21:H21 (템플릿이며 실거래 장부가 아님). 템플릿 실측 수식: 수입 합계 C18 `=sum(H6:H17)`, 지출 합계 C33 `=SUM(H22:H32)`, 회사수익 C35 `=C18-C33`. 이 행 번호는 원본 양식의 현재 위치이지 앞으로 모든 여행 탭의 고정 위치가 아니다.

지출 헤더/열: **B 거래일자 | C 항목 | D 내용 | E 기간 | F 예약번호 | G 증빙유형 | H 금액(원)**.

수입 헤더/열: **B 거래일자 | C 이름 | D 닉네임 | E 예약금 | F 잔금 | G 추가금 | H 금액(원)**.

수입 H열에는 실제로 SUM(E:G) 같은 행별 수식이 있다. COST가 읽는 것은 허용하지만 지출 복사 과정에서 수입/수식 영역을 덮어쓰지 않는다.

<a id="src-docs-google-workbook-layout-md--구형-양식-관측-기록-bi-비연속-5열-구조-신규-구현-대상-아님"></a>
##### 구형 양식 관측 기록: B:I 비연속 5열 구조 (신규 구현 대상 아님)

- 메인 **0909_제주**: 수입 제목 B6/헤더 B7·D7·F7·I7, 지출 제목 B24/헤더 B25·D25·F25·H25·I25.
- 보관 **0107_대만**: 수입 제목 B6/헤더 B7·D7·F7·I7, 지출 제목 B26/헤더 B27·D27·F27·H27·I27.

지출 헤더/열: **B 거래일자 | D 항목 | F 내용 | H 증빙유형 | I 금액(원)**.

중간 C/E/G 등은 빈칸·서식/병합 영역일 수 있다. **이 구형 시트에는 공식 템플릿의 7열 복사 결과를 붙여넣으면 안 된다.** 사용자가 직접 `양식_rev` 기준으로 수정할 예정이므로, COST가 별도의 레거시 호환 복사 또는 자동 변환을 구현하지 않는다.

수입은 B 거래일자, D 이름, F 내용(예약금/잔금), I 금액. A형의 수입 세부 구조와도 다르다.

<a id="src-docs-google-workbook-layout-md--의미와-탐지-규칙"></a>
##### 의미와 탐지 규칙

- 사용자가 구어로 말한 “증빙내용”의 **실측 헤더는 “증빙유형”**이다.
- 실제 값은 **카드, 이체, 영수증, 세금계산서** 등이 관측됐다. 증빙값을 카드/이체/영수증 세 종류로 제한하지 않는다.
- **사용자 확정(2026-10-11): 지출 C열 `항목` = 결제처·가맹점명·지급처(예: 아고다·트립닷컴·현지 식당), D열 `내용` = 비용 분류(예: 숙박비·항공료·식비·차량비)**다. COST 내부 필드명이 같아도 이 의미에 맞춰 명시적으로 매핑하며, 원본 카드의 가맹점 문자열을 규칙 없이 덮어쓰지 않는다.
- 기간·예약번호는 A형에 있지만 B형에는 없다. 없는 열을 임의로 만들어 구글 표를 밀지 않는다.
- 신설 여행 탭은 `양식_rev` 기준의 동일한 열 계약을 전제로 하되 행이 늘어나면 수입·지출 시작과 끝은 달라질 수 있다. Google이 제공하는 rowCount(약 900~1,200)는 실제 장부 거래 행수가 아니다.
- **기준 양식의 ‘수입 내용’·‘지출 내용’·실제 헤더·총액/수익 계산 경계**로 읽을 범위와 붙여넣기 영역을 결정한다. 구형 레이아웃을 자동 호환시키지 않는다. 형식이 기준 양식과 다르거나 수식/병합 셀을 침범할 위험이 있으면 **HOLD/비표준 표시**한다.
- 붙여넣기는 사용자가 직접 한다. COST는 합계·수식 셀을 직접 갱신하지 않는다.

<a id="src-docs-google-workbook-layout-md--3-수식의-권위와-관측-오류"></a>
#### 3. 수식의 권위와 관측 오류

- 메인 0630_오제: 수입 H의 SUM(E:G), 지출합계에 SUM(H47:H75), 회사수익에 수입-지출 수식이 관측됐다.
- 메인 0909_제주: 지출합계가 I열 대상(예: SUM(I26:I28))으로 계산된다.
- **메인 3분기_기타비용 C50에는 실제 “=#REF!-C48” 수식이 있으며 결과가 #REF!**이다. C48의 지출합계는 SUM(H6:H47)이다. 이 부분을 원본 변경 없이 발견했다. COST는 이 결과를 정상 회사수익 또는 0원으로 위장하면 안 된다. 실제로 오류인지 불필요한 템플릿 잔재인지는 사용자 판단 필요.
- Google의 집계 오류나 마감 후 수정은 COST가 무단으로 고치지 않고 원본 오류·최신 확인 시각을 그대로 드러낸다.

<a id="src-docs-google-workbook-layout-md--4-정본-라우팅--분기-마감-이동"></a>
#### 4. 정본 라우팅 / 분기 마감 이동

- 기본 정보: 어떤 여행 시트가 **어느 파일에 실제 존재하는지** 양쪽 탭 목록에서 확인한다. 월/분기만 보고 파일을 결정하지 않는다.
- **사용자 확정(2026-10-11): 여행 마감 완료의 유일한 업무 트리거는 해당 여행 시트가 활성 메인 Google 장부에서 과거/보관 Google 장부로 이동되는 시점**이다. COST는 **보관 장부에 실제 여행 시트가 확인되는 경우 마감 완료로 취급**하며, **여행 종료일·월·분기·수익 수식 존재·메인 장부에서 자체 결산 완료만으로는 마감 처리하지 않는다**. 따라서 메인에만 남은 여행은 출발일이 과거라도 미마감이다.
- **중복 공존과 마감은 별도 속성:** 동일한 실제 여행 시트가 **양쪽에 존재해도 보관본의 존재로 마감 완료 상태**이며, 정본 금액은 기존 확정대로 **메인 우선 + `확인 대상`**, 사용자가 정본을 변경할 수 있다. '마감 완료'가 '보관본 금액을 우선 집계'한다는 뜻은 아니다. Google 조회·데모 순위에서 한 여행은 항상 한 번만 반영한다.
- **실제 이동 시각과 관측 시각 구분:** 동기화로 보관본이 최초 확인된 KST 시각은 `마감 감지 시각`으로 기록할 수 있지만, Google에서 실제 이동한 정확한 시간이라고 주장하지 않는다. 보관 장부에 이미 있던 과거 여행도 적법한 여행 탭임이 확인되면 마감 완료로 볼 수 있다.
- 템플릿·총괄표·기타비용·프리랜서 대장이나 다른 여행과 우연히 이름이 비슷한 `의 사본`을 실여행의 보관 이동으로 오인하지 않는다. 여행 식별이 모호하거나 Google 보관본 조회가 실패하면 새로 마감 완료로 확정하지 않고 `확인 대상`으로 둔다. 원본 시트 이동·복사·삭제는 사용자만 수행하고 COST는 읽기 전용이다.
- **사용자 확정(2026-10-11): 동일 회계 여행이 두 파일에 동시에 존재하면 활성 메인의 여행 시트를 기본 정본으로 우선 선택한다.** 동시에 `확인 대상`으로 표시하고, 사용자가 COST에서 양쪽 내용을 비교·확인하여 정본 선택을 수동 조정할 수 있게 한다. 두 사본의 내용이 같더라도 중복 존재 자체를 확인 대상으로 표시한다. 금액이 다르다고 자동으로 보관본을 선택하거나 전체 조회를 중단하지 않는다.
- 두 사본의 파일 ID/탭 ID/읽기 시각/행수 및 합계 차이를 비교 가능하게 유지한다. **집계·확정 조회에는 선택된 사본의 수입·지출만 한 번 반영한다.** 정본 수동 선택은 기록·이력을 보존하고 이후 동기화에도 유지한다. 어느 쪽을 선택해도 Google 원본을 COST가 쓰거나 수정하지 않는다.
- 메인에서 해당 여행이 실제로 사라지고 보관본만 남으면 보관본을 읽되, 정본 원본 변경을 표시·기록한다. 다른 여행을 이름 유사성만으로 동일 여행이라 단정하지 않는다.
- “의 사본” 문구와 파일 수정시간은 단독으로 권위를 증명하지 않는다.
- Google 파일·sheetId는 복사/이동 과정에서 달라질 수 있으므로 **실제 회계 여행의 안정 식별 키**와 파일별 현재 sheetId를 따로 관리해야 한다. 제목만으로 유사 여행을 합치지 않는다.
- 같은 여행의 장부가 두 파일에 있다면 **메인 우선·확인 대상 표시·사용자 선택 조정 가능·수입/지출 두 번 합산 금지**. 내용이 달라도 선택 전에는 '양쪽 일치 검증 완료'로 표시하지 않는다. 누락된 시트를 분기 이동으로 추측해 자동 0원 처리하지 않는다.
- 파일이 읽히지 않거나 탭이 사라지면 마지막 정상 스냅샷의 날짜·오류 상태를 표시하고, 최근 확정 장부라고 주장하지 않는다.
- 분기 마감 후에도 보관 파일은 수정될 수 있어 변경 감지 후 해당 시트만 업데이트한다.
- 메인에서 사라진 시트가 보관에 들어와도 기존 카드 원본·사용자 확정·환불·OTA 연결을 삭제/덮어쓰지 않는다.

<a id="src-docs-google-workbook-layout-md--5-다음-구현-전에-사용자-확인이-필요한-질문"></a>
#### 5. 다음 구현 전에 사용자 확인이 필요한 질문

1. **연도 판정 — 두 여행은 확정:** `0206_하쿠산`, `0302_야쿠시마`는 **2027년 출발**이다. 나머지 탭의 2027년 여부는 명시 근거로 식별한다. 상단 템플릿 문구만으로 연도를 정하지 않는다.
2. **열 의미 — 확정:** 공식 `양식_rev` 지출 C열 **항목=결제처·가맹점명·지급처**, D열 **내용=비용 분류**. 예: `아고다/숙박비`, `트립닷컴/항공료`, `현지 식당명/식비`, `렌터카 업체명/차량비`.
3. **출력 단위 — 사용자 확정(2026-10-11): 카드와 영수증 지출은 실제 거래 한 건당 Google 지출표 한 행으로 출력한다.** 같은 날짜·가맹점·항목·금액이라도 서로 다른 실제 결제이면 각각 독립 행이다. 가맹점/항목/기간 기준 집계·병합·묶음 출력은 제공하지 않는다. 영수증 한 장은 기본 한 건이며, 법인카드 영수증이 이미 존재하는 카드 매입과 동일 거래로 확인된 경우에 한해 카드 지출 행 하나만 출력하고 영수증은 증빙으로 연결한다. 취소·환불도 원거래와 임의 합산·상쇄해 거래 행을 숨기지 않는다. 동일 원본 파일 재수신으로 발생한 중복은 기존 거래 ID·중복 방지 규칙대로 처리한다.
4. **양쪽 파일 중복 탭 — 사용자 확정:** **활성 메인 우선**, 보관본도 보존하고 `확인 대상`으로 표시한다. 사용자는 두 장부 차이를 비교하고 **정본 선택을 수동 조정**할 수 있다. 선택된 한 쪽만 조회·집계하며 Google 원본은 자동 수정하지 않는다. 우선순위 질문은 해결됐다.
5. **별도 관리 시트:** 분기 기타비용, 프리랜서 지급대장, 행사경비총괄표는 웹 제3자 조회에서 어떤 수준까지 공개해야 하는가?
6. **증빙의 레거시값:** 신규 법인카드 지출 복사값은 “카드”, 개인/현금 영수증은 “영수증”으로 하되, 과거 “영수증” 레거시 항목은 그대로 둘 것인가?
7. **수식 오류:** 메인 3분기_기타비용 C50의 #REF!는 별도 수정해야 할 오류인가, 사용하지 않는 템플릿 칸인가?

<a id="src-docs-google-workbook-layout-md--6-완료-범위"></a>
#### 6. 완료 범위

- **실측/사용자 확인 완료:** 두 Google 원본의 제목/MIME/타임존/탭 목록(각 26/43), 기준 `매출자료 양식_rev`의 헤더·수입/지출·합계 수식 구조, 대표 과거 양식과 차이, 실제 증빙값, 기타비용 C50의 계산 오류, `0206_하쿠산`·`0302_야쿠시마`의 2027년 귀속. 공식 기준은 `양식_rev` 하나이며 구형 양식 호환 구현은 범위 밖.
- **아직 미실행:** 기준 템플릿으로 신규 작성된 실제 여행 탭의 붙여넣기/병합 셀 안전 검증, Google API 프로덕션 권한 확인, 시트 간 마감 이벤트 대사, Render 이전, 자동 읽기 구현, 운영 Google/웹 표시 동일성 검증. **구형 양식 전수 호환 검사는 사용자 지시에 따라 수행하지 않는다.**
- **문서만 변경**하므로 기존 테스트·배포·서버 재시작·운영 DB 수정은 불필요하고 수행하지 않는다.

<a id="src-docs-access-and-top3-demo-md--1-사용자-확정-정책"></a>
#### 1. 사용자 확정 정책

1. **본인만 기본 열람:** COST의 전체 수입·지출·순수익, 카드/영수증 원본, 분류·로컬 AI 작업, 관리 기능은 기본적으로 owner 본인만 열람·작업한다.
2. **계정별 권한 부여:** owner가 명시적으로 승인한 계정에만 여행별 **읽기 권한**을 부여하거나 철회한다. 별도 계정 생성만으로 장부가 보이지 않으며, 기본 차단(default deny)이다. viewer는 허용된 여행의 Google 최종 정본 회계내용만 읽고 원본·AI·수정·계정 관리 권한은 없다.
3. **누구나 접근 가능한 비로그인 공개 데모 — 사용자 확정(2026-10-11):** Google 최종 정본의 **회사수익인식(순수익) 금액이 높은 실제 여행 3건**을 선정한다. **성명·닉네임 등 개인식별정보를 서버에서 마스킹/제외**하고 **실제 수입·지출·순수익 금액을 포함한 회계 내용**을 제공한다. **데모 페이지는 로그인 없이 인터넷의 누구나 볼 수 있어야 한다.** 단, owner/viewer 장부 접근과 분리된 읽기 전용 안전 데이터 표현만 공개한다. 비로그인 요청으로 원본 장부와 다른 여행, 내부 관리 API에는 접근할 수 없다.

| 범주 | 보이는 범위 | 수정/원본 접근 |
| --- | --- | --- |
| owner | 모든 허가된 Google 정본과 COST 작업 데이터 | 계정·여행 열람권한 관리 및 COST 작업 기능. Google 자동 쓰기는 금지 |
| 승인된 viewer | 해당 계정에 할당된 여행별 확정 Google 장부 | 읽기 전용; 타 여행과 카드/영수증 원본 접근 불가 |
| 데모 방문자(비로그인 포함) | 마스킹된 순수익 상위 실제 여행 3건만, 인터넷에 공개 | 보기 전용, 다른 여행·원본·계정 조회 불가 |

<a id="src-docs-access-and-top3-demo-md--기존-구현과의-관계"></a>
##### 기존 구현과의 관계

- **확인된 코드 기반:** webapp/access_control.py 에 owner/viewer 역할, 계정 활성 상태, 여행별 visible_tabs/can_view_tab 및 권한 철회 경로가 있다. webapp/ledger_board.py 는 허용된 여행만 서버에서 조회하도록 구성하는 viewer 렌더러가 있다. 이 기능을 우선 재사용하며 별도 사용자/권한 엔진을 처음부터 재작성하지 않는다.
- **미구현(요구):** Google 실데이터 순수익 순위 상위 3개 자동/수동 선별, 서버 수준 개인정보 익명화 데모, 해당 데모의 배포·접근 허용은 아직 구현/검증된 것으로 보지 않는다. 코드에 있는 trip-demo-a/b 등 합성 예시와 이번 요청은 서로 다른 기능이다.
- **주의:** 기존 viewer 기능이 있다는 사실은 새로운 Google 데이터 경로의 권한 검사까지 완료됐다는 뜻이 아니다. 서비스 코드·운영 세션·Render 이전 상태는 별도 점검한다.

<a id="src-docs-access-and-top3-demo-md--2-서버-수준-권한-불변조건"></a>
#### 2. 서버 수준 권한 불변조건

- 계정은 owner의 명시적 승인 전까지 전체 금전·장부 정보 접근 불가. viewer는 계정별 허용 여행 allowlist만 볼 수 있고, 해당 여행의 수입·지출·수익 합계만 포함한다.
- **서버가 매 요청마다 검증:** HTML뿐 아니라 API/실시간 새로고침/검색/CSV·XLSX·다운로드/캐시에도 같은 역할과 여행 필터를 적용. 클라이언트에서 메뉴만 숨기는 권한 처리는 금지.
- owner만 사용자 권한 부여/철회, 정본 중복 선택 조정, AI 분류 승인 및 데모 게시 설정 가능. 권한 철회가 이전 캐시·URL 재사용으로 우회되지 않도록 한다.
- 사용자가 허용하지 않은 여행의 제목, 인원, 재무 정보, 원본 내부 ID 등을 viewer 응답에 포함하지 않는다. Google 파일이 메인에서 보관으로 이동할 때도 계정별 여행 권한을 의도 없이 확대하지 않는다.
- viewer는 별도 허가 없이 결제자·승인번호·계좌·카드·영수증 스캔 원본·AI 대화·내부 메모·운영 비밀을 조회할 수 없다.

<a id="src-docs-access-and-top3-demo-md--3-실데이터-데모-상위-3개-선별"></a>
#### 3. 실데이터 데모 상위 3개 선별

- **정렬 기준:** 매출액·매출총액이나 이익률(%)이 아니라 **여행별 회사수익인식/순수익 원화 금액 내림차순**. 원칙은 Google에서 읽은 최종 수입에서 최종 지출을 차감한 값(해당 장부의 검증 가능한 결산 값과 대조). 아직 Google에 미반영된 COST 지출 후보는 확정 수익에 포함하지 않는다.
- **후보 단위 — 사용자 확정(2026-10-11): `마감 완료`가 확인된 실제 여행 장부만 순위 후보에 포함한다.** 예정·진행 중·마감 미확인 여행은 현재 Google 장부에 높은 수익이 표시되더라도 후보에서 제외한다. 빈 매출자료 양식_rev, 프리랜서 지급대장, 기타비용, 분기 행사경비총괄표도 여행 순위 후보가 아니다.
- **마감 완료 판정 — 사용자 확정(2026-10-11):** 여행 시트를 메인 Google 장부에서 과거/보관 Google 장부로 **이동한 시점**에 마감 완료로 인정한다. 두 Google 파일 읽기 후 **보관 장부에 실제 여행 시트가 확인되면 마감 완료 후보**로 본다. 과거 이미 보관된 실제 여행도 포함한다. 반면 메인에만 존재하는 여행은 종료일·회계 수식 계산 여부와 관계없이 미마감이므로 데모 후보에서 제외한다. 단순 제목 유사성, `의 사본` 표기만으로 다른 여행을 연결하거나 템플릿·총괄표를 여행으로 취급하지 않는다. 실제 여행 식별이 모호하거나 보관 조회가 실패하면 새 마감 판단을 보류한다.
- **상태와 정본 선택 분리:** 보관 장부에 해당 여행이 확인되면 마감 완료다. 같은 여행이 메인에도 남아 있어도 마감 판정을 취소하지 않으며, **회계 수입·지출은 메인 우선 + `확인 대상` / owner 수동 선택**을 적용한다. 보관 이력은 마감 신호, 정본 선택은 계산 금액의 출처다. 두 사본을 동시에 합산하지 않는다.
- **두 장부 중복:** 메인·보관에 동일 여행이 함께 있으면 사용자 확정 규칙인 메인 우선(확인 대상)과 owner가 선택한 정본을 사용하고 **여행을 중복 순위/집계하지 않는다**.
- **자료 유효성:** 수익 계산 불가, #REF! 등 수식 오류, 구형 양식 인식 불가, 개인정보 마스킹 실패 여행은 무리하게 공개하지 않고 owner 확인 대상으로 둔다. 3건 미만이면 가짜 여행으로 채우지 않는다. 동기화 실패·일부 시트 누락·정본 원본 선택 불능 시 그 시도를 성공한 새 순위로 취급하지 않고 **마지막 정상 익명화 스냅샷을 확인 시각·갱신 지연 표시와 함께 유지**한다. 이전 스냅샷이 없으면 실제 장부를 노출하지 않고 데모 준비 중 상태를 보여 준다.
- **금액 공개:** 사용자 요청은 이름·닉네임 등 개인정보만 가리고 수입·지출·순수익을 실제로 노출하는 것이다. 금액을 임의로 가짜 값으로 교체하지 않는다. 단, 식별 위험이 있는 세부 행은 제외/일반화해야 하며 회계 총합이 서로 불일치하면 그 상태를 표시한다.
- **자동 갱신 처리 경계:** 성공한 Google 읽기 스냅샷에서 **보관 장부에 실여행 시트가 확인된 마감 완료 여행만 필터링** → 여행별 확정 수익 계산 → 메인·보관 중복 정본 선택 반영 → 적격 여행 내림차순 **최대 3건 선정** → 새 후보 **각각 서버에서 개인정보 제거·허용 필드 검증** → 전체 데모 스냅샷을 준비 완료한 경우에만 **원자적으로 교체**한다. 바뀐 순위의 새 여행을 원본 데이터 그대로 먼저 게시하지 않는다. 특정 후보가 비공개 사유로 제외되면 다음 적격 순위 여행으로 채우되, 3개를 채울 수 없으면 안전한 개수만 공개하고 관리자 확인 대상으로 기록한다.
- **자동 재선정 자체에는 owner의 매회 수동 승인을 요구하지 않는다.** 초기 실제 공개 전에 개인정보·출력 계약 검증은 필요하며, 이후 새 선정 여행도 같은 서버 측 비식별 검증을 통과한 결과만 자동 공개한다.
- **공개 범위·선정 갱신 방식 확정(2026-10-11):** 데모는 비로그인 누구나 조회한다. **두 Google 정본의 정상적인 읽기·동기화가 끝날 때마다 회사수익인식 KRW 금액 기준 상위 3개 여행을 자동으로 다시 선정**한다. owner가 초기 3건을 고정하거나 매 갱신을 승인하는 수동 워크플로는 요구하지 않는다. 같은 결과라면 불필요한 재게시·쓰기 없이 유지한다. **마감 완료는 보관 Google 장부로의 여행 시트 이동으로 판정하도록 확정됐다.** 남은 미결은 수익 동률 시 일관된 보조 정렬 기준과 여행 식별이 모호한 경우의 운영 검토다. 실제 공개 배포는 별도 구현·검증을 필요로 한다.

<a id="src-docs-access-and-top3-demo-md--4-데모-개인정보-익명화-계약"></a>
#### 4. 데모 개인정보 익명화 계약

- 최소한 **실명·닉네임·전화·이메일·주소·계좌·카드 번호·예약번호/PNR·여권/신분증·승인번호·원본 거래 ID·개인 메모·원본 영수증 이미지**는 데모에서 숨긴다.
- 사용자 자유 입력 텍스트에는 **가맹점/지급처(항목)**에 실제 사람 이름이 들어가거나 **내용/메모**에 연락처가 섞일 수 있다. 성명/닉네임 열만 가리는 방식으로는 불충분하다. 식별 가능한 지급처는 '개인 지급처'로 일반화하거나 항목을 출력하지 않는다.
- 날짜·여행명·드문 지출 조합만으로 개인이 역추적될 수 있는 경우도 개별 검토/일반화한다. 데모에 실제 재무 정보 공개를 허용한다는 것이 개인정보까지 공개하라는 뜻은 아니다.
- **서버에서 허용된 필드만으로 새 payload를 만든 후 마스킹/일반화**하고, HTML·API·다운로드·검색·페이지 메타데이터·툴팁·캐시·에러에 원본 개인정보가 전달되지 않도록 한다. 브라우저에서만 텍스트를 별표 처리하고 숨은 JSON/DOM에 원본을 남기는 방식 금지.
- 데모에서 Google 원본 파일 URL, 원본 sheetId, 거래 원본과 사진, 내부 관리자 경로를 직접 열어주는 링크/상호작용은 제공하지 않는다.
- owner가 실제 데모에 나갈 결과를 미리 확인할 수 있도록 한다. 개인식별정보 마스킹의 정확성은 합성 테스트와 **초기 공개 전 검수**로 확인한다. 이후 정기 동기화에서 새로 선정되는 여행은 **매번 동일한 서버 측 비식별·허용 필드 검증을 자동 통과해야 하며 owner의 매회 수동 검토를 필수로 만들지 않는다**.

<a id="src-docs-access-and-top3-demo-md--5-범위-및-단계"></a>
#### 5. 범위 및 단계

- 1단계: 기존 owner/viewer 서버 권한을 Google 정본 조회 경로까지 연장하고 계정별 여행 할당을 검증한다.
- 2단계: **매시 정각(Asia/Seoul) 두 Google 파일의 정상 동기화 완료 후** 해당 스냅샷의 최종 순수익 상위 3건을 중복 없이 자동 재선정하고, 공개 가능한 필드만 서버에서 추출하는 데모 projection을 생성한다. 갱신 실패·데이터 미변경 시 불필요한 재게시를 피한다.
- 3단계: 원본이 아닌 익명화된 데이터만 렌더링/다운로드/캐시하도록 검증한다. 차단 계정, 다른 여행 URL, 금액 순서, 3건 제한, 실명·닉네임·자유 텍스트 누출 여부를 합성 데이터로 표적 테스트한다.
- 4단계: **비로그인 공개, 정상 정본 동기화 후 자동 재선정, 보관 장부로 이동된 마감 완료 여행만 선별**은 모두 확정됐다. 실여행 식별·마스킹·초기 공개 결과 검수를 마친 후 배포한다. 이후 매회 자동 재선정은 안전 검증을 통과한 투영만 원자적 갱신한다. **이 문서 수정은 실제 데이터의 외부 공개 또는 서비스 배포가 아니다.**

<a id="src-docs-access-and-top3-demo-md--6-남은-확인-질문"></a>
#### 6. 남은 확인 질문

**비로그인 공개 여부 — 확정(2026-10-11): 누구나 로그인 없이 열람하는 인터넷 공개 데모.**

**선정 주기 — 확정(2026-10-11):** 성공한 Google 정본 동기화 시 수익 상위 3개 자동 재선정. 현재 목표 주기는 매시 정각(Asia/Seoul) 읽기 전용 동기화이며, 마감/보관 양쪽을 확인하고 중복 없이 계산한다.

**후보 범위 — 확정(2026-10-11): 마감 완료가 확인된 여행만 포함. 진행 중·마감 미확인 여행은 제외한다.**

**마감 판정 — 확정(2026-10-11):** 사용자에 의해 여행 시트가 메인 장부에서 과거/보관 장부로 이동되어, 정상 Google 동기화에서 **보관 장부에 해당 실제 여행 탭이 확인된 경우 마감 완료**다. 메인에만 남은 여행은 미마감이다. 양쪽 동시 존재 시 마감 완료·메인 우선·확인 대상 표시가 모두 적용된다.

1. 수익 동률일 때 어떤 보조 정렬 기준을 사용할지는 추후 구현 전 확정한다.
2. 식별이 모호한 보관 사본과 실제 여행의 대응은 owner 검토 대상으로 남기되 마감 정의를 변경하지 않는다.

원본/여행 식별 정확성과 실제 최종 마스킹 검증을 마치기 전에는 실데이터 데모를 배포하지 않는다. 로그인 없는 조회는 **공개 허용된 별도 데모 projection만** 가능하며 다른 모든 회계 정보는 기존 owner/viewer 인증·권한을 유지한다.

<a id="src-docs-google-authority-sync-readiness-md--1-현재-동작-저장소-기준"></a>
#### 1. 현재 동작 (저장소 기준)

- `tools/google_authority_sync.py --snapshot <공개 스냅샷 경로> --rows <비공개 행 경로>`로 1회 실행한다. 경로는 항상 명시한다. 기본 경로는 없다.
- 두 워크북을 xlsx로 읽기만 한다. Google에는 쓰지 않는다.
- 공개 스냅샷에는 합계·검증 상태·행 변경 건수만 있다. 행 값(이름·예약번호 등)은 비공개 행 파일에만 있다.
- 실패 시 이전 정상 값을 유지하고 `stale`로 표시한다. 빈 결과로 덮어쓰지 않는다.

<a id="src-docs-google-authority-sync-readiness-md--2-주기-실행-설계-승인-전-미활성"></a>
#### 2. 주기 실행 설계 (승인 전 미활성)

| 변경 없음 | 지문이 같으면 파싱 생략 | 구현됨 (`unchanged`) |
| 중복 실행 억제 | 동시 실행 금지 | 구현됨. CLI의 OS 파일 잠금 안에서 지연 상태 조회·동기화·결과 기록을 수행한다. |

<a id="src-docs-google-authority-sync-readiness-md--3-기존-작업과의-충돌-확인-필수"></a>
#### 3. 기존 작업과의 충돌 확인 (필수)

- `tools/refresh_review_source.py --watch`는 기본 30초 간격으로 **같은 메인 워크북**을 내려받는다. 검토용 흐름이며 정본 읽기와 목적이 다르다.
- 운영에서 이 `--watch`가 상시 실행 중인지 저장소 문서로 확인되지 않았다. 등록 전 운영 PC에서 프로세스와 작업 스케줄러 목록을 확인한다.
- 두 흐름이 같은 원본을 동시에 읽는 것 자체는 쓰기가 아니지만, 요청 수를 줄이기 위해 하나로 합치거나 간격을 분리하는 결정이 필요하다.

<a id="src-docs-google-authority-sync-readiness-md--4-저장-위치와-권한"></a>
#### 4. 저장 위치와 권한

- 공개 스냅샷과 비공개 행 파일은 **저장소 밖**에 둔다. 예: `D:\WebLedgerHost\data\google-authority`. 저장소 안이나 임시 공개 폴더에 두지 않는다.
- 비공개 행 파일은 고객 개인정보와 재무 행을 포함한다. 접근 권한을 운영자 계정으로 제한하고, 백업에 포함할지 별도로 정한다.
- 공개 스냅샷에는 개인정보가 없다는 것을 테스트(`test_public_snapshot_has_no_row_contents_but_private_file_does`)로 확인한다.

<a id="src-docs-google-authority-sync-readiness-md--5-승인-전-확인-항목"></a>
#### 5. 승인 전 확인 항목

1. 운영 PC의 작업 스케줄러에 기존 `--watch` 또는 다른 Google 접근 작업이 있는지
2. 실행 계정이 두 워크북에 읽기 권한을 가지는지 (`SOURCE_ACCESS_DENIED` 재현 여부)
3. 로컬 PC가 꺼져 있을 때의 공백 시간 표시 방식 (명세 Q7의 미결)
4. 백업 대상에 비공개 행 파일을 넣을지
5. 실패 알림 채널 (현재는 표준 출력 상태 코드만 있다)

<a id="src-docs-google-authority-sync-readiness-md--6-활성화-절차-승인-후에만"></a>
#### 6. 활성화 절차 (승인 후에만)

1. 구현된 CLI의 `sync.lock`과 `sync-state.json` 경로 및 실행 계정의 파일 권한을 확인한다. 합성 잠금·장애 테스트는 구현되어 있다.
2. 격리된 임시 경로에 스케줄러를 **비활성 상태로** 등록하고 수동 1회 실행으로 확인한다.
3. 사용자 승인을 받은 뒤 활성화한다. 활성화 전 공개 스냅샷과 비공개 행 파일을 백업한다.
4. 활성화 후 첫 정각 실행 결과를 `synced_at`과 오류 코드로 확인한다.

<a id="src-docs-google-authority-sync-readiness-md--7-render-전환-메모-검토만-미실행"></a>
#### 7. Render 전환 메모 (검토만, 미실행)

- 현재 코드는 Windows 경로와 `openpyxl`만 쓴다. Linux 이식성은 실행 전에 확인이 필요하다.
- 비공개 행 파일을 Render 디스크에 두면 개인정보가 국외 서버에 저장된다. 호스팅 지역·보관 기간·백업을 먼저 정한다 (명세 Q8).
- Google 읽기 권한은 서비스 계정 또는 OAuth 중 하나로 정해야 한다. 현재 익명 xlsx 내보내기에 의존하며, 공개 범위 확인이 필요하다.

<a id="src-docs-google-authority-sync-readiness-md--8-이번-단계에서-하지-않은-것"></a>
#### 8. 이번 단계에서 하지 않은 것

- 스케줄러 등록, 운영 설정 변경, 운영 재시작
- 운영 SQLite·OTA DB 쓰기
- Render 배포나 이전
- Google 원본 쓰기


<a id="src-docs-google-authority-sync-readiness-md--9-2026-10-11-google-원본-공유-설정-실측-및-인증형-읽기-준비"></a>
#### 9. 2026-10-11 Google 원본 공유 설정 실측 및 인증형 읽기 준비

- 연결된 Google Drive 권한 메타데이터에서 **메인·보관 모두 anyone/reader**가 확인됐다. `allowFileDiscovery=false`이므로 검색 공개를 뜻하지는 않지만, 링크를 아는 사람이 읽을 수 있는 공유 방식이다. 원본에 회계·개인정보가 포함될 수 있어 운영 보안 승인이 필요하다. **공유 설정은 변경하지 않았다.**
- 기존 기본 `tools/google_authority_sync.py` 실행은 인증 없는 Google XLSX export를 사용한다. 두 문서의 공유를 제한하면 기존 방식은 실패할 수 있다. 공유 권한을 바꾸기 전에 대체 인증이 실제로 동작하는지 검증해야 한다.
- 개발 브랜치에는 `--google-auth adc` 선택형 읽기가 추가됐다. `google-auth`의 Application Default Credentials와 Google Drive **읽기 전용** scope를 사용하며, 허용된 두 원본에만 Drive export를 요청한다. 비허용 URL과 외부 리다이렉트는 차단하고 인증 실패 시 공개 링크로 폴백하지 않는다. 기본값 `public`은 호환을 위한 현재 동작이며 운영 안전 승인으로 해석하지 않는다.
- 코드에는 비밀키·토큰이 없다. 운영 계정의 ADC/서비스 계정 접근권한 부여, 실제 인증 XLSX 응답, token 만료/재발급, 비공개 전환 이후 재시도는 **미검증 HOLD**다. 실제 자료·인증정보를 GitHub나 외부 AI로 전송하지 않는다.
- 후속 Windows 실제 저장소에서 인증 내보내기·정본 동기화·스케줄 상태의 표적 검사를 실행했다. ADC 초기화 실패도 기존 정상 행을 보존하면서 즉시 stale로 전환한다. 복구 불가 토큰 갱신 실패는 `GOOGLE_AUTH_REFRESH_REQUIRED`, 일시적인 갱신 장애는 `SOURCE_UNREACHABLE`로 구분한다. 응답 정리 오류는 인증 오류를 덮거나 원문 오류를 노출하지 않는다. Google 실계정 검증은 여전히 HOLD다.
- API 계약은 [Google Drive files.export 문서](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export)와 대조했다. 이 API는 내보내기 크기를 10 MB로 제한하며 읽기 전용 Drive scope를 허용한다. 원본이 API 한도를 넘는 경우에도 공개 링크로 우회하지 않는다.
- [Google Drive 오류 문서](https://developers.google.com/workspace/drive/api/guides/handle-errors)에 따라 403의 `rateLimitExceeded`·`userRateLimitExceeded`는 권한 거절과 구분해 일시 장애로 표시하고 기존 지연 재시도를 따른다. 오류 본문은 최대 16 KB까지만 판독하며, 알려지지 않은 사유나 권한 거절이 섞이면 접근 거절을 유지한다. 본문과 토큰은 출력하지 않는다.
- 전환 순서: 승인된 비운영 인증 자격 준비 → 두 원본에 명시적 읽기 권한 부여 → 격리에서 `--google-auth adc` 정상 읽기 확인 → 운영 동기화 설정·복구 계획 승인 → Google 공유를 제한 → 인증된 읽기 및 stale 표시 검증. 각각 별도 권한 승인이 필요하다.

#### 1. 0630_오제 수입을 못 가져오는 문제: 확인 사실과 미확정 원인

<a id="src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md--11-확인-사실"></a>
##### 1.1 확인 사실

- [Google 원본 구조 실측](google-ledger.md#src-docs-google-workbook-layout-md)의 2026-10-11 기록에 따르면 **`0630_오제`는 활성 메인 Google 장부에 존재**했다. **2026-10-25 사용자 확정: `0625_아키타`가 회계상 2분기 마지막 여행, `0630_오제`는 여행이 7월까지 이어져 회계상 3분기 첫 여행이다.** 출발일이 6월 30일이라는 이유로 2분기/보관 장부로 취급하면 안 된다. 최신 실원본 존재·값은 아직 재확인되지 않았다.
- 해당 여행의 당시 수입 제목 B6, 헤더 **B7:H7**, 지출 제목 B45, 헤더 B46:H46. 수입 B:H는 거래일자·이름·닉네임·예약금·잔금·추가금·금액(원); H열 수식은 E:G 합계 구조로 관측됐다.
- `app/google_authority.py`의 `parse_workbook()`은 이름 규칙에 맞는 여행 탭을 수집하며 `parse_trip_sheet()`은 수입/지출 **양쪽** 블록의 숫자·수식·합계·레이아웃을 검증한다. 개별 수입 행은 비공개 rows snapshot에 보존한다. 정확한 헤더와 수식 규칙에 맞지 않으면 비표준 또는 검증 실패가 될 수 있다.
- 현재 여행 화면은 `webapp/ledger_design.py:page()`이 `google_ledger_page.trip_income_html(tab_id)`을 별도 호출해 Google 수입 표를 구성한다. 반면 동일 화면의 `COST 기록` 수입 행/장부 상단 집계는 `ledger_board._income_rows()` / 내부 저장소를 사용한다. **Google에서 조회한 수입은 기존 COST 수입 행으로 자동 복제되는 구조가 아니다.** 두 숫자/영역의 출처를 구별해야 한다.
- `webapp/ledger_design.py`의 `previous_trip()`은 시작일이 **2026-06-25 이하인 여행만** 과거 분기 목록으로 보내므로 `0630_오제`의 여행 목록 위치 자체는 사용자 회계 분기 경계와 대체로 일치한다. 반면 `_quarter_of()`는 **시작 월 기준 달력 분기**를 계산해 6월 30일을 2분기로 반환한다. 따라서 이 함수가 추후 회계 분기 집계에 사용되는 경로는 사용자 지정 회계 분기와 분리해야 한다. **현재 수입 패널은 `_quarter_of()`가 아니라 Google key ↔ COST tab_id 및 검증 상태로 조회하므로, 이 차이만으로 현재 수입 실패가 증명되지는 않는다.**
- `trip_income_html()`은 mapping 파일에서 해당 COST `tab_id`에 해당하는 Google key를 **정확히 하나** 찾지 못하면 '수입 장부가 연결되지 않았습니다.'를 보인다. 원본이 있어도 자동 연결이 실패했을 수 있다. `auto_mapping_candidates()`는 Google/COST 표시명 고유 일치, 기간/연도 일치 등을 요구하며, `auto_link_trips()`는 연결을 파일로 유지한다.
- 현재 `trip_income_html()`은 `show_rows = bool(trip.get('verified')) and not numeric_gap` 조건이 참일 때만 수입 표를 출력한다. `trip['verified']`는 `app/google_authority.py:parse_trip_sheet()`의 **수입·지출 모두 검증된 값**을 반영한다. 따라서 **정상 수입 행을 읽었더라도 별도의 지출 검증 오류만으로 수입 표 전체가 숨겨질 수 있다.** 이는 확인된 코드상 과도한 표시 결합이다.
- `snapshot_for_display()`는 마지막 정상 동기화가 2시간을 넘거나 출처가 실패/오래된 경우 여행 전체를 미검증 처리해 수입 표를 숨길 수 있다. `trip_income_html()`은 원본 rows 부재, 합계 차이, 권한/선택 사본 미설정도 별도 상태로 처리한다.
- 이러한 **코드상의 가능한 차단 경로는 확인**했지만, **0630_오제 운영 스냅샷의 현재 mapping/상태/flags/실제 행을 읽은 것은 아니다.** 따라서 특정 한 원인을 확정했다고 주장하지 않는다.

<a id="src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md--12-읽기-전용-운영-진단-티켓-oze-income-diag-01"></a>
##### 1.2 읽기 전용 운영 진단 티켓: OZE-INCOME-DIAG-01

실행자는 승인된 운영 환경의 로컬 읽기 전용 점검을 수행하되 개인정보·금액 행 원문은 보고하지 않는다. 외부 모델/로그/PR에는 식별 불가 상태 코드와 건수만 전달한다. 사용자 허가 없는 운영 DB 조회·외부 API 반복 호출·설정 변경·Google 원본 재내보내기는 하지 않는다.

**진단 순서 (중복 검사·불필요한 동기화 금지):**

1. 대상 COST 여행의 `display_key`가 정확히 `0630_오제`인 현재 `tab_id`, `starts_on`, `event_year`, deleted/archived 여부를 식별한다. Google key와 표시명·연도 일치를 확인한다. 기존 수동 매핑을 변경하지 않는다.
2. `WEBLEDGER_GOOGLE_LEDGER_SNAPSHOT`, `WEBLEDGER_GOOGLE_LEDGER_ROWS`의 **설정 존재 여부만** 확인. 경로·원문·인증값은 외부 보고하지 않는다. 두 파일의 유효성/동일 generation, 마지막 정상 동기화 시각, `main/archive` 각각의 status/stale/error_code를 확인한다.
3. `google-tab-mapping.json`에서 Google `0630_오제` key → 현재 COST `tab_id`가 유일하게 연결됐는지 판정한다. 충돌·없음·과거 tab_id면 `TRIP_MAPPING_MISSING/AMBIGUOUS/STALE` 등으로 이유를 남긴다. 사용자 확인 없이 매핑을 수리하지 않는다.
4. 선택된 Google 원본이 **main**인지, 중복 사본/선택 미설정/사용자 선택으로 차단되는지 확인한다. 단지 6월 여행이라는 이유로 archive를 강제하지 않는다.
5. 해당 source의 공개 스냅샷에서 `layout`, `review flags`, `income.verified`, `expense.verified`, `trip.verified`, `income.total` 검증 상태와 개인정보 없는 **income row count**를 비교한다. 상세 비공개 rows는 해당 `source/key` 존재 여부와 **행 개수**만 확인한다. 숫자 금액/이름/예약번호/계좌 등 원문 출력 금지.
6. 수입만 정상이고 지출만 검증 실패했는지, 수입 행 합계 불일치/금액 캐시 부재인지, sync stale인지, 정본 사본 미선택인지, 권한 차단인지 **원인 코드를 분리**한다.
7. **회계 분기 분류를 독립 점검한다.** `0625_아키타`를 2분기 마지막, `0630_오제`를 3분기 첫 여행으로 취급하는지 확인하고, `previous_trip()`의 6월 25일 경계와 `_quarter_of()`의 달력 분기 계산을 구분한다. 이 계산이 실제 수입 조회 차단 조건인지 여부는 호출 경로로 입증한다.
8. 화면에서 COST 내부 수입 0건인 상황과 Google 수입 별도 패널 비노출 상황을 각각 판정한다. **서로 다른 증상**이므로 동일한 '수입 미수집'으로 보고하지 않는다.
9. 출력은 `trip_key / mapping_status / selected_source / source_freshness / layout / income_verified / expense_verified / rows_present / rows_count / ui_hide_reason / action` 형태의 비식별 요약만 제출한다. 원본 고객자료·금액은 현장 사용자 화면으로만 확인한다.

**진단 결과 상태:** `MAPPING_UNLINKED`, `SOURCE_STALE`, `SOURCE_UNAVAILABLE`, `COPY_CHOICE_REQUIRED`, `LAYOUT_NONSTANDARD`, `INCOME_BLOCK_UNVERIFIED`, `EXPENSE_ONLY_FAILURE_HIDES_INCOME`, `INCOME_TOTAL_MISMATCH`, `ROWS_MISSING`, `VIEWER_FORBIDDEN`, `COST_INCOME_NOT_IMPORTED_BY_DESIGN`, `UNKNOWN` 중 근거와 직접 대응되는 코드를 사용한다. 복수 원인 허용.

<a id="src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md--13-수입-표시-개선-oze-income-view-01"></a>
##### 1.3 수입 표시 개선: OZE-INCOME-VIEW-01

- **읽기와 표시를 분리한다.** 수입 표를 보이는 조건을 여행 전체 `verified`와 직접 결합하지 말고 **선택된 원본의 수입 블록 상태**로 평가한다. 지출 검증만 실패했으면 정상 수입 행은 계속 표시하되, 여행 전체 회계/순수익의 검증 실패는 별도 경고로 유지한다.
- 수입 블록 금액/합계 자체가 검증되지 않으면 확정 수입 합계를 표시하지 않는다. owner에게 조회 가능한 행의 원문 상태를 '수입 금액 검증 필요'로 설명할 수 있으나, 미검증 금액을 확정 매출로 승격하지 않는다. 비공개 rows가 없으면 정상 0건으로 꾸미지 않는다.
- Google snapshot이 stale이면 승인된 마지막 정상 **읽기 사본**을 '마지막 정상 자료 / 동기화 시각 / 최신 여부 미확인'으로 구별하여 표시할 수 있다. 권한을 확장하지 않고, stale 자료를 현재 확정 수입이나 재대조 정본으로 쓰지 않는다.
- 연결·사본·파싱·금액·행 부재·열람 권한을 사용자에게 구별 가능한 상태 메시지로 표시한다. 단순히 '내역이 없습니다'로 합치지 않는다.
- 내부 COST 수입과 Google 수입을 합산·자동 기장·자동 복제하지 않는다. 'COST 내부 기록 수입'과 'Google 정본 수입(읽기 전용)'을 분명히 구분한다.
- `0630_오제` 전용 하드코딩/임의 레거시 양식 호환기를 만들지 않는다. 기존 `매출자료 양식_rev` 구조 계약을 지키고, 이 여행의 원인이 어떤 조건인지 확인한 뒤 보편적인 표시 버그만 수정한다.

#### 2. 기존 Google 장부와 COST 웹 장부 간 '볼드체 동일 거래 후보' 규칙

<a id="src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md--21-사용자-확정-매칭-조건"></a>
##### 2.1 사용자 확정 매칭 조건

동일한 **여행**의 **지출 거래끼리** 비교할 때, 아래 조건을 모두 만족하면 **같은 거래의 표시용 후보**로 간주하고 해당 **웹 장부 거래 행 전체를 볼드체**로 강조한다.

1. **금액이 정확히 일치해야 한다 (필수).** 통화와 부호/거래 방향까지 동일해야 한다. KRW 원 단위 정수 비교를 기본으로 하며, 외화 환산액을 원화 원본과 무조건 동일시하지 않는다. '100,000원'과 숫자 100000은 동등하지만, +100000과 -100000은 동등하지 않다.
2. 다음 네 개 필드 중 **하나 이상**이 일치하면 충분하다.
   - **날짜:** 실제 거래일자 또는 기존 계약이 권위 있게 정한 장부 날짜가 동일. 날짜 정규화가 불가능하면 날짜 일치로 세지 않는다.
   - **가맹점명/거래처:** 웹 장부의 원본 가맹점/거래처와 Google 지출 C열 '항목'(지급처)의 정규화한 이름이 동일. 대소문자·Unicode NFC·앞뒤/연속 공백 정리 등 안전한 비교만 허용. 부분 문자열·유사 발음·AI 유추는 일치로 세지 않는다.
   - **분류:** 웹 장부의 확정/표시용 지출 분류와 Google 지출 D열 '내용'의 검증된 대응값이 동일. 서로 다른 의미의 '항목'/'내용'을 임의 바꿔 비교하지 않는다.
   - **예약번호:** 웹 장부의 확인된 예약번호와 Google 지출 F열의 실제 예약번호가 완전 동일. 비어 있음, placeholder, 불확실한 제안 ID는 일치로 인정하지 않는다.
3. 필드가 없거나 빈 값, 0원과 빈 문자열, 조회 오류로 비교 불가능한 값은 '일치'로 세지 않는다. **0원 거래끼리는 금액이 0원으로 실재함이 확인된 경우** 다른 필드까지 일치해야 후보가 된다.

**Boolean 계약:**

`match_candidate = same_trip && same_kind_expense && amount_valid && amount_currency_direction_equal && (date_equal || merchant_equal || category_equal || reservation_equal)`

예시:

| Google 지출 vs 웹 지출 | 표시 |
| --- | --- |
| 금액 120,000원 동일 + 날짜 동일, 나머지 다름 | **볼드** (금액+날짜) |
| 금액 120,000원 동일 + 가맹점명 동일 | **볼드** (금액+가맹점) |
| 금액 120,000원 동일 + 분류 동일 | **볼드** (금액+분류) |
| 금액 120,000원 동일 + 예약번호 동일 | **볼드** (금액+예약번호) |
| 금액 동일, 다른 네 필드 모두 다름 또는 비어 있음 | 일반 글씨 |
| 날짜·가맹점·예약번호 동일, 금액 다름 | 일반 글씨 + 필요 시 차이 안내 |
| 금액만 같은 서로 다른 여행/수입 대 지출 | 일반 글씨 |
| 금액·분류가 같은 Google 거래가 2건이고 웹 거래가 1건 | **볼드 + 복수 후보 경고**, 자동 1:1 확정 금지 |

<a id="src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md--22-ui와-사용자-의미"></a>
##### 2.2 UI와 사용자 의미

- 대조는 **선택된 Google 정본 한 사본(main 또는 archive)**과 동일 COST 여행의 웹 장부 지출만 사용한다. 메인+보관을 모두 합쳐 매칭하거나 중복 집계하지 않는다. 동일 여행 연결/정본 선택/동기화가 미확정이면 강조하지 않고 근거 확인 필요를 표시한다.
- 일치 거래의 **웹 장부 행 텍스트(날짜·가맹점/내용·분류·이용일·금액)를 `font-weight: 700` 정도로 볼드체** 표시한다. 사용자 키보드/스크린리더를 위해 `Google 장부 대조 후보: 금액+날짜` 같은 화면 낭독 가능한 근거 설명을 제공한다. 선택/호버/기존 상태 색상만으로 매칭을 표현하지 않는다.
- 현재 화면에 Google 지출 행이 함께 보이는 경우 대응 원본 행도 구별 가능하게 표시해도 된다. 기본 필수는 **웹 장부 거래 강조**다.
- **'동일 거래 후보'는 시각적 대조 편의 기능**이다. 원본 거래 ID가 Google에 없을 수 있으므로 '장부 반영 확정', '회계 동일성 검증 완료', '중복 거래 확정'처럼 표시해서는 안 된다. 사용자가 말한 '같은 거래로 보고 볼드체'를 화면 판정으로 구현하되 **데이터 정본 합치기/중복 제거/실제 전기는 하지 않는다**.
- 한 Google 행이 여러 COST 거래와 맞거나, 한 COST 거래가 여러 Google 행과 맞으면 **해당 후보 모두 볼드 + '복수 후보 · 확인 필요'** 표시. 임의로 첫 번째 1:1 쌍을 확정하거나 나머지 행을 숨기지 않는다. 서로 다른 실제 결제 ID는 영구 독립이다.
- 일치 근거가 있었던 값이 바뀌거나 선택 원본이 전환·stale가 되면 캐시/표시를 재계산 또는 철회한다. 추정 결과를 DB의 확정 외래키·수동 결정으로 저장하지 않는다.

<a id="src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md--23-읽기-전용-데이터성능권한-경계"></a>
##### 2.3 읽기 전용 데이터·성능·권한 경계

- 웹 장부 `webapp/ledger_design.py`의 `_selected_rows()`, `_table_html()`과 Google `webapp/google_ledger_page.py:owner_rows()`의 선택 사본 조회는 기존 경로를 우선 재사용한다. 정본 지출 B:H 대응은 **B 날짜 / C 지급처 / D 분류 / E 기간 / F 예약번호 / G 증빙 / H 금액**이다. 웹 거래의 실제 필드 위치는 감사로 확정한다.
- 비교용 Google 원본은 기존의 세대 일관성을 가진 비공개 snapshot에서 서버 내부에서만 조회한다. 고객 이름·예약번호·시트 원본은 권한 없는 viewer/public 응답, JS 전역 객체, 로그·PR로 누출하지 않는다. owner에게만 원본 상세 및 근거를 노출하며 기존 viewer 여행별 열람 권한보다 넓히지 않는다.
- `GET /board` 및 대조 API는 DB/Google에 쓰기를 하지 않으며 Google API 호출이나 주기 동기화를 화면 요청에 새로 추가하지 않는다. 선택된 정상 snapshot이 없으면 '대조 불가'로 표시하며 금액만 보고 억지 매칭하지 않는다.
- 현재 여행/선택 원본/원본 generation/페이지 필터 변경 시 일치 후보만 재산정한다. 월별·여행별 거래 수가 커도 지출 금액별 인덱스(hash map 등)로 N×M 전수 비교를 피한다. 원본 텍스트 이스케이프와 시스템 라이트/다크 스타일·모바일 표를 보호한다.

<a id="src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md--3-개발-티켓과-수락-기준"></a>
#### 3. 개발 티켓과 수락 기준

**INCOME-ROOT-01:** §1.2 읽기 전용 진단으로 `0630_오제`의 운영/스냅샷 실제 차단 원인 코드를 판정한다. 원본 권한 없으면 `UNVERIFIED / ACCESS_BLOCKED`로 종료하고 근거 없는 수정에 착수하지 않는다.

**INCOME-VIEW-01:** §1.3 수입/지출 검증 게이트 분리, 상태 안내, 출처 구분. 수입이 정상이고 지출만 실패하는 합성 사례에서 수입은 보이되 전체 손익은 확정되지 않는지 검증한다.

**LEDGER-MATCH-READ-01:** 실제 웹 지출 필드와 Google 정본 지출 필드를 증거 기반 연결하고, side effect 없는 동일 여행·금액+1 조건 비교 유틸리티/서버 표시 모델 구축.

**LEDGER-MATCH-UI-01:** 볼드 강조, 근거 설명, 복수 후보, 없음/지연/권한 차단, 반응형 접근성 구현.

| AC | 테스트 가능한 완료 조건 |
| --- | --- |
| INCOME-AC-01 | 0630_오제 정확한 Google 키·COST tab_id·선택 source·수입 행 존재·실패 코드가 실제 읽기 근거로 확인되거나 미검증으로 명확히 보고된다. 실원문 Git/외부 모델 미반출. |
| INCOME-AC-02 | `0625_아키타`는 2분기 마지막, `0630_오제`는 3분기 첫 여행이라는 사용자 지정 회계 분기 경계를 따른다. `0630_오제`가 출발일 6월 30일만으로 2분기 보관 장부에 잘못 라우팅되지 않고 기존 자동/수동 mapping 및 정본 선택이 보호된다. |
| INCOME-AC-03 | 수입 행과 합계가 독립 검증됐으면 지출 불일치만으로 수입 행이 숨지 않는다. 다만 전체 회계/회사수익은 미검증으로 유지된다. |
| INCOME-AC-04 | 연결 없음/사본 미선택/동기화 지연/수입 검증 실패/행 부재/권한 차단이 구별되며, Google 수입을 내부 COST 수입으로 자동 추가하지 않는다. |
| MATCH-AC-01 | 같은 여행의 **부호·통화·금액 동일 + 날짜/가맹점/분류/예약번호 중 정확히 하나 동일**인 네 독립 fixture가 모두 볼드체로 표시된다. |
| MATCH-AC-02 | 금액만 동일, 다른 여행, 다른 거래 유형, 금액·통화·부호가 다른 경우 볼드체가 아니다. |
| MATCH-AC-03 | Google 1건 ↔ 웹 다수 또는 Google 다수 ↔ 웹 1건은 볼드 후보를 보여 주되 복수 후보 상태를 표시하고 자동 병합/기장/확정하지 않는다. |
| MATCH-AC-04 | source 선택 변경, 원본 snapshot stale/부재, 미연결 여행에서는 오래된 강조를 유지하지 않는다. |
| MATCH-AC-05 | 모든 비교는 읽기 전용, 원본/Google/내부 장부 거래·여행/권한/수동 결정 불변. viewer는 허용된 여행의 필요한 표시만 보며 개인·예약 원문 누출 금지. |
| MATCH-AC-06 | 기존 거래 정렬·금액·명세상 UI/접근성·모바일을 유지하고 필요한 표적 합성 테스트와 diff, 누락된 운영 검증 경계를 PR에 남긴다. |

실행 순서: **INCOME-ROOT-01(현장 접근 허용 범위 내) + LEDGER-MATCH-READ-01(합성 개발) → INCOME-VIEW-01 → LEDGER-MATCH-UI-01**. 독립 구현 작업은 서로 다른 브랜치/worktree로 수행하며 동일 파일 동시 수정 금지. 테스트는 관련 표적만 한 번 실행. 운영 배포와 실제 고객 자료 확인은 별도 승인/권한 필요.

<a id="src-docs-trip-income-visibility-and-ledger-match-spec-20261025-md--4-진행-상태-및-변경-이력"></a>
#### 4. 진행 상태 및 변경 이력

- 2026-10-25: 사용자 요청을 본 명세에 기록. 위 §1의 Google 원본 정보는 **과거 실측**, 수입 숨김 조건은 **현재 저장소 코드 분석**이다.
- 실제 0630_오제 운영 상황의 특정 차단 원인: **UNVERIFIED**. Google 연결 파일·비공개 rows·현재 운영 페이지를 직접 읽지 않았다.
- 대조 볼드 기능 및 수입 표시 개선: **SPEC_ONLY / NOT_IMPLEMENTED**.
- 문서 PR 또는 병합만으로 코드 적용·테스트·운영 배포 완료로 표시하지 않는다.
