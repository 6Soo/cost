# 대사 규칙 (카드 거래 ↔ 예약 ↔ 여행)

이 문서는 카드 거래에 항목과 여행을 정하는 규칙 전체를 한곳에 적는다. 날짜 판정 함수와 출처 이름은 `app/reconciliation.py`, 분류 순서는 `app/classify.py`, 여행 검증과 예약 근거는 `webapp/card_flow.py`에 있다.

## 1. 날짜의 의미

| 날짜 | 출처 | 쓰는 곳 |
|---|---|---|
| 카드 이용일 | 명세에 `이용일` 열이 있을 때 (H.xlsx, G.xlsx) | 카드 거래의 날짜. `approval_date` 칸에 들어간다 |
| 카드 승인일 | 명세에 `승인일` 열만 있을 때 (E, F, KB) | 이용일이 없을 때 카드 거래의 날짜 |
| 매입일(청구일) | 모든 명세 | 대사에 쓰지 않는다 |
| 예약 이용기간 | OTA 메일·포털 (숙박: 체크인~체크아웃, 항공: 가는편~오는편) | 여행과 겹치거나 덮는지 판정 |
| 여행 기간 | 여행 탭 (시작일~종료일) | 종료일은 마지막 이용일을 포함한다 |

- 카드 이용일과 예약 이용기간은 다른 날짜다. 카드 쪽은 `card_use_date()`, 예약 쪽은 `covers_stay()` / `overlaps_stay()`로 판정한다.
- 숙박은 밤 단위로 본다. 여행의 밤은 시작일 밤부터 종료일 전날 밤까지다(종료일은 체크아웃하고 돌아오는 날). 그래서 숙박이 여행 안이려면 체크인 ≥ 시작일, 체크아웃 ≤ 종료일이어야 한다. 여행 종료일에 체크인하는 숙박은 그 여행과 겹치지 않는다(다음 일정의 숙박이다). 시작일에 체크아웃하는 숙박도 겹치지 않는다.
- 항공은 출발일과 도착일을 모두 이용일로 본다. 여행 종료일에 출발하는 귀국편은 그 여행과 겹친다.

## 2. 여행의 검증 (`CardFlow.trip_valid`)

자동 배정은 검증된 여행에만 한다. 여행이 삭제·보관되지 않았고, 아래 중 하나를 만족하면 검증된 여행이다.

1. **구글 여행 탭의 시트 기간과 같다.** 여행 탭이 구글 탭에 연결되어 있고(`google-tab-mapping.json`), 구글 스냅샷의 기간이 여행 탭의 시작일·종료일과 같다. 시트 제목이나 지출 행 기간에서 읽은 종료일만 인정한다. 다음 여행 전날로 추정한 종료일(`PERIOD_END_FROM_NEXT_TRIP`)과 빈 종료일은 인정하지 않는다.
2. **기존 일정 권한 기록과 같다.** 권한 파일(`trip-authority.json`)의 기록과 증거 파일이 여행 탭과 같다. 기록의 원본이 옛 장부 스냅샷이면, 현재 검토 스냅샷의 같은 시트 제목이 그대로여야 한다. 장부를 옮겨 현재 스냅샷에 시트가 없을 때는 해시로 확인한 원본 제목을 쓰되, 구글 탭이 연결되어 있고 시작일이 같으며 구글 쪽 종료일이 추정값일 때만 쓴다. 구글 시트에 다른 기간이 적혀 있으면 이 경로로 검증하지 않는다.

시트의 기간을 고치면 여행 탭의 기간도 같아야 다시 검증된다. 해시를 손으로 맞출 필요는 없다.

## 3. 분류 순서 (앞이 우선)

0. **보호**: 사용자가 정한 거래(`user_decision`, `user_exception`, `decided_at`)와 장부에 기록된 거래는 분류하지 않는다. 정리 완료 기간(`review_from`, 운영 2026-04-01) 이전 거래는 `preserved`로 두고 분류하지 않는다.
1. **일반 규칙 단계** (`_classify_transaction`): 맞는 규칙을 모두 모은다. 서로 다른 항목·여행을 내면 `rule_conflict`로 확인 대상이다.
   - 예약 증거 규칙 (`ota-mail-live`, `ota-portal-live`, 실행 때 생성): 확정·완료·예정 예약의 이용기간을 덮는 검증된 여행이 하나뿐이면 그 여행이다(`booking_trip`). 저장된 여행 이름이 바뀌었어도 이용기간으로 찾는다.
   - 장부의 미래 적용 규칙 (`board-rule`): 같은 가맹점의 일반 카드 규칙을 대체한다.
   - 저장된 가맹점 규칙: 가맹점 → 항목. 여행은 정하지 않는다.
   - 저장된 가맹점 현지 사용 규칙 (`travel_country`): 카드 사용 국가와 날짜에 맞는 검증된 여행이 있으면 그 여행이다(`retail_trip`). 없으면 `travel_location_hold`로 확인 대상이다.
   - 맞는 규칙이 없으면 카드사 업종(항목만) → 가맹점 패턴(항목만) → 현지 사용 기본 규칙(`*` → 현지경비 + 여행) 순서다. 예약·온라인 결제는 현지 사용으로 보지 않고 `booking_evidence_needed`로 둔다.
2. **카드 3820 싱가포르 예외**: 2026-09-19~09-24 카드 3820 사용은 싱가포르 여행이다(코드 고정, 사용자 지정).
3. **거래별 추론 단계**: 1단계에서 여행이 정해지지 않았을 때만 본다.
   - 사용자가 예약마다 고른 여행(`owner-ota-booking`)이 같은 거래의 다른 추론보다 앞선다.
   - 나머지 추론이 서로 다르면 `inference_conflict`로 확인 대상이다. 같으면 확신이 높은 근거를 쓴다.
   - 확정 예약의 이용기간을 덮는 검증된 여행이 하나뿐이면 그 여행으로 추론한다(`auto-ota-period`).
   - 소유자가 승인한 추론(`owner-authorized-inference-20261003`)은 카드 날짜가 여행 시작보다 30일(`LEAD_DAYS`)을 넘게 앞서면 자동 배정하지 않는다.
   - 저장된 추론은 다음 경우 쓰지 않는다: 예약 취소, 이용기간 충돌, 확정 이용기간이 검증된 여행 하나에 맞지 않음, 사용자가 예약 배정을 함, **확정 전이라도 예약 이용기간과 하루도 겹치지 않는 여행을 가리킴**. 사용자 예외(`owner-country-exception-20261003`)는 이 확인에서 뺀다.
4. **카드 3820 잔여**: 위에서 아무것도 정해지지 않은 카드 3820 구매는 분기 기타비용이다.

## 4. 확정 여부

- 예약 메일의 제목에 `확정`이 있으면 확정으로 본다. 숙박 메일과 결제 대사 모두 같은 규칙을 쓴다 (`ota_mail.extract_mail`, `lodging_mail_facts`, `lodging_mail_matches`).
- 확정 상태는 `confirmed`, `completed`, `upcoming`이다 (`CONFIRMED_STATUSES`).
- 결제 메일만 있고 확정 메일이 없으면 `observed`(수집됨)이며, 이용기간으로 배정하지 않는다. 다만 3단계의 이용기간 가드에는 쓴다.
- 취소 메일은 `cancelled`이다.

## 5. 저장된 규칙의 정리 (`tools/consolidate_rules.py`)

저장된 규칙(`cost_classification_rules`)은 지우지 않고 `status='retired'`로 정리한다. 실행마다 `change_log`에 `rule.retired`와 실행 ID가 남고, `--restore <실행 ID>`로 되돌린다.

정리 대상은 두 가지다.

- `closed-transaction`: 거래 하나에 묶인 규칙인데 그 거래가 장부 기록·사용자 결정·정리 완료 기간 보존으로 닫혀 다시 분류되지 않는다.
- `same-as-local-default`: 가맹점 현지 사용 → 현지경비 규칙인데 현지 사용 기본 규칙과 결과가 같다. 가맹점 패턴이 있거나, 그 가맹점 거래에 카드사 업종이 있거나, 같은 가맹점에 다른 규칙이 있으면 정리하지 않는다.

2026-10-14 운영 사본 기준: 활성 2,172개 → 779개 (정리 1,393개: 닫힌 거래 616, 기본 규칙과 같음 777). 같은 데이터로 전체 분류를 다시 돌려 거래 6,037건의 항목·여행·상태가 하나도 바뀌지 않음을 확인했다. 37건은 분류 근거 문구만 "가맹점 일치"에서 "현지 사용 기본 규칙"으로 바뀐다.

## 6. 판정 함수 요약

| 함수 | 위치 | 의미 |
|---|---|---|
| `card_use_date(tx)` | reconciliation | 카드 이용일 또는 승인일 |
| `covers_stay(ts, te, ci, co, service=)` | reconciliation | 체크인(출발일) ≥ 시작일이고 체크아웃(도착일) ≤ 종료일 |
| `overlaps_stay(ts, te, ci, co, service=)` | reconciliation | 숙박은 여행의 밤이 하나라도 겹침, 항공은 이용일이 하루라도 겹침 |
| `payment_within_lead(day, ts)` | reconciliation | 여행 시작 30일 이내 |
| `trip_valid(tab)` | webapp/card_flow | 2장의 여행 검증 |
| `booking_trip(tx, period)` | webapp/card_flow | 이용기간을 덮는 검증된 여행이 하나뿐인지 (여러 개면 저장된 이름으로 고름) |
| `retail_trip(tx, country)` | webapp/card_flow | 현지 구매 또는 추론 여행 확인 (30일 규칙 포함) |
| `_period_trip(candidates)` | webapp/ota_catalog | 검증된 여행 중 덮는 여행이 하나뿐인지 |
| `_relation(stay, trip, service=)` | webapp/ota_catalog | 덮음 / 일부 겹침 / 없음 |

`service` 인자는 항공 예약일 때 참이다. 항공 여부는 예약 라벨에 `항공`이 있는지로 판단한다 (`ota_catalog._build_index`), 또는 예약 기간 초안의 `item == 항공료`로 판단한다 (`card_flow._classify`).

## 7. 정해야 할 것

1. **결제 뒤 가까운 여행 추론 91개**는 결제일로 여행을 추정한다. 지금은 30일 규칙과 이용기간 가드 안에서 자동 배정한다(정리 후 분류에서 90건, 4,850,078원). 추천만 하고 자동 배정하지 않을지 정해야 한다.
2. **구글 시트에 종료일이 없는 여행 8개**(0721_황금해안, 0830_변산, 0903_양평, 0912_세종, 0915_길상사, 0916_박달고치, 1104_아오모리, 0302_야쿠시마)는 검증되지 않는다. 시트 제목에 종료일을 적으면 검증된다.
3. **여행 경계일의 현지 구매**: 한 여행의 종료일과 다음 여행의 시작일이 같고 나라가 같으면, 그날 구매는 그날 시작하는 여행으로 간다(0924_야마구치 → 0927_북큐슈 6건). 확인 대상으로 둘지 정해야 한다.
4. **현지 구매의 나라 매핑이 코드에 고정되어 있다** (`card_flow.retail_trip`의 `countries` 표). 새 행선지는 현지 사용으로 배정되지 않는다.
5. 같은 판정이 두 경로에 남아 있다. 예약 기간 초안(`card_flow._classify`)과 자동 배정(`_booking_period_assignments`)이다. 같은 판정 함수를 쓰지만 호출 흐름이 나뉘어 있다.
