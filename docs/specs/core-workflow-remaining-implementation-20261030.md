# COST 본질적 업무 완성: 잔여 구현·운영 수락 작업 (2026-10-30)

> 상태: **실행 명세만 추가. 코드 구현·운영 데이터 변경·배포 없음.**
>
> 핵심 목표: 카드·OTA·현지 영수증 원본 → 안전한 중복/취소/환불 대사 → 실제 여행·분기 귀속 → 사용자 검토 → Google B:H 수기 복사 → Google 정본 읽기에서 반영·마감 확인.
>
> Google은 유일한 최종 회계 정본이며 **자동 쓰기 금지**. 원천·수동 결정·기존 장부/금융 링크·환불 보류는 변경 전에 보호한다. 기존 구현을 재구축하지 말고, 각 작업의 '미구현'과 '운영 미수락'을 구분한다.

## 0. 실행 전 게이트

1. 최신 `main`·운영 SHA·열린 PR·현재 API/DB 스키마·Google 원본 스냅샷의 실제 상태를 읽기 전용으로 재조사한다. 이 문서의 과거 수치나 완료 상태를 현재 실측으로 간주하지 않는다.
2. `docs/session_handoff.md`, `docs/operations.md`, `docs/specs/google-ledger.md`, `docs/specs/finance.md`, `docs/specs/ota.md`, `docs/specs/participants.md`, `docs/specs/remaining-acceptance-20261030.md`와 최신 구현을 대조한다.
3. 각 작업을 **코드 없음 / 코드 있음·합성 검증 / 운영 read-only 수락 / 운영 실쓰기 승인 대기 / 외부 근거 대기 / 사용자 보류** 중 하나로 분류하고 증거·책임자·다음 게이트를 기록한다.
4. 기존 수집/업로드 **사용자 보류 유지**. Google 자동 쓰기 금지. 실제 금융·분류·참가자·원본 DB 쓰기, 카드 다운로드, 원격 메일 전환, 배포는 기존 승인/백업/복구 게이트 없이는 실행하지 않는다.
5. 새 화면·추가 상태·중복 대사 엔진을 만들기보다 기존 경로를 재사용한다. 독립 사실인 예약 연결, 결제 확인, 여행 귀속, Google 반영, 실제 환급을 하나의 '완료'로 합치지 않는다.

## P0: 핵심 회계 흐름

### CORE-01. 카드 원천 수집 완결성

- 기존 국민/하나 카드 업로드·중복 검증·수집 기능을 코드/운영 증거로 재감사하고 카드사·국내외·이용일·승인/매입·환불/취소별 누락 범위를 조회한다.
- 카드 업로드 기능 자체의 기존 구현을 반복하지 않는다. 원본 식별·파일 재업로드 idempotency·원천 보존·분류 수동 override·원자성·재시도·권한·XLSX 보안 회귀를 유지한다.
- **카드 수집·업로드는 보류 중이므로 현 단계에서 실제 다운로드·DB 적재 금지.** 수집 재개가 승인될 때 필요한 실행 계획·읽기 전용 사전검사·기대 행수/파일 지문/중복 보고만 준비한다.
- 수락: 승인 후 카드사별 최신 허용 구간의 원본 수량·중복·신규·보류·누락 보고, 운영 복구/재실행 무쓰기 확인. 승인 전에는 **WAIT_USER_APPROVAL**.

### CORE-02. OTA·카드·환불 금융 대사 완결

- OTA 정규 예약/공급자별 원천·카드 결제·기존 수동 링크·환불 원결제·보류를 **실제 원본 증거**로 조회하고, 분류 완료와 결제/환급 완료를 구분하는 누락/충돌 목록을 만든다.
- 기존 중앙 OTA solver·projection과 `row_assignment` 공유 판정을 재사용한다. 동일일·동액 후보, 부분 환불, 원결제 누락, 예약 취소, 카드 미매입, 기간 근거 불일치를 별도 상태로 유지한다.
- 외부 원결제 증거가 없으면 **WAIT_EXTERNAL_EVIDENCE**로 유지. 카드/OTA 임의 연결, 금액 재작성, 자동 분류 강제 확정 금지.
- 수락: 근거 있는 표적 케이스에서 유일한 대사 판정·수동 결정 우선·환불 독립성·원본 불변·재실행 무쓰기; 증거 없는 건은 설명 가능한 보류 목록으로 남는다.

### CORE-03. Google 최종 장부 반영 검증

- 이미 배포된 **GEMN 여행+signed KRW 금액 그룹 M:N 대조** 및 수기 Google 지출 중복 방지 로직을 재사용한다. **새 매칭 엔진을 만들지 않는다.**
- 모든 접근 가능한 여행을 대상으로 Google 원본 매핑/최신성/권한·실제 지출 범위·COST 지출 원행과 Google 원행 수량을 read-only 감사한다. 검증 불가 여행은 0건/완료로 속이지 않는다.
- 그룹별 일치·부분·미기록·Google 전용·비교 불가를 분리하고 원본 행 번호·마지막 정상 동기화 시각·건수 차이·복사 대상 여부를 명시한다. 동일 금액 반복 거래를 1:1로 임의 확정하지 않는다.
- Google 자동 쓰기 없이 **사용자 수기 복사→다음 정본 읽기→실제 반영 확인** 경로를 실제 승인된 여행 1~2개로 수락한다. 복사 클릭만으로 반영 완료 금지.
- 수락: 정상/오류/오래된 스냅샷·원본 행 이동·반복 결제·금액 차이·Google 전용 이체를 포함해 거짓 초록 체크0, 실제 시트 변경 없음.

### CORE-04. 여행별 마감·누락 검토

- 여행별 '원천 수집 상태 / 미배정·보류 / OTA 대사 / 영수증 / Google 반영 / Google 보관본 이동(마감)'을 기존 화면·API에서 한 흐름으로 확인할 수 있는지 조사한다.
- 기존 상태가 분산된 경우 **새 저장 상태를 만들지 않고** 현재 source of truth에서 읽기 전용 집계·탐색 링크를 제공한다. 분기 기타비용은 실제 여행으로 위장하지 않는다.
- 여행 마감은 **메인 Google 장부에서 보관 장부로 여행 시트가 이동해 정상 조회된 경우**에만 확정한다. 종료일·COST 분류 완료·TSV 복사는 마감 증거가 아니다.
- 수락: 완료/진행/보류/Google 조회 불가/메인·보관 중복/마감 후 변경 케이스, 사용자 권한·원본·확정 수익 보호.

## P1: 영수증·운영 수락

### CORE-05. 영수증 실제 입력→지출 검토→Google 복사

- 현재 다중 영수증 업로드/OCR/원본 보관/JPY 처리/결제수단 분기/카드 매입 연결/복사 기능의 실제 구현 범위를 먼저 감사한다.
- A4 여러 영수증, 현금, 개인카드(사용자 회사비용 인정), 법인카드(기존 카드 거래의 증빙으로만 연결), 불명확 금액 HOLD, 환율·금액 출처를 테스트한다.
- 기존 카드 결제를 영수증 때문에 2건으로 늘리지 않는다. 개인카드 사후 이체 자동 상계/중복 처리 기능은 **명시적 비범위**.
- 합성 OCR 테스트 후 실제 원본은 승인된 격리/권한 경로로만 수락. 고객 이미지·식별정보를 Git/외부 모델에 보내지 않는다.
- 수락: 원본 1건당 적정 비용 1건 또는 증빙 연결 1건, 금액/여행/증빙 유형 검토, Google B:H 복사, 재실행 무중복.

### CORE-06. Google 읽기 동기화·오류 복구

- 기존 정본 읽기 작업/캐시/정각 주기/메인·보관 양쪽 원본/권한을 점검한다. 정상 원본 무변경 시 불필요한 재파싱·DB 쓰기 방지.
- 원본 API 오류·권한 만료·부분 실패·시트 이동·원본 구형 양식·동기화 지연 때 마지막 정상 시각과 보류 이유를 표시한다. 이전 성공 스냅샷을 빈 데이터로 덮지 않는다.
- 사용자 직접 Google 수기 작성과 수집 타이밍 경계를 검증한다. 자동 쓰기 기능은 개발하지 않는다.
- 수락: 실제 읽기 스케줄·최신성·복구·보관 이동·마감 후 변경의 운영 read-only 증거. 스케줄 변경/전환은 별도 승인.

### CORE-07. 운영 end-to-end·성능·실기기 수락

- 카드 원본→OTA 근거→귀속→검토→TSV→Google 정본 확인의 대표 1~2개 실제 여행 경로를 읽기 전용으로 우선 추적한다. 쓰기/재배포는 승인 게이트 분리.
- 실제 카드 전체 내역 모바일 UI(320/375/390/430/759/760/900px), 카드 상세·필터·긴 가맹점/금액, 지출 M:N PC 상태 열, 다크/라이트, Safari/Android 실기기 수락. 합성 Chromium 통과를 실기기 수락으로 바꾸지 않는다.
- 느린 초기 카드 요청과 실제 p95의 구간별 계측(연결/SQL/렌더/외부 IO)을 재현한 뒤 근거 있는 병목만 최적화. 무근거 캐시·전면 리팩터링 금지.
- 수락: 대표 경로 실제 원본/정본 대조, UI 회귀 없음, 운영 health/ready·보호 API·13개 금융 보호 테이블 전후 불변, 백업/복구 증거.

## P2: 참가자·보험 및 주변 업무

### CORE-08. 보험 마스킹 명단→참가자 DB→수입 대조 실제 수락

- 기존 마스킹 명단 후보 대조 기능은 이미 배포됐으므로 재구현하지 않는다. 실제 API의 `configured=false/STORE_UNAVAILABLE` 문제와 참가자 DB/등록 영수증 수락을 별도 작업으로 추적한다.
- 가림 이름·동명이인·닉네임 입금·동일 금액 복수 입금·계약별 여행 연결에서 **후보와 확정 동일인/실제 가입/입금 수령**을 분리한다.
- Travel INS 연계는 현재 main과 호환되는 경로만 검토하고, 증빙 없는 자동 등록·보험 가입 완료 승격·개인정보 외부 전송을 하지 않는다.
- 수락: 실제 구성/권한/수신 영수증/중복·재시도 보호가 검증된 후 별도 승인된 end-to-end 연결. 증거가 없으면 WAIT_EXTERNAL_EVIDENCE.

## 작업 분리 및 순서

1. **감사(읽기 전용):** CORE-01/02/03/05/06/08을 병렬 조사하고 완료 기능과 실제 미결만 이슈화한다.
2. **최소 코드 구현:** CORE-03/04/05/06 중 확인된 결손을 우선 구현. 기존 GEMN·OTA·카드 분류·Google API 재사용, 새로운 상태 테이블/서비스 금지.
3. **합성 보호 테스트:** 각 작업별 표적 테스트 + 금융/Google 권한·환불·중복·수동 결정 회귀.
4. **운영 읽기 전용 수락:** CORE-07을 통해 실제 여행/Google 원본/운영 로그의 검증 결과를 정리.
5. **외부 게이트:** 카드 재수집·참가자 실제 DB 연결·원결제 증거·운영 쓰기·배포는 사용자 승인/외부 자료 충족 후 개별 실행.

## 보고 형식 및 완료 정의

각 CORE 작업에 **현재 근거 / 구현 변경 / 테스트 / PR·병합 / 운영 배포 / 실제 데이터 수락 / 보류 사유 / 다음 실행자**를 별도로 기록한다. `SPEC_ONLY`, `CODE_COMPLETE`, `MERGED`, `DEPLOYED`, `READONLY_ACCEPTED`, `WAIT_USER_APPROVAL`, `WAIT_EXTERNAL_EVIDENCE`를 혼용하지 않는다. 문서 작성은 기능 완료가 아니다.

**비범위:** Google API 자동 쓰기, 모든 카드 무승인 재수집, 임의 OTA 결제 확정, 외부 증거 없는 보험 가입 확정, 개인카드 상환 자동 상계, 대규모 마이크로서비스화, 새 대시보드만을 위한 중복 저장 구조.
