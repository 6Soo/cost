# 모든 OTA의 직접 수집·메일 통합 DB

## 현재 승인과 범위

2026-10-20 사용자가 모든 OTA 직접 수집 자료와 메일 자료를 하나의 DB에서 관리하도록 지시했다. 이 문서가 현재 저장 구조 변경의 기준이다. 앞서 승인한 아고다 상세 수집은 계속하며 트립닷컴·부킹닷컴 조사 결과를 보존한다. Google 장부 자동 쓰기와 새 여행 생성은 포함하지 않는다.

목적은 기존에 등록된 메일·포털·참고 자료와 새 사이트 관측을 한 SQLite DB에 보존하고 현재 예약 목록·결제 대사에서 읽는 것이다. 결제 ID·사용자 결정·장부 금액·날짜를 바꾸지 않는다. 직접 영향을 받는 범위는 OTA 출처 등록, 읽기 어댑터, 저장·추가 적재 도구다. 검증은 관련 표적 검사와 실제 이전 전후의 원문·이벤트 전체 비교를 한 번 수행한다. 종료 조건은 통합 DB 적재, 반복 적재 불변, 운영 읽기 전환과 최소 확인이다.

## 저장 계약

- `ota_sources`, `ota_source_revisions`, `ota_raw_entries`는 출처와 원문 버전을 보존한다. 원문은 무손실 압축하며 해시는 압축 전 정규 JSON을 기준으로 한다. 기존 원본 파일을 삭제하거나 이동하지 않는다.
- `ota_messages`, `ota_mail_origins`는 메일 ID와 원문 해시, 여러 수집 범위의 출처를 보존한다. 같은 ID의 다른 본문·인증 헤더는 충돌로 중단하고 해당 적재를 롤백한다. 원래 JSON의 추가 메타데이터도 원문 버전에 보존한다.
- `ota_bookings`, `ota_booking_evidence`는 공급자·계정·예약번호와 직접 관측·메일의 연결을 관리한다. 서로 다른 계정을 같은 예약으로 자동 합치지 않는다. 계정을 확인할 수 없는 기존 자료는 별도 레거시 계정 구분을 쓴다.
- 기존 포털의 예약·직접 원문·근거 역할·여행 연결은 원래 행을 보존한다. 조회 시 원래 레코드 ID와 출처별 그룹 경계를 유지하므로 DB를 합쳐도 기존 결제 이벤트 ID를 바꾸지 않는다.
- 아고다 캡처는 같은 DB에 바로 적재한다. 다른 OTA도 `OtaStore.import_direct()`로 원문과 공급자별 사실을 저장한다. 관측을 저장했다는 이유로 결제를 생성하지 않는다.
- 직접 관측의 기간·카드·금액 충돌과 취소 이후 정상 상태 복귀는 보류한다. `오늘 결제됨`에 수집일을 넣지 않으며 `portal_payment_date_required` 보호를 유지한다.
- 참고 문서도 같은 DB에 원문을 보존하되 기존처럼 진단에만 사용한다. 결제 권위로 승격하지 않는다.

기존 `mail_directories`, `portal_databases`, `reference_documents` 읽기 인터페이스는 유지하고 통합 DB를 어댑터로 읽는다. 운영 manifest의 `unified_database`가 있으면 이 DB가 단일 읽기 경로다. 예전 폴더와 DB는 복구·추가 수집 원본으로 보존하며 런타임이 함께 중복해서 읽지 않는다.

## 실제 이전과 검증

등록된 메일 폴더 5곳, 포털 DB 11개, 참고 문서 53개를 로컬 통합 DB로 복사했다. 메일 1,921개와 기존 결제 이벤트 1,464개의 전체 내용·ID, 메일 출처 목록, 참고 문서 진단 결과가 이전 전후 동일했다. 반복 적재 전후 모든 테이블의 행 내용 해시가 같았고 무결성 검사도 통과했다. 수치는 등록된 자료 범위이며 전체 Gmail 계정의 모든 메일 수를 뜻하지 않는다.

아고다의 검증된 전체 목록 40페이지·예약 1,550건과 기존 상세 표본도 이 DB에 추가했다. 목록에는 연도가 없는 날짜를 채워 넣지 않는다. 직접 수집 계정과 기존 레거시 계정의 색인을 따로 두므로 `ota_bookings` 행 수를 실물 예약의 중복 제거된 총수로 보고하지 않는다.

실제 원문·DB·검증 보고서는 `.local-archive/ota-unified-20261020/`에만 보존한다. 개인정보를 Git에 넣지 않는다. 신규 저장·통합 검사, 관련 기존 보호 검사 28개가 통과했다. 예약 목록 검사 8개가 통과했고 캐시 검사 1개는 수정 전 `e6276a4`에서도 같은 실패가 재현돼 기존 실패로 기록했다. 전체 pytest와 전체 브라우저 검사는 수행하지 않았다.

## 추가 수집과 원자적 적재

새 직접 캡처·메일·포털 DB·참고 문서는 `tools/sync_ota_store.py`로 통합 DB에 추가한다. 이 도구는 복구 사본과 모든 행 해시의 일치를 확인하고, 전체 추가 작업을 하나의 트랜잭션으로 처리한다. 하나라도 실패하면 전체 추가를 롤백한다. 작성자는 하나만 둔다. 운영 장부와 확정 DB는 쓰지 않는다.

```powershell
python tools/sync_ota_store.py --db <통합_DB_절대경로> --capture-root <검증된_수집폴더> --backup <새_복구사본_경로> --report <실행결과_경로>
```

메일은 `--mail-directory`, 포털 DB는 `--portal-database`, 참고 문서는 `--reference-document`로 지정한다. 같은 옵션을 여러 번 사용할 수 있다. 최초 이전은 `tools/consolidate_ota_sources.py`로 새 DB에만 수행한다. 기존 장부 DB나 다른 SQLite DB를 통합 저장소로 열려고 하면 거부한다.

## 운영 전환 상태

첫 전환의 실제 화면에서 결제 예정일 대사의 별도 읽기 경로가 통합 DB를 지원하지 않는 문제가 확인돼 즉시 기존 manifest로 되돌렸다. 해당 어댑터와 상태 충돌 근거를 보완했고, 결제일 없는 새 관측이 기존 검증된 예정일 연결을 대체하지 않도록 했다. 격리한 실제 카드 자료에서 기존·통합 경로의 카드 연결 300개가 동일했고 새 출처 읽기 오류도 없었다. 해당 예정일·취소·원문 중복 보호 검사를 추가했다. 전체 참고 문서는 순서대로 읽고, 검증된 조회용 행을 사용해 원문 전체를 반복 해제하지 않는다.

상시 수집 시각만 바뀌어도 같은 원문이 다시 복사되지 않도록 원문 내용을 해시로 구분해 한 번만 저장한다. 원문 버전과 실제로 변경된 수집 메타데이터는 각각 보존한다. SQLite의 WAL과 일관된 읽기 트랜잭션을 사용하고 실제 작성은 적재 트랜잭션으로 직렬화한다.

최종 운영 코드는 `0a88cb7f63c6515c760ed0cb25b5d76dde9fae02`, 경로는 `D:/WebLedgerHost/data/ota-evidence.sqlite`다. 우선 상세 큐 370건과 원래 ID 기준 메일 1,932개가 반영됐다. 파서 버전 2는 현장 결제·캐시 전용·취소·환불 예정·카드 없는 완료 표시·결제 거부를 구분하고 이전 해석을 보존한다. 상세 370건 모두 실제 결제일이 없어 이를 만들어 넣지 않았다. 대상 카드 213건은 결제일 부족 138건·정확 금액과 카드 근거 부족 75건으로 남겼다.

DB 5개 복원 검증·health/ready·실제 예약의 카드와 보완된 이용기간 표시를 확인했다. 최종 적재와 화면 조회 뒤에도 모든 보호 대상 행이 같았다. 기존 이벤트 1,468개의 ID·금액·날짜·근거가 같았고 새 메일 출처만 목록에 추가됐다. 전체 캡처 반복 적재의 모든 테이블 행 해시도 같았다. [최종 운영 기록](operations.md)을 따른다. 저장소 전환과 우선 수집은 COMPLETE이며 실제 카드 원본 보완과 두 공급자의 개별 연결 결함 수정은 별도 범위다.
