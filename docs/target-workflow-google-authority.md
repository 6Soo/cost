## 1. 제품 목적과 최종 권위 — 확정

COST의 주목적은 **법인카드 지출 및 현지 영수증을 자동 추출·대사·분류하고, 사용자가 확인해 Google 스프레드시트에 그대로 복사·붙여넣을 수 있는 지출표를 완성하는 것**이다.

- **Google 스프레드시트가 여행별 수입·지출·결산에 대한 유일한 최종 회계 정본(source of truth)**이다.
- 사용자는 Google의 기존 여행별 시트를 계속 직접 관리하며, 최종 반영·수정·결산 마감의 주체다. COST는 Google에 회계 행을 자동 쓰기 하지 않는다.
- COST의 웹 지출표는 **Google 반영 전 작업물**이다. 준비·검토·복사를 모두 끝내더라도 Google에 기록됐다는 의미는 아니다.
- COST가 제3자에게 보여 주는 **확정 장부/최종 결산 화면은 Google을 읽어서 구성**한다. 아직 Google에 없는 지출 후보를 확정 실적으로 합산하지 않는다.
- **신규 여행 시트의 공식 기준은 메인 Google 장부의 `매출자료 양식_rev` 하나**이다(사용자 확정, 2026-10-11). 이 양식의 상단 수입/하단 지출과 열 순서·합계 수식을 유지한다. 과거 다른 레이아웃은 사용자 직접 수정 예정인 구형 잔재이며, 별도 호환 구현이나 자동 변환을 하지 않는다. 실제 열 계약/수식은 [실측 문서](google-workbook-layout.md)를 따른다.
- Google은 영수증 이미지 저장소, 카드 raw transaction DB, AI 규칙 엔진, 검토 작업 DB가 아니다. 이런 비정본 데이터는 적절한 별도 저장소에 둔다.

### 입력 방향의 비대칭 — 절대 뒤집지 않는다

| 회계 데이터 | 최초 작성·분류 | COST와 Google 사이 흐름 | 최종 권위 |
| --- | --- | --- | --- |
| **수입** | 사용자, Google 시트 **상단**에 직접 입력 | **Google → COST** 읽기 전용 | Google |
| **은행 이체 지출** | 사용자, Google 시트 지출 영역에 직접 입력; 증빙내용 **이체** | **Google → COST** 읽기 전용 | Google |
| **법인카드 지출** | 법인카드 매입 raw → COST 대사·분류 → 웹에서 사용자가 완성 | **COST → 복사 → 사용자 → Google**, 이후 Google → COST 조회 | Google |
| **현지 현금 영수증** | A4 다중 영수증 업로드 → OCR → COST 분류·검토 | **COST → 복사 → 사용자 → Google**, 이후 Google → COST 조회 | Google |
| **현지 개인카드 영수증** | 영수증 OCR → COST 분류·검토; 회사 비용 인정 여부는 사용자 결정 | **COST → 복사 → 사용자 → Google**, 이후 Google → COST 조회 | Google |
| **현지 법인카드 영수증** | 영수증 OCR 후 기존 법인카드 매입과 대사 | **기존 카드 지출 한 건**으로 통일; 영수증은 증빙으로 연결 | Google 카드 지출 기재 |

**중요:** COST의 카드 대사는 은행 이체를 수집하거나 자동 대사하는 기능이 아니다. 은행 이체는 사용자가 Google에 직접 쓰는 예외적 지출 경로다. **개인카드 경비를 회사에서 계좌이체로 사후 상환하더라도 사용자가 Google 기존 지출 내역을 직접 확인하고 중복 기입을 피한다(2026-10-11 사용자 확정).** COST가 개인카드 영수증과 상환 이체를 자동 대사·상계·수정하거나 별도 정산 기능을 만드는 것은 요구 범위 밖이다.

## 2. 배치·조회·작업 구조 — 확정된 요구 / 배포는 계획

### 목표 컴포넌트

1. **로컬 Windows PC**: 법인카드 XLS/CSV 및 보존 OTA 근거의 원본, 카드 중복·취소·환불·여행 귀속 검사, 분류 규칙과 AI 처리기. 원본 고객/카드 자료를 로컬에 유지하는 것이 기본 원칙.
2. **Render 상시 웹서버(목표)**: 로그인·권한, 카드·영수증 지출 검토 UI, 규칙 수정 메시지·대기 상태, Google에 복사할 지출표, Google 정본 읽기/제3자 확정 장부 표시. Render 이전은 **아직 승인·구현·배포 완료가 아니다**.
3. **Google 스프레드시트**: 사용자가 직접 작성하는 수입·이체 지출과, COST 검토 후 사용자가 붙여넣는 카드·영수증 지출의 최종 정본.

### 주기

- **Google 정본 읽기: 매시 정각(Asia/Seoul, 분 00) 1회**를 희망한다. 읽기 전용이며 Google 데이터 변경이 없으면 파싱·캐시 갱신·DB 쓰기를 불필요하게 반복하지 않는다. 실패하면 마지막 정상 스냅샷과 확인 시각을 표시하고 빈 장부로 덮어쓰지 않는다.
- **로컬 원본 수집/갱신:** 사용자는 매일 00:00 KST 1회를 희망한다. **현재 어떤 로컬 작업이 주기적으로 실행되는지는 미확인**이므로 실제 scheduler·파일 수집·OTA 스냅샷 지문 확인·웹 폴링을 조사한 뒤, 안전하게 늦출 수 있는 **원본 수집 작업만** 대상으로 결정한다.
- **로컬 AI 자연어 수정 요청:** 일일 배치와 독립적으로, 사용자 요청 시 응답 가능한 구조가 목표. 로컬 PC가 오프라인이면 대기·재개로 표시하며 작업이 성공했다고 주장하지 않는다.
- **사용자 수동 카드 업로드·웹 검토·원본 저장·보안 검사·결산 화면**을 자정까지 대기시키거나 서버를 하루 한 번만 켜는 구조로 바꾸지 않는다.
- Render로 이전해도 로컬 원본을 직접 읽을 수는 없다. 로컬 PC가 허가된 인증 채널을 통해 **검토에 필요한 최소 후보 필드만** 동기화하는 방법을 검토한다. 실제 원본이나 비밀값의 무단 외부 전송은 금지한다.

### 읽기·쓰기 경계

- Google → Render: **읽기 전용** (수입 + 사용자가 기입한 은행 이체 + 붙여넣기 완료 지출 + 여행별 결산).
- COST → Google API: **자동 쓰기 금지**. 복사 기능은 사람의 클립보드/붙여넣기 동작일 뿐.
- 로컬 → Render: 검토용 지출 후보/규칙 결과/상태를 인증·최소필드로 제공. 어떤 개인정보·원본 세부 필드가 필요한지는 별도 확정.
- Render → 로컬 AI: 규칙 수정 요청 전달 및 제안 결과 수신. 로컬 PC의 인터넷 포트를 임의 공개하지 않고 인증된 연결/작업 조회 방식으로 구성; 구체적 기술 선택은 구현 전 검증.

## 3. 카드 지출: 기존 안정화된 기능을 활용 — 확정

- 법인카드의 **국내·해외 매입 확정 자료**만 회계 비용 근거다. 승인내역은 비용이 아닌 보조 증거다.
- 승인·매입이 겹치거나 동일한 파일을 다시 받아도 비용을 중복 계상하지 않는다.
- 지연 매입, 승인 취소와 매입 취소, 부분 환불, 완전 취소, 실제 다중 결제를 구별한다. 해외 카드의 실제 청구 KRW 원금·수수료·합계를 보존하고 영수증 고정 환율로 덮어쓰지 않는다.
- 검증된 OTA·여행 일정 권위와 사용자 확정을 보존한다. 모호한 귀속은 HOLD하며 원문 날짜·금액·거래 ID를 규칙으로 변경하지 않는다.
- 화면에서 웹 사용자가 **가맹점/항목/설명/여행 귀속/증빙 구분**을 검토하고 재사용 가능한 규칙의 적용 범위를 승인한다.
- 사용자 수정은 원본 변조가 아니라 **분류·귀속·회계 표시 결정**이다. 금액 일부만 비용 처리하는 사례는 원본을 그대로 보존하고 별도 회계 조정·사유·결정으로 취급한다.
- **사용자 확정(2026-10-11): C열 `항목`은 가맹점·결제처·지급처이고, D열 `내용`은 숙박비·항공료·식비 등 비용 분류**다. 규칙 적용/복사 출력에서도 두 값을 혼동하지 않는다.
- **사용자 확정(2026-10-11): 지출표는 실제 거래 한 건당 한 행으로 출력한다.** 같은 가맹점·비용 항목·날짜·금액을 공유해도 서로 다른 실제 거래는 합산/병합하지 않는다. 원결제와 별개로 발생한 취소·환불도 임의로 상계해 행을 없애지 않는다. 승인 증거는 지출 행이 아니며, 법인카드와 중복되는 영수증은 카드 거래 하나만 대표 지출로 출력하고 영수증은 증빙에 연결한다. 중복 업로드는 기존 멱등성 규칙을 따른다.
- 최종 출력은 공식 `매출자료 양식_rev`의 **B:H 지출 7열(거래일자·항목·내용·기간·예약번호·증빙유형·금액(원))** 계약을 따른다. **현재 여행/구간의 검토가 끝난 지출만** 선택해 TSV 등 다중 셀 붙여넣기 가능한 형태로 복사한다. 구형 B:I 비연속 양식에는 복사를 지원한다고 주장하지 않으며 사용자가 템플릿으로 정비한다.

## 4. 현지 영수증(A4 다중 OCR) — 신규 기능 요구 확정

### 입력과 원본

- 주된 대상은 **일본 현지 영수증**이다. 사용자가 **A4 한 장에 여러 장의 종이 영수증을 붙여 촬영/스캔**하여 업로드한다.
- 한 이미지/PDF 안의 **서로 다른 영수증을 자동 감지·분리**하여 개별 비용 후보로 만든다. 잘렸거나 겹쳤거나 경계가 불명확하면 사용자에게 분리/확인을 요청하고 누락 또는 중복 생성하지 않는다.
- 영수증별로 가능한 범위에서 **상호명, 일자, 최종 결제금액, 통화(JPY), 결제수단, 원본 이미지 위치**를 인식한다. 영수증의 합계/현금 지급/거스름돈/세금/할인/취소를 구별한다.
- OCR 신뢰도가 낮거나 총액이 불명확하면 HOLD. 개별 물품 목록 전체를 자동 비용 행으로 쪼개지 않는다(별도 사용자 지시가 없으면 **영수증 한 장당 비용 한 건**).
- 원본 이미지와 추출 텍스트/원화 환산값을 구분해 보존한다. 이력/재처리 시 같은 이미지를 다시 입력해도 중복 후보가 증가하지 않아야 한다.
- OCR 엔진·비용·개인정보 보관/학습 정책은 **미확정**. 별도 허가 없이 영수증 이미지나 개인정보를 외부 무료 AI/OCR 서비스로 전달하지 않는다.

### 결제수단과 중복 대사

사용자가 예상한 월별 법인카드 중복은 **1~2건 수준**이다. 복잡한 자동 매칭 엔진을 새로 만들지 않는다.

- **현금(대부분):** 독립 영수증 지출 후보. 최종 Google 증빙내용 **영수증**.
- **개인카드(일부):** 사용자가 회사 경비로 인정하면 독립 영수증 지출 후보. 최종 Google 증빙유형 **영수증**. 나중에 상환 이체가 발생하더라도 **Google에 이미 기록한 경비와 중복되지 않는지 사용자가 직접 확인하고 기입 여부를 결정**한다. COST는 상환 이체의 자동 중복 탐지·대사·제외·상계 기능을 만들지 않고, Google의 수입·이체 지출은 그대로 읽기 전용으로 다룬다.
- **법인카드(일부):** **기존 법인카드 매입 거래가 대표 지출**, 영수증은 그 거래의 증빙/설명으로 연결한다. 카드 원화 청구액을 최종 금액 기준으로 사용하고 영수증의 단순 JPY 환율 금액을 추가 비용으로 기록하지 않는다. 매입 미도착, 후보 복수, 불일치 때는 HOLD.
- **결제수단 불명:** 함부로 현금/법인카드라고 확정하지 않는다. 사용자가 확인한다.

법인카드 거래의 날짜·상호·현지 통화·원금액·카드 여부를 참고하되 **유일성이 확보되지 않은 후보를 자동 병합하지 않는다**. 이 기능은 드문 중복을 사용자에게 보여 주고 정리하는 가벼운 경로여야 한다.

### 환산: 간편한 내부 장부 작성 규칙

- **JPY 100엔 = KRW 1,000원**. 즉 내부 표에 복사할 금액은 **엔화 1엔당 원화 10원**이다.
- 적용 대상은 현금 및 사용자 승인 개인카드 **영수증 기반 경비**다. 엔화 원본 금액과 적용 환율(10 KRW/JPY), 산출 원화 금액을 각각 보존한다.
- **법인카드의 확정 청구 KRW는 카드 매입을 따르며 고정 환율을 적용하지 않는다.**
- 이 환율은 사용자가 정한 **간편 장부 환산 기준**이지 카드사 청구액·세무상 법정환율을 뜻하지 않는다.
- 원 단위 반올림/소수 엔화 처리 및 실제 세무 신고 사용 가능 범위는 별도 확인이 필요하다.

## 5. 지출 검토 UI + 로컬 AI에 자연어로 규칙 수정 요청 — 목표

- 여행별 지출 검토표는 **메인의 `매출자료 양식_rev`의 지출 7개 열과 동일한 의미·순서·표시 형식**으로 제공한다. 과거 레거시 양식의 서로 다른 열 배치까지 별도 지원하지 않는다.
- 각 지출 행에서 사용자가 **자연어 메시지**를 작성해 로컬 PC의 응답 가능한 AI에게 보낸다.
- 예: “이 편의점 결제는 식비가 아니라 현지 잡비야. 앞으로 같은 가맹점은 그렇게 분류해 줘.”
- AI는 허용된 규칙 스키마와 현재 사용자 결정/원본 근거를 조회해 **(a) 현재 거래만 수정, (b) 기존·미확정 거래에 적용할 재사용 규칙, (c) 추가 확인 필요**를 구분한 **제안**을 만든다.
- 사용자는 변경 전·후 및 **영향받을 거래/여행/금액**을 미리 본 후 명시적으로 적용한다. AI가 임의로 원본 카드 내역·구글 시트·확정된 거래를 변경하지 않는다.
- 같은 상호라는 이유만으로 임의 여행 전체를 자동 귀속하지 않는다. 원본 금액/일자/ID 변경 명령은 거부하거나 별도 표시 조정으로 안내한다. 기존 사용자 확정 우선.
- 적용 승인 후 영향을 받는 **미확정 지출표만** 다시 계산한다. 이미 한 번 통과한 전체 KB 대사·OTA 회귀는 반복하지 않는다.
- 로컬 PC/AI가 꺼져 있으면 메시지를 보존하고 **대기**로 표시한다. 외부 무료 모델로 임의 폴백하지 않는다.
- 로컬 AI가 실제 **로컬 추론 모델**인지, 로컬 PC에서 동작하는 클라우드 코딩 에이전트인지, 연결·호출·인증 방식은 아직 확인되지 않았다. 이와 무관하게 개인정보 최소 전달·명시적 승인·감사 이력은 유지한다.

## 6. Google 복사/붙여넣기 계약과 최종 웹장부 — 확정/미확정 구분

### 복사 전

- 대상 여행과 지출 행, 총 건수·합계·원화 단위를 명확히 표시한다.
- **`매출자료 양식_rev`를 기반으로 신설·정비된 여행 시트의 지출 데이터 영역**으로 복사한다. 수식·합계·기존 수입·수기 이체 행은 침범하지 않는다. 대상 시트가 아직 레거시 양식이면 무리한 복사를 허용하지 않고 기준 템플릿 정비를 안내한다.
- 카드/영수증 구분과 시트 실제 증빙내용 값을 표시한다. **이체는 Google 수기 입력만**, **영수증은 현금/개인카드 기반 최종 증빙 표기**. 카드 지출의 기존 증빙 표기값은 실제 시트 확인 전까지 정하지 않는다.
- Google에 붙이기 전 규칙 수정과 지출 검토를 최대한 끝내어 Google 내 사후 수정·삭제를 최소화한다.

### 복사 후

- 복사 버튼 클릭 또는 사용자의 “붙여넣기 했음” 표시는 **Google 기록의 독립적 증명이 아니다**.
- 다음 Google 읽기에서 확인할 수 있는 **행/항목/금액/건수/합계**로 실제 반영 상태를 판단한다. 원본 거래 ID가 Google에 없으면 동명이액·삭제·재정렬·직접 수정이 결합된 경우 **1:1 거래 동일성을 입증할 수 없으므로 UNKNOWN/HOLD**한다.
- Google에 기입된 금액과 COST 원본 카드 금액이 다른 경우, 원본을 고치거나 조용히 역동기화하지 않는다. 사용자가 Google에서 수정한 최종 장부가 회계 정본이며 불일치를 표시한다.
- **여행 마감 완료는 여행 시트를 메인 Google 장부에서 보관 Google 장부로 이동한 시점으로 판정한다**(사용자 확정, 2026-10-11). 정상 동기화에서 보관본의 해당 실여행 탭이 확인되면 마감 완료이며, 메인에만 남은 여행은 종료일이나 장부 내 결산 수식 존재 여부와 무관하게 미마감이다. 여행 식별이 불확실하면 임의로 마감 처리하지 않는다. **동일 여행이 활성 메인과 보관 장부에 동시에 존재하면 마감 상태는 완료이며, 금액 정본은 메인을 기본 선택하고 `확인 대상`으로 표시한다**(사용자 확정, 2026-10-11). 사용자가 두 사본의 내용을 비교해 정본 선택을 수동 조정할 수 있어야 한다. 어떤 경우에도 수입·지출을 중복 집계하지 않고 **선택된 한 사본만** 조회·집계하며, 사용자 선택·수정 이력을 보존한다. 다른 사본은 비교·검토 자료로 보존하고 양쪽 일치 검증 완료로 속이지 않는다. COST가 Google의 어느 사본도 자동 수정하지 않는다. [장부 구조 및 중복 원본 규칙](google-workbook-layout.md)을 따른다.
- Google 원본이 읽히지 않으면 마지막 정상 시각과 **동기화 지연**을 표시한다. 최신 장부라고 속이지 않는다.
- **결산 완료 여행**은 Google 여행 시트의 확정 수입·지출 행 및 계산된 합계를 COST 확정 장부 화면에서 일치시켜야 한다. 단순 합계만 맞는 것으로 성공 처리하지 않는다.
- Google 시트 마감 후 변경이 감지되면 웹에서도 마감 당시와 달라진 사실을 표시한다. 자동 재마감·자동 삭제·Google 쓰기는 하지 않는다.

### 웹장부의 두 화면/상태를 섞지 않는다

1. **지출 작성·검토 작업 공간:** 아직 Google에 붙여넣지 않았거나 붙여넣기 확인 전인 카드·영수증 후보; AI 규칙 수정 가능.
2. **최종 장부/권한별 조회:** **Google에 실제 존재하는 수입·이체·카드·영수증 지출**과 결산을 표시하되, **기본은 owner 본인만 전체 열람**, owner가 승인한 계정은 **계정별 허용 여행만 읽기 전용**으로 제공한다.
3. **비로그인 공개 데모 — 사용자 확정(2026-10-11):** 인터넷 일반 방문자가 **로그인 없이** 열람할 수 있는 별도 데모 페이지를 제공한다. **마감 완료가 확인된 실제 여행 중 Google 확정 회사수익 금액 상위 3건**을 **성공한 Google 정본 동기화 시마다 자동으로 재선정**해 이름·닉네임 등 개인정보를 서버에서 제거하고, 실제 수입·지출·순수익 금액을 보여 준다. 두 장부의 메인 우선/수동 정본 조정과 중복 방지 규칙을 반영하며, 동기화 실패 시 잘못된 새 순위로 갱신하지 않는다. 새로 선정된 여행도 공개 전에 같은 서버 측 익명화 검증을 통과해야 한다. 원본 Google/owner·viewer API 접근은 인증 없이 허용하지 않는다. **마감 판단은 정상 동기화로 확인한 보관 Google 장부의 해당 실여행 탭 존재를 기준으로 하며, 단순 종료일이나 이름이 유사한 사본으로 마감 완료를 추정하지 않는다.** 같은 여행이 두 파일에 동시에 있으면 마감 완료 + 메인 정본 우선 + 확인 대상 정책을 함께 적용한다. 이 문서의 요구 확정은 실데이터 게시·배포를 뜻하지 않는다. 세부 명세는 [접근제어·데모 정책](access-and-top3-demo.md)을 따른다.

예상 손익 계산에 아직 Google에 없는 미반영 지출을 포함한다면 **예상**이라고 별도 명시한다. 확정 순수익과 섞지 않는다.

## 7. 안전·복구·인프라 제약

- 현재 운영 DB는 로컬 SQLite **D:/WebLedgerHost/data/board.sqlite**로 설계돼 있고, 장부 수정/환불/사용자 확정/OTA 링크를 보존한다. **Google이 정본이 되는 것은 목표 구조 변경**이지 기존 SQLite 파일을 즉시 삭제하라는 뜻이 아니다.
- 목표 Render 서버는 24시간 접근을 지원하되, 이행 전에는 코드의 Linux 이식성, 지속 저장소, 예약 작업, OAuth 콜백, 시트 읽기 권한, 파일 의존성, 백업·복구, 비용/보존 정책, 개인정보/국외 이전을 조사한다. 서비스 규모에 맞춰 단순 구조를 우선하며 PostgreSQL 재작성은 기본 요구가 아니다.
- Render에 저장할 후보 필드와 이미지/고객정보/원본의 전송 범위를 정하기 전에는 실제 자료를 업로드하지 않는다.
- 원본 파일, 운영 DB, 비밀값, 사용자 결정, OTA 정확 연결과 환불 관계를 임의 삭제·초기화·덮어쓰지 않는다.
- 기존 역할을 바꾸는 작업은 **코드 변경+데이터 migration**으로 오해하기 쉽다. Google 권위로 전환하기 전에 현재 ledger_entries/board_rows와 Google 정본의 차이를 먼저 인식해 충돌 전략을 승인받는다. 양방향 자동 쓰기/무작정 일괄 재계산 금지.
- 문서만 고치면 코드 테스트/배포/운영 재시작을 하지 않는다. 코드 수정은 AGENTS.md의 표적 검증 최소화 원칙을 따른다.
- 사용자에게 확인받지 않은 “추정 시트 구조”나 “완료된 Render 배포”를 사실로 보고하지 않는다.

## 8. 우선순위와 구현 경계 — 제안(사용자 승인 전 자동 착수 금지)

**P0 — 공식 `양식_rev` 계약 확정(진행 중)**  
Google 원본 두 개와 공식 `매출자료 양식_rev` B:H 수입·지출 열/합계 수식을 읽기 전용으로 확인했다. 사용자가 2027년 여행 `0206_하쿠산`·`0302_야쿠시마`의 연도를 확정했다. 남은 것은 **실제 최신 양식 기준의 붙여넣기 대상 범위·빈칸·합계 보호 확인**이며, 과거 양식별 호환 매핑이나 전수 재작성은 개발 범위 밖이다.

**P1 — Google 읽기 전용 최종 조회 경로**  
매시 정각 Google 읽기, 수입·이체·붙여넣기 지출 모두 정본으로 조회, 마지막 정상 시각/오류와 진행 중 지출 분리. 현재 운영 데이터는 건드리지 않는 격리 검증부터.

**P2 — `양식_rev`와 같은 웹 검토표 및 복사**  
기존 카드 분류·규칙·검토 엔진을 재사용하고, 공식 지출 7열에 맞춘 TSV/표 형식 복사만 제공. 과거 시트 양식별 별도 출력 기능을 만들지 않는다. Google 자동 쓰기 구현 금지.

**P3 — 행별 자연어 규칙 제안·적용**  
로컬 AI의 유효한 연결 경로를 확인 후, 제안/영향 미리보기/사용자 승인/미확정 행 재분류를 구현. 개인정보 외부 전송과 임의 DB 수정을 금지한다.

**P4 — A4 다중 일본 영수증 OCR**  
한 장에서 여러 영수증 인식, cash/private/corporate 분기, JPY×10, 법인카드 중복 수동 확인, 기존 검토/복사 재사용. 별도의 복잡한 매칭 엔진은 금지.

**P5 — Render 전환과 로컬 PC 전송 주기 조정**  
현재 서버·워커·동기화와 파일 의존성을 실측한 뒤 격리 Render 실행 및 데이터 보호 확인. Google 읽기 주기와 PC 원본 수집 주기를 분리. 도메인 전환은 기능/복구 검증 이후에만 수행.

각 단계는 작은 별도 PR과 직접 영향을 받는 검증 한 번으로 끝낸다. 하나의 대형 재구축 PR로 모든 단계를 동시에 진행하지 않는다.

## 9. 구현 전 결정해야 할 미확정 사항 — 질문 목록

Q1. **Google 원본/공식 양식/두 여행 연도 확정**: 과거 보관(26탭), 활성 메인(43탭)을 확인했다. **메인 `매출자료 양식_rev`가 유일한 신규 여행 기준**이며 B:H 지출 7열을 사용한다. `0206_하쿠산`, `0302_야쿠시마`는 2027년 여행이다. 과거의 비연속 B:I 시트들은 추후 사용자가 직접 정비하며 **호환 구현 대상이 아니다**. C열 `항목`(결제처/지급처), D열 `내용`(비용 분류)은 사용자 확인으로 확정됐다. 아직 확인할 것은 템플릿의 실제 복사 대상 범위와 마감 후 변경 이력/동기화 시점이다. **동일 여행이 두 파일에 있으면 메인 우선·`확인 대상` 표시·사용자 수동 정본 조정**으로 우선순위는 확정됐다. [실측 문서](google-workbook-layout.md)를 따른다.

Q2. **지출 출력 단위 — 사용자 확정(2026-10-11)**: 카드·영수증은 **실제 지출 거래 한 건당 한 행**으로 출력한다. 동일 결제처/항목으로 묶어 합산하지 않는다. 원결제·취소·환불의 구분 및 법인카드 영수증의 증빙 연결은 기존 거래 무결성 규칙을 따른다. 이 사항은 더 이상 미결 질문이 아니다.

Q3. **개인카드 사후 상환 — 사용자 확정(2026-10-11)**: 개인카드 영수증의 비용 기입 후 회사가 이체 상환하더라도, 사용자가 Google에 이미 기입된 비용을 직접 확인하고 **중복 기입하지 않도록 수동 관리**한다. 별도 자동 이체 대사·정산·상계 개발은 하지 않는다. 기존 Google 수기 이체 입력 → COST 읽기 전용 원칙은 유지한다. 이 사항은 더 이상 미결 질문이 아니다.

Q4. **일본 영수증 세부 사항**: 대부분 JPY 영수증이지만 다른 통화도 있는가? 소수 금액·반올림·일본 세금계산 실무에서 100엔=1000원 가정의 예외가 있는가? A4 PDF/사진 지원 범위와 OCR 엔진 사용 동의/정책은 별도 확정.

Q5. **로컬 AI 구현체**: 응답 가능한 로컬 PC AI가 실제 온디바이스 추론인가, 로컬 PC의 Paseo/OpenCode·Codex와 연결된 클라우드 모델인가? 외부 모델에 허용하는 데이터/로그 범위 및 오프라인 시 대기 정책을 확정한다.

Q6. **권한·데모 — 사용자 확정(2026-10-11)**: 전체 장부 기본 열람은 owner 본인만, 별도 계정에는 owner가 **계정별로 여행 조회 권한을 부여**한다. 데모는 **로그인 없이 누구나 접근 가능한 공개 페이지**이며 Google에서 **마감 완료가 확인된 여행 중 수익금액 상위 3건을 성공한 정본 동기화 시마다 자동 재선정**하여 성명·닉네임 등 개인정보 마스킹 후 실제 회계 금액과 함께 공개하는 목표다. 자동 갱신마다 별도의 owner 승인을 요구하지 않지만 새 선정 여행도 개인정보 검증을 통과해야 한다. **마감 판정 근거는 메인→보관 장부 여행 시트 이동으로 확정**됐으며, **수익 동률 시 보조 정렬 규칙**은 아직 미정이다. 마감 미확인/진행 중 여행은 데모 후보에서 제외한다. 공개 데모용 서버-side 데이터와 인증된 전체 장부를 분리한다. [자세한 요구와 개인정보 검증 경계](access-and-top3-demo.md)를 따른다.

Q7. **마감 기준 확정 / 갱신 동작 미정**: 여행의 마감 완료는 **사용자가 여행 시트를 메인 Google 장부에서 보관 Google 장부로 이동한 시점**으로 판정한다. COST는 정상 읽기에서 실제 보관 여행 탭을 확인해 마감을 인지한다. 보관본과 메인본이 동시에 있으면 **마감 완료**지만 재무 정본은 메인 우선 + 확인 대상/수동 조정이다. 매시 정각 읽기 외 마감 직후 수동 새로고침 허용 여부 및 마감 후 원본 수정 이력 표시의 세부 방식은 별도 결정한다.

Q8. **Render 이전 승인·데이터 보관**: 호스팅 지역/개인정보/백업·복구·비용, 후보 거래와 OCR 이미지를 서버에 얼마나 저장하는지, PC 오프라인 허용 지연.

## 10. 변경 관리

2026-10-20 사용자가 보험가입 명단을 실제 참가 기록으로 인정하고 참가자와 기존 수입을 대조하는 시스템의 계획·명세 작성을 요청했다. [참가자 확정·수입 대조 명세](participant-income-reconciliation-spec.md)와 [작업 인덱스](participant-income-task-index.md)에 전달 계약과 구현 계획을 기록한다. 기본 설계는 COST 대조표에 이름만 추가하거나 기존 수입 행에 참가 표시를 붙이는 방식이며 Google 수입 자동 쓰기를 허용하지 않는다. 계획 작성 완료이며 제품 구현·배포는 미실행이다.


이 명세는 **사업 흐름에 대한 요구사항**이며, 현재 코드·배포 상황과 분리되어 있다. 확정된 방향을 새 모델에 긴 프롬프트로 계속 복제하지 말고 이 문서를 먼저 읽게 한다. 미확정 사항은 확인 후 본 문서에서 ‘확정’으로 승격한다. 기존 운영 기록과 상충하면 과거 기록을 지우지 않고 **현재 운영 사실 vs 목표 정책**을 명시한다.

새 단계 작업 전: **목표 / 변경 동작 / 직접 영향 / 한 번의 필요한 검증 / 종료 조건**을 먼저 정하고 불필요한 전체 재검증·다중 에이전트 중복 작업을 피한다.
