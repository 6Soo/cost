# 판정 규칙집

> **상태:** 정본 (2026-11-11 초판). 지출을 어떻게 판정하는지에 대한 규칙은 이 문서와 `docs/policy/` 아래 영역별 파일에만 둔다.
> **짝 문서:** 시스템이 무엇을 만드는지는 [통합 명세](SPEC.md)에 있다.
> **독자:** P1 규칙을 구현하는 에이전트, 개별 지출을 판정하는 P2 에이전트, 분기 검수의 교정을 규칙으로 옮기는 감독 세션.

## 1. 읽는 법

| 층 | 어디 | 누가 언제 읽나 |
| --- | --- | --- |
| 핵심 원칙 | 이 문서 §3 | P2 실행마다 항상 받는다. P1 구현자는 먼저 읽는다 |
| 영역별 상세 규칙 | `docs/policy/<영역>.md` (§4 목차) | P2는 판정할 건에 해당하는 영역만 받는다. P1 구현자는 구현할 영역 전체를 읽는다 |
| 사용자 예외 | §5 | 특정 가맹점·카드·기간에 대한 사용자의 결정. 일반 규칙보다 먼저 적용한다 |
| 코드와 다른 곳 | [코드와 규칙이 다른 곳](policy/CODE_GAPS.md) | M2 구현 작업의 입력 |

- 규칙마다 ID가 있다(`TRIP-003` 등). 판정의 근거에는 적용한 규칙 ID를 적는다.
- 규칙의 종류는 셋이다. **일반**(어떻게 판정하는가), **사용자 예외**(범위가 한정된 결정), **보호**(하지 말아야 할 것).
- 핵심 원칙과 상세 규칙이 다르게 읽히면 핵심 원칙이 우선한다. 그런 곳을 발견하면 고쳐야 할 결함으로 올린다.

## 2. 무엇이 우선하는가

**규칙 사이:** 사용자의 최신 명시 결정 > 이 규칙집 > 코드. 코드가 규칙과 다르면 코드가 틀린 것이다.

**판정 사이:** 사용자의 수동 교정 > 정확 근거에 의한 P1(예약번호·원승인번호 등) > P2 > 추론에 의한 P1(업종·날짜로 고른 최선 후보).

**사용자 결정으로 보지 않는 것:** 빈 여행 값, `unclassified` 기본값, 결정 이력 테이블에 행이 있다는 사실만으로는 사용자가 "미배정"을 골랐다고 보지 않는다. 사용자가 실제로 입력한 항목·여행·연결·제외만 보호한다.

## 3. 핵심 원칙

### 3.1 판정을 끝낸다

1. PROC-072의 완료 자료는 판정·재판정·검토·미분류 집계에서 먼저 제외한다. 그 밖의 정상 거래는 모두 판정을 갖는다. P1이 먼저 판정하고, P1이 못 정했거나 일반 항목으로만 정한 건은 P2가 근거를 대조해 판정을 끝낸다. (PROC-001, PROC-002)
2. 사용자에게 묻지 않는다. 확인함·질문 대기·보류·미배정·미분류·확정 대기 같은 상태와 화면을 만들지 않는다. 사용자는 분기 검수에서 교정한다. (PROC-003, PROC-068)
3. 추천하지 않는다. 근거가 있으면 한 곳에 배정한다. (PROC-007)
4. 낮은 신뢰도, 후보 동률, 예약 단서 부족은 판정을 미루는 이유가 아니다. 근거와 불확실성으로 적는다. (PROC-006)
5. 분류되면 완료다. 자동 판정에 별도 확정 단계는 없다. (PROC-008)
6. 날짜를 읽을 수 없거나 금액이 깨졌거나 원본이 서로 충돌하는 거래는 정상 거래가 아니다. 판정을 지어내지 않고 내부 보호 상태로 남긴다. (PROC-005)

### 3.2 여행 귀속 — 어느 여행의 지출인가

위에서부터 처음 맞는 것으로 정한다.

1. **수동 교정이 있으면 그대로 둔다.** (PROC-016)
2. **취소·환불은 원결제를 따른다.** 원결제와 연결된 취소·부분환불은 원결제의 항목과 여행을 이어받는다. 전액 환불로 합계가 0인 묶음은 환불 쌍으로 완료한다. (§3.6)
3. **사용자 예외에 해당하면 그 결정을 따른다.** (§5)
4. **예약 이용기간이 있으면 그 기간으로 정한다.** 이용기간은 결제일보다 항상 우선한다. 이용기간 전체를 덮는 여행 → 겹치는 날이 가장 많은 여행 → 그래도 같으면 수입에서 비용을 뺀 차액이 큰 여행. (`policy/trip.md`, `policy/date.md`)
5. **이용기간이 없으면 카드 이용일로 정한다.** 그 날을 포함하는 여행 중 국내/해외 구분이 맞는 여행.
6. **예약 이용기간도 없고 카드 이용일이 어느 여행 기간에도 들지 않으면 결제일 분기 기타비용으로 끝낸다.** 일반 준비기간 추론으로 다음 여행에 붙이지 않는다. 범위가 명시된 사용자 예외와 준비 숙박 특례는 해당 범위에서 유지한다. (PROC-004, TRIP-043, DATE-040)

- 대체된 옛 규칙 (소유자 결정 2026-11-12 밤): 어느 여행에도 들지 않으면 같은 국내/해외 구분에서 그 날 이후 가장 먼저 출발하는 여행에 준비 비용으로 배정하고 준비기간 추론임을 적는다. 이 일반 fallback은 폐지됐다.
- 후보가 여럿이고 끝까지 같으면 수입−비용 차액이 큰 여행, 그것도 같으면 출발이 빠른 여행을 고르고 동률이었다는 사실을 근거에 적는다. 입력 순서에 따라 결과가 달라지면 안 된다. (PROC-021)
- 여행을 만들어내지 않는다. 여행은 Google 시트 탭에서만 생긴다. 연도와 종료일은 시트 제목에서, 시작일은 탭 이름에서 읽는다. **종료일이 없는 여행은 다음 여행 시작 전날까지다.** (TRIP-001~003)
- 결제일이 여행 기간과 가깝다는 것만으로 이용기간이 확인된 다른 여행을 밀어내지 않는다.

### 3.3 항목 — 무슨 비용인가

위에서부터 처음 맞는 것으로 정한다. (PROC-020, `policy/item.md`)

1. 수동 교정과 이미 정해진 항목.
2. 예약 근거가 말하는 상품(숙박·항공·렌터카·입장권 등)과 가맹점별 사용자 결정(§5).
3. 카드사 업종.
4. 가맹점 이름에 드러난 서비스 용도.
5. 해외에서 쓴 현지 결제면 `현지경비`.
6. 그래도 단서가 없으면 `기타경비`. 원결제를 찾지 못한 취소는 `취소·환불`.

- `미분류`라는 이름의 항목으로 바꿔 두지 않는다.
- 공급자 이름만으로 상품을 정하지 않는다(사용자가 정한 예외는 따른다).

### 3.4 날짜 — 어느 날짜를 쓰는가

1. 카드 거래를 여행에 놓는 날짜는 **이용일**이고, 없으면 **승인일**이다. **매입일은 쓰지 않는다.** 분기 기타비용의 분기를 정할 때만 결제일이 없으면 매입일로 보완한다. (`policy/date.md`)
2. OTA 예약의 장부 날짜는 이용일(체크인·탑승·픽업)이다. 결제일은 이용일이 없을 때만 쓴다.
3. 숙박의 이용일은 체크인일부터 체크아웃 전날까지다. 항공은 출발일과 도착일 모두다.
4. 결제일의 근거로 인정하는 것은 실제 결제 사실(카드 원행, 서명 확인된 결제·확정 메일의 발송일(단, 사용자가 직접 수집한 메일은 LINK-061에 따라 서명 확인 불필요), 포털의 청구 기록)이다. 무료 취소 기한, 화면을 본 시각, "오늘 결제됨" 같은 표시는 결제일이 아니다.
5. 원문에 없는 날짜를 만들어 넣지 않는다. 모르면 비워 두고 모른다고 적는다. 오늘 날짜로 대신하지 않는다.
6. 항공권에 예약일이 없으면 같은 공급자·예약번호의 보관 메일 중 가장 이른 수신일을 한국 날짜로 쓰고 "최초 메일 수신일 기준"이라고 적는다.

### 3.5 OTA 예약과 카드 결제의 연결

1. **가맹점명과 같은 통화의 정확한 금액이 일치하고, 카드 끝 4자리 또는 결제일 중 하나가 더 일치하면 연결한다.** (LINK-002)
2. 끝자리나 결제일이 "없는 것"과 "다르다고 적힌 것"은 다르다. 명시된 값이 서로 다르면 연결하지 않는다. 가맹점이 결제대행사 이름으로 찍힌 경우의 처리는 LINK-018에 있다.
3. 관계는 M:N이다. 예약 여러 개와 카드 여러 건이 얽혀도 하나를 골라 붙이거나 합치지 않는다. 예약과 카드가 서로 유일해야 한다는 조건을 요구하지 않는다. 카드 원행은 한 번만 집계한다.
4. 가맹점 표기가 달라졌다는 이유로 별칭 승인을 요구하지 않는다. (PROC-067)
5. 연결의 종류(정확·수동·추론)를 구분해 적고, 추론이 정확·수동 연결을 덮지 않는다.
6. 금액·부호·원승인 관계·환불 짝·장부 기록은 P1만 쓴다. P2는 연결을 판정의 근거로 제시할 뿐이다.
7. 결제일 없는 예약의 공통 이용기간은 LINK-108 조건으로 인정한다. 객실별 예약번호나 새로운 결제일을 확정하지 않는다.

### 3.6 취소와 환불

1. 같은 발급사·카드에서 원승인번호가 정상 원결제 하나를 가리키면 그 번호의 취소·부분환불을 모두 연결한다. 취소 건수나 가맹점명·금액 차이로 연결을 낮추지 않는다. (RFND-004)
2. 원승인번호가 없어도 같은 발급사·카드·가맹점·이용일·정확한 원화 금액의 양수와 음수가 서로 유일하게 대응하면 연결한다. (RFND-007)
3. 승인번호 없는 해외 취소는 같은 카드·가맹점·외화 통화·외화 금액의 앞선 구매와만 짝짓는다. 여러 건이면 날짜순으로 하나씩. 원화 차이는 환율·수수료로 보고 잔액에 남긴다. (RFND-011~015)
4. 연결된 환불 합계가 정확히 0이면 전액 환불 쌍으로 완료한다. 잔액이 남는 부분 환불은 원결제의 여행에 함께 두고 잔액을 그 여행의 비용으로 본다. 원결제 금액을 잔액으로 덮지 않는다. (RFND-021, RFND-022)
5. 누적 환불이 원결제보다 크면 기록을 막는다. 환불 묶음은 전부 함께 기록하거나 전부 기록하지 않는다. (RFND-018, RFND-025)
6. 승인 취소와 매입 취소는 다른 상태다. 매입되지 않은 승인 취소를 환불로 기록하지 않는다. (RFND-055)

### 3.7 서로 다른 사실을 섞지 않는다

다음은 각각 따로 증거가 있어야 하는 사실이다. 하나가 확인됐다고 다른 것을 확인된 것으로 적지 않는다. (PROC-024, PROC-025)

- 예약이 있다 / 예약이 취소됐다
- 카드로 결제됐다 / 카드 취소 원행이 있다
- 예약과 카드가 같은 거래다
- 여행에 귀속됐다
- COST 내부 장부에 기록됐다
- Google 장부에 반영됐다
- 은행에 실제로 환급이 들어왔다

환불 요청 메일, 환불 가능 안내, 예정 결제 안내는 요청·조건·예정의 근거일 뿐 완료의 증거가 아니다. 사전승인은 결제 완료가 아니다.

### 3.8 하지 않는 것

1. 카드 원문·금액·부호·ID, 메일 원문, 영수증 원본을 바꾸거나 지우지 않는다. 금액을 읽지 못하면 0원으로 적지 않는다.
2. 수동 교정을 덮지 않는다. P2의 추론을 사용자 확인으로 기록하지 않는다. 추론 결과를 수동 교정 사례로 학습하지 않는다. (PROC-014, PROC-015)
3. 한 거래의 예외나 교정을 다른 거래·다른 여행으로 넓히지 않는다. 범위가 적힌 규칙만 범위 안에서 다시 쓴다. (PROC-030)
4. 중복·환불 짝·초과 환불·원본 충돌에 걸린 내부 보호를 풀지 않는다. 문제 있는 묶음 때문에 관계없는 정상 거래를 막지도 않는다.
5. Google 최종 장부에 쓰지 않는다. (PROC-042)
6. 단순한 경과 일수로 자료를 폐기하지 않는다. 소유자가 지정한 완료 자료는 판정 전에 제외한다. (PROC-048, PROC-072)

### 3.9 근거와 불확실성을 적는 법

- **근거 문장:** 무엇을 보고 이렇게 정했는지 한두 문장. 본 자료(메일·포털 기록·카드 원행)와 적용한 규칙 ID를 적는다.
- **불확실성:** 확인하지 못한 것을 적는다. 예: "이용일을 확인할 근거가 없어 결제일로 배정", "같은 기간에 여행이 둘이라 차액이 큰 쪽을 선택".
- 근거에 고객 이름·카드 번호·예약번호 전체를 옮기지 않는다. 사건 폴더의 근거 파일 이름으로 가리킨다.
- 모르는 것을 아는 것처럼 적지 않는다. 불확실성이 비어 있으면 "모두 확인했다"는 뜻이다.

## 7. 고치는 법

1. **새 지시는 이 규칙집의 개정으로만 반영한다.** 대화에서 받은 지시를 코드에만 넣거나 다른 문서에 따로 적지 않는다.
2. **분기 검수의 교정을 규칙으로 옮긴다.** 같은 원인의 교정을 묶어 규칙을 추가하거나 고치고, 교정 사례를 그 규칙의 "예"로 붙인다(식별값 없이). 표로 표현되는 규칙은 P1 데이터 규칙으로도 넣는다. ([통합 명세](SPEC.md) §8)
3. **ID는 바꾸지 않는다.** 내용을 고칠 때는 같은 ID에 새 내용을 쓰고 옛 내용을 "대체된 옛 규칙"에 날짜와 함께 남긴다. 없앨 때는 지우지 않고 "폐지"로 표시한다. 새 규칙은 그 영역의 다음 번호를 쓴다.
4. **정책과 양식 지식을 섞지 않는다.** "어떻게 판정하는가"만 여기에 둔다. "어느 공급자 메일의 어느 칸이 결제일인가" 같은 양식 지식은 추출기의 데이터와 테스트에 둔다.
5. **한 번 나온 사례를 규칙으로 만들지 않는다.** 같은 유형이 반복되고(제안: 5건 이상) 분기 검수에서 교정되지 않았을 때 규칙으로 올린다. 사용자가 범위를 정해 준 예외는 한 건이어도 §5에 올린다.
6. **모호하면 고르지 않고 묻는다.** 날짜와 원문으로 가릴 수 없는 충돌은 §6.2에 잠정 규칙과 선택지를 적어 한 번에 여쭌다.
7. 규칙을 고친 뒤에는 그동안 쌓인 교정 사례로 되돌아간 판정이 없는지 다시 돌려 본다.

## 8. 이 규칙집을 만든 방법

- 2026-11-10~11에 레포의 문서(`AGENTS.md`, `docs/specs/` 112개, `docs/history/` 8개, 현재 상태·운영 기록), 사용자 지시 메모, 판정 코드와 테스트에서 규칙 진술 7,195개를 뽑았다(출처 위치 3,086곳).
- 같은 뜻끼리 묶어 754개 규칙으로 줄였다. 날짜가 지나며 바뀐 규칙은 가장 최근의 사용자 결정을 현재 규칙으로 삼고 옛 규칙을 각 규칙 아래에 남겼다.
- 일회성 운영 기록(특정 거래를 한 번 처리한 내용), 아직 승인되지 않은 후속 제안, 화면 배치와 배포 절차는 규칙으로 올리지 않았다.
- 원문과 날짜로 가릴 수 없던 충돌 5건은 사용자에게 여쭤 확정했다(§6.1의 LINK-002, ITEM-019, TRIP-005, TRIP-047, LINK-061). 확정 뒤 드러난 겹침 1건은 §6.2에 잠정으로 남겼다.
- 한계: 문서와 코드에 남지 않은 구두 지시는 복원할 수 없다. 영역별 규칙은 추출·묶기 에이전트의 산출을 감독 세션이 표본으로 확인한 것이며 전수 검토하지 않았다. 빠지거나 틀린 규칙은 분기 검수의 교정으로 드러나고 §7의 절차로 고친다.
