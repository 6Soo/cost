# OTA·카드 거래 ‘우선 잠정 귀속 → 사용자 검토·교정’ 정책 명세 (2026-10-28)

> **2026-10-29 대체 정책:** 분류가 되면 완료이며 별도 확정/미확정 또는 잠정 후 승인 단계는 없다. 현재 계약은 [금융 명세의 자동분류 완료 계약](finance.md#자동분류-완료-계약-2026-10-29)이다. 아래 `AUTO_PROVISIONAL`·사용자 확정과 작성 당시 미구현 표시는 과거 설계 기록이며 재실행 지시가 아니다. 수동 교정·원본·금융 보호와 근거 표시 계약은 유지한다.

> **현재 구현 대조(2026-10-28 18:30):** [구현현황 감사](implementation-status-audit-20261028.md). 기존 분류 엔진에 `inferred_assignment`와 수동 우선 로직은 이미 존재하지만 **공통 `AUTO_PROVISIONAL` 결정 상태·유효 후보 ranker·검토/교정 새 UI는 미구현**. PA-01~06을 기존 코드와 별도 정책 구현으로 구분하고, 여행 우선 배정이 기존 금융 HOLD/실제 결제 확인을 대체하지 않도록 한다. 오래된 미해결 자동 숨김은 여전히 **명시적 불허**다.

- 상태: **SPEC_ONLY / 신규 정책 미구현 / 운영 배포 미실행**
- **사용자 반대 결정:** 오래된 미해결 OTA를 90일 경과만으로 검토 화면에서 제외하거나 과거 기록으로 보내지 않는다. **해결 가능한 보류는 근거가 적어도 최선 후보를 빠르게 잠정 배정한 다음 사용자가 검토해 교정**하는 기존 제품 대원칙을 우선한다.
- 대상: 카드 정상 지출의 여행 귀속, OTA 예약↔거래 후보의 추론·검토 우선순위, 화면 보류 감소, 확인/교정/학습 제안.
- 제약: [금융 원본·여행 권위 규칙](finance.md), [OTA solver](ota.md), [OTA 대기열](ota-review-queue-performance-20261027.md), [전면 리팩토링](refactor-master-20261027.md), [지출 정리 필터](expense-cleanup-status-filter-actions-20261028.md).
- 최중요 구분: **여행에 대한 잠정 배정(provisional trip attribution)**과 **특정 OTA 예약과 실제 카드 결제를 금융적으로 확정 연결(settlement/payment identity)**은 서로 다른 상태·권한·증빙을 가진다.

## 1. 현 상태와 문제 정의

현재 COST에는 자동 여행 추론 규칙, 높은 추론 표시, 정상 카드 우선 비용 준비, 원본 충돌/취소/동일 금액 결제 보호, OTA 사유 큐와 사용자 교정 수단이 이미 있다. 그러나 다음 운영 경험이 목표를 만족하지 못한다.

- 화면에서 `추론 배정 높음`을 표시하면서 실제 여행 ID가 비어 있거나, 근거가 적은 거래는 수동 미배정으로 장기간 남는 경우.
- 실패한 OTA 개별 사건의 사유를 규칙 하나하나 추가해서 처리하는 데 개발 자원이 소모된다.
- 읽기 근거/결제/여행 ID가 다른 상태인데 단일 `보류`로 묶여 사용자가 무엇을 검토해야 하는지 알기 어렵다.
- 수동 교정 후 모델/규칙 제안·검증된 패턴 재사용이 업무 흐름에 연결되지 않아 같은 유형의 일이 반복된다.
- 현재 OTA 426세대 실제 큐 수: 총 3,799사건, needs_action 43, waiting_source 820, evidence_missing 2,740, completed 196. 숫자는 **사건의 결제 증거 큐**이지 ‘3,560건 여행 미배정’을 뜻하지 않는다. 이것을 여행 미배정 건수로 오해하거나 모두 ‘완료’로 승격하지 않는다.

**해결 방향:** 정책 예외를 무한 추가하기보다 **공통 여행 후보 생성 → 근거별 점수화 → 안전한 조건에서 잠정 여행 선택 → 하나의 사용자 검토 대기열 → 교정 근거 축적**이라는 결정 파이프라인을 만든다.

## 2. 사용자 확정 정책

1. **소수 근거에서도 우선 배정**: 유효한 단일 최선 여행 후보가 있고 사용자 결정/금융 보호 충돌이 없으면 낮은 신뢰도라도 `AUTO_PROVISIONAL`로 배정한다.
2. **사용자 검토 후 교정**: 자동 배정은 확정이 아니라 검토 전 임시 판단. 화면에서 추론 근거·대안 후보·상세 원본을 보고 한 번에 교정/확정/배정 해제할 수 있어야 한다.
3. **나이가 오래됐다는 이유로 미해결 건을 숨기지 않는다**: 90일·180일·연도 경과로 미해결을 자동 완료/폐기/이력 분리해 검토에서 제외하는 정책 **불채택**. 자료의 오래됨은 정렬/검색 기준일 수 있지만 접근 가능성과 해야 할 조치 상태를 바꾸지 않는다.
4. **여행 후보를 고르는 데 예약의 완전한 금융 증빙은 필수 아님**: 여행 기간, 확인된 예약 이용기간, 결제일과 사용일, 위치/공급자, 전후 여행 맥락 등 사용 가능한 단서로 여행을 잠정 고를 수 있다.
5. **금융 결제 증빙은 별개**: 카드↔예약 identity, 실제 매입/환불/기장 확정에는 기존 엄격한 보호·1:N·통화·금액·사용자 권한을 유지한다. `AUTO_PROVISIONAL`을 `MATCHED_AUTO`나 실제 환불 완료로 변환하지 않는다.
6. **수동 교정이 제일 강함**: 기존 owner의 여행 이동, 예약 pin, 제외·보류·카드/장부 결정은 자동 재대사와 신규 명세로 절대 덮지 않는다. 사용자가 확정한 뒤의 자동 재분류는 방지.
7. **규칙 추가보다 일관된 엔진/피드백**: 공급자별 특수 사례는 반드시 필요한 파싱/금융 식별자에만 남기고, 공통 여행 귀속은 1개 score/ranker·정책 버전과 교정 로그로 관리한다.

## 3. 단일 결정 모델 (두 축 분리)

### 3.1 여행 배정 상태

| 값 | 뜻 | UI와 회계 처리 |
| --- | --- | --- |
| `USER_CONFIRMED` | 사용자가 현재 여행과 관계를 확정 | 가장 높은 우선순위, 자동 덮기 금지 |
| `AUTHORITY_VERIFIED` | 직접 연결된 검증된 원본/예약과 여행 정본 일치 | 기본 여행으로 표시, provenance 유지 |
| `AUTO_PROVISIONAL` | 일반 추론에서 최선의 유효 여행 하나 선택, 근거 낮음/중간 가능 | **여행 탭에 잠정 표시**, ‘검토 필요’ 배지/대안 제공. 내부 비용 준비/Google 출력은 별도 금융 적격 게이트 적용 |
| `UNASSIGNED_NO_VALID_TRIP` | 유효한 여행 없음/원본 시기 완전히 미일치 | 대상 없음, 명시 검토 큐 |
| `CONFLICT_REVIEW` | 동점 후보·원본 날짜 충돌·확정된 다른 권위 충돌 | 거래·후보는 보여 주되 임의 최종 배정 금지 |
| `FINANCIAL_HOLD` | 환불/취소/중복/수동 보류 등 금융 보호 우선 | 단순 여행 후보가 있어도 금액·기장 해제 금지. 여행 후보는 참고 읽기 상태로만 노출 |

### 3.2 OTA 예약↔금융 거래 관계 상태

- `MATCHED_VERIFIED`: 현행 검증된 카드/OTA 관계 (정본 근거, 1:N 환불 및 전역 점유 정책 충족).
- `POSSIBLE_MATCH`: 금액·일자·거래처 등 낮은 증거로 생성된 **읽기 전용 후보**. 최선 후보라도 실제 결제 확인/장부 확정값으로 쓰지 않는다.
- `NO_PAYMENT_EVIDENCE`: 검증된 결제 증빙이 없음. 여정·여행 귀속은 별도 유지.
- `CONTESTED_MATCH`: 여러 예약이 하나의 카드 원행을 경쟁/원본 충돌. 최상위 후보를 표시할 수는 있으나 금융 연결 확정 금지.
- `CANCELLATION_REFUND_UNVERIFIED`: 취소/환불 관련 본래 보호 상태 유지.

**금지:** `AUTO_PROVISIONAL` 여행 배정 성공을 OTA 사건의 `completed` count에 합산하거나 `POSSIBLE_MATCH`를 `payment_status=paid`로 쓰기.

## 4. 추론 후보 생성·점수 설계

### 4.1 1차 후보 생성

권위 있는 현재 여행 목록을 한 번 읽고, 카드/OTA 예약별로 날짜·정본을 기준으로 후보 여행을 수집한다.

우선적 증거(상대적 중요도 높은 순서):
1. 기존 검증된 booking_ref→trip_id 또는 예약의 실제 이용기간과 여행 기간이 겹치는 직접 연결.
2. 최초 출발/체크인/이용일이 여행 기간에 포함.
3. 실제 카드 사용일(없으면 승인일)과 여행 기간의 시간적 근접성. **매입일은 귀속 날짜가 아님**.
4. 검증된 공급자/장소·여행지·가이드의 기존 연결과 일치.
5. 단일 활성 여행 후보, 같은 카드의 전후 정상 거래에 사용자가 확인한 여행 패턴, 이전에 **사용자 승인된** 별칭/교정 패턴.

일부 OTA는 결제 선행 기간이 길기 때문에 카드 승인일이 여행일에 가까워야 한다는 **고정 ±N일만**으로 예약을 탈락시키지 않는다. 예약 이용일이 있으면 그것을 우선한다.

정보가 없으면 `UNKNOWN`으로 명시하고 무관한 사실을 생성하지 않는다. 모든 점수 요소는 출처·시각·정책 버전과 함께 보존한다.

### 4.2 잠정 배정 결정

- 유효한 여행 후보가 **1개뿐이고** 기존 확정 사용자 결정·금융 보호·신뢰 가능한 반대 근거가 없다면, 소수 단서만 있어도 `AUTO_PROVISIONAL`로 설정. 예: 1개의 이용일과 활성 여행 기간 일치.
- 후보가 복수라면 설명 가능한 점수/우선순위로 비교해 **충분히 차별화되는 최상위 1개**가 있을 때만 그 후보를 `AUTO_PROVISIONAL`로 선택. 일정·장소·사용자 확정 권위를 정면 위배하면 선택 불가.
- 후보가 동률 또는 차이가 미미하면 `CONFLICT_REVIEW`: 상위 2~3개 제안 및 사용자의 한 클릭 선택. **낮은 근거를 허용한다는 이유로 임의의 첫 여행을 고르지 않는다.**
- 후보가 없거나 유효하지 않으면 `UNASSIGNED_NO_VALID_TRIP`. 새 여행 생성·가짜 ID 부여 금지.
- 분류가 이미 장부에 쓰인 사용자 승인 값/수동 제외/잠긴 비용 행을 보호한다. 저장 위치를 바꿔서 이런 보호를 우회하지 않는다.
- **낮은 추론 임계치의 구체 점수·마진은 읽기 전용 shadow 비교와 실제 owner 교정률을 측정해 한 정책 버전으로 고정한다.** 숫자를 문서에서 임의로 “성공 100%”라고 만들지 않는다.

### 4.3 누적 규칙 병목 제거

- 데이터 파싱 규칙은 실제 원본 포맷에 필요한 최소화. 여행 귀속은 공급자별 독립 ‘맞춤 예외 수십 개’가 아니라 공통 candidate generator/ranker를 통해 처리.
- 후보 생성·점수 계산은 snapshot 단계에서 한 번 하고, UI/카드 상세/지출 검토/여행 탭은 **같은 decision projection**을 소비.
- 읽기 GET마다 메일 전량 파싱·전 여행 전체 재점수/전체 DB 스캔 금지. 변경된 원본·여행 권위·수동 결정·정책 버전에 따라 generation/cache invalidate.
- 과거 같은 패턴의 owner 교정을 분석해 **규칙 제안** 생성. 기존 정책대로 최종 일반화는 사용자의 승인이 있어야 하고, 승인 범위(가맹점/기간/여행) 외에 적용 금지. 교정 하나가 모든 여행에 무제한 적용되지 않음.
- 사용자 교정값을 명시적으로 예측 평가 데이터로 유지해 heuristic 추가 전후 오배정률을 측정한다.

## 5. 업무 흐름: 거래가 들어온 순간부터

~~~text
새 카드/OTA 예약 수집 (원본 보존)
      ↓
1. 기존 중복/환불/보호/사용자 결정 확인
      ↓
2. 유효 여행 후보 자동 생성 + 점수/근거
      ├ 확정 권위 → AUTHORITY_VERIFIED
      ├ 단일/차별화된 최선 후보 → AUTO_PROVISIONAL
      ├ 충돌 → CONFLICT_REVIEW (후보 2~3개 제안)
      └ 유효 여행 없음 → UNASSIGNED_NO_VALID_TRIP
      ↓
3. 금융·OTA 관계는 별도 MATCHED_VERIFIED / POSSIBLE_MATCH / HOLD 판정
      ↓
4. 기본 거래 화면에 '잠정 배정: 여행 A / 검토 필요' 표시
      ↓
5. owner가 확인/여행 B로 교정/보류·해제, 한번에 다음 거래
      ↓
6. 사용자 확정 우선의 감사 결정 + 재분류 보호
      ↓
7. 향후 같은 패턴에서 규칙 제안 → 승인 후 제한적 자동 재사용
~~~

### 5.1 구체 UI

- 거래 카드: `여행 A (자동 잠정)`, 신뢰 등급, 최소 1개 **실제로 유효한** 근거, `대안 여행 보기`, `확정`, `다른 여행 선택`, `보류`를 같은 카드에 표시.
- `지출 정리`에는 `잠정 배정·검토 필요 N건` 탭/상태 필터 추가를 권장. 이미 정한 `항목 미분류 / 여행 미배정 / 보류·오류 / 기타 검토`의 배타적 주된 사유 분류와 **별도 보조 검토 태그**를 둬 건수 중복이나 누락을 방지.
- `여행 미배정`에는 유효 후보 0·충돌로 최종 귀속이 없는 거래만. 이미 `AUTO_PROVISIONAL`로 선택된 항목은 미배정으로 표시하지 않되 **검토 대기**에서 반드시 찾을 수 있어야 한다.
- 전체 OTA 사건 수천 건에서 근거 없는 결제 문제를 숨기지 않는다. 예약별 인라인 상세·서버 20건 페이지·검토 우선순위를 사용해 편하게 처리한다.
- `일괄 검토`는 정상 잠정 배정 다수의 **미리보기/승인 확인**을 지원할 수 있지만 owner 재확인과 금융 보류 제외/정본 보존 검증이 필수. 실 결제/환불 확정 자동 배치는 별도 정책.
- UI에서 보여주는 추론 문구와 실제 `trip_id/display_tab_id` 상태는 같은 결정 소스를 읽는다. `높음`인데 화면은 `여행 미배정` 같은 모순은 오류로 보고한다.
- owner의 교정은 단순 레이블 변경이 아니라 기존 감사 경로를 통해 저장되고 재접속/재수집 후에도 유지.

## 6. 오래된 미해결 거래 정책: 사용자 거부사항 반영

**자동 보관/숨김/완료 처리 금지.**

- 보류의 나이를 이유로 `historical`로 보내 기본 검토 대상에서 제외하는 90일 정책은 **사용자 명시적 거부로 취소**.
- 전체 미해결/원본 미확인 거래는 상태·사유가 남아 있고 현재 검토 대기열의 필터/검색/정렬에서 찾을 수 있어야 한다.
- 너무 긴 목록은 **서버 측 페이지네이션 20건, 예약 그룹화, 우선순위, 검토 완료만 별도 접음**으로 다룬다. 오래된 미해결 자체를 숨기지 않는다.
- `waiting_source`, `evidence_missing`도 여행 후보 추론이 가능하면 별도의 여행 잠정 배정은 진행할 수 있다. 그러나 결제 완료 보류 여부·원본 증빙 부족은 그대로 남긴다.
- owner는 `근거 부족 전체 보기`, `잠정 귀속 검토`, `충돌`, `유효 여행 없음`, `원본/외부 증빙 대기`를 검색 가능해야 한다.
- 별도의 수동 보관을 미래에 만든다면 금융 상태 불변·모든 기록 검색 유지·소유자 명시 조작과 되돌리기를 필요로 한다. 사용자 승인 없이 구현 금지.

## 9. 수락 테스트 시나리오

1. 여행 A가 유일하고 카드 사용일·가맹점이 부분 근거만 있는 일반 비용 → `AUTO_PROVISIONAL(A)`, 여행 탭과 지출 정리에서 실제 A 표시, 검토 필요 태그; OTA 결제 완료로 오인하지 않음.
2. 환불 링크 근거 없어도 여행 후보 A만 있으면 참고 후보를 제시하되 취소/환불 금융 HOLD와 실제 금액·기장 권한 보호.
3. 두 여행 A/B가 같은 날, 보조 근거 없이 동률 → `CONFLICT_REVIEW`, 임의 한 곳 자동 쓰기 금지.
4. A가 시간/이용기간과 맞고 B는 단순 결제일 근접 → A 선택, 귀국일이 A 종료일 넘어도 별도 항공권 최초 출발 여행 정책 유지.
5. 예약 출처가 없고 카드에서 OTA 후보 2개가 같은 금액 경쟁 → 각 여행의 가능한 후보는 표시, 둘 중 하나를 금융 확정하지 않음.
6. 사용자가 잠정 A를 B로 이동 확정 → 재수집/규칙 갱신/worker 재시작 후 B 유지.
7. 사용자가 `미배정으로 유지`·`보류`·`제외`한 항목은 자동 추론으로 다시 배정되지 않음.
8. UI에 `추론 높음` 근거만 있고 실제 유효 여행 ID가 없는 오래된 거래 → 동일 서버 decision에 맞춰 레이블 수정/재분류 결과 표시, 서로 모순 없음.
9. 과거 90일 초과 근거 부족 OTA 보류는 자동 archive/완료/숨김 0; 페이지·검색에서 계속 접근 가능.
10. 금융 카드 1:N 환불, 초과 환불, 유일성 경쟁, 미확인 외화 환율, 사용자 확정 예약 관계의 보호 회귀.
11. 잠정→검토 완료 카운트 전환 시 중복 count 0, 필터 변경 후 20건 제한 유지.
12. 10k/100k 합성 OTA 이벤트와 대량 카드에서 ranking 성능/summary p95 및 전체 재대사 반복 비용 측정.
13. 낮은 근거 배정의 **owner 수정률, 1차 여행 배정 성공률, false positive 발견률, 미배정 건수 감소**를 기준선과 비교. 숫자만 개선되도록 근거 없는 100% 배정 금지.
14. Google final ledger/사용자 확정/원본 카드 금액·날짜/보호 테이블 내용 불변. 수동 교정만 기존 승인된 감사 경로에서 기록.

## 10. 기존 OTA 큐 분류와의 정합성

OTA 사건의 `needs_action/waiting_source/evidence_missing/completed`는 **금융/증거 검토 상태**다. 잠정 여행 귀속으로 `evidence_missing`→`completed`를 자동 변경하지 않는다. 두 축을 결합한 대기열 필터로 owner가 계속 대처할 수 있게 한다.

기존 `historical` projection은 화면 내 검색 이력/완료 기록에만 활용할 수 있으나 **미해결의 연령 기반 자동 제외 정책으로 사용 금지**. 필요하면 기존 큐 UI의 90일 정책 문구를 삭제하고 사용자 최신 결정을 링크한다.

## 11. 완료 판정

이 문서의 병합만으로 `PA-01~06`가 동작하지 않는다. 운영 DB 검증/실제 배정 수정/성능·교정률은 별도. 상태는 `SPEC_ONLY → CODE_WRITTEN → TEST_PASSED → MERGED → DEPLOYED → REAL_DATA_ACCEPTED`로 기록한다. 추론 단서가 낮아도 **먼저 유효한 여행 후보를 제안·잠정 배정하고, 사람이 검토해 교정하는 제품 흐름**을 구현하는 것이 완료 기준이다.
