## 2. 항공권 예약일 문제의 제품 결정

### 2.1 왜 '예약일'을 못 찾았나

- 항공권 확인 메일에 있는 **출발일**은 예약 생성일이 아니다. **이메일 수신/발송일, 발권일(issue), 카드 승인일/매입일, 여정 일자**도 예약일로 대체할 수 없다.
- 기존 항공권 인덱스의 이름/예약번호/구간·검증 근거는 활용할 수 있지만 예약 생성 일자 필드는 현재 보장되지 않는다. 메일 280건의 지원 표기 검사 0건은 현재 파서의 한계이지 모든 형식에서 실제 예약일이 없다는 뜻이 아니다.
- 수동 날짜 필터는 **이미 구현·배포**했으며, 선택 날짜는 `USER_SELECTED_CARD_DATE`일 뿐 **확정 항공권 예약일이나 결제 연결 근거가 아니다**.

### 2.2 근거 출처 조사 우선순위 (read-only)

1. **예약을 생성한 공급사/OTA의 주문 상세:** Trip.com 등 예약 원천에서 `created_at`, `booking_created_at`, `order_time`, `예약 완료 일시`처럼 **실제 예약 생성 사건**을 뜻하는 필드가 있는지, 그 필드가 **항공권 예약번호 + 공급자/주문 ID**와 확실히 연결되는지 확인. *API 필드명이 있다고 예약일 의미가 보장되지는 않으며, 문서·화면 설명을 교차검증해야 한다*. 읽기 전용의 기존 인증/연동 수단 우선. OTP·신규 계정 인증 우회 금지.
2. **예약 확정/구매 완료 원본 메일·첨부 영수증·PDF:** 본문/첨부에 **명시적인 예약 생성일/예약 확정 시각**이 있을 때만 그 텍스트와 동일 예약 식별자/이름·공급자 근거를 비교한다. 출발일·발권일·메일 Date/Received만 있는 경우 `BOOKING_DATE_UNKNOWN` 유지.
3. **카드 기록의 승인 날짜·OTA 결제 영수증:** *카드 검색을 좁히는 보조 날짜* `PAYMENT_DATE_EVIDENCE`로만 사용. 결제일이 예약일과 같은 경우도 있으나 자동으로 동치 취급 금지. 모든 후보는 연결 미확정.
4. 위 근거가 없으면 **사용자 명시 날짜** 필터(기존 PR #129)를 사용한다. 사용자가 선택한 날짜는 영구 예약일 확정/저장값이 아니라 이번 조회의 필터다.

### 2.3 예약일 데이터 계약과 표시

- 각 예약은 안정적인 예약 키에 `booking_date_status = CONFIRMED | UNKNOWN | CONFLICT`를 가지며, CONFIRMED에는 날짜/시간대/출처 종류/원본 내용 digest/원본 revision/필드 의미를 결속한다. 공급자마다 예약번호 충돌 가능성이 있으니 `provider + order_id + booking_ref`를 검증하고 인덱스 세대 바뀌면 근거를 재평가한다.
- 두 출처 날짜 충돌, 취소 후 재발행·여정 변경으로 사건이 달라짐, 여러 탑승객이 같은 예약번호를 공유하는 경우 자동 결합하지 않고 `CONFLICT/NEEDS_REVIEW` 표시. UTC와 한국/현지 시간의 자정 경계에 주의하고 카드 승인일의 시간대 차이는 사용자 명시 선택 없이 ±1일 자동 확장 금지.
- UI 구역: `예약일: 2026-..-.. (예약 원본 확인됨)` / `예약일: 확인 불가`; 결제일/발권일은 다른 라벨로 표시. 확정된 결제 연결은 별도 카드로 표시하고, **미연결**이며 CONFIRMED일 때만 `예약일의 카드 전체 내역`을 기본 열람하게 한다.
- 원본 확인 실패 시 문구: **'예약일을 확인할 수 없습니다. 날짜를 직접 선택하면 그날의 카드 거래를 모두 확인할 수 있습니다. 선택한 날짜는 예약일로 확정되지 않습니다.'** 날짜 선택 후 헤더는 **'직접 지정한 날짜의 카드 거래'**. 고객 이름과 예약번호를 URL 쿼리/로그·Git/운영 증빙에 기록하지 않는다.
- 카드 후보는 일별 100건 커서 등 현재 읽기 전용 API를 재사용한다. 취소·환불·중복·타 예약 점유 원행을 누락 없이 제공하되, 자동 완납/미결제·배정/링크/기장 결정은 하지 않는다.

### 2.4 단계별 구현 티켓

| 단계 | 티켓 | 작업/검증 |
| --- | --- | --- |
| 1 | `FLIGHT-DATE-AUDIT-01` | 항공권 공급자 주문 상세·메일 파서·예약 근거 인덱스를 **읽기 전용으로** 지도화. 실제 예약일 제공 필드의 뜻/예약 ID·지문/시간대를 합성 fixture로 증명. 근거가 없으면 UNKNOWN 보고하고 parser 수정 금지. |
| 2 | `FLIGHT-DATE-INDEX-01` | 검증한 예약일 필드를 기존 인덱스에 **nullable, provenance/revision bound** 형태로 투영. 기존 예약 API 호환·source changed/stale·충돌 검증. **개인 실자료를 테스트로 복제하지 않음**. |
| 3 | `FLIGHT-DATE-UI-01` | CONFIRMED일 때 예약일 표시와 모든 카드 후보 읽기 조회 자동 제공. UNKNOWN/CONFLICT는 수동 날짜 필터를 기본 대안으로 제공. 취소·환불/다중 결제/동명이인 상태별 명확한 표시. |
| 4 | `FLIGHT-DATE-AC-01` | 합성 테스트: 날짜 출처 우선·메일 Received 거절·발권/출발/결제일 대용 거절·충돌·시간대·1,005건 페이징·no-store/owner·DB bytes 불변/읽기 전용·원본 revision 변경. 실제 owner 사용 경로는 별도 수락. |

**작업 완료 게이트:** 실제 예약 생성일 필드를 확보하지 못하더라도 **수동 날짜 조회를 정상 제품 기능으로 유지하고 작업을 `BLOCKED_EXTERNAL_EVIDENCE`로 명확히 표기**한다. 미확인 정보를 사용자가 원한 결과처럼 꾸미지 않는다. 출처가 확인되면 추론이 아닌 증거 기반 자동 조회로 발전시킨다.
