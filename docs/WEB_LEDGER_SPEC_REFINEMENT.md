# 웹 장부 후속 명세 보완

후속 구현 검토: [확인된 결함·재현 결과·수정 순서](WEB_LEDGER_IMPLEMENTATION_REVIEW.md). 기존 구현 결함과 이 문서에서 나중에 확정한 기능을 구분한다.

작성일: 2026-09-24. 작성 범위: 현재 설계 세션의 후속 명세. 앱 구현·구현 승인·배포 기록이 아니다.

기준: [제품 명세](WEB_LEDGER_APP_SPEC.md), [상세 동작 계약](WEB_LEDGER_DETAILED_CONTRACT.md), [결정 등록부](DECISION_REGISTER.md).

현재 [구현 기록](WEB_LEDGER_IMPLEMENTATION_LOG.md)에 다른 작업자의 Phase 1~4 합성 구현·검증 보고와 Phase 5 예정이 있다. 이 문서는 그 보고를 독립 검증한 결과가 아니다. 해당 작업자의 코드·진행 기록을 수정하거나 완료 상태를 재설정하지 않는다. 이 보완 문서는 한 파일에 이어 쓰며 질문마다 새 문서를 만들지 않는다.

## 1. 상태와 적용 방법

- `기존 확정의 구체화`: 이미 사용자가 선택한 정책을 구현 동작으로 명확하게 표현한다. 새 업무 권한을 부여하지 않는다.
- `사용자 확정`: 이번 답변으로 정한 업무 정책이다. 세부 저장 방식과 오류 처리는 그 정책을 만족하기 위한 설계이며 사용자가 모든 기술 선택을 직접 지정했다는 뜻은 아니다.
- `설계 수정안`: 기존 초안의 중복·불일치를 고치기 위한 제안이다. 확정 정책을 뒤집는 용도로 쓰지 않는다.
- `답변 대기`: 선택지를 제시했으나 사용자 답변이 없다. 구현자가 추천안을 선택한 것으로 취급하지 않는다.

구현자는 이 문서의 답변 대기 항목과 기존 완료 범위를 구분한다. 후속 사용자 답변이 확정되면 변경된 정책과 영향을 받는 화면·API·검증을 함께 기록하고, 해당 범위에만 적용한다. 이전 구현 결과는 당시 기준으로 보존하되 새 명세까지 충족한다고 자동 승격하지 않는다.

## 2. 항상 보이는 장부와 출력의 일치

상태: 기존 확정의 구체화. 대상: Phase 2~5.

웹 표의 정본은 저장된 현재 장부다. 사용자는 파일 출력을 하지 않고도 출력 대상의 업무 내용을 확인할 수 있어야 한다. 엑셀의 인쇄 모양과 웹의 편집 화면이 픽셀 단위로 같아야 한다는 요구는 아니다.

| 상황 | 장부에 표시할 내용 | 출력 |
|---|---|---|
| 편집 전 | 현재 저장값과 같은 버전의 합계 | 현재 저장값 |
| 편집 중 | 편집 중인 행에 초안과 미저장 표시, 공식 합계는 저장값 | 먼저 저장 또는 돌아가기 |
| 저장 성공 | 서버가 확정한 새 행과 영향 여행의 합계 | 새 저장값 |
| 업로드 처리 중 | 커밋된 결과부터 표시, 가져오는 중임을 별도로 표시 | 아래 진행 중 출력 기준 적용 |
| 규칙 미리보기 | 현재 장부는 유지, 예상 변경은 별도 비교 영역 | 실제 적용 전 값 |
| 규칙 적용 완료 | 적용된 저장값과 합계 | 같은 저장값 |
| 후보·미확정 포함 | 기본 표는 일반 행, 내부 상태 보존 | 그대로 출력, 안내는 출력 대화창에만 표시 |
| AI 연결 장애 | 장부 저장과 이미 반영된 행 유지 | AI와 무관하게 출력 가능 |

진행 중 출력의 구현 기준: 출력 대화창에 `내역을 가져오는 중입니다. 현재 저장된 내용만 포함합니다`와 현재 포함 건수를 표시한다. 사용자가 출력하면 그 순간 커밋된 행을 일관된 스냅샷으로 고정한다. 아직 처리하지 않은 행을 누락 없는 최종 가져오기 결과라고 설명하지 않는다. 완료된 뒤 다시 출력하면 새 출력 버전이 된다. 부분 업로드 결과를 출력하려고 전체 작업을 재실행하거나 AI를 호출하지 않는다.

화면에서 확인한 값과 출력 값이 달라질 수 있는 시점은 출력 준비 중 다른 저장이 일어났을 때다. 출력 기록에 기준 버전을 고정하고, 이후 변경이 있으면 `출력 준비 후 장부가 변경되었습니다`를 알려 새 버전 출력 여부를 선택하게 한다. 출력 스냅샷의 일부만 최신 값으로 교체하지 않는다.

검증: 규칙 미리보기만 열었을 때 출력값이 바뀌지 않아야 한다. 카드 작업이 일부 커밋된 시점에 출력하면 포함 건수가 고정되고, 나머지가 끝나도 이미 생성된 파일은 변하지 않아야 한다. 저장 응답을 받기 전에 출력 버튼을 연 경우 미저장 초안을 조용히 제외하지 않아야 한다.

## 3. 기존 양식 대비 화면 간소화 검토

상태: 설계 수정안. 아직 사용자가 모든 조정을 확정한 것으로 기록하지 않는다. 요청된 업로드·모바일·직원 조회·AI 보조·이력을 제거하는 제안이 아니다.

기존 `매출자료 양식_rev`의 기본 업무 표는 수입 7열과 지출 7열, 수입·지출 합계와 회사수익인식이다. 추가 보조 정보는 업무 표에 새 열로 계속 붙이지 않는다.

| 위치 | 기본 표시 제안 | 필요할 때 열기 |
|---|---|---|
| 여행 목록 | 날짜·행선지·현재 선택, 분류대기 건수 | 보관 목록·관리 |
| 상단 | 여행 제목, 내역 가져오기, 선택 탭 출력 | 설정·세부 정보 |
| 본문 | 기존 두 표와 합계 | 고객별 합계 |
| 행 상세 | 선택 행의 내용·증빙, owner의 메모 | owner의 원천 비교·변경 이력·기술 근거 |
| 규칙 변경 | 저장한 행과 규칙 대화 | 영향 행 상세 |
| 출력 대화창 | 선택 여행·순서·행 수·미확정 안내 | 템플릿·기준 버전·해시 |

중복 금액 카드를 여행 목록·전역 상단·본문에 모두 표시하는 요구를 기본으로 두지 않는 안이다. 원천 보존·권한 검사·중복 방지는 서버에서 계속 수행하되 매번 사용자 확인창으로 만들지 않는다. 수정 이유는 기존 확정대로 예외와 규칙 변경을 구분하되 행 저장 영역에 함께 배치하는 안이다.

이 화면 조정을 구현 범위에 포함할지는 사용자 확인 이후 확정한다. 다른 구현자가 진행 중인 Phase 5의 완료 조건을 이 제안만으로 바꾸지 않는다.

## 4. 원래 양식의 제목과 작성 정보

상태: 기존 양식 보존의 구체화와 작성일·담당자 사용자 확정. 대상: Phase 2·5.

2026-09-24 읽기 전용 확인: `ledger/data/ledger_current.xlsx`의 `매출자료 양식_rev`에 회사 표시 B2, 제목 C2:H2, 작성일자 D4·E4, 담당자 H4가 있다. 확인 파일 SHA-256은 `76e839c5c001f67d8cb94a266b9f0e42eff5164e93591163d15b474b6b37fa56`이다. 이 해시는 최신 Google Drive와의 일치를 증명하지 않는다.

- 기존 회사 표시와 양식의 위치·병합을 보존한다. 앱 개발자 이름이나 모델 이름으로 바꾸지 않는다.
- 여행 제목은 선택한 여행과 연결한다. 고객별 거래일을 모아 여행 일정을 추정해 제목을 만들지 않는다.
- 템플릿에 들어 있는 작성일과 담당자 예시를 모든 새 출력의 실제 작성값으로 무조건 복사하지 않는다.
- 회사 정보·담당자·작성일은 수입·지출 행마다 입력시키지 않는다. 장부 또는 출력 메타데이터로 관리한다.
- 작성일은 여행별 저장값으로 관리하고 최초에는 오늘 날짜를 사용한다. 담당자는 소유자 이름을 기본으로 사용하되 여행별로 변경할 수 있다. 화면의 역할명 `대장`을 양식의 담당자와 자동으로 같다고 보지 않는다. 상세 기준은 12절을 따른다.
- 값이 미정인 합성 출력에서는 예시값임을 구현 보고에 명시한다. 실제 제출용 정보가 확인됐다고 보고하지 않는다.

## 5. 여행 탭의 상태를 구분하는 계약

상태: 내역 처리 후 삭제, 표시 이름 전체 자유 편집, 수동 보관·복원은 사용자 확정이며 8·14절을 따른다. 아래 상태 분리는 이 정책과 기존 권위 규칙을 함께 지키기 위한 기술 계약으로 제품 명세에 반영했다. 대상: Phase 2의 탭 관리, Phase 7의 권한.

제품 명세의 과거 `authority_status: authoritative | needs_review | archived`는 일정 근거와 화면 보관 상태를 한 필드에 섞고 있었다. 현재는 다음처럼 독립된 책임으로 구분한다. 물리 테이블을 둘 더 만들라는 뜻은 아니다.

- 일정 근거 상태: 기존 권위 일정 규약의 authoritative·검토 필요 상태를 참조한다.
- 화면 보관 상태: 활성·보관 여부를 나타낸다. 여행 종료 자체가 보관이나 담당 해제는 아니다.
- 조회 권한: 예약 시스템의 유효 담당 배정을 따른다. 보관 여부로 권한을 우회하지 않는다.

선택 결과와 관계없이 보존할 조건:

1. 표시 이름을 바꿔도 trip_id·tab_id·원천 거래 ID는 바뀌지 않는다.
2. 표시 이름 변경으로 예약 원천의 목적지·시작일·종료일을 수정하지 않는다.
3. 보관으로 비용이나 수입을 삭제하거나 합계에서 몰래 제외하지 않는다.
4. 이전 출력은 당시 이름과 저장 버전을 보존한다. 새 이름으로 과거 파일을 덮어쓰지 않는다.
5. 삭제하더라도 수입·지출·규칙·원천 연결이 끊기는 숨은 삭제를 만들지 않는다. 내역 처리 방법을 선택한 뒤 삭제하는 범위는 확정됐으며 8절을 적용한다.

사용자 답변: 내역 있는 탭도 연결된 내역의 처리 방법을 선택한 뒤 삭제할 수 있다. 삭제의 구체적 처리와 검증은 8절을 따른다. 기존 특수 권위 탭의 원천 보존 의무는 그대로 유지한다.

## 6. 저장 취소·되돌리기·실제 환불의 구분

상태: 기존 계약의 구체화와 직전 행 수정 되돌리기 사용자 확정. 대상: Phase 2·4·6.

| 동작 | 의미 | 저장 이력 |
|---|---|---|
| 편집 취소 | 아직 저장하지 않은 초안 폐기 | 새 업무 변경 사건 없음 |
| 저장 후 되돌리기 | 이전 값을 현재 값으로 복원하는 새 변경 | 원래 변경과 복원 변경 모두 보존 |
| 수입·지출 정정 | 실제 업무값 또는 해석 오류 수정 | 원천 종류별 편집·정정 계약 적용 |
| 실제 취소·환불 | 돈의 흐름에 새 사건이 발생 | 원래 거래와 별도의 사건·부호 보존 |

되돌리기는 현재 revision을 검사한다. 다른 변경이 생긴 뒤 과거 값으로 무조건 덮어쓰지 않는다. 카드 날짜·금액·원천은 되돌리기 경로로도 변경할 수 없다. 은행 정정의 복원은 이전 정정 사건을 삭제하는 대신 새 정정 기록을 남긴다. 같은 복원 요청 재시도는 이력과 금액을 두 번 변경하지 않는다.

행을 되돌리는 것과 미래 규칙을 비활성화하는 것은 서로 다른 동작이다. 행 복원만으로 다른 행이나 미래 규칙이 자동으로 바뀌지 않는다. 사용자 답변으로 해당 행의 직전 수정 되돌리기만 확정됐다. 임의 과거 revision 선택과 규칙 묶음 전체 복원은 이번 범위에 넣지 않는다.

| Q-WEB-EVIDENCE-DOWNLOAD | 직원 증빙 다운로드 | 증빙도 미리보기만 제공으로 확정 | 증빙 제공 |
| Q-WEB-HOSTING-BUDGET | 웹앱·DB·파일 저장 운영비 기준 | 무료 범위로 먼저 시험, 유료 전환은 필요성과 비용을 제시한 뒤 별도 승인으로 확정. Gemini 정책과 별개 | Phase 9 운영 환경 |

분할 수입은 기존 `입금 한 건당 한 행`의 표시 범위를 변경한다. 원천 입금 사건은 계속 한 건이고 분할한 사건에 한해 화면과 xlsx에 배분 행을 표시한다. 일반 입금을 고객별 합계 행으로 합치는 것은 여전히 금지한다. 10절에 원금·배분 합계·출력 계약을 정의한다.

재개 위치: 8~16절의 확정 정책과 교차 동작을 결정 등록부·제품 명세·구현 계약·상세 계약·구현자 전달문에 연결했다. 세부 동작은 이 문서에 유지해 중복 복제하지 않는다. 운영비도 무료 선행 시험·유료 전환 별도 승인으로 확정됐다. 공통 운영 기준은 17절, 현재 시험안은 19절을 따른다. 이미 답한 정책을 다시 질문하지 않는다. 현재 세션은 코드 구현·모델 구현 호출·다른 작업자의 진행 상태 수정 없이 명세 작업만 수행한다.

## 8. 내역이 있는 여행 탭 삭제

상태: 사용자 확정 정책과 구현 세부 기준. 확정 내용은 내역 처리 방법을 선택한 뒤 탭을 삭제할 수 있다는 것이다. 아래 삭제 방식은 원천 보존을 만족하는 구현 계약이다.

### 8.1 삭제 화면

1. owner의 여행 관리에서 삭제를 선택한다. 탭 제목, 수입·지출 건수·금액, 연결 규칙·증빙 유무를 보여 준다.
2. 현재 내역의 처리 방법을 `다른 여행으로 이동` 또는 `분류대기로 이동` 중 선택한다. 내역이 없으면 이동 선택은 생략한다.
3. 행마다 다른 여행이 필요하면 기존 행 이동 기능으로 먼저 배정한 뒤 남은 내역에 삭제 작업을 적용한다. 첫 버전에 삭제 화면 전용 대량 배정 편집기를 중복 구현하지 않는다.
4. 이동 후 양쪽 합계와 분류대기 변화, 사용 중지할 배정 규칙을 미리 보여 주고 한 번 확정한다. 금액·원천·이력이 보존됨을 짧게 안내한다.

`삭제`는 화면 탭의 논리 삭제다. 원천 파일·거래·권위 일정·변경 사건·과거 출력은 지우지 않는다. 탭 삭제를 수입·지출 자체의 취소나 환불로 해석하지 않는다. 새 음수 거래를 자동 생성하지 않는다.

### 8.2 저장 경계

- 요청은 대상 tab_id, expected_revision, 미리보기 ID, 처리 방법, 목적지, client_request_id를 포함한다. 목적지를 원래 탭이나 삭제·사용 불가 탭으로 지정할 수 없다.
- 미리보기 후 관련 행·규칙·탭이 변경되면 `DELETE_PREVIEW_STALE`로 거부하고 갱신된 범위를 보여 준다. 숨은 새 행을 남기거나 같이 옮기지 않는다.
- 현재 행 이동, 관계 갱신, 해당 목적지로 보내는 규칙 효과의 비활성화, 탭 논리 삭제, 이력, 요청 결과를 같은 저장 작업으로 처리한다. 실패하면 일부만 삭제된 상태를 남기지 않는다.
- 다중 효과 규칙은 삭제한 여행으로 보내는 효과만 중지한다. 항목 분류 등 다른 효과를 분리해 보존할 수 없으면 해당 규칙을 중지하고 미리보기에서 설명한다. 새 규칙 버전과 원래 버전을 기록한다.
- 삭제된 여행을 대상으로 들어오는 이후 거래는 다른 여행으로 임의 배정하지 않는다. 기존의 유효 분류가 새 대상을 고르지 못하면 분류대기로 보낸다. 지연된 업로드 결과가 삭제 탭에 행을 넣지 못하도록 저장 직전에 탭 상태를 다시 검사한다.
- 이동한 행·증빙에는 이동 후 여행의 조회 권한을 적용한다. 과거 담당자가 이력 링크로 새 여행을 읽을 수 없게 한다.
- 예약 시스템의 여행·가이드 배정 자체를 삭제하지 않는다. 이후 예약 동기화가 같은 외부 여행 ID의 삭제 탭을 조용히 재생성하지 않도록 삭제 기록을 유지한다.

특수 시스템 탭인 분류대기와 가져오기 오류는 여행 삭제 대상이 아니다. 기존 권위·종결 자료는 보존한다. 표시 이름 변경과 수동 보관·복원은 14절을 따른다.

검증: A의 수입 300000원·지출 100000원을 빈 B로 옮기고 A를 삭제하면 B의 수입·지출은 각각 300000원·100000원이며 전체 합계와 원천 사건 수는 그대로다. 같은 요청 재시도는 추가 이동 이력을 만들지 않는다. 미리보기 이후 A에 행이 추가되면 삭제 전체를 거부한다. 삭제 이후 예약 동기화·지연 업로드가 A를 재생성하거나 그 탭에 저장하지 않아야 한다.

## 9. 해당 행의 직전 수정 되돌리기

상태: 사용자 확정. owner가 행의 마지막 일반 편집으로 바뀐 필드를 직전 값으로 복원한다. 일반 편집에는 여행 이동, 항목·내용·메모 변경, 직접 수입·수기 지출의 날짜·금액 변경, 은행 정정이 포함된다.

행 상세 또는 저장 직후 안내에서 `직전 수정 되돌리기`를 제공한다. 이전 값과 되돌린 후 값을 보여 주고 복원한다. 요청에는 현재 revision, 복원 대상 event_id, client_request_id를 넣는다. 같은 필드의 원천 제한은 그대로 적용한다.

- 직전 수정 하나만 대상이다. 버튼을 반복 눌러 변경 이력을 여러 단계 거슬러 올라가는 기능으로 확장하지 않는다. 같은 사건을 이미 되돌렸으면 비활성으로 표시한다.
- 이후 새로운 일반 편집을 저장하면 그 편집이 새 되돌리기 대상이다.
- 다른 편집·분할·원천 연결로 현재 revision이 바뀌면 이전 화면의 복원 요청을 거부한다. 최신 상태를 먼저 확인한다.
- 원본 사건을 삭제하지 않고 `reverts_event_id`를 참조하는 새 변경 사건을 만든다. 당시 값과 수동 고정 상태를 함께 복원한다. 미래 규칙은 그대로다.
- 이전 여행이 삭제됐거나 더는 배정할 수 없으면 복원을 강제로 적용하지 않는다. 사유와 수동으로 새 목적지를 선택할 경로를 제공한다.
- 신규 입금·지출 생성, 탭 삭제, 여러 행의 규칙 적용, 입금 배분 저장은 직전 행 수정 버튼의 대상이 아니다. 이 작업들을 일반 편집으로 위장해 일부만 복원하지 않는다. 배분은 배분 편집에서 수정한다.
- 분할 수입의 날짜·금액 정정은 원천 입금 단위의 변경이다. 한 배분 행에서 원금만 되돌려 배분 합계를 깨뜨리지 않는다. 이전 변경이 배분 조정을 함께 포함했다면 배분 편집에서 원금과 전체 배분안을 함께 정정하도록 안내한다. 배분 행의 고객·여행·종류만 변경한 일반 편집은 해당 배분의 직전 수정으로 처리할 수 있다.

검증: 메모 A→B를 저장 후 되돌리면 A가 되고 이력 두 건이 남는다. 같은 되돌리기 요청 재시도는 이력을 늘리지 않는다. 그 뒤 날짜를 수정하면 날짜 수정만 새 대상으로 잡힌다. 카드 금액은 복원 경로로도 변경할 수 없어야 한다.

## 10. 한 입금을 여러 고객·여행·종류로 배분

상태: 사용자 확정. 기존 미지원·질문 대기 문구를 분할 수입에 한해 대체한다. 기존 지출 분할 정책의 확대 승인은 아니다.

### 10.1 원천과 화면

원천 입금은 하나의 income_event_id와 금액·거래일·근거를 유지한다. 각 배분은 안정된 allocation_id, 원천 입금 ID, 고객, 여행, 입금 종류, 부호 있는 배분액을 가진다. 기존 배분 구조가 있으면 재사용하고 별도 수입 정규화 체계를 만들지 않는다.

여기서 원천 보존은 은행 자료와 원래 입력·변경 이력을 보존한다는 뜻이다. 직접 입력 수입의 현재 날짜·금액을 편집할 수 있다는 기존 권한은 유지한다. 은행 연결 이후에는 별도 정정 기록을 사용한다. 어느 경로든 분할된 입금의 금액 변경은 아래 전체 배분안의 합계 조건을 함께 충족해야 한다.

- 분할하지 않은 입금은 기존처럼 한 행이다.
- 분할하면 각 여행에는 그 여행에 속한 배분액만 일반 수입 행으로 표시한다. 원금 전체 행을 동시에 합계에 넣지 않는다.
- 같은 여행·고객이라도 예약금과 잔금으로 나눴으면 각 배분을 별도 행으로 표시한다. 고객별 요약은 해당 배분만 합산한다.
- 거래일과 근거는 원천을 따른다. 기본 표의 7열을 늘리지 않고 행 상세에서 `한 입금에서 배분된 내역`과 원래 입금·배분 구성을 확인한다.
- 직원은 담당 여행의 배분·고객·금액만 볼 수 있다. 같은 입금에서 다른 여행으로 배분된 고객·금액을 원천 연결을 통해 노출하지 않는다. 원천 증빙이 다른 여행 정보를 포함하면 기존 증빙 분리 계약을 적용한다.

### 10.2 배분 편집

owner가 수입 행의 `입금 나누기` 또는 상세의 `배분 편집`을 연다. 위에는 원래 입금액과 현재 장부 반영액, 아래에는 고객·여행·예약금/잔금/추가금·금액 입력 행을 둔다. 분할은 사용자가 직접 결정하며 AI가 금액을 나누지 않는다.

화면은 `배분한 금액`과 `남은 금액`을 항상 보여 준다. 원 단위 정수로 계산하고 초과 배분은 저장을 거부한다. 양수 입금은 양수 배분, 별도 음수 환불은 음수 배분을 사용하며 양수·음수 배분을 섞어 차액을 숨기지 않는다. 0원 배분 행은 새로 만들지 않는다.

부분 배분의 구현 기준: 남은 금액을 같은 원천의 미배정 잔액으로 보존하고 분류대기 수입에 표시한다. 원래 입금을 새 사건으로 복사하지 않는다. 모든 활성 배분액과 미배정 잔액의 합계는 현재 장부 반영액과 정확히 같아야 한다. 원천 입금액과 정정된 반영액은 별도 보존한다.

요청은 원천 입금 ID·현재 revision·전체 배분안·client_request_id를 받는다. 전체 배분 교체와 이력·영향 여행 합계를 한 트랜잭션으로 저장한다. 기존 배분을 수정할 때 allocation_id를 유지하고, 제거한 배분은 현재 합계에서 제외하되 이력은 남긴다. 저장 중 두 화면이 충돌하면 한 요청만 성공해야 한다.

은행 원천을 재업로드해도 분할 결과는 유지한다. 직접 입력 수입에 은행 원천을 연결해도 원금과 배분을 두 번 만들지 않는다. 분할 후 원금 정정으로 합계가 달라지면 금액을 임의 비례 조정하지 않는다. 새 반영액과 배분안을 함께 제시해 사용자가 조정한 뒤 원자적으로 저장한다. 날짜만 정정할 경우 각 배분의 표시 거래일을 함께 갱신하고 여행 배정은 유지한다.

### 10.3 합성 기대값과 출력

원천 입금 P1은 500000원이다. 사용자가 A 여행의 U1 예약금 300000원과 B 여행의 U2 잔금 200000원으로 배분한다.

- 원천 입금 사건 수: 1건.
- 현재 배분 행 수: 2행. 미배정 잔액: 0원.
- A 수입과 U1 합계: 300000원. B 수입과 U2 합계: 200000원.
- A·B를 함께 출력하면 각 시트에 배분액만 표시하며 합계는 500000원이다. 어느 시트에도 원금 500000원을 별도 합계 행으로 더하지 않는다.
- A만 출력하면 300000원만 포함한다. B의 금액을 미선택 시트나 추가 안내 시트에 넣지 않는다.
- A에 300000원만 배분하고 저장하면 분류대기 잔액은 200000원이다. 총 입금이 800000원으로 늘어나서는 안 된다.
- A 300000원과 B 250000원은 초과 배분으로 거부한다.
- 은행 원천이 500000원인 상태에서 장부 반영액을 450000원으로 정정하려면 배분안도 함께 조정한다. 원천은 500000원을 유지한다.

| D-WEB-REVERT-001 | 해당 행 직전 수정 되돌리기 | 제품 명세·Phase 2의 되돌리기 미정 | 행 복원 API·revision·원천 제한·은행 정정 |
| D-WEB-INCOME-SPLIT-001 | 사용자가 금액을 나누어 고객·여행·종류에 배분 | 구현 계약의 분할 미지원, 제품·상세 명세의 사건 1건=표 1행을 분할 사건에 한해 보완 | Phase 4 수입·Phase 5 출력·Phase 7 권한 |
| D-WEB-HEADER-METADATA-001 | 여행별 작성일 저장·최초 오늘 날짜, 소유자 이름 기본·여행별 변경 허용 | 이 문서의 작성일·담당자 미정을 확정 | Phase 2 장부 정보 편집·Phase 5 화면과 출력 일치 |

근거는 이 세션에서 받은 삭제·되돌리기·수입 분할 답변과 뒤이은 작성일·담당자 답변이다. 네 결정은 결정 등록부에 통합했다. 이 절에는 영향 범위를 보존하며 기존 문서의 과거 미정 문구 때문에 동일 질문을 다시 하지 않는다. 구현자의 진행표·구현 기록은 이 설계 세션에서 덮어쓰지 않았다.

구현자는 기존 Phase 4·5 결과가 새 배분 계약을 충족하는지 별도 확인한다. 이전의 합성 테스트 통과 수로 새 분할·복원·삭제 기능의 검증을 대신하지 않는다. 필요한 추가 경계 사례만 검사하며 모든 파이프라인을 반복 실행하지 않는다.

## 12. 여행별 작성일과 담당자

상태: 사용자 확정 정책과 구현 세부 기준. 작성일은 여행별로 저장·수정하며 최초에는 오늘 날짜를 사용한다. 담당자는 소유자 이름을 기본으로 사용하고 여행별로 변경한다.

### 12.1 기본값과 표시

- 새 장부를 만들 때 `prepared_on`에 앱 업무 시간대인 `Asia/Seoul`의 오늘 날짜를 한 번 저장한다. 날짜 전용 값으로 저장하며 다른 기기의 시간대나 재접속 때문에 날짜가 바뀌지 않는다.
- `prepared_by_name`에는 소유자 설정의 이름을 복사해 저장한다. 소유자 이름이 아직 없으면 최초 설정에서 입력받는다. 템플릿 예시 이름·로그인 이메일·모델 이름을 실제 이름으로 추측하지 않는다.
- 두 값은 여행 제목 아래 간단한 작성 정보로 보여 준다. owner는 장부 정보 편집에서 수정하고 한 번 저장한다. 수입·지출 표에 새 열이나 별도 관리 화면을 추가할 필요는 없다.
- 각 여행은 자체 저장값을 가진다. 소유자 기본 이름을 나중에 바꿔도 이미 만든 여행의 담당자를 일괄 변경하지 않는다.
- 기존 장부 이관에서는 유효한 작성일·담당자 값을 보존한다. 기존 값이 충돌하면 기존 차이 선택 절차를 따른다. 값이 없을 때 기본값을 넣은 사실을 이관 미리보기에 표시하며, 원래 자료에서 확인된 값처럼 기록하지 않는다.

### 12.2 저장·권한·출력

저장 요청은 tab_id, expected_revision, prepared_on, prepared_by_name, client_request_id를 사용한다. 기존 장부 메타데이터 저장 경로가 있으면 재사용한다. 유효한 날짜와 공백만으로 구성되지 않은 이름을 검증하고, 변경값·이력·요청 결과를 같은 저장 작업으로 처리한다. 충돌 시 현재값을 보여 주며 다른 변경을 조용히 덮어쓰지 않는다.

담당자 이름은 작성 정보이며 접근 권한의 근거가 아니다. 예약 시스템의 가이드 배정과 로그인 연결은 별도로 유지한다. 직원은 접근 가능한 여행의 작성 정보를 조회할 수 있지만 수정할 수 없다.

화면과 xlsx는 같은 저장 버전의 작성 정보로 만든다. 작성일은 템플릿의 작성일자 값 위치에, 담당자는 기존 담당자 위치에 넣는다. 출력일·내보내기 실행자·파일 생성 시각으로 대체하지 않는다. 여러 여행을 출력하면 각 시트에 해당 여행의 값을 사용한다. 기존 템플릿의 표시 형식과 병합은 보존하고 과거 출력 파일은 바꾸지 않는다.

장부 정보 저장은 여행 일정·거래일·분류 규칙·수입·지출 합계를 바꾸지 않는다. AI 호출과 전체 파이프라인 재실행도 필요하지 않다. 9절의 직전 행 수정 되돌리기는 거래 행 대상이므로 장부 제목 정보를 수정했다고 그 행의 되돌리기 대상을 교체하지 않는다.

### 12.3 합성 기대값

합성 소유자 이름이 `테스트 소유자`이고 서울 기준 2026-09-24에 A 장부를 만들면 작성일은 2026-09-24다. 다음 날 열거나 출력해도 저장값은 그대로다. A의 작성일을 2026-09-23, 담당자를 `테스트 담당자`로 바꾸면 A 화면과 A 시트에만 그 값이 반영된다. B 장부의 작성 정보·가이드 조회 권한·양쪽 여행 합계는 바뀌지 않아야 한다. 같은 저장 요청의 재시도는 이력을 추가하지 않는다.

## 13. 분할·이동·삭제·정정이 만나는 동작

상태: 확정된 기능을 함께 구현하기 위한 기술 계약이다. 추가 업무 기능이나 새로운 사용자 승인 절차가 아니다. 대상: 수정 B·D와 Phase 2·4·5·7의 해당 경로. UI에 별도 관리 화면을 늘리지 않고 기존 행 상세·배분 편집·탭 삭제 화면에서 처리한다.

### 13.1 화면 행과 입금 전체를 구분

분할 후 보이는 행의 금액은 해당 배분액이다. 원천 입금액과 현재 입금 전체 반영액은 owner의 배분 편집에서 확인한다. 같은 입금에 속한다고 다른 여행의 행을 함께 바꾸지 않는다.

| 사용자 동작 | 변경 대상 | 유지하는 값 |
|---|---|---|
| 배분 행의 고객·여행·입금 종류 수정 | 선택한 allocation_id의 해당 필드 | 원금·해당 배분액·나머지 배분 |
| 배분액 변경 | 입금 전체의 배분 편집에서 배분안 저장 | 원천 금액·원천 사건 ID |
| 직접 입력 입금의 전체 금액 수정 | 입금 전체 현재값과 필요한 배분안 | 최초 입력·이력·원천 사건 ID |
| 은행 입금의 전체 금액 정정 | 별도 정정 사건과 필요한 배분안 | 은행 원천 날짜·금액·근거 |
| 입금 날짜 변경·정정 | 같은 입금의 모든 배분 표시 날짜 | 각 배분의 여행·고객·금액 |
| 여행 탭 삭제 후 이동 | 삭제할 탭에 있는 배분 행만 이동 | 다른 탭의 배분·전체 원금 |
| 배분 행의 직전 일반 수정 복원 | 해당 행의 직전 변경 필드와 수동 고정 상태 | 다른 배분·미래 규칙 |

배분 행의 금액 칸에서 편집을 시작하면 `배분 편집`으로 연결한다. 여기서 `원래 입금액`, `현재 장부 반영액`, `배분한 금액`, `남은 금액`을 구분해 보여 준다. 배분액을 원금 수정으로 처리하는 공용 amount 필드를 사용하지 않는다. 원금을 바꿀 때는 기존 원천별 편집·정정 경로로 연결한다.

날짜는 모든 배분이 공유하므로 owner가 해당 행에서 날짜 변경을 시작하면 같은 입금의 배분 전체에 반영된다는 안내를 저장 영역에 표시한다. 기존 저장 버튼 한 번으로 확정하며 추가 확인창을 반복하지 않는다. 여러 여행에 걸친 날짜 정정을 한 행의 변경처럼 설명하지 않는다.

### 13.2 안정 식별자와 충돌 검사

- 원천 입금 ID, 배분 ID, 화면 행 ID의 연결을 유지한다. 화면 정렬·여행 이동·탭 삭제 후 이동으로 새 ID를 만들지 않는다.
- 분할 전 단일 행을 여러 배분 행으로 바꿀 때 기존 단일 행의 참조는 원천 입금 상세로 연결한다. 임의의 첫 배분을 원래 전체 입금인 것처럼 대신 보여 주지 않는다. 현재 행 집합에 원금 행을 계속 포함하지 않는다.
- 수입 관련 쓰기에는 원천 입금의 현재 revision을 결속한다. 선택 배분 편집에는 행 revision도 검사한다. 기존 revision 구조에 대응할 수 있으면 중복 버전 저장소를 만들지 않는다.
- 배분 저장·원금 정정·원천 연결·배분 행 이동은 같은 입금의 버전을 갱신한다. 다른 배분 변경을 모르는 낡은 전체 배분안이 새 결과를 덮어쓰지 못하게 한다. 충돌은 해당 입금 범위이며 다른 입금이나 여행 전체의 작업을 잠그지 않는다.
- 탭 삭제 미리보기에는 대상 행과 그 원천 입금의 버전을 묶는다. 미리보기 후 다른 탭에서 같은 입금의 배분을 수정했다면 재미리보기가 필요하다. 무관한 입금 수정은 삭제 요청을 실패시키지 않는다.
- 동일 요청 재시도는 저장된 요청 결과를 먼저 확인한다. 자기 첫 요청 때문에 revision이 바뀐 경우를 충돌로 돌려주지 않는다. 같은 요청 ID·다른 내용만 요청 ID 충돌이다.
- 성공 응답에는 변경된 행, 더는 표시하지 않는 행 ID, 영향 탭, 새 버전 또는 같은 버전으로 재조회할 수 있는 정보를 준다. 화면은 원금 행을 제거하고 배분 행을 넣는 변화를 한 번에 반영한다. 중간에 둘 다 합산한 합계를 보여 주지 않는다.

### 13.3 미배정 배분과 아직 나누지 않은 잔액

둘은 같은 분류대기 구역에 보일 수 있지만 업무 의미가 다르다.

- `미배정 배분`: 배분액·고객·입금 종류는 정했지만 여행이 없는 행이다. 탭 삭제 시 분류대기로 보낸 배분도 여기에 속한다. allocation_id와 정해 둔 고객·종류를 유지한다.
- `미배분 잔액`: 사용자가 아직 고객·여행·종류별로 나누지 않은 나머지 금액이다. 해당 원천 입금에 하나의 잔액만 계산하며 독립 입금 사건을 만들지 않는다. 금액은 원금에서 활성 배분 합계를 뺀 값이다.
- 미배정 배분은 이미 활성 배분 합계에 포함된다. 이를 미배분 잔액에도 더하지 않는다. 고객·종류가 같다는 이유로 기존 배분과 자동 병합하지 않는다.
- 잔액의 고객·종류가 미정이면 공란으로 보이고 예약금으로 추정하지 않는다. 분류대기 합계에는 확인된 잔액 금액을 포함하되 여행별 수입에는 포함하지 않는다. 종류별 금액 열의 합계 규칙은 종류가 정해진 일반 수입 행에 적용한다.
- 잔액에서 `배분 편집`을 열어 목적지와 고객·종류·금액을 정한다. 드롭다운만으로 필요한 정보가 부족하면 해당 편집 영역을 열며 임의 기본값으로 조용히 확정하지 않는다.
- 이미 배분한 행을 배분안에서 제거하면 그 금액은 잔액으로 돌아간다. 원금 감소·실제 환불·원천 삭제로 처리하지 않는다. 잔액이 0이면 잔액 행은 숨긴다.

금액 조건은 `전체 활성 배분액 합계 + 미배분 잔액 = 현재 입금 반영액`이다. 활성 배분 합계에는 여행 배정 여부와 관계없이 모두 포함한다. 음수 환불도 원래 부호를 유지한 같은 식을 적용하며 초과 배분은 절댓값 크기로 판정한다. 실제 입금이나 환불의 부호를 바꾸는 기능으로 사용하지 않는다.

### 13.4 교차 동작의 합성 수용 사례

각 사례는 별도 초기 상태에서 시작한다. 기본 상태는 P1 500000원, L1=A/U1/예약금 300000원, L2=B/U2/잔금 200000원, 잔액 0원이다. 모든 성공 사례에서 원천 입금은 1건이다.

| 사례 | 조작 | 기대 결과 |
|---|---|---|
| X01 | L1을 A에서 B로 이동 | A 0원, B 500000원. B에는 2개 배분 행, ID 유지 |
| X02 | A 탭을 삭제하고 내역을 분류대기로 이동 | L1은 미배정 300000원, L2는 B 200000원. 미배분 잔액은 0원 |
| X03 | 배분 편집에서 L1을 제거 | B 200000원, 미배분 잔액 300000원. L1 과거 이력 보존 |
| X04 | A만 출력 | L1 300000원만 포함. 원금·B 금액을 추가하지 않음 |
| X05 | L1 이동 전 연 배분 편집 화면에서 오래된 전체안을 저장 | 충돌. L1의 새 목적지를 되돌리지 않음 |
| X06 | L1 이동을 저장한 뒤 같은 요청 재전송 | 최초 성공 결과 재사용, 행·이력·원천 사건 수 추가 없음 |
| X07 | L1 이동 직후 직전 수정 되돌리기 | L1은 A로 복원, L2 유지. 단 이전 A가 삭제됐다면 복원 거부 |
| X08 | 은행 원금 500000원을 장부 450000원으로 정정하고 L1 250000원·L2 200000원 제출 | 원천 500000원 유지, 화면·출력 합계 450000원, 잔액 0원 |
| X09 | X08의 정정액만 내고 기존 배분 500000원 유지 | 전체 저장 거부. 정정만 먼저 반영하지 않음 |
| X10 | A 담당 직원이 L1 상세·증빙 조회 | A의 배분 정보만 제공. B 고객·금액과 전체 배분 구성은 미노출 |

이 표는 기존 검사에 더할 경계 사례 목록이다. 같은 사례를 API·DB·여러 모델에서 반복 승인받는 절차가 아니다. 저장·합계·권한별 적절한 검사 계층에서 한 번 확인하고, 사용자가 직접 조작하는 대표 흐름만 브라우저에서 확인한다.

### 13.5 되돌리기 가능 여부의 서버 응답

행 상세의 allowed_actions에 직전 수정 복원 가능 여부를 포함한다. 가능하면 대상 변경 사건과 영향 범위를, 불가능하면 짧은 이유를 제공한다. 화면이 이력 목록에서 임의로 복원 사건을 선택하지 않는다.

대표 불가 사유는 `직전 변경은 배분 전체 수정입니다`, `이미 되돌린 수정입니다`, `이전 여행이 삭제됐습니다`, `최신 내역을 다시 확인해 주세요`다. 사용자는 상세 이력을 읽어 기술적 조건을 추측할 필요가 없어야 한다. 버튼을 숨기거나 비활성화해도 API에서 동일 조건을 다시 검사한다.

탭 삭제·원천 연결·입금 전체 배분처럼 일반 행 수정이 아닌 변경 이후에는 이전 일반 편집을 건너찾아 복원하지 않는다. 복원 성공 후 행·합계를 갱신하되 AI 대화를 자동 시작하지 않는다. 기존 규칙을 비활성화하거나 전체 배분을 복구하는 기능과 혼동하지 않는다.

## 14. 표시 이름 자유 편집과 수동 보관

상태: 사용자 확정. 표시 이름 전체를 자유롭게 수정할 수 있으며, 사용자가 보관을 누르면 보관 목록으로 옮기고 필요하면 복원한다. 여행 종료일만으로 자동 보관하지 않는다. 아래 동작은 해당 정책의 구현 기준이다.

### 14.1 이름과 여행 식별

- 탭 추가 시 날짜·행선지 형식의 초기 표시 이름을 제안하되 저장 후 이름 전체를 편집할 수 있다. 최초 추가 때도 표시 이름을 직접 고칠 수 있다. 날짜·행선지·권위 일정 필드는 이름과 별도로 관리한다.
- 이름 변경은 tab_id·trip_id·예약 시스템 여행 ID·일정 권위·행 배정·작성일·담당자를 바꾸지 않는다. 이름에서 날짜나 행선지를 다시 파싱해 업무 필드를 갱신하지 않는다.
- 이름은 일반 텍스트로 저장·표시하며 공백만 있는 이름은 거부한다. Excel 시트의 길이·문자 제약 때문에 웹 이름을 잘라 저장하지 않는다. 화면의 긴 이름은 줄바꿈 또는 상세 표시로 확인할 수 있게 한다.
- 같은 이름을 가진 다른 여행을 자동 병합하지 않는다. 선택 목록에서 동명이 있는 경우 실제 일정·행선지 보조 정보를 함께 표시한다. 실제 일정이 없으면 날짜를 추측하지 않고 이름 외 안정된 구분 정보를 상세에서 제공한다.
- 검색은 표시 이름과 보존된 여행 정보로 찾는다. 예약 동기화가 사용자가 바꾼 표시 이름을 덮어쓰지 않도록 수동 변경 여부를 보존한다.
- 새 출력의 제목은 저장된 표시 이름을 사용한다. 시트 이름만 Excel 제약에 맞춰 변환하며 충돌은 결정론적인 접미사로 구분한다. 시트 이름과 tab_id의 대응은 기존 출력 기록에 남기고 안내용 시트를 추가하지 않는다. 과거 파일은 그대로다.

### 14.2 보관·복원 화면과 업무 동작

owner의 여행 관리에 `보관`을 둔다. 보관 후 기본 활성 목록에서는 숨기고 같은 목록의 `보관된 여행` 필터에서 조회한다. 보관 목록에는 `다시 꺼내기`를 제공한다. 보관·복원은 현재 화면에서 한 번 저장하고 결과를 안내하며 삭제용 내역 이동 미리보기를 요구하지 않는다.

보관은 목록 정리 기능이며 장부 마감·편집 금지·권한 회수·분류 제외를 뜻하지 않는다.

- 보관된 여행도 owner가 열면 기존 권한으로 조회·편집·출력할 수 있다. 직원은 담당 권한이 유효하면 보관 목록과 직접 링크로 조회할 수 있다. 다른 사람의 보관 여행 목록이나 건수는 노출하지 않는다.
- 보관된 여행에 이미 연결된 규칙·업로드 분류는 계속 적용된다. 보관을 이유로 내역을 분류대기로 보내거나 탭을 자동 복원하지 않는다. 가져오기 결과에서 실제 목적지와 해당 보관 여행을 여는 링크를 제공한다.
- 이미 선택한 여행을 보관하더라도 현재 상세 화면을 오류나 빈 장부로 바꾸지 않는다. 보관 안내와 목록으로 가는 경로를 제공한다. 새로 기본 목록을 열 때는 활성 여행만 보여 준다.
- 전체 업무 합계에 보관 여행을 포함한다. 활성 목록만 조회하는 합계가 필요하면 `활성 여행 합계`라고 범위를 표시한다. 특정 여행을 열었을 때 수입·지출 합계는 보관 전후 같다.
- 출력 선택창에서 보관 목록으로 전환해 여행을 선택할 수 있다. 선택한 보관 여행은 다른 여행과 같은 파일의 개별 시트로 출력한다. 목록 필터 변경으로 사용자가 이미 고른 여행을 조용히 빼거나 추가하지 않는다.
- 삭제한 여행을 보관 복원 API로 되살리지 않는다. 일반 보관과 논리 삭제는 서로 다른 상태다. 삭제 후 복원은 이번 수동 보관 복원 결정의 범위가 아니다.

### 14.3 저장과 검증

기존 장부 메타데이터 저장 경로를 재사용한다. 요청은 tab_id·expected_revision·client_request_id와 변경 필드만 포함한다. owner 권한·존재·삭제 상태를 서버에서 검사하고 이름·보관 상태·이력·요청 결과를 함께 저장한다. 실제 변경이 없는 요청은 revision과 이력을 늘리지 않는다. 보관·복원을 거래 행의 직전 수정 되돌리기 목록에 넣지 않는다.

합성 검증: A 이름을 `봄 여행 / 정산`으로 바꿔도 A의 300000원 배분·trip_id·일정은 그대로다. 새 xlsx 제목은 그 이름이며 시트 이름은 안전하게 변환된다. A를 보관하면 활성 목록에서 빠지고 보관 목록·담당 직원의 허용된 직접 링크에서는 보인다. A 대상 신규 내역은 A에 들어가되 A는 보관 상태를 유지한다. 복원하면 같은 tab_id로 활성 목록에 돌아온다. 같은 요청 재시도는 이력을 늘리지 않으며 viewer의 변경 요청과 삭제 탭 복원 요청은 거부한다.

## 15. 로그인·담당 배정·증빙 접근의 공통 계약

상태: Google 로그인, 직원 신청 후 소유자 승인, 직원 증빙 미리보기만 제공으로 사용자 확정됐다. 공통 권한 계약은 이 절, 로그인·신청의 상세 구현은 16절을 따른다. 실제 인증 공급자 설치·계정 생성·외부 연결은 수행하지 않았다. 대상: Phase 7이며 현재 Phase 1~5 수정의 선행 조건이 아니다.

### 15.1 로그인과 담당 권한은 별도로 확인

로그인 성공은 누구인지 확인한 상태이며 장부 조회 허용을 뜻하지 않는다. 최초 로그인 계정을 owner로 자동 승격하지 않는다. 소유자 계정은 배포 설정 또는 명시된 최초 설정으로 한 명을 지정하고, 이름·이메일 문자열이나 첫 접속 순서만으로 소유권을 부여하지 않는다.

웹앱의 안정된 사용자 ID와 예약 시스템의 담당자 ID를 연결한다. 인증 공급자의 안정된 계정 식별자를 사용자 ID에 결속하고 표시 이름·닉네임 변경으로 새 계정이나 권한을 만들지 않는다. 개인 계정 연결과 여행 담당 배정의 두 관계가 모두 유효해야 해당 여행을 조회할 수 있다.

| 상태 | 사용자 화면 | 허용 범위 |
|---|---|---|
| 로그인 전 | 선택된 로그인 수단 표시 | 합성 포트폴리오 외 운영 자료 없음 |
| 로그인 성공·담당자 연결 없음 | 담당자 연결 준비 안내 | 여행 목록·고객·합계 없음 |
| 담당자 연결됨·배정 여행 없음 | 담당 여행이 아직 없다는 안내 | 다른 여행이나 전체 직원 목록 없음 |
| 연결·배정 모두 유효 | 담당 여행 목록 | 허용된 여행의 표·합계·증빙 |
| 담당 해제 | 해당 여행 접근 종료 안내 | 나머지 유효 담당 여행은 유지 |
| 계정 비활성화 또는 연결 해제 | 재연결 또는 관리자 문의 안내 | 운영 여행 조회 차단 |
| 배정 확인 만료·예약 서버 장애 | 담당 권한 확인 대기 안내 | 만료된 허용 결과로 새 자료를 보내지 않음 |

owner의 장부 작업은 예약 서버 장애와 독립적으로 유지한다. 직원 계정 연결 화면을 통해 원천 여행 담당자를 생성하거나 예약 DB에 배정을 쓰지 않는다. 직원의 연결 신청만으로 권한을 부여하지 않고 소유자 승인과 유효 배정을 확인한다.

### 15.2 예약 연동의 적용 경계

2026-09-24 로컬 코드 읽기 확인: 예약 저장소에 `leader_sessions` 구조가 있으며 `leaderLink.ts`에는 여행별 서명 링크도 있다. `leaderTours.ts`의 여행 목록은 닉네임·예약 담당·과거 제목 접두어를 함께 사용하고 완료 여행을 제외하는 경로가 있다. 이 관찰만으로 기존 개인 로그인 재사용이 가능하거나 불가능하다고 확정하지 않는다. 실제 개인 세션 검증·해제·서버 간 연결 계약을 확인해야 한다. 여행 링크 보유를 개인 신원으로 대체하거나 그 목록을 그대로 장부 권한으로 사용하지 않는다.

예약 연동은 기존 구현 계약의 담당자 ID·여행 ID·배정 ID·상태·revision·관찰 시각을 소비한다. 동일 revision 재전송은 효과를 늘리지 않고, 더 오래된 배정으로 해제된 권한을 복구하지 않는다.

- 완전 스냅샷의 범위와 완료 표지가 확인된 경우에만 누락을 해제로 해석한다. 페이지 일부·통신 실패·완료 여행 제외 목록은 해제의 근거가 아니다.
- 스냅샷 여러 페이지를 받는 동안 기존 권한을 부분 갱신하지 않는다. 같은 원천 버전의 수집이 끝난 뒤 해당 범위를 한 번에 갱신한다. 중간 실패는 이전 확인 결과를 유효기간 안에서만 유지한다.
- 증분 방식에서는 명시적인 배정 해제·계정 비활성화 사건을 반영한다. 계정이 비활성화됐으면 배정 행이 남아 있어도 조회를 차단한다.
- 같은 여행에 담당자가 여러 명인 경우 명시 배정된 각 계정의 조회를 허용한다. 대표자 한 명을 임의로 고르지 않는다. 동명이인·닉네임 중복은 ID 대응을 확인하기 전까지 연결 대기로 남긴다.
- 장부에서 행을 다른 여행으로 이동하면 새 여행의 권한을 즉시 적용한다. 예약 동기화 주기를 기다리며 이전 여행 담당자에게 그 행을 계속 제공하지 않는다.

권한 캐시를 쓰면 `last_verified_at`과 `valid_until`을 기록한다. 요청마다 유효기간과 로컬 해제 상태를 검사한다. 유효기간은 구현자가 무제한으로 두지 못하며 Phase 7 실제 연결 보고에 설정값·조회 비용·최대 해제 지연을 함께 제시한다. 설정되지 않은 유효기간을 임의의 무기한 허용으로 처리하지 않는다. 캐시 성능을 위해 원천 전체 배정을 매 행 요청마다 새로 동기화할 필요는 없다.

### 15.3 브라우저 상태와 서버 응답

모든 조회·저장·출력 요청은 현재 세션과 역할을 서버에서 확인한다. owner 응답에서 필드를 숨기는 방식 대신 viewer에게 필요한 필드만 반환한다. 401은 재로그인, 권한 없는 여행·행·증빙의 조회는 존재 여부를 드러내지 않는 404 응답을 사용한다. 오류 메시지에 다른 고객·여행 이름을 넣지 않는다.

로그아웃·계정 전환·권한 해제 응답을 받으면 브라우저의 해당 운영 자료 캐시와 선택 행을 비운다. 해제 이후 도착한 이전 요청의 응답을 다시 렌더링하지 않도록 계정·권한 세대와 요청을 결속한다. 서버도 권한 변경 후 새로 읽은 자료를 낡은 허용 결과로 보내지 않는다.

새 요청 차단과 이미 전달된 화면 자료의 회수는 다르다. 화면 캡처·사용자가 이미 저장한 내용까지 기술적으로 회수한다고 안내하지 않는다. 서비스 워커·공용 CDN에 운영 장부나 증빙을 공개 캐시하지 않는다. 공개 포트폴리오는 별도 합성 데이터와 응답 경로를 사용한다.

### 15.4 증빙 미리보기의 범위

증빙 접근은 현재 행→현재 여행→유효한 담당 권한→해당 증빙의 제공 범위를 순서대로 확인한다. evidence_id를 안다는 이유만으로 원본 파일을 제공하지 않는다. 한 증빙을 여러 행이 참조하더라도 직원 응답에는 허용된 여행의 참조만 포함한다.

- A 전용 자료는 A 담당자에게 미리보기로 제공한다. A·B 혼합 자료는 A 전용으로 분리한 자료가 준비돼야 한다. 분리 자료에는 원본 참조·원본 해시·분리 버전·허용 여행을 결속한다.
- 원본이나 분리 기준이 바뀌면 이전 파생 자료를 최신 증빙처럼 제공하지 않는다. 분리 자료가 준비되지 않아도 장부 행과 금액 조회는 계속 가능하며 증빙 영역에만 준비 필요를 표시한다.
- 원본 파일 링크를 그대로 iframe에 넣거나 외부 공개 URL로 돌려보내지 않는다. 인증된 앱 경로에서 안전한 미리보기 형식을 제공한다. 지원하지 않는 형식은 원본 공개로 우회하지 않고 미리보기 미지원으로 알린다.
- HTML·스크립트가 포함된 업로드를 앱과 같은 실행 권한으로 렌더링하지 않는다. 미리보기 생성 실패를 장부 저장 실패로 확대하지 않는다.
- 직원에게 별도 증빙 다운로드 버튼·다운로드 API 권한을 제공하지 않는다. 브라우저로 전달한 이미지·내용의 저장을 완전히 막을 수 있다고 약속하지 않는다. 실제 제공 기능과 한계를 구분한다.

### 15.5 최소 권한 수용 사례

합성 계정은 owner O, A 담당 V1, B 담당 V2, 미연결 V3를 사용한다. 실제 개인정보·계정·인증 키는 테스트에 넣지 않는다.

| 사례 | 기대 결과 |
|---|---|
| V3가 최초 로그인 | 다른 여행·고객·직원 목록 없이 연결 준비 안내 |
| V1이 B의 행 ID·증빙 ID를 직접 요청 | 404, 원문·다른 여행 이름·내부 메모 없음 |
| A 종료·보관, V1 배정 유지 | A 조회 유지 |
| V1 담당 해제 수신 후 행·검색·증빙 요청 | 모두 차단, 과거 응답 캐시로 복원하지 않음 |
| 해제 뒤 더 오래된 활성 배정 도착 | 권한 복구 없음 |
| 스냅샷 두 페이지 중 두 번째 실패 | 누락 여행을 해제로 단정하지 않음, 만료되면 직원 조회 대기 |
| 예약 서버 장애 | owner 입력·업로드·출력은 유지, 만료된 직원 권한은 갱신 대기 |
| A·B 혼합 증빙을 V1이 요청 | A 분리 자료만 또는 준비 필요. 혼합 원본 없음 |
| owner 로그아웃 후 V1 로그인 | owner의 메모·이력·대화·출력 작업 캐시 미노출 |

직원의 증빙 다운로드 직접 요청은 거부하고 허용된 미리보기 경로만 제공하는 사례를 포함한다. 이 절의 합성 권한 검증은 실제 로그인·예약 운영 연동 검증을 대신하지 않는다.

## 16. Google 로그인과 직원 연결 신청

상태: 사용자 확정 정책의 구현 기준. Google 로그인은 신원 확인이며 예약 시스템 담당 배정과 앱 소유자 승인까지 대체하지 않는다. 이 절에서 정의한 상태와 필드는 논리 계약이며 새 인증 프레임워크·별도 승인 서비스를 만들라는 지시가 아니다.

### 16.1 인증 경계

검증된 OpenID Connect 라이브러리를 사용하고 서버에서 ID 토큰의 서명·발급자·대상 클라이언트·만료를 검증한다. 서버 로그인 흐름의 state와 사용한 nonce를 확인한다. 계정 키는 이메일이 아닌 Google의 안정된 sub를 기준으로 한다. 기술 근거: [Google OpenID Connect 공식 문서](https://developers.google.com/identity/openid-connect/openid-connect), 2026-09-24 확인.

앱 설계 기준:

- 로그인에 필요한 openid·email 범위부터 사용한다. 이름 표시가 필요하면 profile을 추가하되 Gmail·Drive·Sheets 접근 권한을 로그인에 함께 요구하지 않는다.
- Google 로그인 버튼 옆에 계정 전환 경로를 둔다. 신청 전 현재 로그인한 이메일을 보여 주어 개인·업무 계정을 혼동하지 않게 한다. 클라이언트가 보낸 이메일·역할값은 신원 검증 근거가 아니다.
- Google 토큰을 장부 API의 영구 비밀번호처럼 저장하지 않는다. 서버가 검증 후 앱 세션을 만들고 로그아웃·로컬 비활성화 시 해당 세션의 접근을 종료한다. 비밀값·토큰은 로그나 구현 인계에 남기지 않는다.
- 기존 웹앱의 세션·CSRF 방식을 재사용하되 합성 고정 토큰과 개발용 역할 전환을 운영 인증으로 사용하지 않는다. 앱 세션 쿠키는 운영 HTTPS와 서버 측 검증을 사용한다.
- OAuth 클라이언트·허용된 콜백 주소·소유자 최초 연결은 배포 환경 설정 항목이다. 아직 자격 증명이 없으면 합성 인증 검증과 실제 로그인 미연결을 구분한다. 설치·과금·운영 계정 설정을 문서 작성만으로 실행하지 않는다.

### 16.2 직원의 신청 화면

미연결 직원이 로그인하면 `담당자 연결 신청` 화면을 보여 준다. 현재 Google 이메일은 확인용으로 고정 표시하고, 예약 시스템에서 사용하는 이름·닉네임과 선택적인 설명만 입력받는다. 직원에게 전체 담당자 목록·여행 목록을 검색시키지 않는다. 입력한 이름은 신청 근거이며 자동 권한 키가 아니다.

신청을 보내면 `승인 대기` 상태와 신청 시각을 표시한다. 대기 중에는 장부를 보여 주지 않는다. 같은 계정의 중복 클릭·재전송은 대기 신청을 늘리지 않는다. 대기 신청을 수정하려면 기존 신청을 수정하고 revision을 증가시키며 이력을 남긴다. 철회는 신청 상태만 바꾸고 예약 DB를 수정하지 않는다.

별도 이메일·메신저 발송 기능은 첫 버전에 추가하지 않는다. owner에게 앱의 계정 관리 진입점과 대기 건수를 제공한다. 직원은 로그인 후 신청 상태를 조회할 수 있다. 이후 외부 알림이 필요해지면 별도 범위로 정한다.

### 16.3 소유자의 확인·승인

owner가 신청을 열면 Google 계정·신청 내용·신청 시각을 보고 예약 시스템의 안정된 담당자 ID를 선택한다. 이 관리 화면에서만 필요한 담당자 목록을 조회한다. 같은 이름이 여럿이면 구분 정보를 보여 주고 정확히 한 대상을 고르게 한다. 동일 이름만으로 자동 승인하지 않는다.

승인 저장 시 신청 revision·대상 담당자의 존재와 활성 상태·현재 연결 상태를 다시 확인한다. 연결 생성·신청 승인·이력·요청 결과를 한 번에 저장한다. 승인 자체가 담당 여행을 추가하지는 않으며, 이후 유효한 예약 배정 범위만 보인다.

첫 버전의 중복 연결 처리 기준은 다음과 같다. 동일 Google 계정의 같은 담당자 재승인은 검증된 재사용이다. 다른 담당자와 이미 연결된 계정이나 다른 계정이 이미 사용하는 담당자는 충돌로 표시하며 자동 덮어쓰기하지 않는다. 여러 Google 계정을 한 담당자에 연결하는 기능은 자동 추가하지 않는다. 계정 변경은 owner가 이전 연결을 해제한 뒤 새 신청을 승인하며, 이전 계정에 권한이 남지 않아야 한다.

거절하면 사유를 직원에게 보여 주고 이후 새 신청은 허용한다. 소유자가 비활성화한 계정은 신청 제출만으로 복구하지 않는다. 재활성화는 owner의 명시 작업이며 이전 승인 이력을 삭제하지 않는다.

### 16.4 상태·API 저장 계약

신청 상태는 pending·approved·rejected·withdrawn으로 구분하고, 계정 연결의 active·revoked 및 계정 활성 상태는 별도로 관리한다. 신청이 과거 approved여도 연결이 revoked이면 조회할 수 없다.

| 동작 | 요청의 핵심 값 | 서버 조건과 결과 |
|---|---|---|
| 신청 생성 | 신청 이름·닉네임·설명, client_request_id | 사용자 ID는 로그인 세션에서 결정, 열린 신청은 중복 생성하지 않음 |
| 신청 수정·철회 | application_id, expected_revision, client_request_id | 신청 본인·pending 상태만 허용 |
| 승인 | application_id, expected_revision, reservation_person_id, client_request_id | owner만 가능, 활성 담당자·중복 연결 검사 후 원자적 연결 |
| 거절 | application_id, expected_revision, 사유, client_request_id | owner만 가능, 최신 pending만 변경 |
| 연결 해제 | connection_id, expected_revision, client_request_id | owner만 가능, 해당 계정의 후속 여행 요청 차단 |
| 상태 조회 | 로그인 세션 또는 owner가 선택한 신청 ID | 직원은 자기 신청만, owner는 관리 범위만 |

신청 승인과 직원 철회가 경합하면 최신 revision을 먼저 저장한 한 요청만 성공한다. 서버는 다른 내용의 동일 요청 ID를 거부한다. 계정 연결을 장부 행 수정 이력이나 입금 사건으로 기록하지 않는다. 기존 관리 감사 기록을 재사용한다.

### 16.5 화면과 검증 기준

직원 기본 흐름은 Google 로그인→연결 신청→승인 대기→담당 여행 목록이다. owner는 관리 화면에서 대기 신청 확인→담당자 선택→승인한다. 담당 여행이 없으면 승인 실패로 표시하지 않고 `현재 배정된 여행이 없습니다`를 보여 준다. 거절·철회·연결 해제·계정 비활성화를 같은 오류 메시지로 뭉치지 않는다.

최소 검증은 다음과 같다.

1. 첫 로그인·신청 제출만으로 여행이나 owner 권한이 생기지 않는다.
2. 동일 신청 재전송은 하나이며 승인 재전송도 연결을 하나만 만든다.
3. 동명이인 신청을 자동 승인하지 않고 owner가 선택한 담당자 ID만 연결한다.
4. 승인·철회 경합에서 두 상태가 동시에 성공하지 않는다.
5. 연결 해제 뒤 이미 로그인한 이전 계정의 여행·증빙 요청도 차단한다.
6. 거절 후 새 신청은 가능하되 비활성화 계정은 스스로 권한을 복구하지 못한다.
7. 직원은 자기 신청 상태와 허용 여행 증빙 미리보기만 조회하며 타인 신청·원본 파일·증빙 다운로드·xlsx 경로는 거부한다.
8. Google 로그인 취소·잘못된 토큰·만료된 세션은 로그인 완료로 표시하지 않는다. 실제 공급자 연결 전에는 이 검증이 합성이라는 사실을 기록한다.

## 17. 공급자와 무관한 배포·백업·복구 기준

작성일: 2026-09-25. 상태: 기존 PC 독립 동작·원천 보존 요구를 구현하기 위한 운영 설계다. 무료 선행 시험·유료 전환 별도 승인 정책은 확정됐으며 공급자 후보의 실제 자원 확보·운영 전환은 미완료다. 실제 배포를 수행하지 않았다. 대상: Phase 8~9. 현재 Phase 1~5 수정에 운영 인프라 설치를 추가하지 않는다.

### 17.1 최소 실행 구성

웹앱 서버는 장부 조회·저장, 원천 접수, 가져오기 처리, 규칙의 결정론적 적용, xlsx 생성과 Google 세션 검증을 담당한다. 원천 파일·DB·출력은 서버 재시작이나 앱 배포 후에도 유지되는 저장소에 둔다. 사용자 PC에는 Muse 연결 프로그램만 의존하도록 구성한다.

첫 버전은 한 앱과 한 업무 정본 저장소에서 시작한다. 동시 쓰기 문제를 피하려고 사용자마다 복제 DB를 만들거나 요청마다 SQLite 파일을 내려받아 다시 올리는 방식을 사용하지 않는다. 기존 SQLite를 유지할 경우 영속 디스크와 쓰기 프로세스 운영 조건을 확인한다. 후보 호스팅이 이를 지원하지 않으면 임시 디스크로 억지 배포하지 않고 지원 가능한 실행 환경 또는 DB 어댑터 변경안을 비교한다.

장시간 처리는 내구성 있는 작업 상태를 기록한 한 작업자가 처리하도록 시작한다. 외부 큐·별도 마이크로서비스는 실제 제약이 있을 때만 추가한다. 작업자가 꺼져도 접수된 원천과 처리 커서는 남아야 하며, 복귀 시 같은 작업을 이어가야 한다. PC 종료를 서버 작업자 종료로 처리하지 않는다.

운영과 공개 포트폴리오는 데이터·인증·파일 경로를 분리한다. 포트폴리오의 편집 체험이 있다면 합성 자료에만 적용하고 실제 계정 연결·예약 동기화·유료 또는 개인 API 키 호출은 연결하지 않는다. 공개 화면에서 운영 DB를 읽은 뒤 이름만 가리는 방식은 사용하지 않는다.

### 17.2 보존 대상과 복구 묶음

백업은 DB 파일 하나만 있다는 이유로 완전하다고 판단하지 않는다. 하나의 일관된 복구 시점에 다음 내용을 대응시킨다.

| 대상 | 보존할 내용 | 복구 시 확인 |
|---|---|---|
| 업무 DB | 원천 참조·행·배분·정정·규칙 버전·수동 고정·변경 이력·요청 결과 | 같은 사건과 적용 결정을 재현할 수 있음 |
| 원천 파일 | 업로드 원본 바이트와 digest·저장 위치 참조 | 참조하는 원천이 실제 존재하고 해시가 일치 |
| 작업 상태 | 접수·처리·완료·실패 상태와 커서 | 완료 작업을 새 작업으로 중복 실행하지 않음 |
| 출력 | 불변 파일·기준 스냅샷·양식 버전·출력 기록 | 과거 파일을 새 값으로 덮어쓰지 않음 |
| 사용자 설정 | 계정 연결·소유자 설정·화면 메타데이터·모델 선택 | 업무 설정 보존, 권한은 복구 후 별도 최신 확인 |
| 비밀 설정 | 배포 비밀 저장소와 복구 절차 | DB 백업·로그에 평문 키를 넣지 않음 |

SQLite 실행 중 백업은 일관된 스냅샷을 만드는 백업 방식으로 수행한다. WAL을 사용 중인 DB 본체 파일만 복사해 최신 저장까지 보존됐다고 보고하지 않는다. 운영 원본의 저널 파일을 지워 백업을 통과시키지 않는다. 파일 저장소와 DB의 참조 일관성은 백업 완료 표지를 기록하기 전에 확인한다.

백업 주기·보관 기간·복구 목표 시간은 운영비와 저장소 기능을 비교한 뒤 배포안에 수치로 적는다. 미정 상태에서 무손실 복구나 무중단 운영을 약속하지 않는다. 사용자가 선택할 자료에는 `최대 잃을 수 있는 최근 입력 범위`, `시험 복구에 걸린 시간`, `저장 비용과 보관 기간`을 제시한다. 복구 검증은 별도 시험 DB에서 하며 운영 DB를 덮어쓰지 않는다.

### 17.3 시험 복구와 재개

1. 복구 묶음의 기준 시점과 해시를 확인하고 별도 DB·파일 경로로 복원한다.
2. 사건별 금액·배분·정정·수동 고정·규칙 버전과 업무 의미를 대조한다. 전체 합계만 같다고 통과시키지 않는다.
3. Google 앱 세션과 이전 직원 권한 캐시는 그대로 활성화하지 않는다. 재로그인과 현재 계정 연결·예약 배정 확인을 거친다. 오래된 백업이 담당 해제를 되돌리는 우회로가 되지 않아야 한다.
4. 소유자의 현재 활성 계정 설정과 복구된 연결 기록이 충돌하면 복구 관리 절차로 확인한다. 첫 로그인 사용자를 owner로 바꾸지 않는다.
5. 완료된 가져오기·행 저장 요청을 같은 ID로 재전송해 업무 효과가 늘지 않는지 확인한다. 미완료 작업은 기록된 커서와 원천을 검증한 후 재개한다.
6. AI 대화는 질문·답변·초안·적용 상태를 복구하되 이미 승인·적용한 규칙을 자동 재적용하지 않는다. 이전 공급자 응답이 뒤늦게 도착해도 복구된 현재 revision을 덮어쓰지 않는다.
7. 합성 자료로 한 행 저장·카드 처리·수입 정정·선택 탭 출력을 확인하고, 복구 시점 이후 미포함 입력이 있으면 범위를 명시한다.

복구 가능 판정과 운영 전환은 구분한다. 시험 결과를 제시한 뒤 구체적인 전환 대상·시점·되돌아갈 경로를 정한다. 운영 중 새 입력을 받은 DB를 이전 백업으로 조용히 교체하지 않는다.

### 17.4 공급자 비교와 비용 보고

무료 선행 시험 정책에 맞춘 현재 비교와 시험안은 19절을 따른다. 비교 기준은 PC 독립 동작, 영속 DB·파일, Google 로그인 콜백, 서버 작업 재개, 원본 접근 제어, 백업·복구, 지역·전송 비용이다. 무료라는 이름만으로 상시 실행·영속 저장·외부 파일 다운로드가 모두 무료라고 가정하지 않는다.

초기 자료 규모가 확인되지 않으면 사용자 수·원천 파일 용량·월 업로드·출력 횟수를 명시한 합성 가정으로 비용을 산정하고 실제 측정 전임을 표시한다. 무료 한도 초과 시 자동 유료 전환을 새로 허용하지 않는다. Gemini 비용 정책과 호스팅 비용을 합쳐 설명하지 않는다.

운영 화면에는 저장 실패, 처리 지연, 예약 권한 확인 지연, 백업 실패처럼 사용자의 조치가 필요한 상태만 간단히 표시한다. 매 행 저장 때 전체 감사·백업·원천 해시 재검사를 실행하지 않는다. 개발용 해시·스택 추적·모델 공급자 내부 설정을 장부 표의 새 열로 노출하지 않는다.

R2는 무료 사용량이 있다는 뜻이지 한도 초과 과금을 자동 차단한다는 뜻이 아니다. [Workers](https://developers.cloudflare.com/workers/platform/pricing/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [R2](https://developers.cloudflare.com/r2/pricing/)

현재 추천은 조건부다. 구현 변경과 검증 부담을 줄이는 목표에는 영속 디스크를 가진 Python 앱 방식이 더 잘 맞는다는 설계 판단이다. 사용자 예산이 무료만 허용한다면 이 추천을 확정하지 않고 무료 구성의 파일 처리·작업 재개 적합성을 먼저 확인한다. 무료 호스팅을 맞추기 위해 원천 보존·PC 독립 동작을 없애지 않는다.

### 18.3 영속 디스크 방식이 선택된 경우

1. 기존 업무 로직과 단일 정본 DB를 유지하고 운영 HTTP 실행·Google 세션·비밀 설정을 연결한다. 현재 합성 stdlib 서버를 그대로 외부에 공개하는 것을 완료로 보지 않는다.
2. DB, 봉인 원천, 증빙 파생 자료, 불변 출력의 경로를 명시적인 영속 저장 루트 아래에 둔다. 소스 체크아웃 경로·현재 작업 디렉터리의 상대 경로에 맡기지 않는다. 로그와 재생성 가능한 임시 파일은 구분한다.
3. 한 서비스 인스턴스 내부에 내구성 있는 작업 처리 경로를 둔다. 별도 서비스가 같은 로컬 SQLite 디스크를 읽을 수 있다고 가정하지 않는다. HTTP 요청과 작업자 사이의 DB 연결·트랜잭션 경계를 명시한다.
4. 재배포 시 새 요청 접수·진행 작업의 종료 또는 커서 보존·프로세스 종료 순서를 정한다. 영속 디스크 연결은 무중단 배포를 보장하지 않으므로 짧은 중단 가능성을 운영 설명에 적는다. [Render 디스크 제약](https://render.com/docs/disks)
5. DB 마이그레이션은 기존 파일 존재와 스키마 버전을 확인하고 한 작성자만 수행한다. 운영 시작 때 합성 시드 행을 추가하지 않는다. 백업 없이 운영 DB를 초기화하거나 실패한 마이그레이션을 성공으로 처리하지 않는다.
6. 백업은 앱 데이터와 별도 장애 범위에 보존할 경로를 정한다. 같은 디스크 안의 복사본만으로 디스크 유실 복구가 가능하다고 보고하지 않는다. 저장소와 보관 주기는 비용안에 포함한다.

### 18.4 무료 지향 방식이 선택된 경우

호스팅 결정 전에 작은 합성 적합성 검증만 수행한다. 원장 전체·UI 전체를 먼저 새 런타임으로 재작성하지 않는다.

- 저장 어댑터: 현재 저장·이력·요청 결과·revision 계약을 대상 DB의 원자적 쓰기로 표현할 수 있는지 확인한다. SQL 문법이 비슷하다는 이유로 SQLite 연결 코드를 그대로 사용할 수 있다고 보고하지 않는다.
- 파일 처리: 대표 합성 카드 파일 접수·파싱·51행 이상 처리·중간 중단 재개와 xlsx 생성을 CPU·메모리·시간 제한 안에서 측정한다. 초과하면 유료 전환 또는 별도 처리 서비스가 필요한 범위를 보고한다.
- 저장 비용: 원천·증빙·출력·백업의 합산 저장량과 읽기·쓰기 작업 수를 계산한다. 무료 한도 초과 시 거부·대기할 기능과 요금제의 실제 청구 동작을 확인한다. 결제수단 등록이나 유료 활성화는 자동으로 진행하지 않는다.
- 포기 기준: 필수 기능을 구현하려고 다른 상시 서버가 추가로 필요하거나 전체 정규화 재작성 비용이 커지면 무료 후보의 장점을 다시 비교한다. 실패를 숨기려고 업로드·xlsx·PC 독립 동작 요구를 빼지 않는다.

### 18.5 배포 전 제출할 한 장의 결과

구현자는 별도 장문의 검증 문서를 계속 만들지 않고 기존 구현 기록에 다음 결과를 한 묶음으로 보고한다.

| 항목 | 반드시 구체적으로 적을 내용 |
|---|---|
| 선택 구성 | 앱·DB·파일·백업 공급자와 요금제, 기존 코드 변경 범위 |
| 월 비용 | 고정비·가정한 사용량·초과 단가·미포함 세금/환율, 무료 여부 확인 근거 |
| 재시작 결과 | 저장한 행·원천·규칙·출력이 유지되는지, 미완료 작업의 재개 결과 |
| PC 종료 결과 | 장부 저장·업로드·출력 유지, Muse 장애 시 Gemini 또는 대기 상태 |
| 복구 결과 | 별도 DB 복구 시점·누락 가능 시간 범위·실측 소요 시간·권한 재확인 |
| 사용자 선택 | 구체적인 운영 전환 대상·비용·남은 제한을 보고 승인받을 사항 |

이 비교는 세 후보 계열의 사전 검토이며 전체 시장에서 가장 저렴한 조합을 입증한 결과가 아니다. 예산 답변 이후 필요한 후보만 추가 조사한다. 계정 생성·결제·배포·운영 자료 이동은 아직 하지 않았다.

## 19. 무료 선행 시험 배포안

확정일: 2026-09-25. 사용자 정책은 무료 범위로 먼저 시험하고 유료 전환이 필요하면 별도 승인받는 것이다. 이전의 `무료 범위만 허용` 답변은 현재 시험의 비용 상한으로 적용하며, 뒤이은 답변에 따라 유료 전환안을 보고하는 것까지 금지하지 않는다. 자동 결제·유료 전환·무료 체험 만료 뒤 유료 유지에는 동의한 것이 아니다.

### 19.1 시험 후보와 선택 근거

첫 시험 후보는 **Oracle Cloud Always Free VM에서 Python 앱·SQLite를 유지하는 구성**이다. 이는 구현자가 조사할 설계 추천이며 사용자 계정의 실제 자원 확보나 공급자 사용 승인을 완료했다는 뜻이 아니다. 기존 Python 정규화와 저장 로직을 무료 서버리스 환경에 전면 이식하는 부담을 피하기 위한 판단이다.

공식 문서 확인: A1 무료 자원은 현재 총 2 OCPU·12GB 메모리 상당이며 부트·블록 저장소 합계 200GB, 비유료 계정의 Object Storage는 합계 20GB와 월 API 요청 50000회가 안내돼 있다. 무료 자원은 홈 리전과 계정 전체 한도를 확인해야 한다. VM 용량 부족과 유휴 인스턴스 회수 가능성이 있다. 과거 4 OCPU·24GB 안내를 현재값으로 복사하지 않는다. [Oracle Always Free 자원](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

계정은 비유료 상태를 유지한다. 기간 한정 체험 크레딧으로만 가능한 자원을 상시 무료 구성에 넣지 않는다. 무료 등급에는 SLA가 없고 가입 과정에서 결제수단 확인이 요구될 수 있으므로 사용자의 계정 설정 단계가 필요하다. 계정 전환을 통해 용량 부족을 해결하지 않는다. [Oracle Free Tier FAQ](https://www.oracle.com/cloud/free/faq/)

### 19.2 초기 자원 명세

다음 수치는 시험용 상한 설계이며 계정에서 이미 사용하는 자원을 뺀 무료 잔여량이 부족하면 줄이거나 접수를 보류한다.

| 구성 | 시험안 | 확인할 조건 |
|---|---|---|
| 앱 실행 | Always Free 표시가 확인된 A1 VM 1대, 1 OCPU·6GB 이내 | 홈 리전에서 실제 생성 가능, ARM에서 기존 Python 의존성 동작 |
| 부트·데이터 | 부트 50GB, 데이터 블록 50GB 이내 | 계정 전체 부트·블록 합계가 무료 범위 안, 유료 성능 옵션 사용 안 함 |
| 정본 DB | 데이터 볼륨의 SQLite 한 개 | R01의 원자적 저장·현재 스키마·재시작 보존 검증 |
| 업로드·증빙·출력 | 데이터 볼륨 내 구분된 비공개 경로 | 원본 불변, 출력 불변, 인증된 조회·다운로드 |
| 작업자 | 같은 VM의 단일 작업 실행 경로 | 커서·상태 저장, 재시작 재개, HTTP와 분리된 정상 진행 |
| 백업 | 무료 Object Storage의 비공개 버킷 | 계정 전체 저장량·요청량 안에서 DB 스냅샷·불변 원천 보존 |
| HTTPS | 사용자 소유 도메인 사용 가능 여부 확인, 없으면 무료 DNS 후보 검증 | 새 도메인 구매 안 함, Google 콜백 등록·인증서 갱신을 실제 확인 |

무료 DNS 후보로 Duck DNS, 인증서 발급 후보로 Let's Encrypt를 검토한다. 무료 DNS 제공 사실과 인증서 발급 절차는 각각의 공식 안내를 따른다. 해당 주소가 앱의 Google OAuth 설정과 소유 확인 조건을 충족하는지는 실제 설정 단계에서 확인하며, 미확인 주소를 배포 확정값으로 적지 않는다. [Duck DNS 소개](https://www.duckdns.org/about.jsp), [Let's Encrypt 시작 안내](https://letsencrypt.org/getting-started/)

외부에는 HTTPS 앱 경로만 제공하고 SQLite·원천 디렉터리·작업자 관리 포트를 공개하지 않는다. SSH 관리는 제한된 관리자 접근으로 둔다. 원격 웹앱은 로컬 Muse의 포트를 직접 공개하는 대신 기존 명세의 인증된 연결 프로그램 방식으로 연결한다. 공개 합성 포트폴리오는 별도 데이터 경로이며 운영 로그인 링크나 실제 원천을 포함하지 않는다.

### 19.3 비용을 발생시키지 않는 실패 처리

- 계정 등급·리전·이미지·컴퓨트·볼륨·백업·네트워크의 무료 적용 여부를 실제 콘솔과 공식 조건으로 확인한 뒤 자원 명세에 기록한다. 앱 수준 사용량 경고만으로 공급자 과금을 차단했다고 주장하지 않는다.
- Always Free 용량이 없으면 해당 시험을 자원 확보 대기로 남긴다. 유료 계정으로 전환하거나 다른 리전의 유료 자원을 만들지 않는다. 무한 생성 재시도·회수 방지를 위한 인위적인 부하도 만들지 않는다.
- 무료 한도 부족 시 새 파일 접수·새 출력 생성처럼 추가 공간이 필요한 작업부터 사유를 표시하고 거부한다. 이미 저장된 장부·원천·출력을 지우거나 파싱 오류처럼 표시하지 않는다. 최소 여유 공간도 없으면 행 저장 역시 성공으로 위장하지 않고 거부한다.
- 계정의 사용량과 앱의 예상 저장량을 확인하고 공간 부족 전에 경고한다. 아직 받지 못한 파일을 접수 완료로 기록하지 않는다. 실패한 출력의 임시 파일만 정리하며 과거 산출물을 자동 삭제하지 않는다.
- 무료 VM이 회수·중지되면 PC와 무관하게 서비스가 중단될 수 있다. 이 경우를 `PC가 꺼져도 항상 무중단`으로 설명하지 않는다. 자원 복구 또는 유료 대안의 필요성을 보고하고 무료 계정 안에서만 재개를 시도한다.

### 19.4 시험 순서와 중간 확인

1. **로컬 선행:** 기존 수정 A~D를 끝내고 Phase 6~7의 필요한 기능을 준비한다. 호스팅이 무료여도 미검증 합성 서버를 바로 운영 원장으로 쓰지 않는다.
2. **자원 확인:** 계정·홈 리전의 실제 무료 잔여량·주소·인증 설정 가능 여부를 확인한다. 실제 가입과 비밀 입력은 사용자가 자신의 계정 화면에서 수행한다. 구현 모델에 결제정보·원본 고객 자료를 전달하지 않는다.
3. **합성 배포:** 별도 합성 DB로 앱을 시작하고 Google 로그인, 직원 신청·승인, 담당 여행별 조회, 증빙 미리보기 제한을 확인한다. 실제 예약 연결이 없으면 합성 배정임을 표시한다.
4. **핵심 업무:** 51행 카드 처리, 직접 수입 수정, 은행 정정·원천 연결, 분할 입금, 이름 변경·보관·삭제, xlsx 다운로드를 기존 수용 사례로 확인한다. 배포 환경 때문에 달라질 수 있는 경로만 다시 검사한다.
5. **지속성:** 앱 프로세스·VM 재시작과 미완료 작업 재개를 확인한다. 사용자 PC를 끈 상태에서 장부·업로드·출력이 유지되는지 확인하며 Muse 장애 시 Gemini 또는 대기가 정확히 표시돼야 한다.
6. **복구:** 별도 경로에 백업을 복원해 사건·배분·정정·요청 멱등성·권한 재확인을 검사한다. 현재 VM을 지우면서 복구를 시험하지 않는다.
7. **시험 보고:** 사용량·성능·실패 경로·원본 형식 지원 범위를 보고한다. 실제 이관과 운영 기준 전환은 이 결과 이후 정하며 무료 시험 성공을 운영 전환 승인으로 취급하지 않는다.

백업 시험 기준은 매일 일관된 DB 스냅샷 1회와 최근 7개 보존, 원천 파일은 해시 기준으로 한 번씩 보존하는 구성으로 시작한다. 이는 구현 기본값이며 무손실 복구 약속이 아니다. 예상 총량이 무료 공간을 넘으면 최신 성공 백업과 원천을 먼저 보존하고 새 업로드를 제한한 뒤 조정안을 제시한다. 보관 정책에 따른 시험 DB 백업 순환과 원천·과거 출력의 임의 삭제를 혼동하지 않는다. 최대 최근 24시간의 입력이 백업에 없을 수 있음을 보고하며, 실제 손실 범위는 최종 성공 백업 시각으로 계산한다.

같은 계정의 Object Storage는 VM 유실에 대비하는 별도 저장 위치일 뿐 계정 전체 상실을 완전히 대비한 외부 백업은 아니다. 운영 전환안에는 owner가 별도 보관할 복구 묶음의 내보내기 경로도 명시한다. 백업을 직원의 다운로드 권한에 연결하지 않는다.

### 19.5 후보가 막혔을 때의 분기

| 발생 조건 | 후속 작업 | 하지 않을 일 |
|---|---|---|
| 무료 VM 확보 불가·가입 불가 | 로컬 구현 유지, 무료 후보 적합성 검토 또는 대기 사유 보고 | 유료 계정으로 몰래 전환 |
| ARM 의존성·메모리 문제 | 무료 AMD 후보의 실제 처리량 검증 또는 영향 범위 보고 | 파서·원천 필드 생략으로 통과 |
| 무료 DNS·Google 콜백 조건 미충족 | 사용자 소유 주소 활용 가능 여부와 다른 무료 주소 후보 확인 | 유료 도메인 구매, 인증 검사 제거 |
| 무료 저장량·처리량 부족 | 신규 작업 제한, 현재 자료 보존, 실제 부족량 보고 | 기존 자료 삭제, 자동 과금 옵션 활성화 |
| 무료 운영의 회수·중단 위험이 수용 불가 | 최소 유료 대안의 비용·개선점·이관·복구 경로 제시 후 승인 요청 | 무중단이라고 과장하거나 이미 승인됐다고 처리 |

Cloudflare 대안은 18.4절의 작은 적합성 검증을 먼저 통과해야 한다. R2의 무료 사용량 안내만으로 초과 비용이 원천 차단된다고 간주하지 않는다. Render 무료 로컬 저장, Vercel Hobby의 회사 장부 사용을 무료 대체안으로 자동 채택하지 않는다.

### 19.6 명세 인계의 완료 범위

이 인계본은 기능 정책, 저장·중복 방지·권한 계약, 실제 구현 결함의 수정 지시, 단계별 검증 기준, 무료 선행 시험 배포안까지 작성했다. 선택된 시험 후보의 실제 계정·자원 가용성, Google 자격 증명, 원천 파일 형식, 예약 API, 실제 자료 이관, 운영 전환은 구현·연결 단계에서 확인할 실행 조건이다. 이 실행 조건을 문서에서 확인한 사실처럼 꾸미지 않는다.

구현자는 기존 전달문과 구현 검토 7절에서 현재 담당 묶음을 받아 시작한다. 문서를 더 늘리는 것보다 실제 재현 실패를 수정하고 결과를 기존 구현 기록에 남긴다. 새 정책 판단이 필요한 충돌이 발견될 때만 해당 조항을 보완한다. 코디네이터가 앱 구현이나 배포를 완료한 것은 아니다.
