# 비용분류 v2 정합성 개선 실행 계획

## 목적

신규 v2 모델의 금액 불변식은 통과했지만, legacy 분류를 도메인별로 분해하면서
판정 신뢰도, 취소 관계, 여행 귀속, 예약 공급자에 남아 있던 품질 문제가 드러났다.
이 문서는 해당 문제를 위험도와 선후관계에 따라 해소하고, v2를 기존 v14/v76
산출 경로와 병렬 검증할 수 있는 상태로 만드는 실행 계획이다.

현재 기준선은 다음과 같다.

| 지표 | 현재값 |
|---|---:|
| 원천/결제/활성 배분 | 1,705 / 1,705 / 1,705건 |
| 결제 합계/활성 배분 합계 | 310,719,899원 / 310,719,899원 |
| 결제별 배분 차이 | 0건 |
| 고신뢰이면서 불확실한 근거 | 196건 |
| 취소·환불 원거래 미연결 | 7건 |
| 여행 미배정 | 19건, 2,734,540원 |
| 공급자 미확정 예약 | 112건 |
| 저신뢰 결제 | 87건 |
| 0원 결제 | 9건 |

수치는 `classified_v14.csv` 이관 기준이다. 최신 원천을 다시 적재하면 기준선을
새로 기록하고 증감 사유를 함께 남긴다.

## 공통 원칙

1. 금액 불변식보다 분류 건수 감소를 우선하지 않는다. 억지 귀속 대신
   `needs_review`와 `unassigned`를 명시적으로 유지한다.
2. 원천 사실은 수정하지 않고, 관계·판정·배분의 새 버전을 추가한다.
3. 자동판정에는 반드시 `rule_id`, 근거, 신뢰도와 적용 결과 건수를 남긴다.
4. 취소·환불은 승인번호 또는 카드사별 구조적 키로 연결한다. 승인번호가 있는
   거래에 가맹점·금액 폴백을 적용하지 않는다.
5. OTA·항공·PG 결제는 결제일 근접성만으로 여행에 귀속하지 않는다.
6. 단계별 작업 후 결제 건수, 총액, 결제별 배분합계와 외래키 검증을 다시 수행한다.
7. 최신 수기장부와 OTA 메일을 사용하는 단계는 P8·P10의 진실원천 순서를 따른다.

## 우선순위

### P0. 검토 큐와 회귀 기준 고정

후속 작업이 같은 기준으로 반복 실행되도록 품질 이슈를 행 단위로 조회하고
수정 전후 차이를 비교할 기반을 만든다.

구현:

- `review-report`의 집계값마다 대응하는 상세 조회 명령 또는 CSV 출력 추가
- 각 큐에 결제 키, 현재 판정, 근거, 규칙, 신뢰도, 예약번호, 배분대상 포함
- 실행 시점, 입력 문서 해시, 규칙 버전과 기준선 지표 저장
- 여행별·계정별·배분대상별 기존 v14 합계를 회귀 기준으로 출력

완료 기준:

- 모든 집계값에서 동일 건수의 상세 행을 재현할 수 있다.
- 같은 DB에서 반복 실행한 결과가 동일하다.
- 수정 전후 추가·해소·잔존 건을 구분할 수 있다.

### P1. 고신뢰·불확실 근거 196건 해소

가장 먼저 처리한다. 확정처럼 보이는 판정이 불확실한 근거를 가진 상태는 자동전기
오염 위험이 가장 크다.

구현:

- `추정`, `유사`, `불명`, `확인 필요` 등 충돌 문구를 유형과 `rule_id`별로 묶는다.
- 예약번호+메일 실증, 수기 단독매칭, 현지정합 등 `상` 신뢰도 허용조건을 규칙으로 명시한다.
- 허용조건을 충족하면 근거를 구조화해 `confirmed` 판정을 새 버전으로 생성한다.
- 충족하지 않으면 신뢰도를 낮추고 `needs_review`로 전환한다.
- 기존 판정은 `superseded` 연결로 보존한다.

완료 기준:

- `상` 신뢰도이면서 불확실한 근거가 있는 현재 판정이 0건이다.
- 신뢰도 변경 전후 건수와 규칙별 사유가 리포트에 남는다.
- 재판정으로 결제금액 또는 배분합계가 변하지 않는다.

### P2. 취소·환불 원거래 미연결 7건 정리

취소 관계는 순액과 여행별 비용을 동시에 바꿀 수 있으므로 여행 미배정보다 먼저
확정한다.

구현:

- 국민 국내: 취소번호 괄호 안 원승인번호로 연결
- 하나: 동일 승인 행의 승인취소금액 구조로 연결
- 국민 해외: 카드4·통화·현지금액을 소수 보존해 페어링
- 기업: 승인번호 링크 부재가 확인된 경우에만 가맹점+금액 예외 규칙 적용
- 원거래가 조회기간 밖이면 미연결 오류로 숨기지 않고 `전기예약_환불` 사유를 기록
- 완전상쇄와 부분환불을 구분해 배분계획을 새 버전으로 생성

완료 기준:

- 7건 각각이 `원거래 연결`, `조회기간 밖`, `자료 부족` 중 하나로 설명된다.
- 자료 부족 건은 근거와 검토 상태를 가진 채 남고, 원인 없는 미연결 건은 0건이다.
- 완전상쇄쌍의 순액은 0이고 부분환불은 원여행 배분과 함께 검증된다.

### P3. 여행 미배정 19건 재분류

취소 관계 정리 후 남은 실결제를 예약·메일·수기 근거로 검토한다.
`MISC-*` 신규 격리 11건과 현재 전체 미배정 19건을 별도 지표로 유지한다.

구현:

- 가맹점/예약번호/카드/금액/사용일 기준으로 중복 없는 검토 묶음 생성
- OTA·항공·렌터카는 메일 또는 예약 문서에서 서비스 기간과 예약번호 확인
- 판관비 후보는 카드 기명자·용도와 확정 규칙을 적용
- 여행 귀속이 확인되면 새로운 allocation plan을 만들고 기존 계획을 대체
- 자료가 부족하면 미배정 상태, 부족한 근거와 검토 담당을 명시

완료 기준:

- 19건 모두 `여행`, `판관비`, `취소/정산`, `근거 부족 미배정` 중 하나로 설명된다.
- 근거 부족 건을 제외한 자동 미배정은 0건이다.
- 변경된 여행별 합계가 원천 결제와 역추적된다.

### P4. 공급자 미확정 예약 112건 정규화

공급자 식별은 예약번호 중복 방지와 메일 어댑터 연결에 필요하지만, 결제금액
정합성에는 직접 영향을 주지 않으므로 귀속 문제 뒤에 처리한다.

구현:

- 예약번호 형식 규칙 적용: Agoda 10~12자리, Trip.com `1400` 시작 16자리,
  Booking.com 10자리 내외
- 기존 `booking_info`, 판정 근거와 메일 발신자/본문을 구조화된 evidence로 연결
- 형식만으로 단정할 수 없는 번호는 `proposed`, 메일 실증은 `confirmed`로 구분
- provider 변경 시 동일 예약의 중복 레코드를 탐지하고 관계를 병합

완료 기준:

- 자동 식별 가능 건에는 재현 가능한 `rule_id`가 있다.
- 잔여 `unknown`은 자료 부족 사유와 검토 상태를 가진다.
- `(provider, booking_number)` 중복 및 관계 유실이 0건이다.

### P5. 저신뢰 87건과 0원 결제 9건 감사

앞 단계의 판정 변경 후 큐를 다시 산출하고 잔존 건만 검토한다.

구현:

- 저신뢰 건을 예약 미확정, 여행 미확정, 계정 미확정, 증빙 미확정으로 분리
- 0원 거래를 포인트 결제, 완전상쇄, 카드 승인자료의 금액열 오류, 실제 0원으로 구분
- 포인트 사용은 P13에 따라 상쇄 전 총액을 비용으로 인식하고 근거를 연결
- 해결할 수 없는 건은 자동전기 대상에서 제외되는 `needs_review` 게이트 적용

완료 기준:

- 0원 9건 각각의 비용 인식 금액과 사유가 설명된다.
- 저신뢰 잔존 건은 부족한 근거와 자동전기 차단 여부가 명시된다.
- `confirmed` 상태에는 저신뢰 판정이 없다.

### P6. 직접 적재와 산출 경로 병렬 검증

legacy 품질 문제를 해소한 후 `classified_v14.csv`를 중간 진실원천으로 쓰는 의존을
줄이고 실제 전환 가능성을 검증한다.

구현:

- 카드, 수기장부, OTA 메일별 source adapter를 만들어 원천 계층에 직접 적재
- 중복 원천과 동일 거래를 별도 관계로 관리하고 원문 해시를 보존
- v2의 확정 배분을 읽는 read-only 워크북 어댑터 구현
- 기존 v76과 결제별·여행별·계정별·예약번호별 회귀 대조
- 차이를 `의도된 개선`, `legacy 오류`, `v2 오류`, `자료 부족`으로 분류

완료 기준:

- 동일 원천을 반복 적재해도 결제와 관계가 중복되지 않는다.
- 기존 워크북과의 모든 차이가 행 단위로 설명된다.
- 도메인 모델 문서의 전환 게이트 7개를 모두 통과한다.
- 전환 승인 전까지 기존 v14/v76 경로는 그대로 유지된다.

## 권장 작업 단위

| 순서 | 작업 단위 | 선행 조건 | 핵심 산출물 |
|---:|---|---|---|
| 1 | 상세 검토 큐와 기준선 스냅샷 | 없음 | 재현 가능한 큐/리포트 |
| 2 | 신뢰도-근거 충돌 재판정 | 1 | 판정 버전과 규칙별 결과 |
| 3 | 취소 관계 해결 | 1 | 관계 판정과 순액 검증 |
| 4 | 미배정 재분류 | 2, 3 | 새 배분계획과 잔여 큐 |
| 5 | 예약 공급자 정규화 | 1 | provider 판정과 병합 결과 |
| 6 | 저신뢰·0원 감사 | 2~5 | 자동전기 차단/확정 목록 |
| 7 | 직접 적재 어댑터 | 2~6 | 원천별 멱등 적재 |
| 8 | v2 워크북 어댑터와 회귀 대조 | 7 | 전환 게이트 리포트 |

P1과 P2는 P0 이후 병렬 구현할 수 있지만, P3의 최종 배분은 두 작업이 끝난 뒤
수행한다.

## 매 단계 공통 검증

```bash
python3 ledger/domain/ledger_db.py validate
python3 ledger/domain/ledger_db.py review-report
python3 -m unittest discover -s ledger/tests -p 'test_*.py' -v
```

추가로 단계별 테스트에는 다음을 포함한다.

- 원천·결제 건수 보존
- 결제합과 활성 배분합 일치
- 결제별 배분 차이 0
- 현재 판정 차원별 중복 0
- 활성 allocation plan 중복 0
- 외래키 위반 0
- 규칙 적용 전후 상세 diff 재현
