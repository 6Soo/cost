# COST 통합 사용자 확인함과 자동 지출 처리 파이프라인 재설계 (2026-11-05)

> **상태: 사용자 결정 반영 / 상세 설계 확정 / 구현 미착수.** 이 문서는 지출정리 UX와 사용자 개입 흐름의 새 정본이다. 실제 코드·DB·운영 화면은 아직 바뀌지 않았다. 구현은 이 문서와 현재 금융·자동화 계약을 함께 읽고 진행한다.

## 0. 최종 제품 결정

사용자가 카드 내역이 추가될 때마다 “모든 내역 확인해”라고 에이전트에게 반복 지시하거나, 여러 화면을 돌아다니며 미해결 건을 찾아 처리하는 구조를 없앤다.

1. **새 카드 거래와 지출 관련 근거가 들어오면 COST가 자동으로 전체 파이프라인을 실행한다.** 모든 신규 원행은 수집·무결성·중복·금융 관계·분류 검사를 거친다. 코드로 결론이 나지 않는 항목만 연결 에이전트가 근거를 대조한다.
2. **에이전트가 해결할 수 있는 일은 끝까지 처리한다.** 기존 코드 규칙, 예약·취소 메일, OTA 스냅샷, 영수증, 여행 일정, Google 읽기 스냅샷 등 승인된 자료를 먼저 확인한다. 낮은 신뢰도만으로 사용자에게 넘기지 않는다.
3. **사람이 실제로 답해야 하는 일만 한곳에 모은다.** 모든 사용자 작업의 유일한 진입점은 최상위 메뉴의 **내 확인 필요**다. 사용자는 다른 화면을 순회해 미결 건을 찾지 않는다.
4. **사용자에게 보류 기능을 제공하지 않는다.** 보류함, 보류 탭·필터·건수, 보류 해제 버튼, “자료 확인 후 보류 해제” 체크박스, 보류 상태를 완료시키는 우회 버튼을 제거한다. 사용자가 할 일은 보류를 해제하는 것이 아니라 구체적인 사실에 답하거나 필요한 자료를 제공하는 것이다.
5. **자동 처리 중인 작업을 사용자 대기열에 노출하지 않는다.** P1/P2 작업·재시도·provider 장애·코드 결함 조사는 내부 작업 상태다. 사용자가 할 수 있는 일이 없으면 사용자 작업으로 만들지 않는다.
6. **금융 안전장치는 제거하지 않는다.** 기존 원본·금액·ID·중복·환불·수동 결정·권한·원자성 보호는 유지한다. transaction_review_holds 등 기존 보호 데이터는 우선 내부 안전 잠금으로만 취급한다. 사용자가 직접 생성·해제하거나 별도 목록에서 관리하지 않는다. 충분한 근거와 원본 버전 검증을 통과한 경우에만 시스템이 잠금을 자동 해소한다. 기존 이력·행을 이 작업만으로 삭제하거나 일괄 초기화하지 않는다.
7. **실제 환불·COST 내부 기록·Google 최종 장부 반영을 서로 다른 사실로 유지한다.** 예약 취소만으로 카드 환불이나 순지출 0원을 만들지 않는다. Google 최종 장부 자동 쓰기 금지는 계속 유지한다.

## 1. 현재 구조에서 확인한 문제

현재 main의 구조는 일부 자동화 기반을 이미 갖고 있으나, 사용자 작업의 단일 진입점은 아니다.

- P1 코드 처리 → P2 연결 에이전트 → P3 사용자 개입이라는 처리 단계와 autonomous cleanup worker가 있다.
- /import의 지출 정리에는 cleanup_owner=user|auto 필터와 분류·기록·근거·금융·수동 사유 분류가 있다. 그러나 이 모집단은 카드 거래와 일부 미배정 장부 지출 중심이며, 전체 COST 화면의 사용자 작업을 집계하지 않는다.
- 카드 지출 정리 렌더러는 transaction_review_holds를 읽어 “보류 중”으로 표시하고, 일부 행에서는 일반 편집 폼 대신 카드 자료 전체 검토와 보류 해제를 안내한다.
- 취소·환불, OTA 예약 근거, 영수증, 실제 자료 검토, 예약 연결, Google 대조·복사, 여행 귀속 등 관련 작업은 각각의 탭·상세·검토 화면에 분산되어 있다.
- 따라서 사용자는 “내 확인 필요” 건수만 보고 모든 인간 작업이 모였다고 신뢰할 수 없다. 일부 화면은 상태만 보여주거나 다른 화면으로 이동시킨다. 같은 거래가 카드·OTA·환불·영수증 화면에 중복 노출될 위험도 있다.
- 이전 상태 필터 명세의 “보류·오류” 칩과 과거 UX 명세의 “보류 해제” 동작은 새 제품 결정과 충돌한다. 해당 문서들은 이 명세로 대체한다.

### 기존 코드에서 우선 확인할 위치

| 영역 | 현재 책임 | 재설계 시 변경 방향 |

## 2. 새 파이프라인: 입력부터 종료까지

### 2.1 입력·변경 감지

다음 사건은 동일한 지출 검토 오케스트레이터를 깨운다.

- 카드 파일 신규 업로드 또는 기존 파일의 새로운 원행 유입
- 같은 카드 원본의 취소·환불 원행 추가
- OTA 예약·변경·취소 메일 또는 OTA 스냅샷의 새 세대
- 영수증 이미지·추출 데이터의 신규 등록 또는 수정
- 여행 권위 일정·Google 읽기 스냅샷 등 기존 거래 판단에 영향을 주는 근거 변경
- 사용자 답변 저장

각 사건은 원본 ID, source hash/digest, revision, 출처 유형, 발생 시각을 기준으로 멱등 처리한다. 같은 파일·같은 원행·같은 근거 버전은 중복 작업이나 중복 기록을 만들지 않는다. 새로운 근거가 기존 판단을 바꿀 수 있을 때만 해당 거래·환불 그룹·연관 작업을 다시 평가한다.

카드 파일 업로드가 사용자에게 요구하는 일의 기본값은 파일 제출까지다. 이후 전체 내역 확인, 분류, 여행 배정, 환불 대조, 내부 기록 가능성 검사는 자동으로 진행한다. 카드사의 조회 기간처럼 원본 자료에 없는 필수 범위 정보만 업로드 과정에서 한 번 확인받는다.

### 2.2 P1: 결정적 코드 처리

모든 신규 원행은 P1을 통과한다. 구매뿐 아니라 취소·환불·음수 원행·중복·회사 경비·원본 오류도 평가 대상에서 빠지면 안 된다.

- 원행 파싱, 원본 동일성, 거래 ID, 금액·통화·날짜, 중복과 카드별 조회 범위를 검증한다.
- 기존 규칙과 승인된 업무 계약으로 비용 항목·여행 후보·OTA 연결·취소/환불 관계를 계산한다.
- 유효한 실제 여행의 최선 후보가 있으면 낮은 추론 점수만으로 사용자 질문을 만들지 않는다. 근거와 불확실성을 기록한다.
- 수동 결정·수동 링크·회사 경비 제외·이미 기록된 행은 자동 추론이 덮어쓰지 않는다.
- 원승인번호 1:N 환불, 무날짜 M:N OTA 연결 등 기존 금융 명세를 그대로 따른다.
- OTA 정확 예약 ID가 없다는 이유만으로 정상 카드 비용 분류·내부 기록 준비를 멈추지 않는다.

### 2.3 P2: 연결 에이전트의 전수 근거 검토

P1에서 확정되지 않은 항목과 새로운 근거로 재검토가 필요한 항목은 기존 연결 에이전트가 처리한다.

- “기타경비/현지경비” 등 특정 기본값만 후보로 삼아 다른 신규 거래를 누락하지 않는다. **신규 원행 전체가 P1 평가를 받았는지**가 첫 조건이며, P2 대상은 P1 결과와 기존 확정 이력으로 산출한다.
- 거래 한 건만 보지 않고 같은 환불 그룹, 관련 예약·취소 메일, OTA 이벤트, 영수증, 여행 일정, 기존 수동 결정 및 Google 읽기 스냅샷을 필요한 범위에서 대조한다.
- 이미 같은 source digest와 같은 정책으로 검토 완료한 거래는 다시 호출하지 않는다. 근거 digest 또는 판단 코드 fingerprint가 바뀌었을 때만 재평가한다.
- P2는 제한된 기존 여행·항목과 근거를 제안·적용하는 기존 preview/apply 계약을 사용한다. 원본·금액·ID·수동 결정·환불 링크를 AI가 임의 변경하지 않는다.
- 모델 미실행, timeout, 한도 도달, 잘못된 응답, 오래된 원본 버전은 내부 retry/diagnostic 상태로 남긴다. 사용자에게 “자료를 확인하고 보류를 풀라”고 넘기지 않는다.
- 모델이 실제 실행되지 않았으면 AI 검토 완료로 표시하지 않는다. 합성 성공과 운영 성공을 구분한다.

### 2.4 코드 결함 자동 개선 루프

같은 유형의 미처리·실패가 반복되면 거래마다 사용자에게 질문하지 말고 에이전트가 코드 결함 여부를 조사한다.

1. 원인 fingerprint로 반복 실패를 묶고, 이미 해결된 과거 금융 충돌·정상 사용자 결정은 재개하지 않는다.
2. 실제 실패를 익명화된 합성 fixture로 재현하고 최소 회귀 테스트를 만든다.
3. 기존 금융·여행 업무 계약을 바꾸지 않는 코드 결함이면 원인을 수정하고 영향 테스트와 보호 테스트를 실행한다.
4. 변경 파일·실패 재현·회귀 테스트·CI 결과를 PR에 기록한다.
5. 기존 권한과 배포 게이트를 통과한 코드 수정은 정상 main 병합·허용된 배포 절차로 반영한다. 운영 소스 직접 덮어쓰기, 테스트 skip, 권한·보호 약화로 녹색을 만들지 않는다.
6. 수정된 판단 코드 fingerprint로 영향 거래를 재평가한다. 이미 해결된 거래를 다시 사용자 작업으로 만들지 않는다.
7. 금융 정책·원본 사실·새 권한이 필요한 문제는 코드 결함으로 위장하지 말고 필요한 한 가지 사용자 판단만 작업함에 올린다.

### 2.5 P3: 실제 사용자 작업 생성

P3는 아래 조건을 모두 만족할 때만 생성한다.

- 필요한 사실이 현재 카드 원본·예약/취소 자료·영수증·여행 일정·기존 사용자 답변 등 승인된 자료에 없다.
- P1/P2와 기존 규칙으로 합리적인 결론을 낼 수 없다.
- 답변에 따라 실제 금융 처리·여행 귀속·비용 성격·외부 반영 중 하나가 달라진다.
- 질문 대상과 선택지가 구체적이고 사용자가 직접 답할 수 있다.

낮은 AI 신뢰도, 정상 예약 ID 부재, 내부 작업 재시도, 단순 provider 장애, 코드가 아직 처리하지 못한 상태만으로 P3를 만들지 않는다.

작업 생성은 한 개의 실제 판단 단위로 묶는다. 원결제 1건과 여러 취소·부분환불, 같은 예약의 여러 OTA 이벤트, 한 영수증과 카드 거래가 같은 질문을 요구하면 각각 별도 작업으로 세지 않는다.

### 2.6 답변 후 자동 재처리

사용자는 작업함에서 구체적인 질문에 답하거나 요청된 자료를 제공한다.

1. 답변은 작업 ID, 원본 hash/revision, 질문 schema와 함께 저장한다.
2. 답변을 기존 사실로 기록하되 AI가 실제 카드 환불 전표·예약 원문·Google 반영을 만들어낸 것처럼 취급하지 않는다.
3. 저장 직후 해당 거래·그룹을 P1부터 다시 실행하고 필요하면 P2를 호출한다.
4. 안전하게 완료되면 작업함에서 즉시 사라진다. 사용자가 별도 “보류 해제”, “완료 승인”, “기록 확정”을 누르지 않는다.
5. 여전히 답이 필요한 경우에는 기존 답변을 반복하지 않고 새로 부족한 사실만 같은 작업에 갱신한다.
6. 다른 기기에서 답변했거나 원본 revision이 바뀌면 stale write를 거부하고 최신 근거로 재평가한다.

## 3. 통합 사용자 작업함

### 3.1 단 하나의 진입점

- 전역 주 메뉴에 최상위 **내 확인 필요 N건**을 둔다. 관리 메뉴 안에 숨기거나 여러 하위 메뉴로 나누지 않는다.
- N은 거래 수나 내부 job 수가 아니라 **사용자가 실제로 답해야 하는 고유 작업 수**다.
- 작업함은 전체 인간 작업을 합친 유일한 목록이다. /import, /ota, 환불, /receipts, /review, /reserve-links, Google 대조 등의 하위 화면은 별도 사용자 작업 목록을 만들지 않는다.
- 하위 화면은 원본·세부 근거를 제공할 수 있지만, 해당 작업의 답변·상태·완료는 같은 작업 ID와 같은 작업 서비스에 반영한다. 가능한 경우 “내 확인 필요에서 답변” 링크로 정확한 작업을 연다.
- “자동 진행·대기”, “보류·오류”, “수동 보류” 등의 별도 사용자 필터·목록·건수는 제거한다. P1/P2 내부 진행 상태를 사용자가 관리할 이유가 없다.

### 3.2 작업함에 포함할 범위

| 작업 유형 | 포함 조건 | 기본 처리 |
| --- | --- | --- |
| 카드 거래의 비용 성격·여행 귀속 | 실제 업무 사실이 없거나 합리적인 후보가 둘 이상 남아 사용자 판단이 결과를 바꿀 때 | 가능한 후보와 대조 근거를 먼저 제시하고 필요한 한 가지 사실만 질문 |
| 취소·환불 | 실제 환불 수령 여부, 부분 환불 금액, 원결제 대응 등 필수 사실이 승인 자료로 확인되지 않을 때 | 원결제·취소·환불을 하나의 그룹으로 제시 |
| 원본·파싱·중복 충돌 | 코드로 복구 불가하고 카드사 파일 재업로드·원본 확인 등 사용자가 제공해야 할 자료가 있을 때 | 실패 행·영향 금액·필요한 파일/필드를 명시 |
| OTA 예약·카드 연결 | 연결이 실제 비용 귀속/환불 판단에 필수이고 기존 자료로 결정할 수 없을 때 | 관련 예약·결제·취소 근거를 같은 작업에 묶음 |
| 영수증·증빙 | 필수 금액/일자/통화/결제수단 등이 원본·메일 등으로 복구되지 않을 때 | 이미 추출된 값은 채우고 비어 있는 필드만 질문 |
| 미배정 장부 지출·여행 비용 | 유효한 여행 후보가 없거나 실질적인 충돌이 남을 때 | 기존 최선 후보와 이유를 보여주고 필요한 사실만 질문 |
| Google 최종 장부 반영 | COST 내부 처리와 읽기 대조가 끝나 사용자가 직접 복사·붙여넣기 해야 하는 실제 묶음이 있을 때 | 거래마다 중복 작업을 만들지 않고 여행/기간 단위로 묶은 복사 작업 제공 |

여행·보험·참가자·항공권 등 다른 영역은 **지출의 비용 귀속 또는 금융 판단을 실제로 막는 경우에만** 작업함에 포함한다. 계정 설정, 규칙 관리, 일반 보고서 출력, 업무와 무관한 여행 운영은 지출 작업함에 섞지 않는다.

### 3.3 작업 카드의 필수 정보

각 작업은 사용자가 다른 화면을 추가로 찾아다니지 않아도 판단할 수 있어야 한다.

- 날짜·가맹점/대상·금액·카드/여행 등 식별 가능한 최소 정보
- 관련 거래와 예약·환불·영수증·장부 행을 묶은 관계 요약
- **에이전트가 이미 확인한 자료와 결과**: 예를 들어 예약 취소 메일은 확인했으나 카드 환불 원행은 찾지 못함
- 아직 부족한 정확한 사실 하나와 왜 필요한지
- 추천 판단과 근거, 추천과 다른 선택 시 영향
- 질문에 맞는 직접 답변 컨트롤과 하나의 주 행동 버튼
- 원본·상세 근거로 이동하는 보조 링크
- 답변 저장 후 자동 재처리 중임을 알려주는 짧은 완료 피드백

“확인 필요”, “검토해 주세요”, “보류 중”만 적힌 카드, 실제 다음 행동이 없는 배지, 전체 자료를 다시 열어보라는 안내는 수락하지 않는다.

### 3.4 작업 분류·정렬

- 기본 화면은 모든 열린 작업을 하나의 목록으로 보여준다.
- 필터는 같은 화면 안의 보조 필터일 뿐 별도 대기열이 아니다. 예: 결제·환불, 여행·항목, 증빙·원본, Google 반영.
- 금융 영향이 큰 항목과 오래된 작업을 우선하되 같은 원결제/환불 그룹은 하나의 카드로 유지한다.
- 완료·대체·취소된 작업은 기본 목록에서 제거하고 이력에서만 조회한다.
- 시스템 재시도·AI provider 장애·코드 수정 작업은 작업함 숫자에 포함하지 않는다. 인증 만료처럼 사용자가 실제로 해결해야 하는 권한 문제만 구체적인 사용자 작업으로 등록한다.

## 4. 취소·환불 사례의 구체적인 UX 계약

예: 2026-07-11 트립닷컴 119,965원 거래에서 사용자가 “예약을 취소했다”고 확인한 경우.

예약 취소와 카드 환불은 다른 사실이다. 기존 체크박스 “자료 확인을 마쳤으며 보류를 해제하고 이 금액을 기록합니다”는 삭제한다.

작업함은 다음 사실을 분리해 보여준다.

| 사실 | 확인 근거 | 처리 |
| --- | --- | --- |
| 예약 취소 | 사용자 답변 또는 취소 메일 | 예약 상태만 취소로 저장 |
| 원결제 카드 거래 | 카드 원행 | 원금·거래 ID 보존 |
| 카드 환불 전표 | 실제 카드 취소/환불 원행 | 발견되면 원결제와 연결하고 부분/전액 순액 계산 |
| 실제 환불 수령 | 카드 원행 또는 사용자가 답할 수 있는 실제 수령 사실 | 확인되지 않았으면 환불 완료로 표시하지 않음 |
| COST 내부 기록 | 기존 금융 preview/commit 및 중복 방지 | 검증된 순액·비용 성격으로만 기록 |
| Google 최종 장부 | 사용자 직접 반영 | 자동 쓰지 않고 필요한 경우 여행/기간 단위 복사 작업 제공 |

환불 원행이 아직 없고 실제 수령 여부가 회계 처리에 필요한 경우에만 작업함에 **“카드 환불 119,965원이 실제 반영됐나요?”**처럼 정확히 질문한다. 사용자가 “아니오”라고 답하면 환불 완료를 만들지 않고 실제 지출 상태로 재처리한다. “예”라고 답해도 카드 원행을 창작하지 않으며 답변 출처를 사용자 확인으로 보존한다. 확인 불가이면 그 사실만 기록하고 추가로 필요한 자료를 구체적으로 요청한다.

환불 원행이 나중에 들어오면 기존 작업을 자동 재평가하고, 별도 사용자의 보류 해제 없이 해결되면 작업함에서 제거한다. 취소 메일·예약 취소만으로 원결제 금액을 0원으로 만들거나 일반 숙박비로 확정하지 않는다.

## 5. 데이터·API·상태 계약

### 5.1 작업은 거래 상태와 분리

거래의 업무 상태와 사용자 작업은 같은 필드로 표현하지 않는다.

- 거래 분류/기록 상태: 기존 처리 필요 / 완료 / 제외 및 내부 분류·기록 사실을 보존한다.
- 처리 출처: 자동 / 코드 추론 / AI 추론 / 직접을 보존한다.
- 사용자 작업: 별도 action task의 존재와 lifecycle로 표현한다.
- 내부 안전 잠금: 원본 hash·거래 ID·금융 사유에 묶인 시스템 보호로 표현하며 사용자 작업 상태나 사용자 해제 기능으로 사용하지 않는다.

사용자에게 “보류”라는 상태·사유·필터를 보여주지 않는다. 기존 DB의 manual_hold, evidence_pending, refund_pending 같은 값은 내부 호환·안전 잠금으로만 남길 수 있다. 구현 시 표시 문자열·API DTO·필터·카운트·작업함 집계가 이 내부 값을 직접 노출하지 않도록 한다.

### 5.2 통합 작업 식별과 멱등성

- 작업은 안정적인 action_id와 action_group_key를 가진다.
- action_group_key는 실제 사용자 판단의 루트(원결제/환불 그룹, 카드 거래+예약, 영수증+거래 등)를 기준으로 한다.
- 같은 원인·같은 답변을 여러 화면에서 각각 등록하지 않는다. 같은 group key가 다시 들어오면 기존 작업의 근거·revision·질문을 갱신한다.
- 한 그룹에 서로 독립적인 두 가지 인간 판단이 필요한 경우에만 별도 task를 허용한다.
- 각 작업에는 source references, source digest/revision, reason code, 질문 schema, evidence summary, 추천안, 사용자 답변 출처, 생성·갱신 시각을 최소 저장한다.
- 사용자 답변은 전역 규칙으로 승격하지 않는다. 사용자가 별도로 규칙 저장을 선택한 경우에만 기존 규칙 승인 절차를 따른다.

### 5.3 작업 lifecycle

| 내부 상태 | 의미 | 사용자 화면 |
| --- | --- | --- |
| OPEN | 사용자 답변/자료가 실제로 필요함 | 내 확인 필요에 표시 |
| ANSWERED | 답변 저장, 재검토 요청됨 | 즉시 “답변 저장 · 자동 재검토 중”으로 피드백 |
| REPROCESSING | P1/P2 재실행 중 | 별도 대기열로 표시하지 않음 |
| RESOLVED | 근거·정책 검증 후 완료 | 기본 목록에서 제거 |
| SUPERSEDED | 새 원본/새 작업으로 대체 | 기본 목록에서 제거, 이력 유지 |
| SYSTEM_RETRY / SYSTEM_BLOCKED | provider·코드·기술 실행 문제 | 사용자에게 조치가 없으면 숨김. 실제 사용자 권한/자료가 필요한 경우만 OPEN 작업 생성 |

OPEN 외 상태는 사용자 작업함의 열린 작업 건수에 포함하지 않는다. 시스템 오류를 사용자 답변으로 위장하지 않는다.

### 5.4 기존 안전 보호

- 기존 transaction_review_holds 데이터와 source hash 검증을 보존한다.
- 기존 수동 교정·사용자 결정·원본 오류·중복·초과 환불·불완전 환불 묶음·회사 경비 제외·원자 기록 보호를 유지한다.
- 내부 잠금은 자동 검증 조건이 충족될 때만 코드 경로에서 해소한다. 단순히 답변이 저장됐다는 이유로 지우지 않는다.
- 작업함 GET은 읽기 전용이다. 답변 POST만 CSRF·owner 권한·action ID·revision/digest를 검증하고 저장한다.
- 원본/금액/ID·Google 최종 장부 자동 쓰기 금지와 외부 모델 전송 경계는 기존 금융 명세를 따른다.
- 첫 구현은 기존 저장 구조와 요청 테이블을 우선 재사용한다. 스키마 변경이 꼭 필요하다는 증거가 있을 때만 별도 마이그레이션·복구 계획을 제시한다. 기존 보호 이력을 일괄 삭제하거나 재작성하지 않는다.

## 6. 기존 화면별 통합 원칙

| 기존 화면/도메인 | 새 역할 |
| --- | --- |
| /import 지출 정리 | 카드 업로드·자동 처리 결과·거래 상세 근거를 보는 작업 공간. 사용자 작업함의 별도 대기열이 되지 않음 |
| /cards/all 및 카드 상세 | 전체 원행·기간 조회. 사람이 답할 작업이 있으면 동일 action_id로 내 확인 필요에 연결 |
| OTA 예약 검토 | 예약 근거·연결 상세. 사람 판단이 필요한 경우 같은 작업 카드의 근거 탭으로 연결 |
| 환불/취소 정산 | 원결제·환불 그룹 상세. 동일 그룹에 대해 별도 보류 목록이나 중복 사용자 작업을 만들지 않음 |
| /receipts | 영수증 원본과 추출 필드 수정. 누락된 필수 정보가 있을 때 같은 통합 작업에 자료를 제출 |
| /review | 실제 원본 대조와 검토 근거. 별도 사용자 작업함으로 사용하지 않음 |
| /reserve-links 및 여행 귀속 | 여행·예약 관계의 상세 편집. 지출 귀속 판단에 필수인 건만 통합 작업으로 노출 |
| Google 장부·지출 복사 | 읽기 대조·복사 준비. 최종 반영은 계속 사용자 수행; 복사할 묶음이 실제로 있을 때만 그룹 작업 제공 |
| 참가자·항공권 | 지출 귀속에 직접 영향을 주는 명단/탑승 사실만 통합 작업으로 연결. 일반 보험/참가자 운영은 제외 |

어느 화면에서 답변하더라도 동일 작업 서비스에 저장되어야 한다. 화면별 별도 답변 DB·별도 카운트·별도 완료 기준을 만들지 않는다.

## 7. 구현 단계와 단일 에이전트 책임

한 주 에이전트가 조사부터 PR·검증·안전한 배포 수락까지 소유한다. 하위 에이전트는 독립 검토·테스트에만 사용할 수 있다. 동일 DB·호스트·동일 파일의 작성자는 하나로 제한한다.

1. **DISCOVER:** 최신 main, 열린 PR, 기존 변경·파일 소유권, 실제 라우트, 기존 작업/보호 테이블, 모든 사용자 조작·카운트·답변 저장 경로를 조사한다. 이 문서와 finance.md, autonomous-expense-cleanup, status-and-inference-stages, 기존 카드/OTA/환불/영수증 명세를 함께 읽는다.
2. **MAP:** 각 도메인의 인간 작업 발생 조건, 원본 ID, 중복 키, 답변 API, 상세 경로를 표로 만든다. 실제 사용자 작업이 아닌 내부 재시도·시스템 오류를 분리한다.
3. **DESIGN/IMPLEMENT:** 통합 action task 서비스와 source adapters를 만든다. 단일 action_group_key, 작업 생성·갱신·답변·재평가·완료·대체를 구현한다. 기존 P1/P2 worker와 연결하되 두 번째 병렬 작업 엔진을 만들지 않는다.
4. **REMOVE HOLD UX:** 보류 메뉴/필터/카운트/문구/체크박스/해제 API의 사용자 진입점을 제거한다. 내부 금융 보호 데이터와 원자성 검증은 그대로 유지한다. 각 기존 화면의 미결 동선은 통합 작업함 링크로 연결한다.
5. **AUTOMATE:** 모든 신규 카드 원행의 P1 평가와 필요한 P2 전수 근거 검토를 보장한다. 새 예약·환불·영수증 근거가 들어오면 관련 작업을 자동 재평가한다. provider 실패·코드 결함은 내부 retry/repair 루프로 처리한다.
6. **ANSWER/REPROCESS:** 작업함의 답변이 저장되면 자동으로 P1/P2를 재실행하고, 해결된 작업은 자동 종료한다. 수동 해제·완료 체크를 요구하지 않는다.
7. **VERIFY:** 합성 DB·익명 fixture·브라우저로 모든 도메인의 작업 생성·병합·답변·재평가·중복 방지와 금융 보호를 검증한다. 320/390/760/1024/1440px, 키보드·스크린리더, 라이트/다크, 동시 답변·stale revision을 포함한다.
8. **DELIVER:** 영향 기반 QA, 실제 diff review, CI, PR, 정상 main 병합과 기존 승인된 코드 배포 게이트를 수행한다. 운영 AI 성공·사용자 작업 감소·금융 실제 처리·Google 반영은 각각 관측된 근거가 있을 때만 완료로 보고한다.

문서 작성이나 합성 테스트만으로 실제 운영 무인 처리가 완료됐다고 표시하지 않는다. 기존 AI provider timeout·실제 P2 적용 0건이라는 운영 제한은 별도 최신 증거로 재검증한다.

## 8. 필수 수락 테스트

| 시나리오 | 기대 결과 |
| --- | --- |
| 정상 카드 신규 업로드 | 모든 원행이 P1 검사되고 해결 가능한 건은 자동 분류·배정·내부 처리. 사용자 작업 0 |
| 낮은 추론 신뢰도지만 유효한 최선 여행이 있음 | 근거·불확실성을 남기고 자동 배정. 사용자 질문 생성 안 함 |
| 취소 예약 메일만 있고 카드 환불 원행 없음 | 예약 취소와 환불 상태를 분리. 순액 0원/환불 완료를 만들지 않음 |
| 원결제+복수 부분환불 | 하나의 그룹으로 대조·집계. 실제 미확인 사실만 한 작업으로 질문 |
| 원본 충돌이 반복되고 코드 결함임 | 원인 묶음→합성 재현→회귀 테스트→코드 수정 PR/CI→허용 배포→영향 거래 재평가. 사용자에게 같은 건을 반복 질문하지 않음 |
| provider timeout/한도 도달 | 내부 재시도·기술 진단. 사용자가 해결할 권한/자료가 없다면 작업함에 표시하지 않음 |
| 영수증에 금액·날짜가 있음 | 자동 추출·대조. 필수 필드가 실제로 없을 때만 해당 필드 하나를 질문 |
| 동일 거래가 카드·OTA·환불·영수증에 모두 등장 | 하나의 action_group_key, 사용자 작업 1건. 모든 화면에서 같은 task 링크 |
| 사용자 답변 저장 | source revision 검증 후 P1/P2 자동 재실행. 해결 시 작업함에서 사라지고 수동 해제 버튼 없음 |
| 답변 후 원본이 갱신됨 | stale 답변 적용 거부, 새 근거로 재평가, 기존 답변을 반복 질문하지 않음 |
| Google 최종 장부 반영 필요 | 여행/기간 단위 복사 작업으로 모으고 COST가 Google에 자동 쓰지 않음 |
| 기존 사용자 수동 결정·환불·중복·원본 충돌 | 자동화가 덮어쓰지 않음. 내부 안전 잠금과 감사 이력 유지 |
| 기존 모든 화면 | 별도 보류/미결 대기열이 없고 필요한 사용자 작업은 같은 통합 작업함에서 확인·답변 가능 |
| 사용자 작업 0건 | “모두 완료”를 실제 검사 범위에 맞게 표시. 내부 retry나 기술 backlog를 사용자 작업 0건과 혼동하지 않음 |

### 완료 정의

- [ ] 신규 카드 원행 전체가 자동 파이프라인을 통과한다.
- [ ] P1/P2가 해결 가능한 거래를 처리하고 같은 근거 버전의 반복 질문을 만들지 않는다.
- [ ] 사람만 답할 수 있는 고유 판단만 통합 작업함에 남는다.
- [ ] 관련 도메인 화면에 분산된 인간 작업 목록과 중복 카운트가 제거된다.
- [ ] 사용자 보류 UI·보류 해제 동작·보류 전용 필터가 전부 사라진다.
- [ ] 내부 금융 안전 잠금·원본/금액/ID/환불/수동 결정 보호는 유지된다.
- [ ] 답변 저장 후 자동 재처리·자동 완료·stale revision 보호가 검증된다.
- [ ] provider 실패·반복 코드 결함의 내부 복구 경로가 검증된다.
- [ ] Google 최종 장부 자동 쓰기 0, 허위 환불/기록 완료 0.
- [ ] 실제 운영 화면·작업함 집계·무인 P2 호출·사용자 작업 감소를 각각 별도 근거로 수락한다.

## 9. 구현 에이전트 시작 지시

> COST의 통합 사용자 확인함과 자동 지출 처리 파이프라인을 이 문서대로 끝까지 구현하라. 먼저 현재 main·열린 PR·기존 변경을 보존하고 AGENTS.md와 연결 명세를 읽어 전체 카드/환불/OTA/영수증/여행/Google 지출 흐름 및 모든 사용자 작업 발생 경로를 조사하라. 신규 카드 원행 전체에 P1을 실행하고 P1으로 해결되지 않은 항목은 기존 연결 에이전트 P2가 근거를 대조하도록 하라. 사람만 답할 수 있는 항목은 안정적인 action_group_key로 중복 없이 단일 내 확인 필요 작업함에 모아라. 기존 /import·OTA·환불·영수증·예약 연결·실제 검토·Google 화면의 별도 미결/보류 목록과 사용자 보류 해제 UI를 제거하고 같은 task로 연결하라. transaction_review_holds 등 기존 보호 데이터는 삭제하지 말고 내부 금융 안전 잠금으로만 유지하며 근거·revision 검증을 통과한 코드 경로에서만 해소하라. 사용자가 답하면 별도 해제/완료 버튼 없이 P1/P2를 자동 재실행하라. provider 장애와 코드 결함은 내부 retry 및 재현→회귀 테스트→PR/CI→허용 배포→재평가로 처리하라. Google 최종 장부 자동 쓰기, 원본/금액/ID/사용자 결정/환불 보호 약화는 금지한다. 합성 브라우저·영향 기반 테스트·CI·PR·기존 안전 배포 게이트까지 수행하고 실제 운영 수락 근거와 미검증 항목을 구분해 보고하라. 명세만 읽거나 계획만 제시하고 멈추지 말라.
