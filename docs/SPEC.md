# COST 통합 명세

> **상태:** 정본 (2026-11-10 승인, 2026-11-11 P2 대상·일괄 실행·조직 결정 반영, 2026-11-13 분기 검수의 AI 검수자 위임 반영). 실제 완료 범위는 현재 상태와 작업판을 따른다.
> **이 문서가 하는 일:** COST가 무엇을 하는 시스템인지, 어떤 순서로 무엇을 만들지, 무엇을 지켜야 하는지를 한 곳에 적는다. 과거 명세 112개(`docs/history/specs-20261110/`)와 `docs/history/`의 나머지는 **근거 기록**이며 실행 지시가 아니다. 과거 명세와 이 문서가 다르면 이 문서가 우선한다.
> **짝 문서:** 판정 규칙은 [판정 규칙집](DECISION_POLICY.md), 개발 조직 운영은 [중간 관리자 지침](agents/MANAGER.md), 반복 작업 절차는 [절차서](playbooks/README.md)에 둔다.

## 1. 목적과 성공 기준

### 1.1 목적

여행에 따르는 지출 자료(카드 명세, OTA 메일·포털, 영수증)를 모두 받아 **코드가 먼저 대사·분류하고(P1), 코드가 못 정한 것은 AI가 정한다(P2). 분기마다 AI 검수자가 판정을 다시 보고 교정한다.** 사용자는 처리 흐름 중간에 질문을 받지 않고 건별 판단도 하지 않는다.

### 1.2 사용자의 역할 — 결과 확인과 Google 붙여넣기

- 사용자는 여행사에서 가이드 업무를 뺀 실무 전체를 맡는 결정권자이며 코드를 직접 읽지 않는다.
- **분기 검수의 판단과 교정은 AI 검수자가 한다**(소유자 결정 2026-11-13). 검수자는 Fable 5.2 high 에이전트이며, 쓸 수 없으면 그때의 최상위 Claude 모델이 대신한다. 사용자는 결과를 받아 볼 뿐 건별 판단을 하지 않는다. "먼저 볼 50건" 같은 건별 검토 목록을 사용자에게 주지 않는다(§8).
- 사용자에게 남는 일은 셋뿐이다.
  1. **Google 지출표 붙여넣기.** 검수가 끝난 장부를 기존 복사 기능으로 붙여넣는다. Google 장부에 자동으로 쓰지 않는다.
  2. **로그인·인증 인계.** 카드사 추가 인증, OTA 포털 재로그인은 판정 질문이 아니라 인증 인계다. 수집 스크립트가 로그인 만료를 감지하면 멈추고 상태만 표시한다(§7).
  3. **정책 수준의 새 결정.** 규칙이 없거나 규칙끼리 모순이거나 사업 판단이 필요한 때만, 건별이 아니라 질문 단위로 예시와 함께 받는다. 0건이 목표다.
- 처리 흐름 안에는 **사용자 확인 단계(P3)가 없다.** 질문함·확인 대기·보류 해제 같은 화면과 상태를 만들지 않는다. 판정이 어려운 건도 AI가 근거와 불확실성을 적고 판정을 끝낸다.
- AI 검수자의 교정은 [판정 규칙집](DECISION_POLICY.md) 개정으로 환류한다. **같은 원인의 교정을 두 번 하지 않는 것**이 이 시스템의 품질 기준이다(§8).
- 사용자가 직접 고친 값(수동 교정)은 여전히 모든 자동 판정과 AI 검수 교정보다 우선한다. AI 검수 교정을 사용자 결정으로 기록하지 않는다.
- 영수증 사진 판독 결과는 사용자 요청(2026-11-16)에 따라 원본과 나란히 검수하고 선택한 내역만 COST 장부에 반영한다(§7.1, RCPT-031). 이 등록 전 검수는 카드 자동 판정·분기 AI 검수와 별개다.
- 대체된 옛 내용(2026-11-10~13): 사용자가 분기마다 한 번 최종 검수를 하면서 틀린 판정을 직접 교정했다.

### 1.3 사용자가 받아볼 산출물

1. **여행별 손익** — 여행마다 수입과 지출이 맞춰진 수치.
2. **세무·증빙 자료** — 세무 처리에 넘길 수 있게 정리된 카드·영수증 자료.
3. **직원·가이드 지출 정산** — 직원과 가이드가 쓴 비용의 확인과 정산 자료.

현재 구현 상태와 정의가 비어 있는 부분은 §9에 적는다.

### 1.4 성공 기준

| 구분 | 지표 | 뜻 |
| --- | --- | --- |
| 업무(1순위) | AI 검수자가 고친 건수와 사유별 분포 | 분기 검수에서 AI 검수자가 실제로 고친 건수를 사유(판정 주체·원인)별로 센다. 분기마다 줄어야 한다. 옛 지표 "사용자가 고친 건수와 소요 시간"을 대체한다(2026-11-13) |
| 업무 | 사용자 결정 필요 질문 수 | 분기 검수가 사용자에게 넘긴 정책 질문 수. 0이 목표다 |
| 업무 | 여행 종료 후 손익 수치가 나오기까지 걸린 날 | 지출 판정이 밀리지 않는지 |
| 업무 | 산출물 3종의 준비 상태 | 분기 말에 바로 쓸 수 있는지 |
| 내부(수단) | 판정이 없는 정상 거래 수 | 0이어야 한다 |
| 내부 | P1 처리율, P2 처리율 | P1은 늘고 P2는 줄어야 한다 |
| 내부 | P2 실행 성공률 | 기술적으로 끝까지 도는 비율 |
| 내부 | 수집 지연 | 원천별 마지막 수집일과 오늘의 차이 |

내부 지표가 좋아도 업무 지표가 나쁘면 실패다.

### 1.5 하지 않는 것

- Google 최종 장부에 자동으로 쓰지 않는다. 붙여넣기는 분기 검수가 끝난 뒤 사용자가 한다.
- 사용자의 수동 교정을 자동 판정이 덮지 않는다.
- 카드 원문·금액·ID, 메일 원문, 영수증 원본을 바꾸거나 지우지 않는다.
- 여행을 만들어내지 않는다. 여행은 Google 시트 탭에서만 생긴다.
- 실제 환급 입금이나 Google 반영 사실을 추론으로 만들어내지 않는다.

## 2. 처리 원칙

| 용어 | 뜻 |
| --- | --- |
| P1 | 코드와 데이터형 규칙이 내는 판정. 같은 입력에 항상 같은 결과 |
| P2 | AI 에이전트가 내는 판정. P1이 못 정했거나 약하게 정한 건만 맡는다 |
| 판정 | 지출 1건에 대한 결론: 어느 여행(또는 분기 기타비용)의 어떤 항목인지, 이용기간, 연결된 근거, 누가 정했는지, 근거 문장, 불확실성 |
| 근거 | 판정에 쓴 원천 자료: 카드 원행, 메일 원문, 포털 조회 결과, 영수증, Google 여행 탭 |
| 교정 | 판정을 고치는 것. **수동 교정**은 사용자가 직접 고친 것으로 항상 최우선이다. **AI 검수 교정**은 분기 검수에서 AI 검수자가 고친 것으로, 수동 교정과 금융 보호를 덮지 못한다 |
| 분기 기타비용 | 실제 여행에 귀속할 수 없는 일반 비용의 종착지. 결제일 기준 분기로 나눈다 |

1. **P1을 최대한 늘리고 P2는 줄인다.** P2는 사용자 확인의 대체물이다. P2가 같은 유형을 반복 판정하면 P1 규칙으로 올린다(§6.7).
2. **P2를 0으로 만드는 것은 목표가 아니다.** 한두 번 나오는 사례까지 규칙으로 만들면 공급자별·증상별 패치 반복으로 돌아간다.
3. **모든 정상 거래는 판정을 갖는다.** 근거가 부족하면 최선의 판정과 불확실성을 적는다. "분류 대기"로 남기지 않는다.
4. **판정은 저장된 값이다.** 화면이 그릴 때마다 추론하지 않는다. 화면은 저장된 판정을 읽기만 한다.
5. **증상별 패치를 하지 않는다.** 새 공급자·새 메일 양식을 파서 패치로 쫓지 않고, P2가 원문을 읽어 판정한 뒤 반복되는 것만 규칙·데이터로 올린다.
6. **규칙은 한 곳에만 쓴다.** 판정 규칙의 정본은 [판정 규칙집](DECISION_POLICY.md)이다. 새 지시는 대화로 흘려보내지 않고 규칙집 개정으로 반영한다.

## 3. 현재 상태 (2026-11-10 실측)

기준선 수치·실패 원인·당시 구성은 현재 요구사항이 아닌 **과거 실측**이다. 현재 완료 범위와 운영 SHA는 [현재 상태](session_handoff.md), 실제 배포·복구 근거는 [운영 기록](operations.md), 단계별 작업은 [작업판](agents/BOARD.md)을 따른다.

2026-11-10 기준선과 원래 실측 표는 [개편 전 명세의 §3](https://github.com/6Soo/cost/blob/c0c45c7fa9cdb291d198d5c3e9667801abb6721d/docs/SPEC.md#3-현재-상태-2026-11-10-실측)에 보존한다. 과거 수치를 운영 현재값으로 사용하지 않는다.

### 3.1 규모

기준선 실측은 위에 연결한 당시 명세를 참조한다.

### 3.2 구조

현 구조와 운영 전환은 [현재 상태](session_handoff.md)와 [코어 안내](../core/README.md)를 참조한다.

### 3.3 목표가 달성되지 않은 원인

과거 원인 분석은 이전 명세에 보존하며 현재의 개선 범위는 [작업판](agents/BOARD.md)을 따른다.

## 4. 판정 모델

### 4.1 판정 한 건의 내용

| 항목 | 내용 |
| --- | --- |
| 대상 | 카드 거래 1건(또는 영수증 1건, 캐시·포인트 사용 1건) |
| 귀속 | 실제 여행 하나, 또는 결제일 기준 분기 기타비용, 또는 전액 환불 쌍 |
| 항목 | 숙박비·항공료·식비 등 비용 항목 |
| 이용기간 | 실제 서비스 이용일(숙박 기간, 탑승일 등). 모르면 비워 두고 그 사실을 적는다 |
| 연결된 근거 | 판정에 쓴 예약·메일·포털 기록·다른 카드 거래의 참조 |
| 판정 주체 | P1(규칙 ID) / P2(실행 ID·모델) / AI 검수(검수 실행 ID·모델) / 수동 교정 |
| 근거 문장 | 왜 이렇게 정했는지 한두 문장 |
| 불확실성 | 확인하지 못한 것 |

### 4.2 판정 주체의 우선순위

수동 교정 > 정확 근거에 의한 P1(예약번호·원승인번호 등) > AI 검수 교정 > P2 > 추론에 의한 P1(업종·날짜 기반 최선 후보).

- P2는 추론에 의한 P1을 고칠 수 있다. 정확 근거에 의한 P1과 수동 교정은 고칠 수 없다.
- AI 검수자는 P2와 추론에 의한 P1을 고칠 수 있다. 수동 교정과 금융 보호는 덮지 않는다. 정확 근거 P1이 틀려 보이면 판정을 덮지 않고 원인(근거 연결·규칙·코드)을 고칠 일로 올린다.
- 낮은 신뢰도는 판정을 미완료로 만들지 않는다. 근거와 불확실성으로만 표시한다.

### 4.3 현 시스템에서의 저장 위치 (M2까지)

새 테이블을 만들지 않고 기존 열을 쓴다.

| 판정 항목 | 저장 위치 |
| --- | --- |
| 귀속·항목 | `transactions.trip_id`, `display_tab_id`, `item` |
| 판정 주체 | `transactions.classification_source` (`ai_inference`가 P2와 AI 검수. AI 검수는 근거 문장과 실행 기록에 `AI 검수`·모델을 적어 구분한다. 사용자 결정 표기 `user_decision`을 쓰지 않는다) |
| 근거 문장·불확실성 | `transactions.classification_basis` |
| P2 실행 기록 | 서버 밖 일괄 작업의 보호 경로에 요청 지문·실행 ID·모델·제안 JSONL·집계. 기존 Board 내장 런타임은 비활성 |
| 교정 이력 | `app/classification_correction.py`가 남기는 변경 전 값과 근거 |

투자 단계(§11)에서 `decisions` 단일 테이블로 옮긴다.

## 5. 파이프라인

```
수집 → 추출 → 연결 → 귀속 → 게시
```

| 단계 | 하는 일 | P1 (현재 코드) | P2가 맡는 것 |
| --- | --- | --- | --- |
| 수집 | 카드 명세, OTA 메일, OTA 포털, 영수증, Google 여행 탭을 원본 그대로 받는다 | `app/import_card.py`, `app/mail_collect.py`, `app/ota_portal.py`, `app/agoda_capture.py`, `app/google_authority.py` | 없음 (스크립트, §7) |
| 추출 | 원본에서 날짜·금액·예약번호·이용기간을 읽는다 | `app/ota_mail.py`, `app/flight_evidence.py`, `app/import_card.py` | 파서가 못 읽은 메일을 원문에서 직접 읽는다 |
| 연결 | OTA 예약↔카드 결제(M:N), 취소·환불↔원결제 | `app/ota_payments.py`, `app/partial_refund.py`, `app/ota_inference.py` | 연결 근거를 판정의 근거로 제시한다. 정확 연결·환불 짝은 P1만 쓴다 |
| 귀속 | 여행·항목·이용기간을 정한다 | `app/classify.py`, `app/rules.py`, `app/automatic_classification.py`, `app/reconciliation.py` | P1이 못 정했거나 일반 항목으로만 정한 건을 판정한다 |
| 게시 | 판정을 저장하고 화면·내보내기에 반영한다 | `app/ledger.py`, `app/classification_correction.py` | 없음 |

- 각 단계에서 P1을 먼저 돌리고 남은 것만 P2로 보낸다.
- 금액·부호·원승인 관계·환불 짝·새 장부 기록은 P1만 쓴다. P2는 귀속·항목·이용기간과 그 근거를 제안하고, 승인 후 열린 분기의 기존 내부 기록을 교정할 수 있다(§6.4).

## 6. 서버 밖 P2 일괄 판정

P1이 못 정하거나 포괄적으로만 정한 항목을 P2가 근거와 불확실성을 함께 판정한다. 상세 실행·중단·재개 명령은 [P2 1층](../tools/p2_batch/README.md), [P2 2층](../tools/p2_layer2/README.md), 판정 기준은 [규칙집](DECISION_POLICY.md)과 [처리 규칙](policy/process.md)을 따른다. 실제 운영 실행 방식은 [현재 상태](session_handoff.md)에서 확인한다.

### 6.1 실행 위치와 두 층

- 1층: 가맹점 30~50곳씩 항목 분류(원문·정규화명, 있는 업종·국가·통화, 규칙·예외). 사람 이름·카드번호·예약번호를 입력에 넣지 않고 확신이 낮거나 근거가 부족하면 기존 항목을 유지한다.
- 2층: 이용기간 미확인과 OTA·항공 추론 대상의 예약·카드 근거를 읽어 여행·항목·이용기간을 판정한다. 정확 금융 연결과 수동 결정은 덮지 않는다.
- 서버 밖 격리 실행을 원칙으로 하며 운영 DB는 짧게 읽기 전용으로 조회한다. Board 내장 구형 P2의 실제 활성 여부를 문서만으로 단정하지 말고 운영 설정으로 확인한다.

### 6.2 2층 근거와 입력 예산

건당 목표 약 15,000토큰, 상한 30,000토큰. 관련도 높은 발췌 3~5개를 선별하고 메일의 제목·발신·날짜·금액·예약번호·이용기간·취소 문구를 보존한다. 원문이 잘렸으면 표시하고 추정으로 채우지 않는다. 근거·입출력·변경 전 값은 Git 밖의 보호 경로에 둔다.

### 6.3 도구 없는 실행

승인된 구독 모델만 도구 없는 제한 실행으로 사용한다. 파일·셸·네트워크·추가 에이전트 호출을 막고 도구 이벤트가 나오면 결과를 거부한다. 시간·사용량 한도를 적용하며 장애 시 진행 상태를 보존해 중단한다. 도구 차단과 OS 수준 완전 격리를 혼동하지 않는다. 고객 원문의 외부 전달 범위는 §13 및 PROC-012를 따른다.

### 6.4 제안과 반영

1. 실행 ID·모델·요청 지문·원천 지문·revision·변경 전 판정과 함께 JSONL 제안을 보존한다.
2. 스키마·누락·중복·허용 항목·근거·도구 이벤트를 확인한 뒤 반영 시 원천·규칙·대상 신선도를 다시 검사한다.
3. Fable 승인 뒤 정식 교정 경로로만 열린 분기의 기존 기록을 수정하고, 장부·화면·교정 이력을 함께 유지한다. 제안이 곧 실제 적용은 아니다.
4. 수동 교정·정확 P1·금융 보호는 덮지 않으며 원문·금액·부호·ID·환불 짝·Google 최종 장부는 변경하지 않는다.

### 6.5 대상 — 카드일이 아니라 열린 분기 귀속

2026-06-30 포함 열린 여행 및 2026년 3분기 이후 분기 기타비용이 기본 범위다. 결제일이 과거라도 해당 열린 여행의 선결제면 포함한다. 이미 기록된 자동 판정은 교정할 수 있지만 수동 결정·완료 기간·금융 보호는 제외한다. 닫힌 분기의 의심 건은 자동 변경하지 않고 분기 검수로 넘긴다(REC-007·REC-008, PROC-072).

### 6.6 기록과 검증

호출·성공·실패·소요·토큰·영향 행·유지 비율을 집계한다. 읽지 못한 서버 메모리 근거를 읽었다고 보고하지 않는다. 합성/실호출, 제안/적용, 검증/배포를 분리 기록한다. 미리보기에서 보호가 걸리면 우회하지 않고 멈춘다.

### 6.7 P1 승격과 표본 감사

반복적으로 검증된 P2 항목 결정은 사용자 예외·국가·기간·상품 범위를 보존한 채 승인 후 데이터 규칙으로 승격한다. 단건을 무조건 규칙으로 확대하지 않는다. 반복 유형 5건 이상·분기 검수 교정 0건은 제안 기준이며 최종 수락과 표본 비율은 검수 결과를 따른다.

### 6.8 단계와 멈춤

대상·보호 현황을 읽기 전용으로 집계 → 제안·표본 검증 → 별도 승인된 정식 반영 순이다. 새 단계에 이전 승인 범위를 자동 연장하지 않는다.

### 6.9 2026-11-12 실행 결론

2026-11-12의 1층 반영·2층 시도, 수치 정정과 중단 사유는 [이전 명세의 실행 기록](https://github.com/6Soo/cost/blob/c0c45c7fa9cdb291d198d5c3e9667801abb6721d/docs/SPEC.md#69-2026-11-12-실행-결론) 및 [운영 기록](operations.md)에서 확인한다. 옛 실행 결과를 현재 실행 지시로 재사용하지 않는다.

## 7. 수집 스크립트

절차가 정해진 수집은 스크립트가 수행한다. 수집과 가져오기 이후의 대사·분류는 판정 파이프라인이 맡는다. 원천별 조회·재시도·인증 방법은 [카드 수집](playbooks/card-downloads.md), [카드 로그인](playbooks/card-login-automation.md), [OTA 포털](playbooks/ota-portal-collection.md)과 [수집 규칙](policy/source.md)을 따른다.

- Gmail·OTA 메일, 카드 명세, OTA 포털, Google 여행 탭·수입은 원본과 출처를 보존한다. OTA 포털은 조회만 하고 예약·결제를 변경하지 않는다.
- 인증 만료 시 승인된 로그인 시도를 한 뒤 추가 인증·실패 시 멈추고 **로그인 필요** 상태를 알린다. 자격 증명·OTP·토큰은 저장소와 로그에 남기지 않는다. 무인 수집 성공은 개별 원천의 라이브 검증으로 확인한다.
- Google 여행 탭은 사용자가 생성하고 Google 최종 지출표의 자동 쓰기는 금지한다.

### 7.1 영수증 — 로컬 Paseo 선택과 검수 후 반영

승인된 사진 입력 가능 구독 모델을 사용자가 선택하고, 관리 프롬프트로 원본을 판독한다. 웹페이지를 떠나도 작업과 결과가 유지되어야 하며, 복귀 후 **원본·판독 결과를 나란히 확인하고 선택한 내역만 한 번에 COST 장부에 반영**한다. 이 검수는 자동 카드 판정·분기 검수의 사용자 확인 단계가 아니다. 상세 계약은 [영수증 설계](design/receipt-paseo-workflow-20261116.md)와 RCPT-020·022·031, 실제 운영 상태는 [작업판](agents/BOARD.md)을 따른다.

## 8. 분기 검수와 교정 환류

분기 검수·교정은 AI 검수자가 수행한다. 사용자에게 거래별 판단을 요구하지 않고 Google 붙여넣기·인증 인계·정책 수준의 새 결정만 요청한다. 실행 절차는 [분기 검수 절차서](playbooks/quarter-review.md), 보호 규칙은 [규칙집](DECISION_POLICY.md)과 §13에 따른다.

1. AI 판정·최근 자동 변경·추론 귀속·포괄 항목 등 사유별 표본을 먼저 검증하고, 오류율이 높은 원인·가맹점·패턴은 전수 점검한다. 생략한 전수의 근거도 남긴다.
2. 반복 오류는 같은 규칙 ID를 개정해 P1과 P2에 환류하고 평가 사례로 재실행한다. 단건 예외를 범용 규칙으로 만들지 않는다.
3. 교정은 정식 인증 API 또는 미리보기·지문·백업/복원·감사 이력을 갖춘 유지보수 도구로만 한다. 직접 DB 쓰기와 수동·금융 보호 우회는 금지한다. AI 검수 교정은 사용자 결정으로 기록하지 않는다.
4. 보고에는 사유별 정답률, 교정 건수와 원인, 변경 규칙 ID, 검수 전후 수치, 정책 질문을 **비식별 집계**로 기록한다. 규칙 충돌·사업 판단만 질문 단위로 올린다.
5. 과거 Google 지출표는 참고자료이지 현재 거래의 확정 증빙이 아니다.

## 11. 투자 단계의 설계 원칙

M3 이후에 적용한다. 착수할 때 이 절을 상세 설계로 확장한다. M5·M6 착수 상세 설계는 [M5·M6 착수 설계](design/m5m6-kickoff-20261117.md)다(2026-11-17, M6 고정 기준 수락·M5 제공자 게이트 명시).

M3·M4·M5는 각 단계의 범위·보완 절차·종료 조건을 같은 절에서 관리한다. 단계 간 순서와 증거 기록 방식은 [§11.5](#115-m3m4m5-보완-명세)를 따른다.

### 11.1 Rust 새 코어 (M3, M6)

- 얻는 것: 판정 상태와 금액 규칙을 타입으로 강제해 에이전트가 만든 회귀를 테스트 전에 잡는다. 실행 파일 하나로 배포한다.
- M3 범위는 Rust 판정 모델·저장소·P1 규칙 엔진과 환불 짝·OTA 대사 연결이다. 전환은 판정 작성자, 연결 생산자 순이다. 전환기 수집·추출·P2 실행은 기존 Python 경로를 사용한다. 화면과 JSON 계약은 M4, 작업 큐와 P2 실행기 이관은 M5, Rust 추출기와 Python 퇴역은 M6에서 다룬다. React/TypeScript와 ego-browser 스크립트는 Rust 밖에 둔다.
- 데이터: 원천을 `evidence`(원문 보존) → `facts`(구조화 추출)로 통일하고 SQLite 하나에 테이블 약 25개로 줄인다(evidence, facts, payments, bookings, links, trips, decisions, decision_history, overrides, jobs, agent_runs, 부가 영역). 이관은 테이블 변환이 아니라 **보존된 원본을 새 파이프라인에 다시 넣는 방식**으로 하고, 기존 수동 교정은 overrides로 옮긴다.
- 순서: 착수 시 기존 Python 추출기를 보존 원본에 돌려 **기준 출력**을 만든다. Rust 추출기는 이 출력과 일치해야 병합된다. 전환기에는 Rust 코어가 Python 추출기를 하위 프로세스로 부르는 것을 허용하고, 기준을 통과한 것부터 교체한다.
- 드문 양식은 Rust 파서를 새로 쓰지 않고 P2와 데이터 규칙으로 흡수한다.
- 전제: 착수 당시 이 PC에 Rust 도구가 없어 설치 승인을 받았다. 검증은 `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`와 교정 사례 재실행을 포함한다. 운영 전환에는 신선 사본의 그림자 비교에서 목록 밖 차이 0, 기존 Python이 맞힌 사례의 Rust 회귀 0, 백업 복원·플래그 되돌림 예행을 적용한다. 그림자 비교와 저장된 `decisions`의 실제 완결성을 각각 확인한다. [코어 상세 설계](design/m3-core.md)

#### M3 · 저장 판정 완결성

1. **대상 진단.** 운영 Board·Worker의 적용 SHA와 Rust 판정·연결 설정을 확인한다. 동일 시점 Board·Core 복사본과 신선한 기간 근거로 읽기 전용 감사를 실행한다. 저장이 필요한 누락, 판정 변경 필요, 정책상 보호·보존, 원천·투영·기간 불일치를 각각 집계하고 중복 집계의 관계를 명시한다. 감사에서 집계한 수치는 실행 시점과 입력 사본의 근거 위치를 함께 기록한다. 화면 조회의 `missing_decision_count`는 화면 조회 진단으로 기록한다.
2. **저장 보완.** 화면 판정과 다시 계산한 판정이 일치하는 대상에만 기존 `decisions-only` 보완 경로를 적용한다. 신선 백업·격리 복원 → 복사본 보완 → 동일 입력 재실행 순서로 검증한다. 판정 변경이 필요한 건은 일반 판정·교정 경로의 정책과 보호 기준으로 별도 처리한다. 운영 반영은 [코어 전환 절차](playbooks/core-cutover.md)와 §12~13의 승인·중단·복원 조건을 적용한다.
3. **추출 기준 재현.** 공통 ID 기준 7,965건의 기준 출력은 입력 지문·사본·의존성·출력 지문을 연결해 재현한다. 기준 사본의 내용 지문이 기록되지 않은 경우 동일 입력 재검증은 불가로 기록한다(근거: [추출 기준 재현 증거](agents/artifacts/m3-extractor-repro-20261118.md)의 입력 사본·미검증 절). 새 캡처와 다른 490건은 출처 식별 필드 차이와 추출 내용 차이를 구분해 기록하고, 실제 데이터 재분류는 보호 세션에서 수행한다. 기존 입력을 재현할 수 없으면 그 사실과 영향 범위를 남기고, 기준 변경 여부는 별도 결정으로 남긴다.

**종료 조건.** 운영의 저장 대상 누락 0, 같은 입력으로 재실행 시 추가 보완 0, 설명되지 않은 원천·투영·기간 차이 0을 확인한다. 판정 변경 필요 건은 모두 정책 근거와 처리 결과를 기록한다. 보호된 거래·장부·수동 교정·Google 장부의 보존과 고정 추출 기준의 재현 근거를 함께 제출한다.

### 11.2 화면 (M4)

- Rust JSON API + React/TypeScript 컴포넌트 라이브러리.
- 디자인은 Claude Design에 맡긴다: 컴포넌트 라이브러리를 `/design-sync`로 동기화 → Claude Design에서 설계 → 에이전트가 구현 → 다시 동기화.
- 화면은 분기 검수(판정 열람·교정), 산출물 3종, 자동화 상태를 중심으로 한다. 정보구조는 [UI/UX 감사·재설계 명세](history/specs-20261110/uiux-full-audit-redesign-20261110.md) §5를 이어받는다.
- 부가 기능(수입·참가자 대조, 영수증 처리, Google 장부 비교·복사, 직원 계정·열람 권한)은 모두 새 구조로 옮긴다.
- 2026-11-15 UI/UX 전체 검수 결과는 [M4 화면 수락 기준](design/m4-ui-requirements.md)을 만족해야 한다.
- 2026-11-16 사용자 요청으로 [Plush UI 기반 전체 화면 설계](design/m4-plush-ui-20261116.md)를 구체화했다. PC 장부 업무 중심의 설계 초안이며, 이 문서 작성이 M4 구현·배포나 M3 운영 전환 승인을 뜻하지 않는다.
- 2026-11-16 후속 사용자 지시 “기존페이지에 적용해”: 운영 기본 주소 `/`와 기존 주요 업무 주소에서 Plush UI를 직접 제공한다. 별도 `/ui/` 주소를 알아야 하는 구조로 두지 않는다. 기존 쿼리·로그인·권한·API·작성 경로를 보존하고, 아직 React로 옮기지 않은 상세 교정은 명시적인 기존 화면 링크로 제공한다. 실제 반영 근거는 현재 상태·운영 기록을 따른다.

#### 11.2.1 장부 조회 통합

**상태:** 구현 위임 승인. 통합·검증·운영 상태는 [현재 상태](session_handoff.md)의 날짜별 기록을 따른다. [PR #975](https://github.com/6Soo/cost/pull/975)(`기존 기본·업무 주소에 Plush UI 적용`, head `c77eaa2b`, merge `d088e1cb`, main에 병합됨)에서 기존 기본·업무 주소가 Plush UI를 직접 제공하도록 합류했고, 기본 `/board`는 React로 바뀌었으며 상세·교정 호환 경로는 이전 HTML 화면에 남았다. 두 경로가 같은 장부 저장소를 읽으면서도 행 선택과 합계를 각각 계산해 환불 귀속, 이용기간, Google 대사 등에서 차이가 생겼다.

**사용자 결과.** 여행·분기 기타비용 장부의 기본 진입점은 기존 주소 `/board`다. 같은 자료 시점·권한·탭·필터에서 어느 링크로 들어가도 동일한 거래와 합계를 본다. 별도 장부 목록으로 이동하지 않고 기존 상세를 열거나 교정을 완료한 뒤 보고 있던 탭·검색·정렬·페이지로 돌아온다.

**조회 계약**

1. 권한 검증을 거친 서버 공통 조회가 표시 대상 행, 행별 ID·표시 귀속·날짜·항목·설명·부호 있는 원화 금액, 이용기간과 출처, Google 대사 상태, 화면 합계를 제공한다. React 목록·요약·상세와 남아 있는 호환 조회는 이 결과를 사용한다. 합계는 서버에서 같은 행 집합에 대해 계산하며 브라우저에서 다시 계산하지 않는다. 읽기 기준은 [판정 규칙집](DECISION_POLICY.md)과 기존 저장된 판정·사용자 교정이다. 이전 화면과 규칙집이 불일치하는 사례는 규칙집을 적용하고 차이를 검증 근거에 남긴다.
2. 전체 건수·합계는 권한·탭·수입/지출 종류를 적용한 뒤 검색과 페이지를 적용하기 전에 계산한다. 조회 건수·합계는 검색 적용 뒤 모든 페이지를 대상으로 계산한다. 여행 요약의 수입·지출·차액은 탭 전체 값이며 목록 필터로 바뀌지 않는다. 페이지·정렬은 행 순서와 노출 범위만 바꾸고, 동률에는 행 ID를 사용해 페이지 사이 중복·누락을 방지한다.
3. 여행·분기 기타비용·환불 탭의 표시 범위와 순액은 [환불 규칙](policy/refund.md)과 [항목 규칙](policy/item.md)의 RFND-021·RFND-022·ITEM-011을 적용한다. 환불 탭 귀속 거래는 일반 지출에 중복 노출·합산하지 않으며, 여행에 남는 부분환불은 원결제와 취소의 각 부호 및 순비용을 보존한다. Google 복사와 내보내기는 각 산출물의 기존 범위 계약을 유지한다. 특히 RFND-070에 따른 Google 붙여넣기와 화면의 행 범위 차이는 정상이다. 같은 대상·필터·산출물 종류라면 진입 경로가 달라도 산출물은 동일해야 한다.
4. 목록 또는 행 상세에서 기존에 확인할 수 있던 이용기간, 예약·증빙 근거, Google 대사 상태, Google 수입 원장의 검증 상태를 확인할 수 있다. 저장된 기간과 수동 교정을 기존 우선순위대로 읽고, 추론·미확인과 확정 값을 구별한다. Google 수입과 COST 수입은 [Google 규칙](policy/google.md)의 출처·대사 계약에 따라 표시하며 미검증 수입을 확정 차액에 포함하지 않는다. 원장 미연결·조회 실패·검증 미완료 상태에는 그 상태를 표시하고 금액 미확인을 0원으로 표시하지 않는다.

**적용 순서**

1. 승인된 배포본을 기준으로 두 조회 경로와 화면·산출물의 차이를 같은 입력으로 재현한다. 차이마다 규칙 ID 또는 기존 업무 계약과 기대값을 기록한다. 고객 원본과 행별 비교 자료는 보호 환경에 둔다.
2. 공통 서버 조회를 연결하고 목록·요약·상세의 필드 및 합계를 일치시킨다. 기존 `kind=in`·`kind=ex` 및 React의 `income`·`expense`를 같은 필터로 해석하고 기존 탭·검색·행 링크의 의미를 유지한다. 권한·마감·보관·수동 교정·동시 수정 검사는 기존 서버 경계를 사용한다. 조회 실패와 거래 없음 상태를 구별한다.
3. 수락 기준 충족 후 일반 목록용 `/board?...&legacy=1` 링크를 기본 장부로 연결한다. 기존 교정 폼 주소는 동일 역할·같은 행에서 계속 열리고 완료 또는 취소 후 기본 장부로 복귀한다. `legacy=1` 일괄 제거는 상세 조회·교정 진입이 모두 대체된 뒤에만 한다.

**수락 기준**

| 검사 | 통과 조건 |
| --- | --- |
| 거래·합계 대조 | 동일 스냅샷의 일반 여행·분기 기타비용·환불에 대해 두 조회 경로의 행 ID 집합, 행별 부호 있는 금액, 전체·조회 건수와 합계, 여행 수입·지출·차액 차이가 모두 0이다. 정책 기대값과도 일치한다. 50건을 넘는 표본은 모든 페이지를 합쳐 대조한다. |

### 11.3 서버와 보조 노드 (M5)

- 서버 역할: 화면, API, DB, 원문 저장, P1, 작업 큐. 보조 노드(로컬 PC): P2 실행, 로그인 세션이 필요한 수집. 같은 실행 파일의 두 실행 방식이다.
- 보조 노드는 서버로 **나가는 요청만** 한다. PC로 들어오는 터널을 두지 않는다.
- PC가 꺼져 있으면 화면·P1·웹 업로드는 계속 동작하고 P2와 브라우저 수집만 쌓인다.
- 원문을 포함해 전부 클라우드에 둔다(사용자 결정). 제공자에 묶이지 않게 실행 파일 하나 + SQLite 파일 하나 + 원문 폴더(또는 S3 호환 저장소)로 만들고, 제공자 전용 런타임에 맞춘 코드를 쓰지 않는다. 제공자는 이전 시점에 실제 요청량을 재고 고른다.
- 매일 클라우드 DB와 원문을 로컬 PC로 내려받아 보관한다.
- 제공자를 고르기 전에 고객 개인정보의 국외 이전·처리 위탁 고지 의무를 확인한다(§14).

#### M5 · 클라우드 전환과 보조 노드 운영

1. **제공자 비종속 구현.** 노드는 서버 HTTPS 연결로 작업을 임대하고 결과를 반환한다. 큐는 중복 키, 임대 소유자·만료, 다음 재시도 시각, 예산 키를 관리한다. 임대가 만료되면 재인수할 수 있고 이전 임대의 완료 통지는 거부한다. 실패 호출도 예산에 포함하며 P2 적체 중에도 P1은 먼저 게시한다. P2는 실제 승인 모델 실행과 재생 시험을 각각 검증하고, 결과의 입력 digest·형식·도구 이벤트를 공통 검증한다. 기존 인증 수집과 서버의 교정 반영 경계를 유지한다. 같은 릴리스에서 서버·노드·백업 복원을 격리 검증한다. 상세 계약 근거는 [M5·M6 착수 설계](design/m5m6-kickoff-20261117.md)다.
2. **이전 결정.** 요청량 계측으로 실제 용량과 운영 비용 범위를 산출하고 제공자별 원문 저장 위치·복구·이전 조건을 비교한다. 제공자·계약·과금·원문 이전은 사용자 결정과 §14의 조건을 충족한 뒤 수행한다. 그 전에는 합성 자료로 서버와 노드 검증을 진행한다.
3. **운영 전환.** 이전 전 보호된 스냅샷과 복원 결과를 검증한다. 승인된 클라우드에서 화면·API·웹 업로드·P1·작업 큐를 확인한다. 승인된 점검 창에서 보조 PC가 중단되면 화면·업로드·P1은 계속되고 P2·인증 수집은 큐에 남아야 한다. 재접속 뒤 남은 작업은 중복 반영 없이 이어져야 한다. 실제 스케줄로 생성된 일일 역방향 DB·원문 백업을 별도 경로에 복원해 무결성을 확인한다.

**종료 조건.** 클라우드 릴리스, PC 중단·복구 결과, 일일 역방향 백업·복원 기록을 모두 확인한다. 그 전에는 구현·합성 검증·운영 이전의 상태를 각각 기록한다.

### 11.4 P2 모델 교체 (선택)

- 세 층으로 본다: P1 / 무료 모델 + 절차서 / 프론티어 모델(상위 이관·표본 감사·절차서와 규칙 개정).
- 프론티어 모델이 반복 작업의 절차서를 `docs/playbooks/`에 남긴다. 절차가 고정되면 스크립트로 내리는 것이 먼저이고, 무료 모델은 그 사이 단계다.
- 교체는 작업 유형 단위로 한다. 무료 모델을 같은 작업에 나란히 돌려 프론티어 판정과의 일치율·형식 오류율·시간 초과율을 본 뒤 바꾸고, 검증 실패 건은 프론티어로 올린다.
- 판단이 필요한 드문 사례는 프론티어 모델에 남긴다. P2 물량이 월 100건 안팎이면 비용 절감 효과가 작으므로 우선순위가 낮다.
- 무료 모델에 고객 원문을 주는 것은 제공자의 데이터 이용 조건을 확인한 뒤 따로 승인받는다.

## 12. 개발 운영

### 12.1 증상별 패치 동결

- 2026-11-10부터 공급자별·증상별 파서 패치, 화면 문구·경고 수치를 쫓는 수정, 기록만을 위한 문서 PR을 하지 않는다. 같은 레포의 모든 세션에 적용한다.
- 예외: 운영 장애(접속 불가, 데이터 손상 위험, 수집 중단)와 이 문서의 로드맵 작업.
- 판정이 틀린 사례를 발견하면 코드를 고치지 말고 규칙집의 사례로 기록한다. M2 이후에는 P2가 처리한다.

### 12.2 조직

2026-11-11 결정: **담당 1명 + 최종 검수 1명**, Fable이 직접 지시·판단한다. 중간 관리자는 없다. 담당자는 재귀 위임하거나 별도 구현 작업자를 만들지 않는다.

- 담당자는 승인된 단계의 구현·실행·검증·기록을 맡는다. 최종 검수는 별도 `gpt-6.1-sol` medium 이상이 최종 SHA를 읽고 판정한다.
- [관리자 지침](agents/MANAGER.md)은 **병렬 작업자가 다시 생길 때까지 사용하지 않음**으로 보존한다.
- 고객 원문은 승인된 구독 프론티어 모델 P2 호출과 Qwen4 Max(QwenCloud) 작업자에게만 전달한다(PROC-012, 소유자 결정 2026-11-13, Codex 한도 동안의 개발·예행 작업 포함). Git·PR·일반 보고·무료 모델·Claude에 넣지 않는다. 사용자 의도와 재개 정보는 명세·규칙집·작업판에 남긴다.

### 12.3 통과 조건과 병합·배포

- 통과 조건은 실행 결과다: 바뀐 기능의 표적 테스트, 영향 기반 QA(`python tools/run_quality_checks.py --base origin/main --run`), 교정 사례 재실행(M2 이후). 작업자가 테스트를 고쳐 통과시키지 않는다.
- CI가 결제 한도로 시작되지 못하는 동안에는 `gpt-6.1-sol` medium 이상이 최종 SHA를 검수·승인한 PR만 병합한다. Codex가 한도로 막힌 동안은 구현자와 다른 Claude opus 세션의 독립 검수로 대체한다(소유자 결정 2026-11-13). 모델, 추론 수준, SHA, 판정을 PR에 기록한다. 실제 검사 실패는 이 예외로 통과시키지 않는다.
- 운영 배포는 단일 작성자가 `tools/deploy_verified_release.ps1`로 한다. `-PreviousSha`는 현재 운영 SHA다. 배포 전후에 같은 레포의 다른 세션에 알린다.
- 문서만 바꾼 PR은 테스트·재배포를 하지 않는다. 링크와 인용한 사실만 확인한다.
- 대량 반영·삭제·스키마 변경·금융 원본 변경은 신선 백업과 복원 확인 뒤에 한다. 소수 거래의 교정은 변경 전 값과 이력으로 되돌린다.

## 13. 보호 경계

어느 단계에서도 바뀌지 않는다.

1. 카드 원문·금액·부호·ID, 메일 원문, 영수증 원본을 바꾸거나 지우지 않는다. 금액 해석 실패를 0원으로 기록하지 않는다.
2. 수동 교정은 자동 판정보다 항상 우선한다.
3. 중복·환불 짝·초과 환불·원본 충돌 보호를 풀지 않는다. 환불 묶음은 전부 함께 기록하거나 전부 기록하지 않는다.
4. 연결·분류 완료는 실제 환급 입금이나 Google 반영을 뜻하지 않는다. 그런 사실을 만들어 적지 않는다.
5. Google 최종 장부에 자동으로 쓰지 않는다.
6. 인증을 우회하지 않는다. 암호·인증서·OTP를 읽거나 출력하지 않는다. OTA 포털에서는 조회만 한다(예약 변경·결제·다른 계정 로그인 시도 금지).
7. 강제 push, 운영 DB·고객 원본 삭제, 승인 없는 과금을 하지 않는다.
8. 미리보기·테스트에 운영 포트 8751, 8752, 8790을 쓰지 않는다. 내가 시작하지 않은 프로세스를 종료하지 않는다.
9. 고객 원문은 구독 프론티어 모델의 P2 실행과 Qwen4 Max(QwenCloud) 작업자에게만 준다(PROC-012, 소유자 결정 2026-11-13, Codex 한도 동안의 개발·예행 작업 포함). Git, 보고서, PR, 무료 모델에는 넣지 않는다.
10. 직원 계정·열람 권한 검사를 약화하지 않는다.
