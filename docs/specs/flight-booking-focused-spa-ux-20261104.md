# 항공권 예약 확인 화면 전면 UX 개편 (2026-11-04)

**상태: 신규 승인 요구사항 명세 · 구현 전.** 기존 [UI 정본](ui.md)의 항공권 예약 조회/날짜/카드 근거 계약을 대체하는 것은 **표시 방식과 화면 흐름**에 한한다. 실제 결제 확정, OTA 매칭, 예약/메일/참가자 권한은 유지한다. 기준 구현은 `webapp/flight_passenger_page.py`의 예약 검색 UI와 `/api/flight-passengers/name-search`, 카드 날짜 조회 API다.

## 현행 코드 확인과 문제 정의

- 예약 헤더의 정상 상태 `예약 근거 확인`은 `fb-status`에 출력되는 일반 문구다. 정상 예약이라면 사실상 정보 가치가 없으므로 **기본 배지를 제거**한다. 취소·변경·원본 충돌처럼 실제 조치가 필요한 경고만 강조 표시한다. 원본 검증 상태 자체는 데이터와 접힌 근거에 보존한다.
- `연결된 카드 결제`와 `예약일의 카드 거래 후보`가 별도 섹션으로 항상 출력된다. 연결 없음, 날짜만 같은 후보, 검증된 연결을 하나의 **결제 확인** 영역에서 상태별로 표현해 빈 설명과 반복 경고를 줄인다.
- `카드 전체 내역에서 날짜별 원행 확인`은 현재 `/cards/all` 페이지 링크다. 날짜 필터는 이미 같은 화면에서 API 조회가 가능하므로 이 경로를 재사용해 **SPA형 인라인 카드 원행 목록/상세**로 전환한다. `카드 원행 상세 보기 (새 탭)` 링크도 동일 페이지의 상세 보기로 우선 전환한다.
- `최초 메일 수신일의 카드 거래 전체 조회`, `예약일·원본 근거 확인`, `참가자 연결 정보`는 현재 텍스트/summary/anchor로 렌더링된다. 실제 버튼·아이콘이 깨지는 현상은 브라우저 재현과 스타일/DOM 검증이 필요하며, 정확한 원인이 확인되기 전까지 특정 라이브러리 탓으로 단정하지 않는다.

## 목표 UI: 가운데 한 열에 핵심만

예약 결과의 기본 콘텐츠는 데스크톱에서 중앙 최대 폭 약 760~880px, 모바일은 가로 100%를 사용한다. 화면 끝까지 늘어난 카드, 과도한 여백, 중복 테두리와 설명 문구를 제거한다. 검색 결과가 여러 건이면 예약 단위 목록/요약으로 탐색하며 **한 예약을 볼 때만 상세를 펼친다**.

기본 화면 우선순위:
1. **예약 핵심:** 예약번호, 탑승객 한 명, 여정 출발·도착, 출발/도착일, 항공편/항공사 등 확인 가능한 필수 정보. 한눈에 읽히는 간결한 요약. 근거가 없는 값은 생성하지 않는다.
2. **결제 확인 (단일 섹션):** 상태 `연결 확인` / `카드 거래 후보` / `연결 근거 없음` / `확인 불가·원본 충돌` 중 실제 증거에 맞는 표시. 연결 확정이면 연결된 거래를 먼저 표시하고, 카드 거래 후보는 필요할 때 같은 섹션 내부에서 확장한다. 후보뿐이면 `예약일 기준 거래 보기`를 한 번의 행동으로 제공한다. 자료가 없으면 한 문장만 설명하며 미결제·무거래 확정으로 표시하지 않는다.
3. **보조 정보 (기본 접힘):** `예약일 근거`(명시 일자 또는 최초 인증 메일 수신일, 한국 시간, 근거 시각), `원본 상세` 및 보호 상태. 실제 문제가 없으면 상태 배지나 긴 고지문을 반복하지 않는다. 카드 조회/예약 근거는 결제 확인 섹션에서도 중복 설명하지 않는다.

**동승객 목록은 기본/상세 예약 확인 화면에서 제거한다.** 동일 예약의 다른 승객 자료는 내부 데이터·원본·권한에 계속 보존하고, 연결 알고리즘이나 저장 의미를 바꾸지 않는다. 참가자 연결 작업은 일반 예약 확인의 기본 버튼·아이콘/링크에서 제거한다. 기존 별도 참가자 연결 업무를 삭제하거나 API를 비활성화하지 않는다. 필수 운영 작업자가 필요한 때만 별도의 현행 관리 경로에서 접근한다.

## 결제 확인의 정확한 상태 계약

- `linked_cards`가 검증되면 `연결된 카드`와 금액·가맹점·카드/거래일을 최소 정보로 보여준다. 카드 결제 1건의 연결을 예약 전체 결제/발권 완료로 확장해 표현하지 않는다.
- 연결이 없고 `booking_card_day`가 검증된 경우 `이 날짜의 카드 거래 보기`를 제공. `FIRST_RECEIVED`이면 `최초 인증 메일 수신일 기준`이라는 짧은 출처 표기를 곁들인다. 날짜·금액·이름이 같더라도 카드 연결을 확정하지 않는다.
- 날짜 충돌·취소·stale·출처 검증 실패에는 자동 후보 연결/조회가 차단되는 현행 안전 규칙을 유지한다. 수동 날짜 조회는 허용되는 권한/범위에서 명시적 날짜를 지정하게 한다.
- 예약일과 승인/결제일은 다를 수 있다. 자동 ±1일 확장, 근사 금액 자동 매칭, 원본 없는 연결 생성은 하지 않는다. 취소·환불 원행과 중복·원본 오류·카드별 식별은 그대로 구분한다.

## SPA형 카드 원행 탐색

- 동일 페이지에서 `결제 확인` → 카드 거래 날짜별 원행 목록 → 개별 원행 상세를 인라인 패널/가벼운 드로어로 전환한다. **전체 페이지 이동이나 새 탭 없이** 뒤로가기·닫기로 예약 맥락에 복귀한다. 새 전체 SPA 프레임워크나 전체 애플리케이션 리라이트는 요구하지 않으며 기존 fetch/상태 관리 API를 우선 재사용한다.
- 날짜 선택, 결과 없음, 더 보기/페이지네이션, 조회 중, 오류, 권한 거절, 최신 source revision 변경, 재조회 시 스크롤·검색어 보존을 설계한다. 원행 상세는 기존 안전한 읽기 API/DTO를 재사용하고, 사용자가 조회한 거래를 자동으로 예약과 연결하거나 DB에 쓰지 않는다. 현재 API가 인라인 상세에 필요한 정보를 제공하지 않으면 최소 읽기 전용 API 확장만 허용한다.
- 동일 예약 카드 후보·다른 여행 카드 거래를 혼동하지 않도록 카드사/끝자리, 날짜, 금액, 거래 방향, 중복/환불 보호를 유지한다. 카드 원행을 찾지 못해도 `거래 없음`이 아닌 `현재 조회 범위에서 결과 없음`으로 말한다.

## 버튼·아이콘 수리와 일관성

- `최초 메일 수신일의 카드 거래 전체 조회`는 결제 확인 안의 짧은 **`카드 거래 보기`** 실행 버튼으로 통합한다. 긴 문장은 버튼명이 아니라 근거 세부 정보에 둔다.
- `예약일·원본 근거 확인`은 **`예약일 근거`** 접기 요약으로 축약하고, 원본 충돌이 있을 때만 경고를 강조한다.
- `참가자 연결 정보`는 예약 확인 화면에서 노출하지 않는다. 기존 별도 참가자 연결 기능은 유지.
- 기존 공통 버튼·아이콘 디자인과 접근성 패턴을 사용하고 의미 없는 화살표, 깨진 CSS·폰트 glyph, 중첩 summary/anchor, 중복 클릭 영역을 제거한다. 아이콘은 텍스트 의미를 보조할 뿐 버튼명·기능을 대신하지 않는다.

## 구현 범위·검증·완료 기준

1. 항공권 관련 실제 렌더 함수·API·공통 CSS/JS·최근 PR을 대조하고 중복 섹션/페이지 이동을 제거한다. 사용자가 직접 지적한 여섯 문제를 전부 재현하여 수정한다.
2. 동일 입력을 기준으로 전후 **기본 노출 정보량/수직 높이/클릭 및 화면 이동 횟수**를 측정한다. 예약 상세의 초기 화면에서 필수 여정·결제 상태가 보이며 부가정보는 필요할 때만 연다.
3. 인증 합성 브라우저 PC 1440/1024, 모바일 390/320, 라이트/다크, 키보드/스크린리더 포커스에서 장식 깨짐·오버플로·레이아웃과 뒤로가기/닫기/오류 복귀를 확인한다.
4. 예약 검색 → 예약 요약 → 결제 확인 → 날짜 카드 목록 → 원행 상세 → 같은 예약 복귀를 한 페이지에서 수행. 새 탭·외부 카드 목록 페이지 이동 0회. 날짜 미상·FIRST_RECEIVED·명시일·충돌·취소·확정 연결·카드 결과 0건/다건/다음 페이지 모두 검증한다.
5. 카드 연결 확정/후보 구별, 수동 날짜 선택, source digest/revision, 권한/CSRF, 카드/OTA/환불/중복·원본 이력의 회귀 검사. Google 최종 장부 쓰기 0, 운영 금융/예약 링크 변경 0.
6. 구현 PR과 문서의 상태를 `명세` / `코드 병합` / `합성 브라우저 수락` / `운영 배포` / `실자료 수락`으로 구별한다. 명세 병합만으로 기능 완료 처리하지 않는다.

실제 구현은 후속 작업이며 이 명세 작성 자체는 UI 코드 변경이나 배포를 포함하지 않는다.
