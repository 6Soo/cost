# COST → Google 지출 장부: 수기 행 중복 방지·연결 명세 V1.0

- 작성: 2026-10-29
- 상태: PRODUCT_SPEC_APPROVED / SPEC_ONLY / CODE_NOT_CHANGED / TEST_NOT_RUN / OPERATIONS_NOT_VERIFIED
- 정본: [finance.md](finance.md), [현재 상태](../session_handoff.md)
- 목적: COST에서 분류한 지출을 기존 Google 여행별 스프레드시트에 반영할 때 **수기로 이미 기입한 동일 지출을 중복 추가하지 않도록** 한다.

## 1. 사용자 확정 결정

1. 수기 입력 원본은 유지한다. COST 거래와 날짜·항목·메모 등 내용이 다르면 **수기 셀을 덮어쓰지 않고 차이 표시**한다.
2. 승인번호가 없어도 날짜·금액·통화·가맹점·카드 단서 등 **복합 조건으로 동일 거래가 유일하게 확정되면 자동 연결**한다. 자동 동일성 확정에 일괄 사용자 승인을 요구하지 않는다.
3. 중복으로 판정된 COST 지출은 신규 행을 추가하지 않는다. 명확한 신규 지출만 기존 안전한 장부 반영 경로에 전달한다.
4. 기존 P1 규칙 → P2 추론 → P3 필수 개입 최소화 원칙을 따른다. 다만 유일성이 없거나 원본이 충돌하면 **추측으로 같은 거래를 만들지 않는다**.
5. **Google 최종 장부 자동 쓰기 금지**라는 기존 금융 권한 경계는 이번 정책만으로 해제되지 않는다. 자동 연결 판정과 실제 Google 행 쓰기는 별도 단계다.

## 2. 기존 COST 경로에 통합

- 새 별도 회계 장부/동일성 엔진을 만들지 않는다. 기존 카드 원천·COST 지출 분류·내부 ledger preview/commit/project, Google 여행 탭 read projection, 원본 digest/revision/감사·멱등 보호를 우선 재사용한다.
- 실제 구현 전 코드에서 Google 시트 조회 범위, 수기 지출 열·행 구분, 기존 기록 식별자, 행 쓰기 권한, 보호 범위를 점검해 실제 함수/모듈 소유자를 확정한다.
- 대상은 **같은 실제 여행**의 지출 행. 여행 이름 유사성만으로 다른 탭을 합치지 않는다. 카드 지출과 현금·포인트·합산 예약 비용은 회계 단위가 다를 수 있으므로 금액만으로 1:1 매칭하지 않는다.
- 환불·취소는 일반 지출과 구분하고 기존 환불/원결제 보호·연결 계약을 그대로 적용한다.

## 3. 매칭 판정

### 3.1 후보 생성

- 같은 유효 여행 탭에서 수기 입력된 지출 행을 읽고 COST의 반영 대상 지출과 비교한다.
- 우선순위 A: 원천 거래 ID/승인번호/기존 연계 ID가 같은 카드사·카드 범위에서 일치하고, 부호·통화·금액·거래 유형이 충돌하지 않는 유일한 행.
- 우선순위 B: 안정 ID가 없는 경우 **동일 여행 + 정확한 금액·통화·부호 + 날짜 규칙에 따른 일치/설명 가능한 차이 + 가맹점 또는 거래 내용의 충분한 동일성 + 사용 가능한 카드 단서**를 조합해 유일한 후보를 식별한다.
- 가맹점 표기 정규화(띄어쓰기, 대소문자, 흔한 결제대행사 표기)는 원문을 보존한 채 비교용 값으로만 사용한다.
- COST의 장부 날짜가 OTA 이용일이고 수기 입력은 카드 승인일인 경우처럼 날짜의 의미가 다를 수 있으므로, **각 날짜의 출처를 구분**해 예약번호·사용기간 등 추가 근거로 검증한다. 날짜 허용 오차만으로 확정하지 않는다.
- 결제대행사/공통 가맹점, 같은 날짜 동일금액 반복 결제, 한 수기 행에 여러 카드 거래가 합산된 경우, 하나의 거래가 여러 행으로 분할된 경우는 유일한 1:1 후보가 아니면 자동 확정하지 않는다. 1:N/N:1은 별도 명시적 묶음 증거가 있을 때만 처리.
- 카드 식별 정보가 수기 행에 없는 것은 일반적이므로 **카드 정보가 없다는 이유만으로 전부 수동 보류하지 않는다**. 다른 근거로 충분하고 유일할 때 자동 연결한다.
- 금액·통화·부호 불일치, 원천 ID 충돌, 서로 다른 실제 거래 증거, 다른 여행, 기존 다른 거래에 점유된 행은 자동 동일성 확정 금지. 환율 추정으로 정확 금액을 만들어 매칭하지 않는다.

### 3.2 상태

- MATCHED_MANUAL: 기존 수기 행과 동일 거래 자동 확정, 신규 시트 행 0.
- MATCHED_EXISTING: 이전 COST 연계/기장 행 재인식, 신규 시트 행 0.
- NEW_EXPENSE: 일치 후보가 없는 신규 거래, **권한이 있는 기존 장부 반영 경로**로만 전송.
- REVIEW_CONFLICT: 복수 후보, 점유 충돌, 핵심 불일치, 합산/분할 불명확 등. 자동 시트 추가 0.
- SOURCE_UNAVAILABLE: 시트 조회/최신성/권한/범위 불확실. 신규 시트 추가 0, 성공으로 표시 금지.

### 3.3 내용 충돌과 수기 원본 보호

- 동일 거래로 확정됐더라도 수기 행의 날짜/가맹점/항목/메모와 COST 값이 다르면 원본 셀은 수정하지 않는다.
- 결과에 필드별 차이(수기 값 ↔ COST 값), 매칭 근거, COST 거래 링크를 표시한다.
- **동일성은 확정되지만 분류 내용만 다른 경우**는 '연결됨 · 내용 차이'로 표시하고 중복 추가하지 않는다.
- 금액·통화·부호·여행 등 동일성의 핵심이 충돌하면 '동일 거래 확정'이 아니라 REVIEW_CONFLICT로 보류한다.

## 4. 영속 연결과 행 식별

- 업로드별 임시 보고서와 달리 **수기 시트 행 ↔ COST 원천 거래의 연결은 재전송 중복 방지를 위해 지속 보존**한다. 기존 연결 테이블/감사 경로가 있으면 재사용.
- 연결 기록 최소 필드: COST 거래 안정 ID, 실제 여행/시트 식별자, 수기 행의 안정적 키(있으면), 원본 내용 fingerprint, 매칭 규칙/근거, 연결 시각, 마지막 검증 시각, 연결 상태, revision/감사 출처.
- **시트 행 번호 단독을 영속 ID로 사용하지 않는다.** 시트 정렬·행 삽입·삭제 후에도 원본 fingerprint와 고유 키를 재확인하고 불일치하면 재탐색/보류한다.
- 연결만 저장하는 경우 Google 수기 행은 읽기 전용. 별도 시트 열/메타데이터에 ID를 쓰려면 기존 쓰기 권한 계약에 따른 승인과 마이그레이션이 필요하다.
- 사용자가 수기 행을 수정하거나 이동해도 검증 가능한 동일성이 유지되면 링크를 재검증하고, 삭제/다른 거래로 교체됐으면 링크를 무조건 성공으로 재사용하지 않는다.
- 사용자 수동 연결·교정은 이후 자동 규칙보다 우선한다.

## 5. 결과 UI

상단: 반영 대상 N건 / 기존 수기 행 연결 M건 / 기존 COST 기록 재인식 K건 / 신규 반영 가능 A건 / 검토 보류 R건 / 시트 접근 오류 S건.
상태별 상세: 거래일·여행·가맹점·금액·카드 마스킹·COST 거래 ID·수기 시트 위치·동일성 근거·차이 필드·기록 상태·링크.
수기 일치 행은 '이미 수기로 기록됨 · 새 행 추가 안 함', 내용 차이는 '연결 완료 · 수기 원본 유지 · 차이 있음', 충돌은 '중복 가능성 확인 필요'로 표시한다.
**자동 연결 = Google 시트에 새로 기입했다는 뜻이 아님**. '신규 반영 가능', '내부 장부 기록됨', 'Google 반영됨'을 구분한다.

## 6. 동시성·안전·실행

- 반영 직전 Google 원본 범위와 revision/fingerprint를 재조회하고, 처음 미리보기 이후 수정되면 재대조한다.
- 같은 거래를 두 작업자가 동시에 처리해도 신규 행/연결이 중복되지 않도록 기존 잠금·멱등성·원자성 경로를 사용한다.
- 시트 접근 실패, 오래된 캐시, 보호 범위, 부분 기록, API 타임아웃은 무조건 안전 보류. 재시도 시 실제 적용 여부를 다시 확인한다.
- 새 Google 쓰기 권한을 암묵적으로 열지 않는다. 실제 쓰기는 기존 허용된 경로와 사용자 승인 범위에서만.
- Google 원본의 수기 셀·서식·수식·정렬·필터·메모·수입 데이터·다른 여행 탭은 불변.
- 사용자 식별·금융 원문·Google 시트 실데이터는 테스트 fixture 또는 승인된 읽기 전용 점검으로만 다룬다.

## 7. 검증 시나리오 및 완료 기준

1. 수기 지출 1건과 COST 지출 1건이 복합 조건으로 유일하게 일치 → MATCHED_MANUAL, 신규 행 0, 기존 수기 셀 변경 0.
2. 동일 거래지만 수기 항목/메모가 다름 → 링크 성공 + 차이 표시, 수기 값 불변.
3. 같은 날 같은 금액의 실제 카드 결제 2건 → 다른 승인번호/원행이면 2건 유지, 같은 수기 행에 이중 연결 금지.
4. 승인번호 없음 + 유일한 충분 근거 → 자동 연결. 가맹점만 같은 경우/후보 2개면 보류.
5. 수기 행 정렬·삽입·삭제·수정 후 재실행 → 안정 재탐색 또는 안전 보류, 엉뚱한 행 연결 0.
6. 기존 COST 기록, 취소/환불, OTA 예약 합산, 현금/포인트, 날짜 기준 차이, 통화 차이, 다른 여행, 시트 접근 오류.
7. 동일 배치 재실행·동시 실행·중간 실패 후 재시도 → 신규 중복 0, 사용자 교정/원본 불변.
8. UI 모바일/키보드·owner 권한·민감정보 마스킹·검토 상세 재현.
9. 실제 코드/테스트/PR 병합/운영 배포/실제 Google 수락은 각각 독립적으로 보고. **문서만 작성해 기능이 동작한다고 주장 금지.**

## 8. 구현 순서

- SDD-01: 현재 Google 조회/지출 preview·commit·project·연결/감사 구현 코드 대조 및 소유권 확정.
- SDD-02: 수기 행 read projection과 동일성 후보 생성/고유키 우선 매칭.
- SDD-03: 복합 조건 유일 자동 확정·충돌 안전 보류·원본 차이 계산.
- SDD-04: 기존 연결 저장소/감사/멱등성 재사용, 시트 행 이동·수정 재검증.
- SDD-05: 신규 행 전송 직전 전체 재대조 및 기존 승인 경계 연동.
- SDD-06: 결과 요약/차이·검토 UI, 합성·격리 DB·시트 mock 회귀.
- SDD-07: 승인된 운영 읽기 전용 실자료 검수, 별도 쓰기 승인·배포 수락.

## 9. 다른 명세와의 경계

- 카드 업로드 전수 분류 검증은 **파일 원천 거래의 분류 완결성**을 판정한다.
- 이 명세는 **Google 지출 장부의 중복 기입 방지**를 판정한다. 두 성공률을 섞지 않는다.
- 최신 finance.md의 '분류가 되면 완료' 정책은 분류 완료 상태에 적용한다. 수기 장부 연결/Google 쓰기/환불 금융 확정은 별개의 결과다.
