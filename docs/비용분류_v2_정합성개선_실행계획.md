# 비용분류 v2 정합성 개선 실행 계획

## 목적

신규 v2 모델의 금액 불변식은 통과했지만, legacy 분류를 도메인별로 분해하면서
판정 신뢰도, 취소 관계, 여행 귀속, 예약 공급자에 남아 있던 품질 문제가 드러났다.
이 문서는 해당 문제를 위험도와 선후관계에 따라 해소하고, v2를 기존 v14/v76
산출 경로와 병렬 검증할 수 있는 상태로 만드는 실행 계획이다.

현재 기준선은 다음과 같다.

| 지표 | 현재값 |
|---|---:|
| 원천/결제/활성 배분 | 1,705 / 1,705 / 1,705건 |
| 결제 합계/활성 배분 합계 | 310,719,899원 / 310,719,899원 |
| 결제별 배분 차이 | 0건 |
| 고신뢰이면서 불확실한 근거 | 196건 |
| 취소·환불 원거래 미연결 | 7건 |
| 여행 미배정 | 19건, 2,734,540원 |
| 공급자 미확정 예약 | 112건 |
| 저신뢰 결제 | 87건 |
| 0원 결제 | 9건 |

수치는 `classified_v14.csv` 이관 기준이다. 최신 원천을 다시 적재하면 기준선을
새로 기록하고 증감 사유를 함께 남긴다.

> **기준선 갱신 전제:** 위 수치는 PR 작성 시점의 과거 기준선이다. P1에 들어가기
> 전에 현재 `classified_v14.csv`, 수기장부, 검증된 OTA 연결, Gmail OTA 인덱스,
> 퇴사자 불변 시트를 다시 적재해 최신 기준선을 만든다. 최신 기준선과 과거
> 기준선의 차이는 UID별로 설명하고 승인되지 않은 차이가 있는 동안 P1을 시작하지
> 않는다.

## 공통 원칙

1. 금액 불변식보다 분류 건수 감소를 우선하지 않는다. 억지 귀속 대신
   `needs_review`와 `unassigned`를 명시적으로 유지한다.
2. 원천 사실은 수정하지 않고, 관계·판정·배분의 새 버전을 추가한다.
3. 자동판정에는 반드시 `rule_id`, 근거, 신뢰도와 적용 결과 건수를 남긴다.
4. 취소·환불은 승인번호 또는 카드사별 구조적 키로 연결한다. 승인번호가 있는
   거래에 가맹점·금액 폴백을 적용하지 않는다.
5. OTA·항공·PG 결제는 결제일 근접성만으로 여행에 귀속하지 않는다.
6. 단계별 작업 후 결제 건수, 총액, 결제별 배분합계와 외래키 검증을 다시 수행한다.
7. 최신 수기장부와 OTA 메일을 사용하는 단계는 P8·P10의 진실원천 순서를 따른다.
8. 운영 DB는 언제든 불변 원천과 판정 변경 원장만으로 완전 재생성할 수 있어야 한다.
9. 예약 PIN, 생년월일, 전화번호, 이메일, 여권정보 등 대사에 불필요한 개인정보는
   DB에 저장하지 않는다.
10. 카드 이벤트의 안정 식별키와 원천 행 식별키를 분리하며, 예약번호나 금액을
    카드 이벤트의 기본키로 사용하지 않는다.

## 우선순위

### P0. 검토 큐와 회귀 기준 고정 — 완료(2026-07-25)

후속 작업이 같은 기준으로 반복 실행되도록 품질 이슈를 행 단위로 조회하고
수정 전후 차이를 비교할 기반을 만든다.

구현:

- `review-report`의 집계값마다 대응하는 상세 조회 명령 또는 CSV 출력 추가
- 각 큐에 결제 키, 현재 판정, 근거, 규칙, 신뢰도, 예약번호, 배분대상 포함
- 실행 시점, 입력 문서 해시, 규칙 버전과 기준선 지표 저장
- 여행별·계정별·배분대상별 기존 v14 합계를 회귀 기준으로 출력

완료 기준:

- 모든 집계값에서 동일 건수의 상세 행을 재현할 수 있다.
- 같은 DB에서 반복 실행한 결과가 동일하다.
- 수정 전후 추가·해소·잔존 건을 구분할 수 있다.

구현 결과:

- `review-snapshot` 명령으로 8개 상세 큐 CSV와 기준선 파일을 생성한다.
- `manifest.json`에 입력 해시, 규칙 버전(`p0-v1`), 안정적인 semantic hash와
  큐별 자연키를 기록한다.
- `regression_totals.json`에 배분대상·여행·계정별 건수와 금액을 기록한다.
- `--compare-to`로 이전 기준선 대비 추가·해소·잔존 건을 `diff.json`에 기록한다.
- 현재 집계와 상세 큐 건수 일치, 동일 DB 재실행 해시 일치 및 합계 회귀 테스트를 통과했다.

### P0.5. 운영 안전 기반과 최신 기준선 고정 — 진행 중

P1 이후 생성되는 수동 판정과 연결 이력이 유실되지 않고, OneDrive 동기화나 원천
재적재로 거래가 중복·변형되지 않도록 운영 기반을 먼저 고정한다.

구현:

- SQLite 실행 DB는 OneDrive 동기화 폴더 밖의 로컬 경로에 두고 WAL·SHM 파일도
  같은 로컬 파일시스템에서 관리한다. `ledger/data/ledger_v2.db`는 개발용 기본값으로
  사용하지 않는다.
- DB는 캐시·조회 모델로 취급한다. 수동 판정, 예약 연결, 연결 거부와 정정은
  append-only 변경 원장(JSONL 등)에 기록하고 Git 또는 별도 백업 대상에 포함한다.
- 불변 원천과 변경 원장만으로 빈 DB를 완전 재생성하는 `rebuild` 절차와 복구
  검증을 추가한다.
- `source_event_id`, 안정적인 `card_event_id`, `source_record_id`를 분리한다.
  승인번호가 없는 해외결제도 카드사·카드·승인시각·원통화금액 등 카드사별 구조
  규칙으로 안정 키를 생성하며 키 충돌은 자동 병합하지 않고 검토 큐로 보낸다.
- 같은 카드 이벤트의 새 스냅샷이 들어와도 거래 사실을 제자리 수정하지 않는다.
  새 거래 버전 또는 정정 이벤트를 추가하고 현재 뷰만 최신 버전을 가리킨다.
- `payment_booking_links`, `booking_target_links`, 취소·환불 관계에 유효기간 또는
  superseded/rejected 상태를 둔다. 새 스냅샷에서 연결이 제거·변경되면 과거 연결을
  종료하고 이력을 보존한다.
- 결제 사실에 예약 표시금액, 원통화 금액·통화, 카드 청구 원화금액, 할인·포인트,
  현장 결제액을 분리한다. 금액 대사는 `exact`, `discount_adjusted`,
  `within_2_percent`, `mismatch`로 기록한다.
- 퇴사자 시트는 불변 원천으로 취급하고 금액 정확 일치를 우선한다. ANA 등
  해외원화결제는 카드 청구액과 2% 이내 차이를 보조 근거로 인정하되 정확 일치와
  구분한다.
- 서비스 기간은 연도를 포함한 ISO 날짜로 저장한다. 월일만 확인된 경우
  `date_precision`과 원문을 함께 저장하고 2026년을 암묵적으로 고정하지 않는다.
- OTA 메일·예약 페이지 적재 전에 허용 필드만 추출한다. PIN, 생년월일, 전화번호,
  이메일, 여권정보를 제거하고 `redaction_version`과 원격 메시지 ID·해시만 남긴다.
- 최신 `classified_v14.csv`, `ota_event_links_verified.json`, Gmail OTA 인덱스,
  퇴사자 시트 416행과 수기장부를 적재해 P0 기준선을 갱신한다.

완료 기준:

- 로컬 DB를 삭제한 뒤 불변 원천과 변경 원장만으로 동일 semantic hash, 결제 건수,
  총액, 현재 판정과 연결을 재현한다.
- 수정된 스냅샷을 연속 적재해도 과거 거래·연결은 이력으로 남고 현재 뷰에는
  최신 활성 연결만 한 번 나타난다.
- 동일 원천 반복 적재, UID 생성 규칙 변경, 승인번호 없는 해외결제에서도 카드
  이벤트가 중복 생성되지 않는다.
- 저장 데이터 개인정보 검사에서 금지 필드가 0건이다.
- 최신 기준선과 기존 v14/v76의 모든 차이가 UID 단위로 설명된다.
- DB 백업·복구와 기존 워크북 경로 롤백이 각각 한 번 이상 검증된다.

현재 구현 결과:

- PR #8을 기준으로 별도 브랜치에서 SQLite 기본 실행 경로를 OneDrive 밖의
  사용자 로컬 데이터 디렉터리로 변경했다.
- `payment_transaction_versions`를 추가해 동일 카드 이벤트의 사실 변경을
  append-only 버전으로 보존하고, `payment_transactions`는 현재 투영으로 유지한다.
- legacy 예약·여행·취소 관계를 새 전체 스냅샷 적재 전에 `superseded`로 종료하고
  새 스냅샷에서 다시 관찰된 관계만 현재 연결로 복원한다.
- 음수 거래를 기본 `refund`로 보존하고, 원거래와 절대금액이 같은 경우만
  전액 `cancellation`; 금액이 다르거나 원거래가 없으면 부분·미해결 `refund`로
  유지한다.
- 수정 스냅샷의 거래 버전 보존, 제거된 예약 연결 종료, 전액취소·부분환불 구분,
  동일 스냅샷 재적재 시 버전 미증가를 회귀 테스트로 추가했다.
- append-only 변경 원장, 안정적인 `card_event_id`, 개인정보 제거 어댑터,
  최신 기준선 재적재와 백업·복구는 후속 작업으로 남아 있다.

### P1. 고신뢰·불확실 근거 196건 해소

가장 먼저 처리한다. 확정처럼 보이는 판정이 불확실한 근거를 가진 상태는 자동전기
오염 위험이 가장 크다.

구현:

- `추정`, `유사`, `불명`, `확인 필요` 등 충돌 문구를 유형과 `rule_id`별로 묶는다.
- 예약번호+메일 실증, 수기 단독매칭, 현지정합 등 `상` 신뢰도 허용조건을 규칙으로 명시한다.
- 허용조건을 충족하면 근거를 구조화해 `confirmed` 판정을 새 버전으로 생성한다.
- 충족하지 않으면 신뢰도를 낮추고 `needs_review`로 전환한다.
- 기존 판정은 `superseded` 연결로 보존한다.

완료 기준:

- `상` 신뢰도이면서 불확실한 근거가 있는 현재 판정이 0건이다.
- 신뢰도 변경 전후 건수와 규칙별 사유가 리포트에 남는다.
- 재판정으로 결제금액 또는 배분합계가 변하지 않는다.

### P2. 취소·환불 원거래 미연결 7건 정리

취소 관계는 순액과 여행별 비용을 동시에 바꿀 수 있으므로 여행 미배정보다 먼저
확정한다.

구현:

- 국민 국내: 취소번호 괄호 안 원승인번호로 연결
- 하나: 동일 승인 행의 승인취소금액 구조로 연결
- 국민 해외: 카드4·통화·현지금액을 소수 보존해 페어링
- 기업: 승인번호 링크 부재가 확인된 경우에만 가맹점+금액 예외 규칙 적용
- 원거래가 조회기간 밖이면 미연결 오류로 숨기지 않고 `전기예약_환불` 사유를 기록
- 완전상쇄와 부분환불을 구분해 배분계획을 새 버전으로 생성
- 음수 거래를 금액만으로 모두 `cancellation`으로 분류하지 않는다. 전액취소,
  부분환불, 조정 이벤트를 구분하고 하나의 예약·원거래에 여러 환불 이벤트를
  독립적으로 연결한다.

완료 기준:

- 7건 각각이 `원거래 연결`, `조회기간 밖`, `자료 부족` 중 하나로 설명된다.
- 자료 부족 건은 근거와 검토 상태를 가진 채 남고, 원인 없는 미연결 건은 0건이다.
- 완전상쇄쌍의 순액은 0이고 부분환불은 원여행 배분과 함께 검증된다.

### P3. 여행 미배정 19건 재분류

취소 관계 정리 후 남은 실결제를 예약·메일·수기 근거로 검토한다.
`MISC-*` 신규 격리 11건과 현재 전체 미배정 19건을 별도 지표로 유지한다.

구현:

- 가맹점/예약번호/카드/금액/사용일 기준으로 중복 없는 검토 묶음 생성
- OTA·항공·렌터카는 메일 또는 예약 문서에서 서비스 기간과 예약번호 확인
- 판관비 후보는 카드 기명자·용도와 확정 규칙을 적용
- 여행 귀속이 확인되면 새로운 allocation plan을 만들고 기존 계획을 대체
- 자료가 부족하면 미배정 상태, 부족한 근거와 검토 담당을 명시

완료 기준:

- 19건 모두 `여행`, `판관비`, `취소/정산`, `근거 부족 미배정` 중 하나로 설명된다.
- 근거 부족 건을 제외한 자동 미배정은 0건이다.
- 변경된 여행별 합계가 원천 결제와 역추적된다.

### P4. 공급자 미확정 예약 112건 정규화

공급자 식별은 예약번호 중복 방지와 메일 어댑터 연결에 필요하지만, 결제금액
정합성에는 직접 영향을 주지 않으므로 귀속 문제 뒤에 처리한다.

구현:

- 예약번호 형식 규칙 적용: Agoda 10~12자리, Trip.com `1400` 시작 16자리,
  Booking.com 10자리 내외
- 기존 `booking_info`, 판정 근거와 메일 발신자/본문을 구조화된 evidence로 연결
- 형식만으로 단정할 수 없는 번호는 `proposed`, 메일 실증은 `confirmed`로 구분
- provider 변경 시 동일 예약의 중복 레코드를 탐지하고 관계를 병합
- 번호 길이가 겹치는 Agoda·Booking.com은 형식만으로 확정하지 않는다. 내부
  불변 `booking_id`와 복수의 `booking_identifier(provider, identifier, status)`를
  분리해 provider 정정 이력을 보존한다.

완료 기준:

- 자동 식별 가능 건에는 재현 가능한 `rule_id`가 있다.
- 잔여 `unknown`은 자료 부족 사유와 검토 상태를 가진다.
- `(provider, booking_number)` 중복 및 관계 유실이 0건이다.

### P5. 저신뢰 87건과 0원 결제 9건 감사

앞 단계의 판정 변경 후 큐를 다시 산출하고 잔존 건만 검토한다.

구현:

- 저신뢰 건을 예약 미확정, 여행 미확정, 계정 미확정, 증빙 미확정으로 분리
- 0원 거래를 포인트 결제, 완전상쇄, 카드 승인자료의 금액열 오류, 실제 0원으로 구분
- 포인트 사용은 P13에 따라 상쇄 전 총액을 비용으로 인식하고 근거를 연결
- 해결할 수 없는 건은 자동전기 대상에서 제외되는 `needs_review` 게이트 적용

완료 기준:

- 0원 9건 각각의 비용 인식 금액과 사유가 설명된다.
- 저신뢰 잔존 건은 부족한 근거와 자동전기 차단 여부가 명시된다.
- `confirmed` 상태에는 저신뢰 판정이 없다.

### P6. 직접 적재와 산출 경로 병렬 검증

legacy 품질 문제를 해소한 후 `classified_v14.csv`를 중간 진실원천으로 쓰는 의존을
줄이고 실제 전환 가능성을 검증한다.

구현:

- 카드, 수기장부, OTA 메일별 source adapter를 만들어 원천 계층에 직접 적재
- 중복 원천과 동일 거래를 별도 관계로 관리하고 원문 해시를 보존
- OTA 어댑터는 P0.5의 개인정보 허용목록·제거 규칙을 공통 적용하고 원문 전체를
  로컬 DB에 복제하지 않는다.
- 카드 어댑터는 예약 표시금액과 카드 청구액을 혼합하지 않고 할인·해외원화결제
  오차 유형을 구조화한다.
- v2의 확정 배분을 읽는 read-only 워크북 어댑터 구현
- 기존 v76과 결제별·여행별·계정별·예약번호별 회귀 대조
- 차이를 `의도된 개선`, `legacy 오류`, `v2 오류`, `자료 부족`으로 분류

완료 기준:

- 동일 원천을 반복 적재해도 결제와 관계가 중복되지 않는다.
- 기존 워크북과의 모든 차이가 행 단위로 설명된다.
- 도메인 모델 문서의 전환 게이트 7개를 모두 통과한다.
- 전환 승인 전까지 기존 v14/v76 경로는 그대로 유지된다.
