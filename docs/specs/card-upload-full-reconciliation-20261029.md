# 카드 파일 업로드 전수 대조·자동 분류·검증 명세 V1.0

- 확정일: 2026-10-29
- 상태: IMPLEMENTED / SYNTHETIC_VALIDATED / OPERATING_ACCEPTANCE_NOT_RUN / DEPLOY_NOT_DONE
- 목적: 업로드 파일의 **모든 원천 거래**를 누락 없이 DB에 대조하고 신규 거래를 자동 등록·분류한 뒤, **이번 파일만** 대상으로 분류 완결성을 증명한다.
- 기존 카드 수집·분류·여행 귀속·환불·감사 엔진 재사용. 별도 회계 정본 생성 금지.

## 최신 실행 계약 (2026-10-29)

사용자 최신 지시로 명세 전체 구현을 재대조한다. 구현자는 Luna low 4명이며 감독자가 통합·검증한다. 자동·수동 모두 분류되면 완료이며, 저장된 유효 여행과 거래 성격을 낮은 신뢰도·동률 설명·과거 잠정 문구만으로 미완료로 되돌리지 않는다. 아래 최초 명세의 고신뢰·잠정 확정 대기 문구보다 [금융 명세의 자동분류 완료 계약](finance.md#자동분류-완료-계약-2026-10-29)이 우선한다. 실제 여행 부재·원본 충돌·명시 수동 보류·금융 검증은 계속 보호한다. 운영 수락·실카드 검증·병합·배포는 각각 별도 상태로 보고한다.

## 1. 확정 제품 결정

1. 거래 분류 완료 = **확정된 거래 성격 + 유효한 특정 여행 귀속**. 개인 지출이라도 특정 여행에 귀속되지 않으면 미완료. 존재하지 않는 가짜 여행을 자동 생성해 통과시키지 않는다.
2. 업로드는 검증 전용이 아니다. 기존 DB 거래와 중복 대조 후 **확실한 신규 거래만 자동 등록**하고 분류를 시도한다.
3. 거래 식별은 카드사/계정 범위 내 승인번호 등 안정적 고유키 우선, 없으면 날짜·시간·금액 부호·통화·가맹점·카드 식별·원천 행 등 복합 조건으로 대조한다. 충돌·애매함은 자동 병합/등록하지 않고 보류한다. 승인번호가 없는 반복 동일금액 거래를 단일 거래로 합치지 않는다.
4. 결제·취소·환불은 각각 원천 거래로 계산한다. 취소의 원결제 연결은 분류 완료와 **별도 금융 대사 상태**로 보고한다. 원결제 근거가 없으면 환불 확정/금융 완료로 표시하지 않는다.
5. 확실하게 분류할 수 있는 건은 자동 처리하고 미완료·충돌·파싱 실패·연결 실패를 원인별 표시한다.
6. 검증 결과 스냅샷/업로드별 보고서는 영구 보관하지 않는다. 단 **기존 거래 원본, 분류 결정, 신규 등록, 변경 감사, 멱등성 키, 오류 복구에 필요한 운영 로그**는 기존 보존 정책을 따른다.
7. 검증 분모는 이번 파일의 원천 거래다. 기존 DB 전체 상태는 이번 업로드 성공 판정에 혼합하지 않는다.
8. 신뢰도 높은 자동 여행 추론은 즉시 분류 완료로 인정한다. 단 **실제 유효 여행 ID**, 거래 성격 확정, 근거가 있는 단일 우세 후보, 기존 수동 결정/잠금 비침해, 동률·충돌 부재를 모두 요구한다. 근거 없는 숫자 임계값이나 모델 확률만으로 완료 금지. 기존 AUTO_PROVISIONAL은 조건 미달 시 계속 미완료; 조건 충족 시 명시적 확정 자동결정으로 기록해야 완료로 인정한다.

## 2. 처리 파이프라인

A. 파일 사전 검사: 카드사/파일 형식/인코딩/기간/파일 행수/헤더·공백·합계행/거래행/파싱 실패를 구분한다. 지원하지 않는 형식, 누락 필수 필드, 카드 계정 식별 불능은 안전하게 중단한다.
B. 원천 행 정규화: 승인일시, 매입일, 금액·통화·부호, 가맹점, 승인번호, 카드 식별, 원천 파일 내 행 번호와 취소 여부를 보존한다. 민감 카드번호는 마스킹한다.
C. 동일성 판정: 기존 DB와 매칭, 신규, 충돌/모호, 파일 내부 중복을 **서로 배타적**으로 분류. 파일 내부 중복은 원천 행 기준 집계하되 동일 DB 거래로 연결될 수 있고 중복 등록은 0이어야 한다.
D. 안전한 신규 등록: 기존 저장소 트랜잭션/멱등성/감사 경로 재사용. 쓰기 전 파일 전체 구조 검증. 처리 중 오류는 원자성 또는 명확한 부분 성공/실패를 제공하고 허위 성공 금지. 기존 수동 분류·여행 귀속·원본·금융 연결 덮어쓰기 금지.
E. 자동 분류: 기존 사용자 확정 규칙/신뢰 가능한 카드·여행 증빙·단일 우세 후보를 적용한다. 여행 성격 둘 다 확정 시 완료. 높은 신뢰도의 자동 추론은 완료 가능하지만, 증빙과 결정 출처/규칙 버전/결정 시각을 감사에 남기고 재검토·수동 교정 가능하게 한다. 기존 잠정 배정과 완료를 구분한다.
F. 결제/취소 각각 분류 및 원결제 연결 상태를 별도 계산. 추론으로 환불 완료/결제 정산을 만들어내지 않는다.
G. **업로드한 원천 행 전부**를 결과 DB와 다시 대조하고 합계 검증. 파일에 없는 기존 거래는 계산 제외.

## 3. 완료 판정과 집계

- 파일 원천 거래행 수 T = 기존 일치 E + 신규 등록 N + 식별 보류 H + 파싱 실패 P (각 원천 거래행은 정확히 한 구간).
- E+N 중 분류 완료 C, 미완료 U로 분할하여 **E+N=C+U**. 식별 보류·파싱 실패는 분류 완료 아님.
- **분류 완료율 = C/T** (T=0이면 0%가 아닌 '검증할 거래 없음'). 월별 합계는 유효 거래 날짜 기준, 날짜 파싱 실패는 '날짜 확인 필요'로 별도 집계. 전체 합계와 월별/미상 합계가 일치해야 한다.
- 동일 파일 중복 원천행은 원천 행 수에 포함해 표기하고, 중복 저장은 금지. 원천 파일의 실제 중복 거래 여부는 확인 필요로 분리할 수 있다.
- 성공 = T>0, P=H=U=0, 신규 등록·DB 재조회 성공, 모든 거래에 확정 거래 성격과 유효 여행 ID가 존재, 원천 행 수 합계 일치. **취소 원결제 미연결이 있으면 '분류 100%, 금융 대사 미완료'로 별도 경고**, '모든 금융 처리 완료' 표시 금지.
- 신뢰도 높은 자동 결정의 '분류 완료'는 **금융 지급·환불·예약 매칭 완료**를 의미하지 않는다.

## 4. 업로드 결과 UI

상단: 파일명(민감정보 제거), 카드사, 조회기간, 업로드 거래 T, 기존 일치 E, 신규 등록 N, 분류 완료 C, 미완료 U, 대조 보류 H, 파싱 실패 P, 취소 원결제 미연결 R, 분류 완료율.
월별 표: YYYY-MM, 거래 수, 기존 일치, 신규, 분류 완료, 미완료, 식별 보류, 파싱 실패; 날짜 미상 별도.
상태: '전수 분류 검증 통과' / '분류 미완료 N건' / '검증 불가(파일/시스템 오류)'를 구분. 금융 대사 경고는 별도.
실패 상세: 원천 행 번호, 거래일, 마스킹 카드, 가맹점, 금액/통화, 기존 매칭 여부, 현재 여행·성격, 실패 원인, 근거/후보, 기존 검토 화면 링크. 실패가 없는 경우 상세 목록을 비운다.
업로드 결과는 응답 시점에 표시하고 별도 영속 보고서 테이블을 만들지 않는다. 화면을 떠난 후 재조회 보장은 하지 않음. 모바일 표·접근성·다크모드는 기존 디자인 토큰 준수.

## 5. 오류/보안/성능

- 파일 포맷 불명·부분 파싱·타임아웃·DB 장애·부분 등록은 100% 완료로 위장하지 않는다. 가능한 재시도는 멱등 처리.
- owner/관리자 권한과 CSRF/파일 크기·확장자·내용 검사·악성 수식/CSV injection·민감정보 마스킹 적용.
- 같은 파일 재업로드 시 신규 등록 0, 기존 거래/수동 결정/원본 불변. 서로 다른 파일에 같은 거래가 있어도 중복 등록 0.
- 파일 상한은 20 MiB·50,000 거래행이며 물리 행수도 제한한다. 업로드는 기존 동기 요청으로 처리하고 화면에 처리 중 상태를 표시한다. 완료/오류 응답 전 수치 진행률을 추정해 표시하지 않는다. 원천 저장 후 후속 단계 실패는 503·batch ID·저장 여부·동일 파일 재시도 안내를 반환한다. 실패 상세는 전체 집계를 보존하고 페이지당 50건을 표시한다.
- 운영 실카드 파일로 테스트할 때 금융 변경 승인을 별도 확인하고, 기본 회귀 테스트는 합성 파일/격리 DB로 수행.

## 6. 테스트 및 수락 게이트

1. 기존 100건 재업로드 → 신규 0, 총 100건 검증, 원본/감사 불필요 중복 0.
2. 기존 70 + 신규 30 → 신규 정확히 30, 전체 100; 자동 분류 후 미완료 원인 정확.
3. 승인번호 동일/다른 카드, 승인번호 없음/반복 금액/가맹점, 취소·재승인, 파일 내부 중복, 날짜·통화·부호 차이.
4. 확정 여행+성격 / 잠정 여행 / 고신뢰 자동 확정 / 수동 잠금 / 여행 삭제·유효하지 않은 ID / 개인 결제 여행 미귀속 각각 완료 판정.
5. 결제·취소 각각 분류 완료지만 원결제 미연결 → 분류율과 금융 대사 경고 분리.
6. 여러 달·연도·날짜 미상, 실패 행 포함 → 전체/월별 합계 일치, 성공 오판 0.
7. 업로드 실패·중간 중단·동시 업로드·재시도·권한/CSRF·모바일/키보드·대용량.
8. 기존 카드/여행/환불/Google 원장 데이터 보호 및 수동 결정 불변 검증.
9. 구현/테스트/PR 병합/운영 배포/실파일 검증은 각기 별도 상태로 보고. 명세만으로 기능 완료 주장 금지.

## 7. 구현 순서

CUV-01 기존 카드 업로드·분류·중복·감사 경로 코드 대조 및 소유 파일 확정
CUV-02 파싱/원천 행 정합성 및 동일성 판정
CUV-03 멱등 신규 등록과 기존 사용자 결정 보호
CUV-04 신뢰도 높은 자동 확정 결정과 여행/성격 완료 판정
CUV-05 환불 별도 대사 및 전수 검증 집계
CUV-06 업로드 직후 요약·월별·미완료 UI
CUV-07 합성 회귀·실제 운영 read-only 검증·별도 배포 수락

이 명세는 기존 카드 분류의 제품 정책을 확장하되, 자동 여행 귀속을 근거 없이 금융 정산 완료로 승격하지 않는다.

## 검증된 대용량 범위

10,000행 합성 CSV를 격리 SQLite의 실제 업로드 dispatch 경계로 실행했다. 첫 업로드 21.230초(T=10,000/E=0/N=10,000), 동일 파일 재시도 26.783초(T=10,000/E=10,000/N=0), 재시도 후 거래 수 10,000건을 확인했다. 응답은 압축 전 compact UTF-8 JSON 기준 각각 27,457,858바이트였다. 이는 단일 합성 환경 측정이며 시간 상한·운영 성능·50,000행의 성능 보장이 아니다. 근거는 [측정 기록](../../tests/results/cuv_api_10k_dispatch_metrics.json)과 [API 검사](../../tests/test_cuv_api_persistence.py)다. 감사 조회는 별도 10,000건 합성 측정에서 첫 실행 0.654초/재실행 0.476초였고 감사 건수는 10,000건을 유지했다.
