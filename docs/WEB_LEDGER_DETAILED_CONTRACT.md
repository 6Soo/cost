# 웹 장부 상세 동작 계약

작성일: 2026-09-24. 설계 문서이며 코드 구현·운영 연결·배포 기록이 아니다.

후속 적용: [후속 명세 8~14절](WEB_LEDGER_SPEC_REFINEMENT.md)의 탭 삭제·직전 수정 복원·입금 분할·작성 정보·교차 동작·자유 이름 편집·수동 보관을 적용한다. 구현의 알려진 결함과 수정 수용 기준은 [구현 검토 R01~R09](WEB_LEDGER_IMPLEMENTATION_REVIEW.md)를 따른다.

이 문서는 [제품 명세](WEB_LEDGER_APP_SPEC.md)와 [구현·검증 계약](WEB_LEDGER_IMPLEMENTATION_CONTRACT.md)의 확정 요구를 작은 동작으로 나눈다. 업무 정책의 정본은 [결정 등록부](DECISION_REGISTER.md)다. 아래 API 이름·화면 상태·예시는 구현 기준이며 사용자가 직접 선택한 정책으로 기록하지 않는다. 예시 ID와 금액은 모두 합성 자료다.

## 1. 구현자가 판단해도 되는 범위

| 구분 | 처리 기준 |
|---|---|
| 확정 정책 | 후보 자동 배치, 상태 숨김, 행 저장, 수동 수정 보호, 직원 조회 범위, owner 전용 출력은 그대로 구현 |
| 상세 구현 기준 | 아래 오류 코드, 요청 필드, 트랜잭션 경계와 같은 동작을 구현. 기존 구조 때문에 이름을 바꾸면 대응표와 이유를 보고 |
| 실행 조건 확인 | 운영비는 무료 선행 시험·유료 전환 별도 승인으로 확정. 공급자 후보의 실제 자원 확보·연결은 후속 명세 19절에 따라 확인하며 관련 경로만 미완료로 남김. Google 로그인·직원 연결 신청 후 소유자 승인·증빙 미리보기만 제공도 확정 |
| 금지 | 미정 정책을 추천값으로 자동 확정, 합성 연결을 실제 연결로 보고, 전체 정규화 재작성, 원본·운영 출력 변경 |

명세가 상세하다는 이유로 명세의 논리 객체마다 테이블·마이크로서비스·검증 단계를 새로 만들지 않는다. 한 애플리케이션과 기존 저장소 어댑터에서 시작한다. 기존 구현을 재사용할 수 있으면 재사용한다. 모델 성능은 실제 작업 결과로 판단하며 문서만으로 구현 정확성을 보장한다고 주장하지 않는다.

## 2. 필드와 객체 경계

API의 `row_id`는 화면의 안정 식별자다. 기존 거래 ID와 구분되며 반드시 기존 원천·거래·분할 관계를 참조한다. 페이지 번호, 정렬 순서, 탭 이동 때문에 바뀌지 않는다. 아래 필드는 논리 계약이며 별도 중복 정규화 DB를 만드는 지시가 아니다.

| 필드 | 의미와 규칙 |
|---|---|
| `row_id` | 수입 사건·수입 배분 또는 지출 투영 행의 안정 ID. 분할 전후 연결은 후속 명세 13절을 따름 |
| `row_kind` | `income` 또는 `expense` |
| `source_kind` | 카드·은행·직접 입력·기존 이관의 출처. 기존 분류와 대응표 작성 |
| `source_event_id` | 기존 원천 사건 참조. 직접 입력은 자체 수입 사건 참조 |
| `display_tab_id` | 현재 화면 위치. 미배정은 null이며 화면의 분류대기 목록에 포함 |
| `revision` | 성공한 실제 행 변경마다 증가. 변화 없는 저장은 증가하지 않음 |
| `occurred_on` | 원천 거래 날짜. 여행 날짜로 대체하지 않음 |
| `amount_krw` | 부호 있는 정수 원화. 실수 반올림으로 원천을 바꾸지 않음 |
| `item`, `description`, `operator_note` | 항목·내용·메모. null과 빈 문자열 처리 기준을 어댑터에서 고정 |
| `manual_overrides` | 사용자가 직접 고친 필드와 해당 변경 사건. 행 전체를 무조건 잠그지 않음 |
| `classification_detail` | 기존 후보·확정 상태와 근거 참조. 기본 표의 표시값과 별개 |
| `allowed_actions` | 현재 권한과 상태에 따른 화면 동작 안내. 서버 권한 검사 대체 불가 |

원화가 아닌 입력의 환산은 기존 파이프라인 근거를 사용한다. 원천 통화·금액·적용 환율을 지우거나 AI로 환율을 만들지 않는다. 화면 합계는 원화 금액이 확인된 행만 대상으로 하며 원화 누락을 0원으로 처리하지 않는다. API는 정수 원화의 정확성을 유지하고 프런트엔드는 안전한 정수 범위를 넘는 값을 실수로 변환하지 않는다.

## 3. 화면과 이동

### 3.1 기본 장부

1. 로그인 사용자에게 허용된 여행 목록을 가져온다. owner는 관리 대상 전체, viewer는 예약 배정과 연결된 여행만 받는다.
2. 왼쪽은 여행 탭 목록이다. 위에는 검색과 owner 전용 탭 추가, 아래에는 owner 전용 분류대기·가져오기 작업 진입점을 둔다. viewer에게 다른 여행의 건수나 전체 분류대기 합계를 노출하지 않는다.
3. 선택한 여행 본문은 수입, 고객별 합계 접기 영역, 지출 순이다. 수입·지출 제목 옆에 해당 구역으로 이동할 수 있는 링크를 둔다.
4. 큰 합계는 선택 여행의 전체 저장 행 기준이다. 검색 중에는 전체 합계와 검색 결과 합계를 구분한다. 화면에 로드한 페이지만 합산하지 않는다.
5. 후보·자동분류 행에 배지·색상·굵기 차이를 두지 않는다. 저장 실패·편집 충돌은 숨기지 않는다. 행 상세에서만 근거와 분류 상태를 확인한다.
6. 다른 탭으로 이동한 행은 복제하지 않는다. 저장 후 원래 목록에서 빠지고 이동 완료 안내에서 목적지로 갈 수 있다. 현재 스크롤을 불필요하게 맨 위로 바꾸지 않는다.
7. 빈 탭은 수입·지출 합계 0과 빈 상태 안내를 보여 준다. 조회 실패 화면을 빈 탭으로 표시하지 않는다.

### 3.2 행 편집 상태

| 현재 상태 | 사용자 동작·사건 | 다음 동작 |
|---|---|---|
| 보기 | 편집 버튼 또는 편집 가능한 셀 선택 | 편집 시작 시 revision과 값을 보관 |
| 편집 중 | 값 변경 | 로컬 초안만 갱신. DB·합계·규칙은 그대로 |
| 편집 중 | 취소 | 초안 폐기, 현재 서버 값 표시 |
| 편집 중 | 저장 | 허용 필드 검사 후 한 요청 전송, 중복 클릭 방지 |
| 저장 중 | 성공 | 서버가 반환한 행·revision·합계로 화면 갱신 |
| 저장 중 | 응답 유실 | 결과 확인 중 표시, 같은 요청 ID로 확인·재시도 |
| 저장 중 | 필드 오류 | 입력 유지, 해당 칸에 오류 표시 |
| 저장 중 | revision 충돌 | 내 초안과 최신 값을 나란히 표시. 강제 덮어쓰기 버튼 없음 |
| 충돌 | 최신 값으로 다시 편집 | 기존 초안을 참고하여 최신 revision에서 새 저장 요청 생성 |

첫 버전은 동시에 한 행을 편집한다. 다른 행·탭으로 이동하려면 저장 또는 취소를 선택한다. 네트워크 단절 중 새 행 편집·오프라인 쓰기 큐는 만들지 않고 현재 초안을 유지한다. 새로고침 후 초안 복구는 미구현일 수 있으므로 닫기 전에 미저장 변경을 안내한다. 개인정보가 포함된 초안을 브라우저 영구 저장 공간에 자동 기록하지 않는다.

저장 이유는 `예외 사항`과 `규칙 변경` 중 선택한다. 메모만 바꾸면 기존 정책대로 AI를 호출하지 않는다. 규칙 변경을 선택한 경우에도 현재 행 저장과 규칙 생성은 별개다. 현재 행 저장 성공 후 규칙 대화를 열고, 대화가 실패해도 저장을 취소하지 않는다.

## 4. 행 저장 API

### 4.1 요청 예시

`POST /api/rows/expense-demo-01/save`

```json
{
  "expected_revision": 4,
  "client_request_id": "save-demo-01",
  "change_mode": "exception",
  "changes": {
    "display_tab_id": "trip-demo-b",
    "item": "교통비",
    "description": "현지 이동",
    "operator_note": "사용자 확인"
  }
}
```

생략한 필드는 유지한다. 비울 수 있는 메모·내용의 명시적 빈 값은 저장하되 null 허용은 스키마에서 일관되게 정한다. 금액·거래일·원천 ID·원천 가맹점 필드가 요청에 섞이면 요청 전체를 거부한다. 불법 필드만 버리고 나머지를 조용히 저장하지 않는다. 권위 근거가 없는 목적지는 자동으로 권위 여행으로 만들지 않는다.

### 4.2 처리 순서와 원자성

1. 인증, owner 권한, 요청 크기·스키마·허용 필드를 검사한다. actor는 인증 세션에서 결정하며 클라이언트가 지정하지 못한다.
2. 요청 중복 키는 사용자·작업 종류·요청 ID 범위로 확인한다. 해시에는 행 ID·expected revision·변경 모드·변경값을 넣는다. 시각과 전송 순서는 의미에 넣지 않는다.
3. 이미 성공한 동일 요청이면 현재 권한을 다시 확인한 후 최초 결과를 반환한다. 변경 내용이 다르면 `REQUEST_ID_REUSED`다. 이미 성공한 요청 재전송을 낡은 revision 오류로 바꾸지 않는다.
4. DB 트랜잭션 안에서 현재 revision과 목적지 유효성을 확인한다. 조건부 갱신 또는 적절한 잠금으로 다른 저장과 경합하지 않게 한다.
5. 실제 변경이 없으면 `outcome=unchanged`로 응답하고 revision·변경 사건·AI 작업을 늘리지 않는다. 외부 전기 중복 방지가 구현됐다는 의미로 설명하지 않는다.
6. 행 변경, 변경 사건, 수동 고정 필드, 학습 사례, 영향 합계, 요청 결과를 한 트랜잭션으로 저장한다. 기존 사건 저장소와 별도 JSON 파일에 나눠 먼저 쓰지 않는다.
7. 커밋 뒤 성공을 반환한다. `rule_change`이면 대화 생성에 필요한 사례 ID를 반환한다. LLM 호출은 DB 트랜잭션 밖에서 수행한다. 대화 생성 재시도도 사례 ID 기준으로 중복되지 않게 한다.

합계를 별도 저장하지 않고 조회 계산하는 구현도 가능하다. 별도 저장하면 행과 같은 트랜잭션에서 갱신해야 한다. 메시지 큐나 별도 집계 서비스는 필수가 아니다.

### 4.3 성공·오류 계약

```json
{
  "outcome": "saved",
  "row_id": "expense-demo-01",
  "revision": 5,
  "event_id": "change-demo-01",
  "affected_tab_ids": ["trip-demo-a", "trip-demo-b"],
  "learning_case_id": null,
  "request_id": "save-demo-01"
}
```

실제 응답은 갱신된 행과 두 탭의 합계를 포함하거나 같은 저장 버전으로 재조회할 수 있는 정보를 포함한다. 과거 응답이 늦게 도착해도 클라이언트는 현재보다 낮은 revision으로 화면을 되돌리지 않는다.

| HTTP 상태 | 오류 코드 | 화면 처리 |
|---|---|---|
| 401 | `AUTH_REQUIRED` | 재로그인 안내. 저장 성공으로 표시하지 않음 |
| 403 | `ACTION_FORBIDDEN` | 해당 동작 불가 안내 |
| 404 | `RESOURCE_NOT_FOUND` | 존재하지 않거나 조회 권한 없는 행·탭에 동일 응답 |
| 409 | `EDIT_CONFLICT` | 허용 범위 내 최신 행·revision과 내 초안을 비교 |
| 409 | `REQUEST_ID_REUSED` | 같은 ID의 다른 요청 거부. 자동으로 새 ID를 발급해 재시도하지 않음 |
| 422 | `FIELD_READ_ONLY`, `INVALID_VALUE`, `TARGET_NOT_ASSIGNABLE` | 문제 필드와 이해할 수 있는 메시지 표시 |
| 503 | `TEMPORARILY_UNAVAILABLE` | 초안 유지, 동일 요청의 결과 확인·재시도 |

DB 경로·SQL·키·원본 고객 정보를 오류 메시지에 포함하지 않는다. 오류 응답은 `code`, 사용자 메시지, 필요한 필드 오류, 추적 ID를 제공한다. 과거 초안의 assign API를 유지한다면 이 저장 서비스에 위임한다. 별도 배정 저장 로직을 만들거나 모든 배정에서 AI를 자동 시작하지 않는다.

## 5. 업로드 진행과 재개

카드·은행 파일은 공통 접수 상태를 사용할 수 있지만 파서와 사건 정규화는 기존 도메인 경계를 유지한다. 한 원본 행이 여러 이벤트를 만들 수 있으므로 다음 집계를 분리한다.

- 원본 행: 대상 데이터 행 수, 읽음, 오류, 설명 있는 제외. 머리글·합계·빈 행의 제외 기준은 프로필에 기록한다.
- 정규화 이벤트: 신규, 이미 존재함, 식별자 충돌, 처리 중. 서로 겹치지 않는 처리 결과다.
- 화면 배치: 신규 이벤트 중 여행·기타 대상·분류대기. 기존 분할 사건은 이벤트 수와 화면 행 수를 따로 센다.

종료 후에만 `대상 원본 행 수 = 읽음 + 오류 + 제외`가 성립해야 한다. 실행 중에는 미처리 수를 추가한다. 서로 다른 단위의 수를 더해 진행률을 만들지 않는다. 전체 수를 아직 모르면 퍼센트 대신 처리 건수만 표시한다.

| 사건 | 반드시 일어나는 동작 |
|---|---|
| 동일 업로드 요청 재전송 | 동일 작업 반환, 새 처리 작업 생성 안 함 |
| 동일 파일을 새 요청으로 업로드 | 기존 봉인 파일·거래 결과 재사용. 과거 실패를 완료로 위장하지 않음 |
| 기간이 겹친 다른 파일 | 원천 링크 추가와 신규 거래만 반영. 같은 값의 별개 거래 유지 |
| 프로세스 중단 | 마지막 커밋 커서부터 재개. 사건 저장과 커서 저장이 한 트랜잭션 |
| 브라우저 닫힘 | 서버 작업은 유지. 다시 열면 작업 상태·결과 조회 |
| 진행 응답이 늦게 도착 | 증가하는 작업 revision으로 과거 진행 표시 무시 |
| 원천 파일 변조·해시 불일치 | 해당 작업 차단, 기존 정상 장부는 유지 |

API는 접수 결과와 작업 ID를 먼저 반환하고 진행 조회를 제공한다. 첫 버전은 적당한 간격의 폴링으로 충분하며 실시간 표시를 위해 별도 메시지 플랫폼을 도입할 필요는 없다. 완료·실패 시 폴링을 종료한다. 업로드 한도를 서버와 화면에 같은 값으로 설정하고 초과 파일에는 이유를 표시한다. 수치 한도는 실제 파서·호스팅 측정 후 정하며 확인 없이 대용량 지원을 주장하지 않는다.

## 6. 규칙 초안에서 적용까지

### 6.1 단계

`행 저장 → 사례 생성 → 필요한 질문 → 규칙 초안 → 영향 미리보기 → 범위 선택 → 적용`

- 질문은 한 사례에서 필요한 1~5개까지만 만든다. 사용자가 이미 답한 내용은 다시 묻지 않는다. 답이 부족하면 사실을 추정하는 대신 규칙을 초안으로 남긴다.
- 모델은 허용된 필드·연산자만 가진 구조화 초안을 반환한다. 코드·SQL·알 수 없는 필드·금액 변경 효과를 포함하면 실행하지 않는다.
- 특정 여행 배정 효과는 여행 ID·연도·적용 범위가 있어야 한다. 동일 가맹점의 미래 모든 거래를 과거 여행에 보내지 않는다.
- 영향 미리보기는 서버가 계산한다. 포함 행, 수동 고정으로 제외한 필드·행, 충돌 행, 변경 전후 합계와 이유를 보여 준다.
- 미래 규칙은 아직 존재하지 않는 거래의 목록이나 금액을 제시하지 않는다. 미래 조건과 대상 범위만 설명한다.

### 6.2 범위 선택의 네 가지 결과

| 기존 행 적용 | 미래 입력 적용 | 결과 |
|---|---|---|
| 아니요 | 아니요 | 초안 저장, 행 변경·규칙 활성화 없음 |
| 예 | 아니요 | 확인한 기존 행만 변경, 이후 새 입력에는 비활성 |
| 아니요 | 예 | 기존 행 변경 없음, 새 사건에만 규칙 활성화 |
| 예 | 예 | 확인한 기존 행 변경과 새 사건용 규칙 활성화 |

미래 입력의 경계는 최초 사건 등록 순서로 고정한다. 과거 거래일의 사건이 규칙 활성화 이후 처음 들어오면 규칙의 날짜·여행 조건 안에서 평가한다. 이미 있는 거래의 재업로드는 새 사건이 아니다. 활성화 경계와 사건 등록이 경합하지 않도록 저장 순서를 정의한다.

### 6.3 적용 요청과 충돌

`POST /api/classification/rules/apply`는 `preview_id`, 초안 revision, `apply_existing`, `apply_future`, 선택 행 ID·revision, `client_request_id`를 받는다. 미리보기의 규칙 해시와 선택 범위를 서버에서 대조한다.

선택 행 중 하나라도 변경되거나 규칙 기준 버전이 달라졌으면 첫 버전은 요청 전체를 `PREVIEW_STALE`로 거부한다. 일부 행만 조용히 적용하지 않는다. 새 미리보기에서 변경된 행을 구분하고 사용자가 범위를 다시 선택한다. 정상 적용은 규칙 버전·선택 행 변경·이력·요청 결과를 원자적으로 저장한다. 대규모 분할 적용이 실제 필요해지면 별도 설계하며 중간 실패를 성공으로 표시하지 않는다.

수동 고정은 필드별로 적용한다. 여행만 직접 고친 행의 항목까지 자동으로 잠그지 않는다. 반대로 수동 항목을 새 규칙이 변경하지 못한다. 규칙 활성화·비활성화가 사용자의 수동 고정을 해제하지 않는다. 고정 해제 UI는 별도 선택 전에는 제공하지 않는다.

## 7. AI 대화와 연결 장애

한 사용자 메시지에 앱의 `turn_id`를 한 번 발급한다. Muse 시도와 Gemini 시도는 같은 turn_id 아래 서로 다른 attempt_id다. 사용자 답변을 저장한 뒤 모델을 호출하고, 채택한 응답은 턴당 하나만 남긴다.

공통 문맥에는 행 ID·revision, 가명화된 관련 필드, 적용 중인 규칙 버전, 사용자 답변 원문, 아직 답하지 않은 질문, 초안, 짧은 요약을 포함한다. 요약이 사용자 답변 원문을 대체하지 않는다. 관계없는 여행·전체 장부·인증정보는 넣지 않는다. 제공자가 바뀌어도 다음 질문이 앞선 답과 모순되지 않는지 합성 사례로 확인한다.

PC가 꺼짐을 확인하면 다음 질문마다 긴 로컬 연결 시도를 반복하지 않는다. 설정된 서버 Gemini를 사용하고 AI 패널에 제공자를 표시한다. 무료 한도 소진이면 대화만 대기하며 현재 행·규칙 초안·질문 답변은 보존한다. Muse가 복귀하면 다음 턴부터 사용한다. 같은 턴에 두 응답을 섞거나 자동으로 규칙을 적용하지 않는다.

모델이 반환하는 영향 건수·합계는 신뢰하지 않는다. 실제 영향값은 미리보기 API 결과만 표시한다. 모델을 추가 호출해서 모델의 답변을 검증하는 절차를 기본으로 두지 않고 스키마·허용 필드·revision·사용자 확정으로 경계를 지킨다.

## 8. 출력과 접근 범위

출력 화면은 선택 여행, 순서, 각 수입·지출 행 수와 합계, 미저장 편집 여부를 먼저 보여 준다. 기술 해시는 상세 정보로 접어 두며 기본 화면에서 읽도록 요구하지 않는다.

1. owner 권한과 선택 탭 목록을 검사한다. 빈 선택, 중복 탭 ID, 없는 탭은 구분해 처리한다.
2. 미저장 편집을 해결한 뒤 선택 탭의 일관된 저장 버전을 고정한다. 출력 중 새 편집이 발생해도 한 파일에 이전 값과 새 값이 섞이지 않는다.
3. 선택 순서대로 탭마다 시트를 만든다. 시트명이 길거나 금지 문자가 있으면 Excel 제약에 맞게 치환·축약하며 이름 충돌은 안정적인 접미사로 구분한다. 원래 탭 ID·이름과 출력 시트명 대응은 출력 기록에 저장한다. 같은 이름 때문에 시트를 덮어쓰지 않는다.
4. `매출자료 양식_rev`의 구조를 복제한다. 슬롯을 넘는 행과 수식 범위·인쇄 영역을 함께 확장한다. 현재 화면의 후보 배치와 저장된 수정을 그대로 사용한다.
5. 새 파일을 완성하고 필요한 한 번의 출력 검증을 수행한 뒤 다운로드 가능으로 전환한다. 출력 검증 때문에 전체 대사나 AI를 호출하지 않는다.
6. 출력 중 실패하면 미완성 파일은 다운로드하지 못하게 하고 기존 출력은 유지한다. 재시도는 같은 입력 스냅샷을 사용하거나 새 스냅샷임을 명시한다.

미확정 행도 화면대로 출력한다는 사용자 답변이 확정됐다. 출력 대화창에 미확정 건수와 안내를 표시하며 파일에 별도 상태 표기나 안내 시트를 넣지 않는다. 후보가 포함되어도 원래 회계 상태·release_eligible은 변하지 않는다. 파싱 오류로 생성되지 않은 행이나 저장되지 않은 편집을 출력값으로 만들지는 않는다.

viewer는 xlsx 출력 생성뿐 아니라 작업 상태·다운로드 경로·과거 파일 목록에도 접근할 수 없다. 공개 다운로드 URL로 우회하지 않도록 인증된 다운로드를 사용한다. 원본 카드·은행 파일 하나에는 여러 여행이 있으므로 담당 여행을 볼 수 있다는 이유로 원본 전체 파일을 직원에게 제공하지 않는다. 직원은 고객 이름·닉네임·예약번호와 해당 여행 증빙까지 조회하되 내부 메모·수정 이력·AI 대화는 받지 않는다. 증빙 조회 경로는 아래 권한 계약을 따른다.

## 9. 합성 기준 자료와 기대값

자동분류 선택 결과를 주입해 화면 어댑터를 검증한다. 이 자료만 통과했다고 기존 분류 엔진이나 실제 카드 파서를 검증했다고 보고하지 않는다. ID는 테스트 내 기호이며 실제 DB ID를 하드코딩하지 않는다.

| 사건 | 내용 | 배치·표시 금액 |
|---|---|---|
| C1 | 구매 100000원, 후보 목적지 A | A 지출 100000원, 기본 표에 후보 배지 없음 |
| C2 | 원천에서 확인된 취소 -20000원, 목적지 A | A 지출 -20000원, 관계 근거 보존 |
| C3 | 구매 30000원, 목적지 없음 | 분류대기 지출 30000원 |
| C4 | 구매 100000원, 날짜·가맹점은 C1과 같지만 다른 원천 거래 ID | A 지출 100000원, C1과 합치지 않음 |
| I1 | 고객 U1 예약금 500000원 | A 수입 500000원 |
| I2 | 고객 U1 잔금 300000원 | A 수입 300000원, I1과 별도 행 |
| I3 | U1과 표시 이름이 같은 고객 U2 예약금 200000원 | A 수입 200000원, U1과 합치지 않음 |

최초 A의 수입은 1000000원, 지출은 180000원, 회사수익인식은 820000원이다. 고객 U1 합계는 800000원, U2는 200000원이다. 분류대기 30000원을 A 지출에 더하지 않는다.

C1을 B로 저장하면 A 지출은 80000원, B 지출은 100000원이다. A 회사수익인식은 920000원, 수입이 없는 B는 -100000원이다. 취소 C2는 C1 이동만으로 따라 옮기지 않는다. 연결 사건의 일괄 이동 기능은 별도 명시가 없으면 구현하지 않는다.

| 시나리오 | 합격 조건 |
|---|---|
| C1 이동 요청 응답 유실 후 재전송 | C1 변경 사건 하나, 위 합계 유지 |
| 같은 요청 ID로 C1 목적지를 A로 바꿔 재전송 | 충돌, 추가 변경 없음 |
| C1의 금액을 바꾸는 요청 | 요청 전체 거부, 행·합계·이력 유지 |
| C1 원본 재업로드 | B 수동 배정 유지, 새 지출 없음 |
| C1 메모만 편집 | 원천 파싱 0회, 전체 대사 0회, AI 0회, 합계 동일 |
| 규칙 미리보기 이후 대상 행을 직접 변경 | 이전 미리보기 적용 거부, 자동 부분 적용 없음 |
| A·B 출력 | 두 시트, 출력 버전의 행별 금액과 합계 일치 |
| A 담당 viewer가 B 행 ID 요청 | B의 존재·금액·근거 노출 없음 |
| viewer가 owner의 출력 작업 ID 요청 | 다운로드와 상태 조회 모두 거부 |
| Muse 실패 후 Gemini 응답, 늦은 Muse 응답 도착 | 채택 응답 하나, 사용자 답변과 기존 행 저장 유지 |

직접 수입 입력 후 은행 파일을 가져오는 사례는 별도 자료로 검사한다. 동일 입금이 확정 연결된 뒤 사건 수와 총수입이 늘지 않아야 한다. 같은 금액·입금자지만 서로 다른 실제 입금은 유지한다. 정정 기대값은 아래 수입 정정 계약을 따른다. 실제 환불은 정정과 별개 사건이며 원래 부호를 보존한다.

## 10. 구현자에게 나눠 줄 작업

아래 W 번호는 기능 식별자다. 실행 순서는 [단계별 진행표](WEB_LEDGER_PHASES.md)를 따르며 현재 Phase에 포함된 작업만 전달한다. 기존 파일과 해당 절만 첨부하고 전체 대화·원장을 반복 전달하지 않는다. 구현자는 작업에 필요한 기존 함수·마이그레이션을 확인한 뒤 코드 변경을 시작한다. 실제 모듈명은 현재 저장소 구조에 맞추되 별도 정규화 체계를 만들지 않는다.

| 작업 | 구현 범위 | 완료 증거 | 선행 조건 |
|---|---|---|---|
| W01 | 기존 사건 저장소·투영 어댑터와 합성 자료 | 기존 ID 대응표, C1~I3 조회·합계 | 없음 |

| W04 | 카드 업로드·작업 진행·재개 | 중복 파일·중간 중단·오류 보존 사례 | W01 |

| W07 | Muse·Gemini 어댑터와 문맥 | 합성 장애 전환·무료 한도·늦은 응답 검사 | W06, 실제 호출은 모델 가용성·키 필요 |
| W08 | 선택 시트 출력 | 저장 스냅샷·시트명 충돌·슬롯 초과·행별 값 검증 | W01 |
| W09 | 로그인·예약 배정·권한 경계 | 타 여행 차단·담당 해제·종료 여행 조회·출력 차단 | Google 인증 설정, 예약 API 계약 구현 |
| W10 | 이관·복구·대표 흐름 | 차이 목록·복구 결과·실측 성능과 호출 수 | 실제 기준본·호스팅 확인 |

각 작업의 검증은 위험한 경계와 사용자가 체감하는 결과에 집중한다. 같은 결과를 여러 모델·전체 파이프라인·반복 수동 감사로 중복 검증하지 않는다. 관련 코드가 바뀌지 않았고 검증이 통과했다면 다음 작업으로 진행한다. 화면 구현 완료는 API 테스트만으로 인정하지 않고 합성 자료로 브라우저에서 실제 동작을 확인한다.

완료 보고는 실제 모델 공급자·ID, 변경 파일, 실행한 검사와 결과, 아직 합성인 연결, 미정 정책으로 남긴 기능을 포함한다. 공개 배포·실제 원천 쓰기·외부 전기는 이 문서의 완료 조건에 포함되지 않는다.

## 11. 수입 정정과 최초 이관

### 11.1 수입 정정

사용자 확정: 직접 입력한 날짜·금액은 편집하고 은행 원본은 별도 정정 기록으로 처리한다. 다음 화면·합계 규칙은 그 결정을 구현하기 위한 기준이다.

- 직접 입력 편집은 기존 수입 사건의 현재 표시값을 바꾸되 원래 값과 변경 이력을 남긴다. 500000원을 450000원으로 고치면 현재 수입은 450000원이며 두 값을 더하지 않는다. 요청에는 expected_revision과 client_request_id가 필요하다.
- 은행 원본 편집 버튼 대신 `정정 기록`을 제공한다. 원래 값, 장부에 반영할 정정값, 이유를 표시하고 정정 전후 차액과 합계 변화를 미리 보여 준다. 정정은 원천 거래를 변경하는 기능이 아니다.
- 은행 수입 500000원을 장부에서 450000원으로 정정하면 원천 500000원과 연결된 정정 사건을 보존하고 현재 장부 표시·합계는 450000원이다. 원본과 정정 전체값을 더해 950000원으로 계산하지 않는다. 기본 표에는 실제 입금 사건 하나를 유지하고 상세에서 원천과 정정을 비교한다.
- 다음 정정으로 470000원을 지정하면 현재 표시는 470000원이다. 최초 원천은 그대로이며 두 정정 사건이 순서대로 남는다. 정정 요청 재시도는 정정 사건을 늘리지 않는다.
- 날짜 정정만으로 여행을 자동 이동하지 않는다. 고객·여행 연결 수정은 별도 허용 필드와 수동 고정 계약을 따른다. 은행 원천의 서명·해시를 정정값으로 재작성하지 않는다.
- 실제 환불은 정정값으로 원입금을 지우는 방식으로 처리하지 않는다. 별도 환불 사건과 부호를 유지하며 관련 수입과의 관계를 보존한다.
- 직접 입력 수입에 은행 원천이 확정 연결되면 이후 금액·날짜 변경은 은행 정정 경로를 사용한다. 은행 근거를 붙였다는 이유로 원래 수동 편집 이력을 삭제하지 않는다.

위 방식은 정정 사건을 원입금과 중복 합산하지 않기 위한 구현 기준이다. 분할하지 않은 입금은 한 행이며 사용자가 분할한 입금은 후속 명세 10절의 배분 행을 표시한다. 정정으로 분할 원금이 바뀌면 배분안과 함께 원자적으로 저장한다. 정정 사건 자체를 수입 추가 행으로 더하지 않는다.

### 11.2 최초 이관 차이 선택

1. 사용자가 지정한 구글 장부 기준본과 파이프라인 DB의 읽기 전용 스냅샷을 각각 봉인한다. 최신본 여부를 확인하지 못했으면 확인 못 한 것으로 기록한다.
2. 원천·거래 식별자와 검증된 연결로 동일 사건을 대응한다. 같은 이름·날짜·금액만으로 불확실한 두 행을 자동 병합하지 않는다.
3. 대응된 동일값은 차이 선택 목록에서 제외하되 이관 집계에는 포함한다. 다른 값, 장부에만 존재, DB에만 존재, 대응 불명확을 구분한다.
4. 비교 화면은 여행, 필드, 구글 장부값, DB값, 근거, 선택값을 제공한다. 같은 행에서 항목은 구글 값·메모는 DB값처럼 필드별 선택이 가능하다. 미선택을 임의 기본값으로 저장하지 않는다.
5. 카드·은행 원천 금액·날짜가 다른 경우는 단순 표시값 선택과 구분한다. 구글 표시값 선택으로 카드 원천을 바꾸지 않고 원천 불일치로 보존한다. 은행 수입은 정정 계약으로 연결한다. 카드 불일치의 업무 처리 결정이 없으면 해당 건만 미해결로 남긴다.
6. 사용자 선택은 비교 ID, 양쪽 입력 해시, 선택 필드·값, 사용자, 시각에 묶는다. 입력이 바뀌면 선택을 조용히 재사용하지 않고 영향 항목만 재비교한다.
7. 초기에는 별도 이관 작업 DB에 결과를 만들고 원본 구글 파일·운영 DB를 변경하지 않는다. 반복 실행해도 같은 사건과 선택 기록이 중복되지 않아야 한다.
8. 미해결 건수, 이관한 사건 수와 부호 있는 합계, 누락된 업무 필드·메모·증빙 링크를 보고한다. 합계가 같다는 이유만으로 완전 이관을 선언하지 않는다. 운영 기준 전환은 사용자가 이 결과를 확인한 뒤 별도 단계에서 수행한다.

## 12. 표·합계·입력의 화면 계약

이 절은 확정 정책을 구현할 때 화면마다 해석이 달라지는 것을 막는 기준이다. 수기 지출·모바일·직원 상세 조회에 관한 후속 확정은 아래 15~17절을 따른다. 역할과 원천 종류에 따른 편집 범위를 구분한다.

### 12.1 수입 행과 고객별 합계

수입 표는 `거래일자 / 이름 / 닉네임 / 예약금 / 잔금 / 추가금 / 금액` 순서를 유지한다. 화면 행 하나는 한 입금 종류에 속하고 그 금액을 해당 열에 표시한다. 한 원천을 여러 종류로 나누면 각 배분을 별도 행으로 표시한다. 다른 종류 칸은 빈칸으로 표시하며 내부 계산에서는 0으로 취급한다. 금액 열은 세 종류의 합계이며 별도로 편집하지 않는다. 원천에서 확인된 0원과 값 자체가 없는 오류는 구분한다.

예시: U1의 예약금 500000원과 잔금 300000원은 두 행이다. 첫 행은 예약금 500000원·금액 500000원, 둘째 행은 잔금 300000원·금액 300000원이다. 고객 요약은 U1 800000원을 한 번 표시한다. 표 아래 총수입은 800000원이며 고객 요약을 다시 더하지 않는다.

수입 신규 입력 폼은 다음 순서를 따른다.

1. 현재 여행을 기본 표시한다. 다른 여행으로 입력할 때만 여행 선택을 바꾼다.
2. 실제 거래일과 입금액을 입력한다. 사용자가 지정하지 않은 실제 거래일을 오늘 날짜로 저장하지 않는다. 오늘 날짜를 제안한다면 저장 전에 보이는 입력값이어야 한다.
3. 예약금·잔금·추가금을 선택한다. 거래 금액만으로 종류를 자동 추정하지 않는다.
4. 고객 검색 결과에서 이름·닉네임과 구분에 필요한 최소 정보를 보여 준다. 같은 이름을 가진 두 고객은 두 선택지다. 원본 계좌번호나 다른 여행 예약 내역을 구분용으로 무제한 노출하지 않는다.
5. 아직 고객을 정하지 못했으면 연결 대기로 보존한다. 가짜 고객을 만들거나 이름이 같은 기존 고객에게 자동 연결하지 않는다.
6. 저장 전 여행·거래일·금액·종류·고객을 한 줄로 요약한다. 입력 완료 후 행 단위 저장하며 별도 승인 절차를 반복 추가하지 않는다.

고객별 합계는 현재 여행 범위에서 계산한다. owner가 여러 여행의 통합 고객 합계를 조회하는 별도 기능은 첫 버전에 자동 추가하지 않는다. 직원 조회는 권한 있는 여행 범위를 항상 적용한다.

### 12.2 합계와 미배정

| 위치 | 포함하는 행 | 포함하지 않는 값 |
|---|---|---|
| 여행 수입 합계 | 해당 탭에 현재 배치된 유효 수입 사건의 표시 금액 | 고객 요약, 미배정 수입, 이전 정정값 |
| 여행 지출 합계 | 해당 탭의 지출 투영 금액, 후보 포함 | 다른 탭의 분할금액, 분류대기 지출, 원천 오류 |
| 회사수익인식 | 같은 저장 버전의 수입 합계에서 지출 합계를 뺀 값 | AI가 추정한 합계, 다른 시점의 집계 |
| 분류대기 | 미배정 수입과 지출을 구분한 건수·금액 | 이미 여행에 배치된 후보, 파싱 실패를 0원으로 바꾼 값 |

필터를 켜면 `전체 수입`과 `검색 결과 수입`처럼 이름을 분리한다. 전체 합계를 검색 결과 합계로 조용히 교체하지 않는다. 출력은 확정 정책대로 선택 여행 전체 저장 행을 대상으로 하며 검색 필터 적용 여부를 출력 대화창에서 안내한다.

현재 여행의 일부 행을 아직 로드 중일 때 합계는 서버가 반환한 전체 집계를 사용한다. 집계 응답이 없으면 `불러오는 중`으로 표시하며 0원으로 대신 표시하지 않는다. 페이지를 추가로 읽는 과정에서 같은 row_id를 두 번 합산하지 않는다.

### 12.3 키보드와 오류 안내

- Tab은 편집 가능한 칸과 저장·취소 버튼을 순서대로 이동한다. 읽기 전용 금액 칸을 편집 가능한 것처럼 보이게 하지 않는다.
- Enter만으로 행 전체를 조용히 저장하지 않는다. 줄바꿈이 필요한 내용·메모 입력을 방해하지 않는다. 별도 저장 단축키를 제공하면 화면에서 확인할 수 있어야 한다.
- Escape는 현재 편집 취소 동작이며 이미 저장한 변경을 되돌리지 않는다. 미저장 변경을 버리는 경우 취소 의사를 확인하고 초점을 원래 행으로 돌린다.
- 필수값 오류는 해당 입력 칸 옆에 표시하고 첫 오류로 초점을 이동한다. 색상만으로 오류를 알리지 않는다.
- 저장 성공은 행 근처의 짧은 안내로 표시한다. 매 저장마다 전체 화면을 가리는 확인창을 띄우지 않는다.
- 저장 실패 시 초안을 유지한다. 서버에서 금액·날짜를 거부했다면 일반 연결 오류라고 표시하지 않고 해당 필드가 고정임을 안내한다.
- 드롭다운은 검색과 키보드 선택을 지원한다. 권위 근거가 부족해 선택 불가한 여행이 표시되는 경우 선택 불가 이유를 함께 표시한다.
- 기본 테이블은 행과 열 머리글을 보조 기술에서 구분할 수 있게 한다. 고정 머리글·가로 스크롤이 편집 버튼을 가리지 않도록 확인한다.

## 13. 규칙 대화의 구체적인 예

다음은 합성 예시이며 미리 정해진 다섯 질문을 매번 묻는 설문이 아니다. 이미 저장된 사용자 답변과 규칙으로 확인되는 내용은 질문에서 제외한다. 대화가 길어져도 규칙 확정을 위한 질문은 한 사례에서 최대 다섯 개로 제한하고, 조건이 부족하면 초안으로 남긴다. 사용자가 추가 설명하거나 기존 답을 고치는 것은 허용한다.

### 13.1 여행 배정 오류를 고친 경우

입력 상황: 후보로 A에 들어간 C1을 사용자가 B로 이동하고 `규칙 변경`을 선택했다.

1. 먼저 `C1을 B로 옮겨 저장했어요`를 표시한다. AI 응답을 기다려야 행 이동이 완료되는 구조가 아니다.
2. AI가 이미 아는 값은 다시 묻지 않는다. 가맹점·카드 종류·거래 방향과 이동 전후 여행은 앱 문맥에 있다.
3. 원인이 없으면 `이번 거래를 B로 판단한 근거는 무엇인가요?`를 묻는다. 일정·예약 근거, 가맹점의 특정 서비스, 이번 건만의 예외를 구분할 수 있는 선택지와 자유 입력을 제공한다.
4. `이번 건만`이라는 답이면 영구 규칙을 만들지 않는다. 현재 행의 예외와 사용자의 설명을 남기고 대화를 마친다.
5. 반복 가능한 근거라면 아직 불명확한 기간·여행 범위만 추가 질문한다. 새 일반 권위 일정을 AI가 생성하지 않는다.
6. 마지막에 `어떤 거래에 / 무엇을 바꾸는지 / 언제까지 적용하는지 / 제외되는 거래`를 짧게 설명하고 영향 미리보기로 이동한다.

이미 답이 충분하면 추가 질문 없이 규칙 초안을 보여 줄 수 있다. 질문 최소 개수를 채우려고 아는 내용을 묻지 않는다. 사용자가 새로운 업무 근거를 제시해 기존 권위 규칙과 충돌하면 충돌을 설명하고 해당 범위만 초안으로 남긴다.

### 13.2 항목만 바꾸는 경우

입력 상황: 가맹점 `DEMO TRANSIT`, 카드 종류 K1, 구매 방향인 행의 항목을 교통비로 수정했다. 여행 이동은 하지 않았다.

규칙 효과는 항목 변경으로 한정한다. `같은 가맹점·카드·구매 방향의 거래를 교통비로 분류`하는 초안을 만들되, 모든 여행을 특정 여행으로 옮기는 효과를 추가하지 않는다. 가맹점이 여러 서비스를 파는 상황이라면 항목을 구분하는 조건이 필요한지만 묻는다. 취소·환불 방향은 기존 관계·규칙에 따라 별도로 처리하며 구매용 규칙을 임의 확장하지 않는다.

### 13.3 메모만 바꾸는 경우

메모 오타나 개인 참고사항의 저장은 AI 호출 없이 끝난다. 사용자 메모를 모든 미래 행에 복사하는 규칙을 자동으로 만들지 않는다. 사용자가 명시적으로 메모를 근거로 규칙 대화를 열면 그때 관련 사례만 전달한다.

### 13.4 대화를 중단하거나 제공자가 바뀌는 경우

사용자가 패널을 닫으면 현재 행 저장과 답변은 유지하고 규칙 초안은 미적용으로 둔다. 재개 시 `이미 답한 내용 / 남은 질문 / 아직 적용하지 않은 초안`을 보여 준다. 모델이 바뀌었다는 이유로 첫 질문부터 다시 시작하지 않는다. 이전 설명과 상충하는 답이 나오면 자동 적용하지 않고 같은 초안의 변경점으로 표시한다.

## 14. 실제 파이프라인과 화면의 검증 경계

구현자가 합성 화면에 임의 성공값을 넣은 뒤 전체 기능 완료로 보고하지 않도록 아래 근거 수준을 구분한다.

| 근거 수준 | 증명하는 범위 | 증명하지 않는 범위 |
|---|---|---|
| 합성 화면 | 화면 배치·버튼·표시·정해진 합계 | 실제 카드 파싱·예약 연결·모델 호출 |
| 합성 API·작업 DB | 요청 검증·저장·재시도·트랜잭션·권한 경계 | 운영 DB 이관 성공·운영 인증 설정 |
| 기존 파서와 합성 파일 | 지원 프로필의 파싱·정규화 어댑터 | 아직 확인하지 않은 은행·카드 형식 |
| 실제 원천 읽기 전용 검사 | 해당 파일 구조·원천 연결·행별 대조 | 운영 쓰기·배포·외부 전기 |
| 실제 제공자 호출 | 기록한 시점의 모델 ID·연결·응답 | 미래 가용성·무료 유지·항상 동일한 답변 |

검증 결과에는 위 수준을 표시한다. UI의 개발용 성공 응답·역할 전환·합성 지연 시뮬레이터가 운영 경로에 남지 않게 단계 종료 시 확인한다. 모델 성능을 보완하려고 여러 모델의 승인 절차를 추가하지 않는다. 규칙 효과의 허용 필드, 의미 있는 경계 사례, 사용자 확인 화면으로 구현 결과를 판단한다.

## 15. 수기 지출 입력과 편집

사용자 확정: 카드에 없는 현금·계좌이체 지출은 직접 추가하고 날짜·금액도 편집하며 이력을 보존한다. 실제 원천 종류에 따라 API 허용 필드를 정한다. 클라이언트가 `source_kind=manual`을 붙였다는 이유로 카드 행을 편집할 수 없어야 한다.

| 원천 | 날짜·금액 | 여행·항목·내용·메모 | 이력 |
|---|---|---|---|
| 카드 지출 | 고정 | owner 편집 가능 | 원천과 변경 사건 보존 |
| 수기 지출 | owner 편집 가능 | owner 편집 가능 | 이전·새 값 보존 |
| 직접 입력 수입 | owner 편집 가능 | 수입 종류에 맞는 필드 편집 | 이전·새 값 보존 |
| 은행 수입 | 원천 고정, 별도 정정 | 고객·여행 연결과 허용된 업무 필드 | 원천·정정 사건 보존 |

수기 지출 추가 버튼은 지출 구역 제목 옆에 둔다. 날짜, 지급 수단(현금·계좌이체), 항목, 내용, 부호 있는 원화 금액, 여행, 메모를 받는다. 원천 증빙이 아직 없다는 사실만으로 사용자가 입력한 비용을 삭제하지 않는다. 증빙 연결은 별도 기록이며 입력한 현금 지출을 카드 원천으로 위장하지 않는다. 예약번호·기간·증빙유형은 기존 양식과 연결하되 여행 전체기간을 서비스 기간으로 자동 채우지 않는다.

신규 수기 입력은 client_request_id로 중복 저장을 막는다. 수정은 expected_revision을 요구하며 날짜·금액·합계·변경 사건을 한 트랜잭션에 반영한다. 날짜 수정만으로 현재 여행 배정을 자동으로 바꾸지 않는다. 분류에 영향을 줄 수 있으면 행 상세에 검토 사유를 기록하되 현재 수동 배정을 보존한다.

예시: B 여행의 수기 지출 25000원을 27000원으로 수정하면 현재 표에는 27000원인 행 하나만 있고 합계는 2000원 증가한다. 이력에는 25000원과 27000원이 남는다. 수정 요청을 다시 보내도 2000원이 또 더해지지 않는다. 같은 API에 카드 거래 ID를 보내 금액 변경을 요청하면 거부한다.

수기 입력과 나중에 가져온 카드·은행 원천이 같은 사건일 가능성은 후보로 표시한다. 날짜·금액·내용이 같다는 이유만으로 병합·삭제하지 않는다. 확정 연결 시 실제 비용은 한 번만 합산하고 원래 수기 입력과 원천 계보는 보존한다. 미확정 중복 후보를 거래 누락 없이 보존하는 처리는 기존 원천 동일성 계약을 따른다.

## 16. 직원·대장 조회와 증빙

계정 연결 상태·예약 배정 동기화 실패·권한 해제·브라우저 캐시·혼합 증빙 제공과 Google 로그인·직원 연결 신청은 [후속 명세 15~16절](WEB_LEDGER_SPEC_REFINEMENT.md)을 적용한다. 직원 증빙은 미리보기만 제공한다.

사용자 확정: 담당 여행의 고객 이름·닉네임·예약번호·증빙을 조회한다. 내부 메모·수정 이력·AI 대화는 숨기며 xlsx 출력도 허용하지 않는다.

| 요청 | viewer 서버 응답 |
|---|---|
| 담당 여행 표 | 허용된 표시 필드와 금액만 반환 |
| 담당 여행 고객 합계 | 해당 여행의 고객 ID별 합계. 다른 여행 내역 없음 |
| 행 상세 | 표시 필드와 권한 있는 증빙 참조. 내부 메모·변경자·과거 값·대화 없음 |
| 변경 이력·AI 대화·규칙 사례 | 접근 거부. 빈 목록으로 성공한 것처럼 처리하지 않음 |
| 원본 카드·은행 업로드 파일 | 접근 거부 |
| xlsx 작업·파일 | 접근 거부 |
| 증빙 미리보기 | 행·여행·증빙 관계와 현재 담당 권한을 검사한 후 허용 |

owner용 JSON을 보내고 CSS로 숨기는 방식은 금지한다. API는 역할별 허용 필드를 반환한다. 검색 결과, 내려받는 JSON, 캐시 응답, 오류 세부정보에서도 내부 메모·이력·AI 대화가 새지 않아야 한다. 사용자가 로그아웃하거나 역할·계정이 바뀌면 이전 owner 응답을 viewer 화면의 캐시로 재사용하지 않는다.

증빙마다 evidence_id, 연결 행·여행, 원본 참조, 제공 가능한 범위, 파일 종류를 관리한다. 원본 하나가 여러 여행을 포함하면 해당 여행만 분리한 조회 자료를 제공한다. 분리 자료는 원본의 대체 정본이 아니라 원본과 연결된 파생 자료로 기록한다. 다른 여행 정보가 없는지 확인할 수 없으면 `담당 여행용 증빙 준비 필요`를 표시하고 원본 전체는 반환하지 않는다.

증빙은 로그인된 조회 경로로 제공한다. 영구 공개 URL이나 원본 저장 경로를 응답에 넣지 않는다. 담당 해제 후 새 미리보기 요청은 차단하며 기존에 화면으로 전달된 자료를 기술적으로 회수할 수 있다고 주장하지 않는다. 직원에게 별도 증빙 다운로드 버튼과 다운로드 API 권한은 제공하지 않는다.

검증 자료에는 A 전용 증빙, B 전용 증빙, A·B 혼합 파일, owner 메모·이력·AI 대화를 포함한다. A 담당 viewer가 A 표와 A 증빙을 보고, B와 혼합 원본·내부 자료·xlsx는 API 직접 요청으로도 받지 못해야 한다.

## 17. 모바일 기능과 화면 전환

사용자 확정: 모바일에서도 PC와 동일한 입력·업로드·규칙 대화·출력을 지원한다. 아래 레이아웃은 구현 기준이며 별도 모바일 앱이나 앱스토어 출시를 요구하는 것은 아니다.

### 17.1 작은 화면 구성

- 넓은 화면의 세로 여행 목록은 작은 화면에서 `여행 선택` 버튼으로 여는 패널로 바꾼다. 날짜·행선지·검색·현재 선택과 추가 기능은 유지한다.
- 본문은 수입 위·지출 아래 순서를 유지한다. 표를 읽기 전용 카드 요약만으로 대체하지 않는다. 열이 넘치면 표 영역 안에서 가로 스크롤하고 전체 페이지가 옆으로 밀리지 않도록 한다.
- 행 편집과 상세는 전체 높이 패널로 연다. 날짜·금액 등 고정 필드는 그대로 읽기 전용이며 수기 날짜·금액은 편집 가능하다. 키보드가 열려도 현재 입력과 저장·취소가 가려지지 않아야 한다.
- 규칙 대화는 별도 전체 화면 패널로 전환하되 여행과 대상 행 요약을 위에 유지한다. `장부로 돌아가기`는 답변·초안을 버리지 않는다.
- 영향 미리보기는 건수·변경 전후 합계·제외 사유를 먼저 보여 주고 행별 비교를 펼친다. 기존·미래 적용 선택은 각각 독립된 스위치이며 작은 화면에서 한 버튼으로 합치지 않는다.
- 주요 터치 버튼은 손가락으로 구분해 누를 수 있는 크기와 간격을 확보한다. 호버에만 존재하는 편집·출력 기능을 만들지 않는다.

### 17.2 파일 업로드·다운로드

파일 선택 버튼으로 기기의 파일 선택기를 연다. 끌어놓기만 제공하지 않는다. 카드·은행 CSV/XLSX 파일을 선택하고 PC와 같은 프로필·원천 봉인·중복 처리 과정을 거친다. 사진 촬영·영수증 OCR은 별도 요청되지 않았으므로 이 기능의 완료 조건에 넣지 않는다.

파일 전송 중, 서버가 접수한 후, 파싱·분류 중을 구분한다. 모바일 브라우저가 전송 중 종료되면 접수 완료라고 표시하지 않는다. 서버 접수 후에는 브라우저가 닫혀도 작업을 유지하고 복귀 시 같은 작업 상태를 조회한다. 전송 성공 여부가 불명확하면 같은 요청 ID로 조회·재시도하여 중복 작업을 막는다. 재개 가능한 청크 업로드는 첫 버전의 필수가 아니며 미구현 상태에서 전송 이어받기를 보장하지 않는다.

owner의 xlsx 출력은 모바일에서도 같은 선택 화면과 출력 작업을 사용한다. 파일이 준비되면 파일명·시트 수와 다운로드 버튼을 제공하고 운영체제의 저장·열기 동작으로 연결한다. 앱이 파일을 생성한 사실과 사용자가 기기에 저장한 사실을 구분한다. viewer에게는 다운로드 버튼과 API 권한이 없다.

### 17.3 전환·복귀와 검증

화면 회전·앱 전환 후 현재 여행과 서버에 저장된 행·대화·출력 작업을 복원한다. 새로고침 전의 미저장 초안을 영구 복구한다고 약속하지 않는다. 클라이언트에만 있는 초안과 서버 저장된 답변의 차이를 안내한다. 모바일에서도 응답 유실 후 새 요청 ID를 만드는 대신 같은 저장 요청을 확인한다.

최소 합성 검증은 좁은 세로 화면, 가로 화면, 화면 키보드 표시, 파일 선택, 업로드 후 브라우저 복귀, 규칙 미리보기 네 가지 범위 선택, xlsx 다운로드 경로다. 데스크톱 브라우저의 작은 화면 시뮬레이션과 실제 모바일 브라우저 검증을 구분해 기록한다. 실제 기기에서 확인하지 못했으면 확인하지 못한 기능을 명시한다.
