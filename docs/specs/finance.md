# 금융·카드·여행 배정 규칙

**상세 계약·참고 자료.** 아래 절의 작성 시점별 구현/배포 표시는 현재 상태가 아니다. 최신 사용자 정책과 현재 상태를 먼저 확인하고 필요한 절만 읽는다.

> **2026-10-29 최신 사용자 결정 — 분류가 되면 완료:** 자동·수동 모두 `classified`가 최종 분류다. 별도의 확정/미확정, 확정 대기, 잠정 분류 후 승인 단계를 두지 않는다. 낮은 신뢰도는 근거·불확실성 정보이며 완료를 취소하거나 재확정을 요구하는 상태가 아니다. 사용자는 완료된 분류를 교정할 수 있으며 수동 교정은 자동 규칙보다 우선한다. 이 결정은 아래 과거의 “분류만 수행하고 확정하지 않는다”는 문구를 대체한다.

### 자동분류 완료 계약 (2026-10-29)

- **최신 추가 승인:** 사용자가 “틀려도 괜찮고 근거가 부족해도 추론하며 미분류 카드결제를 남기지 말라”고 지시했다. 에이전트가 공통 추론 규칙을 설계·코드화하고 현재 미분류 거래에 적용한다. 이전의 개별 질문·신규 공통 규칙 논의 대기는 이 승인 범위에서 해제한다. 원본·수동 교정·금융 증거 보호는 유지한다.
- 같은 가맹점만 반복 처리하는 거래별 예외보다 카드사 업종→서비스 용도 단어→해외 현지 사용→업무 카드 지출 기본값 순으로 추론한다. 이미 정해진 항목을 우선하며 단서가 없으면 `기타경비`, 해외 사용이면 `현지경비`, 원결제가 식별되지 않은 취소는 `취소·환불`로 항목을 채운다. 추론의 출처·낮은 신뢰도·선택 근거를 저장하며 `미분류`라는 항목으로 이름만 바꾸지 않는다.
- `app.automatic_classification`을 카드 분류의 마지막 단계로 사용한다. 기존 메일·규칙 엔진의 더 구체적인 근거가 먼저다. OTA 자료 읽기 실패나 정확 예약 ID 부재만으로 비용 분류를 멈추지 않는다. 실제 원승인번호 검증·초과 환불·중복·원본 충돌·사용자 보류를 해제하거나 결제 연결을 창작하지 않는다.
- 여행은 실제 권위 여행 중 기존 기록의 유효한 배정을 먼저 유지하고, 없으면 가맹점 지역명·이용일과 일정 거리·수입-비용 차액으로 선택한다. 같은 점수도 일정·ID 고정 순서로 하나를 선택하고 동률 근거를 남긴다. 이용일이 없으면 가장 최근 시작한 실제 여행을 약한 기본값으로 삼고 매입일을 이용일로 바꾸지 않는다. 유효 여행이 없으면 여행을 창작하지 않고 비용 항목 분류만 완료한다.
- **미배정 의도 오인 정정:** 사용자는 미배정으로 정한 적이 없다고 명시했다. `review_decisions`, `board_manual_overrides`, `decided_at`의 존재나 `unclassified` 기본값만으로 여행 미배정을 사용자 결정으로 간주하지 않는다. 실제 입력된 항목·유효한 여행은 보존한다. 비어 있는 여행은 현재 장부의 유효 여행→가장 최근 저장한 유효 여행→기존 장부 기록의 유효 여행→새 추론 순서로 복원/배정한다. 환불 탭의 기존 귀속은 여행에 강제 배정하지 않고 환불 탭으로 복원한다. 이 과정은 과거 결정/override 기록을 삭제·위조하지 않는다. 새로 추론한 여행을 사용자 교정 사례로 학습하지 않는다.
- 실제 기존 자료 적용은 `tools/complete_card_classification.py`와 SHA 고정 `tools/apply_card_classification.ps1`을 사용한다. 읽기 전용 사본에서 결과·재실행 무변경을 먼저 검증하고, 단일 작성자 정지→신선 백업·별도 복원→원본 상태와 미리보기 digest 일치→원자 분류→원본/금융 링크/사용자 결정 불변→재실행0→서비스 복구 순서다. 새 장부 행·Google 쓰기는 포함하지 않는다. 기존 자동 장부 행의 비어 있는 항목/여행 표시만 원자적으로 보완할 수 있다.
- 분류 결과의 항목·여행·설명과 출처·근거를 저장하면 완료다. `decided`/`decided_at`는 기존 수동 결정·기록 보호용 호환 필드이며 자동분류의 미확정 여부가 아니다. 자동 결과를 수동 답변으로 위장하지 않는다.
- 여행 결정 DTO의 배정 결과는 `CLASSIFIED`, 출처는 `assignment_source=automatic|manual`이다. 기존 함수명·저장 근거의 `provisional_assignment`는 호환 경로이며 별도 잠정 상태가 아니다. 유효 후보 없음·실제 동률·원문 충돌·수동 보류는 해결할 근거가 필요한 상태로 유지한다. 이미 저장된 여행을 단순히 신뢰도가 낮다는 이유로 미배정으로 되돌리지 않는다.
  - 동일 카드/발급사와 원승인번호로 원결제 하나가 검증되면 여러 취소·부분환불을 모두 연결하고 원결제의 항목·여행을 따른다. 합계 0인 전액환불은 `환불쌍`으로 분류 완료하며 별도 확정 버튼이 필요 없다. 원본 오류·원결제 중복·초과환불·수동 보류·이미 기록된 행은 보호한다.
  - 환불 묶음의 내부 기록 성공 후 같은 미리보기를 새 요청 ID로 재전송하면, 동일 범위의 실제 성공 기록·성공 직후 미리보기·전체 묶음 revision·실제 장부 내용이 잠금 안에서 모두 일치할 때만 `applied=0`으로 응답한다. 부분 기기록 묶음을 완성한 경우도 전체 묶음으로 검증한다. 금액/장부/사용자 결정/묶음 멤버 변경·새 보류·임의 digest·성공 증명 없는 과거 응답은 이 예외로 허용하지 않는다.
  - 정상 환불 탭은 여행 ID가 비어 있어도 분류 완료다. 금융 기록 보류와 사용자 검토 보류는 별도로 표시하고 보호한다. 과거 빈 여행 이력은 카드·OTA 화면에서 사용자 미배정 의도로 표시하지 않으며, `AUTO_TRIP_INFERRED` 여행을 수동 교정·수동 규칙 학습 근거로 취급하지 않는다.
  - 분류 완료, 내부 장부 기록, 예약과 카드의 실제 동일성, 은행 환급 완료는 각각 실제 근거로 표시한다. 분류 완료만으로 은행 환급이나 Google 반영 사실을 만들지 않는다. Google 최종 장부 자동 쓰기 금지와 기존 원자성·중복 방지는 유지한다. 운영 재처리·원본/금융 쓰기는 기존 데이터 게이트를 따른다.

### 여행 자동분류 구현 계약 (2026-10-29)

`app.provisional_assignment.rank_trip_candidates`는 현재 권위 여행 목록으로 검증된 참고 후보를 평가한다. 낮은 점수라도 유일한 최선 후보는 `CLASSIFIED`, 사실상 동률은 `CONFLICT_REVIEW`, 후보가 없으면 `UNASSIGNED_NO_VALID_TRIP`를 반환할 수 있으나, 이는 후보 평가 결과다. 카드 분류의 마지막 단계인 `app.automatic_classification`은 위 최신 계약에 따라 실제 여행 동률을 일정·ID 순서로 해소하고 날짜 단서가 없으면 실제 여행 기본값을 선택해 저장한다. 이미 저장된 분류를 참고 후보의 충돌·낮은 신뢰도 때문에 미완료로 되돌리지 않는다. 실제 사용자 선택·명시 보류·원본 오류는 보존한다. OTA `service_period`가 있으면 승인일 근접보다 우선한다. 이 결정은 여행 귀속에 한정되며 카드/OTA 결제 검증, 환불, 원장·Google 쓰기 권한을 변경하지 않는다. [이전 PA-01~06 명세](provisional-assignment-review-first-20261028.md)의 잠정·확정 분리는 위 최신 계약이 대체한다.

## 사용자 확정 규칙

아래는 기존 작업 지침의 금융·여행 규칙을 현행 상세 명세로 옮긴 것이다. 사용자 확정값을 후보로 격하하거나 수동 교정을 덮지 않는다. `tests/test_owner_rules.py`가 지키는 규칙은 명시 지시 없이 바꾸지 않는다. 원승인번호 1:N과 항공권 최초 메일 수신일 보완은 시작 안내의 최신 계약이 추가로 우선한다.

1. 여행은 구글 시트 탭에서만 만든다. 연도와 종료일은 시트 최상단 제목에서 읽는다.
2. **종료일이 없는 여행(종료일 누락 또는 당일여행)은 다음 여행의 직전일까지다.** 이 종료일은 시트에 적힌 종료일과 같은 효력의 여행 기간이며 검증에 그대로 쓴다. 다음 여행이 바뀌면 따라 바뀌고, 사용자가 직접 고친 종료일은 덮지 않는다(`reconciliation.open_trip_end`).
3. 카드 거래의 날짜는 이용일, 이용일이 없으면 승인일이다. 매입일로 배정하지 않는다(`card_use_date`).
4. OTA 결제는 예약 이용기간의 여행에 배정한다. 이용기간이 결제일 추론보다 앞선다. 예약 메일이 옛 포털 기록보다 앞선다.
4-1. OTA 예약의 장부 날짜는 이용일(체크인·픽업·출발)이다. 결제일은 이용일이 없을 때만 쓴다(`reconciliation.ledger_date_for_booking`). 한 예약의 카드 부분과 캐시 부분은 같은 예약번호로 묶어 장부에서 한눈에 보이게 기장한다. 이미 기록된 장부 행의 날짜는 바꾸지 않는다.
4-2. 캐시·포인트(아고다캐시, 클룩 포인트, 트립코인)로 치른 예약은 캐시 부분을 비용으로 기장한다. 카드 결제가 함께 있든 캐시만 썼든 기장한다. 자료에 원화 환산 금액이 있으면 그 금액을 쓰고, 엔화만 있으면 간편환율(100엔 = 1,000원)을 쓴다. 이용일을 덮는 검증된 여행이 하나뿐이면 그 여행에, 없거나 여러 개면 미배정에 둔다(`app/ota_cash_use.py`). 취소·환불된 예약은 기장하지 않는다.
4-3. 여행 시작 전에 든 숙박은 그 여행의 준비 숙박으로 배정한다. 조건은 다음과 같다. 숙박의 체크아웃이 여행 시작일 이하이고, 체크인이 직전 검증 여행의 종료일 이후이며, 어느 여행과도 숙박 밤을 공유하지 않는다(`reconciliation.prep_trip`). 후보 여행이 둘 이상이면 시작일이 가장 가까운 여행으로 배정하고, 거리가 같으면 미배정으로 둔다. 기존 여행과 밤을 공유하는 숙박은 종전 규칙을 따른다.
5. **2026-10-23 최신 규칙:** 정상 카드 비용은 후보 여행이 한 곳 이상이면 추론 신뢰가 낮거나 여러 후보여도 가장 개연성 있는 실제 여행에 **AUTO_INFERRED**로 우선 배정하고 근거/불확실성을 기록한다. authoritative 여행 자체가 없을 때만 미배정하고 여행을 창작하지 않는다. 수동 여행 이동은 절대 우선. 이는 OTA 결제의 정확 연결/환불/중복까지 허위 확정하라는 뜻이 아니다. 캐시·포인트 등 비카드 특례는 별도 검증한다.
6. 같은 조건의 여행이 둘 이상이면(한 여행이 끝나고 다음 여행이 시작하는 날 등) 수입-비용 차액이 큰 여행으로 배정한다.

<a id="src-docs-business-rules-md--2026-10-16-승인번호-없는-해외-취소의-짝"></a>
#### 2026-10-16 승인번호 없는 해외 취소의 짝

해외 카드 원본에는 승인번호가 없어서 취소가 어느 구매를 취소했는지 번호로 알 수 없다. 승인번호 없는 취소는 카드·가맹점명·외화 통화·외화 금액이 같은 구매와만 짝짓는다. 구매는 취소보다 앞서고 이 기간 안에 있어야 한다(`config/refund-pairing.json`, 최대 365일). 같은 조건의 구매와 취소가 여러 건이면 날짜 순서대로 구매 하나에 취소 하나씩 짝짓는다. 같은 금액끼리라 순서를 바꿔도 합계는 같다. 쓸 구매가 없는 취소는 짝 없이 둔다. 같은 조건의 구매가 있는데 짝을 정하지 못한 남는 취소는 개별로 기록하지 않고 묶음으로 보류하며(`refund_count_group`), 개수를 명세와 맞춘 뒤 기록한다. 번호를 붙이지 않는다. 원화 청구액 차이는 환율·수수료로 보고 잔액에 남긴다. 짝 계산은 쓰기가 없고, 기록된 행은 이 규칙으로 바꾸지 않는다. 같은 가맹점 이름을 가진 다른 취소를 묶던 승인번호 빈 칸 비교는 2026-10-16에 고쳤다.

<a id="src-docs-business-rules-md--2026-10-13-분류-후-자동-기록과-다음-행동"></a>
#### 2026-10-13 분류 후 자동 기록과 다음 행동

비용 항목과 여행 또는 분기 비용 목적지가 정해지고 원본·중복·권위 일정·회사 경비 제외·사용자 보류·OTA 연결·환불 묶음 검사를 통과한 거래는 별도 기록 버튼 없이 COST 내부 장부에 자동 기록한다. 카드 화면의 소유자 요청과 답변 저장에서만 쓰며 조회 API 자체는 기록하지 않는다. Google 최종 장부 자동 쓰기는 계속 하지 않는다.

자동 기록은 기존 원자적 미리보기·기록 경로와 거래 ID의 중복 방지를 사용한다. 자동 기록으로 사용자 확정 여부를 바꾸거나 추론을 사용자 확정으로 표시하지 않는다. 원문 ID·금액·날짜·분류 근거를 보존하고 이력에는 자동 처리를 표시한다. 문제 있는 환불 묶음은 보류하되 같은 파일의 관련 없는 정상 거래까지 막지 않는다. 새로 기록할 환불은 여전히 전체 구성원을 함께 검증하고 기록하며 일부만 기록하는 것은 금지한다. 기존 수동 기록 경로의 보호 기준은 유지한다.

화면에는 원본 상태명 대신 실제 다음 행동과 이유를 표시한다. 원본 충돌·환불 상태·예약 연결 보류를 단순 여행 미지정보다 먼저 안내한다. 파일 전체 처리 오류를 각 거래의 보류 사유로 덮지 않는다. 거래 링크는 원행 ID를 포함하며 여행 지정은 해당 수정창, 환불 확인은 해당 거래와 연결된 환불, 예약 연결 확인은 기존 결제 연결 영역으로 이동한다.

<a id="src-docs-business-rules-md--2026-10-13-환불-탭과-과거-내역-표시"></a>
#### 2026-10-13 환불 탭과 과거 내역 표시

원결제와 연결된 모든 환불 원행의 합계가 정확히 0일 때만 환불 탭에 모은다. 여러 번 나눈 환불도 전체 합계로 판정한다. 잔액이 남는 부분 환불은 원결제의 여행에 함께 표시하고 잔액을 해당 여행 비용으로 유지한다. 원결제 금액을 잔액으로 덮거나 환불 원행을 합쳐 삭제하지 않는다. 원거래가 모호하거나 충돌한 자료는 자동으로 묶지 않는다. 여행 귀속·확정·보류·기존 기록은 유지하며 환불 탭은 읽기 전용 표시 분류다.

이미 장부에 기록된 전액 환불 쌍은 모든 구성원이 기록돼 있고 같은 여행에 속하며 저장 금액 합계도 0일 때만 기존 여행의 표시 목록에서 옮긴다. 한쪽만 기록됐거나 서로 다른 여행에 속하면 기존 기록을 숨기지 않는다. 미기록 전액 환불은 환불 탭에 미기록 상태로 보이며 조회를 장부 기록이나 확정으로 해석하지 않는다.

2025년과 2026년 1분기 자료는 이전 합의대로 원본을 보존하고 신규 카드·OTA 검토 목록과 미배정 집계에서 제외한다. 카드 목록은 원본 거래일, OTA 목록은 실제 이용기간으로 판정하며 날짜에 붙은 시간도 파싱한다. 기준일을 넘기는 기간·충돌한 기간·날짜 미확인 자료는 과거 완료 자료로 단정하지 않는다. 미래 이용 예약을 과거 결제일만으로 제외하지 않는다.

<a id="src-docs-business-rules-md--2026-10-12-카드-3820-싱가포르-여행-예외"></a>
#### 2026-10-12 카드 3820 싱가포르 여행 예외

사용자 지정에 따라 2026-09-19~2026-09-24의 카드 끝자리 3820 사용내역은 같은 기간의 싱가포르 여행에 배정한다. 이 기간에는 분기 기타비용보다 여행 배정을 우선한다. 등록된 일정과 보존된 사용자 지시가 일치하는 여행이 하나일 때만 적용한다. 기존 비용 항목을 유지하고 항목이 없는 일반 사용내역은 기존 여행 기본 항목인 현지경비로 분류한다. 비용 항목 규칙이 충돌하면 배정과 별개로 검토 상태를 유지한다.

원본 금액·날짜·ID, 기존 사용자 결정·장부 기록·회사 경비 제외·보류·취소·환불·중복 보호를 유지한다. 이 특례의 분류는 완료로 저장하며 장부 기록·Google 쓰기를 자동으로 실행하지 않는다. 다른 연도·카드·기간으로 확대하지 않는다.

<a id="src-docs-business-rules-md--2026-10-12-카드-3820-잔여-거래의-분기-기타비용"></a>
#### 2026-10-12 카드 3820 잔여 거래의 분기 기타비용

카드 끝자리 3820 거래 중 기존 대사·확정 규칙·여행 배정으로 처리되지 않고 남은 매입 거래는 `분기 기타비용`으로 분류한다. 거래일의 연도와 분기를 설명에 표시하고, 거래일이 없으면 매입일을 사용한다. 날짜를 읽지 못하면 보류한다. 다른 여행이나 Google 시트를 추측해서 연결하지 않는다.

기존 사용자 결정·장부 기록·회사 경비 제외·보존 기간·구체적 규칙·여행 배정을 덮지 않는다. 취소·환불·중복·충돌·원문 오류는 이 규칙으로 새 비용을 만들지 않는다. 원본 금액·날짜·ID를 보존하며 분류는 완료로 저장한다. 이 특례의 실행만으로 장부 기록·Google 쓰기를 자동으로 수행하지 않는다. 분기 설명은 회계 비용의 구분이며 여행 일정의 근거가 아니다.

<a id="src-docs-business-rules-md--ota-자료-확인-순서"></a>
#### OTA 자료 확인 순서

기존 메일 조사와 포털 전수조사 자료, 예약 후보 문서를 먼저 함께 조회한다. 자료가 존재한다는 사실과 정확 카드 결제 연결을 구분한다. 등록 자료 읽기 실패는 근거 부재로 표시하지 않는다. 예약 확정·실제 결제는 실제 이용 완료의 증명이 아니다. 같은 사용자 보류를 자동 해제하거나 이미 답한 내용을 다시 질문하지 않는다. 구현과 현재 검증은 [최신 OTA–카드 A 정책](ota.md#src-docs-ota-card-reconciliation-policy-a-v3-md)를 따른다.

<a id="src-docs-business-rules-md--2026-10-10-대장가이드-항공권의-업무-여행-귀속-규칙"></a>
#### 2026-10-10 대장·가이드 항공권의 업무 여행 귀속 규칙

노선·목적지·OTA 업체와 관계없이 **서명·출처가 검증된 예약/결제 메일 또는 그 첨부 전자항공권에서 실제 탑승자 이름이 확인되고, 그 사람이 운영에 저장된 여행 담당자 또는 사용자가 이미 확정한 회사의 대장·가이드 신원과 일치할 때** 해당 항공권을 일반 고객 항공권과 달리 **업무 이동 항공권 후보**로 본다.

여행 귀속은 단순히 “직전 여행”이나 “다음 여행”으로 고정하지 않는다. 해당 대장·가이드가 담당하는 authoritative 여행들을 놓고 항공권의 전체 여정(출발·도착 공항, 각 구간 날짜, 왕복/편도, 연결편), 여행 목적지와 일정, 담당자 정보를 함께 대조한다. 다음 유형을 모두 허용한다.

- 여행 시작 전에 현지로 먼저 들어가는 **사전 출국/사전 답사·준비 이동**
- 여행 종료 직후 또는 고객 일정 종료 뒤의 **귀국 이동**
- 연속된 두 여행 사이의 **현지 이동·포지셔닝**
- 여행 도중 합류하거나 먼저 이탈하는 등 원문 근거가 있는 **부분 기간 업무 이동**

귀속 조건은 “그 여행을 위한 업무 이동”이라는 설명이 원문과 일정에서 유일하게 성립해야 한다. 항공편이 여행기간 바깥에 있다는 이유만으로 배제하지 않으며, 반대로 날짜가 가깝다는 이유만으로 자동 귀속하지 않는다. 사전 출국이면 이후 authoritative 여행, 귀국이면 직전 authoritative 여행, 연속 일정 사이 이동이면 관련 양쪽 여행의 담당·노선·시간관계를 함께 검토해 실제 비용 목적이 가장 명확한 한 여행에 귀속한다. 두 여행에 걸친 공통 이동으로 한 여행만 고를 근거가 없으면 HOLD한다.

후보가 둘 이상 합리적으로 남거나, 담당 대장·가이드 신원을 확정할 수 없거나, 항공 구간과 여행 목적지가 모순되거나, 해당 여행이 authoritative하지 않으면 자동 귀속하지 않고 HOLD한다. 이 규칙은 여행의 시작·종료일을 늘리거나 새 여행 authority를 만드는 규칙이 아니며 **기존 authoritative 여행에 항공료 비용을 귀속하는 규칙**이다.

한 예약에 여러 탑승객이 있고 대장·가이드가 아닌 탑승객이 섞여 있으면, 대장·가이드 몫의 운임이 원문에서 분리돼 확인되지 않는 한 예약 전체 금액을 이 규칙으로 자동 귀속하지 않는다. 취소·부분환불·전액환불은 기존 환불 규칙에 따라 원거래와 별도로 보존한다. 항공료가 아닌 OTA 상품이나 단순 가맹점명·결제일·목적지만으로는 이 규칙을 적용하지 않는다.

현재 `a77c71ff`(1,081,000원, 삿포로 6/15–6/21)은 이 일반 규칙의 한 적용 사례다. 메일/전자항공권의 실제 탑승자가 대장·가이드로 확인되면 `0613_북해도`를 포함해 해당 대장이 담당한 전후 authoritative 여행과 항공 구간을 함께 대조해서 귀속 여행을 결정한다. `0613_북해도`에 무조건 붙이지 않으며, 사전 출국·귀국·다음 여행 준비 이동 가능성까지 검토한 뒤 하나로 확정할 근거가 있을 때만 기록한다. 확인 전에는 HOLD를 유지한다.

<a id="src-docs-business-rules-md--구현-2026-10-10"></a>
##### 구현 (2026-10-10)

- **탑승자·구간 근거**: 서명 검증된 Trip.com 항공 메일 본문에서 `성 (성) 이름 (이름)` 탑승자와 `가는편/오는편` 구간(날짜·공항·편명)을 예약번호별로 모은다(`app/flight_evidence.py`). 인사말의 이름은 예약자이며 탑승자로 쓰지 않는다. 연도가 없는 결제 완료 안내만 있으면 연도를 추정하지 않고 일정 불완전으로 둔다.
- **대장 신원**: 대장·가이드 신원과 담당 여행의 authority는 reservation(`6Soo/reservation`)이다. COST는 reservation 내부 API(`/api/internal/guides`, `/api/internal/tours?include_past=1`)를 읽기 전용으로 소비한다(`app/reservation_authority.py`). active 대장의 항공권 영문명(`flight_name_en`)과 실명이 메일 탑승자와 정확히 일치할 때만 대장이다. 영문명이 없는 대장이 있으면 영문 탑승자는 UNKNOWN이며 한글 이름에서 철자를 추정하지 않는다. COST의 `trip_tabs.prepared_by_name`, `owner_profile.assignee_name`, `guide-identities.json`은 신원 authority가 아니다(코드는 deprecated). 성만 같거나 일부만 같거나 띄어쓰기만 다른 이름은 일치로 보지 않는다.
- **귀속 판단**: 공항·지역 대응표(`config/guide-airfare-airports.json`)에 있는 공항만 여행지와 대조한다. 관문 공항처럼 근거가 약한 공항은 의도적으로 넣지 않았고, 표에 없으면 HOLD다. 구간별로 사전 출국·귀국·여행 사이 이동·중도 합류·조기 이탈을 판정하고, 모든 구간이 같은 여행 하나로 설명될 때만 귀속한다(`app/guide_airfare.py`). 일정 간격 한도(`max_gap_days`)는 설정이다.
- **연결**: 판정은 OTA 스냅샷 워커에서 계산되고 스냅샷 결과에는 이름 없이 판정·여행·근거 해시만 남는다. 카드 분류는 신선한 스냅샷의 `ATTRIBUTED` 판정만 `guide_airfare_evidence` 소스의 추론 규칙으로 읽는다. 사용자 확정 거래와 환불은 건드리지 않는다. reservation의 대장·여행 자료(영문명·상태·담당 대장·날짜), COST 여행 일정 권위, 메일 근거, 파서, 공항 대응표가 바뀌면 스냅샷 입력 지문이 바뀌어 기존 미리보기는 STALE로 거부된다.
- **여행 브리지**: reservation 여행과 COST 회계 여행은 제목·목적지·날짜만으로 연결하지 않는다. reservation `cafe_fldid`가 COST reserve 등록(`reserve:{fldid}:{연도}`)과 같고 시작·종료일이 정확히 같거나, reservation `tours.code`(`MMDD_지역` 또는 `YYYYMMDD_지역`, 8자리는 연도도 같아야 함)가 COST `display_key`와 같고 날짜가 정확히 같을 때만 후보이며 결과가 유일해야 한다. 두 키가 서로 다른 여행을 가리키거나 코드가 다르면 연결하지 않는다. 날짜 불일치·키 충돌·한쪽만 있는 여행은 `HOLD_RESERVATION_TRIP_AUTHORITY_MISMATCH`, COST에서 수동 지정된 담당자가 reservation과 다르면 `HOLD_GUIDE_ASSIGNMENT_CONFLICT`, reservation을 읽지 못하면 `HOLD_GUIDE_AUTHORITY_UNAVAILABLE`다. 여행 일정의 회계상 authority는 계속 COST다.
- **쓰기 신선도**: reservation authority를 이번 확인에서 정상으로 읽은 상태(fresh)이고 마지막 성공이 90초 이내일 때만 대장 항공권 귀속을 새로 만들거나 장부에 기록한다. 마지막 정상본을 최대 10분 보여 주는 유예(degraded)는 화면 표시용일 뿐 기록 근거가 아니다. 이미 귀속된 미확정 행도 기록 시점에 fresh authority, 신선한 스냅샷, 같은 여행·같은 authority digest가 모두 확인돼야 하며 하나라도 아니면 보류하고 이전 미리보기는 PREVIEW_STALE이다. 비대장 카드는 영향을 받지 않는다.
- **혼합 탑승**: 대장 외 탑승자가 섞이고 원문에서 인별 운임이 분리돼 확인되지 않으면 `HOLD_MIXED_PASSENGERS`다. 인별 운임이 확인돼도 카드 한 건 전체를 장부 한 행으로 쓰므로 자동 기록하지 않고 `HOLD_GUIDE_PORTION_ONLY`로 둔다.
- **운영 적용 결과(2026-10-10)**: 이 규칙은 삿포로 전용도 직전 여행 전용도 아니다. reservation authority 기준 재판정에서 대장 13명 중 항공권 영문명이 등록된 대장이 0명이라 매칭된 항공료 27건 모두 `HOLD_GUIDE_IDENTITY_UNCONFIRMED`다. `a77c71ff`·`cb9f03e7`도 마찬가지로 HOLD이며 어느 여행에도 귀속하지 않았다. 대장 영문명은 reservation 관리자 화면 `대장 관리`에서 한 번 등록하면 다음 스냅샷에서 자동 재평가된다.

<a id="src-docs-business-rules-md--2026-10-08-일정-정리와-원본-확인"></a>
#### 2026-10-08 일정 정리와 원본 확인

사용자가 최신 일정 원본을 기준으로 정리하라고 지정했다. 기존 일정과 최신 원본의 명시 연도·시작일·종료일이 같으면 근거 경로와 digest를 최신 원본에 연결할 수 있다. 최신 원본에 여행 시트가 없거나 종료일이 없으면 과거 사본으로 자동 복원하지 않는다. 사용자 결정·여행 기간·원문 거래는 유지한다.

부분 환불 760,200원의 실제 국민 취소 전표를 찾았고 원결제 1,056,200원과 카드·원승인번호·원승인일로 연결했다. 원결제와 취소 원행을 각각 보존하며 차액 296,000원을 원결제 금액으로 덮지 않는다. 아래 10월 4일의 실제 환불 원행 미확인 기록은 당시 상태다. 취소 원행은 2026-10-09에 운영으로 가져왔다. 가져오기를 보류 해제로 해석하지 않으며 해제는 사용자가 명시적으로 수행한다. 연결된 환불과 원결제는 미리보기에서 한 쌍으로 판정하고, 한쪽이 보류면 둘 다 보류하며 기록은 둘 다 또는 둘 다 없음이다. 환불의 항목·구분·여행은 비어 있을 때만 원거래에서 이어받는다.

2026-10-09 읽기 전용 Drive 재조사에서 `(주) 숲길따라 감성여행_아슬란_26Q1` 보관 워크북의 사본 시트 11개가 기존 권위 날짜와 일치함을 확인했다. 이 자료는 **historical corroborating evidence**일 뿐 일정 authority가 아니다. 최신 운영 원본에 없는 일정을 보관 사본만으로 복원하거나 장부·카드 기록 차단을 해제하지 않는다. 도고·야쿠시마처럼 보관 자료에도 명시 일정이 없거나 몽골·8월 북해도처럼 종료일 authority가 없는 경우에는 추정하지 않고 HOLD를 유지한다.


Agoda 자료는 이미 보존된 메일과 전수조사 원문을 먼저 사용한다. 같은 조사 여부를 사용자에게 반복 질문하지 않는다. 예약 확정·결제 성공·이용 완료·취소 완료를 구분하며 기존 보류와 금액 불일치는 새 후보로 덮지 않는다. 카드 원장에서 원결제와 동일 승인번호의 전액 취소 쌍이 확인되면 해당 카드 거래의 회계상 순액 0원은 확정할 수 있지만, 그 사실만으로 과거 proposed OTA 예약 연결이나 이용 완료 여부를 확정하지 않는다. 카드 회계 상태와 OTA 예약 authority를 분리해 기록한다.

<a id="src-docs-business-rules-md--2026-10-04-ota-추가-답변"></a>
#### 2026-10-04 OTA 추가 답변

- 취소 정산·부분 환불 미확인·사용자 보류·예약과 결제 연결 미확정은 일반 비용 기록에서 제외한다. 보류는 원행 ID와 원문 hash에 묶는다. 답변 저장이나 재분류만으로 해제하지 않으며, 자료 확인 후 사용자가 명시적으로 해제해야 한다. 취소 원문이나 사용자 답변을 삭제하지 않는다.

- 화순 일정은 사용자 확인으로 2026-08-23~2026-08-25다. 노리쿠라 08-01~08-05, 군산 08-27~08-29, 7월 가루이자와 07-22~07-26은 이미 보존된 reserve의 명시 날짜를 사용한다. 과거 여행을 출발 예정으로 위조하지 않는다.
- 같은 결제일·금액의 예약 후보가 모두 같은 숙박 종류와 이용기간이고 취소 후보가 없으면 해당 여행의 숙박비만 배정할 수 있다. 개별 예약번호는 선택하지 않는다. 이번 여섯 거래에 답변을 적용했다. 취소된 후보가 섞이면 사용자에게 실제 거래를 확인한다.
- 7월 11일 트립닷컴 119,965원은 사용자가 취소한 결제라고 확인했다. 여행에서 분리하며 개별 예약번호는 보류한다.
- 7월 30~31일 숙박 두 건은 노리쿠라 사전 숙박으로 의도했지만 취소된 예약이다. 취소·환불을 여행에서 분리하라는 사용자의 마지막 답변을 우선한다. 노리쿠라의 여행 시작일을 변경하지 않는다.
- 6월 8일 트립닷컴 1,056,200원과 7월 15일 1,472,600원은 노리쿠라 서울↔고마쓰 항공권이며 각각 카드 할인 4,000원이라고 사용자가 확인했다. 메일 총액은 각각 1,060,200원과 1,476,600원이다. 원결제액을 수정하지 않으며 다른 거래에 4,000원 차이 허용을 일반화하지 않는다.
- 6월 8일 항공권은 일부 탑승객만 취소했고 나머지는 실제 노리쿠라에서 사용했다. 8월 1일 메일에는 환불 완료 금액 760,200원이 있지만 사용자는 실제 환불 여부를 아직 확인하지 못했다. 실제 카드 환불 원행과 금액을 확인한 뒤 잔여 이용 비용과 취소·환불 부분을 나눈다. 현재 전체 여행 배정은 보류하고 원결제를 보존한다. 메일만으로 새 환불 거래를 만들지 않는다.
- 6월 11일 Agoda 146,018원은 8월 27~29일 군산 예약의 취소 문의 자료다. 50% 위약금과 73,009원 환불 가능 안내는 취소 완료나 실제 환불 증거가 아니다. 사용자는 실제 이용 여부가 불확실하여 보류를 선택했다.
- 취소된 예약과 확인된 환불은 여행에서 분리한다. 원결제·취소·환불 원문과 실제 거래 다중도를 보존한다. 이번 거래별 답변은 기존 확정 답변으로 저장하여 재분류로 덮지 않는다. 실제 비용 전기는 미리보기 이후 별도로 수행한다.

원본 파일과 원천 행을 보존한다. 파일 hash, 거래 ID, 불변 원문 hash, 처리 상태를 구분한다. 같은 거래를 다시 기록하지 않는다. 동일 ID의 다른 원문은 충돌이며, 동일 날짜·가맹점·금액의 실제 복수 거래는 다중도를 보존한다. 구분 근거가 부족한 파일 겹침은 사람에게 확인한다.

카드사별 승인·매입·취소·환불 금액과 원거래 관계를 보존한다. 외화 소수를 정수로 바꾸지 않는다. 금액 해석 실패를 0원으로 기록하지 않는다.

거래별 확정 답변을 보호한 뒤, 확정 규칙과 명확한 업종·패턴으로 분류한다. 불확실한 거래만 질문한다. 거래별 예외와 재사용 규칙, 기존 적용과 미래 적용을 구분한다. 사용자가 확정한 거래를 새 규칙으로 덮지 않는다. 원문 날짜·금액·ID는 편집할 수 없다.

여행 배정은 연도·명시 시작/종료일·종료 의미·권위 종류·authoritative 상태·원천 digest가 확인된 일정만 읽는다. 원천 또는 일정 충돌은 보류한다. 겹침은 서비스 시작일과 여행 시작일 일치, 최근 여행 시작일, 늦은 종료일 순서이며 동률은 보류한다.

카드 결제일·가맹점 지명만으로 OTA 이용기간이나 여행을 만들지 않는다. 워크북 제목 MMDD_MMDD의 종료는 사용자 확인에 따라 그대로 보존하며 하루를 빼지 않는다. 숙박·렌트의 실제 이용기간이 없으면 표시 기간은 공란이다. 보험의 행사기간 표시는 배정 근거가 아니다.

수기 장부·과거 분류는 후보·학습 자료이며 현재 거래의 증거가 아니다. 정확 금액·카드 원행·승인 관계·예약 ID·서비스기간·취소 관계가 검증 근거다. 기본 처리에서는 금액 근사와 브랜드만으로 여행을 확정하지 않는다. 사용자가 허용한 현재 원행의 추론 배정은 아래 별도 기준을 따른다.

부가세 신고 판단은 자동분류 확정 조건에서 제외한다. 출력 양식은 매출자료 양식_rev이며 지출 B:H는 날짜·항목·내용·기간·예약번호·증빙유형·금액이다. 항목을 고객명으로 해석하지 않는다.

미리보기 이후 변경이 있으면 다시 확인한다. 장부·요청 결과·이력은 같은 트랜잭션으로 저장한다. 이관 검증은 거래별 원문·금액·상태·사용자 결정으로 비교한다. 과거 상세 예외는 보존된 비용 규칙 원장과 결정 등록부를 따른다. 이번 구조 변경은 새 비용의 일괄 승인이 아니다.

<a id="src-docs-business-rules-md--2026-10-03-사용자-답변으로-확정한-규칙"></a>
#### 2026-10-03 사용자 답변으로 확정한 규칙

2026-10-04 추가 답변: 아고다 구매는 모두 숙박이므로 아고다 표기 가맹점 그룹의 비용 항목을 숙박비로 재사용한다. 여행은 예약 이용기간과 권위 일정으로 별도 배정하고 취소·환불은 분리한다. 원본 금액과 날짜를 수정하거나 사용자 확정을 덮지 않는다. 예약 확인 메일은 다른 메일 계정에서 POP3로 `kkokkohero6@gmail.com`에 모으며, POP3 수신 여부만으로 메일을 배제하거나 발신 서명 검사를 생략하지 않는다. 예약 하나당 한 번 결제하고 할인은 거의 없다는 답변을 기준으로 합산·분할·할인액을 임의로 만들어 대사하지 않는다. 명시 자동 결제 예정일과 실제 카드 통화·금액이 유일하게 맞으면 예정일 근거와 카드 원행을 함께 보존한다. 예정일 안내 자체를 결제 완료나 실제 환불의 증거로 표시하지 않는다.

| --- | --- |
| FUKUTAKE FOUNDATION | 미술관 입장료로 분류한다. |
| 편의점·마트 | 실제 승인일과 원본 사용 국가가 검증된 여행 일정에 맞을 때 해당 여행의 식비로 분류한다. 국내 거래를 일본 여행에 배정하지 않는다. |
| 업종을 모르는 현지 거래 | 같은 국가의 명시 여행 기간에 사용한 거래는 현지경비로 제안한다. 구체적인 규칙이나 명확한 업종을 우선하며 사용자가 예외를 수정할 수 있다. |
| 트립닷컴·클룩·결제대행 | 예약 자료를 먼저 대조하고, 남은 거래만 질문한다. 공급자 이름만으로 항공·숙박·교통을 정하지 않는다. |
| 아성다이소 | 사용자 답변에 따라 일반 사무용품비로 재사용하고 공통 경비로 처리한다. 여행에 자동 배정하지 않는다. |
| 어드벤처코리아 | 질문한 결제 네 건과 취소·환불 두 건만 여행상품비로 분류한다. 원본 거래 hash에 묶고 여행은 예약 자료로 별도 확인한다. |
| 2025년과 2026년 1분기 | 정리 완료 자료로 내부 보존한다. 검토 화면, 미리보기, 신규 전기에서 제외한다. |

예약 메일은 사용자가 지정한 계정에서 읽었다. 발신 도메인 인증, 예약번호, 실제 원화 결제액, 결제일과 원본 카드 행의 유일한 일치를 확인한다. 같은 금액으로 여러 예약이 남으면 상품 종류만 제안할 수 있으며 특정 예약이나 여행을 임의로 연결하지 않는다. 취소·환불은 구매 거래와 별도로 보존한다.

클룩의 유료 기차표에 함께 제공된 티켓 수령 안내는 해당 상품명이 명시되고 금액이 0원임이 확인된 경우에만 별도 구매에서 제외한다. 두 번째 예약번호가 있다는 이유로 유료 예약의 대조를 누락하지 않는다. 안내에도 결제액이 있거나 다른 상품이 섞이면 자동 연결을 보류한다. 결제일과 이용일이 다르면 이용일을 결제일로 바꾸지 않는다.

예약·온라인·결제대행 거래는 과거에 현지경비로 분류한 가맹점 규칙이 있더라도 사용 국가와 결제일만으로 여행에 배정하지 않는다. 원본 거래에 묶인 구매 목적 규칙과 검증된 예약 이용기간은 별도로 적용할 수 있다.

클룩 2026-05-28의 37,300원은 볼로냐 마찌니에서 프라토를 거쳐 피렌체로 이동하는 두 명의 기차표다. 메일 본문과 첨부 바우처 네 페이지에서 이용일 2026-06-29를 확인했다. 기차표 33,900원과 발급 수수료 3,400원을 교통비로 분류했다. 이후 사용자가 추론 배정을 허용해 과거 같은 원행의 유럽 배정과 이탈리아 이동 구간을 참고하여 유럽 여행에 배정했다. 이용일과 여행기간이 다르므로 확신이 낮은 추론으로 표시하며 6월 29일 원문을 보존한다. 실제 탑승 또는 취소를 확정하지 않는다.

유럽 일정은 사용자 지시에 따라 취소되지 않은 숙박 예약 12건의 명시 기간에서 2026-05-20~2026-06-10으로 정했다. 확인된 국가는 오스트리아, 이탈리아, 프랑스다. 취소된 숙박 두 건은 일정 계산에서 제외했고 체크아웃 날짜는 하루를 빼지 않았다. 관련 메일 원문과 digest는 운영 자료 폴더에 보존한다.

과거에 업종 미상 해외 거래를 식비로 일괄 처리한 결정과 비용제외 결정은 자동 복원하지 않는다. 과거 완료 여부만으로 현재 원본 거래를 자동 승인하지 않는다.

<a id="src-docs-business-rules-md--2026-10-03-추가로-허용한-추론-배정"></a>
#### 2026-10-03 추가로 허용한 추론 배정

사용자가 최대한 추론해 배정하고 나중에 수정하는 방식을 허용했다. 기존 사용자 확정과 검증된 예약 여행을 우선 보호한다. 추론 규칙은 현재 원행 hash에 묶으며 다른 금액·날짜·원행과 미래 거래로 확대하지 않는다. 분류를 다시 실행해도 동일 배정과 사용자의 수정 답변을 유지한다.

같은 카드 원행과 일치하는 과거 장부의 여행, 원래 결제의 여행 후보, 실제 예약 이용기간, 가맹점 지역과 가까운 명시 여행을 차례로 참고한다. 실제 예약 이용일을 아는 경우 다른 달의 결제일로 여행을 골라 넣지 않는다. 구매 상세가 부족한 혼합 예약 상품은 여행상품비로 제안하고 세부 상품 미확인을 표시한다. 구독·통신·사무용품과 일반 업무 경비는 공통 경비로, 취소·환불은 부호를 보존해 분류한다. 국내 현장 구매는 해외 여행에 넣지 않는다.

추론한 거래는 사용자 확정으로 바꾸지 않는다. 화면에 추론 배정과 근거, 높음·중간·낮음 표시를 제공한다. 확신이 낮은 거래는 확인을 권장하지만 기록을 막지 않는다. 원문 오류·중복·충돌과 유효하지 않은 여행은 기존 기록 차단을 유지한다. 현재 없는 여행의 명칭은 참고 자료로 보존하며 일정이나 이용일을 만들어 내지 않는다.

추가 사용자 답변에 따라 이번 조지아·카자흐스탄 거래 18건은 유럽에 배정하는 예외다. 기존 유럽의 명시 숙박 일정과 원문 결제일을 변경하지 않고 사용자 예외임을 표시한다. 미래의 다른 연도나 다른 여행에 무조건 적용하지 않는다.

<a id="src-docs-business-rules-md--2026-10-03-댓글-기준-출발-예정-여행-등록"></a>
#### 2026-10-03 댓글 기준 출발 예정 여행 등록

reserve에서 확보한 여행 목록과 해당 모집글의 전체 댓글 수를 읽는다. 답글·후기·완료 공지를 모집글로 사용하지 않는다. 댓글이 5개 이상이고 명시 출발일이 한국 날짜로 오늘 이후인 여행을 출발 예정으로 분류해 장부의 여행 목록에 등록한다. 댓글 수는 신청 인원이나 입금액으로 해석하지 않는다.

출발일·종료일·연도와 원문 제목의 기간을 대조한다. reserve에서 사람이 확정한 일정은 그 값을 보존한다. 날짜가 맞지 않거나 댓글을 조회하지 못한 여행은 보류하며, 조회 실패를 댓글 0개로 바꾸지 않는다. 같은 게시판과 같은 연도의 여행은 한 번만 등록한다. 기존 여행의 일정·담당자·사용자 수정은 덮지 않는다.

등록 후 댓글이 5개 미만으로 줄거나 일정이 바뀌면 확인 필요 표시를 남기고 여행과 비용을 삭제하지 않는다. 여행 등록은 비용 항목의 확정이나 비용 전기와 별개다. 실제 카드 원문과 비용 기록은 기존 미리보기·중복 방지 절차를 따른다.

여행글은 한국 시간 매일 0시에 하루 한 번 조회한다. 당일 조회가 실패하거나 서버가 재시작되어도 같은 날짜에 추가 조회하지 않는다. 서버가 해당 시각에 꺼져 있었으면 재시작 후 놓친 당일 조회를 한 번 수행한다. 여행 등록 수와 카드 자료 수, 수입·지출 기록 수는 화면에서 구분한다.

<a id="src-docs-reconciliation-rules-md--대사-규칙-카드-거래--예약--여행"></a>
### 대사 규칙 (카드 거래 ↔ 예약 ↔ 여행)

> **규칙 보존 및 V3 우선순위:** 이 문서의 날짜·여행 기간·사용자 확정·카드 금융 안전 규칙은 계속 보존한다. 다만 2026-10-23에 확정한 **유효 카드 비용은 낮은 추론이라도 권위 있는 여행 후보에 우선 배정**, **OTA 링크 미확정만으로 내부 경비 준비를 금지하지 않음**이라는 정책과 충돌하는 구형 `미배정/HOLD` 서술은 새 목표가 아니다. 새 개발은 [COST V3 단일 진입점](../COST_V3_START_HERE.md) 및 [OTA 정책 A](ota.md#src-docs-ota-card-reconciliation-policy-a-v3-md)에서 시작한다. 현행 코드가 과거 동작을 구현 중일 수 있으며 이 문서는 이미 V3가 배포됐다는 주장이 아니다.


이 문서는 카드 거래에 항목과 여행을 정하는 규칙 전체를 한곳에 적는다. 날짜 판정 함수와 출처 이름은 `app/reconciliation.py`, 분류 순서는 `app/classify.py`, 여행 검증과 예약 근거는 `webapp/card_flow.py`에 있다.

<a id="src-docs-reconciliation-rules-md--1-날짜의-의미"></a>
#### 1. 날짜의 의미

| 날짜 | 출처 | 쓰는 곳 |
|---|---|---|
| 카드 이용일 | 명세에 `이용일` 열이 있을 때 (H.xlsx, G.xlsx) | 카드 거래의 날짜. `approval_date` 칸에 들어간다 |
| 카드 승인일 | 명세에 `승인일` 열만 있을 때 (E, F, KB) | 이용일이 없을 때 카드 거래의 날짜 |
| 매입일(청구일) | 모든 명세 | 대사에 쓰지 않는다 |
| 예약 이용기간 | OTA 메일·포털 (숙박: 체크인~체크아웃, 항공: 가는편~오는편) | 여행과 겹치거나 덮는지 판정 |
| 여행 기간 | 여행 탭 (시작일~종료일) | 종료일은 마지막 이용일을 포함한다 |

- 카드 이용일과 예약 이용기간은 다른 날짜다. 카드 쪽은 `card_use_date()`, 예약 쪽은 `covers_stay()` / `overlaps_stay()`로 판정한다.
- 숙박은 밤 단위로 본다. 여행의 밤은 시작일 밤부터 종료일 전날 밤까지다(종료일은 체크아웃하고 돌아오는 날). 그래서 숙박이 여행 안이려면 체크인 ≥ 시작일, 체크아웃 ≤ 종료일이어야 한다. 여행 종료일에 체크인하는 숙박은 그 여행과 겹치지 않는다(다음 일정의 숙박이다). 시작일에 체크아웃하는 숙박도 겹치지 않는다.
- 항공은 출발일과 도착일을 모두 이용일로 본다. 여행 종료일에 출발하는 귀국편은 그 여행과 겹친다.
- 여행 시작 전 숙박의 준비 기간(AGENTS.md 4-3): 어느 여행과도 밤을 공유하지 않는 숙박은 체크아웃이 시작일 이하이고 체크인이 직전 검증 여행 종료일 이후일 때, 시작일이 가장 가까운 다음 여행의 준비 숙박이다. 거리가 같으면 미배정이다. 기간 제한은 없다(`reconciliation.prep_trip`). 항공에는 적용하지 않는다.

<a id="src-docs-reconciliation-rules-md--2-여행의-검증-cardflowtrip_valid"></a>
#### 2. 여행의 검증 (`CardFlow.trip_valid`)

결제일이 없는 아고다 연결에 관한 2026-10-21 사용자 승인: 전체 자료에서 정확한 카드 끝자리·원문 금액으로 카드와 예약이 서로 유일하게 대응하고, 검증된 이용기간이 있으며 취소·환불·기간 충돌이 없으면 `ota_inference.unique_pairs`로 추론 연결한다. 기존 기록·사용자 결정·보류·점유된 카드는 제외하고, 기장된 카드도 유일성 검사에는 포함한다. 결제일은 계속 빈값이고 추론임을 표시한다. 결제일이 없는 다른 공급자와 조건 미달 거래는 종전 규칙대로 보류한다. 이 승인은 검증되지 않은 여행을 만들거나 기존 장부 날짜를 바꾸는 근거가 아니다.

자동 배정은 검증된 여행에만 한다. 여행이 삭제·보관되지 않았고, 아래 중 하나를 만족하면 검증된 여행이다.

1. **구글 여행 탭의 시트 기간과 같다.** 여행 탭이 구글 탭에 연결되어 있고(`google-tab-mapping.json`), 구글 스냅샷의 기간이 여행 탭의 시작일·종료일과 같다. 시트에 종료일이 없으면(누락 또는 당일여행) 다음 여행 전날을 종료일로 본다(`PERIOD_END_FROM_NEXT_TRIP`). 뒤에 여행이 없어 종료일을 정할 수 없는 여행만 검증되지 않는다.
2. **기존 일정 권한 기록과 같다.** 권한 파일(`trip-authority.json`)의 기록과 증거 파일이 여행 탭과 같다. 기록의 원본이 옛 장부 스냅샷이면, 현재 검토 스냅샷의 같은 시트 제목이 그대로여야 한다. 장부를 옮겨 현재 스냅샷에 시트가 없을 때는 해시로 확인한 원본 제목을 쓰되, 구글 탭이 연결되어 있고 시작일이 같으며 구글 쪽 종료일이 추정값일 때만 쓴다. 구글 시트에 다른 기간이 적혀 있으면 이 경로로 검증하지 않는다.

시트의 기간을 고치면 여행 탭의 기간도 같아야 다시 검증된다. 해시를 손으로 맞출 필요는 없다.

<a id="src-docs-reconciliation-rules-md--3-분류-순서-앞이-우선"></a>
#### 3. 분류 순서 (앞이 우선)

0. **보호**: 사용자가 정한 거래(`user_decision`, `user_exception`, `decided_at`)와 장부에 기록된 거래는 분류하지 않는다. 정리 완료 기간(`review_from`, 운영 2026-04-01) 이전 거래는 `preserved`로 두고 분류하지 않는다.
1. **일반 규칙 단계** (`_classify_transaction`): 맞는 규칙을 모두 모은다. 서로 다른 항목·여행을 내면 `rule_conflict`로 확인 대상이다.
   - 예약 증거 규칙 (`ota-mail-live`, `ota-portal-live`, 실행 때 생성): 취소되지 않은 예약은 확정 메일 여부와 관계없이 이용기간의 여행이다(`stay_trip`). 이용기간을 모두 덮는 검증된 여행이 우선이고, 없으면 겹치는 밤이 가장 많은 여행, 그래도 같으면 수입-비용 차액이 큰 여행이다. 저장된 여행 이름이 바뀌었어도 이용기간으로 찾는다.
   - 장부의 미래 적용 규칙 (`board-rule`): 같은 가맹점의 일반 카드 규칙을 대체한다.
   - 저장된 가맹점 규칙: 가맹점 → 항목. 여행은 정하지 않는다.
   - 저장된 가맹점 현지 사용 규칙 (`travel_country`): 카드 사용 국가와 날짜에 맞는 검증된 여행이 있으면 그 여행이다(`retail_trip`). 한 여행이 끝나고 다음 여행이 시작하는 날이면 수입-비용 차액이 큰 여행이다. 맞는 여행이 없으면 `travel_location_hold`로 확인 대상이다.
   - 맞는 규칙이 없으면 카드사 업종(항목만) → 가맹점 패턴(항목만) → 현지 사용 기본 규칙(`*` → 현지경비 + 여행) 순서다. 예약·온라인 결제는 현지 사용으로 보지 않고 `booking_evidence_needed`로 둔다.
2. **카드 3820 싱가포르 예외**: 2026-09-19~09-24 카드 3820 사용은 싱가포르 여행이다(코드 고정, 사용자 지정).
3. **거래별 추론 단계**: 1단계에서 여행이 정해지지 않았을 때만 본다.
   - 사용자가 예약마다 고른 여행(`owner-ota-booking`)이 같은 거래의 다른 추론보다 앞선다.
   - 나머지 추론이 서로 다르면 `inference_conflict`로 확인 대상이다. 같으면 확신이 높은 근거를 쓴다.
   - 예약 이용기간으로 정한 여행이 있으면 그 여행으로 추론한다(`auto-ota-period`).
   - 저장된 추론은 그 여행이 검증되어 있으면 배정한다. 결제일과 여행 시작일의 간격은 보지 않는다.
   - 저장된 추론은 다음 경우 쓰지 않는다: 예약 취소, 이용기간 충돌, 이용기간에 맞는 여행이 없음, 사용자가 예약 배정을 함, 예약 이용기간과 하루도 겹치지 않는 여행을 가리킴. 사용자 예외(`owner-country-exception-20261003`)는 이 확인에서 뺀다.
   - **추천은 없다.** 근거가 있으면 그 여행에 배정하고, 근거가 없거나 맞지 않으면 여행 미배정으로 둔다.
4. **카드 3820 잔여**: 위에서 아무것도 정해지지 않은 카드 3820 구매는 분기 기타비용이다.

<a id="src-docs-reconciliation-rules-md--4-확정-여부"></a>
#### 4. 확정 여부

- 예약 메일의 제목에 `확정`이 있으면 확정으로 본다. 숙박 메일과 결제 대사 모두 같은 규칙을 쓴다 (`ota_mail.extract_mail`, `lodging_mail_facts`, `lodging_mail_matches`).
- 확정 상태는 `confirmed`, `completed`, `upcoming`이다 (`CONFIRMED_STATUSES`).
- 결제 메일만 있고 확정 메일이 없으면 `observed`(수집됨)이다. 수집됨 예약도 이용기간으로 배정한다. 확정 여부는 화면 표시용이다.
- 취소 메일은 `cancelled`이다.

<a id="src-docs-reconciliation-rules-md--5-저장된-규칙의-정리-toolsconsolidate_rulespy"></a>
#### 5. 저장된 규칙의 정리 (`tools/consolidate_rules.py`)

저장된 규칙(`cost_classification_rules`)은 지우지 않고 `status='retired'`로 정리한다. 실행마다 `change_log`에 `rule.retired`와 실행 ID가 남고, `--restore <실행 ID>`로 되돌린다.

정리 대상은 두 가지다.

- `closed-transaction`: 거래 하나에 묶인 규칙인데 그 거래가 장부 기록·사용자 결정·정리 완료 기간 보존으로 닫혀 다시 분류되지 않는다.
- `same-as-local-default`: 가맹점 현지 사용 → 현지경비 규칙인데 현지 사용 기본 규칙과 결과가 같다. 가맹점 패턴이 있거나, 그 가맹점 거래에 카드사 업종이 있거나, 같은 가맹점에 다른 규칙이 있으면 정리하지 않는다.

2026-10-14 운영 사본 기준: 활성 2,172개 → 779개 (정리 1,393개: 닫힌 거래 616, 기본 규칙과 같음 777). 같은 데이터로 전체 분류를 다시 돌려 거래 6,037건의 항목·여행·상태가 하나도 바뀌지 않음을 확인했다. 37건은 분류 근거 문구만 "가맹점 일치"에서 "현지 사용 기본 규칙"으로 바뀐다.

<a id="src-docs-reconciliation-rules-md--6-판정-함수-요약"></a>
#### 6. 판정 함수 요약

| 함수 | 위치 | 의미 |
|---|---|---|
| `card_use_date(tx)` | reconciliation | 카드 이용일 또는 승인일 |
| `covers_stay(ts, te, ci, co, service=)` | reconciliation | 체크인(출발일) ≥ 시작일이고 체크아웃(도착일) ≤ 종료일 |
| `overlaps_stay(ts, te, ci, co, service=)` | reconciliation | 숙박은 여행의 밤이 하나라도 겹침, 항공은 이용일이 하루라도 겹침 |
| `stay_trip(trips, ci, co, service=, nets=)` | reconciliation | 덮는 여행 → 겹치는 밤이 많은 여행 → 수입-비용 차액이 큰 여행 → 겹치는 밤이 없는 숙박은 `prep_trip`(준비 숙박) |
| `prep_trip(trips, ci, co)` | reconciliation | 체크아웃 이후 시작하는 가장 가까운 여행, 거리가 같으면 None |
| `cash_expense_rows(uses, trips=)` | app/ota_cash_use | 캐시 사용분: 이용일을 덮는 여행 1곳 → 숙박 기준 `stay_trip` → 미배정 |
| `trip_valid(tab)` | webapp/card_flow | 2장의 여행 검증 |
| `booking_trip(tx, period)` | webapp/card_flow | 저장된 이름의 여행이 이용기간과 겹치면 그 여행, 아니면 `stay_trip` |
| `retail_trip(tx, country)` | webapp/card_flow | 현지 구매(경계일은 수입-비용 차액) 또는 추론 여행 확인 |
| `_period_trip(candidates, stay)` | webapp/ota_catalog | 검증된 여행 중 `stay_trip` |
| `_relation(stay, trip, service=)` | webapp/ota_catalog | 덮음 / 일부 겹침 / 없음 |

`service` 인자는 항공 예약일 때 참이다. 항공 여부는 예약 라벨에 `항공`이 있는지로 판단한다 (`ota_catalog._build_index`), 또는 예약 기간 초안의 `item == 항공료`로 판단한다 (`card_flow._classify`).

<a id="src-docs-reconciliation-rules-md--7-정해야-할-것"></a>
#### 7. 정해야 할 것

1. **뒤에 여행이 없어 종료일을 정할 수 없는 여행**(현재 0302_야쿠시마)은 검증되지 않는다. 시트 제목에 종료일을 적으면 검증된다.
2. **현지 구매의 나라 매핑이 코드에 고정되어 있다** (`card_flow.retail_trip`의 `countries` 표). 새 행선지는 현지 사용으로 배정되지 않는다.
3. **저장 규칙이 여행을 ID가 아니라 이름으로 기억한다** (`booking_period.target_code`). 이름을 바꾸거나 병합하면 이름이 맞지 않게 되며, 지금은 이용기간으로 다시 찾는다.
4. 같은 판정이 두 경로에 남아 있다. 예약 기간 초안(`card_flow._classify`)과 자동 배정(`_booking_period_assignments`)이다. 같은 판정 함수를 쓰지만 호출 흐름이 나뉘어 있다.

### 카드 처리

> **현재 카드 원본/회계 안전 계약 및 이전 런타임 기록.** 새로운 OTA 연결 미확정이라도 유효 카드 비용 준비를 허용하는 사용자 A 정책은 [COST V3 단일 진입점](../COST_V3_START_HERE.md)과 [OTA 정책 A](ota.md#src-docs-ota-card-reconciliation-policy-a-v3-md)에 있습니다. 기존 OTA 매칭의 구현·수동 확정 보호는 변경 전까지 유지하며, 본문의 과거 기록 수치와 OTA 링크의 무조건 HOLD 문구는 최신 목표가 아닙니다.


<a id="src-docs-card-pipeline-md--현재-ota-자료-연결"></a>
#### 현재 OTA 자료 연결

메일·포털·과거 조사 자료는 운영 `ota-sources.json`에 등록해 함께 조회한다. 자료 내용 변경을 감지하고 미연결 사유를 구분하는 수정까지 적용했다. 현재 연결 수와 남은 항목, 실제 검증 범위는 [현재 OTA A 정책](ota.md#src-docs-ota-card-reconciliation-policy-a-v3-md)의 최신 항목을 따른다.

화면 하나에서 업로드, 자동 분류, 질문 답변, 규칙 수정, 미리보기, 장부 기록을 수행한다. 서버의 별도 카드 작업자 없이 업로드 요청에서 분류까지 처리한다.

기업, 국민 국내와 해외, 하나 국내와 해외의 실제 양식을 읽는다. 금액과 승인일, 원번호, 취소 관계를 보존한다. 취소 금액은 음수로 정규화하고 하나의 분할 거래는 검증된 기존 정규화기를 사용한다. 승인일이 없으면 매입일을 처리 날짜로 사용하되 원본 승인일을 채워 만들지 않는다.

파일 원문은 DB에 보존한다. 같은 파일 재업로드는 기존 처리 결과를 반환한다. 다른 파일에 같은 거래가 있으면 원본 거래를 덮지 않고 파일과 거래의 관계만 추가한다. 승인번호 충돌과 번호 없는 거래의 의심스러운 반복은 보류한다.

확정된 답변은 재분류가 덮지 않는다. 답변 저장과 규칙 수정은 즉시 적용된다. 동일 가맹점 규칙이 미래 여행까지 복제하지 않는다. 여행은 검증된 명시 일정이 있을 때만 선택한다. 저장된 자유 형식 요청을 AI가 처리 중이라고 표시하지 않는다.

운영 검토 범위는 2026-04-01 이후다. 완료된 이전 기간은 원본과 처리 이력을 내부 보존하고 목록, 질문, 미리보기와 신규 전기에서 제외한다. 업로드된 다섯 파일의 현재 거래 1,676건은 그대로 검토할 수 있다.

예약 자료로 확인한 규칙은 원본 거래 hash와 이용기간 조건을 유지한다. 화면에서 비용 항목을 수정해도 해당 조건을 지우지 않는다. 현지경비 기본 규칙은 원본 사용 국가, 실제 승인일과 검증된 여행이 모두 맞을 때만 적용하며 예약·온라인 공급자의 결제일을 이용일로 해석하지 않는다.

확인 질문은 한 페이지에 스무 건씩 표시한다. 자동분류 결과도 개별 수정할 수 있다. 규칙은 가맹점이나 항목으로 검색하고 수정한다. 입력 중에는 다른 기기의 갱신으로 답변을 지우지 않는다.

사용자가 허용한 원행별 추론도 미리보기에 반영한다. 추론 배정과 사용자 예외를 구분해 표시하고 배정 근거를 펼쳐 볼 수 있다. 확신이 낮은 추론은 질문 영역에 확인 권장으로 표시하며 수정하지 않아도 기록할 수 있다. 한 번의 조회에서는 여행별 검증 결과를 미리보기와 선택지가 함께 사용해 반복 원본 읽기를 줄인다. 다음 조회와 장부 기록에서는 명시 일정 근거를 다시 검사한다.

자동 분류 결과와 사용자 답변 결과를 미리 보여 준다. 원본 오류와 충돌, 무효 여행 배정은 기록 대상에서 제외한다. **이 문장은 2026-10-08 당시 수동 경로 설명이다.** 이후 2026-10-13에는 소유자의 답변 저장·자동 처리 요청에 한해 기존 검증된 원자적 기록 경로를 통한 자동 내부 기록이 도입됐다. 최신 목표 A 정책은 정상 카드의 OTA 링크 미확정만으로 내부 준비를 막지 않지만, 이 변경은 아직 구현되지 않았다. 조회 API에서 새 자동 쓰기를 수행하지 않는다. 장부 반영 실패는 거래 상태와 영수증과 장부와 감사 이력을 함께 되돌린다. 같은 요청을 재시도해도 장부가 늘지 않는다.

홈은 카드, 정리할 지출, 장부 건수만 표시한다. 정상 분류됐지만 아직 장부에 기록되지 않은 카드 거래에는 별도 상태명을 표시하지 않는다. 실제 장부 기록 여부는 `ledger_entries` 근거로 판정한다.

카드 검토의 OTA 예약번호와 이용기간은 기존 대조 report에서 가져온다. `CardFlow.preview_metadata()`가 한 미리보기 요청에서 같은 report를 재사용하며, `entry_metadata`로 미리보기 행에 연결한다. `ledger-preview-v2` digest는 `booking_ref`, `service_period`, `ota_evidence`까지 보호한다. 기록 요청은 새 resolver로 미리보기를 다시 계산하고 digest를 비교한 뒤 그 행을 그대로 projection한다. 예약번호는 `board_rows` payload의 `reservation_no`에, 이용기간은 `service_period`에 저장하고 근거 digest는 기존 `classification_basis`에 OTA 출처로 보존한다. `ledger_entries` 스키마는 확장하지 않는다. 자세한 확정·모호성 조건은 [현재 OTA A 정책](ota.md#src-docs-ota-card-reconciliation-policy-a-v3-md)를 따른다.

<a id="src-docs-card-pipeline-md--api"></a>
#### API

모든 카드 경로는 기존 로그인과 소유자 권한을 요구한다. 저장 요청에는 CSRF 토큰을 요구한다.

로그인하지 않은 /import 요청은 로그인 안내와 함께 401을 반환하고, API도 401을 반환한다. 기존 /review 진입은 소유자 권한 확인 후 같은 카드 처리 화면으로 이동한다.

카드 처리 경로가 활성화된 운영 환경에서 기본 로그인 완료 경로는 시작 화면이다. 소유자는 카드 처리 화면으로, 조회 사용자에게는 권한을 확인한 장부 화면으로 연결한다. 명시적으로 지정한 장부 이동 경로는 유지한다. 서버 연결 중단은 사용자가 이해할 수 있는 안내로 표시하고 입력 내용을 지우지 않는다.

- GET /import: 카드 처리 화면을 연다.
- POST /api/imports: 파일을 수신하고 분류한다.
- GET /api/imports: 기존 파일 목록을 조회한다.
- GET /api/imports/{batch}: 질문과 미리보기를 조회한다.
- POST /api/imports/{batch}/decision: 답변을 저장하고 다시 분류한다.
- GET 또는 POST /api/imports/rules: 규칙을 조회하거나 수정한다.
- POST /api/imports/{batch}/commit: 최신 미리보기 digest를 검증하고 기록한다.

답변과 규칙은 revision을 검사하고, 기록은 최신 미리보기를 검사한다. 다른 기기의 수정은 카드 화면에서 이 초마다 확인한다. 입력 중인 답변은 자동 갱신으로 지우지 않고 변경 사실을 알린다.

<a id="src-docs-card-pipeline-md--2026-10-08-확인한-기록-계약"></a>
#### 2026-10-08 확인한 기록 계약

CSV, XLSX와 바이너리 XLS(국민카드 매입 원본)를 웹 파서가 읽는다. XLS는 `xlrd`로 첫 시트의 셀 값을 그대로 읽고 이후 정규화 규칙은 CSV·XLSX와 같다. 같은 기간을 CSV로 이미 가져왔어도 XLS를 올리면 새 거래가 생기지 않고(정규화한 값이 같은 거래는 기존 거래로 인식) 사용자가 확정한 값은 그대로다. 승인내역 XLS(`승인방식` 열이 있고 `매입일` 열이 없는 파일)는 매입 확정 전 자료라 중복을 만들 수 있어 `APPROVAL_FILE_NOT_ACQUIRED`로 거절하며, 거절 사실만 이력에 남는다. 원본 분석과 운영 가져오기 완료는 계속 구분한다.

`recordable_rows()`의 blocked·already_booked 제외와 고유 거래 기준을 API ready와 홈에 함께 적용한다. 기록 후 ready에는 이미 기록한 행이 남지 않는다. 장부 projection은 `source_event_id`로 같은 거래를 먼저 찾는다. 거래 ID가 없는 과거 장부 행은 카드사·카드 끝자리·승인번호·일자·부호 있는 금액·거래 종류가 모두 같을 때만 중복으로 차단한다. 서로 다른 실제 거래 ID와 승인·취소·환불을 보존한다.

운영에 반영한 건수와 남은 일정·보류 문제는 [운영 문서](../operations.md)에 기록한다. 사용자 지시로 수행한 이번 일괄 기록은 일반 웹 흐름의 자동 기록 기능을 추가한 것이 아니다.


<a id="src-docs-card-pipeline-md--2026-10-10-검토--규칙--출력-흐름"></a>
#### 2026-10-10 검토 → 규칙 → 출력 흐름

- 장부 행을 열면 `예외 처리 (이 건만)`과 `규칙 변경 (반복되는 경우)`을 고를 수 있다. 이 건만 저장하면 그 행만 바뀌고 규칙은 만들어지지 않는다.
- `규칙 변경`으로 저장하면 규칙 대화 화면에서 `내 수정 내용으로 규칙 초안 만들기`를 쓴다. 초안은 저장된 수정(항목·여행)과 카드 원천 가맹점으로 서버가 결정적으로 만들며 모델을 쓰지 않는다. 초안은 어떤 행도 바꾸지 않는다.
- 규칙 조건은 가맹점뿐이다(카드 장부 행에는 규칙이 맞출 수 있는 거래 방향·카드 구분이 없다). 화면은 적용 범위를 "모든 여행·모든 카드의 같은 가맹점 거래"로 문장으로 보여 준다.
- 영향 미리보기에서 `기존 행 적용`과 `미래 입력 적용`을 따로 고르고 `이 범위로 적용`을 눌러야 켜진다. 둘 다 끄면 규칙은 초안으로 남는다. 직접 수정해 잠긴 필드는 영향 대상에서 제외된다.
- `미래 입력 적용`을 켜면 카드 업로드 분류에 이 규칙이 들어간다(사용자가 확정한 거래는 덮지 않는다). 같은 가맹점의 일반 카드 규칙이 있으면 명시 적용한 이 규칙이 그 항목을 대체하고, 원천 거래·예약에 묶인 규칙은 건드리지 않는다. 적용 직후 미기록 카드 거래를 다시 분류한다.
- 분류대기(여행 미정) 행도 항목만 고쳐 저장할 수 있다.
- 출력은 선택한 여행 탭의 저장된 장부 상태 그대로 만든다. 검토필요 행도 화면대로 들어가며 분류대기는 들어가지 않는다는 안내가 화면에 있다.

<a id="src-docs-card-downloads-md--국민-기업카드-자료-수집과-사용-기준"></a>
### 국민 기업카드 자료 수집과 사용 기준

> **역사적 수집 결과 + 유효한 카드 안전 규칙**. 이 문서의 수집 건수·당시 업로드 지원 여부는 2026-10-05~09 기록이다. V3 개발 진입은 [COST V3 START HERE](../COST_V3_START_HERE.md), 실제 카드 파서 지원은 `app/import_card.py`와 `requirements.txt`에서 확인한다.


2026-10-09 기준으로 아래 원본 수집 결과와 웹 가져오기 상태를 구분한다. 국민 원본 3개는 보존돼 있고 국내·해외 매입의 행별 검사는 완료했다. **당시(2026-10-09) 웹 업로드 경로는 CSV·XLSX 중심이었다. 최신 main의 `app/import_card.py::read_cells()`는 CSV·XLSX 및 바이너리 XLS를 지원하며, XLS에는 `xlrd` 설치가 필요하다.** 운영 서버의 배포/의존성은 별도 확인이 필요하다. 하나·기업의 기존 승인 파일과 국민의 변환 자료를 포함해 운영에 반영된 카드 파일은 7개다. 현재 운영 수치는 [운영 문서](../operations.md)를 따른다.

국민 국내 매입 원본에서 760,200원 취소 전표가 기존 항공권 원결제와 정확히 연결됨을 확인했다. 기존 미확인 기록을 환불 원문 부재로 계속 해석하지 않는다. 국내 매입 변환 CSV는 승인번호로 기존 534건과 일치시키고 신규 482건을 가져왔다. 해외 매입 764행은 승인번호 대신 카드 끝자리·승인일·통화·외화 금액·가맹점 첫 토큰·총청구액과 원금+수수료 관계를 함께 사용해 재대조했고, 기존과 동일 464건(복수 후보 34건 포함), 안전 신규 227건, 취소 70건, 현금서비스 등 특수 3건으로 분류했다. 안전 신규 227건만 복구 사본에서 충돌 0과 재수신 동일을 확인한 뒤 운영에 가져왔다. 원본 검사 완료를 일괄 장부 반영 완료로 표시하지 않는다.


장부의 비용 금액과 취소 전표는 **국내 매입 내역과 해외 매입 내역을 각각 받아서** 확인한다. 승인 내역은 최근 사용, 승인 취소, 승인번호와 매입 전 거래를 확인하는 보조 자료로 보존한다. 세 파일을 그대로 합쳐 비용으로 기록하지 않는다.

<a id="src-docs-card-downloads-md--자료별-역할"></a>
#### 자료별 역할

| 자료 | 필요 여부 | 확인할 내용 | 조회 기준 |
| --- | --- | --- | --- |
| 국내 매입 내역 | 필수 | 정당전표, 취소전표, 원화 금액, 매입일, 원승인번호 | 매입일 |
| 해외 매입 내역 | 필수 | 현지 금액, 미화 환산액, 결제원금, 수수료, 총 결제금액, 취소매출 | 매입일 |
| 승인 내역 | 보조 | 최근 승인, 승인 취소, 승인번호, 승인시간, 매입 전 사용 | 승인일 |

승인 화면은 매입 취소를 국내 매입 화면에서 조회하라고 안내한다. 국내 매입 화면도 승인 취소는 승인 화면에서 조회하라고 안내한다. **승인 취소와 매입 취소는 서로 다른 상태다.** 승인 취소만 읽어서 정산된 환불이 모두 반영됐다고 판단하지 않는다. 매입되지 않은 승인 취소를 새 환불 비용으로 기록하지 않는다.

<a id="src-docs-card-downloads-md--다운로드-경로와-조건"></a>
#### 다운로드 경로와 조건

2026-10-05에 실제 로그인된 회사 세션에서 확인한 경로다. 탭과 계정, 회사명, 로그인 여부는 실행할 때마다 다시 확인한다.

- 승인: `https://biz.kbcard.com/CXERCMLSD0001.cms`.
- 국내 매입: `https://biz.kbcard.com/CXERCMLSD0002.cms`.
- 해외 매입: `https://biz.kbcard.com/CXERCMLS0008.cms`. 전체메뉴 → My Biz → 이용내역 → 해외매입내역으로 이동한다.
- 회사 전체를 받으려면 조회구분은 `사업자`로 둔다. 승인 매출구분은 `전체`, 국내 매입 전표 필터는 `전체`로 둔다.
- 국내 매입은 최근 24개월 범위에서 전날까지 조회할 수 있다. 해외 매입은 최근 24개월 이내, 승인은 최근 12개월 이내 조회가 가능하다. 최종 허용 종료일은 현재 화면에서 확인한다.
- `XLS 파일저장` → 새 화면의 `엑셀파일저장` 순으로 실행한다. 다운로드 이벤트와 실제 파일을 모두 확인한다. 승인번호를 얻겠다고 마스킹 해제나 재서명을 실행하지 않는다.
- 파일은 `kb-domestic-acquired-시작일-종료일.xls`, `kb-overseas-acquired-시작일-종료일.xls`, `kb-approval-시작일-종료일.xls`로 구분한다. 원래 다운로드 이름은 실행 기록에 남긴다.

같은 숫자의 기간을 입력해도 승인과 매입의 포함 거래는 다르다. 이번 국내 매입 파일에는 2025년 승인 거래의 2026년 매입·취소도 들어 있다. 조회 기간 밖의 원승인일이라는 이유로 매입 행을 버리지 않는다. 기간 갱신은 매입일을 기준으로 겹치는 구간을 다시 받아 검증하며, 지연 매입·취소 누락이 의심되면 더 넓은 매입 기간을 재조회한다.

<a id="src-docs-card-downloads-md--금액과-거래-연결-규칙"></a>
#### 금액과 거래 연결 규칙

1. 국내 금액은 원본 `승인금액`과 `상태`를 함께 읽는다. `승인구분`은 국내외 구분이며 취소 상태가 아니다. 취소 전표의 `승인번호`는 `취소번호(원승인번호)` 형식이므로 두 번호를 별도로 보존한다.
2. 해외 비용의 청구 원화는 `총결제금액`을 사용한다. `결제원금`과 `수수료`를 별도로 보존하고 `결제원금 + 수수료 = 총결제금액`을 검사한다. 총 결제금액에 수수료를 다시 더하지 않는다. 카드사의 원화 금액이 있는데 자체 환율로 재계산하지 않는다.
3. 해외 취소는 `결제방법=취소매출`로 식별한다. 이번 취소 원본 70행의 금액은 모두 양수다. 원본은 그대로 두고 정규화한 취소 효과만 음수로 표현한다. 화면의 취소금액 요약이 0원이어도 상세 취소 행을 누락하지 않는다.
4. 해외 원본에는 승인번호가 없다. 승인번호 없는 취소는 카드·가맹점명·외화 통화·외화 금액이 같은 구매와만 짝짓는다(`app/partial_refund.py`, `config/refund-pairing.json`, 소유자 2026-10-16). 같은 조건의 구매와 취소가 여러 건이면 날짜 순서대로 구매 하나에 취소 하나씩 짝짓는다. 구매가 앞설 때만 짝이고, 쓸 구매가 없는 취소는 짝 없이 둔다. 같은 조건의 구매가 있는데 짝을 정하지 못한 남는 취소는 묶음으로 보류한다. 같은 외화끼리만 비교하고 미화 환산액과 비교하지 않는다. 원화 차이는 환율·수수료로 보고 잔액에 남긴다.
5. 해외 파일에는 모든 열의 값이 같은 복수 거래도 있다. 값이 같다고 삭제하거나 합치지 않는다. 동일 원본의 재수집 방지는 파일 해시와 원본 행 위치로 처리하고, 파일 간 연결은 실제 복수 거래의 개수와 연결 근거를 보존해야 한다. 승인번호 없는 해외 행의 확정 연결은 별도 처리 대상이다.
6. 승인과 매입에 있는 같은 결제는 출처가 둘인 한 거래다. 매입된 거래의 비용 금액은 매입 원본을 사용하며 승인액을 추가 전기하지 않는다. 승인 취소와 취소매입도 각각의 상태를 보존하고 환불 효과를 두 번 기록하지 않는다.
7. `현금서비스`, `리버설-일시불매출` 같은 다른 거래 종류는 원문과 금액을 보존하고 별도 검토한다. 모두 일반 여행 비용이나 환불로 자동 처리하지 않는다. 취소 전표가 있다는 사실과 은행 계좌에 현금 환급이 완료됐다는 사실도 구분한다.

#### 실제 검증 결과

2026-10-05 수동 로그인된 세션에서 조회 기간 2026-04-01~2026-10-04의 원본 세 개를 다운로드했다. 이번 결과는 무인 로그인 성공 증거가 아니다.

| 원본 | 전체 행 | 정상 또는 기타 매출 | 취소 행 |
| --- | ---: | ---: | ---: |
| 승인 | 2,124 | 1,840 | 284 |
| 국내 매입 | 1,016 | 861 | 155 |
| 해외 매입 | 764 | 694 | 70 |

- 국내 취소매입 금액은 42,909,834원이다. 155행 모두 원승인번호가 있고, 같은 카드와 원승인번호로 국내 승인 취소 원본에 일치하는 행은 0행이다. 해외 승인번호와 국내 원승인번호를 섞어서 비교하지 않는다. 승인 취소가 매입 취소를 대신하지 못한다는 원본 근거다. 조회 축과 거래번호 의미가 다르므로 단순 행수 차이를 누락 건수라고 해석하지 않는다.
- 해외 취소매입의 총 결제금액 합계는 12,130,780원이다. 764행 모두 원금·수수료 합산 검사를 통과했다.
- 해외의 694개 비취소 행에는 일시불매출 691행, 현금서비스 1행, 리버설 2행이 포함된다. 해외 원본의 승인번호는 0개이며 값이 같은 복수 행은 보존했다.
- 해외 승인 정상 합계는 화면에서 83,259.99달러, 다운로드 원본 집계에서 83,263.50달러였다. 3.51달러 차이의 원인은 확인하지 못했다. 화면 합계만으로 원본 무결성을 주장하지 않으며 승인액을 청구 원화 대신 사용하지 않는다.

원본, 파일 해시, 행별 구조 집계와 비교 결과는 `.local-archive/card-downloads/20261005-kb-source-review`에 보존했다. 이 절의 2026-10-05 원본 검사는 당시 운영 DB를 변경하지 않았지만, 이후 2026-10-09에 국내 안전 신규 482건과 해외 안전 신규 227건을 별도 변환 CSV로 검증 후 운영에 가져왔다. 장부 기록은 만들지 않았다. 2026-10-09 당시에는 바이너리 XLS를 변환해 가져왔지만, 최신 main 파서는 XLS 원본을 직접 읽도록 구현돼 있다(`xlrd` 필수). 당시 분석 완료와 당시 운영 import 완료는 별개이며, 신규 경로의 실제 운영 배포·현장 업로드 성공은 여기서 확인한 것이 아니다.

<a id="src-docs-card-downloads-md--반복-실행"></a>
#### 반복 실행

카드 다운로드 스킬 `cost-card-download`와 그 `scripts/download.ps1`에 같은 자료 선택 기준을 반영했다. 이미 로그인돼 있으면 해당 세션을 사용한다. 수집 완료 판정에는 국내·해외 매입 각각의 다운로드 또는 실제 0건 근거가 필요하다.

원본 비교는 다음 명령으로 재실행할 수 있다. 실제 파일 경로와 조회 기간을 바꾼다.

```powershell
python tools/inspect_kb_exports.py --approval .local-archive/card-downloads/20261005-kb-source-review/kb-approval-20260401-20261004.xls --domestic .local-archive/card-downloads/20261005-kb-source-review/kb-domestic-acquired-20260401-20261004.xls --overseas .local-archive/card-downloads/20261005-kb-source-review/kb-overseas-acquired-20260401-20261004.xls --from 2026-04-01 --to 2026-10-04 --output .local-archive/card-downloads/20261005-kb-source-review/source-comparison.json
```

분석 도구는 XLS 읽기용 `xlrd`를 사용한다. 현재 작업 환경에서는 이미 보존된 `.local-archive/card-downloads/parser-libs`를 사용할 수 있다. 원본과 운영 DB를 수정하지 않으며 집계 보고서만 쓴다. 새 다운로드를 기존 원본 위에 저장하지 않는다.

<a id="src-docs-company-expense-exclusion-md--회사-경비-제외"></a>
### 회사 경비 제외

카드 검토 화면에서 거래를 고르고 `이 건은 회사 경비 아님`을 제안합니다. 제외할 거래를 확인한 뒤 `회사 경비 제외 확인`을 누르고 별도 확인에 동의해야 적용됩니다. 소유자만 변경할 수 있습니다.

원본 거래와 기존 분류 결정은 유지합니다. 제외된 거래는 장부 기록 준비 목록과 Google TSV에서 빠집니다. 화면의 제외 목록에서 되돌릴 수 있으며, 이후에 확정한 분류도 덮어쓰지 않습니다. 요청 번호와 상태 버전으로 재시도·중복 적용·오래된 되돌리기를 보호하고, 적용과 되돌리기를 변경 이력에 기록합니다.

이미 장부에 기록했거나 사용자 확정이 있는 거래의 신규 제외, 환불 묶음, 중복·충돌·보류 거래는 이 경로로 변경하지 않습니다. 이 범위의 정책은 별도로 확인해야 합니다. Google에 이미 붙여넣은 행을 자동으로 삭제하거나 수정하지 않습니다.

`transaction_company_exclusions` 표는 별도 명령 없이 `app.db.Store`를 만들 때 자동으로 생성됩니다. `Store.open()`과 `Pipeline(connection)`도 이 경로를 사용합니다. 웹에서는 선택된 장부 연결로 첫 `CardFlow`를 만드는 요청이 생성 시점이며, 카드 목록 조회와 규칙 검토도 이 경로를 사용할 수 있습니다. 서버 시작만으로 생성된다고 가정하거나, 쓰기 버튼을 누르기 전에는 DB 변경이 없다고 가정하면 안 됩니다.

스키마 생성은 저장점 안에서 실행합니다. 도중 실패하면 이번에 만든 표와 인덱스를 모두 되돌리고, 호출자가 진행 중이던 트랜잭션을 자동으로 커밋하지 않습니다. 기존 표와 자료는 보존하며 반복 실행은 같은 스키마를 유지합니다. 격리 SQLite에서 기존 자료 보존, 실패 롤백, 호출자 롤백, 첫 `CardFlow` 생성 시점을 검증합니다. 기존 DB 파일을 이전 버전으로 복원하는 운영 롤백은 별도 복구 사본이 필요합니다.

이번 실행에서는 임시 DB만 변경했으며 운영 DB에는 적용하지 않았습니다. 운영 적용 전에는 자동 스키마 생성까지 포함한 DB 변경 승인과 복구 사본 검증이 필요합니다. 승인 전에는 새 코드를 운영 DB에 연결하지 않습니다.

표적 검증 파일은 `tests/card_pipeline/test_company_expenses.py`, `tests/card_pipeline/test_company_expense_integration.py`, `tests/card_pipeline/test_schema_migration.py`, `webapp/tests/test_company_exclusion_http.py`입니다. 원본 보존, 적용과 되돌리기, 재시도, 상태 충돌, 감사 기록 실패의 롤백 및 390px·1440px 화면을 다룹니다. 통합 검사는 제외 전 미리보기의 확정 거부, 제외 행의 기록과 TSV 배제, 되돌리기 후 사용자 결정 보존, 장부 오류 후 같은 요청 재시도, 환불 연결 보호와 제외 후 별도 파일의 환불 도착도 확인합니다.
