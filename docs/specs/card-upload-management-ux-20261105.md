# 카드 자료 수집 현황·조회기간 누락 관리 UX 재설계 (2026-11-05)

> **상태: 제품 방향 확정 / 상세 구현 명세 / 런타임 구현 전.** 기존 조회기간 계산 엔진과 비동기 업로드는 재사용한다. 이번 명세의 핵심은 카드사별 파일 목록을 카드별 조회 범위 관리로 전환하는 것이다. 문서 병합은 UI·API 구현이나 운영 배포 완료를 뜻하지 않는다.

## 0. 목표와 제품 결정

현재 화면은 카드사별 업로드 파일 수와 파일 제목을 보여주는 수준이다. 사용자가 알고 싶은 것은 파일이 몇 개인지가 아니라 **어떤 카드의 어느 조회기간을 확보했고, 어느 기간이 빠져 있으며, 빠진 기간을 어떻게 채우는지**다.

최종 사용 경험은 다음과 같다.

1. 카드 자료 관리 화면에 카드별 수집 현황을 먼저 보여준다.
2. 업로드 파일에서 카드사·카드 식별·실제 조회기간·조회 기준·전체 조회 여부를 자동 추출한다.
3. 기존 조회기간과 대조해 누락·겹침·중복·확인 불가 구간을 구분한다.
4. 누락 기간마다 **이 기간 자료 추가**를 제공한다. 누르면 해당 카드와 날짜가 고정된 업로드 흐름으로 이동한다.
5. 업로드 결과에서 조회기간이 검증되면 카드 현황을 즉시 갱신한다. 사용자는 별도 파일 목록이나 다른 메뉴를 찾아다니지 않는다.
6. 파일의 조회기간을 읽을 수 없는 경우에만 필요한 정보를 입력받는다. 거래일 최소·최대값으로 조회기간을 추정하지 않는다.
7. 0건 조회도 카드·기간·조회 기준·전체 조회 증거가 있으면 유효한 조회 완료로 표시한다.
8. 카드 거래의 수집·분류·내부 기록·환불·Google 반영은 별개다. 조회기간 확인은 금융 완료나 장부 반영을 뜻하지 않는다.

## 2. 정보 구조와 화면 설계

### 2.1 카드 자료 관리가 첫 화면

/import 상단에서 저장된 카드 자료 선택과 카드별 조회 기간을 서로 떨어진 접기 메뉴로 두지 않는다. 하나의 **카드 자료 관리** 영역을 기본 노출한다.

상단 요약은 다음 네 가지를 보여준다.

- 관리 중인 카드 수
- 조회기간 확인 완료 카드/조회 축 수
- 미수집 기간 수
- 조회 범위 확인이 필요한 파일 수

숫자는 파일 수나 거래 수가 아니라 카드·조회 축·기간의 고유 단위를 사용한다. 동일 거래가 여러 파일에 등장해도 카드 수집 현황을 중복 집계하지 않는다.

### 2.2 카드별 현황 카드

카드사별 그룹 아래에 실제 카드 식별 단위의 카드를 배치한다.

**카드 카드의 필수 정보**

- 카드사명
- 카드 별칭이 있으면 별칭, 없으면 마스킹 번호 끝4자리
- 카드 식별 신뢰 범위: 전체 마스킹 번호 확인 / 끝4자리만 확인 / 파일 단위 식별
- 조회 기준: 승인일·이용일·매입일. 서로 다른 기준은 절대 한 타임라인으로 합치지 않는다.
- 관리 시작일과 조회 기준일(기본 오늘)
- 확인된 조회기간 목록 또는 시각적 타임라인
- 미수집 기간 목록
- 업로드 파일 수, 고유 거래 수, 0건 조회 파일 수
- 최근 업로드 시각과 마지막으로 확인된 조회 종료일
- 파일별 상세 목록 열기

**상태 문구**

| 상태 | 표시 | 의미 |
| --- | --- | --- |
| COVERAGE_COMPLETE | 조회 범위 확보 | 관리 시작일부터 기준일까지 확인된 조회기간이 연속됨 |
| GAPS_FOUND | 미수집 기간 N곳 | 명시된 관리 범위 안에 확인되지 않은 기간이 존재 |
| BASELINE_UNSET | 수집 시작일 설정 필요 | 최초 업로드 이전 기간은 누락인지 알 수 없음 |
| FILES_NEED_REVIEW | 조회 범위 확인 필요 N개 | 파일은 접수됐지만 조회기간/기준/카드 식별을 확인할 수 없음 |
| PARTIAL_OR_RESTRICTED | 전체 조회 증빙 불가 | 제한 조회·필터·부분 다운로드·파싱/메타데이터 충돌 |
| PROCESSING | 업로드 처리 중 N개 | 파일 접수 완료, 백그라운드 작업 진행 중 |

색만으로 상태를 구분하지 않는다. 텍스트·아이콘·테두리/패턴을 함께 사용한다.

### 2.3 조회기간 타임라인과 누락 표시

- 기간은 날짜 단위의 inclusive interval로 표시한다.
- 조회 완료 구간과 미수집 구간을 서로 다른 세그먼트로 표현하고, 바로 아래에 정확한 시작일·종료일을 텍스트로 표시한다.
- 부분 월 조회를 월 전체 조회처럼 보이지 않게 한다. 월 단위 요약이 필요하면 일부 기간 확인과 월 전체 확인을 구분한다.
- 긴 기간은 연도별로 접을 수 있지만 기본 카드에서 현재 미수집 기간과 마지막 확인 종료일은 항상 노출한다.
- 누락 기간이 여러 개면 각 기간마다 독립된 이 기간 자료 추가 버튼을 제공한다.
- 기간이 겹치는 파일은 중복 기간을 표시하되 누락으로 계산하지 않는다.
- 조회 기준이 다른 기간은 합치거나 상호 보완하지 않는다.

예시(설명용):

| 조회 기준 | 확인된 기간 | 미수집 기간 | 다음 행동 |
| --- | --- | --- | --- |
| 이용일 | 2025-01-01~2025-03-31, 2025-05-01~2026-11-05 | 2025-04-01~2025-04-30 | 4월 자료 추가 |
| 매입일 | 2025-01-01~2025-12-31 | 2026-01-01~2026-02-15 | 1~2월 자료 추가 |

### 2.4 수집 시작일 설정

현재 CoverageStore.summary()는 관리 시작일이 없으면 최초 확인 기간의 시작을 계산 기준으로 사용한다. 따라서 그 이전의 누락은 알 수 없다.

- 새 카드의 첫 조회 증빙을 등록할 때 관리 시작일을 한 번 설정하도록 안내한다.
- 모르는 경우 최초 확인 기간부터 관리를 선택할 수 있다. 이때 이전 기간은 누락이 아니라 **미관리 범위**로 표시한다.
- 관리 시작일을 설정한 뒤에는 그 날짜부터 누락을 계산한다.
- 관리 시작일은 파일별 값이 아니라 카드 ID + 조회 기준별 기준값으로 취급한다.
- 기존 기록에 기준일이 없다고 임의로 과거 거래를 역산하거나 소급 확인하지 않는다.
- 기준일 변경은 owner 권한·CSRF·감사 기록을 거친다. 변경 전후의 조회 구간을 재계산하고 기존 원본/거래/장부는 수정하지 않는다.

### 2.5 업로드 파일 상세 목록

카드 카드 안에서 파일 목록을 펼치면 각 파일을 한 줄 또는 카드로 표시한다.

- 파일명(HTML escape)
- 실제 조회기간과 조회 기준
- 실제 거래 발생기간은 별도 필드로 거래 발생기간이라고 명시
- 파싱된 거래행 수 및 고유 거래 수
- 0건 조회인 경우 조회 결과 0건 · 기간 증빙 완료
- 업로드 시각
- 파일 처리 상태(접수·분류·내부 기록·검증 결과)
- 조회 증빙 상태(확인 완료·확인 필요·제한 조회·충돌)
- 겹치는 기존 기간 또는 해당 파일이 메운 공백
- 상세 결과 링크

파일이 많아지면 카드별 페이지네이션/더 보기로 확장한다. 최초 화면에 전체 파일명을 길게 나열하지 않는다.

**중요:** period_start/end가 거래 행의 MIN/MAX라면 반드시 거래 발생기간으로 표시한다. 이를 카드사 조회기간으로 표현하지 않는다.

## 3. 업로드 사용자 흐름

### 3.1 일반 업로드

1. 사용자가 카드 자료 추가를 선택한다.
2. 카드 선택은 기존 카드 선택 또는 새 카드 식별을 제공한다. 카드가 특정되지 않으면 파일 메타데이터에서 추출한다.
3. XLS/XLSX/CSV 다중 선택·드래그 앤 드롭·키보드 선택을 유지한다.
4. 서버는 파일 접수 시점에 기존 parser와 app.card_upload_coverage.inspect()를 사용해 파일별 메타데이터를 추출한다. 업로드 응답에 파일별 coverage_evidence를 포함해 분류가 끝나기 전에도 조회기간 미리보기를 보여준다.
5. 각 파일에 카드사·카드 식별·조회 시작/종료일·조회 기준·거래행 수·제한 조회 여부·파싱 상태·기존 파일과의 동일 해시 여부·기존 조회기간과의 겹침/공백을 표시한다.
6. 사용자는 파일별 결과를 보고 접수를 진행한다. 기존 비동기 업로드·백그라운드 분류·새로고침 복구는 유지한다.
7. 명시적 전체 조회 메타데이터가 신뢰 조건을 만족하면 분류·내부 기록 성공 후 시스템이 자동으로 조회 증빙을 저장한다. 사용자가 같은 기간을 다시 입력하거나 체크박스를 누르지 않는다.
8. 파일에 조회기간이 명시되지 않은 경우에만 수동 확인 폼을 제공한다. 거래일 MIN/MAX는 기본값으로 채우지 않는다. 사용자가 카드사 화면에서 실제 선택한 기간·기준·전체 조회 여부를 직접 확인해야 한다.
9. 처리 결과와 조회 증빙을 저장한 뒤 카드 자료 관리 화면을 자동 갱신하고, 메운 공백과 남은 공백을 보여준다.

### 3.2 누락 기간에서 시작하는 업로드

각 gap의 이 기간 자료 추가는 일반 업로드와 다른 고정 문맥을 전달한다.

- 선택된 카드 ID/프로필
- 카드사·마스킹 번호
- 조회 기준
- 요청한 시작일·종료일
- 기준일과 gap 식별자

업로드 영역 상단에 다음과 같은 고정 안내를 보여준다.

국민카드 · 끝 1234 · 이용일 기준 · 2025-04-01~2025-04-30 자료를 추가합니다.

- 사용자는 카드사 웹사이트에서 이 기간을 조회해 전체 결과 파일을 내려받은 뒤 업로드한다.
- 업로드된 파일의 실제 메타데이터 기간이 요청 gap을 포함하는지 서버에서 확인한다.
- 기간이 일치하면 해당 gap을 해소할 수 있다.
- 파일 기간이 요청 범위보다 짧거나 다른 카드/조회 기준이면 gap은 닫지 않는다. 실제 파일은 정상 카드 거래 수신 경로로 처리할 수 있으나 요청 기간과 불일치를 명확히 표시한다.
- 조회기간 메타데이터가 없는 파일은 사용자가 정확한 기간을 확인한 뒤 수동 증빙할 수 있다. 확인 전에는 gap을 닫지 않는다.
- 한 gap을 여러 파일로 나눠 채우는 경우 각 파일의 검증된 구간을 합산하고 남은 구간을 다시 계산한다.

### 3.3 파일별 메타데이터 판정

| 파일 상태 | 조회기간 처리 | 금융 거래 업로드 |
| --- | --- | --- |
| 명시된 기간·기준·카드 식별, 전체 조회, 파싱 정상 | 자동 증빙 가능 | 기존 파이프라인 진행 |
| 거래 0건 + 명시된 기간·기준·카드 식별 + 전체 조회 | 0건 조회 증빙으로 자동 인정 가능 | 빈 거래로 정상 종료 |
| 조회기간 없음 | 사용자 수동 확인 필요 | 기존 parser가 허용하면 진행 |
| 조회 기준 없음 | 사용자 수동 확인 필요 | 기존 parser가 허용하면 진행 |
| 필터/일부 조회/다운로드 미완료 | 전체 기간 증빙 금지, 재다운로드 안내 | 금융 parser의 기존 안전 계약 적용 |
| 카드사/마스킹 번호/행 식별 충돌 | 증빙 보류, 충돌 원인 표시 | 기존 원본/금융 충돌 보호 적용 |
| 파싱 오류 또는 저장 후 후속 처리 실패 | 증빙 완료 금지, 재확인 | 접수된 원본·작업 ID 보존, 기존 복구 경로 사용 |
| 동일 SHA-256 파일 재업로드 | 기존 파일/배치로 연결, 새 증빙/거래 중복 생성 금지 | 기존 멱등 업로드 동작 유지 |
| 기간 겹침, 내용은 다른 파일 | 겹침 경고만 표시. 공백을 줄이는 구간은 반영 | 기존 거래 동일성·중복 보호에 따라 처리 |

수동 확인은 명시적 조회기간을 알 수 없는 정상 파일에만 제공한다. parser가 제한 조회·부분 다운로드·카드 불일치를 발견한 파일을 사용자가 체크박스로 전체 조회로 승격할 수 없어야 한다.

## 4. 카드 식별과 조회 기준

### 4.1 카드 식별

- 강한 식별: 카드사 + 전체 마스킹 번호가 일치하는 실제 카드 ID를 우선한다.
- 약한 식별: 카드사 + 끝4자리만 있는 경우 다른 파일과 자동 병합하지 않는다. 현재 identity_scope='source_file' 보호를 유지한다.
- 끝4자리만 있는 파일을 기존 카드에 합치려면 기존 카드와 동일이라는 명시적 owner 확인을 제공하고, 그 연결을 감사 이력에 저장한다.
- 카드사만 같다는 이유로 여러 카드를 합치지 않는다.
- 복수 카드가 포함된 파일은 단일 카드 조회 증빙으로 자동 승격하지 않는다. 파일에 포함된 카드별 범위가 안전하게 분리되는 별도 검증이 구현되기 전에는 복수 카드 식별 필요로 표시한다.
- 카드번호는 마스킹 끝4자리만 UI에 노출한다. 원본 전체 카드번호는 UI·로그·보고서에 노출하지 않는다.

### 4.2 조회 기준

- 승인일·이용일·매입일을 별도 수집 범위로 관리한다.
- 기준이 다른 파일끼리 기간을 병합하거나 gap을 닫지 않는다.
- 카드사 파일의 거래 행 날짜, 파일명 날짜, 업로드 날짜로 조회 기준을 추정하지 않는다.
- 파일에 명시된 조회 기준이 없으면 수동 확인으로 받는다.
- 파일 조회기간과 실제 거래 발생기간은 별도 정보다.

### 5.2 요약 API

기존 GET /api/cards/coverage/summary를 확장한다. 화면이 별도 목록을 조합하지 않아도 다음을 반환한다.

- cards[]: 카드 식별·별칭·식별 신뢰 범위·조회 기준·관리 시작일·기준일·상태
- periods[]: 검증된 inclusive 기간과 해당 기간을 증빙한 batch/file 참조
- gaps[]: 정확한 시작/종료일, gap key, can_upload 여부
- files[]: 파일명·batch ID·received_at·거래행 수·고유 거래 수·조회기간·기준·증빙 상태·처리 상태·zero-row 여부
- rechecks[]: 원본 파싱·카드 식별·제한 조회·조회기간 메타데이터 충돌 등 구체적 사유
- summary: 관리 카드 수·확인된 조회축 수·gap 수·재확인 파일 수·처리 중 파일 수

파일 목록은 카드 ID/조회 기준별 페이지네이션을 지원한다. 전체 거래 원문이나 마스킹 전 카드번호를 반환하지 않는다.

### 5.3 저장 계약

- 기존 import_batches는 원본 파일과 batch의 정본이다.
- 기존 change_log의 card.query_coverage.v1은 검증된 조회기간 증빙으로 유지한다.
- 파일별 추출 메타데이터/검증 상태가 화면 복귀 후에도 필요하면 기존 change_log에 batch ID·source hash 기반 이벤트로 저장한다. 같은 batch/hash 재처리는 멱등이어야 한다.
- 카드별 관리 시작일은 카드 ID + 조회 기준의 별도 감사 이벤트로 관리한다. 현재처럼 각 파일의 management_start 최솟값만 취하는 로직으로 사용자가 변경한 기준일을 덮어쓰지 않는다.
- 끝4자리만 있는 파일을 사용자가 기존 카드에 연결한 경우 명시적 identity-link 이벤트를 저장한다. 사용자 확인 전에는 자동 병합하지 않는다.
- 우선 기존 change_log와 import_batches를 재사용한다. 새 DDL은 필요성이 입증될 때만 제안하고 migration·복구·보호 테스트를 별도 제출한다.
- 과거 거래 행만으로 과거 조회기간을 소급 생성하지 않는다. 기존 업로드 원본이 남아 있고 명시 메타데이터를 재검사한 경우에도 자동 소급 저장 여부는 별도 검증·감사 게이트를 통과해야 한다.

### 5.4 자동 증빙 시점

card_upload_jobs.process()에서 다음을 모두 만족할 때만 자동으로 CoverageStore.record()를 실행한다.

1. 원본 SHA-256 재검증 통과
2. parser 성공, 필수 원행 오류 없음
3. 단일 카드 식별 또는 별도로 검증된 명시적 카드 범위
4. 파일에 명시된 조회 시작일·종료일·조회 기준이 모두 유효
5. 조회 유형/필터가 전체 조회이며 다운로드 완료
6. batch 상태가 rejected가 아니고 error_count가 0
7. 원본 메타데이터와 실제 파싱 행의 카드 식별이 일치
8. source=metadata인 경우 클라이언트 입력으로 덮어쓸 수 없고 원본에서 다시 추출한 값과 일치

조건을 만족하지 못하면 금융 업로드/분류 경로와 별개로 조회 증빙만 미확정으로 남긴다. 거래가 0건이라는 사실은 위 조건을 만족할 때 실패 사유가 아니다.

## 6. 업로드·파일 목록의 정확한 의미

- **파일 수:** import_batches의 고유 batch 수. 동일 SHA 재업로드는 기존 batch 1개로 계산한다.
- **원천 행 수:** 해당 파일에서 파싱된 원천 거래 행 수.
- **고유 거래 수:** 기존 transactions 정본의 고유 거래 ID 수. 파일 행 수와 혼동하지 않는다.
- **조회기간:** 원본 파일에 명시된 실제 카드사 조회 조건 또는 사용자가 명시적으로 확인한 기간.
- **거래 발생기간:** 파싱된 거래의 실제 날짜 MIN/MAX. 조회기간의 대체값이 아니다.
- **조회 완료:** 전체 조회 조건과 원본·카드 식별 검증이 통과한 기간.
- **미수집 기간:** 설정된 관리 시작일~기준일 중 확인된 조회기간의 합집합에 포함되지 않는 날짜.
- **미관리 기간:** 관리 시작일이 설정되지 않아 누락 여부를 판정할 수 없는 범위.
- **중복 기간:** 조회 구간이 겹치는 상태. 동일 파일 중복과 다른 개념이다.
- **0건 조회:** 거래행이 없지만 전체 조회 결과와 카드/기간/기준이 확인된 파일.
- **금융 처리 상태:** 기존 upload summary의 분류/기록/환불 상태. 조회기간 상태와 별도로 표시한다.

| 조회유형=취소만, 조회필터=해외만, 다운로드 부분 상태 | 전체 조회 증빙 불가. 사용자 체크박스로 승격할 수 없음 |
| 같은 카드의 이용일 파일과 매입일 파일 | 서로 다른 조회 기준으로 분리, 기간 합산 금지 |
| 카드 끝4자리만 같은 다른 실물 카드 | 자동 병합하지 않음 |
| 끝4자리만 있는 파일을 기존 카드로 명시 연결 | owner 승인과 감사 이벤트 후 해당 카드 범위에 합산 |
| 파일 안에 복수 카드 식별 | 단일 카드로 자동 합치지 않고 복수 카드 식별 필요 표시 |
| 같은 파일 재업로드 | 기존 batch 재사용, 파일 수·거래·조회 증빙 중복 증가 0 |
| 다른 파일의 조회기간이 기존 기간과 겹침 | 겹침 표시, 유효 구간 합집합은 유지, 중복 거래는 기존 identity 보호 |
| 기존 batch에 거래는 없지만 coverage evidence가 존재 | 저장 파일 목록과 카드 카드에 정상 표시 |
| 파일이 업로드 중·분류 중·상태 조회 실패 | 접수/처리/조회 증빙을 서로 구분하고 재업로드를 요구하지 않음 |
| 요청 gap과 실제 파일 조회기간 불일치 | gap 유지, 불일치 이유와 실제 파일 기간 표시 |

### 금융·보안 회귀

- 기존 원본·금액·거래 ID·중복·수동 결정·환불·OTA M:N·원자성·감사 보호가 변경되지 않는다.
- 카드 조회기간 자동 증빙은 거래 분류·내부 기록·실제 환불 완료·Google 장부 반영을 생성하거나 확정하지 않는다.
- 기존 Google 최종 장부 자동 쓰기 금지 유지.
- owner 인증·CSRF·revision/source hash 검증 유지.
- 업로드 실패·로그인 만료·권한 거부가 저장된 batch나 다른 파일의 성공 결과를 지우지 않는다.
- parser는 관측된 카드사 파일 형식만 지원하고 임의의 셀/파일명으로 조회기간을 추정하지 않는다.

## 8. 구현 순서와 종료 조건

1. **DISCOVER:** 최신 main·열린 PR·현재 운영 SHA·실제 /import 렌더링·업로드 API·coverage records를 확인한다. 기존 #479/#510 조회기간 구현과 #627 비동기 업로드를 다시 만들지 않는다.
2. **DATA:** batch별 검사 결과, 카드 식별, 조회 기준, coverage records, 관리 시작일을 기존 저장 구조에서 안전하게 연결한다. zero-row batch가 파일 목록에서 빠지지 않도록 한다.
3. **AUTO EVIDENCE:** 원본에 명시된 전체 조회 조건을 성공 후 자동 증빙한다. 메타데이터가 없는 파일만 수동 확인으로 보낸다.
4. **API:** 카드·조회 기준별 요약, gap, 파일 목록, 재확인 상태와 기준일/identity-link 액션을 제공한다.
5. **UI:** 카드 자료 관리 대시보드·카드별 타임라인·gap 액션·파일 상세·업로드 wizard를 구현한다. 기존 중첩 접기·issuer 하드코딩·거래기간을 조회기간처럼 표시하는 UI를 제거한다.
6. **VERIFY:** 합성 DB/fixture/API/브라우저에서 모든 수락 테스트를 실행한다. 0건·부분조회·다중카드·끝4 식별·중복·겹침·기준일·stale revision·비동기 복구를 포함한다.
7. **REVIEW/DELIVER:** 실제 diff review, 영향 기반 QA, CI, PR 병합 및 기존 승인 배포 게이트를 따른다. 코드 병합·운영 배포·실제 카드 파일 업로드는 서로 다른 수락 상태로 보고한다.

**완료 정의**

- [ ] 카드사별 파일 수/파일명 목록이 아니라 카드별 조회 범위가 첫 화면의 중심이다.
- [ ] 각 카드·조회 기준별 정확한 gap과 gap별 업로드 동선이 있다.
- [ ] 업로드 응답에서 파일 조회 메타데이터를 즉시 확인할 수 있다.
- [ ] 검증된 명시적 전체 조회 메타데이터는 자동 증빙되고 수동 체크박스가 필요 없다.
- [ ] 메타데이터가 없는 경우만 안전한 수동 확인이 필요하다.
- [ ] 0건 조회가 파일 목록·조회기간 현황에 보존된다.
- [ ] 파일명·거래기간·조회기간·분류 상태·금융 상태를 서로 구분한다.
- [ ] 카드 식별·끝4·조회 기준·기간·중복·부분 조회의 보호가 검증된다.
- [ ] 기존 비동기 업로드와 금융/Google 보호 회귀가 통과한다.
- [ ] 실제 브라우저 화면과 운영 수락 근거가 확보되기 전에는 구현 완료로 표시하지 않는다.

## 9. 구현 에이전트 시작 지시

> COST 카드 업로드를 이 문서대로 구현하라. 먼저 최신 main, 열린 PR, 현재 /import 실제 라우트·UI·API·기존 coverage change_log와 운영 배포 경계를 조사하라. 기존 #479/#510 조회기간 엔진과 #627 비동기 업로드를 재작성하지 말고 재사용하라. batch_catalog()의 INNER JOIN 때문에 누락되는 0건 batch를 포함하고, 거래 MIN/MAX를 조회기간으로 표시하는 문제를 바로잡아라. loadCardReviewBatches()의 국민/하나/기업 하드코딩 그룹과 숨겨진 plain-text coverage summary를 카드별 조회기간 대시보드로 교체하라. 업로드 응답에 원본에서 추출한 coverage metadata를 포함하고, 유효한 전체 조회 메타데이터는 후속 처리 성공 후 자동 증빙하라. 메타데이터가 없을 때만 실제 기간/기준을 수동 확인하게 하며 거래일 MIN/MAX를 조회기간으로 추정하지 말라. 각 gap에는 해당 카드·조회 기준·정확한 날짜가 고정된 이 기간 자료 추가 동선을 제공하고 업로드 파일이 해당 구간을 실제로 덮는지 서버에서 검증하라. 끝4자리만 같은 카드를 자동 병합하지 말고 사용자 명시 연결만 허용하라. 카드별 기준일, 0건 조회, 겹치는 기간, 중복 파일, 제한/부분 조회, 복수 카드 파일, stale revision을 테스트하라. 파일명·조회기간·거래 발생기간·거래 분류·금융/환불/Google 상태를 혼동하지 말라. owner/CSRF/source hash/원본/금액/ID/중복/수동 결정/환불/OTA M:N/원자성 보호를 약화하지 말고 Google 최종 장부에 자동 쓰지 말라. 모바일/데스크톱/키보드 실제 브라우저와 영향 기반 QA·CI·PR·기존 안전 배포 게이트까지 진행하라. 계획이나 문서 작성만 하고 멈추지 말고, 미검증 항목과 실제 운영 수락을 구분해 보고하라.
