# COST 영수증 등록 단일 흐름·결과 중심 모바일 UX 전면 개선 (2026-11-05)

**상태: SPEC_ONLY · 구현/브라우저/운영 수락 미실시.** 사용자 제공 iPhone Safari 390px 다크 화면에서 PDF가 별도의 접이식 등록 경로로 제공되고, 두 개의 장부 복귀 버튼과 과도한 박스·기술적 단계 안내, 업로드 뒤 보이지 않는 결과 및 행동 부재가 관찰됐다. **최신 사용자 결정이 이 문서의 정본**이다. 기존 코드·원본·API·영수증/카드 중복·권한·Google 최종 장부 경계는 보존한다. 스크린샷 속 선택 파일명만으로 실제 서버 저장/업로드 완료를 증명하지 않는다.

## 1. 소스 조사에 근거한 결함

| 원인/위치 | 현재 동작 | 사용자에게 발생하는 결함 |
| --- | --- | --- |
| `webapp/receipt_review.py:render_html` | `#img-file` + `#img-go`, `#receipt-pdf` 안의 `#pdf-file` + `#pdf-go` 별도 표시 | JPG/PNG/PDF를 각기 다른 등록 방식으로 오해, 중복 입력·버튼 |
| `webapp/receipt_review.py` 파일 업로드 JS | `/api/receipts/image` 또는 `/api/receipts/pdf`에 저장 후 `location.reload()` | 즉시 결과 안내가 사라지고 화면 맥락·파일 선택이 초기화됨. 저장/분석/후보 등록 완료 구분 불가 |
| `render_html` + 공통 `site_shell` | 페이지 내부 `장부로 돌아가기`와 공통 이동 UI가 공존 | 모바일 뒤로 가기 중복·화면 세로 공간 낭비 |
| `#step-ai` 조건 렌더 + `VISION_SCRIPT` | AI 모델이 활성일 때만 '체크한 사진 분석'·후보 검토 CTA가 있음 | 업로드한 사람은 다음 행동이 어디 있는지 모름. 비활성 때 대체 행동이 숨겨진 '직접 입력 / 다른 방법'에 갇힘 |
| `WORKFLOW_SCRIPT.update` | 후보가 0건이면 `#step-review`, `#step-copy`를 숨김 | 초기/오류/분석 없음/업로드 성공 상태가 모두 빈 화면처럼 보일 수 있음 |
| `receipt_page_flow` 계열 테스트 | 업로드, 분석, 검토, TSV 복사 등을 개별 API/시나리오로 검증 | 결과 지속·다음 행동 가시성·모바일 실제 완료까지 연결하는 계약과 스크린샷 검증이 부족 |

**중요:** 서버에는 PDF 원본 보존→최대 10페이지 이미지 변환 `store_pdf()` 및 이미지 `store_image()`가 **이미 존재**한다. 현재 PDF 5MiB 제한, 이미지 5MiB 기준, iPhone HEIC 등 사진의 브라우저 JPEG 변환, owner/CSRF 검사를 재사용한다. 새로운 문서 포맷·모델/과금·원본 변조·Google 쓰기를 위해 별도 시스템을 만들지 않는다.

## 2. UX의 최종 구조

단일 `/receipts` 화면은 아래 의미 있는 구획만 기본 노출한다.

1. **페이지 헤더:** `영수증 처리`, 공통 햄버거/테마 메뉴. 장부·여행에서 넘어오면 기존 `trip` 맥락을 유지한다. 자체 '선택한 여행 장부로'와 '장부로' 중복 버튼을 만들지 않는다. 뒤로 가기 이동은 공통 사이트 셸의 한 동선으로만 제공.
2. **여행:** 선택된 여행을 작고 명확한 콤보박스로 표시. 여행 장부 `?trip=` 진입 시 유효한 여행 자동 선택. 미선택·삭제·권한 없음은 안전하게 안내하고 저장/분류를 막는다. 여행 바꾸기 전 진행 중 업로드·미저장 후보가 있으면 데이터 손실 방지.
3. **파일 등록:** 큰 단일 선택·드롭 영역 **`영수증 파일 선택`**(`JPG · PNG · PDF`; 지원 환경에서 HEIC/HEIF 사진 변환 포함), 파일 다중 선택/추가, 하나의 기본 **`등록 및 확인`** CTA. 별도 `PDF로 등록`·`PDF 페이지 등록`·`사진 등록`·문서별 접이식 메뉴를 사용자 화면에서 제거. 일반 업로드와 iOS 파일 선택/카메라 접근은 같은 사용자 단계. 파일 형식별 제약은 선택 후 파일 행의 안내로만 노출한다.
4. **처리 결과(항상 발견 가능):** 상단 등록 영역 바로 아래 고정 위치에 방금 선택·업로드한 파일별 카드. 상태 `선택됨 → 업로드 중 → 원본 저장됨 → 텍스트 추출/분석 가능 → 후보 검토 필요 → 영수증 등록 완료`; 실패/보호/중복/미지원은 독립 상태. 세션 변경/재로드에도 저장 서버 근거로 복구. 스크롤 밖에서만 나타나는 toast/사라지는 `#status` 한 줄로 성공을 대신하지 않는다.
5. **영수증 검토:** 원본 미리보기(이미지 또는 PDF 변환 페이지) 옆/아래 **상호·날짜·금액·통화·결제수단** 인식 후보(가능한 값 미리 채움)·빠진 값 안내. PDF는 원본 1건 아래 페이지 N개를 펼쳐 보여주며 페이지별 개별 영수증은 동일한 검토 컴포넌트로 처리한다. 여러 영수증이 한 이미지/페이지에 있으면 서로 다른 영수증 후보로 구분한다.
6. **다음 행동:** 상태에 따라 **하나의 주 CTA**: `결과 확인` / `영수증 분석` / `내용 직접 입력` / `수정 후 등록` / `다시 시도` / `카드 내역과 대조` / `장부용 내역 복사`. 유효하지 않은 동작을 빈 버튼으로 두지 않고 정확한 사유·회복 방법 표시. `추가 파일 등록`은 항상 쉽게 접근 가능.
7. **보조 기능:** 인식 재실행/영수증 여러 장 묶기/학습 메모/전문 OCR 설정은 **실제 결과가 있거나 기능이 필요한 상황에만** 보조 액션 또는 접힘 상세로 제공. 초기 화면에서 '1. 2. 3. 4.' 식의 영구 단계 박스를 반복 배치하지 않는다.

### 정보 시각화·디자인 제약

- 공통 COST 토큰/타이포/아이콘, 같은 줄의 제목·상태·주행동을 사용. **중첩 카드 3단 이상/과도한 테두리/빈 박스/설명문 중복 금지**. 상태를 큰 색상 박스로 남발하지 않고 1줄 텍스트+작은 배지+확장 가능한 상세로 표현.
- 모바일 320·375·390·430px에서는 1열, 레이블 위/옆 입력 값의 정렬·너비를 일관되게 하며 파일명은 말줄임/2줄 줄바꿈. 필요 버튼은 높이 최소 44px, 고정 툴바는 컨텐츠 가림·Safari safe-area 충돌 금지.
- PC 768·1024·1440px에서는 폼 최대 너비와 결과 두 열 배치가 가능하지만 완료 흐름·컨트롤 순서는 동일하다. 다크/라이트, 포커스, 스크린리더 `aria-live` 상태, 200% 확대, 키보드 전용을 반드시 검증.
- 디자인 리뷰는 사용자 스크린샷의 영수증 화면과 `카드 내역`/`OTA 내역` 공통 컴포넌트의 타이포·버튼·정보 밀도를 비교한다. **CSS 크기만 줄이거나 색상만 변경하는 작업은 불합격**.

## 3. 파일 형식과 실제 처리의 단일 계약

**사용자에게 보이는 단일 등록 경로**를 제공하되 기존 내부 `POST /api/receipts/image`, `POST /api/receipts/pdf` 서버 핸들러를 즉시 하나로 합칠 의무는 없다. 프런트엔드 단일 파일 큐가 검증된 MIME/파일 signature·확장자를 구분하여 적절한 기존 저장 API로 전송하고 **동일한 결과 DTO/검토 컴포넌트**로 수렴한다. 서버 검증은 클라이언트 accept만 신뢰하지 않는다.

- JPEG/PNG 이미지: 기존 원본 SHA/바이트·서버 검증·중복 방지 유지. 변환이 필요한 HEIC 등 모바일 사진은 지원되는 브라우저의 기존 normalize 로직을 재사용하고 변환 실패 시 원본은 임의 버리지 않고 재선택/변환 안내.
- PDF: **원본 파일 보존**, 최대 5MiB·10페이지 제한, 기존 `store_pdf`의 페이지 이미지/텍스트 생성 기능을 사용. PDF 원본 하나와 페이지 SHA를 묶은 관계를 결과 카드에 유지하며, 페이지 이미지의 SHA가 같아도 원본/페이지 설명을 혼동하지 않는다. 개별 페이지에서 후보를 검토할 수 있게 한다.
- 다중 파일: 이미지와 PDF를 **한 번에 혼합 선택**하고 파일별 진행/실패/재시도/중복 인식 상태를 유지한다. 한 파일 실패로 다른 파일이 완료된 사실을 덮지 않는다. 업로드 중 중복 클릭/화면 이동/인증 만료/서버 재시작 시 서버에 실제 저장된 해시로 복구하고 동일 원본을 중복 비용으로 생성하지 않는다.
- 저장 API 성공은 **원본 저장 완료**이지 **AI 분석 완료/비용 확정/Google 기장 완료**가 아니다. 인식 성공도 사용자의 비용 등록/카드 대사 성공이 아니다. UI 단계·API 응답·서버 저장 진실이 일치해야 한다.
- 로컬 OCR 가능할 때에는 저장 후 실제 가능한 다음 단계로 안내. **클라우드 AI 분석은 기존 사용자 명시 실행/외부 전송 동의, 인증·비용·개인정보 경계**를 유지하므로 업로드만으로 자동 외부 전송하지 않는다. AI 비활성/timeout/미설정 시 분석 버튼이 사라지는 것으로 끝내지 말고 저장 원본 미리보기와 `직접 입력` CTA를 동일 화면에 노출한다.
- 기존 후보 수정/확정은 `/api/receipts/scan`과 `/api/receipts/edit`의 검증·revision/원본 SHA를 재사용한다. 현금·개인카드/법인카드 구분, 카드 거래와 중복 비용 방지, JPY 간편 환산/KRW 금액 처리, Google 사용자 직접 복사를 유지한다. 이 작업에 고객 사진/금액을 Git/외부 모델로 임의 전송하지 않는다.

## 4. 업로드 결과 화면의 필수 시나리오

| 상황 | 화면에 반드시 보이는 결과 | 즉시 실행 가능한 행동 |
| --- | --- | --- |
| 파일만 선택 | 형식·파일명·개수·크기, 개별 제한/오류 | 등록 및 확인 / 선택 제거 |
| 저장 중 | 파일별 진행·재시도 방지, 다른 작업 차단 범위 표시 | 취소가 안전한 단계에서만 취소 |
| 이미지 1개 저장 성공, AI 비활성 | 원본 저장 완료 + 분석 미실시 + 미리보기 | `직접 입력`, 가능한 `글자 읽기`, 다른 파일 추가 |
| PDF 2페이지 저장 성공 | PDF 원본 1개, 페이지 2개/페이지별 원본 이미지 미리보기, 인식 여부 표시 | 각 페이지 분석/직접 입력·검토 |
| 이미지+PDF 혼합 중 한 파일 실패 | 성공 1·실패 1 및 실패 원인·성공 원본 목록 | 실패 파일만 재시도·정상 파일 검토 |
| OCR/AI 결과 0개 | '영수증 후보 0건 · 원본 저장됨' (빈 화면이 아님) | 직접 입력/다시 분석 |
| 인식 결과 2개 | 각 후보 상호·날짜·금액·통화/근거·불확실성 | 한 건씩 수정, 선택 등록/제외 |
| 후보 저장 성공 | 등록 완료 N건·원본 연결·비용 분류/Google 미반영 여부 | 영수증 상세·추가 파일·장부용 내역 복사 |
| 이미 동일 파일 존재 | 기존 원본/후보/기장 이력과 연결 | 기존 기록 열기, 실제 새 거래만 추가 |
| 미로그인/CSRF/timeout/서버 재시작 | 허위 성공 없이 저장 상태 재조회 안내, 입력 보존 | 다시 로그인/상태 재조회·필요 시 파일만 재전송 |
| Google TSV 복사 | 복사 완료 건수, 실제 Google 미반영 안내 | 사용자가 최종 시트에 붙여넣기 |

**핵심:** 사용자는 어떤 파일이 저장됐는지, 분석이 됐는지, 직접 입력이 필요한지, 회계 비용에 기록됐는지, Google 반영은 누가 해야 하는지를 하나의 화면에서 확인해야 한다.

## 5. 구현 범위 및 설계 충돌 방지

- 주요 구현: `webapp/receipt_review.py`의 `render_html`, `PAGE_CSS`, 이미지/PDF 업로드 JS, `WORKFLOW_SCRIPT`, `VISION_SCRIPT`, 후보 검토/TSV 영역. 공통 레이아웃의 단일 탐색은 `webapp/site_shell.py` 및 `webapp/ledger_design.py`와 함께 확인. 필요하면 영수증 원본/페이지 상태 조회 투영만 추가한다.
- API는 현재 `/api/receipts/image`, `/api/receipts/pdf`, `/api/receipts/scan`, `/api/receipts/vision`, `/api/receipts/edit`·TSV 경로 보호. PDF 10페이지 한도와 OCR/AI 실패 경계 유지. 검토 이력·후보의 금액·통화·등록 여부를 임의 변경하지 않는다.
- 최신 [UI 스킬 절차](ui-skill-workflow-20261105.md)의 디자인 분석/최소 구현/독립 UI 리뷰를 실제로 수행한다. 기능이 존재한다는 주장이나 Playwright 단순 `visible` 검사는 완료 증거가 아니다.
- `webapp/tests/test_receipt_mobile_photo.py`, `test_receipt_pdf.py`, `test_receipt_page_flow.py`, `test_receipt_review.py`, `test_receipt_design_contract.py`와 공통 셸 탐색 관련 검사에 **새 단일 흐름**을 반영한다. 오래된 `#img-go`, `#pdf-go` 등 DOM 단언은 신규 UX 계약에 맞춰 적절한 테스트로 교체하되 안전 검사 제거/skip은 금지.
- 테스트 데이터·스크린샷은 합성 자료만. 실고객 원본/PDF/영수증 이미지/이름/금액/비밀값은 PR·CI/공개 아티팩트에 첨부하지 않는다. 운영 실자료 확인은 owner 브라우저에서 안전한 읽기·유효 배포 SHA·명시된 업무 쓰기 승인 범위 안에서 수행한다.

## 7. 후속 구현 에이전트 실행 지시

> COST 최신 main/운영 SHA/AGENTS.md 및 이 문서와 기존 영수증 기능 코드를 읽어 iPhone Safari 첨부 화면의 문제를 실제로 재현하라. `/receipts`에서 JPG/PNG/PDF/지원되는 HEIC을 **한 파일 선택·등록 경로**로 통합하고, 등록 직후 새로고침으로 사라지는 상태 대신 파일별 영구적 결과·분석 가능 여부·원본 미리보기와 직접 입력/분석/수정·등록/장부용 복사의 맥락별 CTA를 구현하라. PDF 원본/페이지·업로드 멱등/중복·원본/권한/CSRF/외부 AI 승인·Google 쓰기 금지를 보호한다. 공통 셸과 자체 뒤로 가기 중복 및 과도한 박스·입력/접이식 메뉴·모바일 밀도 문제를 해결한다. 관련 영향·브라우저 검사를 업데이트하고 RCPT-UX-01~16 전수 수락, 독립 UI 리뷰 및 기존 정책의 공식 배포 게이트까지 검증하라. 문서만 변경하거나 버튼 존재·단일 이미지 성공만으로 완료 처리하지 말라.
