# 웹 장부 단계별 진행과 재개

## 최신 재개 안내 — 2026-09-27

Phase 6 규칙 대화와 선택한 A/Ramp/Pretendard 화면의 통합 후보를 본 저장소에 반영했다.
실제 AI 연결과 운영 전환은 미완료다. [최신 인계](handoff/2026-09-27/README.md)를 먼저 읽고
아래 이전 단계 보고는 과거 기록으로 보존한다.

## 통합 후보 검증 갱신 — 2026-09-26

최종 격리 후보 integration-candidate-final-20260926-01의 전체 검사 152개와 세부 검사 9개가 통과했다. 은행 동일 내용 재업로드의 추가 행 없음과 최종 후보의 Chromium 폭 390 사용자 경로를 확인했다. 실물 휴대폰 검사는 아니다.

Excel 전체 PDF 3쪽에서 수입 200000원, 지출 30000원, 수익 170000원을 코디네이터가 직접 시각 확인했다. 최초 누락은 검증 명령의 첫 페이지 제한 때문이었다. 물리 프린터는 미검증이다. 빈 공간과 합계의 페이지 분리는 사용성 개선 여지로 남으며 원본 양식과 시각적 완전 일치를 주장하지 않는다.

본 저장소 제품 코드 반영과 운영 전환은 아직 하지 않았다. 파일별 통합 계획을 준비 중이다. 아래 은행 대기 및 모바일 미검증은 과거 기록이다. Phase 6 이후를 포함한 전체 프로젝트 완료는 아니다.

## 최신 재개 기준 — 2026-09-26

아래의 과거 상태·모델 표기는 당시 기록으로 보존한다. 현재는 Phase 1~5 보완 검증 중이며 전체 완료나 사용자 최종 확인만 남은 상태가 아니다. 배분 개별 수정·복원과 삭제 요청 결속, 출력 게시 보완을 수용했고 고정 비은행 후보는 124개 통과·은행 5개 제외 상태다. 같은 내용의 중복 테스트 한 개 제거 후 해당 2개도 확인했다.

은행 최종본은 별도 작업 중이다. 도착하면 새 통합 후보에서 제외 없는 전체 검사를 수행한다. 데스크톱 클릭·합성 HTTP 다운로드 증거는 있고, 실제 모바일 390 및 Excel 인쇄는 미검증이다. 본 저장소 코드 통합·운영 DB 변경·배포는 하지 않았다. 상세 경로와 실제 검사 결과는 WEB_LEDGER_IMPLEMENTATION_LOG.md의 최신 상태 정정 및 WEB_LEDGER_IMPLEMENTATION_REVIEW.md를 따른다. 은행 결과를 기다리는 동안 이미 통과한 전체 검사를 반복하지 않는다.

갱신: 2026-09-24. 사용자 지시로 Phase 1~5 구현에 착수한다. 이번 지시에 한해 명세 작업만 제한을 해제하며, 미정 업무 정책을 승인한 것으로 해석하지 않는다. Phase 5 결과 제시 후 멈춘다.

## 현재 위치

- Phase 0: 명세 구체화 완료 선언 없이 구현 착수 지시가 내려옴. 단계별 검증과 기록을 마치면 사용자 응답을 기다리지 않고 다음 단계로 진행한다. Phase 5 결과 제시 후 멈춘다.
- Phase 1 이후: 아래 진행 기록에 따라 순차 구현한다. 구현자 호출·앱 실행은 격리 작업공간에서 수행하며 운영 연결은 하지 않는다.
- 실제 모델 호출: 구현자는 `opencode/muse-spark-1.3-contributor-free`이며 이 세션이 해당 모델로 실행 중이다. 무료 여부 직접 조회는 불가하므로 모델 ID 표기와 세션 실행 사실로 갈음하고, 실패 시 임의 대체하지 않는다.
- 기존 작업공간에는 다른 작업의 미커밋 변경이 있다. 격리 공간 생성 시 현재 코드와 문서 기준을 함께 보존해야 하며 HEAD만 사용해 미커밋 문서를 누락하지 않는다.

## 모든 단계의 공통 진행 방식

`해당 단계 전달 → 단일 구현자 작업 → 코디네이터 검증 → 사용자에게 실행 화면·결과 제시 → 확인 내용 반영 → 다음 단계`

사용자는 코드를 읽거나 테스트를 직접 실행할 필요가 없다. 확인할 대상은 작동하는 화면과 업무 결과다. 코디네이터가 발견한 버그는 같은 단계에서 수정하며 사용자에게 기술 검증을 떠넘기지 않는다. 다음 단계 전에는 사용자가 중간 결과를 확인할 기회를 둔다. 응답이 없다는 이유로 확인 완료라고 기록하지 않는다.

단계마다 격리 작업 경로·기준 커밋과 미커밋 패치·문서 버전·실제 모델·실행 명령·검증 결과·남은 문제를 아래 진행 기록에 남긴다. 다음 세션은 이 파일과 현재 단계에 해당하는 계약만 읽고 재개한다. 새 세션이라는 이유로 모든 단계의 조사와 테스트를 반복하지 않는다.

## 최신 검토 상태 — 2026-09-25

격리 공간의 수정 A~D에 대해 83개 기존 검사는 재실행 통과했다. 추가 경계 검토에서 잔여 결함을 확인했으므로 Phase 5 수용·본 저장소 통합은 아직 완료되지 않았다. 재개 순서는 [구현 검토 8절](WEB_LEDGER_IMPLEMENTATION_REVIEW.md)을 따른다. 아래 단계 구성과 과거 진행 기록은 보존하며, Phase 1부터 재작성하거나 Phase 6 이후로 자동 진행하지 않는다. 기능 명세 작성은 완료됐고 실제 구현 수용과 구분한다.

## Phase 0 — 설계와 인계

작성한 초안은 제품 명세, 결정 등록부, 구현 계약, 요청·상태·오류 상세 계약, 이 진행표, 전달문이다. 합성 C1~I3 자료와 수입·지출 합계 기대값을 명시했다. 사용자는 이 세션에서 명세를 계속 구체화하고 구현은 추후 수동으로 시작하겠다고 정정했다. 따라서 현재 Phase 0은 진행 중이다. 문서 점검은 코드 검증이나 모델 성능 검증이 아니다.

남은 선택은 필요한 단계 직전에 묻는다. Phase 1을 시작하기 위해 실제 은행 파일, API 키, 호스팅 비용, 로그인 수단을 먼저 결정할 필요는 없다. 초기 단계는 합성 자료와 비공개 로컬 환경을 사용한다.

## Phase 1 — 먼저 볼 수 있는 장부 화면

대응: W01의 합성 조회 계약과 W02. 구현자는 기존 webapp의 실행 방식을 확인하고 하나의 화면을 만든다. 프레임워크를 전면 교체하거나 외부 서비스를 새로 가입하지 않는다. 구조상 변경이 필요하면 이유·영향을 코디네이터에게 보고한다.

1. 합성 여행 A·B와 분류대기를 왼쪽에 배치한다.
2. 합성 C1~I3로 수입·지출·고객 합계를 표시한다. 탭 검색·선택·스크롤이 작동해야 한다. 좁은 화면의 여행 선택과 표 스크롤도 함께 구현한다.
3. 후보 표시 없이 일반 행을 보여 주고, 행 상세에서는 원천·분류 근거를 볼 수 있게 한다.
4. 편집 폼은 입력 가능 필드와 고정 필드를 보여 주는 수준까지 만든다. 저장 미구현 버튼은 비활성 또는 준비 중으로 명시하고 성공 알림을 위장하지 않는다.
5. 원천 읽기·대사·AI·실제 예약 연결은 없다. 합성 자료임을 화면에 표시한다.

완료 증거: 실행 방법과 로컬 주소, 브라우저에서 확인한 화면, 합성 합계, 빈 탭·조회 오류 상태. 사용자는 배치·글자 크기·표 밀도·행 상세 위치를 확인한다. 여기서 받은 수정은 Phase 2 전에 반영한다.

모바일은 마지막에 추가하는 별도 단계가 아니다. Phase 1부터 레이아웃을 확인하고 이후 저장·업로드·대화·출력 기능을 연결할 때 같은 단계에서 모바일 동작도 확인한다. 실제 모바일 기기 미검증은 별도 기록한다.

## Phase 2 — 행 저장과 변경 이력

대응: W01의 저장 어댑터와 W03. 합성 자료 전용 작업 DB에서만 쓰기를 수행한다.

1. 기존 사건 저장소를 조사해 단일 쓰기 경로와 필요한 마이그레이션을 정한다.
2. 행 단위 저장·취소, 예외·규칙 변경 선택, 목적지 이동, 메모 편집을 연결한다.
3. 원천 날짜·금액은 API에서도 거부한다. 규칙 변경 선택은 사례와 대화 대기 상태만 저장하고 모델을 아직 호출하지 않는다.
4. revision 충돌, 응답 유실 후 동일 요청 재시도, 중복 클릭, 수동 고정 필드를 검증한다.
5. 프로세스를 재시작해도 저장과 변경 이력이 유지되는지 확인한다.

사용자 확인: C1을 A에서 B로 보내고 메모를 저장한 뒤 이력에서 변경 전후를 본다. 합계는 상세 계약의 기대값과 같아야 한다. 미정인 임의 과거 revision 되돌리기 기능은 이 단계에 추가하지 않는다.

## Phase 3 — 카드 파일과 대사 진행

대응: W04. 실제 파서는 기존 정규화를 재사용하고 처음에는 합성 프로필 자료로 검증한다.

1. 파일 접수·봉인·열 매핑·파싱·진행 조회를 구현한다.
2. 기존 분류가 선택한 후보는 여행 탭으로, 실패만 분류대기로 보낸다.
3. 처리 완료 묶음부터 화면에 표시하고 원본 행 수와 사건 수를 구분한다.
4. 동일 파일, 기간 겹친 파일, 취소·환불, 식별자 충돌, 중단 후 재개를 검증한다.
5. 실제 카드 형식의 로컬 검증이 필요한 경우 원본을 구현 모델에 전달하지 않고 구조와 합성 예시만 전달한다.

사용자 확인: 업로드 후 결과가 하나씩 보이는지, 분류대기 드롭다운으로 옮기기 편한지 확인한다. 지원하지 않는 형식은 지원 완료로 보고하지 않는다.

## Phase 4 — 수입·수기 지출·은행 내역

대응: W05와 상세 계약 11.1절·15절. 이 단계 시작 전에 은행명과 CSV·XLSX 형식을 확인한다. 계좌 키·비밀번호는 대화로 받지 않는다.

1. 입금 한 건 입력, 고객 연결, 예약금·잔금·추가금과 합계를 구현한다.
2. 은행 원천 보존·중복 가져오기·직접 입력과 원천 연결을 구현한다.
3. 직접 입력의 날짜·금액 편집과 은행 원천의 별도 정정 기록을 구현한다.
4. 미식별 수입의 분류대기 구역과 동명이인 처리를 검증한다.
5. 현금·계좌이체 수기 지출 추가와 날짜·금액 편집·변경 이력을 구현한다. 같은 API로 카드 금액을 바꿀 수 없는지 검사한다.

사용자 확인: 500000원 직접 수입을 450000원으로 고치는 흐름과 은행 수입을 정정하는 흐름을 각각 확인한다. 현재 표와 합계가 바뀌고 원천·이력은 남아야 한다.

## Phase 5 — 선택 탭 파일 출력

대응: W08. 기존 양식 복제와 현재 저장 버전의 출력만 연결한다.

1. 여러 여행 선택·순서·미저장 편집 안내·미확정 안내를 구현한다.
2. 한 파일 여러 시트로 출력하고, 파일에는 미확정 상태 표기를 추가하지 않는다.
3. 슬롯 초과, 긴 예약번호, 시트명 충돌, 원천 문자의 수식 오인식을 검사한다.
4. 출력 실패 시 기존 파일 유지와 재시도 동작을 확인한다.

사용자 확인: 실제 생성된 합성 xlsx를 열어 화면 값·수입 위/지출 아래·양식·인쇄 범위를 확인한다. 출력이 성공해도 회계 확정이나 외부 전기를 수행하지 않는다.

## Phase 6 — 규칙 대화와 모델 전환

대응: W06·W07. 모델을 먼저 연결하기보다 규칙 초안·미리보기·적용의 결정론적 계약부터 완성한다.

1. 허용 필드의 규칙 초안과 네 가지 적용 범위를 합성 응답으로 검증한다.
2. 수동 고정, 충돌, 낡은 미리보기, 기존 사건 재업로드를 검증한다.
3. 실제 가용성과 무료 여부가 확인된 Muse 호출을 연결한다. 확인 실패 시 결과를 기록하고 다른 구현 모델로 대체하지 않는다.
4. owner 키 설정과 서버 Gemini fallback을 연결한다. 키 등록은 비밀 입력 화면에서 수행한다.
5. PC 종료·한도 소진·늦은 응답·Muse 복귀를 검사한다. 실제 키가 없으면 합성 전환 검증과 실제 호출 미검증을 구분한다.

사용자 확인: 행 수정 후 필요한 질문만 받는지, 영향 행을 보고 기존·미래 범위를 따로 고를 수 있는지 확인한다.

## Phase 7 — 로그인과 예약 담당 배정

대응: W09. 시작 전에 인증 수단과 예약 계정 연결 방식을 확정한다. 직원의 고객명·닉네임·예약번호·해당 여행 증빙 조회와 내부 메모·수정 이력·AI 대화 숨김은 이미 확정됐으므로 재질문하지 않는다.

1. owner·viewer를 서버에서 구분한다. 개발용 역할 전환 UI를 운영에 남기지 않는다.
2. 예약 시스템의 명시 배정과 안정 ID를 연결하고 누락·해제·과거 revision을 구분한다.
3. 종료 여행 조회는 담당 권한이 유지되면 허용한다. 직원은 출력 생성·작업 조회·다운로드를 할 수 없다.
4. 목록·검색·행·합계·첨부·이력의 다른 여행 접근을 검사한다.

사용자 확인: owner와 합성 담당자 계정으로 같은 화면을 비교한다. 실제 예약 연결과 합성 연결을 구분해 보고한다. 이 단계 전의 로컬 화면을 외부 공개하지 않는다.

## Phase 8 — 기존 자료 시험 이관

대응: W10의 이관, 상세 계약 11.2절. 실제 구글 기준본과 DB 스냅샷 위치·범위를 먼저 확인한다.

1. 두 원천을 읽기 전용으로 봉인하고 동일값·차이·한쪽에만 있음·대응 불명확을 구분한다.
2. 사용자가 차이 목록에서 필드별로 선택한다. 원천 금액 불일치를 표시값 선택으로 숨기지 않는다.
3. 별도 이관 DB에 적용하고 반복 적용·메모·증빙·원천 계보 보존을 검증한다.
4. 미해결 건과 선택 결과를 기록한다. 운영 구글 장부나 DB를 덮어쓰지 않는다.

사용자 확인: 전체 행을 다시 검토하는 대신 차이와 미해결 항목을 본다. 완료는 합계뿐 아니라 업무 필드와 계보 보존으로 판단한다.

## Phase 9 — 운영 환경과 전환 준비

대응: W10의 복구·성능·운영 준비. 호스팅·비용·로그인 방식과 실제 연결 준비가 필요하다.

1. 상시 앱·DB·파일 저장·서버 Gemini·로컬 Muse 연결을 구성한다.
2. 백업에서 시험 복구하고 수동 수정·규칙·원천·출력을 확인한다.
3. PC를 끈 상태에서 조회·행 저장·업로드·Gemini 대화를 검사한다.
4. 실제 규모에서 행 저장·탭 전환·모델 호출 수·전체 대사 횟수를 측정한다.
5. 운영 전환안, 미해결 사항, 복구 방법을 제시한다. 실제 배포·비용 발생·운영 기준 전환은 구체적인 대상과 결과를 보여 준 뒤 사용자 결정에 따라 수행한다.
