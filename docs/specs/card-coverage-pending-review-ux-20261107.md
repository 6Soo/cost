## 사용자 문제
모바일 390px 실운영 화면에 **관리 카드 0 / 조회 기준 0 / 미수집 구간 0 / 조회 확인 필요 파일 23**이 노출된다. 기존 원본 거래는 분류 `classified`이고 각 파일에 거래 발생기간이 기록되어 있지만, 실제 카드사 **전체 조회기간 증빙**은 아직 없다. **0은 누락 구간 없음의 증거가 아니라 계산할 근거 없음**이다. 이전 UI는 23개 파일을 하나하나 펼쳐 보이면서 `업로드 처리 결과 보기`로 이동시켜도 조회기간 확인 폼에 연결되지 않았다.

## 최신 코드 변경 범위 (#717 계획)
1. 서버 `webapp/card_upload_coverage.py::get_coverage_summary`: 기존 읽기 전용 SQL **한 번**에서 거래 행 기준 발급사·카드 끝4자리의 단일 조합인 파일에 한해 `issuer_hint`/`card_tail_hint` 표시 힌트 제공. 다중 카드/거래 0건/식별 불가면 unknown, 다른 파일과 실제 카드 권위를 합치지 않는다. `coverage_state`/ `overview.gaps_assessable`로 확인 근거 부족을 명시하며 0 gap 숫자의 의미를 정확히 구분한다. 거래 발생일부터 조회기간 자동 확정 **절대 금지**.
2. `webapp/static/js/card_history_workspace.js`: 미확인 파일은 카드사·끝4자리 **표시용 그룹** + 카드 미확인 그룹으로 접어 표시한다(동일한 물리 카드/원본 합병 근거 아님). `조회기간 확인` 1차 CTA와 `처리 결과` 2차 CTA 제공. 파일 단위 `/cards/all?panel=upload&batch=...&review=coverage`에서 기존 owner 조회 API `GET /api/imports/{batch}/coverage`로 **그 파일 원본 한 개만 검토**하고, 실제 확인 가능한 카드·기간·날짜 기준·전체 조회 여부를 사용자에게 확인받는 기존 `POST /api/imports/{batch}/coverage/confirm`으로만 저장한다. 명시 근거가 없다면 새로 다운로드하도록 안내하고 조용히 확정하지 않는다.
3. `webapp/cards_all.py`: 좁은 모바일에서 23개 전체 행을 펼쳐야 했던 시각적 과밀을 줄이고, 파일별 44px CTA·그룹·공통 색상 토큰·키보드 표식 유지.
4. 합성 QA: `webapp/tests/test_card_upload_coverage_api.py` 및 `test_card_upload_coverage_ui.py`에 기존 분류 파일 + 조회 증빙 0/미확인 집계, 원본 파싱→폼 이동, API owner/CSRF 보호, 0행/알 수 없는 카드, GET 읽기 불변을 확인. 영향 QA의 기존 `test_card_upload_coverage_*`와 모바일·업로드/환불 보호 인접 검사 통과 요구.
