# COST 경량화: 카드·OTA 단일 업무 경로 설계 V1

작성 2026-10-30 · 상태: 설계/정적 코드 감사. 코드 리팩토링·테스트·운영 배포는 아직 아님.

## 제품 목적과 제외 범위

COST는 카드 원본 및 OTA 예약 근거를 모아 여행별 지출을 정확히 분류하고, 사용자가 검토해 Google 장부에 복사하도록 돕는 작은 내부 업무 도구다. Google은 최종 회계 정본이며 자동 쓰지 않는다. 예약 관계, 결제 검증, 여행 배정, 장부 기록, 환급은 실제 근거가 다른 독립 사실이다. **상태를 합쳐 허위 완료를 만들지 않는다.**

경량화는 기존 원본/사용자 결정/감사/환불/중복/금융 연결/권한/동시성 보호를 제거하는 작업이 아니다. 실제 운영 DB와 과거 거래를 일괄 재분류하거나 OTA 원천을 삭제하지 않는다. 인증·메일·포털 수집 경로의 특수 요구도 변경하지 않는다.

## 정적 코드 감사: 우선 단순화 대상

- `webapp/card_flow.py` 약 3,257줄: 카드 업무 orchestration, OTA 조회/화면, 검토/정리, 여러 캐시와 권한 분기 혼재.
- `app/ota_payments.py` 약 1,942줄: 원천 이벤트 정규화·중복 결제 합치기·후보 탐색·전역 배정·이유/상태 생성이 한 파일에 집중.
- `app/classify.py` 약 581줄과 `app/automatic_classification.py` 약 437줄: 분류, 자동 추론, 카드별 잔여 비용 처리 및 완료 판정이 분산.
- `webapp/card_ota_projection.py`: UI 후보용으로 OTA 원천과 거절 이유를 다시 조합. 화면은 코어의 결정 결과를 읽는 것이 원칙.
- `app/quarter_tab.py`는 `quarter:YYYY:Q`를 정상적인 비용 장부 목적지로 정의하지만, `webapp/card_transactions.py` 미배정 필터와 `app/automatic_classification.py:completion_for_row`는 실여행 ID만 유효한 배정으로 취급할 수 있음. 화면/업로드/완료율의 정의 불일치가 핵심 버그 유형.

## 목표 구조: 단일 판정, 얇은 UI

1. **원천 계층**: 카드 원본·OTA 예약/결제 증거를 변경 불가능한 ID와 출처로 저장. 파서는 원천별로 유지하며 금융 결정을 내리지 않는다.
2. **대사 계층**: 동일한 입력 snapshot에서 OTA 결제 ↔ 카드 거래를 1회 판정한다. `matched`, `candidate`, `unmatched`, `conflict`와 근거·차단 이유·원천 revision을 반환한다. 기존 exact/manual/global occupancy/refund 보호를 그대로 호출한다. UI는 별도 대사 규칙을 만들지 않는다.
3. **귀속 계층**: 대사 근거와 여행 일정·수동 교정 우선순위로 단일 유효 목적지 `trip:<실제 여행 ID>` 또는 `quarter:YYYY:Q`를 산출한다. 실제 저장 필드 `trip_id`·`display_tab_id`는 호환성을 위해 유지하되 의미 판정은 공유 함수에서만 한다. 취소/환불 탭은 별도 금융 상태로 취급한다.
4. **표시 계층**: 카드 전체 내역, 미배정 목록, OTA 후보 화면, 업로드 완료율은 동일한 read-only 판정 snapshot/공유 helper를 사용한다. UI에서 새 결제 매칭·분기 판정을 하지 않는다.
5. **장부 계층**: 내부 기록/Google 수기 중복 대조/TSV 복사는 기존 승인 경로를 재사용한다. 분류 완료를 Google 반영이나 실제 환급으로 해석하지 않는다.

### 반드시 하나로 정의할 배정 상태

- `trip:<유효 여행>` → ASSIGNED.
- `quarter:YYYY:Q` → ASSIGNED. 분기 기타비용은 여행과 **동등한 배정 완료**로 계산하되 실제 여행 ID라고 위장하지 않는다.
- 실제 여행도 분기 탭도 아닌 빈 값/무효 ID → UNASSIGNED. 원천 오류·중복·환불 보류는 별도 이유로 유지.
- 기존 수동 교정은 자동 추론보다 우선. OTA 예약 연결이 있어도 실제 여행 배정/금융 결제 확정과 혼동하지 않는다.
- 거래의 날짜·분기 일치성은 별도 데이터 정합성 검사. 6월 30일이 3분기로 표시된 기존 사례는 실제 날짜/원천을 확인하고 별도 교정하며, UI 표기만으로 데이터를 고치지 않는다.

## 과설계 제거 우선순위

**R1. 정의 중복 제거**: 배정 판정/분기 탭 유효성/분류 출처 라벨을 공통 read-only helper로 수렴. 카드 전체 내역, 미배정 필터, 업로드 검증, 장부 화면에서 동일 fixture로 검증. 첫 단계는 기존 데이터 무변경.

**R2. OTA 카드 대사 결과 단일화**: 코어 대사 함수가 후보·거절 이유·최종 링크를 계산하고 화면은 해당 결과를 투영. 기존 `card_ota_projection`에서 재판정 로직을 없애되 설명·금액 표시는 유지. 한 결제의 결과가 카드 화면/OTA 화면에서 일치하는지 회귀.

**R3. 분류 우선순위 단순화**: 수동 결정 → 검증된 예약/결제 근거 → 검증된 여행 후보 → 카드별 잔여 비용 규칙 순서로 기존 정책과 충돌을 점검. `owner_card_residual` 같은 기본 규칙이 OTA 근거를 영구 차단하지 않도록 한다. 예약 연결 실패를 기타비용 완료로 오인하지 않는다.

**R4. 카드 화면 컨트롤러 축소**: `card_flow.py`는 인증된 요청 라우팅·읽기/쓰기 orchestration만 남기고 기존 코어 함수를 호출한다. 단순한 함수 추출로 파일만 늘리지 않는다. 캐시/중복 조회는 실제 프로파일과 회귀 근거로 제거.

**R5. 죽은 코드/중복 명세 정리**: 호출 관계, 운영 feature flag, 배포 설정, 기존 테스트 사용 여부를 확인한 뒤에만 삭제. 과거 명세는 history로 이동하고 README/AGENTS/시작 안내/현황 문서만 진입점으로 유지. API/DB/외부 스크립트의 호환성을 먼저 확인한다.

## 실행 순서와 수락 게이트

1. 현재 main·운영 SHA 및 PR 충돌 확인. 함수 호출 그래프, 테스트/실행 경로, 데이터 흐름, 중복 계산 지점, 성능 비용 측정. 삭제 후보는 사용 증거가 없을 때만 제안.
2. R1을 첫 **소규모 코드 PR**로 구현. 같은 카드의 분기 탭이 미배정 필터·카드 상세·업로드 완료율에서 동일한 배정 상태인지 확인.
3. R2와 R3를 각각 별도 PR로 구현하고 OTA 동일일·동액, 중복 예약, Gotogate, 수동 링크, 취소/부분환불, 원본 누락, 공급자별 결제일 차이를 회귀.
4. R4/R5는 실제 중복 코드 감소량·응답시간·캐시 크기·불필요한 DB 조회 횟수를 측정한 뒤 진행. 새 추상화/상태/테이블을 무조건 추가하지 않는다.
5. 각 PR마다 관련 표적 테스트 + 직접 영향 금융 보호 통합 테스트를 1회 수행. 사용자 원본/Google/운영 DB 쓰기는 별도 승인 범위를 준수한다.
6. 완료 보고는 기능 변화, 삭제/통합된 코드, 테스트, 병합, 운영 배포, 운영 수락을 각각 구분한다.

### 경량화 성공 기준

- 동일 거래가 카드·OTA·업로드·장부 화면에서 서로 다른 배정/매칭 결과를 보이지 않음.
- 동일 입력과 원천 revision의 재조회가 재대사 없이 같은 결과를 사용함(실시간 최신성·권한 보존).
- 카드/OTA의 핵심 업무 규칙은 각각 하나의 소유자만 가지며 UI는 읽기/표시만 담당.
- 주요 사용자 경로는 카드 가져오기 → OTA 근거 대조 → 여행 또는 분기 비용 귀속 → 검토 → Google 복사. 불필요한 추가 승인·임시 상태·중복 화면을 만들지 않음.
- 코드량·의존성·DB 조회 수·응답시간 중 실제 측정된 지표로 개선을 보고하며 테스트·금융 안전성 회귀 0.
