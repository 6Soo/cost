## B. ‘수정했다’고 말했으나 기능 목표는 미달인 항목

1. **Agoda 20,532 JPY 결제일 미확인 (#165):** ‘예약 연결 불가’ 문구를 수동 예약 확인 안내로 수정했으나 사용자 목표는 **수동이 아닌 자동 결제/예약 대사**. `app/ota_inference.py::unique_pairs`의 기존 자동 추론 게이트를 실제 운영 원행에 대조해 실패 원인을 알아낸 뒤 수정해야 한다. 화면 후보 1건만으로 금융 확정 금지. #165의 문구 수정은 결함 해결이 아니다.
2. **카카오 환불 11건 (#153/#157/#169/#172/#174):** #157의 원승인번호 1:N 및 #169 공백 정규화는 실제 운영에 배포됐으나 원승인번호가 없는 11건은 **미연결**. #172는 진단/문구 변경이고 #174는 새 원화 추론 코드를 작성했지만 미검증·미병합. ‘모두 연결됐다’고 기록하지 말 것. 앞선 읽기 전용 실측에서 동일 카드·가맹점 14일 조회 10건은 동액 후보 없음, 1건만 동액 후보 1개였음. 새 규칙이 실제로 몇 건을 연결할지는 아직 확인되지 않았다.
3. **Agoda +625,280/-625,280원 (#176):** 기존 원승인 근거로 연결·상쇄는 성립한 것으로 파악됐으며 주 문제는 원결제 카드에 OTA 갱신/미매칭처럼 **상태가 섞여 표시**되는 UX. 원결제 화면 수정은 상태 표시 보정이지 새 자동 연결은 아니다. 과거 여행 배정 ID 무효 문제는 별도.
4. **‘배정된 여행이 현재 유효하지 않습니다’ (#176):** 여행 원본 권위·기간/활성 여부가 현재 저장 `trip_id`와 충돌했을 가능성이 있지만 실제 DB 원인은 확정되지 않음. 오류 안내만 상세화. 사용자가 직접 다른 여행을 고르는 해결책으로 끝내지 말 것. 이전 직접 배정을 임의 덮어쓰지 말 것.
5. **‘추론 배정 · 높음’인데 미배정 (#179):** 문구만 바꾸던 선행 커밋은 미해결. 후속 구현은 **유효한 카드 원본 `trip_id`가 이미 있는 기존 장부**만 처리. 카드 원본도 미배정인 거래와 실제 사용자가 제시한 트립닷컴 +230,106원 건은 미검증. 증거가 있는 후보가 유일하면 기존 분류 경로에서 배정까지 이어지고 같은 화면에서 설명해야 한다.
6. **OTA 확인을 다른 화면에서 하라는 안내 (#166/#179):** ‘아래 OTA 검토’ 문구를 같은 화면 설명으로 **치환**했을 뿐, CTA·원본 근거·상태·교정·승인 기능을 거래 카드 안에 통합한 것이 아님. 내비게이션 문구 개선과 실제 UX 흐름 통합은 다르다.
7. **파라타항공 -838,600원 취소 (#180):** DB 원행 직접 추적 요청에 진단 스크립트 작성만 수행. 운영 원행 조회/원결제 식별/매칭 알고리즘 실제 수정이 필요.
8. **비용 항목 선택의 복사 버튼 (#177):** 원인 후보인 지출 검토 렌더러의 자동 버튼 삽입을 제거했으나 스크린샷상 비용 항목 팝업의 생성 경로와 실제 동일 여부가 검증되지 않았다. 제거 PR이 있어도 화면 수락 전 완료로 보고 금지.
9. **항공권 상세 UI (#170):** 별도 운영 기록상 디자인 코드 병합·운영 배포·합성 DOM 검증 완료. 실제 고객 모바일/브라우저 200% 실사용 수락은 별도이며 이를 새 미구현 기능으로 다시 만들지 말 것.
10. **카카오 로그인/SHOP 관련 개발:** COST 작업과 별도의 `6Soo/shop` 저장소이므로 COST의 완료로 합산하지 않음. SHOP 미결은 SHOP 최신 활성 명세를 참조하여 따로 관리한다.

- 카드 검토 UX: 모바일 실제 터치·브라우저 글자 200%·다크/라이트 및 사이드 메뉴 상태, 변경된 지출 카드/입력 폼 회귀 수락.
- Google 시트 및 여행 권위 자료: 동기화 상태, 여행 기간 원본과 카드 배정 ID 일치 여부를 읽기 전용으로 진단. 무단 Google 쓰기나 운영 DB 수정 금지.
- 성능: 카드 검토 전체 데이터 조회 대신 현재 페이지 투영이 적용된 상태 유지. 전후 실제 응답 시간/캐시 신선도 분리 검증.

## D. 후속 실행 순서 및 완료 게이트

1. 최신 `main`/오픈 PR/운영 실행 SHA·프로세스 확인. 이미 완료된 #169/#170/#173/#178은 재구현 금지.
2. Windows 운영 호스트에서 **읽기 전용·개인정보 비출력** 진단: 카카오 11건, Agoda 20,532 JPY, Agoda 625,280원, 파라타 -838,600원, 높은 신뢰도 트립닷컴 거래의 `classification_basis`·`trip_id`·활성 여행 ID·원본 기간. 검색 범위를 카드사·카드끝자리·승인번호·환불 상태·전체 과거 구매까지 넓히되 개인 원문을 Git/AI에 전송 금지.
3. 원인별 구현을 분리해 합성 테스트와 기존 금액·기장/환불·여행 선택 보호 회귀 실행. 특히 #174는 기존 글로벌 분석 캐시와 동일 결과, 여러 환불/원결제 중복, 부분환불, 해외 결제와의 충돌, 서로 다른 카카오 서비스·카드 제외를 검증해야 함.
4. #176/#177/#179는 실제 변경된 UI 동선에서 **기능**이 바뀌었는지 브라우저 수락. 문구만 수정된 상태를 해결로 치지 말 것.
5. 검증 통과 PR만 각각 병합하고 Windows SHA 고정 운영 배포. `/healthz`·`/readyz` 200, 보호 API 401, 프로세스 SHA, 운영 DB 보호 해시, 실제 해당 카드의 자동 연결/배정 결과를 확인.
6. PR·대화의 완료 보고에는 `DIAGNOSTIC_ONLY`/`COPY_ONLY`/`CODE_WRITTEN`/`TESTED`/`MERGED`/`DEPLOYED`/`REAL_DATA_ACCEPTED`를 각각 표시. 읽기 전용 조회와 원장 쓰기는 명확히 분리한다.

**안전 계약:** 추론 연결과 실제 환급 완료는 구분한다. 과거 원본 금액·날짜를 바꾸거나 사용자 확정 배정을 덮지 않는다. 서로 다른 카드, 불분명한 원결제, 환불액 초과, 원본 충돌은 단순 문구 변경으로 해제하지 않는다.
