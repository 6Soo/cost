# COST 자율 지출정리 관리자: P1→P2 선처리·코드 결함 자율 개선 (2026-11-05)

**상태: SPEC_ONLY · 사용자 승인 요구사항, 구현/배포 미완료.** 최신 승인 요청: 카드 지출정리 건수가 생길 때 사용자가 ‘모든 내역 확인해’를 반복하지 않도록 에이전트가 선제 조사·분류·원인 해결을 하고, **에이전트로 해결 불가능한 실제 사용자 판단만 최종 표시**한다. 기존 [금융·분류 계약](finance.md#p1-p2-p3-20261029), [코드/AI 추론 실행 경계](status-and-inference-stages-20261102.md), [금번 108건 가짜 충돌 교정](cleanup-export-conflicts-20261105.md), [다중 업로드 작업자](card-upload-background-navigation-20261104.md), [능동 QA](autonomous-qa-20261102.md) 및 [운영 기록](../operations.md)을 재사용한다.

## 1. 목표 및 비목표

- **성과 기준:** 사용자 최초 신고/‘전체 내역 확인’ 요청 없이 대기열을 탐지·처리하고, 사용자만 확인 가능한 **잔여 실질 예외**를 정확한 이유·근거·다음 행동과 함께 제공한다. 처리 불가를 숨기거나 허위 완료하지 않는다.
- P1 코드 처리→P2 실제 연결 에이전트 추론·근거 대조→P3 사용자 개입(필수 사실/새 금융 정책/권한/보호된 위험 변경) 순서를 따른다. 비용·여행 분류 완료, 내부 기장, Google 반영, 은행 환급은 **각각 별개 사실**이다.
- 카드 파일 업로드·원본 저장·OTA/Google **읽기 스냅샷 갱신** 이후 대기열 항목이 생기거나 성격이 바뀌면 자동 가동한다. 최초 코드 배포/재시작 시 누락된 항목을 재개하고, 이벤트 누락 대비 제한된 주기 보완 검색을 수행한다.
- 새로운 카드사 API, 새 장부 시스템, AI 무제한 실행, 자동 Google 쓰기, 원본 수정, 무검증 운영 셀프 패치는 범위에 포함하지 않는다. 기존 durable upload/completion 작업자·single-writer·권한/재시도/감사 로그·연결 에이전트 경로를 우선 확장한다.

## 2. 자동 처리 단계와 업무 상태

1. **변화 감지:** 파일 접수/분류·OTA 대사/Google 읽기 갱신·실패 재시도·관련 코드 배포를 이벤트로 수집한다. 지출정리 목록과 합계는 **동일한 읽기/권위·필터 계약**으로 계산하며, 같은 트랜잭션을 여러 워커가 중복 소유하지 않는다. 신규/변경 ID·원본 버전·여행 권위 세대·규칙 버전을 고정하고 미완료 항목을 내구적으로 등록한다.
2. **P1 처리:** 기확정 수동 규칙, 자동분류·준비기간, 원본 중복/취소·환불·OTA 대사, 내부 기록 가능 여부를 기존 로직으로 먼저 검증·처리한다. 재실행은 멱등이어야 한다. 검증된 결정을 다시 임의 추론으로 바꾸지 않는다.
3. **P2 자동 기동:** P1의 **실제 잔여 분류/배정 문제** 중 승인된 범위를 기존 `tools/review_card_inference.py`·`app.ai_classification` 연결 에이전트 인터페이스로 넘긴다. 요청에는 민감한 원문·카드번호·예약번호를 넣지 않는다. 실제 agent provider/model/run_id, 원본·시트/여행·규칙 지문, 판단 근거/불확실성·출처를 기록한다. AI가 실행되지 않았으면 P2 성공으로 표시하지 않는다.
4. **원인별 분기:** 단순 거래 귀속 문제, 수집/정본 스냅샷 지연, 원본 충돌·환불 금융 보호, 목록 상태 계산 불일치, 코드/파서 결함, 사용자만 가진 정보 등을 **구별**한다. 임시 수집 장애는 제한적 backoff 재시도·신선도 확인으로 분리한다. 동일 원인·원본 형태·규칙 버전의 다수 건은 **원인 묶음**을 먼저 진단해 불필요한 거래별 AI 호출을 줄인다.
5. **코드 결함 대응:** PR #631의 허위 충돌 108건과 같은 패턴은 동일 원인 재현→유사 입력 전수 조사→보호/반례 테스트→최소 수정→CI/브라우저 영향 검사→별도 PR/배포 게이트→관련 대기열 재평가의 **하나의 업무**로 이어간다. 금융 위험이 없는 검증된 코드 수정만 기존 승인된 자동 병합·고정 SHA 배포 정책 안에서 진행하며, 승인 게이트가 없으면 PR·검증까지 자율 완료하고 배포는 명시적으로 보류한다. 실행 중 운영 호스트의 소스파일을 직접 고치거나 금융 보호/권한을 약화해 테스트를 통과시키지 않는다.
6. **처리 후 검증:** 상태·건수·원본 및 금융 보호 확인 후 `자동 해결`, `에이전트 조사/처리 중`, `자료 재수집 대기`, `위험 보호·확인 필요`, `사용자 결정 필수`를 서로 구분한다. P2가 근거를 못 찾았어도 단순한 ‘신뢰도 낮음’을 P3로 보내지 않는다. 반대로 보호된 금융 미결을 분류 완료로 숨기지 않는다.
7. **P3만 사용자에 노출:** 기본 지출정리 화면의 주 CTA/배지는 ‘내 확인 필요’의 **진짜 사용자 행동 건수**다. 누르면 해당 거래·검토한 근거·왜 스스로 못 해결하는지·선택 가능한 결정·금융 영향이 보인다. P1/P2 진행과 자료/보호 대기는 별도 접힌 상태·필터에서 볼 수 있다. 처리되지 않은 건수를 ‘완료’로 위장하지 않는다.

## 3. 실행·안정성·보안

- **트리거:** 업로드 durable completion 이후 및 OTA/Google 읽기 세대 갱신 완료, 분류/내부 기록 이벤트, 서비스 재시작, 관련 코드 배포. 누락 방지 주기 검사(기본 30분, 운영 설정 가능)는 **변화/미처리만** 대상으로 한다. 이벤트가 폭주할 때 중복 묶음·우선순위·backpressure를 적용한다.
- **신선도·멱등:** 거래 ID + 원본 해시/원행 revision + 여행·Google 세대 + 규칙/모델 판단 버전 등 작업 지문으로 동일한 일을 반복하지 않는다. 실제 승인된 값이 바뀐 경우만 재검토한다. 재시작/접속 장애 후 이어가기, 재시도 상한·오류 분류·dead-letter/운영 경고 제공; 실패한 작업을 성공 표시하지 않는다.
- **모델/비용 경계:** 기존 연결 에이전트가 호스트에서 **무인 호출 가능한지 먼저 검증**한다. 그렇지 않으면 몰래 신규 유료 API/비밀키를 넣지 말고 권한/호출 경로를 확보한다. 승인된 인터페이스에서 제한된 입력·출력 스키마 검증, 실행 비용 상한/타임아웃/동시성 제한, 호출 실패 시 보호 보류 및 대기열 재시도를 설정한다. 개인정보·카드번호·고객 원문은 외부 전송하지 않는다.
- **금융 보호:** 카드 원본·승인번호·금액·수동 결정·중복·환불 연결·기존 금융 링크 보존. SQL 권한/원자성/동시 수정(revision), OTA 근거·여행 권위·수동 보류 보호. Google Sheets 최종 장부 **읽기만**, 자동 쓰기 0. 실제 운영 데이터 일괄 변경·원본/스키마 교정·새 업무 정책·무검증 코드 배포는 별도 승인과 기존 복구 게이트를 요구한다.
- **감사 가능성:** 거래·원인 묶음별 detection/P1/P2/원인 수정/재실행/P3 사건의 시간·소스·검증/실패 사유·관련 코드 버전·PR/배포 SHA를 추적한다. 민감한 원문과 사용자 비밀을 Git/일반 로그에 기록하지 않는다. 기존 인계·운영/검증 파일을 재사용하고 별도 중복 대시보드를 만들지 않는다.
- **데이터와 코드 수정은 분리:** 에이전트가 일반 코드 결함을 수정해도 그 자체로 과거 금융 원본을 소급 수정하지 않는다. 코드 배포 후 읽기 재평가와 승인 범위 내 개별 처리만 재실행한다. 사용자 확인·승인이 필요한 금융 처리/권한은 임의로 진행하지 않는다.

## 4. 우선순위 및 구현 절차

- **P0: 작동하는 자동 루프.** 현재 백그라운드 업로드/완료 워커·cleanup 원인 집계·AI CLI/API의 실제 연결 가능성을 파악하고, 한 번의 파일 업로드부터 P1→P2 자동 기동/재시도·재시작 복구·최종 P3 분리까지 통합한다.
- **P1: 코드 결함 발견과 복구.** 같은 원인 자동 묶음, 변경/회귀 탐지, 테스트 실패를 통한 재현, 격리 브랜치 PR, 기존 승인된 CI·배포 절차 및 재평가를 연결한다. 재현 불가/권한 없음/테스트 실패는 위험 차단과 정확한 사용자 보고로 남긴다.
- **P2: 운영 UX·품질 측정.** 기존 지출정리 페이지에 ‘내 확인 필요’ 우선, 진행/대기/보호 구분, 설명·재검토 이력 표시. 7일 기준 **사용자 최초 발견 결함 수 / 전체 새 대기 건수 / 자동 해결 비율 / P3 회부율 / 최초 탐지부터 처리까지 p50·p95 / 반복 원인 재발률 / AI 호출 및 재시도 수**를 집계해 전후 비교한다. 데이터가 없으면 추정치로 성공을 주장하지 않는다.

## 5. 필수 수락 시나리오

1. 새 카드 파일을 업로드하면 **사용자 명령 없이** P1/필요시 P2가 실행되고 자동 처리된 건은 P3로 나타나지 않는다. 업무 화면을 닫거나 서비스가 재시작돼도 재개한다.
2. **PR #631 재현 유형(108건 허위 충돌)**의 합성 파일을 투입하면 공통 원인 하나로 묶고 허위 108건을 인간 검토로 넘기지 않으며 실제 상이한 원본/금액 충돌은 남긴다.
3. 유효 여행과 근거가 있는 거래는 P1/P2에서 처리, 신선도가 떨어진 OTA/Google 읽기 증거는 재조회 후 판단, 사용자의 명시 보류·모호 환불·실제 카드 원본 충돌은 보호한다.
4. AI 미설치/연결 실패/타임아웃, worker 중지, 동일 파일 재업로드, 동시 실행, 수정된 자료 revision, 규칙 버전 변경, CI/배포 실패에서 **중복 쓰기·무한 재시도·허위 완료 없이** 회복/안전 보류한다.
5. 코드 회귀가 남긴 미해결 건은 원인 재현→테스트·PR→검증된 변경 배포(허용 시)→관련 건 재평가까지 증명한다. 코드만 병합하거나 PR만 닫고 ‘완료’라고 하지 않는다.
6. 운영 인증 PC/390/320px에서 지출정리 ‘내 확인 필요’와 진행/자료대기/보호 항목을 구분해 보여주며, 사용자가 이해할 수 있는 이유와 다음 행동을 제시한다. 화면 목록·집계 불일치 없음.
7. 기존 관련 P1·P2 테스트, 금융 보호/권한/CSRF/중복·환불/Google 쓰기 금지, 영향 QA/CI와 운영 고정 SHA·health/ready·보호13표 전후 불변을 검증한다. **고객 금융 원본 변경·실제 환급·Google 기록은 수락 테스트에서 수행하지 않는다.**

## 6. ‘완료’ 판정

**명세·프로토타입·수동 CLI 실행·합성 테스트·PR 병합만으로 COMPLETE 선언 금지.** 실제 호스트의 지속 실행 트리거가 작동하고 P1→P2(실제 연결 호출)→재평가→P3 분리 루프가 사용자 ‘모든 내역 확인해’ 지시 없이 수행되는지 확인한 뒤, 기존 승인된 절차로 병합·배포하고 인증 운영 읽기 수락을 기록한다. **무인 연결 에이전트 권한이나 자동 배포 권한이 제공되지 않는다면 우회하지 말고 해당 단계만 BLOCKED와 정확한 요구사항을 표시**하되 나머지 구현·검증·문서 인계는 끝까지 수행한다. 결과에는 자동 처리/자료 대기/진짜 P3 숫자와 실패 원인, 검증하지 않은 운영 범위를 구분한다.
