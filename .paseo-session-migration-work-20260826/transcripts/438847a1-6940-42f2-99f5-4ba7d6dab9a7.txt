## 1. 가장 큰 병목과 근거

### A. Agoda 브라우저 수집이 전체 지연의 최상위 병목

근거:

- Agoda 상세 수집은 Paseo IAB 단일 인증 세션·예약별 상세 진입·URL 상태 확인이 필요하다.
- 과거 로그에 10개 병렬 레인, 예약별 새 탭, 상세 재열거, 세션 소유권, 고객센터 패널 fail-closed 등의 운영 복잡성이 누적되어 있다.
- 2026-08-21 로그에는 목록 재열거와 opaque detail route 문제, 고객센터 패널 incident, 재시도 제한이 기록돼 있다.
- 현재 후보 산출물은 카드 5,328건, Agoda 상세/예약 591건, 강한 1:1 후보 77건 수준이다. 즉 전체 카드 건수 대비 브라우저가 실제로 필요한 대상은 소수지만, 현재 구조는 광범위한 census를 먼저 요구한다.

추정 비용 모델:

```text
전체 실행시간
= 브라우저 수집 시간
+ 외부 메일/카페 조회 시간
+ 로컬 import/정규화/projection 시간
+ 검증·회귀 시간
+ 에이전트·권한·알림 대기시간
```

현실적인 비중 추정:

| 영역 | 현재 비용 추정 | 경량화 우선순위 |
|---|---:|---:|
| Agoda 브라우저 | 전체의 50~80% | 최우선 |
| Gmail/카페/일정 원천 수집 | 10~25% | 높음 |
| SQLite import·projection·candidate graph | 5~15% | 중간 |
| 전체 회귀·산출물 재빌드 | 10~25% | 높음 |
| 에이전트·권한·알림 | 변동성이 크나 장애 시 전체 정지 | 별도 통제 |

정확한 초 단위 측정값은 현재 저장소에서 확인하지 못했으므로 위 비율은 추정이다.

### B. 산출물 복제가 많고 “clean/final/rebuild/shadow”가 병렬로 누적된다

현재 output에는 같은 5,328 payment와 77 Agoda 후보를 기반으로 한 SQLite가 여러 개 존재한다.

예:

- `agoda-card-accounting-draft-v3-clean`
- `...clean-rebuild`
- `...v3-final`
- `...v3-rebuild`
- `journal-shadow-v3-clean`
- `journal-shadow-v3-clean-rebuild`

재빌드 검증 자체는 품질에 유익하지만, 운영 경로에 여러 버전이 동시에 존재하면 다음 비용이 생긴다.

- 어떤 파일이 권위 산출물인지 판단 비용
- 전체 DB 복제·해시·무결성 검사 비용
- 잘못된 `v3-final`처럼 구형 분류·배부가 섞인 산출물을 채택할 위험
- 저장공간과 파일 탐색 비용

### C. authoritative trip_schedule이 안전하지만 중앙 계약이 아직 분산돼 있다

현재 구조는 `direct_trip_schedule_authority.py`가 명시적 연도·시작일·종료일·종료 의미·source hash를 요구한다. 이 경계는 안전하다.

다만 다음이 동시에 존재한다.

- reservation export의 `authority_status`
- cost의 `trip_schedule_authority_v3.json`
- `trips.json`의 legacy window
- OTA service period
- `ledger_db.py`의 legacy trip/candidate 처리
- 각 Agoda·OTA 모듈의 재검증

현재 권위 문서가 빈 문서이므로, 2026-08-24 로그의 Agoda 77건은 모두 `authority_missing` 또는 `candidate_only`로 보류된다. 이는 회계 안전성에는 맞지만, 업무자가 “왜 자동 처리되지 않는가”를 추적하는 비용이 크다.

### D. 전체 5,328건 재투영과 전체 회귀가 증분 변경에도 반복될 가능성이 높다

현재 projection은 카드·수기·OTA·PG·서비스 메일·여행·지리 컨텍스트·숙박 fact·OTA reservation fact 등 여러 원천의 key set과 source hash를 관리한다. 좋은 기반이지만, 실제 변경은 대개 다음 중 일부다.

- 특정 카드 파일 추가
- 특정 Agoda 상세 1~수십 건 추가
- trip schedule 한두 행 추가
- 댓글 activity observation 추가

이때 전체 5,328건 projection과 전체 regression을 반복하면 변경 범위보다 검증 범위가 훨씬 커진다.

## 2. 제거·통합·캐시·증분화 기준안

### 제거할 것

1. 운영 경로에서 legacy browser entry point를 계속 노출하는 구조  
   이미 `agoda_browser_policy.py`가 legacy 경로를 차단하므로, 문서·실행 스크립트에서도 브라우저 진입점을 하나로 명확히 줄인다.

2. 브라우저 재수집으로 해결하려는 저가치 후보  
   금액·통화·카드 끝 4자리·Agoda 예약 식별자가 동시에 맞지 않는 건은 브라우저를 열지 않고 `held` 또는 `review_group`으로 남긴다.

3. 매 실행마다 생성하는 중간 복제 DB  
   기존 파일은 보존하되, 향후 실행은 다음 세 종류로 제한한다.

   - immutable input snapshot
   - candidate/shadow run DB
   - 최종 export manifest

4. `exported_at`처럼 내용과 무관한 메타데이터를 변경으로 취급하는 로직  
   reservation export는 이미 이를 제외한 stable hash를 사용하므로 이 원칙을 모든 source import에 통일한다.

### 통합할 것

권장 논리 계층은 다음 다섯 개다.

```text
원천 수집
  ↓
정규화된 source snapshot
  ↓
projection run
  ↓
candidate / authoritative decision
  ↓
shadow journal 또는 posting
```

현재의 `direct_*` 테이블 세분화는 회계 감사상 유용하므로 물리적으로 즉시 합치지 않는다. 대신 실행 진입점을 하나로 묶고 각 테이블을 내부 구현으로 숨긴다.

특히 다음을 공통 `run manifest`로 묶는다.

- source document hash
- code bundle hash
- schedule export hash
- browser census hash
- projection run id
- candidate semantic hash
- validation hash
- output manifest hash

### 캐시할 것

1. reservation schedule export

키:

```text
schedule_export_key =
schema_version
+ parser_contract
+ canonical records
```

`exported_at`은 캐시 키에서 제외한다.

2. 댓글 활동성 증거

키:

```text
activity_key =
cafe_fldid
+ cafe_datanum
+ source_post_sha256
+ listed_comment_count
+ fetched_unique_comment_count
+ activity_status
+ activity_source_status
```

관찰 시각만 바뀌면 content snapshot은 재생성하지 않고 observation만 추가한다.

3. Agoda 상세

예약별 캐시 키:

```text
booking_id
+ opaque_detail_route
+ captured_page_sha256
+ source_session_scope
```

다음 조건이 아니면 상세를 재수집하지 않는다.

- opaque route 변경
- 페이지 hash 변경
- 카드 끝 4자리 또는 결제상태 누락
- 이전 캡처가 fail-closed 상태
- candidate graph가 해당 예약을 실제로 요구함

4. 카드 RAW/정규화

카드 파일 전체 hash를 유지하되, 행 단위 `source_event_id`·`identity_fingerprint`가 변하지 않은 행은 재정규화하지 않는다.

### 증분화할 것

- 새 reservation schedule record가 추가된 trip만 schedule authority 재검증
- 변경된 trip의 서비스 기간과 겹치는 payment만 OTA matching 재계산
- 변경된 Agoda booking과 금액·카드4·통화가 연결 가능한 payment만 candidate graph 재실행
- 카드 RAW 신규 행만 normalize
- 취소·환불은 원 결제와 연결된 event family만 재계산
- classification/projection은 변경된 source key의 dependency closure만 재생성
- 전체 5,328건 총액 검증은 유지하되, row-level 재생성은 변경 집합으로 제한

## 3. 품질·회계 안전성을 보존하는 불변식

다음은 경량화 과정에서 절대 약화하면 안 된다.

### 일정 권위 불변식

- 결제일·가맹점 지역명·legacy `mm/dd/window`로 여행 연도나 행사기간을 추정하지 않는다.
- `event_year`, `starts_on`, `ends_on`, `end_semantics`, `authority_kind`, `authority_status`, `source_sha256`가 모두 있어야 authoritative다.
- 체크아웃 제외형 `service_end_on`은 `-1일`로 정규화하고, 행사 일정의 포괄 종료일과 혼용하지 않는다.
- 일정 충돌·원천 hash 불일치·연도 불일치는 보류한다.

### import·멱등성 불변식

- 동일 export 재수입은 `inserted=0`이어야 한다.
- `exported_at` 변경은 내용 변경으로 취급하지 않는다.
- 동일 `trip_code`의 일정 내용 변경은 조용히 overwrite하지 않고 conflict로 실패한다.
- 기존 authoritative activity evidence를 이후 archive 부재가 삭제하지 않는다.
- import는 posting·allocation을 생성하지 않는다.

### 회계 불변식

- shadow journal의 차변·대변 합계가 항상 일치해야 한다.
- `candidate_only`, `authority_missing`, `ambiguous`, `held`는 allocation·posting으로 승격되지 않는다.
- 카드 실제 청구액과 OTA gross·할인·포인트·현장결제액을 혼동하지 않는다.
- 취소·환불은 원 결제의 비용축을 자동 상속하지 않는다.
- 모든 최종 판단은 source lineage와 idempotency key를 가져야 한다.

### 개인정보·보안 불변식

- reservation export에 댓글 원문·작성자·연락처·주민번호·여권 정보가 들어가지 않는다.
- source raw content는 cost로 전달하지 않고 hash와 필요한 구조화 필드만 전달한다.
- 외부 모델에는 원문 고객 데이터를 보내지 않는다.
- Agoda 수집은 Paseo IAB 단일 전용 세션만 사용하고 고객센터·도움말 경로를 호출하지 않는다.

## 4. 단계별 마이그레이션·롤백 계획

### 0단계: 관측만 추가

변경 내용:

- 각 단계의 시작·종료 시각 기록
- source count, changed key count, cache hit/miss, browser page count 기록
- output 파일 생성 대신 manifest만 우선 생성

롤백:

- 기존 실행 명령 유지
- 관측 필드 제거만으로 원상복귀 가능

### 1단계: reservation export를 단일 경계로 고정

목표:

- reservation → cost 전달을 `reservation-trip-schedule-export-v2` 하나로 통일
- 댓글은 원문이 아닌 count·census completeness·snapshot hash만 전달
- cost import를 모든 후속 권위 일정 입력의 유일한 경계로 지정

롤백:

- 새 export를 authoritative 입력으로 사용하지 않고 기존 snapshot을 재사용
- 기존 cost DB는 건드리지 않고 별도 shadow DB에서만 검증

### 2단계: immutable source/run manifest 도입

목표:

- source document, code bundle, schedule, browser census를 하나의 run manifest에 연결
- `clean`, `final`, `rebuild` 명칭 대신 `run_id + manifest hash`를 권위 식별자로 사용
- 기존 산출물은 삭제하지 않고 legacy artifact로 분류

롤백:

- manifest 기반 실행 실패 시 기존 full rebuild 경로를 사용
- 데이터베이스 schema 변경 없이 메타데이터 계층만 되돌림

### 3단계: 증분 projection

목표:

- source key diff로 영향 payment 집합 계산
- 영향이 없는 payment는 기존 projection row 재사용
- 전체 총액·행 수·FK·uncovered source 검증은 계속 수행

롤백 조건:

- 증분 결과 semantic hash가 full rebuild와 다름
- 영향 집합 밖의 payment가 변경됨
- allocation 또는 journal row가 비의도적으로 증가함

이 경우 해당 run만 폐기하고 full rebuild shadow로 회귀한다.

### 4단계: Agoda 수집 축소

권장 순서:

1. 카드 RAW에서 Agoda 후보를 먼저 좁힘
2. 금액·통화·카드4·provider lifecycle로 1차 필터
3. N:N 또는 불완전 후보만 브라우저 큐에 넣음
4. 상세 캡처 후에도 authority와 service period가 없으면 posting하지 않음

롤백:

- 브라우저 census 축소를 중단하고 기존 sealed census를 사용
- 새 수집 결과는 candidate-only로 격리
- 기존 authoritative evidence는 덮어쓰지 않음

### 5단계: 테스트 계층화

권장 실행 순서:

1. 변경 파일 단위 테스트
2. import/idempotency/schedule authority 회귀
3. 영향 영역 candidate/projection 회귀
4. 전체 totals·FK·source coverage 검증
5. 주기적 전체 회귀

전체 회귀를 매번 생략하는 것이 아니라, “증분 검증 + 전체 불변식 검증”으로 바꾼다.

### 중단 조건

다음 중 하나라도 발생하면 경량화 run을 중단하고 이전 shadow/full 경로로 되돌린다.

- 일정 source hash 불일치
- 동일 trip의 authoritative 일정 충돌
- event year가 서비스 기간 밖으로 나감
- candidate-only 행이 allocation/posting으로 이동
- 차변·대변 불일치
- 동일 RAW가 서로 다른 normalized identity를 생성
- full rebuild와 incremental semantic hash 불일치
- 브라우저 session ownership 불명확
- `CUSTOMER_CENTER_PANEL_VISIBLE`
- `NAVIGATION_STATE_UNKNOWN`
- `PASEO_BROWSER_UNAVAILABLE` 후 허용된 재시도 소진
- 권한·알림 대기 때문에 실행 critical path가 정지
- PII가 export·로그·외부 모델 입력으로 유출될 가능성

## 6. 현재 구조에서 절대 건드리면 안 되는 경계

1. `direct_trip_schedule_authority.py`의 authoritative 판정  
   정확도 향상을 이유로 legacy window나 결제일 기반 추정을 다시 허용하면 안 된다.

2. reservation export의 개인정보 제거 경계  
   raw post, 댓글 원문, 작성자, 연락처를 cost로 보내지 않는다.

3. `load_authoritative_trip_schedule()`를 통한 최종 배정 경계  
   후보 생성기가 권위 일정을 우회해 직접 allocation하지 못하게 유지한다.

4. `direct_projection`의 source hash·run manifest·semantic hash  
   증분화를 하더라도 provenance와 재현성을 제거하지 않는다.

5. `ledger_db.py`의 source version·identity fingerprint·change log  
   단순 overwrite로 바꾸면 멱등 import와 감사 추적이 깨진다.

6. Agoda 브라우저 안전 경계  
   Paseo IAB 전용, 단일 세션 소유권, 명시적 예약 control, 고객센터 경로 금지 원칙은 유지한다.

7. shadow와 실제 posting의 분리  
   shadow 산출물의 숫자가 맞아도 실제 전기로 승격하지 않는다. authoritative evidence와 별도 posting gate가 필요하다.

8. reservation의 PII 권한 경계  
   예약 시스템의 개인정보 저장·복호화·관리자 권한과 비용 시스템의 회계 증거를 통합하지 않는다.

## 최종 기준안

가장 현실적인 경량화는 “검증을 줄이는 것”이 아니라 다음 세 가지를 줄이는 것이다.

1. 브라우저 수집을 전체 census 중심에서 영향 후보 중심으로 축소  
2. 변경되지 않은 source·payment·decision의 재계산을 캐시  
3. 여러 중간 산출물을 하나의 manifest 기반 run으로 통합

권장 목표는 다음과 같다.

- reservation export/import: 내용 동일 시 재처리 0건
- 일반 카드 변경: 전체 5,328건 중 영향 집합만 재계산
- Agoda 상세: 카드·금액·통화·예약 식별자로 좁힌 큐만 수집
- 전체 회계 불변식과 총액 검증은 유지
- authoritative 일정·posting·PII·브라우저 안전 경계는 변경하지 않음
- 기존 dirty tree와 미추적 산출물은 정리하지 말고, 먼저 별도 실행 manifest와 상태 분류를 도입

이 기준이면 지연은 주로 브라우저 수집과 반복 full rebuild에서 줄이고, 회계 안전성은 현재의 fail-closed·hash·shadow 구조로 보존할 수 있다.
