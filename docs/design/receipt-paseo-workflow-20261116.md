# 영수증 처리 변경 — 로컬 Paseo 선택·지속 처리·사용자 검수

> **상태: 구현 승인·진행 중(2026-11-16).** 사용자가 아래 명세의 구현과 다수 Luna xhigh 병렬 위임을 지시했다. 주 세션은 감독·검수·통합을 맡는다. 구현·합성 검증은 승인됐으며 운영 배포·고객 원본 변경은 이번 요청에 추가하지 않는다. 실제 완료 범위는 현재 상태·작업판을 따른다.
> **기준 코드:** `9e2d66a39ea9574c09d51bdcb771f1006dff8b10`. 실행 정본은 [통합 명세](../SPEC.md), 판정·원본·전송 보호는 [영수증 규칙](../policy/receipt.md)이다. 이 문서는 그 요구를 구현하기 위한 설계이며 판정 규칙의 별도 정본이 아니다.

## 1. 사용자에게 보일 최종 흐름

**사진 업로드 → 로컬 PC의 provider·model 조회 → 사용할 모델 선택과 동시에 분석 시작 → 다른 페이지 이용 → 영수증 페이지로 복귀 → 사진과 결과 대조·수정 → 선택한 내역만 COST 장부에 반영.**

모델에 작업을 전달했다는 안내로 끝내지 않는다. 실제 처리 결과를 COST에 저장하고, 사용자가 돌아오면 사진별 상태와 결과를 다시 보여 준다. 분석 결과만으로 장부에 자동 반영하지 않는다. Google 지출표에는 기존대로 사용자가 복사해 붙여넣는다.

### 확인된 사용자 결정

| 질문 | 2026-11-16 답변 |
| --- | --- |
| 전송할 모델 범위 | 승인된 구독 모델 중 사진 입력 가능한 모델만 선택 가능 |
| 프롬프트 | 관리되는 기본 판독 지시만 사용 |
| 검수·반영 단위 | 사진과 결과를 나란히 보고, 선택한 내역만 한 번에 반영 |

영수증 판독 결과의 직접 검수는 이번 사용자가 명시한 흐름이다. 카드 P1/P2의 자동 판정이나 분기 AI 검수를 사용자 건별 검수로 바꾸는 요구는 아니다.

### 로컬 Paseo 확인

- 설치 CLI `0.16.0-beta.2`의 `run --help`와 `send --help`에 `--image`가 있다. 사진 첨부 경로가 존재한다는 근거이며 모든 provider가 사진을 처리한다는 뜻은 아니다.
- 연결된 데몬 조회에서 provider 11개 중 8개가 enabled/available이었다. 이 수는 조사 시점 값이며 화면 목록이나 허용 목록으로 하드코딩하지 않는다.
- Claude·Codex·Qwen Code의 실제 모델 목록을 조회했다. 반환 메타데이터에는 모델 ID·표시명·일부 추론 옵션이 있었으나, 조회 결과만으로 사진 지원·현재 인증·잔여 한도·전송 승인을 모두 판정할 수는 없었다.
- 실행에 쓸 데몬은 이 로컬 PC에 연결된 데몬으로 명시한다. 개발 셸의 데몬 연결과 운영 실행 계정의 연결이 같다고 가정하지 않는다.

## 3. 화면과 실행 계약

### R1. 사용할 provider·model 표시

1. `/receipts` 진입과 `목록 새로고침`에서 COST 서버가 연결된 로컬 Paseo의 provider 목록을 읽는다. provider를 고르면 그 provider의 실제 모델 목록을 조회한다.
2. 서버가 **기존 고객 원문 전송 승인 + 구독 사용 경로 + 사진 입력 지원 + 제한된 판독 실행 가능**을 확인한 모델만 선택할 수 있다. 알 수 없으면 가능하다고 표시하지 않는다. 무료·미승인·별도 종량 과금 경로는 실행 대상이 아니다.
3. provider가 available이라는 사실과 모델의 사진 지원·인증·한도를 구분한다. 선택 불가 모델에는 짧은 이유를 표시한다. 인증·한도는 실제 실행 시 바뀔 수 있음을 실행 실패 상태에 반영한다.
4. ID·이름·추론 옵션은 데몬 응답을 사용한다. 추론 수준은 해당 모델의 제공 기본값을 사용하고 실행 기록에 남긴다. 응답에 없는 모델·옵션을 만들어 넣지 않는다.
5. 목록에는 연결 PC와 마지막 조회 시각을 표시한다. PC 연결 실패 때 캐시를 현재 이용 가능 목록으로 가장하지 않는다. 임의의 원격 데몬 URL을 사용자 입력으로 받지 않는다.

### R2. 모델 선택 시 즉시 실행

1. 먼저 업로드가 완료된 사진을 선택한다. 여러 장이면 배치 하나 아래 사진별 작업을 만든다. PDF는 기존 원본↔페이지 관계를 보존하고 페이지 이미지별로 처리한다.
2. provider 선택은 목록 탐색이다. **모델의 `이 모델로 처리` 선택이 실행 동작**이며, 별도의 전송만 하는 단계나 두 번째 확인 버튼을 두지 않는다. 방향키로 목록을 탐색하거나 화면이 복원됐다는 이유로 실행하지 않는다.
3. 모델을 선택하면 서버가 원본·소유권·승인·실행 가능성을 검증하고 작업을 먼저 영속 저장한 뒤 로컬 Paseo에 관리 프롬프트와 선택한 사진을 보낸다. HTTP 요청은 작업 ID를 반환하고 모델 완료까지 붙잡지 않는다.
4. 정상 연결·빈 큐에서 즉시 전달을 시작하는 것이 목표다. 대기 작업이 있으면 실제 순서를 보여 준다. 외부 모델 완료 시간이나 즉시 시작을 보장하는 허위 표시를 하지 않는다.
5. 모델·프롬프트 버전·사진 SHA가 같은 실행 요청의 중복 클릭·응답 유실 재시도는 기존 작업을 돌려준다. 다른 모델이나 명시적 재분석은 새 실행 이력으로 남긴다.
6. 고정 판독 프롬프트는 기존 절차서의 관리 지시·출력 스키마와 연결한다. 화면에서 전체 프롬프트나 추가 요청을 편집하지 않는다. 기존 자유 입력 재분석 메모·학습 메모도 새 실행에 자동으로 붙이지 않는다. 사용자가 고친 값은 검수 이력으로 저장한다. 버전·해시는 작업 생성 시 고정한다.
7. 사진을 지원하지 않는 모델에 OCR 텍스트를 대신 보내 성공으로 표시하지 않는다. 다른 provider·model·유료 경로로 자동 전환하지 않는다. 기존 직접 입력 경로는 유지한다.

### R3. 페이지를 떠나도 처리·저장

- 브라우저 탭·네트워크·폴링은 작업 수명의 소유자가 아니다. 다른 페이지 이동, 탭 종료, 다른 기기 접속과 무관하게 서버/로컬 실행기가 처리와 결과 저장을 계속한다.
- 원본이 저장되기 전 업로드 중 탭을 닫는 경우까지 완료를 보장하지는 않는다. 화면에서 `업로드 중`과 `원본 저장됨`을 구분한다.
- 배치·사진별 작업·Paseo agent/session ID·실행 시도·원본 SHA·결과·오류·사용자 수정·반영 상태를 영속 저장한다. 결과가 도착하면 브라우저 호출 없이 서버가 검증·저장한다.
- 서버 재시작 후에도 기존 Paseo 실행을 조회·재연결한다. PC 재시작으로 실행이 실제 종료됐으면 실패로 남기고 결과를 지어내지 않는다.
- `전송했으나 agent ID 저장 전 연결 유실` 구간은 작업의 고유 라벨·보존 실행 기록으로 대조한다. 기존 실행 여부가 불명확할 때 같은 사진을 자동 재전송하지 않는다.
- 완료 결과를 기존 1시간 TTL로 지우지 않는다. 사용자가 나중에 복귀해 검수·반영할 수 있게 보존한다. 기존 원본 보존 정책을 약화하거나 자동 삭제를 새로 도입하지 않는다.

### R4. 복귀 시 사진과 결과 검수

| 영역 | 사용자에게 제공할 내용 |
| --- | --- |
| 작업 목록 | 업로드 묶음·사진 수·선택 모델·시작 시각·사진별 처리 상태·결과/반영 건수 |
| 원본 | 사진 확대·이동, 선택한 실물 영수증 영역 표시, PDF 원본과 페이지 관계 |
| 결과 | 실물 영수증별 상호·날짜·통화·금액·결제수단·여행·항목·판독 불확실성 |
| 교정 | 필요한 값을 직접 고치고 저장. 모델 원응답과 사용자 수정값은 분리 보존 |
| 반영 선택 | 내역별 체크, 명시적인 전체 선택, `선택한 N건 장부에 반영` |

- 데스크톱은 사진과 결과를 좌우로, 모바일은 같은 선택 문맥을 유지하며 위아래로 배치한다. 사용자 선택 없이 처음부터 모든 내역을 반영 대상으로 체크하지 않는다.
- 페이지 복귀 시 서버 저장 상태를 읽는다. `localStorage`는 표시 설정 정도에만 쓰며 결과·작업 ID·미반영 내역의 유일한 보관소가 되지 않는다.
- 처리 중에도 이미 완료된 다른 사진의 결과를 검수할 수 있다. 갱신이 사용자의 입력·초점·사진 확대 위치를 덮지 않는다. 수정 내용은 서버에 저장하고 다른 탭의 최신 교정을 오래된 값으로 덮지 않는다.
- `분석 중`, `분석 완료`, `영수증 0건`, `분석 실패`, `장부 반영됨`을 구분한다. 근거 없는 퍼센트 대신 실제 단계와 완료 사진 수를 표시한다. 상태는 색상만으로 전달하지 않는다.
- 처리 대기는 작업의 실행 상태다. 영수증 판독·등록의 사용자 검수를 카드 판정의 질문함·보류함으로 확대하지 않는다.

### R5. 검수한 내역의 COST 장부 반영

1. 사용자 선택과 수정값을 서버에 먼저 저장한다. 반영 요청에는 선택 내역의 ID·기대 revision·고정 request ID를 보낸다. 확인한 버전과 다르면 해당 충돌을 보여 주고 오래된 값으로 쓰지 않는다.
2. 날짜·통화·금액·지정 여행·항목·회사 비용 인정·카드 연결·중복·환불 보호를 정식 코드 경로에서 재검사한다. 필요한 값이 없으면 해당 내역을 수정할 수 있게 안내하며 임의 값으로 채우지 않는다.
3. 현금/인정된 개인카드 비용은 규칙에 따라 COST 장부에 반영한다. 이미 기록된 법인카드 비용이면 증빙만 연결하고 두 번째 지출을 만들지 않는다. 기존 카드 처리·환산 규칙을 따른다.
4. 선택한 묶음을 사전 검증하고 한 트랜잭션에서 반영한다. 충돌·오류가 있으면 그 요청의 장부 변경은 전부 되돌린다. 이미 처리한 다른 배치의 성공은 유지한다.
5. request ID에 대한 실제 장부 쓰기와 멱등 기록은 같은 트랜잭션에 둔다. 같은 요청 재전송·응답 유실·탭 두 개로 같은 비용이 두 번 기록되지 않는다.
6. 결과에 장부 행 ID 또는 기존 카드 행의 증빙 연결 ID를 저장하고 사용자가 해당 내역으로 이동할 수 있게 한다. 실패 때 `반영됨`이라고 표시하지 않는다. 이미 반영한 내역은 재분석으로 덮거나 중복 반영하지 않는다.
7. Google 쓰기·실제 결제·상환 이체·직원 정산 자동화는 이 작업의 범위가 아니다.

## 4. 기술 설계 초안

### 연결 구조

웹 브라우저는 COST 인증 API만 호출한다. COST의 영속 작업 실행기가 이 PC의 Paseo 데몬과 인증된 로컬 연결로 통신한다. 외부에서 접속한 브라우저의 `localhost`를 이 PC로 간주하지 않으며 데몬을 인터넷에 직접 공개하지 않는다.

현재 서버와 PC가 같은 호스트인 구성을 우선한다. M5 클라우드 이전을 이번에 함께 구현하지 않는다. 다만 PC의 연결 정보와 실행 주체를 분리해 미래 보조 노드 구조에서 작업 계약을 재사용할 수 있게 한다.

| 배치 | 소유자, 선택 사진/페이지, 선택 provider/model/추론 수준, 생성 시각 |
| 작업·시도 | 고정 ID·멱등 키, 원본 SHA, 프롬프트·스키마 버전, Paseo 연결 대상·agent/session ID, 실제 상태·시각·오류 |
| 판독 결과 | 검증 전 원응답(비공개), 검증 결과, 영수증별 안정된 ID와 위치, 이전 결과와의 관계 |
| 검수 | 사용자 수정값·revision·선택 상태·변경 전후 이력 |
| 장부 반영 | request ID, 반영한 revision, 처리 결과, 장부/증빙 연결 ID |

작업·결과에는 영속 저장소를 사용하며 기존 영수증 JSON·이미지·PDF를 읽기 실패 때 빈 저장소로 초기화하지 않는다. SQLite 작업 저장소 도입을 우선 검토한다. 기존 자료를 옮기는 설계는 원본 ID·바이트·관계를 보존하는 호환 이관으로 한다.

작업 저장소와 장부 저장소가 다르면 장부의 커밋 결과가 정본이다. 반영 상태 갱신 전에 장애가 나도 멱등 기록을 조회해 실제 결과를 복구하며 중복 쓰기하지 않는다. 다중 저장소를 단일 트랜잭션처럼 가정하지 않는다.

### API 의미 계약(경로명은 구현 시 확정)

- 모델 목록 조회: 로컬 연결 상태·조회 시각·실제 모델 목록·선택 가능 여부와 이유.
- 분석 생성: 원본 ID 목록·선택 모델·request ID → 배치 ID와 사진별 작업 ID를 신속 반환.
- 작업 조회: 브라우저 세션과 독립적인 목록·상세·결과·오류·반영 상태.
- 검수 저장: 기대 revision을 검사하고 변경값·선택 상태 저장.
- 장부 반영: 선택 내역과 기대 revision·request ID → 실제 기록 또는 증빙 연결 결과.
- 재분석: 종료가 확인된 작업에서 명시적으로 새 시도를 생성. 과거 검수·장부 기록 보존.

권한·CSRF·원본 소유권 검증은 서버에서 수행한다. 브라우저가 준 임의 파일 경로나 임의 provider 문자열을 실행 명령에 그대로 넣지 않는다. 사진·프롬프트·결과·데몬 자격 증명은 공개 로그·Git·PR·CI에 넣지 않는다.

사진 첨부와 구조화 결과는 Paseo의 공식 SDK/API 또는 확인한 CLI를 사용한다. 단순 `plan` 이름만으로 도구 차단을 보장하지 않는다. 승인 사진 외 파일 접근·shell·웹·MCP·임의 쓰기를 차단할 수 없는 provider/model은 실행 대상으로 제공하지 않는다. 사용자 작업용 workspace·agent와 개발용 COST workspace를 공유하지 않는다.

## 5. 실패·복구 계약

- **로컬 PC/Paseo 연결 끊김:** 원본·접수 작업을 보존하고 연결 상태 표시. 실제 전송 여부를 대조한 뒤 같은 실행을 추적한다.
- **모델 인증·한도·사진 미지원:** 해당 사진의 실패 사유를 남긴다. 다른 모델이나 OCR로 조용히 바꾸지 않는다. 직접 입력·종료 확인 후 재분석 가능.
- **사진별 일부 실패:** 성공한 다른 사진의 결과를 보존하고 실패한 사진만 다시 처리할 수 있다.
- **잘못된 JSON·결과/원본 불일치:** 검증 실패로 저장하고 장부 반영 금지. 결과를 복구 가능한 비공개 근거로 보존.
- **결과 0건:** 실패와 구분해 원본·0건 결과 저장. 사용자는 직접 입력 가능.
- **통신 중복·새로고침·서버 재시작:** 실행과 장부 반영의 멱등 키를 대조한다. 원격 모델 호출의 완벽한 exactly-once를 주장하지 않는다.
- **늦게 도착한 이전 실행 결과:** 실행별로 보관하고 현재 사용자 교정이나 최신 선택 결과를 덮지 않는다.
- **작업용 agent/workspace 정리:** 결과 영속 저장·검증 뒤 그 작업이 소유한 자원만 공식 archive한다. 사용자의 기존 agent/workspace·원본은 제거하지 않는다.

## 6. 구현 전에 확인할 기술 항목

| 항목 | 필요한 확인 | 현재 상태 |
| --- | --- | --- |
| 실제 운영 실행 계정의 데몬 연결 | 서비스/예약 작업 문맥에서도 동일한 로컬 Paseo 조회·사진 첨부가 가능한지 | 미검증 |
| 모델별 사진·제한 실행 지원 | 승인된 각 모델의 사진 입력과 도구 차단, 구조화 결과를 합성 사진으로 확인 | 목록 조회만 완료, 실제 호출 안 함 |
| 비동기 결과 재수집 | 사진 첨부 실행의 agent ID·종료 결과를 재시작 후 공식 API로 복구 가능한지 | CLI `--image` 존재만 확인 |
| COST 장부의 영수증 반영 | 후보 저장과 실제 장부 쓰기를 구분하고 기존 중복·증빙 경로와 연결 | 현 코드 정적 확인, 신규 계약 설계 |
| 저장소·호환 이관 | 작업 영속화 위치, 기존 draft·원본 보존, 백업·복원 범위 | 설계 초안 |

위 항목은 구현자가 확인할 기술 사항이다. 사용자에게 내부 API·격리 방식·DB 설계를 결정하도록 묻지 않는다. 사진 입력 또는 제한 실행을 제공하지 않는 모델은 초기 선택 대상에서 제외한다.

명세 작성 시 이 표의 앱·모델·브라우저 검사는 실행하지 않았다. 이후 구현 승인에 따라 합성 자료로 표적·영향·브라우저 검사를 수행하고 근거를 현재 상태에 기록한다. 운영 저장소 변경은 신선 백업·복원 확인 후 별도 배포 절차를 따른다.
