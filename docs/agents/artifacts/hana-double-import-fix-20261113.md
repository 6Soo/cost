# 하나카드 해외 이중수입 수정·정리 사본 예행 (2026-11-13, v2)

정책: [SRC-005·SRC-009·SRC-013·SRC-014](../../policy/source.md). 운영 원본(`D:/WebLedgerHost/data/board.sqlite`)은 `mode=ro`로만 읽고, SQLite backup으로 만든 별도 사본에서만 예행했다. 원문·금액·개별 거래 식별값·가맹점·승인번호는 이 보고서에 없다(건수·비율만). 이 문서는 opus 독립 검수(PR #832)의 B1·B2·B3 지적을 반영한 v2다.

## 원인

하나카드 해외 구매가 두 번 수입되어 두 번 장부되었다. 매입 원본 뷰(`xls:hana_foreign`, 청구금액=실제 청구된 원화 총액)와 승인 출처 다운로드(`csv:headered`/`xls:headered`, 승인금액=승인 시점 원화)가 같은 승인번호를 서로 다른 앞자리 0으로 패딩한다(예: `00001111` 대 `1111`). `app/card_export_profiles.py`의 `existing_purchase`가 (1) 승인번호를 **원문 문자열 그대로** 비교하고 (2) 교차 뷰 매칭을 `hana_usage`·`hana_foreign`·`ibk_print` 레이아웃으로만 제한해서, `headered` 승인 출처 행은 매칭되지 않고 별개의 깨끗한 거래로 삽입·장부되었다. 금액은 승인 시점 원화 대 청구 원화(환율·수수료 차이)라 서로 다르지만 같은 구매다. 운영 168쌍은 전부 승인 원본이 먼저 들어왔고, 기존 코드라면 수입 순서 때문에 승인금액이 남고 실제 청구 총액이 충돌로 빠진다(SRC-005·SRC-009 위반).

## B1 — 정본 방향 (수입 순서와 무관하게 청구 총액이 정본)

**수입 코드.** `app/normalize.py`의 `normalize_approval_number`(앞자리 0 제거, 전체 0·공백은 빈 키)로 비교하되 **저장 원문은 바꾸지 않는다.** `existing_purchase`가 정규화 키(`LTRIM(approval_number,'0')`)로 비교하고 `headered`+`하나`를 교차 뷰 매칭에 포함한다(다른 발급사 `headered`는 제외). 금액 배수 가드(0.5~2.0배)로 승인번호 재사용에 따른 서로 다른 구매가 잘못 합쳐지지 않게 한다. 여기에 `acquired_supersedes_approval`을 더해, **해외 매입 뷰(`hana_foreign`)가 승인 출처(`headered`)를 수입 순서와 무관하게 정본으로 대체**한다. 승인 원본이 먼저 들어와도 청구 총액 행이 정본으로 남고 승인 행이 그 중복으로 표시된다. 국내 매입(`hana_usage`)은 이 대체를 적용하지 않아 기존 가맹점번호 원본 충돌 보호를 그대로 유지한다.

**정리 도구.** `app/card_hana_duplicate_repair.py` (`python -m app.card_hana_duplicate_repair`). 카드 원본 행을 삭제하지 않고 기존 `duplicate_of` 구조로 **승인 출처 행을 매입(청구 총액) 행의 중복으로 표시**하며, 열린 분기는 그 행의 장부·화면 투영만 제거해 한 번만 합산한다. 어느 쪽이 먼저 장부되었든 남는 행은 항상 청구 총액 쪽이다(SRC-005·SRC-009). 이미 장부에 기록된 쪽이 승인 원본이어도 정본(청구) 쪽을 남기고 다른 쪽을 중복으로 표시한다. 남는 행이 귀속·항목을 이어받는지는 기존 장부 기록 규칙(`closed_period_repair`)대로 처리한다:

- **귀속 불일치 보호(`ATTRIBUTION_DISAGREEMENT`).** 두 행이 서로 다른 여행으로 귀속되어 있으면(기간이 겹치는 여행 등) 조용히 재귀속하지 않고 보존한다. 기존 닫힌 분기 수리의 `PROJECTION_ATTRIBUTION_DISAGREEMENT`와 같은 기준이다.
- **장부 이동(`move`).** 정본(청구) 행이 아직 장부되지 않았고 승인 행이 장부되어 있으면, 승인 행의 귀속·항목을 정본 행이 이어받고 청구 총액으로 장부·화면 투영을 옮긴 뒤 승인 행 투영을 제거한다. 정본 행이 이미 장부되어 있으면 승인 행 투영만 제거(`unbook`)한다.
- 닫힌 분기(2025·2026 Q1·Q2, 세무사 제출 완료)는 표시만 하고 장부 금액을 바꾸지 않는다. 환불 짝·수동 교정·원본 보호 쌍은 옮기지 않고 사유별로 보고한다.

구조는 `closed_period_repair`와 같이 미리보기/digest/신선 백업·복원 게이트/단일 작성자 확인/감사 원복/재실행 변경0.

## B2 — writer 정지 게이트가 실제 라우트 포트를 검사

`tools/complete_card_classification.py`에 `ledger_route_port(host)`를 추가해 `D:/WebLedgerHost/config/ledger-route.json`의 `port`를 읽는다. 파일이 없거나(`ROUTE_REQUIRED`) `paused`이거나(`ROUTE_PAUSED`) 포트가 8751·8752가 아니면(`ROUTE_PORT_INVALID`) 실패로 멈춘다. 공통 헬퍼 `require_offline_backup`이 마지막에 `require_writers_offline(ledger_route_port(host))`를 호출하므로, 이 헬퍼를 쓰는 도구가 모두 실제 라우트 포트를 검사한다(8751 고정 해제). 격리 사본(`isolated_copy=True`)은 writer 게이트 전에 반환하므로 사본 예행·테스트에는 영향이 없다. `tools/import_kb_card_download.py`는 이미 라우트 포트를 읽는 자체 게이트를 갖고 있어 동작이 그대로다. 테스트: 라우트가 8752일 때 8752 리스너가 있으면 거부, 파일 없음·paused 실패.

## B3 — 남아 있던 이중 기록 처리

- **(가) 금액 배수가 다른 거래.** 같은 가맹점·카드·날짜·정규화 승인번호가 일치하면 금액이 달라도 같은 구매(해외 주유 선승인→최종 청구 패턴)로 보고 청구 총액 쪽을 남긴다. **단, 승인번호가 정규화 후 일치할 때만** 합친다. 규칙집(`docs/policy/source.md`)에 주유 선승인 패턴은 **없어서 새로 만들지 않았고** 이 사실만 보고한다. 금액 배수이면서 가맹점도 다른 쌍은 보수적으로 보존(`MERCHANT_MISMATCH`)한다.
- **(나) 가맹점 표기만 다른 거래.** 정규화 승인번호·카드·날짜·금액이 일치하고 가맹점 표기만 다른(환율 정상 범위) 쌍은 같은 구매로 정리 대상에 넣는다.
- **(다) 수동 교정.** 수동 교정이 있는 쌍은 보존하되 보고서에 **'AI 검수자가 판단할 건'**으로 남긴다(자동으로 합치지 않음).

## 운영 반영 명령 (헤드 세션 수행)

병합·배포·운영 반영은 이 작업에서 하지 않았다. **운영 반영 순서는 AI 검수 교정(#829)을 먼저 반영한 뒤 이 정리다.** 교정 반영 뒤에는 미리보기부터 다시 계산한다(위 재계산 확인). 운영 반영은 단일 작성자 정지 후 신선 백업·복원 검증 증거를 갖추고:

```
python -m app.card_hana_duplicate_repair --host-root D:/WebLedgerHost --request-id hana-double-import-20261113
python -m app.card_hana_duplicate_repair --host-root D:/WebLedgerHost --request-id hana-double-import-20261113 --apply --expected-digest <미리보기 digest> --backup-evidence <신선 증거 JSON>
```

원복은 `--restore`(미리보기) 후 `--restore --apply --expected-digest <원복 digest> --backup-evidence <신선 증거>`. 사본 예행 산출물은 `D:/WebLedgerHost/data/backups/hana-double-import-20261113/v2/`에 있다.
