# 웹 장부 앱 상세 명세 초안

상태: 설계 검토 중
작성일: 2026-09-21
최종 설계 정리: 2026-09-24
구현 상태: 합성 구현 일부 존재. Phase 2~4 보완 필요, Phase 5는 격리 공간 초안. 완료 판정은 [구현 검토](WEB_LEDGER_IMPLEMENTATION_REVIEW.md)를 따른다.

후속 확정: 탭 삭제·직전 행 수정 되돌리기·입금 분할·작성 정보·자유 이름 편집·수동 보관은 [후속 명세 8~14절](WEB_LEDGER_SPEC_REFINEMENT.md)과 결정 등록부의 후속 결정을 적용한다. 13절은 기능 간 교차 동작의 기술 계약이다. 이 문서는 제품 요구이며 구현 완료 보고가 아니다.

API·증분 처리·로컬 Muse 연결·출력·성능과 수용 시나리오는 [구현·검증 계약](WEB_LEDGER_IMPLEMENTATION_CONTRACT.md)에 정의한다. 확정된 사용자 선택과 미정 항목을 구별한다.

## 1. 목적과 확정된 방향

이 앱은 구글 스프레드시트를 읽고 다시 만드는 보조 도구가 아니라, 비용과 수입 장부를 직접 보고 행 단위로 고치는 기준 화면이다. 같은 저장 결과를 화면과 선택한 탭의 xlsx가 함께 소비한다.

현재까지 사용자가 확정한 방향은 다음과 같다.

- 입력과 수정 권한은 사용자 한 명에게만 둔다.
- 가이드와 직원은 조회만 할 수 있다.
- 사용자는 비용·수입 자료를 회사 기밀로 보지 않는다. 로그인한 직원과 가이드는 담당 여행만 조회하고, 포트폴리오는 운영 자료와 분리한 예시 데이터로 공개한다.
- 웹앱을 기준 장부로 삼고, 구글 스프레드시트와 양방향 동기화하지 않는다.
- 사용자는 행 단위로 편집한 뒤 저장한다.
- 카드 내역 파일을 웹앱에서 직접 올린다. 기존 파이프라인의 후보 결과까지 자동 배치에 사용하며, 분류 가능한 행은 행별 승인 없이 해당 여행 탭에 바로 삽입한다. 배정할 수 없는 행만 `분류대기`에 모은다.
- 기본 장부는 자동분류·후보 배지나 색상 구분 없이 일반 행으로 표시한다. 후보 여부·근거·변경 이력은 DB에 유지하고 행 상세에서 확인한다.
- 규칙 변경은 영향 행 미리보기 후 `기존 행에 적용`과 `앞으로 들어올 행에 적용`을 독립적으로 선택한다.
- 규칙 조건의 기본값은 정규화 가맹점·카드 종류·거래 방향이다. 금액·기간은 필요할 때 추가한다. 이는 분류 조건이지 거래 중복 판정 키가 아니다.
- 규칙 질문은 상황에 맞춰 1~5개를 묻고 필요한 답을 얻으면 멈춘다. 이미 답한 내용을 다시 묻지 않는다.
- 카드 원천의 금액과 날짜는 사용자가 고칠 수 없다. 사용자가 고칠 수 있는 업무 값은 여행 배정, 항목, 내용, 메모로 제한한다.
- 사용자가 행을 저장할 때 `예외 사항` 또는 `규칙 변경`을 반드시 구분한다. 규칙 변경은 새 규칙 버전과 적용 범위를 가진다.
- 규칙 변경을 작성하는 동안 로컬 PC의 Muse Spark 1.3 Free와 대화하는 보조 패널을 제공한다. Muse의 제안은 자동 적용하지 않고, 사용자가 미리보기와 적용 범위를 확인한 뒤 저장한다.
- 왼쪽에는 날짜와 행선지를 초기 이름으로 사용하는 세로 탭을 두고, 표시 이름 전체를 자유롭게 바꿀 수 있다.
- 선택한 탭의 현재 장부 내용을 한 xlsx 파일의 여러 시트로 출력한다.
- 직원·가이드의 담당 여행 조회 권한은 예약 시스템의 가이드 배정 정보를 연동한다.
- Gemini는 등록한 API 키의 설정과 무료 한도를 따른다. 앱에 별도 유료 예산을 두거나 자동으로 유료 전환하지 않는다. 한도 소진 시 AI 대화만 대기한다.
- 화면은 토스의 제품 경험에서 보이는 짧은 문장, 큰 핵심 숫자, 가벼운 표면, 명확한 상태 표시, 빠른 피드백을 참고한다. 토스의 로고·전용 아이콘·내부 자산을 복제하지 않는다.
- 로컬 PC가 꺼져도 장부 조회·수정·카드 업로드는 계속 가능해야 한다. Muse가 연결되지 않으면 설정된 Gemini를 웹앱 서버에서 호출한다. Gemini도 사용할 수 없을 때만 AI 대화가 대기한다.
- 수입은 기본적으로 입금 한 건마다 한 행이며 사용자가 분할한 입금은 배분별 행으로 표시한다. 고객별 합계는 별도 요약으로 표시한다.
- 수입은 직접 입력과 은행 입금 파일 업로드를 함께 지원한다. 직원·가이드의 xlsx 다운로드는 허용하지 않으며, 여행 종료 후에도 담당 권한이 유지되면 화면 조회가 가능하다.

## 2. 현재 양식의 데이터 계약

기준 템플릿은 저장소의 `ledger/data/ledger_current.xlsx`와 `ledger/data/ledger_latest.xlsx`에 있는 `매출자료 양식_rev` 시트다. 두 파일의 해당 파일 해시는 현재 일치하지만, 운영 입력은 나중에 원본 해시를 다시 봉인해야 한다. Google Drive 최신본을 다시 받지 못한 실행에서는 그 사실과 입력 해시를 기록하고 앱 기준 자료로 승격하지 않는다.

각 여행 탭은 아래 순서를 유지한다.

### 수입 영역

화면과 xlsx의 표시 열은 다음과 같다.

| 표시 열 | 필드 키 | 형식 | 규칙 |
|---|---|---|---|
| 거래일자 | `occurred_on` | 날짜 | 실제 수입 거래일 |
| 이름 | `customer_name` | 문자열 | 모르면 빈칸, 추정하지 않음 |
| 닉네임 | `nickname` | 문자열 | 원문이 없으면 빈칸 |
| 예약금 | `deposit_krw` | 정수 원 | 입금 사건에서 합산. 환불을 양수로 바꾸지 않음 |
| 잔금 | `balance_krw` | 정수 원 | 입금 사건에서 합산. 환불 부호 보존 |
| 추가금 | `additional_krw` | 정수 원 | 입금 사건에서 합산. 거래별 근거 보존 |
| 금액(원) | `total_krw` | 계산값 | 예약금+잔금+추가금 |

수입의 화면 행은 기본적으로 입금 사건 한 건이며 사용자가 분할한 사건에 한해 배분별 행을 표시한다. 각 행은 `income_event_id`, 분할 시 `allocation_id`, `customer_id`, `income_kind(deposit|balance|additional)`, `event_type(receipt|refund|adjustment)`, 거래일, 부호 있는 금액, 원천과 근거를 가진다. 입금 종류와 환불 여부를 별도로 보존한다. 고객별 합계는 별도 요약으로 표시하며 이름·닉네임만으로 행을 합치지 않는다. 동명이인과 여러 입금일을 보존하고, 고객 요약 금액을 입금 행 합계에 다시 더하지 않는다.

수입 입력 경로는 직접 입력과 은행 입금 파일 업로드다. 직접 입력한 사건에 은행 원천을 나중에 연결해도 수입이 두 번 합산되지 않아야 한다. 은행 파일에서 고객·여행·입금 종류를 결정하지 못한 행은 분류대기의 수입 구역에서 연결한다. 동일 금액·입금자명만으로 서로 다른 입금을 합치지 않는다. 구체적인 원천 식별과 중복 처리 기준은 [구현·검증 계약](WEB_LEDGER_IMPLEMENTATION_CONTRACT.md)의 수입 입력 절을 따른다.

### 지출 영역

| 표시 열 | 필드 키 | 형식 | 규칙 |
|---|---|---|---|
| 거래일자 | `occurred_on` | 날짜 | 카드 또는 수기 지출일 |
| 항목 | `item` | 선택 문자열 | 지출 분류. 고객명으로 쓰지 않음 |
| 내용 | `description` | 문자열 | 가맹점·서비스 설명 |
| 기간 | `service_period` | 날짜 범위 또는 빈칸 | 실제 예약·이용기간이 확인된 경우만 입력 |
| 예약번호 | `reservation_no` | 텍스트 | 숫자처럼 변환하거나 앞자리 0을 잃지 않음 |
| 증빙유형 | `evidence_type` | 선택 문자열 | 카드, 영수증, 현금, 메일 등 |
| 금액(원) | `amount_krw` | 정수 원 | 구매·취소·환불의 부호와 이벤트 성격 보존 |

각 탭의 계산값은 다음과 같다.

- 수입 합계 A = 모든 수입 행의 `total_krw` 합계
- 지출 합계 B = 모든 지출 행의 `amount_krw` 합계
- 회사수익인식 = A-B
- 화면은 계산 결과와 함께 계산에 포함된 행 수를 표시한다.
- xlsx에는 원본 양식의 `SUM` 수식을 주입하고, 앱은 동일한 계산을 정수 데이터로 다시 계산해 수식 결과와 비교한다.

## 3. 탭 모델

탭의 보이는 이름과 내부 식별자를 분리한다.

```text
tab_id: stable UUID 또는 stable slug
event_year: 정수
starts_on: YYYY-MM-DD
ends_on: YYYY-MM-DD
destination: 문자열
display_key: 자유 편집 문자열, 초기값은 MMDD_행선지
tab_kind: trip | overhead | closing | other
authority_status: 기존 권위 일정의 근거 상태를 참조
tab_lifecycle: active | archived | deleted
source_sha256: 원천 일정 해시
sort_order: 명시 정렬값
```

위 필드는 논리 책임이다. 표시 이름·보관 상태·일정 권위를 한 필드로 합치지 않는다. 기존 물리 스키마에 대응할 수 있으면 새 테이블을 추가하지 않는다. 권위 일정의 필수 값이 없으면 미확정으로 유지하며, 화면 탭을 만들거나 보관을 해제하는 동작만으로 authoritative가 되지 않는다. 날짜·행선지·권위 원천의 값과 자유 표시 이름은 별도다.

새 탭 추가 화면은 `날짜`, `행선지`를 필수로 받고 내부 `tab_id`를 새로 만든다. 같은 날짜·행선지의 기존 탭이 있으면 새 행을 만들지 않고 기존 탭을 보여 주며, 병합 여부를 자동으로 결정하지 않는다. 종료일은 권위 일정 원천을 따라 입력하며, 숙박의 체크아웃 제외 의미와 행사 마지막 날짜를 혼동하지 않는다.

필수 기본 탭은 여행 탭, `기타비용`, `2025_종결_권위` 같은 기존 권위 탭을 별도 종류로 보존한다. 일반 여행 탭은 내역 처리 방법을 선택한 뒤 논리 삭제할 수 있다. 원천·이력·특수 권위 자료는 보존하며 세부 처리는 후속 명세 8절을 따른다. 일반 여행의 표시 이름은 자유롭게 수정하며 수동 보관·복원은 14절을 따른다. 날짜·행선지 형식은 초기 표시 이름이며 영구적인 이름 제약이 아니다.

왼쪽 탭에는 다음을 표시한다.

- 표시 이름. 초기 이름은 날짜·행선지 형식이며 사용자가 바꾼 이름을 그대로 표시
- 수입 합계와 지출 합계의 짧은 금액
- `분류대기` 탭의 미배정 건수. 여행 탭에는 자동분류·후보 상태 건수를 상시 표시하지 않음
- 현재 선택 표시
- 긴 목록의 위·아래 흐림과 스크롤 위치 표시

## 4. 화면 구조

### 4.0 카드 파일 가져오기 화면

이 화면은 장부 탭 안의 행을 직접 늘리는 기능과 분리한다.

1. 카드 파일 선택: CSV와 XLSX를 우선 지원하고, 카드별 원본 형식은 가져오기 프로필로 관리한다.
2. 파일 봉인: 업로드 즉시 전체 파일 해시, 파일명, 크기, 업로드 시각, 업로더, 감지한 카드 종류를 기록한다.
3. 열 매핑 미리보기: 거래일, 원천 거래 식별자, 금액, 승인·취소 구분, 카드 식별자, 가맹점, 원문 메모를 보여 준다. 필수 열이 없으면 장부에 넣지 않는다.
4. 원천 행 미리보기: 파서가 해석한 행과 해석하지 못한 행을 나눈다. 사용자는 매핑을 수정할 수 있지만 원본 파일과 원본 셀 값은 바뀌지 않는다.
5. 대사 실행: 기존 카드 원천, 예약·증빙·권위 일정과 비교해 `일치`, `후보`, `중복 가능`, `검토필요`, `취소·환불`, `원천 오류`를 표시한다.
6. 기본 분류: 기존 파이프라인이 선택한 여행 대상이 있으면 후보 결과도 포함해 해당 여행 탭에 바로 삽입한다. 후보라는 이유만으로 행별 승인을 요구하거나 분류대기로 보내지 않는다. 기존 상태와 근거 수준은 보존한다.
7. 분류 실패 탭: 대상이 없거나 기존 선택 규칙으로도 목적지를 하나로 정하지 못한 행만 `분류대기`에 모은다. 파싱할 수 없는 행은 `가져오기 오류`에서 원본 행과 오류를 보존한다. 원천 오류를 0원 장부 행으로 바꾸지 않는다.
8. 결과: 삽입된 행마다 원천 파일 해시, 원천 행 키, 대사 실행 ID, 사용한 규칙 버전, 현재 탭을 연결한다.

업로드 직후 자동으로 장부 행을 확정하거나, 같은 금액·날짜만으로 기존 거래를 삭제하지 않는다. 파일을 다시 올리면 파일 해시와 안정 원천 행 키로 중복 여부를 판정하고, 같으면 검증된 재사용 또는 충돌을 표시한다. 자동 분류된 행은 `auto_classified` 상태를 가지며 사용자가 나중에 개별 수정할 수 있다. 자동 분류에 실패한 행만 `분류대기`로 보낸다.

`auto_classified`는 내부 배치 상태다. 후보의 `proposed`나 `held`를 `confirmed`로 바꾸지 않는다. `display_tab_id`와 검증된 회계 배정은 분리하며, 후보 행도 화면의 탭 합계에 포함하되 합계를 외부 전기 권한으로 사용하지 않는다. 이 분리는 새 정규화 체계가 아니라 기존 결제 ID를 참조하는 화면 투영이다. 동률은 Q-SCHEDULE-001의 기존 선택 규칙을 먼저 적용하고 끝까지 동률이면 분류대기에 남긴다.

### 4.0.1 대사 작업 화면

이 화면은 `대사`를 합계만 비교하는 과정으로 표시하지 않는다.

- 왼쪽: 업로드한 카드 원본 행 목록
- 가운데: 자동 분류된 여행 탭의 장부 행과 `분류대기`에 남은 시스템 후보
- 오른쪽: 선택한 행의 원천·근거·변경 이력·수정 도구

각 원본 행은 `0404_에히메에 자동 분류됨`, `여행 일정 근거 없음`, `기존 행과 원천 키가 같음`, `취소 거래로 보류`처럼 한 문장으로 상태를 표시한다. 분류 실패 행은 `분류대기` 탭에서 바로 편집할 수 있고, 원본 날짜·금액은 고정한다.

### 4.0.2 분류대기 탭과 드롭다운 배정

`분류대기` 탭은 숨겨진 오류 목록이 아니라 자동 분류에 실패한 행을 모아 두는 업무 탭이다. 미배정 행을 표로 보여 주고, 행마다 `여행 탭으로 보내기` 드롭다운을 둔다.

- 드롭다운 값은 현재 권위 탭과 `여행_미배정`을 포함한다.
- 사용자가 여행 탭을 고르고 행 저장을 누르면 행을 복사하지 않고 화면 배정 변경 사건을 만든다. 후보 표시 위치 변경만으로 회계 allocation을 생성하지 않는다.
- 화면에서는 분류대기 목록에 이동 대상 링크와 실패 사유를 남기고, 기본 목록에서는 `미배정만` 필터를 제공한다.
- 행 저장 성공 직후 이전·새 탭 집계가 갱신된다. 드롭다운 선택만으로 저장하지 않는다.
- 이번 행의 저장과 규칙 대화는 독립이다. `예외 사항`이면 행만 저장하고, `규칙 변경`이면 같은 변경을 근거로 대화를 연다. 대화를 나중에 이어 가도 행 저장은 유지된다.

이 흐름의 기본 결과는 `모든 행은 보존`, `성공한 행은 자동 여행 탭 배치`, `실패한 행만 사용자가 분류`, `분류 선택은 다음 규칙의 근거가 됨`이다.

### 4.1 상단 전역 영역

- 앱 이름과 현재 기준 데이터 버전
- 탭 검색: 날짜, 행선지, 예약번호, 가맹점, 고객명 검색
- `저장되지 않은 변경 1건`과 마지막 저장 시각
- 읽기 전용 사용자 표시
- 선택 탭 xlsx 출력 버튼
- 도움말과 변경 이력 진입점

저장 버튼은 행 편집 중에는 행 가까이에 두고, 전역 상단에는 저장되지 않은 행 수만 표시한다. 저장 전 페이지 이탈에는 변경을 버리지 않고 확인창을 띄운다.

### 4.2 왼쪽 세로 탭

탭은 고정 폭 사이드바에 세로로 쌓는다. 마우스와 키보드 모두 사용한다. 탭을 선택해도 다른 탭의 미저장 행은 보존하고, 해당 행을 먼저 저장하거나 취소하도록 안내한다.

`+ 탭 추가`를 누르면 날짜, 행선지, 종료일, 탭 종류, 일정 근거를 입력하는 작은 대화창을 연다. 권위 일정 근거가 없는 탭은 자동 확정하지 않고 `needs_review` 상태로 만든다.

### 4.3 본문 장부

선택 탭 본문은 두 개의 명확한 구역으로 나눈다.

1. 상단 `수입 내용`
2. 하단 `지출 내용`

각 구역은 표 헤더를 고정하고 긴 셀은 줄바꿈한다. 금액 열은 오른쪽 정렬, 날짜는 고정 형식, 예약번호는 고정폭 글꼴을 사용한다. 행 높이는 긴 내용에 맞춰 늘어나며, 열 폭을 지나치게 줄여 내용이 사라지지 않게 한다.

기본 표에는 분류 상태 열·점·배지·행 색상을 넣지 않는다. 후보 행과 자동분류 행도 같은 서식의 일반 장부 행으로 표시한다. 사용자가 행 상세를 열면 원천, 후보 여부, 적용 규칙과 변경 이력을 볼 수 있다. 저장 실패와 편집 충돌은 해당 작업 위치에 즉시 표시한다. 분류 상태 숨김 때문에 저장 실패까지 숨기지 않는다.

### 4.4 행 편집

행 오른쪽의 `편집`을 누르면 해당 행만 편집 모드로 바뀐다. 셀 전체를 즉시 저장하지 않는다.

카드 원천 행에 대해 다음 필드는 읽기 전용이다.

- 카드 원천 거래일
- 카드 원천 금액과 부호
- 카드 원천 안정 식별자
- 카드 원천 가맹점 원문
- 업로드 파일과 원본 행 위치

다음 필드만 수정 가능하다.

- 여행 배정(`allocation_target`)
- 항목(`item`)
- 내용(`description`)
- 사용자 메모(`operator_note`)

예약번호, 증빙유형, 이용기간도 카드 원천값처럼 보존이 필요한 필드라면 기본적으로 읽기 전용으로 표시한다. 이 필드까지 수정해야 한다면 별도 결정으로 범위를 넓힌다.

- 카드 날짜는 읽기 전용이다. 직접 입력 수입은 날짜·금액을 편집하고 은행 수입은 원본을 보존한 별도 정정 기록으로 처리한다. 카드에 없는 현금·계좌이체 지출은 직접 추가하고 날짜·금액도 편집하되 이력을 보존한다.
- 금액은 천 단위 구분을 화면에만 표시하고 저장값은 정수로 보존한다.
- 예약번호는 문자열로 저장한다.
- 항목과 증빙유형은 허용 목록과 자유 입력을 구분한다.
- 기간은 시작일·종료일·종료 의미를 함께 저장한다.
- `저장`, `취소`, `변경 전 보기`를 제공한다.
- 저장 전에 행 단위 검증 결과를 보여 준다.
- 저장 성공 뒤 즉시 합계·상태·변경 이력을 갱신한다.
- 자동분류된 여행 탭 행의 여행 배정·항목·내용·메모를 바꾸면 저장 이유를 `단순 예외`와 `앞으로의 규칙 변경` 중에서 고르게 한다. 단순 오탈자 수정처럼 규칙과 관계없는 변경은 질문을 줄인다.

### 4.5 상세 화면 동작 계약

아래 수치는 구현용 초안이다. 토스의 공식 컴포넌트 사양이라고 주장하지 않는다. 화면에서 분류 상태를 숨긴다는 확정 요구를 우선한다.

| 영역 | 구현 기준 |
|---|---|
| 기본 화면 | 밝은 중립 배경, 흰 본문, 파란 주요 동작, 본문 글자 14~16px, 과도한 그림자·장식 없음 |
| 왼쪽 여행 목록 | 데스크톱 약 240px, 연도·월 묶음, 날짜·행선지 검색, 선택 탭만 명확히 강조 |
| 상단 | 여행명·명시 시작/종료일, 카드 업로드, 선택 탭 출력. 해시·모델·DB 용어는 기본 화면에 넣지 않음 |
| 합계 | 수입·지출·차액을 숫자로 표시. 고객별 요약 합계를 다시 더하지 않음 |
| 장부 표 | 수입 위·지출 아래, 두 구역 사이 바로 이동 링크. 한 구역이 길어도 다른 구역에 쉽게 접근 |
| 수입 행 | 거래일·이름·닉네임·예약금·잔금·추가금·금액. 기본은 한 입금 사건이 한 행이며 분할한 입금은 배분별 행 |
| 고객별 합계 | 수입 구역의 별도 펼침 영역. stable customer_id로 묶고 원래 입금 행으로 이동 가능 |
| 지출 행 | 거래일·항목·내용·기간·예약번호·증빙유형·금액. 분류 배지·색상 없음 |
| 행 상세 | 오른쪽 약 420px 패널. 원천·분류 근거·변경 이력. 긴 자료는 패널 안에서 펼침 |
| 규칙 대화 | 행 상세에서 전환. 원래 행이 무엇인지 항상 보이고 대화 중에도 장부로 돌아갈 수 있음 |

행 편집은 더블 클릭 또는 편집 버튼으로 시작한다. Tab은 편집 가능한 칸 사이를 이동하고, 카드 날짜·금액은 건너뛴다. Escape는 현재 편집 취소이며 이미 저장한 값을 되돌리지 않는다. 한국어 입력 조합 중 Enter를 저장으로 처리하지 않는다. Ctrl+Enter는 행 저장으로 제공하되 저장 버튼도 유지한다.

붙여넣기는 편집 가능한 칸에만 허용한다. 잠긴 날짜·금액을 포함한 다중 셀 붙여넣기를 일부만 조용히 적용하지 않는다. 첫 버전의 대량 붙여넣기는 범위와 변경 미리보기를 정의한 뒤 추가하며, 기본 행 저장에 필수로 넣지 않는다.

모바일에서는 왼쪽 목록을 여행 선택 메뉴로 바꾸고 행 상세는 전체 화면으로 연다. 작은 화면에서 열을 삭제하지 말고 수평 스크롤이나 상세 펼침을 제공한다. 역할별 권한 안에서 PC와 동일한 편집·업로드·규칙 대화·출력을 지원한다.

### 4.6 화면별 빈 상태·실패·복구

| 상황 | 보여 줄 내용과 동작 |
|---|---|
| 여행 없음 | `여행 탭을 추가해 주세요`와 탭 추가. owner에게만 추가 버튼 노출 |
| 수입 없음 | `아직 입력한 입금이 없어요`와 수입 추가. 0원 입금 사건을 자동 생성하지 않음 |
| 지출 없음 | `아직 연결된 지출이 없어요`와 카드 업로드 |
| 분류대기 없음 | `분류를 기다리는 내역이 없어요`. 전체 장부가 회계적으로 확정됐다는 표현은 쓰지 않음 |
| 저장 중 | 해당 행의 저장 동작만 잠그고 다른 탭 조회는 유지 |
| 저장 실패 | 편집값 유지, 같은 요청으로 재시도. 성공 토스트를 먼저 띄우지 않음 |
| 다른 창에서 변경됨 | 현재 서버값과 내 수정값 비교, 임의 마지막 저장 우선 처리 금지 |
| 업로드 중 이동 | 작업은 서버에서 계속하고 재접속하면 동일 작업 진행을 표시 |
| 일부 파일 행 오류 | 정상 결과는 보여 주고 실패 원본 행·이유·다시 가져오기 경로 제공 |
| AI 연결 끊김 | Gemini 전환을 AI 패널에만 표시. 키가 없거나 대체도 실패하면 장부 업무는 유지하고 대화 재시도 제공 |
| 출력 실패 | 기존 출력 보존, 실패한 작업의 사유와 재시도 표시 |

### 4.7 규칙 대화의 구체적인 예시

아래는 합성 예시이며 실제 회사 거래를 모델에 전달하는 프롬프트가 아니다.

1. 사용자가 분류대기 행을 `0410_예시여행`으로 보내고 `규칙 변경`으로 저장한다.
2. 앱은 이번 행 이동을 저장하고 Muse 또는 Gemini에게 허용된 행 속성과 기존 규칙을 전달한다.
3. AI가 `이번 여행에만 해당하나요, 항목 분류를 앞으로도 적용할까요?`처럼 아직 모르는 범위를 묻는다. 이미 답한 금액·기간 조건은 다시 묻지 않는다.
4. 사용자의 답변으로 서버가 규칙 초안을 검사하고 기존 행의 실제 영향 목록을 계산한다.
5. 화면에 `기존 행 6건 변경, 직접 수정한 2건 제외`처럼 서버 계산값을 보여 준다. 예시 숫자를 실제 결과로 사용하지 않는다.
6. 사용자는 기존 행 적용과 미래 입력 적용을 각각 선택해 한 번 확정한다. 확정 후 같은 규칙을 매 거래마다 다시 승인하지 않는다.
7. 다른 제공자로 전환돼도 현재 질문·사용자 답변·규칙 초안·영향 미리보기 참조가 이어진다. 새 모델이 기존 답변을 덮어쓰는 것은 새 제안으로만 취급한다.

## 5. 대사 확인 경험

사용자가 최종 파일을 기다리지 않고 중간 변경을 바로 확인할 수 있어야 한다.

행을 선택하면 오른쪽 패널을 연다. 패널은 다음 순서로 보여 준다.

1. 현재 장부값
2. 원천값
3. 마지막 계산·대사 제안
4. 사용자가 저장한 변경 전후
5. 근거 파일·행·해시
6. 이 행이 합계와 회사수익인식에 미치는 변화
7. 다음 조치: 유지, 수정, 검토 대기, 제안 반영

원천값이 없는 수기 입력은 `원천 없음`으로 표시한다. 이 표시는 오류가 아니라 근거 수준이다. 예약번호·이용기간·여행 배정이 필요한 행은 근거가 없을 때 `검토필요`로 남긴다.

변경 비교 화면에는 필드별로 `이전 값 → 새 값`, 변경자, 변경 시각, 변경 이유, 관련 증거를 표시한다. 숫자 한 필드가 바뀌면 A, B, 회사수익인식의 전후 값도 함께 보여 준다.

## 6. 저장과 감사 모델

기존 append-only 변경 원장과 `ledger_change_events`를 재사용한다. 기존 원천 행을 직접 고치지 않는다. 아래는 논리적 책임 목록이며 테이블을 모두 새로 복제하라는 뜻이 아니다. 실제 연결 경계는 구현·검증 계약 1절을 따른다.

구현자는 아래 투영 테이블을 추가할 수 있지만, 기존 비용 원천·권위 일정·분류 테이블과 식별자를 새로 복제하지 않는다.

- `ledger_tabs`: 탭 메타데이터와 권위 일정 연결
- `ledger_rows`: 현재 화면에 보이는 수입·지출 행의 typed projection
- `ledger_row_revisions`: 저장 때마다 이전·새 값의 정규화 JSON과 의미 해시
- `ledger_edit_events`: append-only 사용자·에이전트 변경 사건
- `ledger_export_jobs`: 선택 탭, 입력 의미 해시, 템플릿 해시, 출력 파일 해시와 상태
- `card_import_batches`: 업로드 파일 해시, 파일 종류, 파싱 프로필, 업로드 상태
- `card_import_rows`: 파일 해시와 안정 원천 행 키, 원본 값, 파싱 값, 파싱 오류
- `reconciliation_runs`: 대사 실행의 원천 범위, 규칙 버전, 결과 의미 해시
- `reconciliation_candidates`: 원천 행과 탭·장부 행 후보의 관계, 상태, 근거, 사용자 배정 상태
- `classification_learning_cases`: 사용자가 분류대기 또는 여행 탭의 행을 수정한 내용과 당시 입력·근거
- `classification_rule_versions`: 조건, 적용 범위, 우선순위, 상태, 사용자 확정 시각
- `classification_rule_matches`: 규칙이 어떤 원천 행에 제안 또는 적용되었는지

필수 키와 제약은 다음과 같다.

- 같은 `tab_id`와 `row_id`는 한 현재 행만 가진다.
- 수정은 `expected_revision`을 요구한다. 다른 저장이 먼저 일어나면 덮어쓰지 않고 `EDIT_CONFLICT`를 반환한다.
- `client_request_id`는 중복 저장을 막는다.
- 삭제는 물리 삭제가 아니라 `voided` 사건으로 남긴다.
- 모든 저장은 원본 행, 변경 행, 실행 시각, actor, 근거, schema version을 기록한다.
- 행 의미 해시는 실행 시각을 제외한 모든 업무 필드를 포함한다.
- 저장이 성공하면 화면의 현재 projection과 감사 원장을 한 트랜잭션으로 갱신한다.
- 사용자의 드롭다운 배정은 `classification_learning_cases`에 기록한다. 이는 모델 재훈련이 아니라 검증 가능한 규칙 근거다.
- 사용자가 직접 배정한 행은 해당 원천 행에 대한 수동 고정값으로 우선한다. 이후 규칙이 바뀌어도 수동 고정값을 덮어쓰지 않으며, 규칙 적용 미리보기에서 `수동 고정으로 제외`라고 표시한다.
- 같은 원천 행을 다른 탭으로 다시 보내려면 기존 배정 사건을 삭제하지 않고 새 사건과 변경 이유를 기록한다.

## 7. 권한과 공개 범위

역할은 최소 두 개다.

| 역할 | 조회 | 검색 | 행 수정 | 탭 추가 | xlsx 출력 | 이력 보기 |
|---|---:|---:|---:|---:|---:|---:|
| `owner` | 가능 | 가능 | 가능 | 가능 | 가능 | 전체 |
| `viewer` | 담당 여행 | 담당 여행 | 불가 | 불가 | 불가 | 불가 |

viewer의 모든 조회·검색·고객별 합계는 담당 여행 범위 안으로 제한한다. 다른 탭의 ID를 직접 요청해도 서버에서 거부하며, 탭을 화면에서 숨기는 것만으로 권한을 처리하지 않는다.

직원·대장은 담당 여행의 고객 이름·닉네임·예약번호와 해당 여행 증빙까지 조회한다. 내부 메모·수정 이력·AI 대화는 API 응답에서도 제외한다. 원본 카드·은행 파일 전체는 제공하지 않는다. 다른 여행 정보가 섞인 증빙은 해당 범위만 분리한 자료를 제공하며 안전한 분리가 안 되면 원본 전체를 노출하지 않는다.

휴대폰도 PC와 동일한 업무 기능을 지원한다. owner는 모바일에서 입력·수정·파일 업로드·규칙 대화·xlsx 출력을 사용한다. viewer는 모바일에서도 허용된 조회만 사용한다. 화면 배치는 바꾸되 기능을 조회 전용으로 축소하지 않는다. 구체적인 작은 화면 동작은 [상세 동작 계약](WEB_LEDGER_DETAILED_CONTRACT.md)의 모바일 절을 따른다.

본인만 쓰고 직원·가이드는 조회한다는 권한 구분이 확정이다. 담당 여행은 예약 시스템의 가이드 배정을 연동하며, 로그인한 사용자와 예약 시스템의 담당자 식별자를 명시적으로 연결한다. 닉네임이 비슷하거나 여행 제목에 닉네임이 있다는 이유로 조회 권한을 주지 않는다. xlsx 출력과 다운로드는 본인만 가능하다. 여행 종료 후에도 담당 권한이 유지되면 직원 조회를 허용하며 담당 해제·계정 비활성화 시 접근을 종료한다. 포트폴리오는 운영 DB와 분리한 예시 데이터만 공개한다. 모델 키와 DB 자격 증명은 브라우저에 노출하지 않는다.

## 8. xlsx 선택 출력

상단 버튼을 누르면 `선택 탭 출력` 대화창을 연다.

- 현재 탭만 선택
- 여러 탭을 체크해 한 파일로 선택
- 탭 순서 미리보기
- 템플릿 버전과 입력 스냅샷 해시 표시
- `검토필요`와 `충돌` 행 수 표시
- 출력 파일명에 선택 범위와 버전 포함

확정된 출력 방식은 선택한 탭의 현재 장부 내용을 한 xlsx 파일의 여러 시트에 담는 것이다. 각 탭은 `매출자료 양식_rev`의 구조·서식·병합·인쇄 영역을 복제하고 값과 수식만 주입한다. 행 범위를 벗어나는 경우 자동으로 새 행을 만들되, 템플릿 서식을 복제하고 변경 기록을 남긴다.

구현 기준: 출력 버튼을 누른 시점의 저장된 장부 버전을 고정한다. 저장하지 않은 편집이 있으면 `저장 후 출력` 또는 `돌아가기`를 제공하며 변경을 조용히 누락하지 않는다. 화면의 현재 내용은 스크롤에 보이는 일부 행이 아니라 선택 탭의 전체 장부 행이다. 검색·필터로 일부 행이 숨겨져 있으면 출력 범위에 전체 행이 포함된다는 안내와 행 수를 보여 준다. 후보 행의 화면 배정과 사용자의 저장된 수정도 그대로 출력하며, 출력하려고 전체 대사를 다시 실행하지 않는다.

출력은 임시 파일로 만들고 다음을 검증한 뒤 새 버전 파일로 확정한다.

1. 선택 탭 수와 출력 탭 수 일치
2. 수입·지출 헤더와 필드 위치 일치
3. 행별 금액·부호·예약번호·기간 보존
4. A, B, 회사수익인식 재계산 일치
5. 입력 의미 해시와 출력 manifest 저장
6. 기존 파일을 덮어쓰지 않음

외부 전기나 게시 권한은 xlsx 출력 성공만으로 생기지 않는다. 권위 일정·대사 관계가 미확정인 행도 화면의 현재 내용대로 출력한다. 미확정 건수와 안내는 출력 대화창에 표시하며 xlsx에 별도 상태 배지·안내 시트를 추가하지 않는다. 이 선택은 읽기 오류로 금액 자체가 없는 행을 만들어 내거나 저장 충돌 중인 초안을 출력하라는 뜻이 아니다. 출력 대상은 저장된 장부이며 후보·보류 상태와 release_eligible은 유지한다.

## 9. 상태와 즉시 수정 흐름

아래 상태는 DB와 행 상세에서 구분한다. 기본 장부 표에는 분류 상태를 노출하지 않는다. 저장 중·실패·충돌 안내는 유지한다.

- `저장됨`: 마지막 행 저장 성공
- `저장 안 됨`: 편집 중
- `분류대기`: 기존 규칙으로 여행 탭을 정하지 못함
- `자동분류`: 기존 규칙으로 여행 탭을 먼저 정함. 사용자 수정 가능
- `충돌`: 다른 버전과 저장 충돌
- `제안`: 에이전트가 만든 후보
- `사용자 수정`: 사용자가 행을 저장한 사실. 원천 관계나 회계 확정과 별개
- `확정`: 해당 업무 축의 근거와 확정 조건이 충족된 값. 화면 배치와 동일하지 않음
- `출력 가능`: 선택한 출력 범위의 구조 검증 통과
- `전기 가능`: 별도 전기 게이트 통과. 화면의 출력 가능과 같은 뜻이 아님

행 수정은 후보를 자동 확정하지 않는다. 정상적으로 읽힌 카드 행은 기존 규칙으로 먼저 분류하고, 실패한 행만 `분류대기` 탭에 보존한다. 사용자가 분류대기 행의 드롭다운으로 여행 탭을 선택하면 배정 사건을 기록하고, 해당 행의 분류 규칙을 만들지 묻는다.

### 9.1 사용자의 배정에서 규칙을 만드는 흐름

분류대기 행을 드롭다운으로 특정 탭으로 보내거나 자동분류된 여행 탭 행을 분류 관련 필드에서 수정하면 앱은 다음 질문을 상황에 맞춰 최대 다섯 개까지 보여 준다.

1. `이번 행에만 적용할까요, 앞으로 같은 조건에도 적용할까요?`
2. `어떤 조건의 행에 같은 분류를 적용할까요?` — 정규화 가맹점·카드 종류·거래 방향이 기본이며 금액·기간은 필요할 때 추가
3. `기존 행과 앞으로 들어올 행 중 어디에 적용할까요?` — 두 범위를 별도 선택
4. `예외를 둘 조건이 있나요?` — 취소·환불, 특정 기간, 특정 탭 등
5. `이 변경은 예외 사항인가요, 규칙 변경인가요?`

질문 답변은 `classification_learning_cases`에 근거로 저장한다. 규칙 변경을 선택한 경우에만 새 `classification_rule_version`을 만들며, 기존 행과 앞으로 들어올 행에 적용할지 별도로 선택한다. Muse는 이 질문을 이해하기 쉬운 문장으로 만들고 반례와 영향 건수를 제안하지만, 사용자의 답변과 적용 버튼 없이 규칙을 저장하거나 장부를 재분류하지 않는다.

위 다섯 문장은 질문 후보이며 고정 순서의 필수 설문이 아니다. 예외·규칙 변경 선택을 이미 답했으면 반복하지 않는다. 영향 행 수와 합계 변화는 Muse의 추정이 아니라 서버가 실제 규칙을 실행해 계산한다.

### 9.1.1 규칙 적용 범위 계약

- 미리보기에는 분류대기뿐 아니라 기존 여행 탭에서 바뀔 행도 포함한다. 이전·새 탭, 항목, 내용, 합계 변화와 수동 고정 제외 건수를 보여 준다.
- `apply_existing`과 `apply_future`는 독립된 선택이다. 어느 조합도 기본 선택만으로 승인 처리하지 않는다.
- 기존 행만 선택하면 해당 미리보기의 행 버전 집합에만 적용하고 이후 업로드에는 활성화하지 않는다.
- 미래 행만 선택하면 확정 이후 새로 들어오는 거래에 규칙을 적용한다. 같은 거래의 재업로드는 새 거래로 취급하지 않는다.
- 둘 다 선택하면 같은 규칙 버전을 기존 선택 행에 적용하고 미래 입력에도 활성화한다. 둘 다 선택하지 않으면 초안으로만 보존한다.
- 미리보기에는 규칙 내용 해시와 행 revision을 묶는다. 적용 전에 입력이 바뀌면 바뀐 영향 범위만 다시 보여 준다. 수동 수정은 덮어쓰지 않는다.
- 정규화 가맹점·카드 종류·거래 방향이 같아도 각각의 거래는 보존한다. 분류 조건을 중복 제거에 쓰지 않는다.
- 특정 여행으로 배정하는 규칙에는 대상 여행 ID·연도·적용 범위를 포함한다. 가맹점 기본 조건만으로 미래의 모든 거래를 과거 여행에 보내지 않는다.

### 9.2 Muse 대화 패널

- 현재 선택한 행과 사용자가 방금 선택한 목적지 탭을 고정 문맥으로 보여 준다.
- `왜 이 행을 이 탭으로 보냈나요?`, `같은 가맹점은 앞으로 같은 여행으로 보내`처럼 자연어로 설명할 수 있다.
- 응답은 설명, 규칙 초안, 적용 조건, 예상 영향 행 수, 반례로 나눈다.
- 대화만으로 저장하지 않고 `미리보기`와 `규칙 확정`을 분리한다.
- 호출 모델은 `opencode/muse-spark-1.3-contributor-free`로 고정한다.
- 카드 원문 고객명·예약번호·메일 본문은 기본적으로 Muse 문맥에 보내지 않고, 정규화된 가맹점과 가명·집계값을 사용한다.
- Muse 연결 실패 시 사용자가 등록·활성화한 Gemini fallback으로 같은 대화를 이어 간다. 둘 다 사용할 수 없거나 응답이 유효하지 않으면 이번 행 수정은 저장하고 AI 규칙 초안 생성만 대기한다.

### 9.3 AI 연결 설정과 문맥 유지

owner는 `설정 → AI 연결`에서 Gemini API 키 등록·교체·삭제, 사용 가능한 모델 선택, fallback 활성화를 할 수 있다. 키는 서버 비밀 저장소에 보관하고 브라우저 저장 공간·로그·채팅에는 남기지 않는다. PC가 꺼져도 Gemini 호출에 필요한 키와 대화 문맥은 웹앱 서버에서 사용할 수 있어야 한다.

대화 문맥과 확정 규칙은 앱 DB에 보존한다. 모델이 바뀌면 관련 규칙, 현재 행, 답변한 질문과 미해결 질문을 다시 전달한다. 제공자 내부 기억이나 모델 학습이 이전되는 것은 아니다. 확정된 규칙의 실행은 일반 코드가 담당하고 모델은 새 규칙 제안과 질문만 보조한다. 실제 provider 전환은 AI 패널에 표시한다.

## 10. API 계약 초안

아래는 API 개요다. 구체적인 요청·오류·재시도는 [상세 동작 계약](WEB_LEDGER_DETAILED_CONTRACT.md)을 따른다. [단계별 진행표](WEB_LEDGER_PHASES.md)에 따라 합성 화면부터 시작하고 해당 API를 연결하는 단계에서 계약을 검증한다.

- `GET /api/tabs`: 권위 상태, 합계, 검토 건수 포함
- `POST /api/tabs`: 날짜·행선지·권위 근거 검증 후 탭 생성
- `GET /api/tabs/{tab_id}/rows`: 수입·지출 행과 상태, 현재 revision 반환
- 행 편집 초안은 우선 브라우저 상태로 보관한다. 서버의 별도 draft API는 첫 버전 필수가 아니다.
- `POST /api/rows/{row_id}/save`: expected revision, client request id, 변경 이유 필수
- `POST /api/rows/{row_id}/revert`: 해당 행의 직전 수정만 복원하는 새 사건 생성. 임의 과거 revision 선택은 지원 범위가 아님
- `GET /api/rows/{row_id}/lineage`: 원천, 제안, 사용자 수정, 이력 반환
- `POST /api/rows/{row_id}/assign`: 필요하면 행 저장 서비스의 별칭으로 제공. 배정을 저장하며 사용자가 규칙 변경을 선택한 경우에만 대화 사례를 생성
- `POST /api/classification/questions/answer`: 규칙 확정 질문 답변 저장
- `POST /api/classification/rules/preview`: 새 규칙이 현재 미배정 행과 기존 행에 미치는 영향 계산
- `POST /api/classification/rules/apply`: 규칙 버전, preview_id, apply_existing, apply_future, 선택 행 revision, client_request_id로 확인된 범위만 적용
- `POST /api/rules/chat`: Muse에게 규칙 설명·반례·질문 도움을 요청. 장부 쓰기 권한 없음
- `POST /api/exports/xlsx`: 선택 tab ids, template version, unresolved policy를 받아 출력 작업 생성
- `GET /api/exports/{job_id}`: 상태, 파일 해시, manifest, 검증 결과 반환
- `GET /api/audit/changes`: 기간·탭·행·actor 필터 지원

모든 쓰기 API는 요청 중복, revision 충돌, 잘못된 부호, 권위 일정 누락, 권한 부족을 구분된 오류 코드로 반환한다.

## 11. 검증 계획

### 단위 검증

- 수입·지출 필드와 템플릿 열 매핑
- 정수 원화와 예약번호 문자열 보존
- 수입 A, 지출 B, 회사수익인식 계산
- 기간 종료 의미 보존
- 음수 환불을 양수 구매로 바꾸지 않음
- 행 저장의 optimistic concurrency
- 같은 client request의 재호출 멱등성
- 기존 파이프라인의 후보 결과도 승인 절차 없이 해당 여행 탭에 들어가며, 대상이 없거나 선택 불가능한 행만 분류대기에 남음
- 기본 장부에는 분류 상태 배지·색상·열이 없고, 상세에는 기존 후보 상태와 근거가 보존됨
- 후보를 화면에 배치해도 기존 회계 확정 상태와 release_eligible은 자동 승격되지 않음
- 드롭다운 배정이 중복 행을 만들지 않고 탭 링크와 학습 근거를 만듦
- 이번 행만 적용한 예외가 다른 행을 바꾸지 않음
- 규칙 변경 미리보기가 확인 전 장부를 바꾸지 않음
- 규칙 확정 뒤 기존 미배정 행의 영향 목록이 정확히 표시됨
- 카드 날짜와 금액을 바꾸려는 요청이 거부됨

### 통합 검증

- 탭 추가 → 행 추가 → 행 수정 → 이력 확인 → 선택 xlsx 출력
- 한 행 수정 뒤 관계없는 탭과 합계가 변하지 않음
- 두 브라우저에서 같은 행을 저장하면 한 건만 성공하고 다른 쪽은 충돌
- 후보를 포함한 자동 배치와 실패 행의 분류대기를 검증하고, 새 규칙 초안만으로 기존 행을 바꾸지 않음
- 기존만·미래만·둘 다·둘 다 아님의 네 선택을 검증하고 수동 고정 행은 보존함
- xlsx를 다시 읽어 앱 계산값과 행별로 비교
- 출력 중 실패해도 기존 xlsx가 변하지 않음

### 수용 기준

- 사용자가 최종 파일을 만들지 않고도 모든 행의 현재값·원천값·변경 전후·검토 사유를 볼 수 있다.
- 한 행의 수정은 한 행 사건과 해당 탭 합계만 바꾼다.
- 다른 에이전트나 재실행이 같은 행을 중복 생성하지 않는다.
- 앱 화면과 선택 xlsx의 업무 필드·금액·부호가 같다.
- 조회자는 어떠한 쓰기 API도 실행할 수 없다.
- 운영 자료와 공개 포트폴리오 자료가 저장소·데이터베이스·자격 증명 수준에서 분리된다.

## 12. 구현 에이전트 전달 지침

구현자는 이 문서와 `AGENTS.md`, 최신 handoff, `docs/AGENT_EXECUTION_CONTRACT.md`, `docs/DECISION_REGISTER.md`, 현행 양식 원장을 먼저 읽는다. 구현 시작 전에 현재 저장소의 변경 상태를 기록하고, 원본 DB·운영 출력·Google Drive 자료를 덮어쓰지 않는 격리 작업공간에서 작업한다.

구현 순서는 다음과 같다.

1. 현재 webapp의 snapshot·read-only 후보 화면과 새 장부 projection 경계를 확인한다.
2. typed row 계약과 마이그레이션을 합성 fixture로 만든다.
3. 저장·revision·append-only 이력을 먼저 구현한다.
4. 탭과 행 편집 화면을 추가한다.
5. 원천·변경 비교 패널을 추가하고 분류 상태는 행 상세에서만 표시한다.
6. 양식_rev 선택 출력기를 연결한다.
7. 합성 자료 테스트를 통과시킨 뒤, 실제 운영 자료는 읽기 전용 점검만 한다.

구현자는 기존 원천 정규화 체계를 새로 복제하지 않고 기존 direct source·projection·authority를 재사용한다. 자동 확정, 외부 전기, 원본 덮어쓰기, 미확인 일정의 사후 보정은 범위 밖이다.

## 13. 남은 사용자 선택

아래 항목은 구현자가 임의로 정하지 않는다. 사용자의 답변을 결정 등록부에 기록한 뒤 명세의 기본값을 확정한다.

| 미결 항목 | 현재 상태 | 영향을 받는 단계 |
|---|---|---|
| 상시 서버 운영비 기준 | 무료 범위로 먼저 시험하고 유료 전환이 필요하면 별도 승인. Gemini 무료 한도와 별개 | Phase 9 운영 환경 |
| 상시 서버 공급자 | 운영비 기준에 맞춰 기존 환경과 후보 비교 후 선택. 실제 배포는 별도 결정 | Phase 9 배포 |

현재 무료 선행 시험안은 [후속 명세 19절](WEB_LEDGER_SPEC_REFINEMENT.md)에 있다. Oracle Always Free VM에서 기존 Python·SQLite를 유지하는 구성은 첫 시험 후보이며 자원 확보·배포 완료를 뜻하지 않는다. 무료 구성의 저장·파일 처리·재개 제약을 검증하고, 충족하지 못한 조건이 있으면 대안과 비용을 보고한다. 유료 전환에는 별도 승인이 필요하다. 18절은 예산 답변 전 비교 이력으로 보존한다.

실제 카드·은행 형식, 최초 이관 기준본의 위치·범위, 예약 API의 현재 제공 필드, 사용 가능한 무료 Gemini 모델은 해당 연결 단계의 입력 확인 항목이다. 합성 구현이나 이미 확정한 업무 정책을 다시 승인받는 항목이 아니다. 원본 자료를 외부 구현 모델에 보내거나 비밀 키를 대화에 입력하도록 요구하지 않는다.

이미 확정된 탭 관리·되돌리기·수입 분할·작성 정보는 후속 명세 8~14절, 권한·증빙과 Google 로그인·직원 신청 후 소유자 승인은 15~16절을 따른다. 직원 증빙은 미리보기만 제공한다. 미확정 안내를 대화창에만 표시하는 출력, 직원의 허용 상세 범위, 모바일 기능, 원천별 편집 정책, Gemini 무료 한도 정책은 재질문하지 않는다. 미결 정책 때문에 독립적인 Phase 1~5 보완을 중단하지 않는다.

## 14. 확정 이력 — 2026-09-21

- 후보 결과까지 여행 탭에 자동 배치한다. 모든 행을 먼저 대기 탭에 넣거나 행별 승인을 요구하는 과거 초안은 폐기한다.
- 분류 상태는 기본 장부에서 숨기고 일반 행처럼 표시한다. 상태는 DB와 행 상세에 보존한다.
- 새 규칙의 영향 행을 먼저 보여 주고 기존 행·미래 입력의 적용 여부를 각각 선택한다.
- 기본 분류 조건은 정규화 가맹점·카드 종류·거래 방향이다. 금액·기간은 추가 조건이다.
- 규칙 질문은 상황별 1~5개이며 답변이 충분하면 멈춘다.
- 직원·가이드는 담당 여행만 조회하고 포트폴리오는 예시 데이터로 분리한다.
- 로컬 PC가 꺼져도 장부 조회·수정·카드 업로드는 가능하게 한다. Muse 연결 불가 시 등록된 Gemini를 서버에서 호출하고 둘 다 불가할 때만 AI 대화를 대기한다.
- 수입은 기본적으로 입금 한 건마다 한 행이며 분할한 입금은 배분별 행으로 표시한다. 고객별 합계는 별도이고 원금을 배분액과 중복 합산하지 않는다.

### 후속 확정 — 2026-09-24 정리

- 사용자가 반복 확인한 `API 한도에 맡김 = 무료한도`와 후속 `내 API 키의 설정과 한도에 맡김`을 함께 적용한다. 별도 유료 예산이나 자동 결제 전환을 승인한 것으로 해석하지 않는다.
- 담당 여행 권한은 예약 시스템의 가이드 배정 정보를 연동한다.
- 선택한 탭의 현재 내용을 한 파일의 여러 시트로 출력한다.
- 수입은 직접 입력과 은행 입금 파일 업로드를 함께 지원한다.
- 직원·가이드는 화면만 조회하고 xlsx 출력·다운로드는 본인만 사용한다.
- 여행 종료 이후에도 담당 권한이 유지되면 조회하며 담당 해제·계정 비활성화 시 접근을 종료한다.
- 직접 입력 수입은 날짜·금액 편집과 이력을 지원한다. 은행 원본은 고정하고 별도 정정 기록을 남긴다.
- 최초 이관은 구글 장부와 DB의 차이만 모아 사용자가 선택한다.
- 미확정 행도 화면대로 xlsx에 넣으며 안내는 출력 대화창에만 표시한다.
- [단계별 진행표](WEB_LEDGER_PHASES.md)에 따라 Phase 0부터 순차 진행하고 중간 결과를 확인한다.
- 이 설계 세션은 명세·검토를 담당한다. 별도 작업자의 합성 구현은 존재하며, 해당 코드의 보완은 구현 검토 문서의 순서를 따른다. 문서 열람만으로 구현·배포 착수를 승인한 것으로 해석하지 않는다.
- 수기 지출 추가와 날짜·금액 편집을 지원하고 이력을 보존한다.
- 직원·대장은 고객 이름·닉네임·예약번호·해당 여행 증빙을 조회한다. 내부 메모·수정 이력·AI 대화는 숨긴다.
- 모바일에서도 역할별 권한을 유지하며 PC와 같은 업무 기능을 지원한다.
