# COST 통합 명세

> **상태:** 정본 (2026-11-10 승인, 2026-11-11 P2 대상·일괄 실행·조직 결정 반영, 2026-11-13 분기 검수의 AI 검수자 위임 반영). 실제 완료 범위는 현재 상태와 작업판을 따른다.
> **이 문서가 하는 일:** COST가 무엇을 하는 시스템인지, 어떤 순서로 무엇을 만들지, 무엇을 지켜야 하는지를 한 곳에 적는다. 과거 명세 112개(`docs/history/specs-20261110/`)와 `docs/history/`의 나머지는 **근거 기록**이며 실행 지시가 아니다. 과거 명세와 이 문서가 다르면 이 문서가 우선한다.
> **짝 문서:** 판정 규칙은 [판정 규칙집](DECISION_POLICY.md), 개발 조직 운영은 [중간 관리자 지침](agents/MANAGER.md), 반복 작업 절차는 [절차서](playbooks/README.md)에 둔다.

## 1. 목적과 성공 기준

### 1.1 목적

여행에 따르는 지출 자료(카드 명세, OTA 메일·포털, 영수증)를 모두 받아 **코드가 먼저 대사·분류하고(P1), 코드가 못 정한 것은 AI가 정한다(P2). 분기마다 AI 검수자가 판정을 다시 보고 교정한다.** 사용자는 처리 흐름 중간에 질문을 받지 않고 건별 판단도 하지 않는다.

### 1.2 사용자의 역할 — 결과 확인과 Google 붙여넣기

- 사용자는 여행사에서 가이드 업무를 뺀 실무 전체를 맡는 결정권자이며 코드를 직접 읽지 않는다.
- **분기 검수의 판단과 교정은 AI 검수자가 한다**(소유자 결정 2026-11-13). 검수자는 Fable 5.2 high 에이전트이며, 쓸 수 없으면 그때의 최상위 Claude 모델이 대신한다. 사용자는 결과를 받아 볼 뿐 건별 판단을 하지 않는다. "먼저 볼 50건" 같은 건별 검토 목록을 사용자에게 주지 않는다(§8).
- 사용자에게 남는 일은 셋뿐이다.
  1. **Google 지출표 붙여넣기.** 검수가 끝난 장부를 기존 복사 기능으로 붙여넣는다. Google 장부에 자동으로 쓰지 않는다.
  2. **로그인·인증 인계.** 카드사 추가 인증, OTA 포털 재로그인은 판정 질문이 아니라 인증 인계다. 수집 스크립트가 로그인 만료를 감지하면 멈추고 상태만 표시한다(§7).
  3. **정책 수준의 새 결정.** 규칙이 없거나 규칙끼리 모순이거나 사업 판단이 필요한 때만, 건별이 아니라 질문 단위로 예시와 함께 받는다. 0건이 목표다.
- 처리 흐름 안에는 **사용자 확인 단계(P3)가 없다.** 질문함·확인 대기·보류 해제 같은 화면과 상태를 만들지 않는다. 판정이 어려운 건도 AI가 근거와 불확실성을 적고 판정을 끝낸다.
- AI 검수자의 교정은 [판정 규칙집](DECISION_POLICY.md) 개정으로 환류한다. **같은 원인의 교정을 두 번 하지 않는 것**이 이 시스템의 품질 기준이다(§8).
- 사용자가 직접 고친 값(수동 교정)은 여전히 모든 자동 판정과 AI 검수 교정보다 우선한다. AI 검수 교정을 사용자 결정으로 기록하지 않는다.
- 영수증 사진 판독 결과는 사용자 요청(2026-11-16)에 따라 원본과 나란히 검수하고 선택한 내역만 COST 장부에 반영한다(§7.1, RCPT-031). 이 등록 전 검수는 카드 자동 판정·분기 AI 검수와 별개다.
- 대체된 옛 내용(2026-11-10~13): 사용자가 분기마다 한 번 최종 검수를 하면서 틀린 판정을 직접 교정했다.

### 1.3 사용자가 받아볼 산출물

1. **여행별 손익** — 여행마다 수입과 지출이 맞춰진 수치.
2. **세무·증빙 자료** — 세무 처리에 넘길 수 있게 정리된 카드·영수증 자료.
3. **직원·가이드 지출 정산** — 직원과 가이드가 쓴 비용의 확인과 정산 자료.

현재 구현 상태와 정의가 비어 있는 부분은 §9에 적는다.

### 1.4 성공 기준

| 구분 | 지표 | 뜻 |
| --- | --- | --- |
| 업무(1순위) | AI 검수자가 고친 건수와 사유별 분포 | 분기 검수에서 AI 검수자가 실제로 고친 건수를 사유(판정 주체·원인)별로 센다. 분기마다 줄어야 한다. 옛 지표 "사용자가 고친 건수와 소요 시간"을 대체한다(2026-11-13) |
| 업무 | 사용자 결정 필요 질문 수 | 분기 검수가 사용자에게 넘긴 정책 질문 수. 0이 목표다 |
| 업무 | 여행 종료 후 손익 수치가 나오기까지 걸린 날 | 지출 판정이 밀리지 않는지 |
| 업무 | 산출물 3종의 준비 상태 | 분기 말에 바로 쓸 수 있는지 |
| 내부(수단) | 판정이 없는 정상 거래 수 | 0이어야 한다 |
| 내부 | P1 처리율, P2 처리율 | P1은 늘고 P2는 줄어야 한다 |
| 내부 | P2 실행 성공률 | 기술적으로 끝까지 도는 비율 |
| 내부 | 수집 지연 | 원천별 마지막 수집일과 오늘의 차이 |

내부 지표가 좋아도 업무 지표가 나쁘면 실패다.

### 1.5 하지 않는 것

- Google 최종 장부에 자동으로 쓰지 않는다. 붙여넣기는 분기 검수가 끝난 뒤 사용자가 한다.
- 사용자의 수동 교정을 자동 판정이 덮지 않는다.
- 카드 원문·금액·ID, 메일 원문, 영수증 원본을 바꾸거나 지우지 않는다.
- 여행을 만들어내지 않는다. 여행은 Google 시트 탭에서만 생긴다.
- 실제 환급 입금이나 Google 반영 사실을 추론으로 만들어내지 않는다.

## 2. 처리 원칙

| 용어 | 뜻 |
| --- | --- |
| P1 | 코드와 데이터형 규칙이 내는 판정. 같은 입력에 항상 같은 결과 |
| P2 | AI 에이전트가 내는 판정. P1이 못 정했거나 약하게 정한 건만 맡는다 |
| 판정 | 지출 1건에 대한 결론: 어느 여행(또는 분기 기타비용)의 어떤 항목인지, 이용기간, 연결된 근거, 누가 정했는지, 근거 문장, 불확실성 |
| 근거 | 판정에 쓴 원천 자료: 카드 원행, 메일 원문, 포털 조회 결과, 영수증, Google 여행 탭 |
| 교정 | 판정을 고치는 것. **수동 교정**은 사용자가 직접 고친 것으로 항상 최우선이다. **AI 검수 교정**은 분기 검수에서 AI 검수자가 고친 것으로, 수동 교정과 금융 보호를 덮지 못한다 |
| 분기 기타비용 | 실제 여행에 귀속할 수 없는 일반 비용의 종착지. 결제일 기준 분기로 나눈다 |

1. **P1을 최대한 늘리고 P2는 줄인다.** P2는 사용자 확인의 대체물이다. P2가 같은 유형을 반복 판정하면 P1 규칙으로 올린다(§6.7).
2. **P2를 0으로 만드는 것은 목표가 아니다.** 한두 번 나오는 사례까지 규칙으로 만들면 공급자별·증상별 패치 반복으로 돌아간다.
3. **모든 정상 거래는 판정을 갖는다.** 근거가 부족하면 최선의 판정과 불확실성을 적는다. "분류 대기"로 남기지 않는다.
4. **판정은 저장된 값이다.** 화면이 그릴 때마다 추론하지 않는다. 화면은 저장된 판정을 읽기만 한다.
5. **증상별 패치를 하지 않는다.** 새 공급자·새 메일 양식을 파서 패치로 쫓지 않고, P2가 원문을 읽어 판정한 뒤 반복되는 것만 규칙·데이터로 올린다.
6. **규칙은 한 곳에만 쓴다.** 판정 규칙의 정본은 [판정 규칙집](DECISION_POLICY.md)이다. 새 지시는 대화로 흘려보내지 않고 규칙집 개정으로 반영한다.

### 3.2 구조

- Python 표준 라이브러리 HTTP 서버가 HTML을 문자열로 만든다. `webapp/`(화면·업무 로직 혼재), `app/`(수집·추출·대사·분류), `tools/`(운영·일회성 스크립트), `tests/`.
- 운영은 이 Windows PC의 `D:\WebLedgerHost`에서 예약 작업 `WebLedger-Board`(8751/8752), `WebLedger-Gateway`(8790), `WebLedger-Worker`로 돈다. 외부 접속은 cloudflared 터널을 거친다.
- 저장은 SQLite 여러 개(`board.sqlite`, `ota-evidence.sqlite` 등)에 테이블 약 130개가 스키마 모듈 10여 개로 흩어져 있다.

### 3.3 목표가 달성되지 않은 원인

1. **P2가 운영에서 한 번도 성공하지 못했다.** 설정은 켜져 있지만(`autonomous_ai_review=true`) 적용 0건이다. 호출 약 1,400회가 전부 실패했고(시간 초과 955, 실행 실패 200, 응답 형식 오류 169, 반영 실패 60), 2,826회는 일일 한도로 차단됐다. 기존 P2(`app/ai_classification.py`와 무료 OpenCode 모델 호출 경로, 이후 PR #860으로 제거)는 무료 모델에게 **가맹점 이름도 원문도 없이** 날짜·국가·후보 여행 목록만 주고 고르게 한다. P1이 못 본 것을 P2도 볼 수 없다.
2. **무엇이 맞는 판정인지 적혀 있지 않았다.** 규칙이 명세 112개와 구두 지시에 흩어져 있어 에이전트가 스스로 검증할 기준이 없었다.
3. **증상을 쫓는 개발.** 2026-11-07~10에 병합된 PR 약 70건의 대부분이 공급자별·증상별 패치와 기록용 문서다.
4. **명세·데이터·코드가 흩어져 있다.** 같은 거래가 `transactions`, `board_rows`, OTA 저장소에 겹쳐 있고, 일부 판정은 화면을 그릴 때 계산된다. main의 테스트는 전부 통과하는 상태가 아니다.

## 4. 판정 모델

### 4.1 판정 한 건의 내용

| 항목 | 내용 |
| --- | --- |
| 대상 | 카드 거래 1건(또는 영수증 1건, 캐시·포인트 사용 1건) |
| 귀속 | 실제 여행 하나, 또는 결제일 기준 분기 기타비용, 또는 전액 환불 쌍 |
| 항목 | 숙박비·항공료·식비 등 비용 항목 |
| 이용기간 | 실제 서비스 이용일(숙박 기간, 탑승일 등). 모르면 비워 두고 그 사실을 적는다 |
| 연결된 근거 | 판정에 쓴 예약·메일·포털 기록·다른 카드 거래의 참조 |
| 판정 주체 | P1(규칙 ID) / P2(실행 ID·모델) / AI 검수(검수 실행 ID·모델) / 수동 교정 |
| 근거 문장 | 왜 이렇게 정했는지 한두 문장 |
| 불확실성 | 확인하지 못한 것 |

### 4.2 판정 주체의 우선순위

수동 교정 > 정확 근거에 의한 P1(예약번호·원승인번호 등) > AI 검수 교정 > P2 > 추론에 의한 P1(업종·날짜 기반 최선 후보).

- P2는 추론에 의한 P1을 고칠 수 있다. 정확 근거에 의한 P1과 수동 교정은 고칠 수 없다.
- AI 검수자는 P2와 추론에 의한 P1을 고칠 수 있다. 수동 교정과 금융 보호는 덮지 않는다. 정확 근거 P1이 틀려 보이면 판정을 덮지 않고 원인(근거 연결·규칙·코드)을 고칠 일로 올린다.
- 낮은 신뢰도는 판정을 미완료로 만들지 않는다. 근거와 불확실성으로만 표시한다.

### 4.3 현 시스템에서의 저장 위치 (M2까지)

새 테이블을 만들지 않고 기존 열을 쓴다.

| 판정 항목 | 저장 위치 |
| --- | --- |
| 귀속·항목 | `transactions.trip_id`, `display_tab_id`, `item` |
| 판정 주체 | `transactions.classification_source` (`ai_inference`가 P2와 AI 검수. AI 검수는 근거 문장과 실행 기록에 `AI 검수`·모델을 적어 구분한다. 사용자 결정 표기 `user_decision`을 쓰지 않는다) |
| 근거 문장·불확실성 | `transactions.classification_basis` |
| P2 실행 기록 | 서버 밖 일괄 작업의 보호 경로에 요청 지문·실행 ID·모델·제안 JSONL·집계. 기존 Board 내장 런타임은 비활성 |
| 교정 이력 | `app/classification_correction.py`가 남기는 변경 전 값과 근거 |

투자 단계(§11)에서 `decisions` 단일 테이블로 옮긴다.


| 수집 | 카드 명세, OTA 메일, OTA 포털, 영수증, Google 여행 탭을 원본 그대로 받는다 | `app/import_card.py`, `app/mail_collect.py`, `app/ota_portal.py`, `app/agoda_capture.py`, `app/google_authority.py` | 없음 (스크립트, §7) |
| 추출 | 원본에서 날짜·금액·예약번호·이용기간을 읽는다 | `app/ota_mail.py`, `app/flight_evidence.py`, `app/import_card.py` | 파서가 못 읽은 메일을 원문에서 직접 읽는다 |
| 연결 | OTA 예약↔카드 결제(M:N), 취소·환불↔원결제 | `app/ota_payments.py`, `app/partial_refund.py`, `app/ota_inference.py` | 연결 근거를 판정의 근거로 제시한다. 정확 연결·환불 짝은 P1만 쓴다 |
| 귀속 | 여행·항목·이용기간을 정한다 | `app/classify.py`, `app/rules.py`, `app/automatic_classification.py`, `app/reconciliation.py` | P1이 못 정했거나 일반 항목으로만 정한 건을 판정한다 |
| 게시 | 판정을 저장하고 화면·내보내기에 반영한다 | `app/ledger.py`, `app/classification_correction.py` | 없음 |

- 각 단계에서 P1을 먼저 돌리고 남은 것만 P2로 보낸다.
- 금액·부호·원승인 관계·환불 짝·새 장부 기록은 P1만 쓴다. P2는 귀속·항목·이용기간과 그 근거를 제안하고, 승인 후 열린 분기의 기존 내부 기록을 교정할 수 있다(§6.4).

## 6. 서버 밖 P2 일괄 판정

### 6.1 실행 위치와 두 층

2026-11-11 사용자 결정에 따라 `tools/p2_batch/`의 독립 프로세스로 실행한다. 운영 Board 내장 P2 런타임은 **배포돼 있으나 꺼 두고 쓰지 않음** 상태를 유지한다. 코드 제거는 후속 작업이다. Board 프로세스·route 잠금·운영 포트에 연결하지 않는다. 운영 `board.sqlite`는 `mode=ro`의 짧은 조회로 필요한 열만 읽고 연결을 닫는다. 새 전체 DB 사본은 만들지 않는다.

| 층 | 대상과 입력 | 출력 |
| --- | --- | --- |
| 1층 가맹점 항목 | 일반 항목이며 수동 결정이 아닌 가맹점 30~50곳씩. 원문·정규화 가맹점명, 있는 경우 업종 코드·국가·통화, 건수·금액대, 실제 허용 항목과 규칙집 §3.3·항목 사용자 예외 | 가맹점별 항목, 확신 높음/낮음, 한 줄 근거. 판단할 수 없으면 기존 항목 유지 |
| 2층 근거 판정 | 이용기간 미확인 및 OTA·항공 추론만 한 건 또는 동일 예약 묶음씩. 규칙집 §2·§3과 해당 예외·유형 규칙, 관련 발췌 | 귀속·항목·이용기간·근거·불확실성의 제안 |

1층에는 사람 이름·카드번호·예약번호를 넣지 않는다. 국가·통화만으로 상품을 단정하거나 복합 OTA의 공급자명만으로 항목을 정하지 않는다. 수동 결정과 금융 보호는 양쪽 모두 제외한다.

### 6.2 2층 근거와 입력 예산

- 건당 입력 목표 약 15,000토큰, 상한 30,000토큰. 규칙집 전체와 원문 묶음을 매번 넣지 않는다.
- 관련도 순 3~5개 발췌를 넣는다. 메일당 2~4KB로 제목·발신 도메인·발송일과 금액·날짜·예약번호·기간·취소 문구 주변 줄을 보존한다. 절단 여부를 표시하고 원문에 없는 사실을 만들지 않는다.
- 기존 2026-11-11 14:36 검증 백업의 근거 저장소를 읽기 전용으로 한 번 훑어 작은 발췌 색인을 만든 뒤 그 색인만 읽는다. 판정마다 압축 묶음을 통째로 해제하지 않는다. 발췌 전 8MiB 제한에 걸린 과거 실패를 반복하지 않는다.
- 입력·출력·표본·변경 전 값은 Git에 넣지 않는 보호 경로에 둔다. 일반 로그·PR·보고에는 집계와 경로만 남긴다.

### 6.3 도구 없는 실행

- `codex exec --sandbox read-only --output-schema <schema.json> --json -`, 승인 `never`, 구독 `gpt-6.1-sol`을 사용한다. 프롬프트/stdin으로 자료를 주고 cwd는 빈 임시 폴더다.
- 기존 `app/frontier_agent_provider.py`의 도구 차단 설정·이벤트 검사와 `app/connected_agent_provider.py::_run_bounded`의 소유 프로세스 시간 제한·종료를 재사용한다. 파일·셸·네트워크·MCP·플러그인·다중 에이전트 도구를 막고 도구 이벤트가 관측되면 결과를 거부한다. OS 격리 보장과 혼동하지 않는다.
- 용량·사용량 한도 오류는 지연 후 재시도한다. 계속 실패하면 저장된 진행 상태를 남기고 멈춘다. 고객 원문을 무료 모델·Claude로 우회하지 않는다.

### 6.4 제안과 반영

1. 먼저 JSONL 제안만 만든다. 실행 ID·모델·요청 지문과 거래의 source_hash·revision·변경 전 판정을 보호 경로에 보존한다.
2. 대상 누락/중복, 허용 항목, 근거, 도구 미실행을 검증한다. 반영할 때 거래·여행·규칙의 신선도와 모든 보호를 다시 확인한다.
3. **Fable 승인 뒤에만** 소량씩 기존 `app/classification_correction.py`와 그 저장 경로로 적용한다. 기록된 내부 장부 행과 화면 행의 귀속·항목을 함께 맞추며 변경 전 값과 이력을 남긴다. 기존 코드의 기기록 AI 교정 거부는 승인 후 반영 단계에서 열린 분기 조건 아래 검증하며, 이번 제안 도구는 그 보호를 변경하지 않는다.
4. 판정 주체는 `ai_inference`이며 근거 문장·실행 ID·모델을 남긴다. 수동 교정·정확 근거 P1·금융 보호를 덮지 않는다.
5. 금액·부호·원문·ID·환불 짝·Google에는 쓰지 않고 새 장부 기록을 만들어내지 않는다. 대량 반영은 §13과 백업·복원 조건을 따로 충족해야 한다.

단계 2의 항목 정리는 모델을 다시 부르지 않는 후처리다. `대중교통`은 장부의 `교통비`로, 시설 이용이 확인되는 `이용료`는 `입장료`로 대응한다. 편의점·시설 이용이 아닌 이용료·운영 장부에 없는 항목은 기존 항목 유지로 둔다. 공백·도시·국가 표기 변형은 묶음 다수결로 통일하고 동률은 유지한다.

### 6.5 대상 — 카드일이 아니라 열린 분기 귀속

- 시작일 2026-06-30 이후 Google 여행 탭에 귀속된 구매와 2026년 3분기 이후 분기 기타비용이다. `0630` 여행은 규칙집 TRIP-012·DATE-009에 따라 3분기에 포함한다. 앞선 카드 이용일의 선결제도 그 여행에 귀속돼 있으면 포함한다.
- 열린 분기는 이미 내부 장부에 기록된 자동 판정도 P2 교정 대상이다(REC-007·REC-008). 수동 출처(`user_decision`, `user_exception`, `manual`, `owner_booking` 등)·실제 수동 결정·금융 보호는 제외한다.
- 닫힌 분기 여행 귀속은 카드일이 경계 이후여도 자동 교정하지 않는다. 근거상 열린 여행 지출로 보이는 건은 **분기 검수 때 볼 것** 목록만 만든다.
- 1층은 일반 항목(현지경비·기타경비·여행경비) 가맹점, 2층은 이용기간 미확인 및 OTA·항공 추론이다. 과거 `autonomous_cleanup_worker.detection_sql()`의 미기록 행 중심 후보는 이 일괄 작업의 대상 정의로 쓰지 않는다.

### 6.6 기록과 검증

- 호출 수·성공률·소요·토큰, 가맹점/영향 행 수, 항목 전환표, 낮은 확신·기존 유지 비율을 집계한다. 표본 30곳은 보호 경로에만 둔다.
- 이용일 경고는 화면의 함수를 재사용한다. 서버 외부에서는 저장된 표시행과 서버 메모리에만 있는 OTA 파생 근거를 구분하고, 후자를 읽지 않은 수치를 실시간 화면과 같다고 보고하지 않는다.
- 운영 DB 쓰기·배포 없이 합성 자료로 보호 제외·출력 스키마·도구 차단·변경 전 값 보존을 검사한다. 실제 모델 호출과 합성 호출을 구분한다.
- 단계 2 반영 전에는 기존 `classification_correction.preview`를 읽기 전용으로 실행한다. 기록된 장부·화면 행의 AI 교정 보호가 걸리면 우회하지 않고 서버 코드 변경 필요를 보고하며 반영을 멈춘다.

### 6.7 P1 승격과 표본 감사

- 1층의 확신 높은 가맹점→항목 판정은 승인 후 기존 데이터 규칙 저장소(`cost_classification_rules`)에 등록해 다음부터 P1이 처리하게 한다. 이번 제안 단계에서는 등록하지 않는다. 사용자 예외·상품 혼합·국가/기간 조건을 보존하며 단일 거래의 결정을 범용 규칙으로 넓히지 않는다.
- 기존 `app/rules.py::normalize_rule`·`save_rule`의 조건/효과 분리, 버전·규칙 해시·변경 이력을 사용한다. 항목 규칙에 여행 이동 효과를 섞지 않는다.
- 그 밖의 반복 유형 승격은 같은 유형 5건 이상·일치·분기 검수 교정 0건을 제안 기준으로 삼는다. P1 표본 감사 비율은 첫 분기 후 조정한다. 정확 근거 P1을 감사 추론으로 덮지 않는다.

### 6.8 단계와 멈춤

0. 읽기 전용으로 대상·보호·이용기간 미확인·경계 교차를 집계한다.
1. 1층 전체 가맹점 제안·집계·표본을 만들어 Fable에 보고하고 멈춘다. 운영 반영·규칙 등록은 하지 않는다.
2. 후속 승인 뒤 1층 반영/P1 등록, 2층 발췌 색인과 20건 오프라인 판정·보고·반영을 순서대로 한다. 이전 단계의 승인을 다음 단계 승인으로 해석하지 않는다.

### 6.9 2026-11-12 실행 결론

1층 367건 반영·P1 규칙 211개 등록·wave3 배포를 완료했다. 2층은 카드일(승인일, 없으면 매입일)이 2026-04-01 이전인 행을 제외한 이용기간 미확인 148건 중 근거에 도달한 75건을 오프라인 판정했다. 37개 예약·근거 묶음, sol 10회 결과에 가드를 적용하니 이용기간 채움 0건, 인용 발췌에 없는 기간 폐기 34건이었다. 현재 수집된 발췌로 이용 날짜를 확인할 수 없어 2층을 중단한다. 항목 변경 제안 21건도 반영하지 않는다.

근거 없는 73건의 원 집계는 결제대행 NICE 표기 57건, 공급자 색인 부재 15건, Agoda 색인은 있으나 조건 불일치 1건이다. 이전 보고의 “결제대행 57·수집 공백 17”은 합계가 74인 집계 오류여서 정정한다. NICE 57건의 공급자 무관 정확 금액 재검색도 0건이었다. 다음 단계는 사용자 로그인 후 OTA 포털에서 예약 상세의 이용기간을 확보하는 것이다. 확보되면 P1의 정확 연결을 먼저 적용한다. 이용기간 저장 경로는 [도구의 제안](../tools/p2_layer2/README.md)에 남기고 이번에는 구현하지 않는다.

- 스크립트는 로그인 만료를 감지하면 로그인 모듈로 사이트당 1회 자동 시도를 하고, 실패·추가 인증이면 멈추고 상태 화면에 "로그인 필요"와 원천 이름만 띄운다.
- 수집 스크립트는 수집과 가져오기까지만 한다. 가져온 뒤의 판정은 파이프라인이 한다.
- 카드 로그인은 등록 자격 증명(DPAPI 사용자 범위 암호화, `D:/WebLedgerHost/secrets/card-login/`)으로 자동 시도한다. 비밀 값은 Git·문서·로그·인자·환경 변수에 남기지 않는다. 추가 인증(휴대폰·OTP·간편인증)은 사람이 승인한다. 완전 무인은 카드사 자료 전송이나 유료 수집 서비스가 필요하며 요금·조건은 조사 항목으로만 둔다(§14). 보안 프로그램 설치는 하지 않고 필요 여부만 기록한다.
- 원천마다 절차서를 `docs/playbooks/`에 둔다. 기존 두 문서(`card_downloads.md`, OTA 포털 수집 절차)가 첫 절차서다.

### 7.1 영수증 — 로컬 Paseo 선택과 검수 후 반영

2026-11-16 소유자 요청: 이 로컬 PC의 Paseo에서 현재 제공하는 provider·model을 조회해 보여 주고, 사용자가 모델을 선택하면 관리 프롬프트와 업로드 사진을 즉시 보내 처리한다. 웹페이지를 떠나도 작업과 결과를 서버에 보존하며, 복귀 후 사진과 결과를 나란히 검수하고 선택한 내역만 COST 장부에 한 번에 반영한다.

사용자 답변으로 **승인된 구독 모델 중 사진 입력 가능한 모델만 선택**, **관리되는 기본 판독 지시만 사용**, **선택 내역 일괄 반영**을 확정했다. 전송·격리·검수·원본 보호의 정본은 RCPT-020·RCPT-022·RCPT-031이다. Google 자동 쓰기는 허용하지 않는다.

상세 흐름·영속 작업·실제 장부 반영·수락 조건은 [영수증 처리 변경 설계 초안](design/receipt-paseo-workflow-20261116.md)에 있다. **현재 승인 범위는 명세 작성과 질문까지이며 구현·모델 호출·운영 변경은 시작하지 않는다.** 현재 코드와의 차이는 [CODE_GAPS](policy/CODE_GAPS.md)에 기록한다.

## 8. 분기 검수와 교정 환류

분기 검수는 **AI 검수자**가 한다(소유자 결정 2026-11-13). 검수자는 Fable 5.2 high 에이전트이며, 쓸 수 없으면 그때의 최상위 Claude 모델이 대신한다. 사용자는 건별 판단을 하지 않는다.

1. **입력.** 분기 말에 검수 자료([분기 검수 절차서](playbooks/quarter-review.md), `tools/quarter_review/`)를 만든다. 검수 목록은 검수자의 입력이며 사용자 산출물이 아니다. 검수자는 구독 프론티어 모델이므로 고객 원문(카드 원행, 메일·포털 근거)을 읽을 수 있다(§13.9).
2. **표본부터 본다.** 검수 사유(AI 판정, 최근 자동 변경, 추론 귀속, 포괄 항목 등)별로 표본을 뽑아 원문 근거·여행 기간·규칙집으로 맞는지 판정하고 사유별 정답률을 낸다. 정답률이 낮은 사유·가맹점·패턴은 끝까지 본다. 정답률이 높은 묶음은 표본으로 승인하고 전수를 생략할 수 있으며, 그 판단과 근거를 기록한다.
3. **원인 단위로 묶는다.** 같은 원인의 오판이 여러 건이면 규칙 문제다. 규칙집을 고치고(같은 ID 개정, 옛 내용 보존) 그 규칙으로 다시 판정할 대상을 정한다. 한두 건짜리 오판은 건별로 교정한다.
4. **교정은 기존 정식 경로로만 한다.** 서버 인증 API의 교정 경로(열린 분기 한정, 요청당 50건 이하)나 미리보기·digest·신선 백업 게이트·감사 원복을 갖춘 유지보수 도구를 쓴다. 운영 DB에 직접 쓰지 않는다. 교정 전 값을 비공개 폴더에 남긴다. 출처는 AI 검수(모델 이름)로 기록해 사용자 결정과 구분한다. 수동 교정, 환불 짝·초과 환불·원본 충돌 보호, 카드 원문·금액·ID는 건드리지 않는다(§13).
5. **사용자 결정 필요.** 규칙이 없거나 규칙끼리 모순이거나 사업 판단이 필요한 것만 남긴다. 건별이 아니라 질문 단위로, 예시를 붙인다. 0건이 목표다. 답은 규칙집 개정으로 반영한다.
6. **결과.** 검수 보고에 사유별 표본 정답률, 원인별 묶음과 처리(규칙 개정·재판정·건별 교정·보존), 교정 건수(여행 귀속·항목·이용기간별), 개정한 규칙 ID, 사용자 결정 필요 질문, 검수 전후 수치를 식별값·금액 없이 적는다. 교정 건수는 사유별로 집계해 §1.4의 지표로 기록한다. 사용자는 이 결과와 검수가 끝난 장부를 받아 Google 지출표에 붙여넣는다.
7. 규칙이 표로 표현되면 P1 데이터 규칙으로 넣는다. 교정 사례는 평가 사례로 누적하고, 규칙이나 P2 구성을 바꿀 때 이 사례들로 되돌아간 판정이 없는지 다시 돌려 본다.
8. 2026년 6월 이전의 Google 지출표는 "대체로 맞지만 오류가 섞인" 참고 자료다. P2 사건 폴더에 "과거 같은 가맹점이 어떻게 분류됐는지"로 넣을 수 있지만 현재 거래의 증거로 쓰지 않는다.

- 대체된 옛 내용(2026-11-10~13): 분기 말에 사용자가 여행별 장부와 분기 기타비용을 검수하고 틀린 판정을 직접 교정했다. 감독 세션이 그 교정을 모아 규칙집에 환류하고 교정 건수를 판정 주체별로 집계했다.

## 11. 투자 단계의 설계 원칙

M3 이후에 적용한다. 착수할 때 이 절을 상세 설계로 확장한다.

### 11.1 Rust 새 코어 (M3, M6)

- 얻는 것: 판정 상태와 금액 규칙을 타입으로 강제해 에이전트가 만든 회귀를 테스트 전에 잡는다. 실행 파일 하나로 배포한다.
- 대상: 판정 모델, 파이프라인, P1 규칙 엔진, 작업 큐·Worker, P2 실행기, JSON API. React/TypeScript 프런트와 ego-browser 수집 `.mjs`는 Rust 밖에 둔다.
- 데이터: 원천을 `evidence`(원문 보존) → `facts`(구조화 추출)로 통일하고 SQLite 하나에 테이블 약 25개로 줄인다(evidence, facts, payments, bookings, links, trips, decisions, decision_history, overrides, jobs, agent_runs, 부가 영역). 이관은 테이블 변환이 아니라 **보존된 원본을 새 파이프라인에 다시 넣는 방식**으로 하고, 기존 수동 교정은 overrides로 옮긴다.
- 순서: 착수 시 기존 Python 추출기를 보존 원본에 돌려 **기준 출력**을 만든다. Rust 추출기는 이 출력과 일치해야 병합된다. 전환기에는 Rust 코어가 Python 추출기를 하위 프로세스로 부르는 것을 허용하고, 기준을 통과한 것부터 교체한다.
- 드문 양식은 Rust 파서를 새로 쓰지 않고 P2와 데이터 규칙으로 흡수한다.
- 전제: 이 PC에 Rust 도구가 없다. 설치는 착수 때 사용자 승인을 받는다. 통과 조건은 `cargo test`·`cargo clippy`와 교정 사례 재실행이다.

### 11.2 화면 (M4)

- Rust JSON API + React/TypeScript 컴포넌트 라이브러리.
- 디자인은 Claude Design에 맡긴다: 컴포넌트 라이브러리를 `/design-sync`로 동기화 → Claude Design에서 설계 → 에이전트가 구현 → 다시 동기화.
- 화면은 분기 검수(판정 열람·교정), 산출물 3종, 자동화 상태를 중심으로 한다. 정보구조는 [UI/UX 감사·재설계 명세](history/specs-20261110/uiux-full-audit-redesign-20261110.md) §5를 이어받는다.
- 부가 기능(수입·참가자 대조, 영수증 처리, Google 장부 비교·복사, 직원 계정·열람 권한)은 모두 새 구조로 옮긴다.
- 2026-11-15 UI/UX 전체 검수 결과는 [M4 화면 수락 기준](design/m4-ui-requirements.md)을 만족해야 한다.

### 11.3 서버와 보조 노드 (M5)

- 서버 역할: 화면, API, DB, 원문 저장, P1, 작업 큐. 보조 노드(로컬 PC): P2 실행, 로그인 세션이 필요한 수집. 같은 실행 파일의 두 실행 방식이다.
- 보조 노드는 서버로 **나가는 요청만** 한다. PC로 들어오는 터널을 두지 않는다.
- PC가 꺼져 있으면 화면·P1·웹 업로드는 계속 동작하고 P2와 브라우저 수집만 쌓인다.
- 원문을 포함해 전부 클라우드에 둔다(사용자 결정). 제공자에 묶이지 않게 실행 파일 하나 + SQLite 파일 하나 + 원문 폴더(또는 S3 호환 저장소)로 만들고, 제공자 전용 런타임에 맞춘 코드를 쓰지 않는다. 제공자는 이전 시점에 실제 요청량을 재고 고른다.
- 매일 클라우드 DB와 원문을 로컬 PC로 내려받아 보관한다.
- 제공자를 고르기 전에 고객 개인정보의 국외 이전·처리 위탁 고지 의무를 확인한다(§14).

### 11.4 P2 모델 교체 (선택)

- 세 층으로 본다: P1 / 무료 모델 + 절차서 / 프론티어 모델(상위 이관·표본 감사·절차서와 규칙 개정).
- 프론티어 모델이 반복 작업의 절차서를 `docs/playbooks/`에 남긴다. 절차가 고정되면 스크립트로 내리는 것이 먼저이고, 무료 모델은 그 사이 단계다.
- 교체는 작업 유형 단위로 한다. 무료 모델을 같은 작업에 나란히 돌려 프론티어 판정과의 일치율·형식 오류율·시간 초과율을 본 뒤 바꾸고, 검증 실패 건은 프론티어로 올린다.
- 판단이 필요한 드문 사례는 프론티어 모델에 남긴다. P2 물량이 월 100건 안팎이면 비용 절감 효과가 작으므로 우선순위가 낮다.
- 무료 모델에 고객 원문을 주는 것은 제공자의 데이터 이용 조건을 확인한 뒤 따로 승인받는다.

## 12. 개발 운영

### 12.1 증상별 패치 동결

- 2026-11-10부터 공급자별·증상별 파서 패치, 화면 문구·경고 수치를 쫓는 수정, 기록만을 위한 문서 PR을 하지 않는다. 같은 레포의 모든 세션에 적용한다.
- 예외: 운영 장애(접속 불가, 데이터 손상 위험, 수집 중단)와 이 문서의 로드맵 작업.
- 판정이 틀린 사례를 발견하면 코드를 고치지 말고 규칙집의 사례로 기록한다. M2 이후에는 P2가 처리한다.

### 12.2 조직

2026-11-11 결정: **담당 1명 + 최종 검수 1명**, Fable이 직접 지시·판단한다. 중간 관리자는 없다. 담당자는 재귀 위임하거나 별도 구현 작업자를 만들지 않는다.

- 담당자는 승인된 단계의 구현·실행·검증·기록을 맡는다. 최종 검수는 별도 `gpt-6.1-sol` medium 이상이 최종 SHA를 읽고 판정한다.
- [관리자 지침](agents/MANAGER.md)은 **병렬 작업자가 다시 생길 때까지 사용하지 않음**으로 보존한다.
- 고객 원문은 승인된 구독 프론티어 모델 P2 호출과 Qwen4 Max(QwenCloud) 작업자에게만 전달한다(PROC-012, 소유자 결정 2026-11-13, Codex 한도 동안의 개발·예행 작업 포함). Git·PR·일반 보고·무료 모델·Claude에 넣지 않는다. 사용자 의도와 재개 정보는 명세·규칙집·작업판에 남긴다.

### 12.3 통과 조건과 병합·배포

- 통과 조건은 실행 결과다: 바뀐 기능의 표적 테스트, 영향 기반 QA(`python tools/run_quality_checks.py --base origin/main --run`), 교정 사례 재실행(M2 이후). 작업자가 테스트를 고쳐 통과시키지 않는다.
- CI가 결제 한도로 시작되지 못하는 동안에는 `gpt-6.1-sol` medium 이상이 최종 SHA를 검수·승인한 PR만 병합한다. Codex가 한도로 막힌 동안은 구현자와 다른 Claude opus 세션의 독립 검수로 대체한다(소유자 결정 2026-11-13). 모델, 추론 수준, SHA, 판정을 PR에 기록한다. 실제 검사 실패는 이 예외로 통과시키지 않는다.
- 운영 배포는 단일 작성자가 `tools/deploy_verified_release.ps1`로 한다. `-PreviousSha`는 현재 운영 SHA다. 배포 전후에 같은 레포의 다른 세션에 알린다.
- 문서만 바꾼 PR은 테스트·재배포를 하지 않는다. 링크와 인용한 사실만 확인한다.
- 대량 반영·삭제·스키마 변경·금융 원본 변경은 신선 백업과 복원 확인 뒤에 한다. 소수 거래의 교정은 변경 전 값과 이력으로 되돌린다.

7. 강제 push, 운영 DB·고객 원본 삭제, 승인 없는 과금을 하지 않는다.
8. 미리보기·테스트에 운영 포트 8751, 8752, 8790을 쓰지 않는다. 내가 시작하지 않은 프로세스를 종료하지 않는다.

10. 직원 계정·열람 권한 검사를 약화하지 않는다.
