# 개발·배포 중 운영 502 방지

사용자 승인: 2026-11-02 운영 502 조사 후 “적용해”.

## 목적과 완료 조건

- 목적: 검증·배포 때문에 정상 운영 서버를 먼저 정지하는 중단을 없앤다.
- 변경 동작: 고정 loopback 게이트웨이 8790 → 활성 앱 8751/8752. 후보 앱의 health/ready 및 인증 보호를 먼저 확인한다. 새 연결을 잠시 대기시키고 기존 요청·자동 작성 작업을 마친 다음 기존 앱을 종료하고 후보를 활성화한다.
- 직접 영향: Windows 작업 스케줄러·Cloudflare 원본 경로·코드 배포·카드 완료 작업과 Google에서 읽은 여행의 내부 동기화. Google 최종 장부 쓰기는 추가하지 않는다.
- 검증: 합성 연결 전환·진행 중 요청·업로드/인증 전달·재전송 없음·후보 실패·drain 실패·자동 작성자 배제, 기존 Windows 호스트 검사와 영향 QA. 실제 전환 시 연속 요청·health/ready·보호 API·13표 불변을 확인한다.
- 완료 조건: CI 녹색 병합 SHA 고정 배포, 게이트웨이와 새 앱 스케줄러 실행 확인, 실제 전환 근거 및 남은 한계 기록.

## 2026-11-05 Gateway 유휴 HDD I/O 최적화 후속 (진행 중)

[상세 명세 #644](https://github.com/6Soo/cost/pull/644)는 문서 PR **열림/미병합**, [구현 #646](https://github.com/6Soo/cost/pull/646)은 코드 PR **열림/미병합**이다. #646의 제안은 status 이벤트별 즉시 게시와 30초 유휴 heartbeat, route 파일 250ms stat cache, 로그 체크 감소다. 해당 PR의 ‘~97% 감소’는 예정 heartbeat 횟수에 대한 추정이며 운영 HDD/소음 실측이 아니다. **현재 main/배포의 적용 증거로 사용하지 말 것.** route pause/generation·drain 최신성·기존 연결 보존, 후보 실패 원복, Gateway 프로세스 교체·잠금/작업 스케줄러·보호13표·실측 수락이 선행되어야 한다. 주기 숫자만 고치거나 구상태 파일을 근거로 연결 종료를 승인하지 않는다.

## 실행 계약

1. 검증된 SHA의 `tools/install_ledger_gateway.ps1`을 `-Apply` 없이 미리보기한다. 첫 설치만 `-Apply`로 실행한다. 기존 앱을 유지하고 새 터널 연결의 `/ready`가 200인 뒤 기존 터널 연결을 종료한다. 터널 인증·공개 hostname은 유지한다.
2. 후속 코드는 후보 SHA의 `tools/deploy_verified_release.ps1 -CandidateSha <sha> -PreviousSha <active-sha> -ReviewEvidence <review.json> -Apply`를 사용한다. SHA·Git blob 감사·이전 검증 릴리스·검사 근거·보호 13표 baseline이 필요하다.
3. 활성 앱 포트는 `D:/WebLedgerHost/config/ledger-route.json`에서 읽는다. 8751을 활성 서버라고 고정 가정하지 않는다. 공개 경로는 게이트웨이 8790이며 Cloudflare도 그 포트를 사용한다.
4. `WebLedger-Prepared`는 후보 준비 동안만 존재한다. `WebLedger-Board`가 새 앱을 인계받고 `WebLedger-Gateway`는 재시작하지 않는다. 프로세스 종료 전에 loopback 포트·launcher·SHA를 확인한다.
5. 후보에는 `-DeploymentRoute`를 명시한다. 카드 자동 완료와 여행 동기화는 route 역할 및 프로세스 간 잠금을 확인한다. 대기 후보는 두 자동 작성 작업과 상태 파일을 쓰지 않는다.
6. 전환 실패 시 기존 요청을 강제 종료하지 않는다. drain 시간 초과는 기존 경로를 재개한다. 후보 준비 실패는 기존 앱을 유지한다. 전환 이후 복귀도 같은 drain·단일 작성자 경계를 사용한다.
7. 일반 코드 배포는 이전 릴리스·task XML을 보존하고 전체 고객 자료 백업·복원을 반복하지 않는다. 데이터 변경·마이그레이션에는 별도 보호 게이트가 필요하며 `-BackupProducts`를 무중단 코드 전환으로 확대하지 않는다.

## 경계와 한계

- 게이트웨이는 TCP 바이트를 중계하며 금융 요청을 자동 재시도하지 않는다. 기존 업로드·세션·쿠키·인증 응답을 그대로 전달한다.
- 긴 진행 요청은 기존 앱에서 완료한다. 전환 중 새 연결은 잠시 대기한다. 30초 안에 drain되지 않으면 전환을 취소한다.
- 게이트웨이·Windows 호스트·네트워크 자체의 장애까지 무중단을 보장하는 다중 호스트 구성이 아니다.
- 역할 보호가 없는 과거 릴리스를 후보로 병렬 시작하지 않는다. 최초 전환의 기존 앱은 별도 종료 후 새 작성자를 활성화하며 과거 버전으로의 복구는 별도 단일 작성자 절차가 필요하다.
- 개발 검증은 합성 입력과 별도 경로를 사용한다. 운영 DB·Google·고객 원문에 테스트 쓰기를 하지 않는다.
