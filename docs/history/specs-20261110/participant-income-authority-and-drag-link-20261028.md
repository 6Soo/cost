## 1. 왜 현재 구조를 바꾸는가

현재 `app/participant_roster.py::ParticipantStore`는 보험 명단에서 참가자 객체를 저장하고 `app/participant_income.py::reconcile`는 명단과 Google 수입 행을 별도로 대조한다. `webapp/participant_income_page.py`의 `/participants`에는 owner 전용 대조·수동 연결·해제 기능이 존재한다. 이 기능은 **재사용할 수 있는 핵심 서비스**다.

다만 여행 탭의 수입/지출과 명단이 별개 화면으로 분리돼 있어, 수입을 먼저 받고 나중에 보험을 가입하는 실제 업무 순서와 닉네임 입금·공동입금을 한눈에 처리하기 어렵다.

**변경점:** 여행별 Google 수입 원장을 화면의 첫 목록으로 제시하고, 그 아래 보험 확정 참가자를 같은 컨텍스트에 배치한다. 수입 행의 추가 `보험 등록` 열에서 **어느 확정 참가자와 연결됐는지** 확인한다. 이름만으로 연결되지 않은 보험 실명 카드는 드래그하여 수입 행에 놓아 사용자가 명시적으로 연결한다. 두 원본 테이블을 덮어쓰는 DB merge가 아니다.

| 영역 | 권위 / 사실 | 금지되는 추론 |
| --- | --- | --- |
| 여행(실제 tab_id) | Google 여행 탭 정본 및 COST의 검증된 매핑 | 보험 명단 때문에 새 여행 생성 금지 |
| 여행 참가자 | **Travel INS에서 가입 완료 증빙과 연결돼 COST에 수신·등록된 확정 보험 명단의 사람별 ID** | Google 수입 행이 먼저 생겼다고 보험 가입 확정 아님 |
| 입금 증거 | Google 수입 원장 원행. 날짜·입금자명/닉네임·금액·열 값이 최종 정본 | COST가 입금 날짜/실제 금액·이름을 수정해 동기화하는 것 금지 |

| 보험 효력 | 보험사 가입 완료 확인/증빙과 수신 배치의 명시된 범위·rev | 파일 수신/명단 제출/기존 체크포인트만으로 보험 효력 확정 금지 |
| 항공권 | 예약번호·검증된 여정/탑승객 인덱스 | 같은 이름만으로 보험 가입·입금·항공권 사람 동일 확정 금지 |

### 2.1 참가자 명단의 권위 범위

- **`insured_confirmed` 또는 이와 동등한 실제 가입 완료 증빙을 통과한 명단만** ‘보험가입 확정 참가자’로 표기. 보험사 등록 대기, 결제 직전, 명단 사진 전사만 완료한 배치는 별도 `가입 확인 전` 상태로 표시하며 확정 인원에 산입하지 않는다. 실제 Travel INS `authority=owner_confirmed_insurance` 필드와 확인증/영수증 수락 계약을 재사용.
- `scope=partial`이면 해당 명단에 포함된 사람에 대한 확정 근거만 있을 뿐 여행 전체 명단이 완결됐다는 뜻이 아니다. `scope=complete`/전체 인원 검증과 구별한다.
- 보험 가입 전 입금 행은 **미연결 수입**으로 정상 보존하며, 새 보험 명단 도착 시 다시 매칭한다. 수입 기록만으로 참가자 정본을 새로 만들거나 참가 인원에 포함하지 않는다.
- 취소·보험 해지·참가 변경/교정은 원본/기존 참가자 revision·event history를 통해 상태를 변경·보존하며 과거 입금 연결이나 원본 행을 삭제하지 않는다.
- ‘보험 확정 참가자 수’와 ‘입금 확인 연결 인원’, ‘수입 원장 행 수’, ‘실제 금액 합계’는 독립된 집계다.

## 3. 최종 화면 구조

~~~text
[여행명 · 여행일자]
[여행 참가 확정 12명] [수입 연결 9명] [미연결 수입 4건] [가입 확인 전 2명]

1. 수입내용                    [미연결만 보기] [연결된 항목 보기] [검색]
┌일자┬입금자/닉네임┬입금액┬보험 등록┬기타 기존 컬럼┐
│11/01│산책냥이      │100,000│미연결   ◀ 여기로 끌어놓기│…│
│11/02│김예시        │100,000│✓ 김예시 (확정)         │…│
│11/03│여행모임장    │300,000│✓ 2명 연결 (확정)      │…│

2. 보험가입내역                [미연결 우선] [이름 검색] [확정/변경 이력]
[김예시 · 가입 확정 · 수입연결됨]   [박예시 · 가입 확정 · 수입 미연결  ⠿]
[정예시 · 가입 확정 · 수입 미연결  ⠿]  ← 카드를 잡아 수입 행 '보험 등록'에 놓음
[변경/취소 내역 펼치기]

3. 지출내용                     [기존 COST 장부/Google 복사 기능 유지]
[기존 지출표 그대로]

[항공권 예약 N건]             ← 독립 보조 영역, 기존 귀속 명세 따름
~~~

- 정확한 시각 스타일은 공통 디자인 토큰/컴포넌트를 사용한다. 위는 정보구조 예시이고 실제 고객 데이터가 아니다.
- **수입·보험·지출 순서 확정.** 수입과 보험의 관계를 보려면 동시에 볼 수 있어야 하므로, 필수 두 영역은 **화면에서 기본 표시**하되 수입 행/보험 사람 카드가 많을 때는 각각 최대 20개 server pagination + 필터. 수입 영역에는 고정/근접 drop target을 제공해 스크롤 길어져도 이동이 가능하게 한다.
- 보험 상세에 실명/명단이 포함되므로 현재 `/participants`와 같은 **owner-only** 권한을 기본 적용한다. 여행 탭 자체를 다른 역할이 열 수 있다면 명단·체크의 개인 연결 정보는 owner 전용 projection으로 요청/노출; HTML에 숨겨진 상태로 실명을 미리 포함하면 안 된다.
- 입금 원장에 존재하는 실명/닉네임은 기존 열을 그대로 보여주되, COST가 자동으로 Google 수입의 입금자 이름을 보험 실명으로 바꿔 표시해 원본을 흐리지 않는다.
- 표의 `보험 등록` 열은 **COST 화면 가상 열**이다. Google 시트의 새 열이나 B:H 원본을 수정/밀어내지 않는다.

## 4. 수입 '보험 등록' 열 상태·표시 계약

| 코드 | 수입 표의 표시 | 의미 |
| --- | --- | --- |
| `INSURED_LINKED_AUTO` | ✓ 보험 등록 · 실명(유일 매칭) | 현재 여행에서 확정 보험 참가자와 검증된 유일 이름/기존 alias가 연결됨 |
| `INSURED_LINKED_MANUAL` | ✓ 보험 등록 · 실명(직접 연결) | owner가 드래그 또는 키보드 동작으로 참가자와 이 입금 행 관계를 확정 |
| `INSURED_LINKED_MULTI` | ✓ N명 연결 · 상세 | 동일 수입 행을 여러 확정 참가자와 명시적으로 공동 연결 |
| `INCOME_UNLINKED` | 미연결 · 보험 명단에서 끌어오기 | 수입은 존재하나 보험 참가자 연결이 없음. **보험 미가입 확정이 아님** |
| `MATCH_REVIEW_REQUIRED` | 확인 필요 · 후보 N명 | 동명이인/닉네임 충돌/원본 변경/복수 후보; 자동 체크 금지 |
| `ROSTER_NOT_READY` | 보험 명단 확인 전 | 명단 수신·가입 증빙·갱신 미완료 |
| `INSURED_CHANGED_OR_CANCELLED` | 변경·취소된 명단 관계 확인 | 과거 링크와 현재 참가 상태가 달라 재검토 필요 |
| `SOURCE_STALE` | 수입·보험 자료 최신성 확인 필요 | Google/명단 DB 오류 또는 지문 변경. 0건/미연결로 오인 금지 |

- 체크 표시 **✓의 의미는 해당 수입 행과 가입 확정 참가자의 신원 연결**이지 입금액 정산·여행비 완납·보험료 납부·실제 은행 입금 확인 완료를 새로 증명하지 않는다. 수입 금액은 Google 원장 사실만 표시.
- 수입 1건에 참가자 2명이 연결되면 `✓ 2명`처럼 표시하고 hover/focus/상세에서 두 실명을 확인한다. 한 명에 여러 입금 행이 연결돼도 합계·횟수는 원본 금액만 합산해 별도로 표시한다.
- 기존 `app/participant_income.py`의 identity 우선순위 `수동 결정 → 검증된 명시 연결 → 안전한 유일 이름 일치 → 미연결`을 그대로 서비스의 시작점으로 사용한다. ‘보험 등록’ 열은 같은 `reconcile` 결과를 단일 projection으로 소비해야 한다.

## 5. 수입이 먼저 들어오는 실제 운영 순서

**업무 타임라인**

1. Day 1: Google 수입에 `입금 닉네임=산책냥이, 100,000원` 등록. 보험 명단 아직 없음 → 원본 수입행 유지, `보험 명단 확인 전` 또는 `미연결` 표시, 입금 총액 반영.
2. Day 3: Travel INS에서 가입 완료 증빙/승인된 인원 1명 `박예시`를 COST 등록. 닉네임 정보가 명단에 없으면 자동 동일인 추측 금지.
3. COST 화면에서 owner가 `박예시` 보험 카드를 Day 1 수입 행의 `보험 등록` 칸에 드롭. 확인창: `이 입금 기록(닉네임/날짜/금액)을 박예시의 보험 참가자와 연결할까?`, source generation 확인.
4. 확인 시 **참가자 ID ↔ Google 수입 ref**의 결정 저장. 화면은 `✓ 박예시(직접 연결)`로 즉시 최신 state 재조회.
5. 닉네임이 자주 반복되고 owner가 별도 **별칭 저장**을 선택한 경우, 기존 alias/동일인 확정 API로 `박예시 ↔ 산책냥이` 관계를 기록할 수 있다. 별칭을 ‘자동 학습’해 전 여행·전 사람에 무조건 적용하지 않는다.
6. 이후 Google 입금 원문/행 위치 변경으로 fingerprint가 달라지면 기존 연결은 삭제하지 않되 `재확인 필요`. 검증된 동일 행 identity만 유지한다.

**금지:** 보험 명단이 늦게 도착했다는 이유로 기존 수입의 날짜·금액·닉네임/Google 셀을 수정·재작성하지 않는다.

## 6. 드래그 앤 드롭의 상세 기능

### 6.1 동작

- 드래그 **출발점**: 보험가입내역의 확정 참가자 카드 또는 20건 리스트의 드래그 핸들.
- **도착점**: 수입행의 `보험 등록` 컬럼·명시 drop zone. 서로 다른 여행의 수입행은 대상이 아님.
- `dragstart`에서 실제 개인정보를 DataTransfer plaintext로 내보내지 않는다. 세션에서 검증 가능한 단기 token/participant_id를 내부 상태로 보유하고, POST는 서버에서 대상 여행과 권한·현재 참가자 상태를 다시 검증한다.
- `dragover/drop`에서 대상 하이라이트, 잘못된 권한·다른 여행/이미 확정·충돌/취소는 거절. 브라우저 기본 텍스트 드래그로 실명을 다른 앱에 복사하지 않도록 한다.
- drop 직후 무조건 저장하지 않고 **미리보기 확인**: 참가자 실명·현재 여행·Google 수입의 입금자/닉네임·일자·원금액·기존 연결 여부·사용자 확인/취소. 취소 시 쓰기 0.
- 확인 POST 후 표시/카운트를 서버 재조회. 중복 드롭은 기존 동일 `participant_id + income_ref`를 재사용하거나 명시적 idempotency로 이중 연결·중복 감사 이벤트를 막는다.
- **되돌리기**: 이미 연결된 실명 칩의 `연결 해제`를 통해 기존 `DECISION_UNLINKED`/감사 경로로 취소. 제거 후 자동 이름 매칭이 다시 붙지 않게 수동 해제 우선 정책 적용.
- 입금 행에 이미 A가 연결돼 있을 때 B를 놓으면 `기존 연결 교체`와 `공동입금으로 추가`를 명확히 분리. 기본은 자동 교체 금지, 다인 연결은 owner가 공동입금임을 확인한 경우에만 추가.
- 같은 참가자를 다른 입금 행에 추가하는 것은 분할 입금·추가입금 등 합법적인 운영 패턴이므로 금지하지 않는다. 기존 두 명 이상 연결을 자동 완납으로 계산하지 않는다.
- 입금 행이 아닌 보험 참가자 카드를 목록 바깥/여행 다른 영역에 드롭하면 데이터 쓰기 0.

### 6.2 모바일/접근성 대체

- 드래그만 있는 UI는 금지. 각 수입행 `연결` 버튼 → 참가자 검색/선택, 또는 보험 카드 `수입 연결` 버튼 → 수입행 검색/선택을 제공. **드래그와 선택 버튼은 동일 POST/서버 검증을 호출**한다.
- 320/375/390px·200% zoom·터치/키보드, Enter/Space, 취소·선택·focus return을 자동 테스트. 스크롤 중 항목이 보이지 않을 경우 sticky drop target/찾기 필터 제공.
- 44px 이상 터치 영역, aria-describedby/label/피드백, light/dark, 인터넷 느림/요청 중/409 stale에서 일관된 메시지.
- DOM에 복사 가능한 전체 보험 원본 사진, 주민번호, 보험증권 번호 등을 포함하지 않는다.

### 6.3 쓰기·읽기 경로와 보안

- 가능하면 **기존 owner-only** `webapp/participant_income_page.py`의 `/api/participants/link`/`/api/participants/unlink` 및 `app/participant_income.py::save_decision`을 재사용. 기존 소스에서 실제 route를 확인하고 UI view의 새로운 drop 요청 DTO만 adapter로 연결한다.
- `save_decision`의 `presented_fingerprint/current_fingerprint`, `income_fingerprint`, `expected_revision`, actor, CSRF, 감사·같은 여행 검증, 원본 Google row reference를 유지.
- 원본 행 식별은 `source|sheet|row`와 원문 fingerprint를 함께 사용. 행 위치가 바뀌거나 이름/금액이 바뀌면 stale 확인을 거치며 다른 입금행에 링크를 조용히 이동시키지 않는다.
- 개인정보 권한: 기존 `/participants`는 owner-only. 여행 탭에 별도 읽기 경로를 추가하더라도 **owner-only** 보호를 기본으로 한다.
- Google은 수입/이체의 최종 정본이고 COST는 **연결 결정만 전용 DB에 기록**한다. 수입 원장 자동 쓰기·금액 자동 분배·새 행 생성 금지.

## 7. 자동 연결 정책: 빠르되 신원 확정은 엄격하게

- 같은 여행, 확정 보험 참가자, `display_name/nickname/english_name`의 정규화된 **유일 일치**, 같은 수입 행의 `name/nickname` 및 Google C/D를 기준으로 자동 후보를 확인한다.
- 참가자 2명 이상이 같은 이름/별칭을 공유하거나 수입 1행이 여러 사람과 유일하지 않으면 **자동 체크 금지**, `확인 필요`와 후보를 제시.
- 이름 유사도·문맥·여행일만으로 같은 사람을 확정하지 않는다. 이 부분의 수동 드래그가 핵심 UX다.
- 사용자가 확정 연결 후 동일인 별칭을 설정할 때에만 장래 동일인 후보를 추천. 별칭을 모든 참가자에게 자동 전파하지 않는다.
- 보험 명단의 실명이 바뀌거나 취소되면 자동 연관을 무조건 삭제하지 않고 변경 이력/수동 검토로 전환한다.
- 입금된 닉네임이 보험 명단에 아직 없을 수 있다. `미연결 수입`은 오류/손실이 아니라 정상적인 **보험 등록 전 업무 상태**.

## 8. 다대다 입금 특수 사례

| 상황 | 화면/저장 규칙 |
| --- | --- |
| 한 사람 여러 차례 입금 | 한 `participant_id`에 여러 `income_ref`를 연결 가능, 원본 금액 합산 계산은 유일 원행 기준 |
| 한 사람이 부부/동행인 2명분을 입금 | 하나의 `income_ref`에 2명의 `participant_id` 연결, owner가 ‘공동 입금’ 명시; `✓ 2명` 표시. **금액을 자동 50:50 배분 금지** |
| 수입은 있으나 보험 명단 이전 | 입금 행 유지, 보험 열 `미연결/확인 전`, 참가자 명부 추가 없음 |
| 보험 확정 명단엔 있으나 수입 없음 | 실명 카드를 보험 목록에 `수입 미연결`로 표시, 입금액 0원으로 만들지 않음 |
| A 입금 뒤 B 이름으로 변경 | 원문과 기존 연결 보존, row fingerprint 변경 시 재확인 |
| 동명이인/동일 닉네임 | 수동 검토/드래그·명시 확인, 전역 자동 이름 일치 금지 |
| 이미 참가자 A 연결 수입에 B 드롭 | 추가/교체 선택과 명시 확인, 조용한 덮어쓰기 금지 |
| 입금 취소·환불·마이너스 원행 | Google 원본 부호/금액 유지; 보험 상태/참가 확정 자체를 자동 취소하지 않음 |
| 다른 여행 동일 사람 | **여행별 참가/입금 관계를 독립** 관리. 보험 명단·수입을 여행 사이 자동 이동 금지 |

## 9. 구현 범위와 단계 (엔지니어 실행 명세)

### PIR-01: 데이터/권위 통합 계약 (P0)
- 현재 참가자 `state/authority/active/revision`, `scope`, confirmation receipt, Google income index의 확정 상태를 읽기 전용으로 대조.
- 실제 보험가입 **확정**과 단순 명단 수신 상태를 분리해 view DTO에 노출.
- 이름, alias, 결제 이전/이후, 다대다 연결의 golden fixture 확보.
- **완료:** 참가자 확정 수와 입금 연결 수가 각각 독립 계산되고 원본/Google·보험 DB 동작 불변.

### PIR-02: 여행별 수입 projection + 보험 열 (P0)
- 기존 여행 수입 표/Google 행 정본을 재사용해 `보험 등록` 가상 열 추가.
- 기존 대조 `reconcile` 결과를 key로 join; 미연결/자동/직접/복수/충돌 상태 표시.
- 참여자/보험 소유 권한 확인 후만 이름·실명 연결 UI 노출. 비owner에게 실명이나 연결 메타데이터 포함한 HTML 전달 금지.
- **완료:** 모든 원래 수입 행/합계/정렬/Google 복사 B:H 전후 동일, 보험 등록 상태와 owner 명단 `/participants` 결과 동일.

### PIR-03: 보험가입내역 영역 + 조회 성능 (P0)
- 같은 여행 탭에서 수입 뒤, 지출 전에 보험 확정 명단 카드/검색/미연결 우선 필터.
- 20명 서버측 페이징, 첫 카드/입금 view는 전체 수집·대사 재실행 없이 준비.
- **완료:** 명단 미존재/수신 대기/가입 전/부분/확정/취소/오류 상태 구분, 같은 원본을 중복 이름 카드로 만들지 않음.

### PIR-04: 드래그·확인·해제/키보드 동등 (P0)
- 기존 `save_decision` + owner-only route 사용, CSRF/현재 화면 입력지문/revision 확인. 드래그 미리보기 확인 UI, 공동입금 1:N/분할입금 N:1, 취소/undo.
- **완료:** 실제 직접 연결과 수동 버튼 연결의 저장 결과 동일, 기존 자동 이름 연결로 수동 해제를 덮지 않음, DB 쓰기는 참가자 연결·audit에만 한정.

### PIR-05: 교정·자동 매칭/별칭·충돌 (P1)
- 한글 실명/닉네임, 동명이인, 명단 선후, Google 시트 행 이동/원문 변경, 보험 수정 rev, stale view 회귀.
- 사용자 확정 별칭·동일인 규칙은 제안/승인 후 적용. 자동 전역 이름 합치기 금지.
- **완료:** 결제 원본과 참가자 원본 둘 다 보존, 자동 추천 시 실제로 고유한 검증 후보만 체크.

### PIR-06: 공통 UI 디자인·배포·실자료 수락 (P1)
- RF-201/203 공통 카드·폼·버튼·배지·시각 상태. 모바일/데스크탑·light/dark·200% E2E.
- 운영 읽기전용 수락: 기존 수입 먼저 발생한 여행, 실제 확인된 보험 명단, 1대다 연결, 0명·부분/완료 차이.
- 실제 배포는 Supervisor가 승인된 SHA, health/auth, 참가자/장부 DB 무변경(명시 연결 저장 제외), Google 쓰기 0으로 검증.
- **완료:** UI 수락/운영 DB 동일성, 실제 여행의 명단·수입 대조 정확성. 문서 병합만으로 완료 처리 금지.

## 10. 테스트 행렬

1. Google 3행(실명 1·닉네임 1·그룹입금 1) 먼저 생성, 보험 확정 명단 0명 → 수입 3행 유지, 가입 확정 0, 체크 0.
2. 2일 뒤 보험 확정 실명 3명 수신, 실명 1건만 유일 자동 체크, 닉네임 행은 미연결/후보.
3. 보험 `박예시` 카드를 `산책냥이` 수입 행에 드롭→확인→✓ 박예시; 다시 드롭→ 중복 링크/감사 삽입 0.
4. 그룹 입금 1행에 2명 연결 확인 → ✓ 2명; 원래 Google 금액 단 한 번 집계, 자동 나누기 없음.
5. 같은 보험인에게 2회 입금 행 연결 → 각 원행 보존, 인원 1명.
6. 여러 동명이인 및 별칭 충돌 → 자동 체크 0, 수동 확인만.
7. 수동 연결 후 취소/해제하면 자동 재매칭으로 되살아나지 않음.
8. Google 원금액/행 변경, 보험 roster revision 갱신, stale view에서 연결 POST 409, 원본 무변경.
9. `scope=partial`에 2명 등록 → 2명은 확정일 수 있지만 여행 전체 인원 확정 아님.
10. 보험가입 완료 증빙 누락한 명단 → ‘가입 확인 전’, 자동 체크 0; 영수증만 `registered` 표시한 경우 무조건 가입확정 아님.
11. 권한 없는 세션/공개 여행 탭에 실명·수입 연결 상태 누출 0, DOM/JSON 네트워크에도 없음.
12. Drag/drop와 모바일 검색 선택 버튼은 같은 검증·저장·해제 상태; 키보드/200%/390px 동작.
13. 참가자 DB 미구성/Google stale/HTTP 오류를 ‘명단/수입 0건’으로 잘못 표시하지 않음.
14. 동일 보험 명단 재전송·정정 revision 후에도 기존 수입 연결과 1명=1 identity 보존.
15. Google B:H TSV, 기존 수입·지출 표 금액/행 해시, 카드/OTA/보험 원본 데이터가 연결 작업 전후 불변.
16. 수입→보험→지출 순서에 항공권 영역이 나중에 추가돼도 기존 독립 읽기 계약을 준수.

## 11. 승인/범위와 아직 남긴 정책 질문

**이미 확정:** 보험 완료 명단 최우선, 수입 먼저·닉네임 허용, `보험 등록` 체크 열, 미연결 명단의 드래그 명시 연결, 수입→보험→지출 순서, owner-only 보험명단, Google 수입 원본 불변, 20건 목록, 모바일 대체 버튼, 사용자의 수동 관계 최상위.

**후속에만 필요한 질문:** 참가자별 ‘여행비 완납’ 산출 기준(여행 가격/환불/분할/공동입금)의 유무. 이번 범위는 **입금행 연결·기존 수입 금액 조회만** 구현하고, 참가자별 완납 여부/입금액 배분을 독자 확정하지 않는다. 필요 시 새로운 제품 정책으로 명세화한다.

## 12. 완료 주장 금지

현재 기능은 일부 재사용 가능하지만, 통합 여행 탭 보험 체크/드래그 UI는 **실제 구현되지 않았다**. 이 문서가 main에 병합돼도 `SPEC_ONLY`다. 다음 구현자는 PIR-01~06을 코드/테스트/병합/운영/실자료 수락으로 각각 기록해야 한다.
