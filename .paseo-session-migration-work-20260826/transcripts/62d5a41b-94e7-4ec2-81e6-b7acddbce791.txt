[User] 당신은 아키텍처 검토 모델이다. 파일을 읽지 말고 아래 제공된 정보만으로 검토하라. 한국어로 답변하라.

## 현재 파이프라인 (㈜숲길여행, 소규모 여행 법인, 1인 운영)

### 기술 스택
- **입력**: 카드사 RAW CSV(4곳), 수기장부 CSV, OTA 데이터, Gmail 영수증
- **처리**: Python 스크립트 8단계 순차 (build_v13 → fix_v14 → patch_v14 → build_workbook → gen_rev × 2 → consolidate)
- **저장소**: SQLite DB + Google Sheets 원장 (단일 시트, 여행탭 41개)
- **출력**: Excel 워크북 (36시트, 1,833행, ~320M원)
- **자동전기**: Apps Script → Google Sheets 직접 기록

### SQLite 스키마 (도메인 분리 모델 v2, 테이블 15개+)
- 원천: source_documents, source_records, direct_source_records
- 결제: payment_methods, payment_transactions, transaction_sources, cancellations
- 배분: allocation_plans, allocations, allocation_targets
- 예약/여행: reservations, trips
- 판정/근거: decisions, evidence
- 장부: journal_entries, journal_line_items
- 검증: review_snapshots, baselines

### 현재 파이프라인 실행 (8단계)
```
cd ledger
python3 build_v13_trip.py       # CSV + 수기 → classified_v13
python3 fix_v14.py              # v13 + cardindex → classified_v14
python3 patch_v14.py            # 수기 마스터 재주입
cd data
python3 build_workbook_v76.py   # → Excel 워크북
python3 gen_april_rev.py        # → 4월 매출확인자료
python3 gen_mayjun_rev.py       # → 5-6월 매출확인자료
python3 consolidate_2q.py       # → 2분기 통합
```

### 현재 문제
- Google Sheets를 "원장"으로 쓰되 처리는 오프라인 Python
- Apps Script가 별도로 Sheets에 자동전기
- 수기장부와 자동분류가 분리
- 워크북 버전이 76까지 감 (build_workbook_v64~v76)

## 검토 대상
"비용 파이프라인을 수기+자동화 통합 관리하는 웹앱으로 전환"

## 아키텍처 관점 검토 포인트
1. **아키텍처 선택**: 현재 Python 스크립트 체인 → 웹 서비스 전환 시 적절한 패턴은?
2. **데이터 레이어**: SQLite → PostgreSQL? 아니면 SQLite 유지 + 웹 프론트만?
3. **Google Sheets 대체**: 자동전기를 어떻게 통합? 웹앱이 Sheets를 대체하는가?
4. **배포**: Vercel? self-hosted? 1인 운영 환경에서 적절한 선택?
5. **전환 전략**: Big Bang vs 점진적 마이그레이션?
6. **비용**: 인프라 운영 비용 vs 현재 무상 (Google Sheets + 로컬 Python)

구체적 아키텍처 제안과 전환 경로를 포함한 검토 결과를 제시하라.
제공하신 정보만을 기준으로 검토하겠습니다. 파일·외부 자료는 보지 않으며, 독립적인 반대 관점 검토도 병행합니다.
[Independent arch review] independent_arch_review
제공된 정보만 기준으로 보면, 전환은 타당합니다. 다만 목표는 “Python을 웹으로 재작성”이 아니라 **수기 입력·자동분류·전기·산출물의 권위 원장을 하나로 만드는 것**이어야 합니다.

현재 v2 도메인 분리 스키마는 좋은 출발점입니다. 반면 8단계 스크립트, Sheets, Apps Script가 각각 판정·전기를 갖는 구조는 웹앱으로 그대로 옮기면 분리 문제가 재현될 가능성이 큽니다.

```text
CSV / Gmail / OTA / 수기 입력
            ↓
 원본 보관·해시·수집 이력 (불변)
            ↓
정규화 → 분류/판정 → 배분 → 대사 → 승인
            ↓
 PostgreSQL 권위 원장
      ├─ 웹 검토·수정 UI
      ├─ Excel·매출확인자료 생성
      └─ 동기화 Outbox → Google Sheets
```

| 검토 항목 | 권고 |
|---|---|
| 아키텍처 | Python 기반 **모듈러 모놀리스 + 백그라운드 워커** |
| 데이터베이스 | 운영 권위 원장은 PostgreSQL |
| Sheets | 즉시 폐기하지 말고, 권위 원장 지위만 종료 |
| Apps Script | 업무 규칙·직접 전기 기능을 제거하고 얇은 동기화 계층으로 축소 |
| 배포 | 관리형 컨테이너 PaaS + 관리형 PostgreSQL |
| 전환 | Big Bang이 아닌 병렬 검증형 점진 전환 |

### 권장 구현 형태

1인 운영과 기존 Python 자산을 고려하면, 마이크로서비스·Kubernetes·Kafka는 과합니다.

- Django 같은 Python 웹앱: 내부 검토 화면, 수기 입력, 승인, 관리자 기능
- 단일 코드베이스의 도메인 모듈:
  `수집 → 정규화 → 분류 → 배분 → 대사 → 전기 → 검증 → 내보내기`
- 별도 백그라운드 워커: Gmail/OTA 수집, 대용량 Excel 생성, 재분류, Sheets 동기화
- 객체 저장소: CSV·영수증·첨부파일 원본 보관
- PostgreSQL: 거래·판정·근거·전기·처리 이력의 권위 저장소

기존 15개 이상 테이블은 버리지 말고 유지·정리하는 편이 낫습니다. 다만 아래 통제 테이블은 추가하는 것이 좋습니다.

- `import_batches`: 어떤 원본을 언제 가져왔는지
- `processing_runs`, `processing_run_steps`: 어떤 코드·규칙으로 무엇을 실행했는지
- `rule_versions`: 분류·배분 규칙의 버전
- `review_tasks` 또는 승인 상태: 사람 수정과 확정의 분리
- `sync_outbox`, `sync_attempts`: Sheets/Excel 전송의 멱등 처리와 실패 재시도
- `audit_events`: 원본·자동판정·사람 수정·전기 확정의 변경 이력

핵심 원칙은 원천 거래를 직접 덮어쓰지 않는 것입니다. 수기 수정은 `decisions`·`evidence`·`allocations`에 새 판정으로 남기고, 승인된 판정만 `journal_entries`를 만들게 해야 합니다.

### SQLite와 PostgreSQL

데이터량 때문에 PostgreSQL이 필요한 것은 아닙니다. 1,833행이나 3.2억 원 규모는 기술적으로 작습니다. 필요한 이유는 웹 UI, 자동수집, 백그라운드 작업, Sheets 동기화가 함께 쓰기를 시작할 때의 잠금·복구·감사 추적 때문입니다.

- 초기 그림자 운영 단계에서는 SQLite를 유지할 수 있습니다.
- 그러나 웹앱을 실제 원장으로 승격하기 전에는 PostgreSQL로 옮기는 것을 권합니다.
- SQLite는 로컬 개발, 재현용 스냅샷, 단일 사용자 오프라인 도구로 남길 수 있습니다.

### Google Sheets와 Apps Script

웹앱이 대체해야 하는 것은 Sheets 자체가 아니라 **Sheets의 원장 권위**입니다.

전환 후에는 다음처럼 두는 것이 안전합니다.

- PostgreSQL: 유일한 거래·판정·전기 원장
- Google Sheets: 조회, 회계사 공유, 익숙한 보고 화면, 내보내기 대상
- Apps Script: 필요 시 승인된 전기 배치를 받아 쓰는 얇은 동기화기만 담당

Apps Script와 웹앱이 동시에 원장에 쓰는 이중 쓰기 기간은 최소화해야 합니다. 유지가 불가피하면 모든 전기 배치에 고유 키를 두고, 같은 배치가 재실행되어도 중복 행이 생기지 않게 해야 합니다.

### 배포 판단

기본 선택은 **관리형 컨테이너 PaaS + 관리형 PostgreSQL + 객체 저장소**가 적합합니다.

Vercel은 대시보드나 프론트엔드에는 적합할 수 있지만, 현재처럼 Python 배치·대용량 Excel 생성·수집·재시도가 핵심이면 Vercel만으로 운영 엔진을 구성하기보다 별도 워커가 필요합니다. 그 경우 배포 체계가 둘로 나뉩니다.

따라서 1인 운영에서는 다음이 더 단순합니다.

- Python 웹앱과 워커를 같은 저장소·같은 컨테이너 계열로 운영
- 웹 프로세스와 워커 프로세스만 분리
- DB 백업·복구 테스트·비밀정보 관리만 관리형 서비스에 맡김

직접 VPS를 운영하는 방식은 현금비용은 낮을 수 있지만, 보안 패치·백업·장애복구 책임까지 혼자 가져오므로 기본 선택으로는 권하지 않습니다.

### 전환 경로

Big Bang은 비권고입니다.

1. **기준선 고정**  
   현재 워크북 36시트, 1,833행, 약 3.2억 원을 회귀 기준으로 보관합니다. 단순 총액뿐 아니라 카드·월·여행·취소/환불·분개별로 비교해야 합니다.

2. **기존 Python을 실행 가능한 모듈로 감싸기**  
   v13~v76 로직을 즉시 재작성하지 말고, 먼저 실행 ID·입력 해시·규칙 버전·단계별 결과를 남기는 작업 실행기로 감쌉니다.

3. **웹 UI는 수기 수정과 검토부터**  
   수기장부를 별도 CSV로 재주입하는 대신, 웹에서 판정·근거·배분을 기록하게 합니다. 이 단계의 결과는 기존 산출물 형식을 계속 유지합니다.

4. **그림자 병렬 실행**  
   같은 입력으로 기존 체인과 새 엔진을 여러 결산 주기 동안 병렬 실행하고, 모든 차이에 사유를 붙입니다.

5. **PostgreSQL을 권위 원장으로 승격**  
   거래 단위 대사, 차변·대변 일치, 취소·부분취소, Sheets 재전송 멱등성, 백업 복구가 검증된 뒤 전환합니다.

6. **Sheets 직접 쓰기 종료**  
   Apps Script의 독립 전기 로직을 끄고, 웹앱에서 확정한 전기 배치만 Sheets로 동기화합니다.

7. **구형 스크립트 정리**  
   안정화 후에만 v64~v76 같은 버전별 산출 스크립트를 폐기합니다. 과거 산출물과 실행 기록은 읽기 전용으로 보존합니다.

### 비용 판단

현재는 인프라 현금비용이 거의 없지만, 수기 재주입·버전 추적·이중 원장·재현 실패의 운영비용이 누적됩니다.

새 구조의 최소 직접비는 관리형 DB, 앱/워커 실행 환경, 원본 파일 저장소, 백업·모니터링입니다. 현재 정보만으로 공급자별 금액을 산정할 수는 없지만, 이 규모에서는 고가의 자동확장·다중 리전·복잡한 메시지 플랫폼 없이 소규모 관리형 구성으로 시작하는 것이 맞습니다.

최종 권고는 **PostgreSQL 기반 모듈러 모놀리스 + 단일 백그라운드 워커 + 웹 검토 UI + 기존 Excel/Sheets 호환 출력**입니다. 첫 성공 기준은 화면 완성도가 아니라, 동일 입력에서 기존 결과를 재현하면서 수기 수정과 자동 판정이 하나의 감사 추적 안에 들어오는 것입니다.

AGY_ACP_UNAVAILABLE: 이 세션에는 Paseo AGY ACP 호출 경로가 제공되지 않아, 제공된 정보만으로 직접 검토했습니다.
