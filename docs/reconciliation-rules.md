# 대사 규칙 (카드 거래 ↔ 예약 ↔ 여행)

이 문서는 카드 거래를 여행에 배정하는 규칙의 현재 동작을 적는다. 규칙 값과 판정 함수는 `app/reconciliation.py`에 모여 있다.

## 1. 날짜의 의미

| 날짜 | 출처 | 쓰는 곳 |
|---|---|---|
| 카드 이용일 | 명세에 `이용일` 열이 있을 때 (H.xlsx, G.xlsx) | 카드 거래의 날짜. `approval_date` 칸에 들어간다 |
| 카드 승인일 | 명세에 `승인일` 열만 있을 때 (E, F, KB) | 이용일이 없을 때 카드 거래의 날짜 |
| 매입일(청구일) | 모든 명세 | 대사에 쓰지 않는다 |
| 예약 이용기간 | OTA 확정·완료 메일 (숙박: 체크인~체크아웃, 항공: 가는편~오는편) | 여행과 겹치거나 덮는지 판정 |
| 여행 기간 | 여행 탭 (시작일~종료일) | 종료일은 마지막 이용일을 포함한다 |

- 카드 이용일과 예약 이용기간은 다른 날짜다. 카드 쪽은 `card_use_date()`, 예약 쪽은 `covers_stay()` / `overlaps_stay()`로 판정한다.
- 숙박은 밤 단위로 본다. 여행의 밤은 시작일 밤부터 종료일 전날 밤까지다(종료일은 체크아웃하고 돌아오는 날). 그래서 숙박이 여행 안이려면 체크인 ≥ 시작일, 체크아웃 ≤ 종료일이어야 한다. 여행 종료일에 체크인하는 숙박은 그 여행과 겹치지 않는다(다음 일정의 숙박이다). 시작일에 체크아웃하는 숙박도 겹치지 않는다.
- 항공은 출발일과 도착일을 모두 이용일로 본다. 여행 종료일에 출발하는 귀국편은 그 여행과 겹친다.

## 2. 배정 순서 (앞이 우선)

1. **사용자 판단**: 장부 기록이 `user_decision`, `user_exception`이거나 장부에 기록된 거래는 자동 분류가 바꾸지 않는다.
2. **소유자가 예약마다 고른 여행** (`owner-ota-booking`): 그 예약의 카드 거래에만 적용한다. 같은 원본의 자동 예약 초안을 대체한다 (`card_flow._classify`의 `owned`).
3. **예약 이용기간 (확정 예약)**: 확정·완료·예정 예약의 이용기간을 덮는 검증된 여행이 **하나뿐**일 때 배정한다. 예약 기간 초안(`card_flow._classify`)과 자동 배정(`ota_catalog._period_trip`)이 같은 기준을 쓴다. 수집됨 예약은 배정하지 않고 후보로만 보여 준다.
4. **현지 카드 구매 (국가 일치)**: 카드 날짜가 같은 나라의 여행 기간 안이면 배정한다 (`retail_trip`).
5. **추론 배정** (`inference`, 가장 낮은 우선순위): 위 단계에서 여행이 정해지지 않았을 때만 본다. 확신도가 높은 쪽의 근거를 쓴다.
   - 소유자가 승인한 추론(`owner-authorized-inference-20261003`)은 카드 날짜가 여행 시작보다 30일(`LEAD_DAYS`)을 넘게 앞서면 자동 배정하지 않고 확인 대상으로 둔다.

## 3. 확정 여부

- 예약 메일의 제목에 `확정`이 있으면 확정으로 본다. 숙박 메일과 결제 대사 모두 같은 규칙을 쓴다 (`ota_mail.extract_mail`, `lodging_mail_facts`, `lodging_mail_matches`).
- 확정 상태는 `confirmed`, `completed`, `upcoming`이다 (`CONFIRMED_STATUSES`).
- 결제 메일만 있고 확정 메일이 없으면 `observed`(수집됨)이며, 이용기간으로 배정하지 않는다.
- 취소 메일은 `cancelled`이다.

## 4. 여행의 검증

- 자동 배정 대상 여행은 `trip_valid`를 통과해야 한다. 여행 탭의 `source_sha256`이 권한 파일(`trip-authority.json`)의 기록과 같고, 그 기록이 가리키는 증거 파일의 일정과 같아야 한다.
- 권한 파일이나 증거 파일을 바꾸면 여행 탭의 `source_sha256`도 같이 바꿔야 한다. 현재 이 값을 바꾸는 정식 경로가 없다 (미해결 1).

## 5. 판정 함수 요약

| 함수 | 위치 | 의미 |
|---|---|---|
| `card_use_date(tx)` | reconciliation | 카드 이용일 또는 승인일 |
| `covers_stay(ts, te, ci, co, service=)` | reconciliation | 체크인(출발일) ≥ 시작일이고 체크아웃(도착일) ≤ 종료일 |
| `overlaps_stay(ts, te, ci, co, service=)` | reconciliation | 숙박은 여행의 밤이 하나라도 겹침, 항공은 이용일이 하루라도 겹침 |
| `payment_within_lead(day, ts)` | reconciliation | 여행 시작 30일 이내 |
| `_period_trip(candidates)` | webapp/ota_catalog | 검증된 여행 중 덮는 여행이 하나뿐인지 |
| `_relation(stay, trip, service=)` | webapp/ota_catalog | 덮음 / 일부 겹침 / 없음 |
| `booking_trip(tx, period)` | webapp/card_flow | 예약 기간 초안의 대상 여행 확인 |
| `retail_trip(tx, country)` | webapp/card_flow | 현지 구매 또는 추론 여행 확인 (30일 규칙 포함) |

`service` 인자는 항공 예약일 때 참이다. 항공 여부는 예약 라벨에 `항공`이 있는지로 판단한다 (`ota_catalog._build_index`), 또는 예약 기간 초안의 `item == 항공료`로 판단한다 (`card_flow._classify`).

## 6. 이번 리팩토링에서 바뀐 것

- 날짜 판정이 세 곳(card_flow 두 곳, ota_catalog 한 곳)에서 같은 함수로 모였다.
- 숙박 판정은 배포된 코드와 같다(체크아웃 ≤ 종료일이면 덮음, 체크인이 종료일이면 겹치지 않음). 한때 마지막 숙박일 기준으로 바꿨으나, 여행 종료일 체크인을 겹침으로 표시하는 오류가 생겨 되돌렸다.
- 항공은 이용일(출발·도착일)을 포함해 비교한다. 이전에는 숙박과 같은 기준이라 종료일 출발 귀국편이 겹침에서 빠졌다.
- 자동 배정의 "하나뿐" 판정은 검증되지 않은 덮는 여행도 셌다. 지금은 검증된 여행 중에서만 센다.
- 출처 이름과 확정 상태 집합을 `app/reconciliation.py`로 옮겼다. 기존 import 이름은 `app/classify.py`에서 그대로 쓸 수 있다.

운영 색인 비교 결과 (같은 데이터, 이전 코드와 새 코드): 자동 배정이 바뀌는 예약 13건(모두 이전에 배정 없음), 덮음/겹침 판정이 바뀌는 예약 24건, 후보 목록에 추가된 여행 175건(제거된 것은 없음). 13건에 연결된 카드 거래 5건은 다음 분류 때 이용기간 규칙으로 배정된다.

## 7. 아직 정해지지 않은 것 (미해결)

1. **여행 검증 해시의 갱신 경로가 없다.** 권한 파일이나 증거 파일을 바꾸면 여행 탭을 직접 고쳐야 한다. 정식 갱신 명령이 필요하다.
2. **현지 구매의 나라 매핑이 코드에 하드코딩되어 있다** (`card_flow.retail_trip`의 `countries` 표). 새 행선지는 자동으로 매칭되지 않는다. 여행 데이터의 나라 항목으로 옮겨야 한다.
3. **과거 장부 재사용에 이용기간 가드가 없다.** 같은 카드·승인일·금액의 과거 배정이 이용기간 근거와 충돌해도 재사용된다 (재대사에서 13건). 충돌하면 재사용하지 않는 규칙을 추가해야 한다.
4. (해결) 여행 종료일 체크인 숙박은 겹치지 않는 것으로 판정한다.
5. **소유자가 승인한 추론 규칙 140건**이 저장되어 있다. 이 규칙들의 근거 문구는 "결제 뒤 가까운 여행"이 대부분이다. 30일 규칙의 적용 대상이지만, 저장된 규칙 자체를 정리할지는 정해지지 않았다.
6. 같은 판정이 두 경로에 남아 있다. 예약 기간 초안(`card_flow._classify`)과 자동 배정(`_booking_period_assignments`)이다. 두 경로는 같은 판정 함수를 쓰지만 호출 흐름이 나뉘어 있다.
