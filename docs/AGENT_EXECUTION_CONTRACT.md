# 여러 에이전트의 공통 목표와 멱등 실행 규약

이 문서는 에이전트가 작업을 선택하고 결과를 수용하는 공통 기준이다. 모든 파이프라인이 이 기준을 이미 구현했다는 선언은 아니다. 업무 판단의 근거와 미결정 사항은 [결정 등록부](DECISION_REGISTER.md), 실행 상태는 최신 인계, 원천별 상세 규칙은 [비용 규칙 원장](비용분류_지시사항_원장.md)에서 확인한다.

## 목표

전 기간의 실제 비용 이벤트를 누락·증폭·중복 없이 보존하고, 검증된 관계와 명시 여행 일정으로 비용을 설명한다. 검토 화면·워크북·장부는 같은 확정 결과를 소비해야 한다. 에이전트나 실행 순서가 달라져도 업무 결과는 같아야 하며, 실행을 반복해 비용이나 전표가 추가로 생겨서는 안 된다.

확정 근거가 없는 결과를 만들어 자동 분류율을 높이지 않는다. 원천 무결성, 금액 보존, 관계 검증, 여행·계정·비용 성격, 화면 표시, 외부 전기는 각각 구분해서 확인한다. 미결정 사항과 오류는 원인을 기록하고 해당 결과의 승격만 막는다. 그 결정과 무관한 코드 검토·합성 테스트·문서 정리는 계속할 수 있다.

## 무엇을 같다고 비교하는가

| 대상 | 비교 기준 | 취급 |
|---|---|---|
| 원본 파일과 개별 산출물 | 전체 바이트의 `sha256` | 파일 변조·입력 교체·감사 불일치를 검출한다 |
| 업무 결과 | 버전이 명시된 정규화 표현의 `semantic_sha256` | 같은 입력과 규칙의 반복 계산 및 행순서 변경을 비교한다 |
| 실행 시도 | `attempt_id`, 실행 시각, 담당 에이전트 | 감사 기록에 남기되 업무 결과의 새 이벤트로 취급하지 않는다 |
| 원천 범위 | 안정 원천 키와 원천 digest 집합 | 파일명이나 가장 최근 수정 시각만으로 선택하지 않는다 |
| 외부 효과 | 원장 범위·안정 이벤트 키·효과 종류·분할 식별자 | 실행 ID가 달라져도 같은 효과를 다시 반영하지 않는다 |

같은 원천, 규칙 버전, 스키마 버전, 적용 결정 집합은 같은 업무 결과를 만들어야 한다. 실행을 식별할 때 이 입력들의 digest를 모두 결속한다. 원천·규칙·스키마·결정이 바뀌면 새 계산이며, 이전 실행의 권위를 그대로 재사용하지 않는다.

의미 비교에서는 정렬된 행 집합과 **모든 업무 필드**를 사용한다. 금액·부호·통화·이벤트 식별자·예약 관계·여행·계정·상태·전기 가능 여부를 빼면 안 된다. 제외 가능한 운영 메타데이터는 각 버전 계약에 명시한다. 모든 날짜나 모든 해시를 일괄 제거하는 구현은 금지한다. 서비스일과 근거 digest는 단순 실행 시각과 다르다.

생성 시각이 달라진 두 SQLite 파일의 전체 해시는 다를 수 있다. 각 파일은 각각의 감사 해시와 일치해야 하고, 업무 의미는 같아야 한다. 전체 합계만 같은 두 결과는 멱등성 증명이 아니다. 원천 이벤트별 행과 금액을 대조한다.

## 재시도와 중복 처리

1. 같은 입력을 새 작업공간에서 다시 계산하면 같은 업무 결과가 나와야 한다. 입력 순서와 에이전트 이름이 판정의 우선순위가 되어서는 안 된다.
2. 기존 결과를 재사용하려면 입력·규칙·스키마·결정·결과 해시와 완료 상태를 먼저 검증해야 한다. 검증된 결과에 대한 성공적인 `NOOP`는 명시적으로 구현되고 테스트된 경로만 사용할 수 있다.
3. 기존 출력 경로를 거부하고 파일을 보존하는 동작은 **안전한 재시도 거부**다. 이것만으로 성공적인 멱등 재개가 구현됐다고 보고하지 않는다. 현재 v5 shadow 빌더는 이 동작을 사용한다.
4. 동일 효과 키와 동일 내용의 외부 반영은 한 번만 존재해야 한다. 같은 키인데 내용이 다르면 충돌로 남기고, 새 실행 ID를 붙여 두 번 반영하지 않는다. 이미 반영된 결과의 정정은 독립 근거가 있는 정정 경로에서 처리한다.
5. 외부 쓰기가 timeout이면 성공 여부를 먼저 조회한다. 같은 키·내용이 확인되면 결과를 기록하고, 미반영이 확실할 때만 재시도한다. 조회할 수 없으면 `OUTCOME_UNKNOWN`으로 보류한다. 새 키로 재전송하지 않는다.
6. 같은 금액·가맹점·날짜라는 이유로 서로 다른 실제 거래를 삭제하지 않는다. 한 예약의 여러 청구·취소·환불도 독립 이벤트다. 중복 수집과 실제 복수 거래를 구분한다.

## 에이전트가 작업을 시작할 때

`AGENTS.md` → 최신 인계 → 이 규약과 결정 등록부 → 해당 원천의 상세 규칙 순으로 읽는다. `CLAUDE.md`는 `AGENTS.md`로 연결하는 진입 파일이며 업무 규칙을 별도로 복제하지 않는다.

각 작업 명세에는 아래 항목만 간결하게 적는다. 원장 전체나 긴 대화 이력을 다른 에이전트에게 반복 전달하지 않는다.

```text
task_id:
목표와 범위:
담당 에이전트와 실제 모델/추론 설정:
기준 커밋과 시작 시 로컬 변경:
입력 원천/manifest와 해시:
적용 결정 ID와 규칙/스키마 버전:
수정 가능한 파일과 단독 작성자:
산출물 위치:
검증 명령과 성공 조건:
미결정 의존성:
중단 시 완료 상태와 다음 동작:
```

구현 모델은 현재 적용되는 전역 위임 규칙과 이후의 명시적 사용자 지시를 따른다. 이 저장소의 현재 기본 구현자는 `opencode/muse-spark-1.3-contributor-free`이며 호출 전에 실제 제공 목록과 무료 여부를 확인한다. Luna Max·Reserve Max 선택은 과거 실행 기록이다. Jev는 전역 규칙에 따른 제한된 선택 보조이며 코드 작성자로 대체하지 않는다. 실제 호출이 불가능하면 원인과 구현 대기 범위를 알리고 문서·로컬 검토는 계속한다. 특정 모델의 이름은 업무 규칙이나 원천 권위가 아니다.

## 병렬 작업과 인수인계

- 같은 파일·DB·외부 효과에는 작성자를 하나만 둔다. 독립적인 코드 변경은 별도 작업공간에서 진행하고 코디네이터가 검토해 통합한다. 작업 중인 에이전트에 새 프롬프트를 보내 실행을 끊지 않는다.
- 실행기가 여러 작성자를 지원하려면 원자적 소유권 획득과 이전 소유자의 늦은 쓰기 차단이 검증돼야 한다. 이 기능이 없는 경로는 단일 작성자로 실행한다. 단순히 파일에 담당자 이름을 적는 것은 동시 실행 잠금이 아니다.
- SQLite 원천은 읽기 전용의 봉인된 스냅샷으로 취급한다. 부속 파일이 남으면 원본을 수리하거나 체크포인트해 통과시키지 않는다. 원천 파서는 실행당 한 번만 수행하고 마지막에는 바이트 해시로 변경을 확인한다.
- Agoda는 별도 전용 Paseo IAB 세션 소유권과 재시도 한도를 그대로 적용한다. 이 공통 규약이 브라우저 제한을 완화하지 않는다.
- 각 단계는 임시 결과를 검증한 뒤 완료를 기록한다. 중단 후에는 마지막 명령이 실행됐을 것이라고 추정하지 말고 실제 파일·해시·완료 증거를 확인한다. 덮어쓰기나 새 키 생성으로 실패를 숨기지 않는다.
- 인계에는 완료한 변경, 실제 테스트 결과, 입력·산출물 해시, 미결정 ID, 외부 효과의 실행 여부를 기록한다. 기존 실패·생략·미검증을 성공으로 합산하지 않는다.

## 최소 수용 검사

| 검사 | 수용 조건 |
|---|---|
| 서로 다른 작업공간의 두 번 계산 | 같은 입력과 규칙에서 의미 해시와 행별 업무 값이 같음 |
| 입력 순서 반전·셔플 | 의미 결과가 같음; 정렬 순서로 모호한 매칭을 강제하지 않음 |
| 단일 의미 필드 변경 | 관련 의미 해시가 달라지며 기존 결과를 같은 실행으로 재사용하지 않음 |
| 실제 중복 수집과 동일 금액 복수 거래 | 같은 이벤트는 한 번, 다른 이벤트는 각각 보존 |
| 동일 출력 재호출 | 기존 결과가 변하지 않음; 성공 재사용과 충돌 거부를 구분 |
| 단계 중간 실패·외부 timeout | 완료 증거를 확인해 재개하며 중복 효과가 생기지 않음 |
| 원천·결정·규칙 변경 | 기존 권위를 stale로 판정하고 다시 검증 |
| 두 작성자의 경합 | 한 작성자만 효과를 만들고 나머지는 검증된 재사용 또는 충돌로 종료 |
| 후보·미결정·미검증 | 최종 전표·외부 쓰기로 승격되지 않음 |

일부 검사만 통과했다면 검증된 경로와 남은 경로를 구분해 보고한다. v5 shadow의 반복 계산 검증이 Apps Script의 원격 멱등성까지 증명하지는 않는다.

## 사용자에게 질문할 조건

이미 명시된 업무 규칙의 구현 오류, 오래된 감사표, 누락된 원천, 인코딩 오류, 테스트 환경 문제는 우선 에이전트가 조사한다. 사실을 확인할 도구가 있는데 사용자에게 가용성을 추측해 답해 달라고 요청하지 않는다.

테스트 생략 문구의 `pending approval`도 실제 동작을 확인한다. 예를 들어
`COST_ALLOW_PIN_DRIFT`는 검사를 활성화하는 스위치이며 테스트 기대값 변경 승인이 아니다.
기준값을 바꾸지 않는 읽기·합성 검사를 먼저 실행하고 결과로 판단한다. 준비된 원천이 필요한
검사는 그 파일과 해시를 확보하지 않은 채 환경 변수만 설정해 검증 완료로 표시하지 않는다.

동일한 적용 범위에 서로 다른 업무 결과를 요구하는 지시가 있고 우선순위를 확인할 수 없거나, 새로운 예외의 범위를 결정해야 할 때 질문한다. 질문에는 실제 충돌 사례, 선택에 따른 결과, 추천안, 답변 전 처리 방식을 포함한다. 답변·미답변·에이전트 제안을 구분해서 결정 등록부에 기록한다. “계속해”와 시간 경과를 특정 선택지의 동의로 기록하지 않는다.
