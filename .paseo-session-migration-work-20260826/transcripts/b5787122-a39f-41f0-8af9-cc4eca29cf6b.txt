
### 현재 자동화 수준
- 분류·대사·워크북 생성은 Python으로 자동화 (테스트 90개+)
- 카드사 RAW → Google Sheets 자동전기는 Apps Script
- **수동 작업**: 카드사 CSV 다운로드(OTP 필수), 수기장부 입력, 여행 매핑, 특수건 처리, 최종 사업적 판단

### 현재 문제 (사용자 관점)
- 파이프라인이 구글 스프레드시트를 참조 (다운로드 → 오프라인 처리 → 엑셀 출력)
- 스프레드시트는 "비용있고, 지출있고" 단순 구조
- 수기+자동화가 분리
- Python 스크립트 체인이 복잡 (8단계)

## 검토 대상
"비용 파이프라인을 수기+자동화 통합 관리하는 웹앱으로 전환"
- 구글 스프레드시트를 대체하는 웹 인터페이스
- DB 기반으로 웹에서 직접 입력·조회·수정
- 자동분류 결과를 웹에서 검토·승인

## 검토 포인트 (각각에 대해 반박 포함 균형 분석)
1. **타당성**: 이미 SQLite 도메인 모델이 정교한데, 웹앱이 추가하는 가치는?
2. **리스크**: 전환 비용 vs 기대 효과. 작동 중인 파이프라인을 왜 바꾸나?
3. **대안**: Python CLI + SQLite + 간단한 로컬 UI(Streamlit 등) vs 완전한 웹앱
4. **실용성**: 1인 운영 법인에 웹앱 운영·유지보수 부담
5. **기술적 위험**: Google Sheets 의존성 제거 시 Apps Script와의 관계

핵심 결론을 먼저 제시하고, 각 포인트를 분석하라.
## 핵심 결론

전환 자체는 타당하지만, 지금 당장 Google Sheets와 기존 파이프라인을 폐기하고 완전한 웹앱으로 재구축하는 것은 과투자 가능성이 큽니다.

가장 실용적인 방향은 **SQLite를 단일 기준 데이터로 삼고, 그 위에 로컬 웹 UI를 추가하는 점진적 전환**입니다. 우선 자동분류 검토·승인, 여행 매핑, 특수건 처리, 수기 입력처럼 사람의 판단이 필요한 부분만 웹으로 통합하고, 기존 Python 산출물과 Google Sheets 자동전기는 당분간 유지하는 편이 안전합니다.

즉, 목표는 “웹앱 구축”보다 **수기 판단과 자동화 결과가 하나의 DB 상태·이력으로 연결되게 만드는 것**이어야 합니다.

참고로 제공된 실행 목록은 “8단계”라고 되어 있으나 명시된 스크립트는 7개입니다. 실제 전환 전에 실행 단계와 숨은 수동 단계를 정확히 목록화해야 합니다.

## 1. 타당성: 웹앱이 추가하는 가치

이미 정교한 SQLite 도메인 모델이 있으므로 웹앱은 새로운 회계 로직보다 다음과 같은 **운영 인터페이스**에서 가치가 있습니다.

- 자동분류 결과의 검토·승인·보류
- 미매핑 결제와 여행의 연결
- 특수건 및 예외 수정
- 원천자료·결제·배분·예약·여행·전기 결과의 연결 조회
- 수기 입력과 자동 처리 결과의 통합
- 누가, 언제, 무엇을, 왜 수정했는지에 대한 변경 이력
- 파이프라인 전체 재실행 없이 특정 건을 수정하고 재처리

현재 구조에서 가장 큰 문제는 계산 능력 부족이 아니라 **자동화 결과와 사람의 판단이 서로 다른 도구에 분리되어 있다는 점**입니다. 이 부분은 웹 UI가 잘 해결할 수 있습니다.

반박도 있습니다. 운영자가 한 명이고 SQLite를 직접 조회하거나 기존 Excel·Sheets만으로 충분하다면, 웹앱은 단순히 또 하나의 화면과 코드베이스를 만드는 결과가 될 수 있습니다. 특히 기존 Python 스크립트가 DB를 매번 재생성하거나 수정값을 덮어쓴다면, UI만 추가해도 통합 효과가 거의 없습니다.

따라서 선행 조건은 다음과 같습니다.

- 수동 판단을 DB에 영속적으로 저장
- 원천 사실, 자동 판정, 사용자 확정을 구분
- 확정된 사용자 판단을 재실행해도 보존
- 승인·보류·재검토 상태를 명시적으로 관리

## 2. 리스크: 전환 비용과 기대 효과

### 기대 효과

- Sheets 다운로드 및 파일 버전 혼선 감소
- 미처리·보류·승인 완료 건을 한 화면에서 관리
- 수기 수정의 재현성과 감사 가능성 향상
- 8단계 스크립트 체인을 하나의 작업 흐름으로 감쌀 수 있음
- 특정 건의 출처와 최종 산출물까지 추적 가능
- 향후 카드 RAW 수집을 제외한 대부분의 작업을 일관된 화면에서 수행 가능

### 주요 비용과 위험

- 기존 Python과 Apps Script 로직을 웹 백엔드에 중복 구현할 위험
- 기존 산출물과 새 시스템의 결과가 달라지는 전환기 이중 기준 문제
- DB 스키마 변경, 마이그레이션, 백업·복구 기능 추가
- 인증, 배포, HTTPS, 비밀정보 관리 등 웹 운영 업무 발생
- 수정 도중 일부 단계만 실행될 때 데이터 정합성이 깨질 가능성
- 편리한 수정 화면이 원천자료까지 변경하게 만들 경우 증거 보존 약화

“작동 중인데 왜 바꾸는가?”라는 반박은 유효합니다. 단지 UI가 낡았다는 이유로는 부족합니다. 다음 문제가 반복적으로 발생할 때만 투자 근거가 강해집니다.

- 수동 입력의 중복 또는 누락
- Sheets와 SQLite 사이의 불일치
- 어떤 판정이 최종인지 확인하기 어려움
- 전체 재실행 비용이 큼
- 예외 처리 근거가 사람의 기억에 의존
- 월·분기 마감 때 같은 수작업을 반복

이 문제가 크지 않다면 기존 시스템을 유지하고 작은 관리 화면만 추가하는 것이 낫습니다.

## 3. 대안: 로컬 UI와 완전한 웹앱

| 선택지 | 장점 | 단점 | 적합성 |
|---|---|---|---|
| 기존 CLI 유지 | 변경 비용과 장애 위험 최소 | 수기·자동화 분리가 계속됨 | 현재 불편이 작을 때 |
| Streamlit 등 로컬 UI | 빠른 구현, 배포·인증 부담이 작음 | 복잡한 편집·상태 관리와 장기 유지에는 한계 | 1인 운영의 첫 단계로 가장 적합 |
| 로컬 전용 정식 웹앱 | UI와 도메인 로직을 체계적으로 설계 가능 | 개발량 증가, 프로세스 운영 필요 | 로컬 UI로 가치가 검증된 뒤 |
| 클라우드 웹앱 | 어디서나 접근, 다중 사용자 확장 가능 | 보안·인증·백업·운영 부담이 가장 큼 | 다중 사용자나 원격 접근이 실제 필요할 때 |

권고 순서는 다음과 같습니다.

1. 기존 Python 로직을 재사용 가능한 서비스 함수로 정리
2. SQLite 위에 로컬 검토 UI 구축
3. 승인·보류·여행 매핑·특수건 처리만 먼저 이전
4. 기존 Excel 및 Sheets 결과와 병행 비교
5. 한두 번의 실제 마감에서 효과를 확인한 후 정식 웹앱 여부 결정

Streamlit은 검증용으로 적절하지만, 복잡한 동시 편집이나 세밀한 업무 흐름까지 영구적으로 맡기기에는 불편할 수 있습니다. 다만 1인 운영에서는 그 한계가 실제 문제가 되지 않을 가능성도 큽니다.

## 4. 실용성: 1인 법인의 운영 부담

1인 운영에서는 기능 수보다 다음이 중요합니다.

- 실행이 간단할 것
- 고장 났을 때 원인을 찾기 쉬울 것
- 백업과 복구가 쉬울 것
- 기존 CLI로 우회할 수 있을 것
- 배포나 서버 관리가 필요 없을 것

따라서 초기에는 인터넷 공개 서비스보다 **PC에서만 실행되는 로컬 웹앱**이 합리적입니다. 브라우저 인터페이스는 사용하되 서버는 로컬에서 실행하고, DB와 첨부파일은 정기 백업하면 됩니다.

반대로 “운영자는 한 명이므로 웹앱이 불필요하다”는 주장도 절반은 맞습니다. 다중 사용자 기능, 복잡한 권한, 알림, 실시간 협업은 불필요할 가능성이 높습니다. 그러나 1인 운영이라도 처리 건이 많고 몇 달 뒤 판정 이유를 다시 확인해야 한다면, 검토 큐와 변경 이력은 충분한 가치가 있습니다.

필요한 것은 SaaS급 제품이 아니라 **운영자용 내부 관리도구**입니다.

## 5. 기술적 위험: Sheets 제거와 Apps Script의 관계

Google Sheets를 제거하면 Apps Script 자동전기는 그대로 유지되기 어렵습니다. 현재 Apps Script가 카드 RAW를 읽어 여행탭 41개에 전기한다면, 웹앱 전환 시 다음 중 하나를 선택해야 합니다.

1. **Sheets를 최종 출력 대상으로 유지**

   SQLite가 기준 데이터가 되고, 승인된 전기 결과만 Sheets에 동기화합니다. 전환 위험이 가장 낮습니다.

2. **Apps Script를 API 연동 계층으로 변경**

   웹앱 API에서 데이터를 받아 Sheets에 쓰게 할 수 있지만, 인증·재시도·중복 전기 방지가 추가로 필요합니다.

3. **Python이 Sheets API로 직접 전기**

   Apps Script를 제거할 수 있지만, 현재 자동전기 규칙의 완전한 이식과 결과 대사가 필요합니다.

4. **Sheets와 Apps Script를 모두 폐기**

   웹앱과 Excel이 최종 시스템이 됩니다. 가장 단순해 보이지만 여행탭이 담당하던 조회·공유·업무 기능까지 대체해야 하므로 실제 전환 위험은 가장 큽니다.

권고는 1번입니다. 초기에는 **SQLite를 기준 원장으로 승격하되 Sheets는 호환 출력물로 유지**하십시오. 웹에서 승인된 건만 고유 전기 ID와 함께 Sheets로 보내고, 같은 ID는 재실행해도 중복 생성되지 않도록 해야 합니다.

전환기에는 다음 원칙이 특히 중요합니다.

- 원천 데이터는 수정하지 않고 정정 레코드를 추가
- 자동 판정과 사용자 확정을 별도 저장
- 승인된 데이터만 전기
- 전기 결과에 고유 ID와 버전 기록
- 부분 실패 후 재실행해도 중복되지 않도록 설계
- SQLite·Sheets·Excel의 합계와 건수를 자동 대사
- 기존 파이프라인을 즉시 제거하지 않고 복구 경로로 유지

## 최종 판단

**조건부 찬성**입니다.

완전한 웹앱 재개발은 현재 규모에 비해 부담이 클 수 있지만, 기존 SQLite 모델을 유지한 채 수기 판단 업무를 통합하는 로컬 웹 UI는 비용 대비 효과가 높습니다. 성공 기준은 화면의 완성도가 아니라 다음 세 가지입니다.

1. 자동 결과와 수동 판단이 하나의 DB에 남는다.
2. 승인 전후 및 수정 이력을 재현할 수 있다.
3. 기존 Excel·Sheets 결과와 자동 대사가 가능하다.

이 세 조건이 검증된 뒤에만 Google Sheets와 Apps Script의 폐기를 검토하는 것이 안전합니다.
