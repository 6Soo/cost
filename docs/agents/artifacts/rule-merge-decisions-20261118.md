# 판정 규칙 정밀 병합 — 사용자 결정과 미확정 경계 (2026-11-18)

> 이 기록은 [현행 판정 규칙집](../../DECISION_POLICY.md)과 [영역별 규칙](../../policy/README.md)의 변경을 추적하기 위한 **검수 증거**다. 실제 판정의 권위는 현행 규칙 문서에 있다. 운영 데이터·코드·DB는 이 작업에서 변경하지 않았다.

## 1. 확정: 사용자 질문 2의 B안 — 날짜/끝4가 모두 없는 OTA 관계

2026-11-18 사용자 답변: **“질문2 B”**.

- 기존 `LINK-002` 원칙의 카드 끝 4자리 또는 실제 결제일 대조 경로는 그대로 유지한다.
- 결제일과 카드 끝4가 모두 없더라도 **승인된 가맹점명/확장명, 같은 통화의 정확 금액, 끝자리 외에 검증 가능한 카드 식별 맥락**이 뒷받침하면 OTA↔카드 관계를 M:N으로 보존할 수 있다. `ITEM-080` 범위.
- 카드사명이나 금액 **단독** 일치를 확인된 개별 카드 식별로 확대하지 않는다. 명시적인 카드·발급사·공급자 충돌, 중복·원본 오류, 기존 수동 점유·고정 묶음·환불 보호는 유지한다.
- 사라진 결제일·끝자리는 창작하지 않는다. 관계 확인은 카드의 금융 확정·별도 장부 기장·Google 반영을 의미하지 않는다.
- 동기화한 명세: `docs/DECISION_POLICY.md` §3.5의 원칙, `LINK-002`, `DATE-026`, `ITEM-080`. 새 규칙 ID를 만들지 않고 기존 ID를 개정한다.

**남은 검증:** 실제 어떤 카드 식별 속성이 충분한지에 대한 구현의 증빙·반례 시험은 미실행이며, 일치/충돌·M:N·원행 1회 집계와 현재 M3/M6 차등 검증이 필요하다. 이 정책 개정 문서가 런타임 적용이나 수락을 뜻하지 않는다.

## 2. 질문 1 — 실제 기록에서 검증된 사실

[2026-11-01 OTA 무날짜·M:N 운영 조사](../../history/specs-20261110/ota-undated-many-to-many-20261101.md)의 **실제 운영 입력에 대한 기록**:

1. 트립닷컴 152,358원·395,000원 사건은 **이미 `MATCHED_AUTO/unique_exact_evidence`였다**. 여행 미배정·환불 보류와 카드 결제 미연결을 혼동했던 설명을 정정했다.
2. 395,000원 원결제에는 원승인번호로 355,000원 취소가 연결돼 있었다. **순잔액 40,000원**은 확인되지만, 그 돈이 위약금인지 또는 은행 환급이 끝났는지는 이 연결만으로 결론 내리지 않는다.
3. 트립닷컴 119,965원은 예약 둘과 카드 원행 하나의 관계를 M:N 2:1로 보존했다. 두 예약이 각각 실제 결제되었다는 뜻은 아니다.
4. 아고다 146,018원은 결제일 원문이 없었지만 가맹점·동액·카드 끝자리 일치로 관계를 보존한 다른 실제 사례다.

**핵심 한계:** 해당 공개 운영 기록에는 위 카드들의 **가맹점이 서로 다른 제3회사였는지, PG가 아닌 회사였는지, 카드 가맹점 별칭이 승인돼 있었는지**가 행별로 나와 있지 않다. 따라서 위 사건들을 “다른 회사·비PG인데 날짜/금액만 맞은 결제”의 검증된 실사례라고 주장할 수 없다. 실제 원행 상세·고객 원문은 Git 제외 보호 위치에 있다고 명시돼 있어 이번 규칙 정리에서 열거나 복사하지 않았다.

### 2.1 현행 규칙의 해석이 갈리는 경계

- **기본 조건 `LINK-002`:** 가맹점(원문/확장/승인 별칭) + 정확 동일 통화·금액 + 끝자리 또는 결제일. 명시된 공급자·카드·통화·금액 충돌이면 불허.
- **결제대행 `LINK-018`:** 카드 가맹점이 실제 결제대행사 이름으로 찍혔을 때 한해 가맹점 직접 일치를 대신해 검증 결제일=카드 이용일·정확 동액을 사용. PG가 아니라는 사실이 확인되면 이 예외는 적용되지 않음.
- **동일일 `DATE-023`:** 검증된 결제일과 같은 통화·정확 금액이 동일한데 **추가 끝자리·payment ID·승인 가맹점 별칭이 없는 것**만으로 연결을 막지 않음. 다만 “별칭 증거 없음”과 “명시된 다른 공급자”는 같지 않음.
- [2026-10-29 원래 결정](../../history/specs-20261110/ota.md): 동일일·동액은 추가 단서 없어도 연결하되 **명시 카드·발급사·다른 OTA 공급자·중복·원문 오류·기존 점유 충돌**은 유지한다고 적혀 있다.

**문서에서 확인되는 범위:** 단지 카드 가맹점 별칭/추가 신원 근거가 **없는** 동일일·동액 건과, 카드가 확실하게 **무관한 다른 공급자**라고 확인된 건은 구별해야 한다. 뒷경우는 `LINK-002`의 명시 충돌 보호와 `LINK-018`의 PG 한정 때문에 일치한다고 보아서는 안 된다. 추가적인 예외 정책을 만들지 않는 한 연결을 허용하기 어렵다.

### 2.2 차이를 설명하는 합성 예시 — **실제 거래 아님**

- 예약: OTA 숙박 결제 150,000원, 실제 검증 결제일 11월 10일.
- 카드: 같은 날 150,000원 지출.
- **경우 A:** 카드 가맹점명이 예약 공급자의 승인 별칭임 → 기본 연결 가능.
- **경우 B:** 카드 가맹점명이 실재 PG임이 검증됨 → `LINK-018` 결제대행 조건으로 연결 가능.
- **경우 C:** 가맹점 표기의 정체가 미확인이고 다른 공급자라고 확인되지 않음 → `DATE-023`에 따른 동일일·정확 동액 적용 여부와 기존 충돌·점유 조건을 확인해야 함.
- **경우 D:** 가맹점이 **실제로 다른 독립 사업자이며 PG도 아님**이 확인됨 → 단순히 날짜·금액이 우연히 같다는 사실만으로 자동 연결하면 잘못된 상품·여행 근거를 붙일 위험. 현재 기본/보호 규칙상 연결 불허.

**미결 정책 질문:** 사용자가 D의 **명시된 다른 사업자**까지 같은 날·정확한 금액만으로 연결하라고 새로 허용할 의사인지 여부. 이는 기존의 충돌 보호를 실제로 완화하므로 사용자 명시 결정 없이 변경하지 않는다. 허용한다면 상품·업체 간 우연한 동액 반복, 취소/환불과 예약 귀속 혼동에 대한 보호 조건을 따로 정해야 한다.

## 3. 1차 병합 작업과 잔여

- 같은 판단의 영역별 문장 반복을 정본 ID 참조로 축약했다. 원래 ID는 남겨 M3~M6 구현·테스트·P2 근거와의 참조를 끊지 않는다.
- 개별 거래·환불 원행·수동 교정·Google 쓰기·DB 스키마·운영 서비스는 변경하지 않았다.
- **이력/의미 비교, 정확 SHA 독립 검수, P2 및 회귀 시험은 아직 완료되지 않았다.** 확인 전 자동 병합·배포하지 않는다.
