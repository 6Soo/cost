> **상태:** 정본 (2026-11-10 사용자 승인). 구현은 아직 시작하지 않았다 — 이 문서의 작성·병합은 구현 완료가 아니다.
> **이 문서가 하는 일:** COST가 무엇을 하는 시스템인지, 어떤 순서로 무엇을 만들지, 무엇을 지켜야 하는지를 한 곳에 적는다. 과거 명세 112개(`docs/history/specs-20261110/`)와 `docs/history/`의 나머지는 **근거 기록**이며 실행 지시가 아니다. 과거 명세와 이 문서가 다르면 이 문서가 우선한다.
> **짝 문서:** 판정 규칙은 [판정 규칙집](DECISION_POLICY.md), 개발 조직 운영은 [중간 관리자 지침](agents/MANAGER.md), 반복 작업 절차는 [절차서](playbooks/README.md)에 둔다.

## 1. 목적과 성공 기준

### 1.1 목적

여행에 따르는 지출 자료(카드 명세, OTA 메일·포털, 영수증)를 모두 받아 **코드가 먼저 대사·분류하고(P1), 코드가 못 정한 것은 AI가 정한다(P2).** 사용자는 처리 흐름 중간에 질문을 받지 않는다.

### 1.2 사용자의 역할 — 분기 검수

- 사용자는 여행사에서 가이드 업무를 뺀 실무 전체를 맡는 결정권자이며 코드를 직접 읽지 않는다.
- 사용자가 하는 일은 **분기마다 한 번의 최종 검수**다. 검수하면서 틀린 판정을 교정하고, Google 지출표에 붙여넣는다.
- 처리 흐름 안에는 **사용자 확인 단계(P3)가 없다.** 질문함·확인 대기·보류 해제 같은 화면과 상태를 만들지 않는다. 판정이 어려운 건도 AI가 근거와 불확실성을 적고 판정을 끝낸다.
- 분기 검수의 교정은 [판정 규칙집](DECISION_POLICY.md) 개정으로 환류한다. **같은 교정을 두 번 받지 않는 것**이 이 시스템의 품질 기준이다(§8).
- 인증(카드사 공동인증서, OTA 포털 재로그인)은 판정 질문이 아니라 인증 인계다. 수집 스크립트가 로그인 만료를 감지하면 멈추고 상태만 표시한다(§7).

### 1.3 사용자가 받아볼 산출물

1. **여행별 손익** — 여행마다 수입과 지출이 맞춰진 수치.
2. **세무·증빙 자료** — 세무 처리에 넘길 수 있게 정리된 카드·영수증 자료.
3. **직원·가이드 지출 정산** — 직원과 가이드가 쓴 비용의 확인과 정산 자료.

현재 구현 상태와 정의가 비어 있는 부분은 §9에 적는다.

### 1.4 성공 기준

| 구분 | 지표 | 뜻 |
| --- | --- | --- |
| 업무(1순위) | 분기 검수 교정 건수와 소요 시간 | 사용자가 실제로 고친 건수. 분기마다 줄어야 한다 |
| 업무 | 여행 종료 후 손익 수치가 나오기까지 걸린 날 | 지출 판정이 밀리지 않는지 |
| 업무 | 산출물 3종의 준비 상태 | 분기 말에 바로 쓸 수 있는지 |
| 내부(수단) | 판정이 없는 정상 거래 수 | 0이어야 한다 |
| 내부 | P1 처리율, P2 처리율 | P1은 늘고 P2는 줄어야 한다 |
| 내부 | P2 실행 성공률 | 기술적으로 끝까지 도는 비율 |
| 내부 | 수집 지연 | 원천별 마지막 수집일과 오늘의 차이 |

내부 지표가 좋아도 업무 지표가 나쁘면 실패다.

### 1.5 하지 않는 것

- Google 최종 장부에 자동으로 쓰지 않는다. 붙여넣기는 분기 검수 때 사용자가 한다.
- 사용자의 수동 교정을 자동 판정이 덮지 않는다.
- 카드 원문·금액·ID, 메일 원문, 영수증 원본을 바꾸거나 지우지 않는다.
- 여행을 만들어내지 않는다. 여행은 Google 시트 탭에서만 생긴다.
- 실제 환급 입금이나 Google 반영 사실을 추론으로 만들어내지 않는다.

## 2. 처리 원칙

| 용어 | 뜻 |
| --- | --- |
| P1 | 코드와 데이터형 규칙이 내는 판정. 같은 입력에 항상 같은 결과 |
| P2 | AI 에이전트가 내는 판정. P1이 못 정했거나 약하게 정한 건만 맡는다 |
| 판정 | 지출 1건에 대한 결론: 어느 여행(또는 분기 기타비용)의 어떤 항목인지, 이용기간, 연결된 근거, 누가 정했는지, 근거 문장, 불확실성 |
| 근거 | 판정에 쓴 원천 자료: 카드 원행, 메일 원문, 포털 조회 결과, 영수증, Google 여행 탭 |
| 교정 | 사용자가 분기 검수에서 판정을 고치는 것. 항상 자동 판정보다 우선한다 |
| 분기 기타비용 | 실제 여행에 귀속할 수 없는 일반 비용의 종착지. 결제일 기준 분기로 나눈다 |

1. **P1을 최대한 늘리고 P2는 줄인다.** P2는 사용자 확인의 대체물이다. P2가 같은 유형을 반복 판정하면 P1 규칙으로 올린다(§6.7).
2. **P2를 0으로 만드는 것은 목표가 아니다.** 한두 번 나오는 사례까지 규칙으로 만들면 공급자별·증상별 패치 반복으로 돌아간다.
3. **모든 정상 거래는 판정을 갖는다.** 근거가 부족하면 최선의 판정과 불확실성을 적는다. "분류 대기"로 남기지 않는다.
4. **판정은 저장된 값이다.** 화면이 그릴 때마다 추론하지 않는다. 화면은 저장된 판정을 읽기만 한다.
5. **증상별 패치를 하지 않는다.** 새 공급자·새 메일 양식을 파서 패치로 쫓지 않고, P2가 원문을 읽어 판정한 뒤 반복되는 것만 규칙·데이터로 올린다.
6. **규칙은 한 곳에만 쓴다.** 판정 규칙의 정본은 [판정 규칙집](DECISION_POLICY.md)이다. 새 지시는 대화로 흘려보내지 않고 규칙집 개정으로 반영한다.

- Python 표준 라이브러리 HTTP 서버가 HTML을 문자열로 만든다. `webapp/`(화면·업무 로직 혼재), `app/`(수집·추출·대사·분류), `tools/`(운영·일회성 스크립트), `tests/`.
- 운영은 이 Windows PC의 `D:\WebLedgerHost`에서 예약 작업 `WebLedger-Board`(8751/8752), `WebLedger-Gateway`(8790), `WebLedger-Worker`로 돈다. 외부 접속은 cloudflared 터널을 거친다.
- 저장은 SQLite 여러 개(`board.sqlite`, `ota-evidence.sqlite` 등)에 테이블 약 130개가 스키마 모듈 10여 개로 흩어져 있다.

### 3.3 목표가 달성되지 않은 원인

1. **P2가 운영에서 한 번도 성공하지 못했다.** 설정은 켜져 있지만(`autonomous_ai_review=true`) 적용 0건이다. 호출 약 1,400회가 전부 실패했고(시간 초과 955, 실행 실패 200, 응답 형식 오류 169, 반영 실패 60), 2,826회는 일일 한도로 차단됐다. 현재 P2(`app/ai_classification.py`, `app/connected_agent_provider.py`)는 무료 모델에게 **가맹점 이름도 원문도 없이** 날짜·국가·후보 여행 목록만 주고 고르게 한다. P1이 못 본 것을 P2도 볼 수 없다.
2. **무엇이 맞는 판정인지 적혀 있지 않았다.** 규칙이 명세 112개와 구두 지시에 흩어져 있어 에이전트가 스스로 검증할 기준이 없었다.
3. **증상을 쫓는 개발.** 2026-11-07~10에 병합된 PR 약 70건의 대부분이 공급자별·증상별 패치와 기록용 문서다.
4. **명세·데이터·코드가 흩어져 있다.** 같은 거래가 `transactions`, `board_rows`, OTA 저장소에 겹쳐 있고, 일부 판정은 화면을 그릴 때 계산된다. main의 테스트는 전부 통과하는 상태가 아니다.

## 4. 판정 모델

### 4.1 판정 한 건의 내용

| 항목 | 내용 |
| --- | --- |
| 대상 | 카드 거래 1건(또는 영수증 1건, 캐시·포인트 사용 1건) |
| 귀속 | 실제 여행 하나, 또는 결제일 기준 분기 기타비용, 또는 전액 환불 쌍 |
| 항목 | 숙박비·항공료·식비 등 비용 항목 |
| 이용기간 | 실제 서비스 이용일(숙박 기간, 탑승일 등). 모르면 비워 두고 그 사실을 적는다 |
| 연결된 근거 | 판정에 쓴 예약·메일·포털 기록·다른 카드 거래의 참조 |
| 판정 주체 | P1(규칙 ID) / P2(실행 ID·모델) / 수동 교정 |
| 근거 문장 | 왜 이렇게 정했는지 한두 문장 |
| 불확실성 | 확인하지 못한 것 |

### 4.2 판정 주체의 우선순위

수동 교정 > 정확 근거에 의한 P1(예약번호·원승인번호 등) > P2 > 추론에 의한 P1(업종·날짜 기반 최선 후보).

- P2는 추론에 의한 P1을 고칠 수 있다. 정확 근거에 의한 P1과 수동 교정은 고칠 수 없다.
- 낮은 신뢰도는 판정을 미완료로 만들지 않는다. 근거와 불확실성으로만 표시한다.

### 4.3 현 시스템에서의 저장 위치 (M2까지)

새 테이블을 만들지 않고 기존 열을 쓴다.

| 판정 항목 | 저장 위치 |
| --- | --- |
| 귀속·항목 | `transactions.trip_id`, `display_tab_id`, `item` |
| 판정 주체 | `transactions.classification_source` (`ai_inference`가 P2) |
| 근거 문장·불확실성 | `transactions.classification_basis` |
| P2 실행 기록 | `requests`(scope `ai_classification`), 작업 상태(`autonomous_cleanup_worker`의 job 저장), `autonomous-cleanup-metrics.jsonl` |
| 교정 이력 | `app/classification_correction.py`가 남기는 변경 전 값과 근거 |

투자 단계(§11)에서 `decisions` 단일 테이블로 옮긴다.

## 5. 파이프라인

```
수집 → 추출 → 연결 → 귀속 → 게시
```

| 단계 | 하는 일 | P1 (현재 코드) | P2가 맡는 것 |
| --- | --- | --- | --- |
| 수집 | 카드 명세, OTA 메일, OTA 포털, 영수증, Google 여행 탭을 원본 그대로 받는다 | `app/import_card.py`, `app/mail_collect.py`, `app/ota_portal.py`, `app/agoda_capture.py`, `app/google_authority.py` | 없음 (스크립트, §7) |
| 추출 | 원본에서 날짜·금액·예약번호·이용기간을 읽는다 | `app/ota_mail.py`, `app/flight_evidence.py`, `app/import_card.py` | 파서가 못 읽은 메일을 원문에서 직접 읽는다 |
| 연결 | OTA 예약↔카드 결제(M:N), 취소·환불↔원결제 | `app/ota_payments.py`, `app/partial_refund.py`, `app/ota_inference.py` | 연결 근거를 판정의 근거로 제시한다. 정확 연결·환불 짝은 P1만 쓴다 |
| 귀속 | 여행·항목·이용기간을 정한다 | `app/classify.py`, `app/rules.py`, `app/automatic_classification.py`, `app/reconciliation.py` | P1이 못 정했거나 일반 항목으로만 정한 건을 판정한다 |
| 게시 | 판정을 저장하고 화면·내보내기에 반영한다 | `app/ledger.py`, `app/classification_correction.py` | 없음 |

- 각 단계에서 P1을 먼저 돌리고 남은 것만 P2로 보낸다.
- 금액·부호·원승인 관계·환불 짝·장부 기록은 P1만 쓴다. P2는 귀속·항목·이용기간과 그 근거만 낸다.

## 6. P2 런타임

### 6.1 무엇이 달라지는가

| | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 모델 | 무료 OpenCode 모델 | `codex/gpt-6.1-sol` 기본, 도구 비허용이 검증된 경우에만 `claude/opus` 대체 (구독, 건당 과금 없음) |
| 받는 자료 | 날짜·국가·후보 여행·항목 목록 | 카드 원행 전체, 관련 메일·포털 원문, 과거 같은 가맹점의 판정, 규칙집 |
| 도구 | 없음 | 없음. Worker가 사건 자료·규칙·스키마를 프롬프트 본문/stdin으로 직접 넣는다 |
| 추가 자료 | 요청 불가 | 결과에 "더 필요한 조회"를 적으면 Worker가 정해진 조회를 실행하고 다시 묻는다 |
| 묶음 | 한 번에 최대 50건 | 관련된 소수 건(같은 가맹점·같은 예약)씩 |

### 6.2 사건 폴더 방식

Worker가 P2에 넘길 건마다(또는 관련된 몇 건마다) 사건 폴더를 조립·기록한다. **에이전트가 이 폴더를 읽는 방식은 쓰지 않는다.** Worker가 아래 자료를 프롬프트 본문/stdin으로 직접 넣고, 에이전트의 cwd는 별도의 빈 임시 폴더로 둔다.

```
<작업폴더>/<작업ID>/
  case.json          판정할 거래(원행 전체), 현재 P1 판정, 후보 여행 목록, 허용 항목 목록
  evidence/          관련 근거 원문: 메일 본문, 포털 조회 결과, 연결된 다른 카드 거래, 과거 같은 가맹점 판정
  policy/CORE.md     규칙집의 핵심 원칙
  policy/<영역>.md   이 건에 해당하는 영역 규칙
  schema.json        출력 형식
```

- 근거는 코드가 고른다: 금액(원화·외화) 일치, 날짜 범위, 카드 끝자리, 공급자·가맹점 단어, 예약번호로 관련 메일·포털 기록을 찾아 넣는다. 전체 프롬프트 크기 상한을 두며, 근거를 잘랐으면 그 사실과 범위를 사건 자료에 표시한다. 필수 핵심 원칙·출력 스키마는 보존한다.
- 에이전트는 파일·셸·네트워크 도구를 실행하지 못한다. 운영 DB·레포·비밀값을 직접 조회하지 않는다.
- 에이전트의 출력은 `schema.json`에 맞는 JSON 하나다.

출력 형식(요지):

```json
{
  "request_digest": "<Worker 요청 지문>",
  "execution": {"kind": "connected_agent", "provider": "codex", "model": "…", "run_id": "…"},
  "results": [
    {
      "transaction_id": "…",
      "trip_id": "<후보 중 하나 또는 분기 기타비용 값>",
      "item": "<허용 항목 중 하나>",
      "service_start": "YYYY-MM-DD 또는 빈 문자열",
      "service_end": "YYYY-MM-DD 또는 빈 문자열",
      "evidence_refs": ["evidence/…"],
      "basis": "근거 문장",
      "uncertainty": "확인하지 못한 것",
      "rule_ids": ["규칙집에서 적용한 규칙 ID"]
    }
  ],
  "more_evidence": [
    {"kind": "mail_search|portal_lookup|card_search", "query": "…", "why": "…", "transaction_id": "…"}
  ]
}
```

- `more_evidence`가 있으면 Worker가 허용된 조회만 실행해 `evidence/`에 더하고 프롬프트를 다시 조립한다. 추가 조회·문의는 최대 2회. 임의 URL·명령은 실행하지 않는다. 그 뒤에도 부족하면 에이전트는 최선의 판정과 불확실성을 낸다. 추가 조회만 요청할 때는 `results`가 비어 있을 수 있으나, 최종 반영은 §6.4의 모든 대상 검증을 통과해야 한다.

### 6.3 실행

- 기본은 직접 `codex exec --sandbox read-only --output-schema <schema.json> --json -` 호출이다. 승인 정책은 `never`, 모델은 `gpt-6.1-sol`, cwd는 빈 임시 폴더다. 자료는 stdin으로 넣고 파일·셸·네트워크 도구가 실행되지 않는 호출 조건을 유지한다. `full-access`·`bypass`로 대체하지 않는다.
- `paseo run --provider codex/gpt-6.1-sol`은 같은 조건에서 도구가 실행되지 않음이 검증된 모드에서만 쓴다. 그렇지 않으면 직접 호출한다.
- `claude -p`는 도구를 전부 비허용하는 옵션으로 비대화형 완료가 검증된 경우에만 대체로 등록한다. 검증되지 않으면 대체 없이 구독 한도가 풀릴 때까지 기다린다. 권한 대기로 멈추는 호출은 대체 경로로 수락하지 않는다.
- 실행기는 `webapp/autonomous_cleanup_worker.py`의 `provider` 주입 지점에 연결한다. 기존 `app/connected_agent_provider.py::_run_bounded`의 프로세스 시간 제한·소유 프로세스 트리 종료 처리를 재사용하고 stdin 주입을 지원한다. JSONL 이벤트와 최종 JSON을 구분해 검증하며 도구 실행이 관측된 응답은 반영하지 않는다.
- CLI 설치·로그인과 실제 예약 Worker 맥락의 실행 완료를 구분한다. 실제 예약 작업에서 호출·검증·종료까지 이어지는지는 D5 합성 검증으로 확인한다.

### 6.4 결과 검증과 반영

1. 형식 검증: 모든 대상 거래가 정확히 한 번씩, `trip_id`는 후보 안, `item`은 허용 목록 안, 날짜 형식, 근거 문장 존재.
2. 신선도 검증: 요청 뒤 거래·여행·규칙이 바뀌었으면 버리고 다시 만든다(기존 `ai_classification.preview`의 방식).
3. 보호 검증: 수동 교정·정확 연결·환불·중복·원본 충돌이 걸린 거래는 대상에서 빼거나 반영을 거부한다.
4. 반영: 기존 `app/classification_correction.py` 경로로 단일 트랜잭션에 저장하고 변경 전 값을 남긴다. 판정 주체는 `ai_inference`, 실행 ID와 모델을 함께 기록한다.
5. 금액·부호·원문·ID·환불 짝·장부 기록·Google에는 쓰지 않는다.

### 6.5 대상

- 정상 구매 거래 중 판정이 없거나, P1이 일반 항목(`기타경비`·`현지경비`·`여행경비`)으로만 정했거나, 여행 귀속이 빈 건. 현재 탐지 조건은 `autonomous_cleanup_worker.detection_sql()`이며 한 번에 400건으로 잘려 있다 — 전체 미해결 건을 다 돌도록 고친다.
- 이용기간을 확인하지 못한 건(화면의 이용일 경고 대상).
- 파서가 읽지 못한 메일과 연결될 가능성이 있는 거래(Worker가 관련 원문을 사건 자료로 조립해 프롬프트에 직접 넣는다).
- P1 판정의 표본 감사(§6.7).

### 6.6 운영 조건

| 조건 | 내용 |
| --- | --- |
| 권한 | 메일 원문은 신뢰할 수 없는 입력이다(지시문이 숨어 있을 수 있다). 안전 근거는 OS 격리 검증이 아니라 **에이전트의 도구 실행 불가와 코드의 스키마·후보·신선도·보호 검증**이다. P2에 `full-access`·`bypass`를 쓰지 않으며 샌드박스 복구를 선행 조건으로 삼지 않는다 |
| 한도 | 구독 한도를 개발 세션과 나눠 쓴다. 일일 실행 예산과 야간 실행 시간대를 설정으로 둔다. 한도 오류는 실패가 아니라 대기다 |
| 순서 | P2가 밀려도 P1 판정은 먼저 저장·게시한다. P2는 나중에 덮는다 |
| 가동 | 계정이 로그인돼 있을 때만 돈다. CLI 로그인 만료, Paseo 데몬 중지, 연속 실패를 상태 화면에 드러낸다 |
| 실패 | 형식 오류는 같은 건을 한 번 더 시도하고, 그래도 실패하면 검증된 대체가 있을 때만 넘긴다. 대체가 없으면 대기하며 실패 사유를 건별로 남긴다 |
| 자료 범위 | 구독 프론티어 모델(sol, opus)에는 고객 원문을 줄 수 있다(사용자 결정 D2). 무료 모델에는 주지 않는다 |

### 6.7 P1 승격과 표본 감사

- **승격:** 같은 유형(같은 가맹점·같은 공급자 양식·같은 판단 근거)의 P2 판정이 반복되고 분기 검수에서 교정되지 않았으면 규칙 후보로 올린다. 제안 기준: 같은 유형 5건 이상, 판정 일치, 교정 0건. 후보는 규칙집에 규칙으로 적은 뒤 P1에 넣는다.
- **규칙은 데이터로.** 가맹점 별칭, 가맹점→항목, 공급자 양식 정의처럼 표로 표현되는 규칙은 코드가 아니라 데이터(`cost_classification_rules` 등 기존 규칙 저장소)에 넣어 배포 없이 반영한다. 새로운 종류의 규칙만 코드로 쓴다.
- **표본 감사:** P3가 없으면 P1의 오판은 조용히 쌓인다. P2가 매달 P1 판정의 일부(제안: 5% 또는 30건 중 작은 쪽)를 다시 보고, 다르게 판정한 건은 규칙 수정 후보로 기록한다. 감사 결과로 판정을 자동으로 덮지는 않는다(정확 근거 P1은 P2보다 우선).

### 6.8 가동 확인

M2에서 전체 미해결 건을 돌리기 전에 **첫 묶음 약 50건**을 돌려 두 가지만 본다.

1. 기술적으로 끝까지 도는가(실행 성공, 형식 통과, 반영 성공).
2. 결과가 분기 검수를 "다시 하는 일"로 만들 만큼 나쁘지 않은가 — 감독 세션이 근거 문장을 표본으로 읽고, 명백한 오판 유형이 있으면 규칙집이나 사건 폴더 구성을 고친 뒤 진행한다.

통과 기준을 둔 사전 채점은 하지 않는다. 오판은 분기 검수가 잡는다.

## 8. 분기 검수와 교정 환류

1. 분기 말에 사용자가 여행별 장부와 분기 기타비용을 검수한다. 화면은 판정 주체(P1/P2/수동)와 근거 문장·불확실성을 보여 주어 어디를 먼저 볼지 알 수 있게 한다.
2. 사용자가 틀린 판정을 교정한다. 교정은 즉시 반영되고 자동 판정이 덮지 못한다.
3. 분기 검수가 끝나면 감독 세션이 그 분기의 교정을 모아 다음을 한다.
   - 같은 원인의 교정을 묶어 규칙집에 규칙을 추가하거나 고친다(교정 사례를 규칙의 예시로 붙인다).
   - 규칙이 표로 표현되면 P1 데이터 규칙으로 넣는다.
   - 교정 건수를 판정 주체별(P1 규칙 ID, P2)로 집계해 §1.4의 지표로 기록한다.
4. 교정 사례는 평가 사례로 누적한다. 규칙이나 P2 구성을 바꿀 때 이 사례들로 되돌아간 판정이 없는지 다시 돌려 본다.
5. 2026년 6월 이전의 Google 지출표는 "대체로 맞지만 오류가 섞인" 참고 자료다. P2 사건 폴더에 "과거 같은 가맹점이 어떻게 분류됐는지"로 넣을 수 있지만 현재 거래의 증거로 쓰지 않는다.

### M2 — 현 시스템에 P2 연결, 오늘까지의 회계 처리 (**업무 목표 달성 지점**)

현 Python 시스템을 최소로 고친다. 새 코어를 만들지 않는다.

1. Worker의 사건 자료 조립·기록과 프롬프트 직접 주입, 근거 선택(§6.2).
2. 도구 없는 CLI 실행기와 결과 검증·반영(§6.3~6.4). Windows에서 도구 미실행·코드 검증과 실제 예약 Worker 맥락의 합성 완료를 확인한다(§6.6).
3. 첫 묶음 약 50건 가동 확인(§6.8).
4. 전체 미해결 건 처리. 대량 반영이므로 신선 백업과 복원 확인 뒤 실행한다.
5. 수집 스크립트(§7): OTA 포털 3곳, 카드사 3곳.
6. 현재 정의된 산출물(여행별 손익, 세무·증빙 자료)을 현 화면과 내보내기에서 확인 가능하게(§9). 직원·가이드 지출 정산은 M2 이후 제안하며 이 단계에서 구현하지 않는다.
7. 상태 화면: 원천별 마지막 수집일, 로그인 필요 표시, P2 대기·실패 건수.

종료 조건:
- 판정 없는 정상 거래 0건, P2 실행 성공률이 기록됨.
- 사용자가 한 분기를 검수하고 Google에 붙여넣을 수 있음.
- 그 분기의 교정이 규칙집에 환류됨(§8).

이후에는 분기 검수로 운영하면서 §6.7의 승격으로 P1을 늘린다.

## 11. 투자 단계의 설계 원칙

M3 이후에 적용한다. 착수할 때 이 절을 상세 설계로 확장한다.

### 11.1 Rust 새 코어 (M3, M6)

- 얻는 것: 판정 상태와 금액 규칙을 타입으로 강제해 에이전트가 만든 회귀를 테스트 전에 잡는다. 실행 파일 하나로 배포한다.
- 대상: 판정 모델, 파이프라인, P1 규칙 엔진, 작업 큐·Worker, P2 실행기, JSON API. React/TypeScript 프런트와 ego-browser 수집 `.mjs`는 Rust 밖에 둔다.
- 데이터: 원천을 `evidence`(원문 보존) → `facts`(구조화 추출)로 통일하고 SQLite 하나에 테이블 약 25개로 줄인다(evidence, facts, payments, bookings, links, trips, decisions, decision_history, overrides, jobs, agent_runs, 부가 영역). 이관은 테이블 변환이 아니라 **보존된 원본을 새 파이프라인에 다시 넣는 방식**으로 하고, 기존 수동 교정은 overrides로 옮긴다.
- 순서: 착수 시 기존 Python 추출기를 보존 원본에 돌려 **기준 출력**을 만든다. Rust 추출기는 이 출력과 일치해야 병합된다. 전환기에는 Rust 코어가 Python 추출기를 하위 프로세스로 부르는 것을 허용하고, 기준을 통과한 것부터 교체한다.
- 드문 양식은 Rust 파서를 새로 쓰지 않고 P2와 데이터 규칙으로 흡수한다.
- 전제: 이 PC에 Rust 도구가 없다. 설치는 착수 때 사용자 승인을 받는다. 통과 조건은 `cargo test`·`cargo clippy`와 교정 사례 재실행이다.

### 11.2 화면 (M4)

- Rust JSON API + React/TypeScript 컴포넌트 라이브러리.
- 디자인은 Claude Design에 맡긴다: 컴포넌트 라이브러리를 `/design-sync`로 동기화 → Claude Design에서 설계 → 에이전트가 구현 → 다시 동기화.
- 화면은 분기 검수(판정 열람·교정), 산출물 3종, 자동화 상태를 중심으로 한다. 정보구조는 [UI/UX 감사·재설계 명세](history/specs-20261110/uiux-full-audit-redesign-20261110.md) §5를 이어받는다.
- 부가 기능(수입·참가자 대조, 영수증 처리, Google 장부 비교·복사, 직원 계정·열람 권한)은 모두 새 구조로 옮긴다.

### 11.3 서버와 보조 노드 (M5)

- 서버 역할: 화면, API, DB, 원문 저장, P1, 작업 큐. 보조 노드(로컬 PC): P2 실행, 로그인 세션이 필요한 수집. 같은 실행 파일의 두 실행 방식이다.
- 보조 노드는 서버로 **나가는 요청만** 한다. PC로 들어오는 터널을 두지 않는다.
- PC가 꺼져 있으면 화면·P1·웹 업로드는 계속 동작하고 P2와 브라우저 수집만 쌓인다.
- 원문을 포함해 전부 클라우드에 둔다(사용자 결정). 제공자에 묶이지 않게 실행 파일 하나 + SQLite 파일 하나 + 원문 폴더(또는 S3 호환 저장소)로 만들고, 제공자 전용 런타임에 맞춘 코드를 쓰지 않는다. 제공자는 이전 시점에 실제 요청량을 재고 고른다.
- 매일 클라우드 DB와 원문을 로컬 PC로 내려받아 보관한다.
- 제공자를 고르기 전에 고객 개인정보의 국외 이전·처리 위탁 고지 의무를 확인한다(§14).

### 11.4 P2 모델 교체 (선택)

- 세 층으로 본다: P1 / 무료 모델 + 절차서 / 프론티어 모델(상위 이관·표본 감사·절차서와 규칙 개정).
- 프론티어 모델이 반복 작업의 절차서를 `docs/playbooks/`에 남긴다. 절차가 고정되면 스크립트로 내리는 것이 먼저이고, 무료 모델은 그 사이 단계다.
- 교체는 작업 유형 단위로 한다. 무료 모델을 같은 작업에 나란히 돌려 프론티어 판정과의 일치율·형식 오류율·시간 초과율을 본 뒤 바꾸고, 검증 실패 건은 프론티어로 올린다.
- 판단이 필요한 드문 사례는 프론티어 모델에 남긴다. P2 물량이 월 100건 안팎이면 비용 절감 효과가 작으므로 우선순위가 낮다.
- 무료 모델에 고객 원문을 주는 것은 제공자의 데이터 이용 조건을 확인한 뒤 따로 승인받는다.

## 12. 개발 운영

### 12.1 증상별 패치 동결

- 2026-11-10부터 공급자별·증상별 파서 패치, 화면 문구·경고 수치를 쫓는 수정, 기록만을 위한 문서 PR을 하지 않는다. 같은 레포의 모든 세션에 적용한다.
- 예외: 운영 장애(접속 불가, 데이터 손상 위험, 수집 중단)와 이 문서의 로드맵 작업.
- 판정이 틀린 사례를 발견하면 코드를 고치지 말고 규칙집의 사례로 기록한다. M2 이후에는 P2가 처리한다.

### 12.2 조직

| 역할 | 누가 | 하는 일 |
| --- | --- | --- |
| 최고 관리자 | Fable | 이 문서와 규칙집의 개정, 사용자에게 묻는 "확인 필요" 정리, 단계 종료 승인, 관리자가 올린 사안. 구현 감독과 코드 검수는 하지 않는다 |
| 중간 관리자 | `gpt-6.1-sol` | 작업 배정, 통과 조건 실행, 통합, 모델 퇴출 결정. [관리자 지침](agents/MANAGER.md)을 따른다 |
| 구현 작업자 | exaone 여러 개, ANUS Free Auto 1개 (필요하면 terra·sol 일부) | 배정받은 작업 하나 |

- **모델 평가는 한 가지 규칙뿐이다.** 배정된 모델을 쓰되, 품질이 나빠 관리 비용이 더 들면 그 모델을 빼고 나머지만 쓴다. 자격 시험·점수표를 두지 않는다. 상세는 관리자 지침.
- 병렬 13은 상한이다. 서로 독립인 작업 수만큼만 동시에 돌린다.
- 무료 모델에는 고객 자료를 주지 않는다(합성·가명 자료만).
- sol이 구현한 코드는 sol 관리자가 아닌 다른 세션이 검수한다.
- 사용자 의도는 이 문서와 규칙집에 남긴다. 특정 세션의 대화 기억에 기대지 않는다.

### 12.3 통과 조건과 병합·배포

- 통과 조건은 실행 결과다: 바뀐 기능의 표적 테스트, 영향 기반 QA(`python tools/run_quality_checks.py --base origin/main --run`), 교정 사례 재실행(M2 이후). 작업자가 테스트를 고쳐 통과시키지 않는다.
- CI가 결제 한도로 시작되지 못하는 동안에는 `gpt-6.1-sol` medium 이상이 최종 SHA를 검수·승인한 PR만 병합한다. 모델, 추론 수준, SHA, 판정을 PR에 기록한다. 실제 검사 실패는 이 예외로 통과시키지 않는다.
- 운영 배포는 단일 작성자가 `tools/deploy_verified_release.ps1`로 한다. `-PreviousSha`는 현재 운영 SHA다. 배포 전후에 같은 레포의 다른 세션에 알린다.
- 문서만 바꾼 PR은 테스트·재배포를 하지 않는다. 링크와 인용한 사실만 확인한다.
- 대량 반영·삭제·스키마 변경·금융 원본 변경은 신선 백업과 복원 확인 뒤에 한다. 소수 거래의 교정은 변경 전 값과 이력으로 되돌린다.

## 13. 보호 경계

어느 단계에서도 바뀌지 않는다.

1. 카드 원문·금액·부호·ID, 메일 원문, 영수증 원본을 바꾸거나 지우지 않는다. 금액 해석 실패를 0원으로 기록하지 않는다.
2. 수동 교정은 자동 판정보다 항상 우선한다.
3. 중복·환불 짝·초과 환불·원본 충돌 보호를 풀지 않는다. 환불 묶음은 전부 함께 기록하거나 전부 기록하지 않는다.
4. 연결·분류 완료는 실제 환급 입금이나 Google 반영을 뜻하지 않는다. 그런 사실을 만들어 적지 않는다.
5. Google 최종 장부에 자동으로 쓰지 않는다.
6. 인증을 우회하지 않는다. 암호·인증서·OTP를 읽거나 출력하지 않는다. OTA 포털에서는 조회만 한다(예약 변경·결제·다른 계정 로그인 시도 금지).
7. 강제 push, 운영 DB·고객 원본 삭제, 승인 없는 과금을 하지 않는다.
8. 미리보기·테스트에 운영 포트 8751, 8752, 8790을 쓰지 않는다. 내가 시작하지 않은 프로세스를 종료하지 않는다.
9. 고객 원문은 구독 프론티어 모델의 P2 실행에만 준다. Git, 보고서, PR, 무료 모델에는 넣지 않는다.
10. 직원 계정·열람 권한 검사를 약화하지 않는다.
