## 현재 코드 조사에서 확인한 문제
- 기본 예약 헤더가 정상 예약도 무조건 ‘예약 근거 확인’이라는 상태 배지를 붙인다. 사용자가 취할 행동 없이 형식적인 검증 문구를 노출한다.
- 예약번호·탑승객 전원·예약일·예약처·여정 개수와 세그먼트 세부가 각각 반복 표시된다. 가로·세로 공간을 불필요하게 소모하고 핵심 여정을 가린다.
- ‘연결된 카드 결제’와 ‘예약일의 카드 거래 후보’를 별도 큰 섹션으로 나누고 긴 설명을 항상 출력한다. 실제 사용자 판단은 하나의 ‘결제·카드 거래’ 흐름에서 이뤄진다.
- `카드 전체 내역에서 날짜별 원행 확인`은 `/cards/all`로 이동한다. `manualDateFilter` 자체는 같은 화면에서 원행 조회하므로 기능이 중복된다.
- ‘최초 메일 수신일의 카드 거래 전체 조회’, ‘예약일·원본 근거 확인’, ‘참가자 연결 정보’ 등이 summary/link로 중첩되어 아이콘·상호작용 및 시각적 위계가 일관되지 않다. 사용자가 지적한 깨진 버튼·아이콘을 실제 브라우저 재현으로 확인하고 공통 UI 계약에 맞춘다.

## 요구 UX 및 정보 우선순위
1. **중앙 집중 레이아웃:** 예약 검색과 결과를 한 화면(SPA 흐름)에 두고 결과 폭을 적당한 최대 너비(예: 760–900px 범위에서 실제 브라우저로 결정)로 제한해 가운데 배치. 전체 화면을 채우려고 카드/그리드를 늘리지 않는다. PC/모바일 모두 과도한 padding·중첩 테두리·공백·제목 반복을 제거한다. 첫 화면에는 예약번호/조회한 승객, 출발·도착/날짜/편명/시간(확인된 값만), 예약처, 취소/충돌 **예외** 상태만 우선 노출한다. 예약 정상 건의 ‘예약 근거 확인’ 배지는 제거한다. 실제 충돌·취소 등 행동이 필요한 경고는 유지.
2. **동승객 표시 제거:** 같이 탑승하는 승객의 목록과 인원수는 예약 결과 기본 화면에서 표시하지 않는다. 검색 대상 승객만 표기한다. 내부 식별·참가자 연결/권한·원문/예약 중복 판정에 필요한 자료는 삭제하거나 변형하지 않는다. 별도 ‘참가자 연결 정보’ 진입점도 항공권 확인 흐름에 직접 필요하지 않으면 제거하며, 필요한 연결 기능은 기존 참가자 화면에서 수행한다.
3. **결제·카드 거래 영역 통합:** ‘연결된 카드 결제’와 ‘예약일의 카드 거래 후보’를 단일 **‘결제·카드 거래’** 영역으로 통합한다. 확정 연결이 있으면 맨 위에 거래(카드/날짜/금액/취소·환불 상태)를 표시한다. 자동 후보는 확정 결제가 **아닌** 별도 하위 상태로 표시하며 동일 날짜만으로 연결 확정하지 않는다. 확정 연결이 없으면 긴 ‘카드가 없거나 미결제라는 뜻이 아니다’ 문장을 반복하지 말고 짧은 중립 상태(예: ‘확인된 카드 연결 없음’)와 ‘거래 조회’ 동작만 제공한다. 실제 무결제 판정·자동 확정·새 링크 저장 금지.
4. **이 화면에서 카드 원행 조회:** `/cards/all`로 이동시키는 버튼을 제거한다. 단일 화면의 결제 영역에서 조회 날짜(근거 있는 예약일 또는 최초 메일 수신일 제안, 직접 날짜 변경 허용)를 고르고 원행 목록을 비동기로 펼쳐 확인할 수 있도록 한다. 로딩·빈 결과·오류·재시도·페이지 추가가 이 화면 안에서 끝나야 한다. 조회 대상이 원행 전체인지 특정 카드 필터인지 명확히 표시하며 전체 결과를 결제 확정/검증 완료로 오인하지 않게 한다. 별도 전역 카드 검색이 필요하면 일반 내비게이션에만 두고 항공권 예약 카드에서는 강제 페이지 이동하지 않는다.
5. **정보의 점진적 공개:** 예약일/메일 수신일의 출처·시간대·원본 증빙은 기본 카드의 작은 보조표시 또는 접힌 ‘날짜 근거’ 안에 배치한다. 근거가 충돌하거나 자료가 부족할 때만 주의 문구를 우선 노출한다. 탑승권/세그먼트는 실제 확인된 항공편을 간결한 시간순 여정으로 묶되 환승/복수 구간은 누락하지 않는다. 목록 내 반복된 ‘미확인’과 법률식 설명을 줄이고 꼭 필요한 결정 정보에 집중한다.
6. **깨진 버튼·아이콘 정비:** 버튼 3종(카드 원행 조회, 날짜 근거, 참가자 연결)과 공통 disclosure, 선택 날짜, 페이지 더보기 아이콘/텍스트의 깨짐·중복 화살표·클릭 영역·포커스·닫기를 점검해 공통 디자인 시스템을 적용한다. 일관된 SVG/문자 폴백, 접근 가능한 버튼 이름, 키보드 Enter/Space/Escape, 44px 수준 터치 영역, light/dark 및 동적 렌더 후 이벤트를 검증. 단순 아이콘 장식으로 기능 부재를 가리지 않는다.
7. **SPA 동작/상태 보존:** 검색 → 예약 선택 → 카드 원행 조회 → 날짜 변경/추가 조회 → 다른 예약 조회 → 원래 결과 복귀까지 전체 페이지 새로고침 없이 작동. 뒤로가기/새로고침 시 검색어와 현재 예약 선택 등 필요한 URL 상태를 복원할 수 있도록 설계. API 권한·페이지네이션·요청 취소/경합 시 오래된 응답이 화면을 덮지 않도록 방어. 프레임워크 도입은 기존 JS로 달성하기 어려운 경우만 검토하고, 새 전역 상태 엔진을 만들지 않는다.

## 기존 계약과의 경계
- `FIRST_RECEIVED`는 최초 **인증 메일 수신일**로 실제 예약·발권·결제일과 구별한다. 날짜 근거 충돌·취소·원본 불일치는 계속 표시하며 날짜/예약/결제 사실을 창작하지 않는다.
- 확정 카드 링크와 날짜 기반 후보를 한 화면에 합쳐도 저장된 원행 ID·예약 근거·수동 연결·환불·중복·M:N 계약은 유지한다. 원본 카드의 결제 완료 여부, 실제 탑승, 은행 환급, Google 최종 장부 쓰기를 조회만으로 확정하지 않는다.
- 읽기 조회는 권한 경계와 개인정보 마스킹을 유지하고 원본·금융·여행/참가자 연결·Google·스키마에 쓰지 않는다.
