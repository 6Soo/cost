# 트립닷컴·부킹닷컴 미완결 연결 조사

## 2026-10-21 후속 해결 상태

외화 숫자 비교, 인증된 같은 예약의 기간·취소·변경 맥락 결합, 실제 결제수단의 카드사 추출을 구현해 운영에 반영했다. 보관 하나 승인 원본 358행을 추가해 사례 C의 두 결제도 코어에서 서로 다른 카드 거래로 대사됐다. 이후 실제 예약 화면에서 코어 결과가 누락되는 별도 결함을 재현해 읽기 투영도 수정했다. 반복 거래의 순서 배정은 개별 정확 연결과 구분한다. 아래 초기 조사 중 하나 원본이 부족하다는 판단은 운영 DB 범위만 본 결과였으며 보관 원본 재조사로 해결했다.

사례 B의 누락 확정 메일은 기존 Gmail ID로 복구했고 결제 이벤트에도 이용기간이 결합된다. 사례 A는 외화 형식 차이가 해소돼도 이미 존재하는 비용·사용자 해제 결정을 바꾸지 않는다. 사례 D의 취소·환불 요청·변경 총액은 표시하지만 차액 카드의 개별 증거와 완료 환불이 없어 그 부분은 PARTIAL이다. 최신 릴리스·표적 검사·실제 자료 보존 근거는 [현재 운영 기록](operations.md)의 첫 항목을 따른다. 아래 내용은 원인 재현 당시의 기록이다.


기록일: 2026-10-20

## 요청과 조사 범위

사용자는 두 공급자의 결제 메일은 정상 수신되고 있는데 장부 연결이 끝나지 않는 실제 사례를 Aside REPL로 확인하고 해결 방안을 마련하도록 요청했다. 이 문서는 아고다 수집·통합 실행 계획에 추가된 조사 결과다.

Aside의 Google 계정·Gmail 스킬로 로그인 계정을 확인하고 실제 메일을 검색·조회했다. 로그인된 COST의 OTA 목록과 예약 판단 화면도 직접 조회했다. 운영 SQLite는 읽기 전용으로 열어 해당 카드 원행·최초 기록·현재 장부 행·결제 스냅샷과 대조했다. 메일 수신이 정상이라는 사용자 설명을 수신 장애로 바꿔 해석하지 않는다.

메일 원문·예약번호·금액·화면 증거는 Git 제외 경로 `.local-archive/trip-booking-investigation-20261020/`에 보존한다. 이번 조사에서 운영 거래·사용자 확정·장부·분류 규칙·메일 수집 등록을 수정하지 않았다. 메일 발송·예약 변경도 실행하지 않았다.

## 확인된 원인

### 부킹닷컴 사례 A: 카드 외화 금액의 쉼표가 금액 불일치로 처리됨

실제 결제 메일의 엔화 금액과 카드 원문의 엔화 금액은 같다. 카드 값에는 천 단위 쉼표와 소수부가 들어 있다. `app/ota_payments.py`의 `_amount_matches()`는 이 값을 바로 `Decimal(str(...))`에 넘기므로 변환이 실패하고 일치하지 않는다고 판단한다.

같은 실제 이벤트·카드 쌍으로 읽기 전용 재현한 결과 `pair_check()`는 원래 값에서 `amount`를 반환하고, 메모리 사본의 외화 금액에서 천 단위 쉼표만 제거하면 통과했다. 환율 추정이나 원화 환산을 추가하지 않아도 발생 원인을 설명할 수 있다.

이 사례는 이미 최초 기록과 현재 장부 행이 존재한다. 따라서 연결 오류를 고친 뒤 비용을 다시 기록하면 안 된다. 현재 장부의 여행 해제·확정 상태와 최초 기록의 여행이 서로 다르므로 최초 기록을 현재 정본으로 덮어쓰지도 않는다.

### 부킹닷컴 사례 B: 결제는 연결됐지만 오래된 예약 확정 메일이 수집되지 않음

COST 예약 판단 화면은 `이용기간이 없어 여행 미배정`을 표시하며 카드 결제 한 건은 연결돼 있다. 해당 카드의 실제 장부 행은 아직 없다.

Aside Gmail 조회에서는 수개월 먼저 도착한 예약 확정 메일에 연도가 있는 체크인·체크아웃이 명시돼 있었다. 현재 등록된 메일 자료에는 이후의 결제 완료 메일과 청구 예고 등이 있지만 이 예약 확정 메일은 없었다. 메일함에는 존재하므로 수신 누락이 아니라 COST 수집 범위의 누락이다. 결제 메일 수집 시작일을 예약 생성일의 하한으로 쓰면 이런 예약이 빠진다.

별도로 사례 A에서는 예약 확정 메일과 결제 메일이 둘 다 로컬에 있는데도 정규 결제 이벤트의 이용기간은 비어 있었다. `_parse_mail_events()`는 메일별 이벤트를 만들고, 결제 이벤트를 같은 예약번호의 별도 확정 메일 기간으로 보완하지 않는다. 예약 목록의 기간 통합과 결제 이벤트의 기간 통합은 서로 다른 경로다.

따라서 날짜 제한 없는 예약번호 추가 수집과, 수집된 자료의 예약 단위 기간 결합을 함께 처리해야 한다.

### 트립닷컴 사례 C: 다른 카드사의 자료가 오래됐는데 금액 불일치로 표시됨

Aside에서 읽은 실제 예약 메일에 온라인 사전 결제 완료와 결제 카드사가 명시돼 있다. 해당 금액의 카드 원행은 현재 DB에 없다. 같은 날의 다른 카드사 결제는 존재하지만 이를 대응 카드로 삼을 근거는 없다.

읽기 전용으로 확인한 카드사별 최종 이용일은 국민 2026-10-01, 하나 2026-07-20, 기업 2026-07-14다. 이 사례의 결제일은 해당 카드사의 자료 종료일보다 뒤다. 메일이 없어 연결되지 않는 문제가 아니다.

파서는 메일의 카드사 이름을 이벤트에 담지 않고, `_strict_card_identity()`가 카드사 구분 없이 같은 공급자 가맹점 후보를 찾을 수 있다. 후보가 없을 때의 `wrong_amount` 진단은 같은 날 다른 카드사의 결제를 보고 `amount_differs`라고 설명한다. 카드 자료 부족과 진짜 금액 차이를 분리해야 한다.

최종 거래일만으로 수집 범위가 완전하다고 판단할 수는 없다. 카드사·카드별 수집 기간과 파일의 범위 증거가 필요하며, 이번 수치는 최신성이 다른 사실을 확인한 근거로만 쓴다.

### 트립닷컴 사례 D: 취소·예약 변경 이력이 결제 후보에 결합되지 않음

동일 숙소의 서로 다른 예약 두 건이 옛 확정 금액이 같은 후보로 남아 카드 한 건을 두고 `partial_repeated_payment_group`으로 보류돼 있다. 한 예약에는 확정 직후 도착한 무료 취소·환불 요청 메일이 있으며, 다른 예약에는 이후 도착한 예약 업데이트 메일이 있다. 실제 메일을 Aside로 확인했다.

업데이트 메일의 최종 예약 금액은 초기 확정 메일의 금액과 다르다. 카드에는 초기 금액과 변경 차액에 해당하는 금액의 거래도 있다. 다만 업데이트 메일은 최종 총액을 보여 줄 뿐, 이 차액의 카드 결제 ID를 직접 증명하지는 않는다. 합계가 맞는다는 이유로 두 거래를 연결하거나 같은 숙소의 다른 예약 결제와 합치지 않는다.

현재 `extract_mail()`은 업데이트 제목에서 숙박 결제액을 읽지 않고, `_parse_mail_events()`는 과거 charge와 별도 취소·변경 이벤트의 예약 상태를 결합하지 않는다. 따라서 오래된 확정 이벤트가 계속 `confirmed`로 보인다. 취소 메일의 `환불을 요청했습니다`는 환불 입금 완료가 아니므로 원결제를 삭제하거나 완료 환불을 생성해서는 안 된다.

해당 원결제에는 사용자의 `숙박 취소·여행에서 분리` 결정이 있다. 이 결정을 그대로 보호하고 취소·환불 요청·변경 이력을 연결해 보여 주는 것이 우선이다.

| 1 | 외화 금액 비교에 엄격한 숫자 정규화를 적용한다. 올바른 천 단위 쉼표만 제거하고 통화·부호·소수·유한값을 검사한다. 원문 필드는 변경하지 않는다. | 같은 외화 금액의 형식 차이만으로 연결이 막히지 않고, 잘못된 숫자·다른 통화·다른 실제 금액은 계속 거부한다. |
| 2 | 미완결 예약번호별로 날짜 제한 없이 확정·변경·취소·결제 메일을 추가 수집한다. 수집 기간과 메일 ID·원문 해시·인증 헤더를 보존한다. | 메일함에는 있으나 COST에 없는 확정 메일이 채워지고 반복 수집으로 중복되지 않는다. |

| 4 | 취소·환불 요청·변경 이력을 결제 사실과 분리해 결합한다. 원결제는 보존하고 환불 요청을 완료로 승격하지 않는다. 변경 총액을 새 결제액으로 덮지 않는다. | 취소 예약이 최신 정상 확정 예약처럼 보이지 않으며, 변경 총액·추가 결제·별도 예약을 구별한다. |
| 5 | 메일에 명시된 결제 카드사·수단을 추출하고 카드사별 자료 범위를 진단에 반영한다. 카드사 정보가 없으면 추정하지 않는다. | 다른 카드사의 동종 가맹점 거래 때문에 금액 불일치라고 오인하지 않고, 원행 부재·자료 기간 부족·실제 금액 차이를 구분한다. |

구현 영향은 `app/ota_mail.py`, `app/ota_payments.py`, 필요한 경우 예약 목록·검토의 진단 투영이다. 아고다 수집기의 새 증거 저장 계층과 원문·식별자·메일 중복 보호 계약을 공유하되 공급자별 결제 해석은 분리한다. 카드 다운로드는 해당 카드 수집의 기존 승인·인증 경로로 진행하며 부족한 원행을 메일에서 임의 생성하지 않는다.

## 필요한 검증과 현재 상태

구현 시 외화 형식 비교, 오래된 확정 메일의 기간 보완, 기간 충돌, 취소와 환불 요청 구별, 변경 총액과 실제 복수 결제 보존, 카드사별 원행 부재, 기존 장부·수동 결정 보존에 대한 표적 테스트만 수행한다. 실제 고객 원문은 테스트에 복사하지 않고 합성 자료로 재현한다. 기존 데이터 비교에서는 원문 금액·ID·날짜·현재 장부·사용자 확정·환불 연결을 개별 확인한다.

이번 요청의 Aside 실제 사례 조회·원인 분석·해결 방안 작성은 완료했다. 읽기 전용 함수 재현과 화면·메일·DB 대조는 수행했으나 제품 코드를 수정하지 않았으므로 코드 테스트·빌드·배포·재시작·전체 OTA 재대사는 수행하지 않았다. 모든 미연결 사례를 전수 해결했다고 주장하지 않는다.

아고다 수집·DB 통합의 앞선 실행 승인은 유지된다. 이번 추가 요청은 두 공급자의 진단과 해결 방안 수립이며, 이 문서의 제품 수정과 운영 데이터 반영은 아직 실행하지 않았다.
