# 웹 장부 구현·검증 계약

작성일: 2026-09-21. 설계 문서이며 구현·배포 완료 기록이 아니다.
후속 반영: [후속 확정과 교차 동작 8~14절](WEB_LEDGER_SPEC_REFINEMENT.md)과 [실제 구현 수정 기준 R01~R09](WEB_LEDGER_IMPLEMENTATION_REVIEW.md)를 함께 적용한다. 후자는 기존 결함의 수정 기준이며 새 업무 정책이 아니다.
사용자 확정 UX는 [명세](WEB_LEDGER_APP_SPEC.md), 전달용 진입점은 [작업 지침](IMPLEMENTATION_PROMPT_WEB_LEDGER_APP.md)이다. 요청·응답·상태별 기대값은 [상세 동작 계약](WEB_LEDGER_DETAILED_CONTRACT.md), 실행 순서는 [단계별 진행표](WEB_LEDGER_PHASES.md)를 따른다.

## 1. 구현자가 먼저 알아야 할 현재 코드의 범위

| 기존 경로 | 읽어서 확인한 역할 | 재사용·수정 경계 |
|---|---|---|
| `ledger/domain/direct_sources.py` | 카드·수기·일정 등의 직접 적재 | 업로드 어댑터가 기존 파서를 호출한다. 별도 카드 정규화기를 만들지 않는다. |
| `ledger/domain/direct_projection.py` | 원천 스냅샷, 입력 목록, 결제 투영 | 기존 결제 키와 정규화 결과를 화면에서 참조한다. 기존 전체 실행을 매 요청마다 호출하지 않는다. |
| `ledger/domain/schema.sql` | 결제, 원천 계보, 원천 버전, 분류 결정 | 기존 `payment_transactions`, `card_event_identities`, `transaction_sources`를 재사용한다. |
| `webapp/operator_ledger.py` | append-only 결정 사건, 체크포인트, materialize | 현재 분류 축 계약만으로 수입·메모·전체 행 편집이 가능한 것으로 가정하지 않는다. 사건 버전·어댑터를 설계한다. |
| `webapp/server.py` | 스냅샷 후보 조회와 제안 폼 | 현재 구현을 외부 공개용 인증 서버로 취급하지 않는다. 새 쓰기 API는 owner 검사를 서버에서 수행한다. |
| `webapp/snapshot_descriptor.py` | 봉인된 후보 파일 검증 | 원천 봉인용이다. 편집 중인 앱 DB에 매 요청 전체 파일 해시를 요구하지 않는다. |
| `tools/build_cost_yangsik_v15_rev3.py` | 고정 경로의 DB·맵·일정을 읽어 워크북 작성 | 모듈 최상위에서 읽기를 실행하므로 웹 요청에서 직접 import하지 않는다. 기존 출력 경로에 쓰지 않는다. |

테이블명을 나열한 명세는 논리적 책임 목록이다. 모두 새 물리 테이블로 만들라는 뜻이 아니다. 기존 사건 저장소 하나를 현재 행과 규칙의 변경 이력 기준으로 삼고, 새 변경 원장·JSONL·SQLite를 동시에 정본으로 운영하지 않는다. 기존 외부 JSONL과 operator 사건 저장소의 실제 사용 경로를 먼저 확인해 어댑터를 택한다. 마이그레이션 시 기존 이력을 삭제하지 않는다.

## 2. 단일 거래와 화면 행의 계약

- 카드 거래는 기존 결제 식별자로 연결한다. 파일명·시트 행번호·화면 행번호를 거래 ID로 만들지 않는다.
- 업로드 시도 ID, 원천 문서 ID, 거래 ID, 화면 행 ID, 규칙 버전 ID는 서로 다른 목적이다.
- 같은 파일의 재전송은 업로드 기록을 재사용할 수 있다. 다른 기간 파일에 같은 거래가 다시 나타나면 기존 이벤트 식별자로 대조하고 원천 링크만 추가한다.
- 동일 금액·가맹점·날짜의 서로 다른 거래를 합치지 않는다. 식별자 충돌은 원본 두 건을 보존하고 원천 확인 대상으로 둔다.
- 가맹점·카드 종류·거래 방향은 분류 규칙의 기본 조건이다. 거래 동일성 판정에는 사용하지 않는다.
- 기존 관계에 한 거래의 여러 여행 분할이 있다면 allocation member를 화면 행에 연결한다. 원거래 전체 금액을 각 탭에 반복 기입하지 않는다. 분할 금액 합계는 원거래 금액과 같아야 한다.
- 수입의 수동 신규 분할은 확정됐으며 후속 명세 10절을 따른다. 지출의 수동 신규 분할 UX는 미정이다. 기존 분할 정보의 보존은 필수다.
- 화면 배치 상태, 원천 검증 상태, 회계 상태를 분리한다. 후보는 일반 장부 행으로 보이지만 DB의 기존 상태를 승격시키지 않는다.

## 3. 업로드와 대사 진행

### 실행 단계

`received → parsing → reconciling → completed | completed_with_issues | failed`

1. 파일 선택 또는 끌어놓기로 접수한다. 기존 카드별 지원 형식을 우선 사용한다. 읽을 수 없는 형식은 이유를 표시하고 내용을 추측하지 않는다.
2. 업로드 파일을 변경할 수 없는 원천으로 보관하고 서버가 직접 해시한다. 파일 이름은 표시용이며 저장 경로에 사용하지 않는다. 매크로·수식·외부 링크를 실행하지 않는다.
3. 카드 원천 프로필을 식별한다. 프로필이 명확하면 열 매핑 확인을 매번 요구하지 않는다. 알 수 없는 형식에만 사용자에게 열을 지정하게 한다.
4. 파싱은 한 번 수행한다. 기존 파서·정규화기의 결과를 미리보기와 대사가 공유한다.
5. 기존 거래 식별자로 신규·중복·충돌을 나눈다. 구매·취소·환불을 기존 정규화대로 보존한다.
6. 기존 분류 결과와 후보 목적지를 화면에 배치한다. 후보라도 선택 가능한 여행 탭이 있으면 바로 넣는다. 분류가 끝나지 않은 행은 진행 작업 안에서 표시하고 실패가 확정된 행만 분류대기에 둔다.
7. 처리한 행 묶음마다 결과와 진행 커서를 함께 저장한다. 화면은 완료된 결과부터 보여 주며 실패 후 재시도는 같은 작업 ID와 커서로 이어간다.
8. 종료 시 원천 범위와 처리 결과 수·부호 있는 금액을 대조한다. 진행 화면에 성공 건수를 임의 추정하지 않는다.

### 사용자 화면

상단에 `읽는 중`, `분류 중`, `완료`를 보여 주고 다음 숫자를 갱신한다.

- 읽은 원본 행 수
- 신규 거래 수와 이미 존재하는 거래 수
- 여행 탭 배치 수와 기타비용 등 기존 대상 배치 수
- 분류대기 수
- 읽기 오류·식별자 충돌 수

`여행 탭에서 보기`, `분류대기 열기`, `오류 확인` 링크를 제공한다. 진행 로그를 보려면 펼칠 수 있으나 모든 사용자가 기술 로그를 읽게 하지 않는다. 읽기 오류가 남으면 완료 대신 `일부 내역을 확인해 주세요`라고 표시한다.

원본 한 행에 승인과 취소가 함께 있는 형식은 두 이벤트로 정규화될 수 있다. 원본 행 수와 장부 이벤트 수가 무조건 같아야 한다는 잘못된 검증을 넣지 않는다. 원본 행별 파싱 결과와 정규화 이벤트별 처리 결과를 따로 센다.

## 4. 변경 범위를 작게 유지하는 실행 계약

| 사용자 동작 | 읽는 범위 | 갱신하는 범위 | 호출하면 안 되는 작업 |
|---|---|---|---|
| 메모 변경 | 현재 행 revision | 행·변경 사건 | 카드 재파싱, 전체 대사, xlsx 재생성, AI 호출 |
| 항목·내용 변경 | 행과 선택한 예외·규칙 범위 | 행·사건, 필요 시 규칙 초안 | 모든 여행의 재대사 |
| 여행 이동 | 현재 행, 이전·새 탭 | 배정·사건·두 탭 합계 | 원천 재다운로드, 전체 워크북 생성 |
| 카드 업로드 | 새 파일, 기존 거래 인덱스, 관련 근거 | 신규 거래와 영향받는 연결 | 과거 모든 카드 파일 재파싱 |
| 규칙 미리보기 | 조건으로 좁힌 기존 행과 revision | 미리보기 결과만 | 기존 행 자동 저장 |
| 규칙 적용 | 확인한 미리보기 범위 | 선택 행·사건·영향 탭 합계 | 다른 규칙의 모든 행 재계산 |
| 선택 xlsx 출력 | 선택 탭의 일관된 저장 버전과 양식 | 새 출력 파일·출력 기록 | 전체 카드 재대사, 구글 장부 재수집 |

서버가 모든 저장의 권한·필드·revision을 검증한다. 반복 전체 감사는 매 셀 편집에 넣지 않는다. 봉인 입력 감사 때는 실제 입력을 직접 해시하며 manifest만 신뢰하지 않는다. 원천 무결성 감사와 앱 DB의 트랜잭션 무결성을 혼동하지 않는다.

수동 메모 변경은 AI 토큰 0이 정상이다. 카드 정규화와 확정된 규칙의 반복 적용도 일반 코드가 수행한다. Muse 호출은 사용자가 규칙 대화를 열었을 때 필요한 문맥에 한정한다.

## 5. 저장과 재시도

- 행 편집 중에는 브라우저에서 초안을 보관하고 저장 버튼으로 제출한다. 초안 하나를 위해 서버의 메모리 전용 API를 만들 필요는 없다.
- 저장 요청에는 row_id, expected_revision, 허용된 변경 필드, exception 또는 rule_change, client_request_id가 들어간다.
- 허용 필드는 서버의 원천 종류로 결정한다. 카드 날짜·금액은 고정하고 직접 입력 수입·수기 지출은 날짜·금액 편집과 이력을 지원한다. 은행 수입은 별도 정정 사건을 사용한다. 클라이언트가 원천 종류를 바꿔 편집 제한을 우회할 수 없다.
- 서버는 같은 요청 ID와 같은 내용이면 최초 저장 결과를 반환한다. 같은 ID의 다른 내용은 충돌로 거부한다.
- 행 revision, 변경 사건, 영향 탭 합계는 같은 트랜잭션으로 반영한다. 저장 성공 응답은 커밋 이후에 보낸다.
- 저장 후 응답이 끊기면 동일 ID로 결과를 조회·재시도한다. 새 요청 ID로 중복 사건을 만들지 않는다.
- 드롭다운 변경만으로 즉시 커밋하지 않는다. 선택 후 행 저장이라는 사용자의 확정 방식을 따른다.
- 수동 변경 필드는 자동 재분류로 덮어쓰지 않는다. 규칙 대화 장애는 이미 저장된 이번 행 수정을 되돌리지 않는다.
- 되돌리기는 이전 사건 삭제가 아니라 이전 값으로 정정하는 새 사건이다. 다른 변경이 추가됐다면 먼저 현재 revision을 대조한다.

## 6. 규칙 명세와 질문

### 규칙 초안의 최소 계약

```text
rule_id, version, base_rule_version
conditions: merchant_normalized, card_kind, transaction_direction
optional_conditions: amount_range, date_or_service_period
effects: display_tab_id, item, description_template
scope: trip_id, event_year, applicability
exceptions: 제외 조건
evidence_case_ids: 사용자 수정 사례
apply_existing, apply_future
status: draft | active | historical_only | superseded
```

규칙 효과에 금액·거래일 변경을 허용하지 않는다. 동작은 허용된 조건 연산자와 필드로 표현하며 Muse가 보내는 코드·SQL·셸 명령을 실행하지 않는다. 현재 파이프라인의 권위 매칭 규칙과 사용자 화면 배치 규칙의 효력을 구분한다.

예시: 숙박 거래를 특정 여행으로 보낸 사실만으로 `같은 가맹점이면 영구적으로 같은 여행`을 만들지 않는다. `숙박 항목 분류`와 `이번 연도 특정 여행 배치`를 분리해 질문하고 적용 범위를 기록한다.

질문은 앞선 답변과 행 변경 내용을 보고 1~5개 중 필요한 것만 묻는다. 예외를 선택했다면 다른 행 규칙 적용 설문을 띄우지 않는다. 새 규칙의 영향 행 수·금액은 서버 계산 결과를 사용한다. AI가 숫자를 추측해 화면에 쓰지 않는다.

### 미리보기와 적용

- preview_id에 규칙 내용 해시, 입력 revision 집합, 이전·새 값과 합계, 제외 행을 묶는다.
- 기존·미래 선택은 독립이다. 확인 화면에는 선택한 범위를 한국어로 요약한다.
- 미리보기 중 새로 변경된 행은 자동 덮어쓰기 대상에서 제외하고 변경된 범위를 다시 보여 준다.
- 새 규칙이 기존 규칙과 충돌하면 충돌 조건과 실제 예시를 보여 준다. 나중에 생성됐다는 이유만으로 기존 규칙을 폐기하지 않는다.
- 미래 적용을 해제해도 과거 적용 이력은 남는다. 규칙 비활성화가 기존 행을 자동 되돌리지는 않는다.

## 7. 로컬 Muse 연결 계약

웹앱·DB·카드 업로드와 기존 규칙 실행은 사용자 PC와 독립된 상시 실행 환경에 둔다. PC가 꺼져도 owner의 조회·수정·업로드와 담당 직원의 조회는 계속된다. Muse 연결만 PC에 의존하며, 연결 불가 시 설정된 Gemini를 웹앱 서버에서 호출한다. 호스팅 공급자와 요금제는 아직 선택하지 않았다.

영속 저장·작업 재개·백업 묶음·권한을 포함한 시험 복구는 [후속 명세 17절](WEB_LEDGER_SPEC_REFINEMENT.md), 무료 선행 시험 배포안은 같은 문서의 19절을 따른다. 유료 전환은 필요성과 비용을 보고한 뒤 별도 승인받는다. 로컬 파일 기반 구현을 영속 저장이 보장되지 않는 실행 환경에 그대로 올려 운영 준비가 끝났다고 보고하지 않는다.

- 웹 브라우저에 OpenCode 키나 Paseo 관리 권한을 전달하지 않는다.
- Muse 연결 어댑터에는 규칙 대화와 구조화 응답만 허용한다. 임의 에이전트 실행·명령 실행·로컬 경로 읽기 API를 웹에 공개하지 않는다.
- 원격 웹앱을 선택하면 로컬 연결 프로그램이 인증 후 외부로 작업을 가져오는 방식을 우선 검토한다. 공용 웹에서 로컬 데몬 포트를 직접 여는 방식을 기본으로 만들지 않는다.
- 요청 ID와 대화 ID로 재연결한다. 응답이 늦게 도착하면 연결된 행·규칙 버전과 맞는지 확인하며 최신 내용을 덮어쓰지 않는다.
- 모델은 `opencode/muse-spark-1.3-contributor-free`로 고정한다. 이 값은 모델 ID다. Paseo provider와 모델 ID를 조합하는 문법은 구현 시 실제 로컬 CLI 도움말과 가용 목록에서 확인한다.
- 로컬 PC에서 호출한다는 사실은 모델 추론이나 데이터 처리가 모두 PC 내부에서 이뤄진다는 뜻이 아니다. 호출 경로와 원천 전송 범위를 별도 관리한다.
- 문맥은 선택 행에 필요한 분류 속성, 관련 규칙, 사용자의 설명으로 제한한다. 전체 저장소·워크북·채팅 이력을 매 요청마다 보내지 않는다.
- 연결 불가·사용량 제한·형식 오류를 구분해 표시한다. 사용자가 설정한 Gemini fallback만 허용하며 임의의 제삼 모델로 전환하지 않는다.
- AI 답변이 늦거나 실패해도 장부 조회·저장·업로드·기존 확정 규칙 실행은 계속된다. AI 대기 때문에 기본 업무를 멈추지 않는다.

### 7.1 Gemini fallback 계약

사용자가 요청한 fallback은 구현자 모델이나 비용 파이프라인의 모델을 바꾸는 기능이 아니다. 규칙 질문을 돕는 대화 어댑터의 fallback으로만 구현한다.

- 기본 제공자는 `opencode/muse-spark-1.3-contributor-free`다.
- fallback 제공자는 사용자가 입력한 Gemini API key와 설정된 Gemini model ID다. API key를 코드·저장소·브라우저 저장 공간·URL에 넣지 않는다.
- owner 설정 화면에서 Gemini 키를 비밀번호형 입력 칸으로 등록·교체·삭제할 수 있다. HTTPS로 서버에 한 번 전송한 뒤 입력 칸을 비우며 키를 다시 반환하거나 브라우저 저장 공간에 남기지 않는다. 서버 비밀 저장소 또는 암호화된 저장소에 보관하고 암호화 키는 앱 DB와 분리한다. 배포 환경 변수 주입도 허용한다. fallback 키를 사용자 PC에만 보관하지 않는다.
- `GEMINI_FALLBACK_ENABLED=false`가 기본이다. 사용자가 켠 경우에만 동작한다.
- Muse 호출이 명시된 실패 조건인 연결 거부, 제한 응답, 시간 초과, 인증 실패, 서비스 오류를 반환할 때만 Gemini로 전환한다. Muse가 정상 응답했는데 내용이 마음에 들지 않는다는 이유로 자동 전환하지 않는다.
- fallback 전환은 조용히 일어나지 않는다. 대화창에 `Muse 연결 실패로 Gemini fallback 사용 중`을 표시하고 provider, model, 전환 사유 코드, 시각, 대화 ID를 기록한다.
- Gemini 호출 실패 시 다시 다른 모델을 시도하지 않는다. 사용자는 재시도 또는 AI 없이 이번 행 저장을 선택한다.
- Gemini model ID는 설정값으로 기록한다. 등록 시 실제 제공 목록과 무료 지원 여부를 확인하며 모델 이름을 추측하거나 유료 모델로 대체하지 않는다. 사용 정책은 `free_only`이며 사용자 API 키의 설정과 무료 한도를 따른다. 앱 자체의 유료 예산은 만들지 않는다.
- Gemini 요청에는 Muse의 제공자 내부 대화 ID를 보내지 않는다. 앱이 저장한 공통 대화 문맥으로 새 provider turn을 만든다.
- Gemini에도 장부 쓰기, 파일 삭제, 셸 실행, 외부 전기 도구를 주지 않는다.

### 7.1.1 키 등록과 전환 UX

- `설정 → AI 연결`에서 Muse 연결 상태, Gemini 등록 여부, 선택 모델, 자동 대체 사용 여부를 표시한다. 직원·가이드는 이 설정에 접근할 수 없다.
- 연결 테스트는 합성 짧은 요청을 보내고 성공 여부·실제 모델 ID만 반환한다. 실제 카드나 고객 자료로 키를 시험하지 않는다.
- 모델은 서버에서 조회한 가용 목록 중 무료 지원이 확인된 항목에서 선택한다. 모델 목록 조회나 키 연결 성공만으로 프로젝트가 무료 등급이라고 판정하지 않는다. Google AI Studio의 프로젝트 등급 확인 경로와 확인 시점을 설정에 남기고, 확인되지 않으면 설정 필요 상태로 둔다. 모델 이름을 코드에 영구 고정하지 않는다.
- 키와 모델이 유효하고 자동 대체를 켰다면 Muse 연결 불가 시마다 다시 허락을 요구하지 않는다. AI 패널에 현재 제공자와 전환 사실만 보여 준다.
- PC 연결이 끊긴 사실이 확인되면 긴 Muse 시간 초과를 매 질문마다 기다리지 않고 Gemini를 사용한다. 기존 Muse 요청이 아직 진행 중이면 attempt_id를 만료 처리하고 새 시도 하나만 연다.
- 늦게 도착한 Muse 응답은 이전 시도로 기록하되 Gemini 응답이나 규칙 초안을 덮어쓰지 않는다. 하나의 대화 턴에는 채택된 응답이 하나만 존재한다. API 비용까지 중복 발생하지 않는다고 보장하지는 않는다.
- Muse가 돌아오면 현재 답변 도중 제공자를 바꾸지 않는다. 다음 턴부터 Muse를 우선하고 같은 앱 문맥을 전달한다.
- 키 미설정·비활성·한도 소진·Gemini 실패라면 규칙 대화만 대기한다. 누락된 키를 대화창으로 보내 달라고 하지 않는다.

무료 한도 소진 시 유료 등급 전환, 자동 충전, 다른 키로 제한 우회를 하지 않는다. 일시적 제한은 공급자의 재시도 안내에 따라 제한된 횟수로 재시도하고, 일일 한도 소진은 문맥을 보존해 대기한다. 키 등록 때 무료 등급을 확인했더라도 사용자가 공급자 쪽 결제 설정을 나중에 바꾸면 API 키만으로 무과금을 보장할 수는 없다. 무료 여부 확인 기능과 실제 공급자 과금 통제를 구분해 보고한다. 이 정책은 AI 사용 정책이며 호스팅 비용까지 승인하거나 확정하지 않는다.

공식 근거: [Gemini 요금 등급](https://ai.google.dev/gemini-api/docs/billing), [요청 한도](https://ai.google.dev/gemini-api/docs/rate-limits). 연결 설정과 배포 시 최신 조건을 확인하며 장부 행 저장마다 외부 요금 문서를 조회하지 않는다.

### 7.2 제공자 사이의 문맥 보존

제공자 사이에서 모델의 숨은 기억이나 가중치가 이어지는 것은 아니다. 문맥의 정본은 앱 DB다.

앱 DB에는 공통 conversation_id, turn_no, provider, 실제 model_id, 사용자에게 보인 질문·답변, 정확한 사용자 확인 내용, 현재 행·탭·규칙 초안·미해결 질문 ID, 규칙 버전, provider 전환 사유를 저장한다. 모델로 보낼 문맥 묶음에는 필요한 대화 일부와 요약, 입력 문맥 해시를 사용한다. 요약만 유일한 근거로 저장하지 않는다. 개인정보는 제공자에게 보내기 전에 최소화한다.

Muse에서 Gemini로 바뀌면 앱은 새 Gemini turn에 현재 행의 허용된 정규화 필드와 revision, 확정된 규칙과 예외, 미해결 질문, 마지막 대화 요약과 규칙 초안, 새 사용자 요청을 전달한다. 전체 카드 파일·워크북·고객명·예약번호·메일 원문은 보내지 않고 가명·정규화·집계값으로 줄인다.

Gemini의 `previous_interaction_id`는 Gemini 내부 대화를 이어 갈 때만 사용한다. Muse로 돌아갈 때도 같은 앱 문맥에서 새 Muse turn을 만든다. 따라서 대화 문맥은 앱이 저장해 다시 보내면 유지되지만, Muse의 제공자 내부 상태나 모델 가중치가 Gemini로 이전되는 것은 아니다. 확정된 업무 규칙은 DB의 규칙 버전으로 유지되며, 대화가 모델을 즉시 재훈련하지는 않는다.

fallback 검증은 Muse 질문, Muse 실패, Gemini 전환, 같은 conversation_id의 추가 질문, Muse 복귀를 합성 자료로 검사한다. 모델이 기억한다고 주장하는지만 보지 말고 앱이 보낸 규칙 ID와 요약을 바탕으로 같은 선택지를 유지하는지 확인한다.

모델별 내부 상태·서명·비공개 추론은 다른 제공자로 옮기지 않는다. 공통 문맥은 사용자가 확인한 사실·규칙·질문 답변과 관련 행 상태로 재구성한다. 확정 규칙은 요약과 충돌하면 원문 결정을 우선한다. 문맥 길이를 줄일 때도 미해결 질문·현재 행 revision·규칙 적용 범위는 누락하지 않는다.

모델이 바뀌면 표현과 추론 결과가 같다고 보장할 수 없다. 앱이 확정된 규칙을 실행하는 결과는 동일한 버전·입력에서 같아야 한다. 새 모델의 제안은 기존과 동일한 구조 검사·영향 계산·사용자 확인을 거친다. 제공자 자체의 대화 저장 기능에만 의존하지 않는다.

공식 참고: [Gemini 대화와 상태 관리](https://ai.google.dev/gemini-api/docs/interactions-overview), [대화 기록 전달](https://ai.google.dev/gemini-api/docs/get-started). API 옵션과 모델 가용성은 구현 시 재확인한다.

## 8. 양식과 선택 출력

확인한 로컬 템플릿은 `매출자료 양식_rev`이며 아래 위치를 가진다. 최신 Drive 실물 확인은 인증 파일 누락으로 미완료다.

| 위치 | 내용 |
|---|---|
| B7:H7 | 거래일자, 이름, 닉네임, 예약금, 잔금, 추가금, 금액(원) |
| B8:H30 | 수입 입력 슬롯 23행 |
| C31 | `SUM(H8:H30)` |
| B34:H34 | 거래일자, 항목, 내용, 기간, 예약번호, 증빙유형, 금액(원) |
| B35:H84 | 지출 입력 슬롯 50행 |
| C85 | `SUM(H35:H84)` |
| C87 | `C31-C85` |

`ledger_current.xlsx`와 `ledger_latest.xlsx`의 확인 시점 SHA-256은 모두 `76e839c5c001f67d8cb94a266b9f0e42eff5164e93591163d15b474b6b37fa56`이다. 두 파일이 같다는 사실은 최신 Drive와 같다는 증명이 아니다. 이관 시 사용자가 지정한 기준본과 비교한다.

- 출력 요청은 선택 tab_ids, 현재 저장 버전, 템플릿 버전을 가진다. 화면에서 보던 저장 결과와 같은 버전으로 출력한다.
- 미저장 행이 있으면 저장된 값으로 출력하는지 또는 먼저 저장하는지 분명히 표시한다. 편집 초안을 조용히 섞지 않는다.
- 출력 구성은 한 파일 여러 시트로 확정됐다. 선택한 탭의 현재 저장 버전을 고정하고 화면 배정·수정값·후보 행을 보존한다. 선택하지 않은 업무 시트는 포함하지 않는다. 미저장 편집은 저장 후 출력하거나 화면으로 돌아가도록 한다. 스크롤·페이지 단위로 행이 잘리지 않게 선택 탭의 전체 행을 출력하며 필터가 켜졌다면 전체 행 출력임을 안내한다. 전체 대사를 다시 실행하지 않는다.
- 23개 수입 또는 50개 지출 슬롯을 넘으면 영역을 확장하고 하단 구역·합계·인쇄 영역을 함께 이동한다. 수식을 이전 고정 행번호에 남기지 않는다.
- 긴 예약번호·선행 0은 텍스트다. 원천 문자가 `=` 등으로 시작하면 수식으로 실행하지 않는다. 수식은 출력기가 생성한 계산 칸에만 넣는다.
- 원화는 정수로 계산하며 빈 금액을 임의의 0으로 바꾸지 않는다. 외화 금액과 통화는 원천 상세에 보존한다.
- 합계 수식과 계산값을 대조한다. openpyxl로 파일을 저장한 것만으로 수식 재계산 검증을 완료했다고 보고하지 않는다.
- 서식·수식 회귀 검사는 출력기 변경 시 대표 합성 자료로 수행한다. 동일한 출력기를 누를 때마다 전체 파이프라인 테스트를 다시 돌리지 않는다.
- 후보를 포함한 출력은 화면 내용대로 제공하고 미확정 안내는 출력 대화창에 표시하는 것으로 확정됐다. 파일에 별도 상태 표기를 추가하지 않으며 화면 상태 숨김을 외부 전기 확정으로 확대하지 않는다.

## 9. 정보 이관과 완전성

정보를 포괄한다는 요구는 금액 합계가 같다는 뜻으로 축소하지 않는다.

1. 원본 탭, 수입·지출 행, 메모, 수식, 증빙 링크, 예약번호, 기간, 통화, 작성 정보의 목록을 만든다.
2. 각 원본 항목에 앱 필드 또는 행 상세의 보존 위치를 연결한다. 매핑되지 않은 항목은 개수와 원문 위치를 보고한다.
3. 수식은 원문과 계산 의미를 보존하되 고객 입력 임의 수식을 서버 코드로 실행하지 않는다.
4. 수입은 기본적으로 입금 한 건마다 한 행으로 입력하며 사용자가 분할한 입금은 배분별 행을 표시한다. 원천 입금은 한 건으로 유지하고 전체 원금을 배분액과 다시 더하지 않는다. 고객별 합계는 별도 요약이며 고객 이름으로 입금 사건을 합치거나 중복 제거하지 않는다. 동명이인과 여러 입금일을 stable customer_id와 income_event_id로 구별한다.
5. 수입과 카드 지출을 모두 원거래와 정정 사건으로 추적한다. 고객 환불을 양수 수입으로 바꾸지 않는다. 입금 종류와 환불 여부는 별도 속성으로 보존해 예약금 환불인지 잔금 환불인지 잃지 않는다. xlsx의 예약금·잔금·추가금 열에도 사건별로 표시하며 고객 요약을 수입 합계에 다시 더하지 않는다. 환불 열 표시 세부 정책은 별도 확인한다.
6. 시험 이관과 본 이관을 구분한다. 본 이관 이후 매 편집마다 구글 시트를 다시 읽는 절차를 새 앱에 가져오지 않는다.
7. 백업은 앱 DB의 일관된 스냅샷과 원천 파일·참조 목록을 함께 보존한다. 실제 복구가 되는지는 시험 복구로 확인한다. 보존 주기·위치는 배포 선택 후 정한다.

### 수입 직접 입력과 은행 파일 가져오기 계약

사용자 확정: 두 입력 경로를 함께 지원한다. 직접 입력한 수입은 날짜·금액을 편집하고 이력을 보존한다. 은행 원본은 고정하고 별도 정정 기록으로 처리한다. 카드 원천 날짜·금액 수정 금지는 그대로 유지한다. 정정 사건과 실제 환불 사건을 구분하고 상세 동작 계약의 수입 정정 계산을 따른다.

1. 직접 입력은 여행, 실제 입금일, 금액, 입금 종류, 고객 연결, 메모를 받는다. 이름과 닉네임은 표시값이며 고객 식별자가 아니다. 고객을 아직 모르면 연결 대기로 보존하고 이름만으로 병합하지 않는다. 저장 요청의 중복 전송은 기존 수입 사건을 반환한다.
2. 은행 파일은 파일 봉인과 프로필별 열 매핑을 사용한다. 은행·계좌의 내부 식별자, 거래 식별자, 입출금 방향, 거래일시, 금액, 입금자 원문, 원천 행을 보존한다. 계좌번호는 화면과 로그에서 마스킹하고 AI에는 보내지 않는다. CSV·XLSX부터 설계하되 실제 은행 양식이 확인되지 않은 파서는 지원 완료로 보고하지 않는다.
3. 출금이나 계좌 내부 이체를 고객 입금으로 자동 승격하지 않는다. 은행 거래 방향과 수입의 예약금·잔금·추가금 분류를 구분한다. 수입에 해당하지 않는 행도 업로드 원천에서 조용히 삭제하지 않으며 처리 결과에 제외 사유를 남긴다.
4. 기존 source·projection 식별 규약을 재사용한다. 은행의 안정 거래 ID가 있으면 계좌 범위와 함께 사용한다. 없는 경우 프로필의 결정론적 식별 규약과 동일값 반복 거래 구분 근거를 보존한다. 날짜·입금자·금액이 같다는 이유만으로 실제 다른 입금을 합치지 않는다. 기간이 겹치는 파일도 중복 사건을 만들지 않아야 한다.
5. 직접 입력한 수입과 은행 원천의 대응이 검증되면 기존 수입 사건에 근거를 연결하고 새 수입을 추가하지 않는다. 근사 일치만 있으면 후보로 보여 주며 자동 삭제·병합하지 않는다. 미해결 중복 후보는 가져오기 검토에서 보존하고 확정 수입 합계에 두 번째 사건으로 넣지 않는다. 이는 원천 중복 판단이며 카드 여행 배정 후보를 자동 배치한다는 정책과 구분한다.
6. 고객·여행·입금 종류가 명시 관계나 확정 규칙으로 결정되면 반영한다. 해결되지 않은 수입 행은 `분류대기`의 수입 구역에서 연결할 수 있게 한다. 예약금·잔금·추가금 비율을 AI가 만들어 내지 않는다. 은행 파일의 입금자명은 고객 연결 전에도 원문으로 보존한다.
7. 한 입금을 여러 고객·여행·입금 종류로 나누는 기능은 사용자 확정이다. 사용자가 배분액을 결정하고 AI가 임의 분할하지 않는다. 원금·배분·잔액·정정·재업로드·출력의 세부 계약은 후속 명세 10절을 따른다.
8. 합성 수용 검증은 동일 파일 재업로드, 기간 겹친 파일, 동일 일시·금액의 서로 다른 입금, 직접 입력 후 은행 근거 연결, 동명이인, 미식별 입금, 출금 포함 파일을 다룬다. 사건 수·행별 부호·합계를 검증하고 고객 요약을 다시 합산하지 않는다. 합성 테스트 통과를 실제 은행 파일 검증으로 표현하지 않는다.

### 담당 여행별 조회 계약

여행 접근 범위는 사용자 ID와 stable trip_id 관계로 관리한다. 탭 숨김만으로 권한을 구현하지 않는다. 목록·행 상세·검색·고객 요약·첨부·출력·이력 API 모두 서버에서 검사한다. 고객별 합계도 담당 여행 범위 안의 입금만 합산한다. 이동 전 여행의 조회자가 이동 후 다른 여행 정보까지 읽지 못하게 현재 권한을 확인한다. 권한 해제를 수신하면 이미 열어 둔 화면의 후속 요청에도 적용한다. 원천에서 해제한 시점부터 수신까지의 지연은 아래 동기화 계약에서 측정한다.

담당 여행은 예약 시스템의 가이드 배정 정보를 연동한다. 직원·가이드는 화면 조회만 가능하며 xlsx 생성·출력 작업 조회·파일 다운로드는 owner만 가능하다. 여행 종료 이후에도 유효한 담당 권한이 유지되면 조회할 수 있다. 담당 해제 또는 계정 비활성화 시 접근을 종료한다. 포트폴리오 예시 데이터는 운영 DB·인증·원천 파일과 분리한다.

직원의 허용된 상세 필드는 고객 이름·닉네임·예약번호·해당 여행 증빙이다. 내부 메모·수정 이력·AI 대화는 서버 응답에서 제외한다. 여러 여행을 포함한 원본 카드·은행 파일은 직원에게 제공하지 않는다. 모바일은 동일한 역할별 권한을 적용하며 owner의 입력·업로드·규칙 대화·xlsx 출력을 모두 지원한다. 상세 계약 15~17절의 수기 지출·증빙·모바일 검증을 해당 구현 단계에 포함한다.

#### 예약 시스템 연동 근거와 구현 경계

2026-09-23 코드 확인 대상은 `C:\AX\reservation`이다. 운영 DB나 비밀값을 읽지 않았다.

- `src/lib/db.ts`: `guides.id`, `tours.id`, `tours.cafe_fldid`와 담당자 닉네임 필드가 있다. 로그인 사용자와 활성 담당자 ID를 연결하고 기존 일정 매핑을 통해 예약 여행 ID와 cost의 trip_id를 연결한다. 닉네임을 새 식별자 체계로 만들지 않는다.
- `src/lib/leaderTours.ts`: 여행 담당자·예약 담당자뿐 아니라 과거 여행 제목의 닉네임 접두사도 목록에 사용한다. 이 목록 전체를 장부 접근 권한으로 그대로 사용하지 않는다. 명시 배정은 예약 서버에서 담당자 ID로 유일하게 해석하며 애매하면 권한을 부여하지 않는다.
- `src/app/api/admin/leader-tours/route.ts`는 닉네임 기반 관리자 조회다. 현재 형태가 안정적인 사용자 식별과 권한 해제 계약을 제공한다고 간주하지 않는다.
- `src/app/api/internal/tours/route.ts`는 완료 여행과 오래된 여행을 제외하므로 전체 권한 동기화 자료로 쓸 수 없다. 목록에 없다는 사실만으로 담당 해제로 처리하지 않는다.
- `src/lib/leaderLink.ts`의 서명된 여행 링크 보유는 개인 로그인 신원이 아니다. 링크 토큰을 복사해 장부 로그인이나 권한으로 재사용하지 않는다.

새 읽기 전용 서버 간 연동 또는 기존 export 확장이 필요하다. 최소 계약은 담당자 ID, 여행 ID, 배정 ID, 활성·해제 상태, 원천 revision, 관찰 시각이다. 완전한 스냅샷인지 증분인지와 범위·커서를 명시하고, 명시 해제 사건 또는 완전한 스냅샷에서만 권한 제거를 계산한다. 이전 revision이 뒤늦게 와도 해제한 권한을 복구하지 않는다. 실제 필드명과 인증 방식은 구현 단계에서 기존 인증 경로와 맞춘다. 예약 DB 직접 공유·쓰기나 고객 원본 자료 전송은 필요하지 않다.

권한 확인은 서버 요청 경계에서 한다. 최신 배정 조회 또는 유효기간이 있는 확인 결과를 사용하고, 원천 장애로 확인 결과가 만료되면 직원 조회만 대기한다. owner의 장부 작업은 유지한다. 캐시를 사용하면 권한 해제의 최대 전파 지연을 명시하고 실제 지연을 검증하며 즉시 반영이라고 과장하지 않는다. 여행 종료일 자체는 권한 만료일이 아니다. 대장이 아닌 직원의 예약 계정 대응이 없으면 매핑 필요로 남기고 이름으로 추정하지 않는다. 예약 시스템과 맞추어 사용자 화면의 가이드 호칭은 `대장`을 사용한다.

성능 목표는 실측 전 제안이다. 기준 데이터와 실행 기기를 기록하고 첫 로드와 캐시된 로드를 구분한다. 한 행 저장 후 화면 반영은 서버 처리 p95 500ms 이내, 탭 전환 p95 1초 이내를 우선 목표로 한다. WAN 지연과 AI 응답 시간은 따로 측정한다. 미달이면 병목과 원인을 보고하고 테스트 값을 임의로 완화하지 않는다.

토큰 절감은 추정 퍼센트 대신 실제 모델 호출 수·입출력 토큰 수·전체 대사 호출 수·원천 파싱 횟수로 보고한다. 기본 조회·저장·확정 규칙 적용·xlsx 출력은 LLM 호출 0이 목표다.

## 11. 구현 작업 단위

아래 표는 기능 묶음이다. 실제 실행 순서·단계별 사용자 확인·재개 상태는 [단계별 진행표](WEB_LEDGER_PHASES.md)가 정본이다. 이 표의 순서를 이유로 합성 화면 전에 모든 API·파서를 구현하지 않는다.

| 순서 | 범위 | 완료 산출물 |
|---|---|---|
| 1 | 현재 파서·사건 저장소의 어댑터 선택 | 재사용 경로와 필요한 마이그레이션 목록 |
| 2 | 합성 여행 탭·행 조회와 편집 | 수입 위·지출 아래 화면, 행 저장·충돌 |
| 3 | 카드 업로드·후보 자동 배치 | 실제 진행 표시, 분류대기 드롭다운, 중복 방지 |
| 3a | 수입 직접 입력·은행 파일 업로드 | 입금 사건 저장, 중복 가져오기 방지, 직접 입력과 원천 연결 |
| 4 | 규칙 질문·미리보기·적용 | 네 적용 조합과 수동 고정 검증 |
| 5 | 로컬 Muse와 서버 Gemini 연결 | 공통 대화 문맥, 무료 한도 대기, 늦은 응답 처리 |
| 6 | 선택 xlsx 출력 | 양식 보존과 슬롯 확장 검증 |
| 7 | 예약 배정 연동·접근 범위·배포 구조 | 담당 해제 반영, 종료 여행 조회 유지, owner 전용 출력, PC 독립 동작 |
| 8 | 실제 이관 준비·대표 흐름 검증 | 매핑 누락 보고, 시험 복구, 성능·토큰 측정 |

현재는 설계 단계다. 이 문서가 있다고 구현·배포를 시작한 것으로 보고하지 않는다. 구현 시 한 작업자에게 한 단계와 필요한 코드·합성 예시만 전달하고, 전체 원장과 과거 대화 전문을 반복 전달하지 않는다.
