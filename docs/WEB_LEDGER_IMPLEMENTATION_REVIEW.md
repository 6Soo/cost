## 3. 수정 순서와 완료 기준

### R01 — 저장·이력·요청 결과를 한 번에 확정

우선순위: 최우선. 대상: `ledger_store.py`의 초기화, `save`, 생성·가져오기 경로, `_replay_pending`.

현재 행과 revision을 먼저 COMMIT하고 나중에 별도 `.operator.sqlite`와 요청 결과를 저장한다. 구현 기록의 같은 SQLite·단일 정본 설명과 다르다. 지연 기록 재생도 최초 사건 payload 대신 다른 action·rationale을 만들고 revision의 사건 연결을 복구하지 않는다.

수정 계약:

1. 기존 사건 저장소 어댑터를 사용하되 장부 행·변경 사건·수동 고정·학습 사례·요청 결과를 같은 DB 트랜잭션에 넣는다. 이 트랜잭션의 사건에 변경 전후 값과 원천 연결이 있어야 한다.
2. 기존 operator 저장 API를 조정해야 하면 해당 웹 장부 경로와 호환성 범위만 수정한다. 구현 기록의 `기존 파일 수정 금지`를 이유로 새 정본 DB를 추가하지 않는다. 운영 DB·원본·과거 출력 보존은 계속 적용한다.
3. 정본 사건을 지연 기록으로 대체하지 않는다. 외부 감사 복제본이 실제 필요할 때만 같은 트랜잭션의 내구성 있는 outbox에서 동일 payload를 복제한다. 이번 범위에 불필요한 별도 복제 서비스를 만들지 않는다.
4. revision 확인은 쓰기 트랜잭션 내부에서 수행하거나 조건부 UPDATE로 보장한다. 인스턴스별 Python lock만으로 서로 다른 연결의 충돌을 보장했다고 보고하지 않는다.
5. 요청 ID에 작업 종류·대상·기준 revision·정규화한 입력을 결속한다. 같은 내용은 최초 결과 그대로, 다른 내용은 `REQUEST_ID_REUSED`다. 생성·수정·정정·연결에도 같은 계약을 적용한다. 빈 ID와 짧게 자른 ID에 의한 행 충돌을 처리한다.

최소 검사: COMMIT 전 중단·COMMIT 후 응답 전 중단 각각 재시작, 동일 요청 재전송, 다른 내용 재전송, 두 연결에서 같은 revision 변경. 완성된 효과는 한 번이며 행과 사건·요청 결과가 함께 있어야 한다. 변경 없는 요청은 새 변경 사건을 만들지 않는다.

### R02 — 실제 서버의 은행 업로드 트랜잭션

우선순위: 최우선. 대상: `BankImporter.receive`, `LedgerStore.import_income_row`, 서버 초기화.

은행 importer가 `store.conn`에서 트랜잭션을 연 채 store가 다시 BEGIN한다. 기존 은행 테스트는 별도 `imports.sqlite`를 사용해 이 구성을 놓쳤다.

- 트랜잭션 소유자를 하나로 정하고 하위 함수는 열린 트랜잭션을 재사용한다. 테스트 통과를 위해 운영 경로와 다른 DB 구성을 만들지 않는다.
- 원천 행·업무 사건·처리 상태를 함께 확정한다. 중간 실패 후 재시작해도 원천 상태와 장부가 엇갈리지 않아야 한다.
- `completed`는 실제 처리 완료 후에만 기록한다. 서버 예외를 구조화된 실패 응답으로 바꾸되 데이터 오류를 성공으로 숨기지 않는다.
- 최소 검사: 실제 `serve`로 은행 1행 업로드, 동일 파일 재업로드, 처리 중 실패·재개. 새 입금은 1건이어야 한다.

### R03 — 카드 50행 제한과 진행 화면

우선순위: 높음. 대상: 카드 처리 예약·재개 경로, `Handler.do_POST`, `import_page`.

HTTP 요청은 `process()`를 한 번만 호출하고 기본 크기는 50이다. 재업로드는 재사용 결과만 반환한다. 화면은 서버 상태와 무관하게 한 번 조회 후 `완료`를 표시한다.

- 접수 후 작업 ID를 반환하고 단일 작업자가 저장된 미처리 범위를 끝까지 처리한다. 첫 버전에서 외부 큐 서비스는 필요 없다. 프로세스 재시작 시 미완료 작업을 안전하게 재개한다.
- 반복 진행 조회는 상태 조회이며 업무 처리를 중복 실행하지 않는다. 이미 커밋한 묶음은 장부에서 볼 수 있어야 한다.
- 일시 실패·서버 오류·네트워크 오류를 화면에 표시하고 재시도 경로를 제공한다. `fetch`의 상태와 JSON 오류를 검사하며 진행 중·오류를 완료로 표시하지 않는다.
- 원천 처리 상태·사건 삽입·누적 건수 갱신의 중단 경계를 맞춘다. 재개 후 신규 사건 수가 중복 생략 수로 잘못 바뀌지 않아야 한다.
- 최소 검사: 실제 HTTP 51행, 중간 중단·재개, 같은 파일 재시도. 마지막은 51건이며 진행 중 화면을 조회할 수 있어야 한다. 브라우저 업로드 실패 원인을 자동화 환경으로 단정하지 않는다.

### R04 — 직접 수입·수기 지출의 실제 편집 경로

우선순위: 높음. 대상: `detail_page`, 행 저장 HTTP 입력 처리, `_validate`.

직접 수입에 편집 폼이 없고 수기 지출도 카드용 폼을 쓴다. HTTP는 모든 금액·날짜 변경을 차단하고 수입의 고객·종류 변경 필드도 전달하지 않는다. 저장소 함수의 테스트 통과로 화면 편집을 완료 처리할 수 없다.

- 서버가 원천 종류를 읽어 허용 필드를 정한다. 클라이언트의 source_kind 값으로 편집 권한을 바꾸지 않는다.
- 직접 수입: 고객·여행·종류·날짜·금액·메모 편집. 수기 지출: 기존 허용 필드와 날짜·금액 편집. 카드: 원천 금액·날짜 고정. 은행: 별도 정정 경로.
- 정상 달력 날짜를 검사한다. `2026-99-99` 같은 정규식 일치 문자열, 불리언 금액, 유효하지 않은 목적지를 거부한다. 생성·수정·가져오기에서 공통 검증을 재사용한다.
- 알 수 없는 필드를 조용히 버리고 성공하지 않는다. 메모를 빈 문자열로 지울 수 있도록 폼 파싱에서도 빈 값과 필드 생략을 구분한다.
- 최소 검사: HTTP 직접 수입 500000→450000, 수기 지출 날짜·금액 수정, 카드 동일 요청 거부, 메모 지우기, 수입의 여행·종류 변경 후 합계. 이후 같은 흐름을 좁은 화면에서 한 번 확인한다.

### R05 — 은행 정정의 순서·revision·날짜

우선순위: 높음. 대상: 정정 저장·조회·화면과 출력 투영.

- 정정 요청에 expected_revision을 요구하고 성공 시 증가시킨다. 같은 시각의 UUID·문자열 정렬로 최신 정정을 고르지 않는다. 확정된 revision 또는 사건 순번을 사용한다.
- 원천 날짜·금액을 유지하면서 현재 장부 날짜·금액을 별도 투영한다. 은행 날짜 정정도 기존 확정 범위다.
- 정정 전 값은 바로 앞 유효 정정값이다. 요청 내용이 달라지면 충돌이며, 재시도 응답에 제출값을 그대로 돌려주지 않는다.
- 공통 투영 결과를 화면·합계·xlsx가 소비하게 한다. 화면만 별도 `display_amount()`로 바꾸는 우회 구현을 제거한다.
- 최소 검사: 시각을 같게 고정한 정정 450000→470000, 낡은 revision 거부, 다른 payload의 요청 ID 재사용 거부, 날짜 정정과 원천 보존.

### R06 — 직접 입력과 은행 원천 연결의 업무 동일성

우선순위: 최우선. 대상: 은행 수집·중복 후보·`link_bank_source`·원천별 편집 제한.

현재 연결은 존재 여부 확인 없는 관계 INSERT뿐이다. 이미 생성한 은행 수입을 합계에서 제외하거나 직접 입력 사건에 결속하지 않으며, 연결 후 편집 정책도 바뀌지 않는다.

- 은행 배치·행 실존, 원천 동일성, 기존 연결, 대상 revision을 검사한다. 존재하지 않는 원천·다른 입금의 연결을 거부한다.
- 직접 입력과 중복 가능성이 있으면 은행 원천을 보존한 채 후보로 표시한다. 미해결 중복 후보를 두 번째 확정 수입으로 합산하지 않는 기존 계약을 지킨다. 근사 일치만으로 자동 연결하지 않는다.
- 사용자가 동일성을 확정하면 한 업무 입금에 두 근거가 연결된다. 기존 식별자·과거 이력은 보존하고 현재 합계에는 한 번만 기여한다. 이미 이중 삽입된 합성 자료도 명시 관계로 바로잡되 과거 기록을 지우지 않는다.
- 연결 이후 날짜·금액 변경은 은행 정정 경로를 사용한다. 같은 은행 원천을 다시 업로드해도 두 번째 사건을 만들지 않는다. 여러 직접 입력에 임의로 같은 원천을 중복 연결하지 않는다. 수입 분할은 후속 명세의 명시 배분 계약으로 처리한다.
- 최소 검사: 직접 500000원→동일 은행 업로드→후보 확인→연결→재업로드의 최종 합계 500000원. 원천 없는 연결 거부·다른 행에 중복 연결 거부·연결 후 일반 금액 편집 거부도 확인한다.

### R07 — 분류대기와 메모 변경의 일관성

우선순위: 높음. 대상: 배정 값 정규화·편집 폼·학습 사례 생성.

- 내부 미배정 표현은 하나로 유지한다. 화면의 `unclassified`를 쓰는 경우 저장 경계에서 기존 NULL 표현으로 변환한다. 실제 여행 ID처럼 저장해 행을 목록에서 잃지 않는다.
- 편집 드롭다운에 현재 미배정 상태를 표현한다. 미배정 행의 메모만 고쳤는데 첫 번째 여행이 자동 선택돼 이동하지 않게 한다.
- 메모만 실제 변경됐다면 rule_change 선택이 있어도 학습 사례·규칙 대화를 생성하지 않는다. 기존 `save()`는 선택값만으로 학습 사례를 만든다. 실제 바뀐 업무 필드만 수동 고정 대상으로 삼는다.
- 최소 검사: 미배정 행 메모 수정 후 미배정 유지, 여행→분류대기 이동 후 조회·전체 합계 보존, 메모만 변경 시 학습 사례 0건.

### R08 — 은행·카드 원천 키와 보존

우선순위: 최우선. 대상: `bank_stable_key`, `stable_key`, 수집 충돌 처리·봉인.

은행 키는 계좌·거래 ID가 없어도 날짜·금액으로 만들어지고 입금자가 달라도 중복 생략한다. 반대로 안정 거래 ID가 같아도 금액이 바뀌면 키가 바뀌어 다른 입금으로 생길 수 있다. 카드도 금액·가맹점 등 변경 가능한 원문을 식별자에 포함한다. 카드의 취소 구분은 키에 빠져 있어 같은 파일의 상반된 상태를 놓칠 수 있다. 뒤의 카드 사례는 정적 검토이며 별도 재현 검사가 필요하다.

- 기존 `direct_sources`·`direct_projection`의 원천 사건 식별 계약을 조사해 재사용한다. 모델에게 신규 통합 정규화 체계를 만들게 하지 않는다.
- 안정 식별자와 내용 digest를 분리한다. 같은 ID·다른 업무 내용은 충돌로 보존하며, 식별 근거 부족을 날짜·금액만의 자동 중복 확정으로 바꾸지 않는다.
- 동일 파일 안과 겹친 파일 사이에 같은 기준을 적용한다. 서로 다른 거래는 원천 행·출처를 보존하고 중복 후보 여부를 구분한다. 통화·방향·취소 상태를 잃지 않는다.
- 현재 구현은 파일 digest와 파싱된 JSON을 저장하지만 원본 바이트 보관 경로가 없다. 봉인 완료라고 보고하려면 접근 제한된 원본 바이트 또는 기존 불변 원천 저장소의 참조와 실제 해시 재검증이 필요하다. 개인정보를 구현 모델에 보내지 않는다.
- 최소 검사: 날짜·금액 같은 서로 다른 입금 2건 보존, 같은 안정 ID의 금액 변경은 충돌, 같은 사건의 파일 간 반복은 한 번, 구매·환불 구분, 원본 바이트 해시 일치. 식별 불명확한 경우 사용자 확인 대상이지 자동 생략 대상이 아니다.

### R09 — 출력 초안의 화면 일치·양식·다운로드

우선순위: 높음. 대상: 격리 공간의 `sheets_export.py`와 출력 HTTP 경로. 아직 본 저장소에 반영되지 않은 코드임을 유지한다.

- 출력은 원천 payload가 아닌 R05의 현재 장부 투영을 고정된 읽기 스냅샷으로 소비한다. 거래·정정·배분·여행 메타데이터·선택 순서·양식 버전을 기준 해시에 결속한다.
- 기존 `매출자료 양식_rev`를 복제하거나 동등한 구조·스타일을 입증한 양식 자산을 사용한다. 현재의 빈 Workbook+헤더 생성은 회사·제목·수입/지출 구역 제목·병합·작성 정보가 없어 동등하지 않다. 인쇄 범위도 제목을 포함해야 한다.
- 소유자에게 실제 파일 다운로드까지 제공한다. 현재 폼은 작업 JSON으로 이동하며 파일 경로·다운로드 경로가 없다. 작업 JSON 응답은 xlsx 출력 완료 UX가 아니다.
- 미저장 초안이 있다는 사실을 감지해 저장 또는 돌아가기를 제공한다. `서버에 초안이 없어서 제외` 안내만으로 조용히 버리지 않는다. 미확정 안내는 대화창에만 표시한다.
- 같은 요청 ID의 다른 탭 선택은 거부한다. 동일 출력 기준의 새 요청은 기존 파일의 동일성을 확인해 재사용하거나 새 불변 파일로 만든다. 단순 `EXPORT_EXISTS`를 성공 재사용으로 보고하지 않는다.
- `exists()` 확인 뒤 `os.replace()`는 사이에 생긴 파일을 덮어쓸 수 있다. 겹친 실행·실패 재시도에도 기존 출력이 변하지 않는 게시 방식을 사용한다. 요청 ID를 파일 경로로 직접 사용하지 않는다.
- 최소 검사: 은행 정정 500000→450000 후 화면·합계·xlsx 일치와 해시 변경, 선택 여행별 작성일·담당자, 23/50행 초과, 선행 0과 긴 예약번호·수식처럼 보이는 원문 보존, 기존 파일 불변, 실제 다운로드. 스타일·인쇄 모습은 생성 파일로 한 번 확인한다.

## 6. 문서 통합 후 재개 기준

2026-09-24 후속 정리: 검토 대상 본 저장소의 네 코드 파일과 격리 공간 출력 모듈의 해시는 1절과 같았다. 해당 경로의 해결 증거는 추가되지 않았으므로 R01~R09를 완료로 바꾸지 않았다. 변경 없는 테스트는 반복 실행하지 않았다.

후속 네 결정은 DECISION_REGISTER.md에 통합했고, 제품·구현·상세 계약과 전달문의 수입 분할 미지원·되돌리기 미정·일반 탭 삭제 금지·전체 미구현 설명을 갱신했다. 5절 전달문의 결정 등록부 통합 지시는 이제 중복 추가가 아니라 기존 네 결정의 구현 상태와 근거 링크 확인으로 수행한다. 각 세부 계약은 후속 명세에 유지한다.

구현자의 WEB_LEDGER_PHASES.md와 WEB_LEDGER_IMPLEMENTATION_LOG.md는 단일 작성자 원칙에 따라 그대로 두었다. 이 두 파일의 과거 완료·미정·다음 작업 문구가 이번 검토나 결정 등록부와 다르면, 작업자가 다음 수정 묶음의 착수 기록에 정정한다. 초기 Phase 1 화면부터 재시작하거나 확정 질문을 다시 묻지 않는다.

- **R08 원본 보존:** 카드·은행 receive는 digest·파싱한 JSON을 기록하지만 전달받은 원본 바이트의 보존 경로는 확인되지 않았다. 파싱 전 파일을 불변 보관하고 digest로 결속해야 한다. 파일명을 바꿔 다시 올려도 중복 사건을 만들지 않으며 원본 바이트를 다시 읽어 해시를 확인할 수 있어야 한다. 실제 카드·은행 파서는 여전히 미연결이다.
- **R01 사건 저장 경계:** board의 행·요청을 함께 저장한 개선은 확인됐다. 하지만 operator 사건은 별도 DB에 기록하며, 은행 바깥 트랜잭션이 열려 있는 동안에도 append가 실행된다. 바깥 저장 실패와 별도 사건 성공이 갈라지는 경계를 제거해야 한다. 정본 변경 사건은 같은 트랜잭션에 완전하게 남기고 별도 복제가 필요하면 COMMIT 후 내구성 있는 기록에서 수행한다. 이를 완료했다고 인정할 장애 주입 증거는 아직 없다.
- **수정 D 범위:** 탭·배분·되돌리기 정상 검사는 추가됐으나 후속 명세 9절의 되돌리기 범위와 대조가 더 필요하다. 코드의 kind=alloc 되돌리기 허용을 전체 배분안 복원 기능의 사용자 승인으로 해석하지 않는다. 이미 확정된 행 단위 되돌리기와 묶음 변경의 경계를 맞추고, 계약에 없는 범위를 조용히 확대하지 않는다.
