#### 0. 목적, 범위, 완료의 의미

사용자는 날짜별로 카드 거래를 육안 확인하고 빠진 항목을 발견해 기존 거래 상세 화면에서 후속조치를 취한다. COST가 수집한 거래 전체를 보는 기능과 **원본 카드사 자료 대비 실제 누락을 자동 탐지**하는 기능은 다르다. 전자는 이번 1차 범위, 후자는 별도 2차 범위다. 이번 화면에서 “누락 없음” 같은 결론을 표시하지 않는다.

또한 웹 전체, 특히 하위 메뉴의 불균일한 UI를 공통 업무용 SaaS 디자인으로 정돈한다. 라이트는 밝고 차분한 A안, 다크는 어두운 B안. **2026-10-26 최신 승인에 따라 우상단 해·초승달 버튼 하나로 사용자가 직접 라이트/다크를 전환한다.** 처음에는 시스템 테마를 따르며, 선택 이후에는 사용자의 설정을 우선한다(§13).

**완료는** (1) 계약을 만족하는 화면과 조회 경로, (2) 해당 경로의 검증, (3) 실제 페이지별 UI 감사표와 적용 범위, (4) 변경 파일·검증 근거·미해결 항목이 있는 PR로 판정한다. PR 생성은 운영 배포 완료가 아니다.

1. docs/COST_V3_START_HERE.md → docs/COST_V3_CURRENT_HANDOFF.md 최신 절 → AGENTS.md를 읽고 기준선 SHA를 기록한다. 기존 완료 작업 재실행 금지.
2. 실제 서비스 라우트와 내비게이션을 검색한다. 후보: webapp/ledger_board.py, webapp/card_flow.py, webapp/card_actions.py, webapp/pages.py, webapp/static/, webapp/card_import.py, webapp/ledger_store.py. **파일명만으로 운영 페이지라고 단정하지 않는다.** webapp/pages.py에는 별도의 KPI/큐/게이트/원장 HTML 생성기가 존재하므로 어느 서버/메뉴에서 쓰이는지 확인한다.
3. 실제 카드 원행 저장소와 접근 API를 찾는다. 거래의 안정적 ID, 이용일, 이용시간(원본 존재 여부), 가맹점 원본/표준화 이름, 부호 있는 원금액, 통화, 카드사, 배치, 원본 중복·취소·환불·충돌, 사용자 확정 여행, 자동 추론 여행, 장부 기록 여부를 조사한다. 스키마·실제 함수/경로는 코드로 증명하고 PR에 기록한다.
4. 현재 owner 로그인/CSRF/접근제어와 거래 상세 링크를 확인한다. webapp/card_actions.py의 next_action()이 반환하는 href 및 /import?batch=...&transaction=... 경로 재사용을 우선 검토한다. UI 읽기 경로가 외부 네트워크 호출, 재분류, 장부 기록, AI 학습, DB 쓰기를 수행하지 않는지 확인한다.
5. 기존 CSS/JS, 공통 레이아웃, inline style, 모바일 구조, 하위 메뉴별 UI, 브라우저 검증 방법을 목록화한다.
6. 발견된 실제 코드에 맞춰 아래 제안 API·파일 위치를 구체화하되 **사용자 확정 UX와 금융 안전 조건은 변경하지 않는다**. 기존 데이터로 충족 불가능한 필드는 가짜로 만들지 않고 미확정 사항을 보고한다.

#### 2. 카드 전체 내역: 정보 구조

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--21-메뉴접근"></a>
##### 2.1 메뉴·접근

- 메뉴 표기: **카드 전체 내역**.
- 기존 owner 카드 관리 내비게이션에서 자연스럽게 접근 가능한 별도 하위 페이지로 둔다. 실제 URL은 기존 라우팅 관례에 맞춰 정한다. 권장 경로는 GET /cards/all 또는 기존 네임스페이스와 충돌 없는 동등 경로.
- 기존 owner 인증/권한 정책 그대로 적용. 익명/권한 없는 사용자는 기존 서비스 계약의 401/403/로그인 유도 흐름을 따른다. 임의로 접근 범위를 넓히지 않는다.
- 최초 진입: **2026년**, **선택 월 없음**, 1~12월 12개 월 타일, 전부 접힌 상태.
- 연도 선택: 2026년 기본. 데이터가 있는 다른 연도를 선택 가능. 연도를 변경하면 선택 월 해제. 선택한 연도는 페이지 내 상태로 유지하되 새로 진입할 때 기본값 2026년. 사용자 계정에 영구 저장하지 않는다.
- 연도 선택 후보는 원본의 유효한 이용일 연도에서 유도하고 2026년은 데이터 0건이어도 제공. 미래 연도/다른 연도 데이터가 있다면 제외하지 않는다.
- 12개월 선택 영역은 데스크톱 기준 **4열 × 3행 그리드**. 최초에 월별 상세 목록 12개를 세로 나열하지 않는다. 좁은 화면에서는 3열 또는 2열로 적응형 배치해 수평 넘침을 막는다.
- 각 타일: “1월”~“12월”과 해당 월 **거래 건수**. 0건도 타일을 표시한다. 선택 상태는 색뿐 아니라 테두리/aria-pressed 등으로 구분.
- 타일 클릭: 해당 월 목록을 그리드 바로 아래에 표시. 한 번에 한 달만 열림. 선택 중인 타일 재클릭 시 목록 닫힘. 월 변경 시 기존 목록 닫고 새 월만 표시.
- 월별 건수는 **선택 연도 전체의 저장된 고유 거래**를 기준으로 한다. 장부 반영 여부·분류 상태로 제외하지 않는다. 원본 업로드의 동일 거래를 가리키는 중복 출처 링크를 여러 거래로 세지 않는다. 단, 서로 다른 실제 거래 ID와 승인·취소·환불 원행은 임의 합치지 않는다.
- 월 타일을 열지 않아도 12개월 건수가 보인다. 서버 조회는 연도별 집계와 선택 월 상세를 분리해도 되며 기존 서버 관례를 따른다.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--22-거래-목록"></a>
##### 2.2 거래 목록

선택 월 목록 헤더: “2026년 10월”, 해당 월 총 N건. 기본 정렬은 **이용일 오름차순 → 이용시간 오름차순 → 안정적 거래 ID 오름차순**. 이용일시 헤더에 화살표(↑/↓) 또는 정렬 버튼을 표시하지 않는다. 정렬을 바꾸는 컨트롤은 1차 범위에서 제외.

필수 4개 논리 열:
1. **이용일시**: YYYY-MM-DD 및 실제 존재하는 경우에만 HH:mm 또는 원본에서 보장되는 정밀도. 시간이 없으면 날짜만 표시한다. “00:00”을 합성하지 않는다. 같은 날짜에서 시간 없는 거래는 시간 있는 거래 **뒤**에 배치한다.
2. **가맹점명**: 사용자가 원본 거래를 찾기 쉬운 이름. 원본명 우선, 없으면 검증된 표시명. 둘 다 없으면 “가맹점 미상”. 사용자 입력값 HTML 이스케이프.
3. **금액**: 원본 거래의 **부호와 통화**를 유지한다. KRW면 “12,345원”, 기타 통화면 통화코드와 원래 단위로 표시한다. 환율 환산액으로 원본을 대체하지 않는다. 취소/환불은 금액의 원래 부호와 별도 상태 표시를 모두 보존한다. 금액 우측 정렬, tabular 숫자.
4. **배정된 여행**: 현재 유효한 사용자 확정 배정 우선, 없으면 현재 유효한 자동/근거 배정. 확정되지 않은 추정은 “추정” 표시 가능하되 정확한 예약 확정으로 표현하지 않는다. 여행 후보가 전혀 없으면 “미배정”. 구글 장부 반영 상태와 여행 배정 상태를 혼동하지 않는다.

**2026-10-28 여행 열 과밀 개선 계약:** 카드 전체 내역의 여행 칸에는 여행명과 배정 출처만 표시한다. 카드 식별은 가맹점 아래, 거래 상태는 금액 아래에 배치하고 `상세 보기`는 별도 `상세` 열로 분리한다. 표는 이용일시·가맹점명·금액·배정된 여행·상세의 5열이며 날짜 그룹도 5열에 걸친다. 이 최신 배치가 아래 과거 4열 명세보다 우선한다. 표시용 이름 매핑·ID fallback·미배정·확정/추정 구별·원래 상세 링크·정렬·페이지네이션을 유지하며 금융/배정/원본 데이터는 수정하지 않는다.

거래 상태 표시(부차적): 취소/환불, 원본 충돌, 검토 필요, 장부 기록 완료, 기록 제외 등 **실제 확인된 기존 상태만** 작고 일관된 배지 또는 상세 텍스트로 표현한다. 새 상태 추론·새 회계 판정 금지. 거래별 조치 링크는 행 클릭/“상세 보기”로 제공하고 키보드로도 접근 가능해야 한다.

날짜별 소제목: 월 내부에서 “10월 21일 · 8건”처럼 그룹화한다. 거래가 없는 날짜를 **빈 날짜로 생성해 누락이라고 경고하지 않는다**. 사용자가 거래 없는 날짜를 찾는 것은 월별 원본 대조의 일부일 뿐, 해당 날짜 거래가 실제 없었는지는 COST가 확정할 수 없다.

월에 거래 0건이면 “이 달에 저장된 카드 거래가 없어.”로 안내하고, 카드사 원본에도 없다는 뜻이 아님을 오해하지 않게 한다.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--23-날짜와-미분류-원본의-경계"></a>
##### 2.3 날짜와 미분류 원본의 경계

- **이용일**은 기존 카드 파이프라인이 권위 있게 정규화한 사용일을 따른다. 원본에 사용일이 없고 기존 계약이 승인일/매입일 fallback을 허용한 경우만 기존 규칙을 그대로 적용하며 출처를 상세에서 구분한다. 정렬 편의를 위해 임의의 현재 날짜를 채우지 않는다.
- 유효한 이용일이 없는 저장 원행도 “전체”에서 사라지면 안 된다. 연도에 배치할 권위 있는 날짜가 없으면 연도 그리드와 별개로 **“날짜 확인 필요”** 섹션과 건수를 제공한다. 연도 필터로 인해 이 원행이 감춰진다는 사실을 안내하고, 이 섹션은 선택 연도와 무관하게 접근 가능하게 한다. 기존 DB에 이런 행이 없다면 0건 상태로 처리한다.
- 파싱 오류·보류·미기록·제외·중복 출처·취소·환불이 존재해도 저장된 거래 원행은 조회 대상이다. **중복 업로드를 하나의 실제 거래로 식별하는 기존 원본 동일성 계약**을 준수하며, 오류로 거래 ID 자체가 만들어지지 않은 업로드 파일은 거래 목록에 가짜 행을 만들지 않는다. 파일 파싱 실패는 기존 업로드 오류 화면으로 연결한다.
- 원본 내역과 Google 장부 내역을 합쳐 거래 수를 부풀리지 않는다. 실제 카드 원행을 중심으로 조회한다.
- 2026년 이전 자료를 다른 기존 화면에서 운영 검토 범위 밖으로 숨기더라도, 이번 화면은 “저장된 모든 카드 거래” 요구를 따른다. 다만 접근제어·법적 보존 정책·데이터 권위 제약을 우회하지 않는다. 충돌이 있으면 임의로 삭제/노출하지 말고 별도 판단 항목으로 보고한다.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--24-상세-및-후속조치"></a>
##### 2.4 상세 및 후속조치

- 행 클릭 또는 “상세 보기” → 기존 거래 상세 화면으로 이동. 가능하면 기존 카드 배치·거래 ID를 이용해 원행을 정확히 지정한다.
- 상세에서 기존 **여행 변경**, **재검토/원본 확인** 기능을 재사용한다. 새 자동 분류기, 새 AI 대화, 새 장부 쓰기 경로를 만들지 않는다.
- 기존 사용자 확정 여행을 화면 조회나 새로고침이 덮어쓰지 않는다.
- 이동/재검토 저장 시 기존 owner/CSRF/revision/감사 기록을 그대로 요구. GET은 읽기 전용.
- 거래가 상세 경로에서 열리지 않는 예외(원본 충돌 등)는 해당 거래 ID·상태를 유지한 채 기존 원본 검토 경로로 안내한다. 임의로 다른 거래로 연결하지 않는다.
- 상세에서 돌아오면 선택 연도·월을 URL query 또는 브라우저 history state 등으로 복원할 수 있도록 권장. 구현은 민감정보 없는 year/month만 허용.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--25-조회-성능응답"></a>
##### 2.5 조회 성능·응답

- 월 상세 데이터가 많아도 최초 화면에 12개월 전체 원행을 로드/DOM 렌더하지 않는다. 초기 연도 집계 → 선택 월 상세 지연 로드.
- 월 상세가 큰 경우 페이지네이션/점진 로딩 적용. 권장 100건 단위, 다음 페이지에서도 정렬 안정성 유지, 월 건수는 전체 월 기준. 서버에 임의 최대 100건만 반환하고 “전체”로 표시하는 오류 금지.
- 기존 데이터 저장소의 read-only 쿼리/인덱스를 재사용하고 N+1 여행 조회를 피한다. 새 DB 인덱스·스키마 마이그레이션이 필요하면 별도 승인 항목으로 분리.
- API JSON 계약을 신규 추가할 경우 예시(실제 코드에 맞게 명명): GET /api/cards/years → years, GET /api/cards/summary?year=2026 → months[1..12].count 및 undated_count, GET /api/cards/transactions?year=2026&month=10&cursor=... → rows/next_cursor/total. **예시 URL은 고정 명령이 아니라 구현 시 기존 라우팅과 충돌 확인 후 확정**.
- 입력 검증: year 유효한 4자리, month 1..12, cursor 위변조/만료/불일치 시 안전한 오류. 모든 API 기존 권한 보호. 개인 데이터가 들어 있는 API는 캐시/로그에 무단 노출 금지.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--3-ui-시각상호작용-계약"></a>
#### 3. UI 시각·상호작용 계약

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--31-정보-위계"></a>
##### 3.1 정보 위계

공통 구조: 서비스 내비게이션 → 현재 위치/페이지 제목/한 줄 설명 → 검색·필터(필요한 페이지에만) → 주요 작업 영역 → 상태/오류 안내. 불필요한 카드 안의 카드, 과도한 설명, 중복 버튼을 줄인다.

카드 전체 내역 화면:
- 페이지 제목 “카드 전체 내역”
- 오른쪽 연도 선택(접근성 있는 label)
- 월 그리드 4×3
- 월 미선택: “확인할 월을 선택해 줘.”와 같은 간결한 빈 상태
- 월 선택: 해당 월 거래 목록, 날짜 소제목, 필수 4열, 상세 진입
- 월 그리드와 목록은 하나의 화면에서 연결. 선택 월이 바뀌어도 전체 페이지 새로고침이 필수는 아니다.
- 데이터 로딩/오류/0건/권한 오류/시간 없음/미배정/취소·환불을 별도 상태로 다룬다.
- 테이블 열 제목은 **이용일시, 가맹점명, 금액, 배정된 여행**. 이용일시 정렬 화살표 금지.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--32-반응형"></a>
##### 3.2 반응형

- 넓은 화면: 월 타일 4열, 테이블 4열 유지.
- 중간 화면: 월 타일 3~4열, 헤더/필터 줄바꿈 허용.
- 모바일: 월 타일 2~3열, 거래는 4열을 억지로 좁히지 말고 **읽기 쉬운 거래 카드/행 요약**으로 전환하거나 명확한 가로 스크롤을 제공. 이용일시·가맹점·금액·여행·상세 액션을 모두 접근 가능하게 유지.
- 터치 타깃 약 44×44px 이상, 키보드 focus-visible, 확대 200%에서도 기능 손실 없이 사용.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--33-접근성"></a>
##### 3.3 접근성

- 월 선택은 button, 선택 상태 aria-pressed 또는 tab 패턴의 올바른 의미론 적용. 탭 순서·Enter/Space 지원.
- 테이블은 th/scope 사용, 날짜별 소제목은 제목 구조 또는 의미 있는 그룹 구분.
- 상태는 색상만으로 전달하지 않는다. 대비는 일반 텍스트 WCAG AA 4.5:1, 큰 텍스트 3:1을 목표.
- 로딩 상태 aria-live 적절히 적용, 과도한 알림 금지. 아이콘 단독 버튼에는 접근 가능한 이름 제공.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--4-웹-전체-디자인-시스템"></a>
#### 4. 웹 전체 디자인 시스템

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--41-테마-정책-2026-10-26-13으로-수동-전환-승인"></a>
##### 4.1 테마 정책 (2026-10-26 §13으로 수동 전환 승인)

- 기본 라이트 = A안, 다크 = B안.
- **초기값은 시스템 테마 자동 연동**: 선택을 저장한 적 없으면 CSS @media (prefers-color-scheme: dark)로 시스템 변경을 즉시 반영. 명시적인 사용자 선택 이후에는 §13의 수동 테마 설정을 우선한다.
- **2026-10-26 사용자 승인 변경:** 우상단 해/초승달 버튼 1개를 허용하며 브라우저 localStorage의 비민감 키에 마지막 명시 선택(light/dark)만 저장한다. 쿠키/DB/API 저장 기능은 금지한다. 상세는 §13.
- 시스템 설정이 확인되지 않거나 미지원이면 라이트를 안전한 기본값으로 사용.
- 첫 화면에서 밝은 테마가 번쩍 나타났다 다크로 바뀌는 현상(FOUC) 방지: 가능한 CSS 초기 렌더 단계에서 시스템 media query 적용.
- 모든 실제 사용자 페이지와 하위 메뉴, 모달, 드롭다운, 폼, 테이블, 알림, 스켈레톤, hover/focus 상태에 동일한 의미론적 토큰 적용. 인라인 hardcoded 색상 최소화.
- 테마는 **시각 표현만** 바꾼다. 금융·여행·분류·접근 권한 로직과 무관.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--42-권장-디자인-토큰-초기값-실제-ui-검증-후-조정"></a>
##### 4.2 권장 디자인 토큰 (초기값, 실제 UI 검증 후 조정)

아래는 목표 팔레트. 기존 UI의 의미 있는 브랜드 요소가 있다면 유지 가능하나 임의의 페이지별 팔레트는 금지.

| 의미 | 라이트 A | 다크 B |
| --- | --- | --- |
| page background | #F8FAFC | #0F172A |
| surface | #FFFFFF | #1E293B |
| secondary surface | #F1F5F9 | #334155 |
| primary text | #0F172A | #F8FAFC |
| secondary text | #475569 | #CBD5E1 |
| subtle text | #64748B | #94A3B8 |
| border | #E2E8F0 | #334155 |
| focus/accent | 접근성 검증된 단일 브랜드 색 | 다크 대비에 맞춘 대응색 |
| success/warning/danger | 각 테마 대비 검증된 의미 색 | 각 테마 대비 검증된 의미 색 |

CSS 변수 예시: --color-bg, --color-surface, --color-surface-muted, --color-text, --color-text-muted, --color-border, --color-accent, --color-focus, --color-danger, --color-warning, --color-success. 토큰 이름은 기존 스타일 구조에 맞추되 **색상값 중복 선언을 억제**한다.

- 폰트: 기존 시스템 한글 가독성 우선. 웹폰트 신규 외부 의존은 기본 범위 제외.
- 간격: 4/8/12/16/24/32px의 일관된 spacing scale.
- 모서리: 필드·버튼·카드의 radius 일관화. 과도한 그림자/중첩 카드 배제.
- 테이블: 숫자 우측, 텍스트 좌측, 행 높이/구분선/hover/focus 통일, 긴 가맹점명은 접근 가능한 전체값 제공.
- 버튼: primary/secondary/danger, disabled/loading/focus 상태 통일. 위험 작업은 색상만으로 구별하지 않는다.
- 상태 배지: 기록 완료/확인 필요/미배정/취소·환불/충돌 등 기존 도메인 의미를 훼손하지 않는 단일 스타일.
- 페이지 헤더/필터/빈 상태/에러/모달/상세 패널은 재사용 가능한 스타일/마크업 패턴으로 통일.
- JS로 전체 DOM에 임의 테마 클래스 토글하는 방식보다 시스템 CSS 미디어 쿼리 우선.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--43-하위-페이지-ui-감사-기준"></a>
##### 4.3 하위 페이지 UI 감사 기준

실제 내비게이션에서 도달 가능한 페이지를 **전수 열거**하고 아래 항목으로 표를 만든다.

| 필드 | 기록 |
| --- | --- |
| URL/메뉴/렌더링 파일 | 실제 코드 근거 |
| 운영 노출 여부 | 운영/합성 전용/미사용/불명 |
| 공통 레이아웃 사용 여부 | 예/아니오 |
| 하드코딩된 색·인라인 CSS | 경로/예시 |
| 제목/여백/내비게이션 일관성 | PASS/ISSUE |
| 표/필터/폼/상태 배지 일관성 | PASS/ISSUE |
| 모바일/키보드/대비 | PASS/ISSUE/NOT_TESTED |
| 라이트·다크 | PASS/ISSUE/NOT_TESTED |
| 기능 리스크 | 금융 write, CSRF, 권한, 대량 DOM 등 |
| 개선 우선순위 | P0(사용 불가·오인) / P1(빈번한 하위 페이지) / P2(저빈도) |

후보 영역: 카드 업로드/검토, 카드 전체 내역, 장부, OTA 결제 검토, 항공 탑승자, Google 조회, 여행/참가자·수입 관련 페이지, 관리자 하위 화면. **실제 존재·운영 여부 확인 후** 목록 확정.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--44-리디자인-변경-범위-통제"></a>
##### 4.4 리디자인 변경 범위 통제

- 먼저 공통 디자인 토큰/컴포넌트와 카드 전체 내역에 적용.
- 기존 하위 페이지는 감사표 우선순위에 따라 **별도 작은 PR**로 순차 개선. 이 명세는 전면 코드 rewrite 허가가 아니다.
- 화면 개편 시 기존 입력 필드, 링크, 사용자 결정을 저장하는 이벤트, 에러 안내, CSRF, 리비전 충돌 처리, 복사/내보내기 계약을 유지.
- 비활성·합성 페이지를 실제 운영 UI로 착각해 배포하지 않는다.
- 사용자 승인 없이 회계 상태/거래 수/장부 반영 상태/OTA 정확 연결 판정을 변경하지 않는다.

##### 4.5 사이드메뉴 다크모드·항공권 메뉴 소실 원인 및 수정 계약 (2026-10-25, P0)

> 사용자가 관찰한 증상: ① 사이드메뉴가 시스템 다크모드에서도 밝게 보임 ② **항공권 참가자 연결** 화면 진입 시 사이드메뉴가 사라짐. 기준: 2026-10-25 GitHub `main` `d4c5934de07543e1c27232dbd53b297f2d8fa387`의 **코드 확인**. 실제 운영 브라우저 computed style, 수정 후 UI/운영 배포는 **NOT_TESTED / NOT_IMPLEMENTED**. 아래 서로 다른 두 원인을 함께 해결한다.

**원인 A: 공통 사이드메뉴 다크 CSS 변수의 적용 대상 누락 (SOURCE_CONFIRMED)**

- `webapp/site_shell.py:STYLE`은 `--shell-bg`, `--shell-paper`, `--shell-ink`, `--shell-muted`, `--shell-selected` 등의 라이트/다크 색상 변수를 `body.site-standalone, body:has(.site-topbar)` 선택자 **안에서만** 정의한다. `#nav`, `#nav .nv`, `#nav .work-menu`, `#nav .site-links`, 검색 필드 등은 `var(--shell-*, 라이트_기본값)`을 사용한다.
- `webapp/ledger_design.py:render()`는 기본 `<body>`의 기존 `#nav`·`#btn-menu`를 만든다. `site_shell.wrap_document()`는 `#btn-menu`가 이미 있으면 `.site-topbar`를 추가하지 않는다. 즉 이 네이티브 장부 페이지의 `body`는 위 둘 중 어느 조건도 충족하지 않아 **`--shell-*`가 미정의인 채 라이트 fallback이 적용되는 경로**가 존재한다. `#nav`의 ID 우선순위가 `ledger_design.py`의 `.nav` 다크 스타일을 덮는 것도 확인했다.
- `ledger_design.py` 내부에는 `prefers-color-scheme: dark`에서 `:root` 토큰을 두 번 정의한 중복 블록도 있다. 중복은 유지보수 위험이지만 단독으로 위 증상의 확정 원인은 아니다.

**수정 티켓 SIDEBAR-DARK-01**

1. 공통 셸의 `--shell-*` 토큰을 네이티브 장부/standalone 문서 **양쪽의 `#nav`에 항상 적용**한다. 우선 권장안: `site_shell.STYLE`이 포함된 문서의 `:root`에 라이트 값을 선언하고 `@media (prefers-color-scheme: dark)`의 `:root`에 다크 값을 선언한다. `body:has(.site-topbar)` 여부에 의존한 색상 게이트를 제거한다. 동일한 안전성의 대안이면 실제 computed style로 증명할 것.
2. `#nav` 배경/텍스트/보조 설명/경계선/선택 메뉴/hover/focus/검색 입력/업무 메뉴/보관 항목/모바일 오버레이가 시스템 테마를 따른다. 라이트→다크 실시간 전환, 수동 토글·cookie/localStorage 저장 없음.
3. 기존 `ledger_design.STYLE`의 중복된 다크 `:root` 블록과 셸 전용 변수 간 우선순위를 표적 확인하고, 기존 레이아웃·금융 기능·여행 선택·권한·스크롤 복원·모바일 메뉴 동작을 보존한다. 큰 규모의 CSS 재작성은 금지한다.

**원인 B: 항공권 문서에 `<body>`가 없어 공통 메뉴 삽입이 건너뛰어짐 (SOURCE_CONFIRMED)**

- `webapp/flight_passenger_page.py:_page()`는 `<!doctype html><html lang='ko'>` 다음 메타·스타일·`<main>`·스크립트를 직접 작성하며 **명시적인 `<head>…</head><body>…</body>`가 없다.**
- `webapp/ledger_board.py:Handler._send()`는 로그인한 사용자의 HTML에 `site_shell.wrap_document()`를 적용한다. 하지만 `webapp/site_shell.py:wrap_document()`는 시작 `<body>`와 끝 `</body>`를 모두 찾지 못하면 **원본 HTML을 반환**한다. 따라서 이 항공권 화면에는 `_nav_html()`의 메뉴가 삽입되지 않는 경로가 확정됐다.
- 기존 항공권 화면 디자인·브라우저 테스트는 `_page()` 원문을 직접 사용한다. **실제 Handler → 공통 셸 통합 결과를 검사하지 않아 메뉴 누락을 잡지 못했다.**

**수정 티켓 FLIGHT-SHELL-01**

1. `_page()`에서 유효한 문서 구조 `<html><head>…</head><body>…</body></html>`를 출력한다. 기존 CSRF 값의 `\\u003c` 이스케이프, 후보 GET/내부 연결 POST, 플래그·인증 경계를 변경하지 않는다.
2. 실제 `Handler._send()`를 통과한 **owner `/flight-passengers` HTML**에서 공통 `#nav`, `#site-content`, 모바일 메뉴 버튼, `<main>`이 각각 중복 없이 1개 나타나야 한다. `_page()` 단독 테스트만으로 수락하지 않는다.
3. 항공권 화면의 전역 CSS `main`, `form`, `button`, `article`, `label`은 화면 전용 루트(예: `#flight-passenger-page`) 아래로 한정해 삽입된 `#nav` 검색폼·업무 버튼을 오염시키지 않는다. 신규 사이드바를 따로 만들거나 모든 페이지 레이아웃을 교체하지 않는다.
4. 데스크톱(메뉴 232px 고정)과 모바일(≤759px 드로어)에 동일한 사이드메뉴를 표시하며, 화면 이동·선택 상태, 열기/닫기·배경 마스크·Escape·포커스 복귀·키보드·스크롤 유지가 정상이어야 한다.
5. 기존 `WEBLEDGER_FLIGHT_PASSENGER_MATCHING` 비활성 시 404, 비소유자 403, owner만 조회·저장, 기존 CSRF·정본 권위·취소/충돌 차단 보호를 변경하지 않는다.

> **2026-10-26 최신 항공권 업무 전환:** 아래 §4.6의 '항공권 참가자 연결' UI 정리는 10월 25일 당시의 구현 이력이다. 사용자 최신 승인으로 주 메뉴와 새 기본 화면은 **[항공권 예약 확인](ui.md#src-docs-flight-booking-verification-spec-20261026-md)**이며 탑승객 이름 한 필드로 시작해 항공권·연결된 카드/예약일 카드 후보를 읽기 전용으로 확인한다. 과거 참가자 연결 기능은 보조 패널로 보존한다. 새 전용 명세가 명칭/기본 검색 UX 충돌 시 우선한다. 이 새 설계는 아직 구현 전이다.

##### 4.6 항공권 참가자 연결 화면 UI/UX·문구 정리 (P1)

**UI 구성 원칙**

1. 공통 제목/보조 설명 → 조회 조건 카드 → 현재 상태 및 검색 결과 요약 → 탑승자별 후보 카드의 **일관된 수직 위계**. 후보가 하나라고 사용자 확인 없이 연결하지 않는다.
2. 데스크톱에는 두 입력과 검색 버튼을 읽기 쉬운 그룹으로 정렬하고, 375/390/759px에서는 좁은 화면 맞춤 한 열 배치. `label`은 입력과 대응시키되 현재 `inline-flex` 중첩으로 압축하지 않는다. 긴 영문 이름/예약번호는 절단하더라도 전체값 접근 가능, 가로 overflow 방지.
3. 저장/조회 성공, 조회 결과 0건, 후보 없음, 동명이인, 이전 연결 무효(stale), 취소, 충돌, 409/422/503 오류는 **각각 다른 상태**로 표시한다. 반복된 전역 경고를 해당 카드 경고로 통합하되 놓치지 않게 한다.
4. 시스템 light/dark에서 라디오/카드/폼/포커스/경고/버튼/disable 상태의 명도와 대비를 확인한다. 키보드만으로 검색→라디오→연결 가능, focus 표시·label·role=status·aria-live 유지.
5. 실제 예약번호·여행 ID·실명은 owner만 접근, 합성 fixture 사용. API 응답 구조, CSRF/후보 정확성, 권한, 정본/항공 취소 검증, 쓰기 범위를 UX라는 이유로 확장하지 않는다.

| FLIGHT-07 | 고객 원본 없는 합성 fixture만 사용, 테스트 명령·출력·diff·브라우저 측정 근거를 PR에 첨부. 브라우저 미실행이면 `NOT_TESTED`, 운영 미배포면 `NOT_DEPLOYED` 유지. |

**현재 상태:** `SOURCE_CAUSE_VERIFIED / SPEC_ONLY / NOT_IMPLEMENTED / BROWSER_NOT_TESTED / NOT_DEPLOYED`. 명세 작성만으로 코드/운영 화면이 고쳐졌다고 표시하지 않는다.

#### 5. 검증 계약: 최소 합성 테스트와 브라우저 확인

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--51-카드-전체-내역-기능-테스트"></a>
##### 5.1 카드 전체 내역 기능 테스트

1. 초기 진입: 2026년, 월 12개, 모두 접힘, 선택 없음.
2. 월 그리드: 4×3 데스크톱, 모바일 2~3열, 선택/재선택/다른 월 선택 상태.
3. 연도 변경: 2025 등 데이터가 있는 연도로 전환, 선택 월 해제, 2026으로 복귀.
4. 월 건수: 장부 기록 완료/미기록/제외/취소/환불/충돌 원행 모두 포함. 재업로드 중복 출처만 중복 계수 금지. 서로 다른 거래 ID는 보존.
5. 정렬: 날짜/시간 오름차순, 시간 없음은 같은 날짜 맨 뒤, 동률 안정 ID, 화살표 없음.
6. 표시: 원본 금액 부호·통화, 시간 없음, 가맹점 미상, 미배정, 사용자 확정 여행 vs 자동 추론 여행, 취소·환불.
7. 날짜별 소제목과 0건 월 빈 상태. 빈 날짜에 가짜 누락 경고 없음.
8. 행 클릭: 정확한 기존 거래 상세로 이동, 여행 변경/재검토 경로 정상; 조회만으로 거래/장부/Google 변경 없음.
9. 권한: 비인증/권한 없는 사용자 차단, 저장 조치는 기존 CSRF·revision 보호.
10. 페이지네이션: 100건 초과 월 전체를 끝까지 조회, 월 전체 건수 일치, 중복/누락 없이 안정 정렬.
11. 날짜 없는 원행: 별도 확인 필요 섹션에 노출, 날짜를 날조하지 않음.
12. 악의적 가맹점 문자열/URL 파라미터 XSS 방어, cursor·year·month 유효성 검증.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--52-디자인접근성-테스트"></a>
##### 5.2 디자인/접근성 테스트

1. 시스템 light/dark 각각에서 공통 레이아웃·표·폼·모달·배지 대비와 가독성 확인.
2. 사용자 선택이 없으면 시스템 테마를 즉시 따른다. 수동 선택 뒤에는 우상단 단일 버튼, 현재 테마·아이콘, 저장된 선택 및 페이지 간 유지 상태가 일치하는지 §13 기준으로 검증한다.
3. 모바일 폭(예: 375px), 태블릿, 데스크톱에서 가로 넘침/클릭 불가 요소 없음.
4. 키보드만으로 월 타일 선택, 상세 링크 접근, focus 표시 확인.
5. 공통 CSS 변경으로 기존 핵심 페이지 기능이 깨지지 않는지 **영향받은 페이지의 표적 검사**.
6. 감사표의 NOT_TESTED를 PASS로 표기하지 않는다. 브라우저 테스트를 실제로 실행하지 못했다면 미실행이라고 보고.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--53-테스트운영-안전"></a>
##### 5.3 테스트·운영 안전

- 합성 fixture만 사용. 실제 고객 원문, 예약번호, 카드 끝자리, 토큰, 개인정보를 Git·로그·모델에 제출하지 않는다.
- 데이터베이스 조회·테스트는 합성/격리된 환경에서만. 운영 DB 접근·마이그레이션·대량 재수집·배포·Google API 쓰기 금지.
- 변경 범위에 해당하는 표적 테스트만 실행. 기존 성공한 무관한 전체 테스트를 반복하지 않는다.
- 테스트 실패는 원인/영향/수정 후 결과를 보고. 테스트를 실행하지 않았는데 통과라고 주장하지 않는다.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--6-구현-단위와-pr-순서"></a>
#### 6. 구현 단위와 PR 순서

**PR-0: UI 감사/코드 맵 (문서 전용)**
- 실제 메뉴/URL/페이지/CSS/JS/권한/데이터 출처 감사표.
- 카드 원행 조회 계약, 거래 ID·날짜·시간·통화·여행 출처 확정.
- 미확정 기술 위험/선택지가 있으면 근거와 권장안 제시.
- 문서만 변경하면 테스트/배포 불필요.

**PR-1: 공통 테마 토큰·레이아웃 최소 구축**
- 시스템 prefers-color-scheme 기본 대응과 §13에서 승인한 해/초승달 단일 수동 토글 구현.
- 기존 공통 컴포넌트 우선 재사용. 영향받는 실제 페이지에 표적 검증.
- 페이지 기능/금융 write path 무변경.

**PR-2: 카드 전체 내역**
- owner 메뉴·연도 선택·월 그리드·원행 조회·월 상세·날짜 그룹·상세 링크.
- 합성 기능 테스트 + 실제 가능한 브라우저 확인.
- 금융/Google/OTA 로직 변경 금지.

**PR-3+: 하위 페이지별 디자인 개선**
- UI 감사 P0/P1 순서로 작은 PR. 페이지별 기존 업무 계약 회귀 방지.
- UI가 바뀌었다는 이유로 회계/예약 알고리즘 변경 금지.

**별도 차기 명세: 카드사 원본 대조 누락 탐지**
- 이번 PR들에 포함 금지. “저장된 거래 목록”만으로 카드사 원본 전체와 일치한다고 주장하지 않는다.

PR-1과 PR-2의 순서는 기술적 의존성이 확인되면 유지하고, PR-0에서 이미 확실한 부분은 불필요한 중복 조사를 줄인다. 한 PR에서 전체 웹을 동시에 수정하지 않는다.

#### 7. 에이전트의 자율 결정 범위와 중단 조건

**자율 결정 가능:** 기존 스타일에 맞춘 컴포넌트 이름, 충돌 없는 라우트, 안전한 읽기 전용 조회 함수, 월 상세 페이징 기술, 반응형 구현, 표적 테스트 구성.

**사용자/상위 승인 없이 변경 불가:** 2026 기본 연도, 4×3 월 그리드, 월 단일 선택/접기, 4개 필수 필드, 시간 없는 거래 처리, 전체 원행 범위, 후속조치 의미, 시스템 기본값 + §13 사용자 승인 수동 토글, Google 직접 쓰기 금지, 금융 불변조건.

**중단 및 보고:** 기존 저장소에 원행 이용일/시간 또는 거래 ID가 없어서 데이터 변조 없이 구현 불가능할 때; 보존 정책과 전체 원행 조회가 충돌할 때; 운영 DB 스키마 변경이 필수일 때; 기존 상세 링크가 원행을 정확히 찾지 못할 때; 기존 접근제어를 우회해야만 화면을 만들 수 있을 때. 조용히 데이터를 날조하거나 범위를 줄이지 않는다.

#### 11. 기존 문서와 통합 규칙

이 파일은 **카드 전체 내역·전체 웹 UI 디자인**의 유일한 활성 세부 명세다. 다른 위치에 이 요구를 복제하지 않는다.

- docs/target-workflow-google-authority.md: Google 최종 정본/직접 쓰기 금지. 복제하지 않고 참조.

- docs/history/, docs/archive/: 이력. 문서 정리라는 이유로 삭제/재해석하지 않는다.

**충돌 해결:** 금융/여행 권위는 V3 START HERE 및 해당 정본 우선. UI 기능과 테마 및 에이전트 실행은 이 파일 우선. 최신 운영 사실은 CURRENT HANDOFF/operations와 실제 배포 증거 우선. 새로운 사용자 결정이 생기면 이 파일을 갱신하고 전역 진입점에는 링크·요약만 유지한다.

#### 12. 지출 정리 화면의 '전체 지출 자동 정리' 버튼 개선 계약 (2026-10-25 결정)

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--121-배경현행-동작-코드-확인-사실-배포-상태와-구분"></a>
##### 12.1 배경·현행 동작 (코드 확인 사실, 배포 상태와 구분)

현재 \`webapp/card_flow.py\`의 \`render_expense_cleanup()\`은 일반 '지출 정리' 화면에 **'전체 지출 자동 정리'** 버튼(\`#cleanup-reclassify\`)을 노출한다. \`CLEANUP_SCRIPT\`는 클릭 시 owner 권한 및 \`X-CSRF-Token\` 검증을 받는 \`POST /api/imports/reclassify-pending\`을 호출한다. 서버의 \`reclassify_cleanup(board)\`은 단순한 조회/화면 정렬이 **아니다**.

- 미분류·미배정 카드 구매 거래 중 안전 필터를 만족하는 대상을 분류하고, 필요 시 OTA 예약 근거의 최신 스냅샷을 확인한다.
- 배치별 \`_auto_record_locked(...)\`를 호출하여 보호 검사를 통과한 거래를 내부 장부에 자동 기록할 수 있다.
- \`assign_existing_local_expenses()\`는 이미 장부에 존재하는 일부 미배정 현지 지출을 검증된 여행에 자동 귀속시킬 수 있다.
- 결과로 \`processed\`, \`recorded\`, \`assigned_existing\`, \`failures\`, \`breakdown\`을 반환한다. 현 UI는 일부 결과만 보여 주거나 성공 시 새로고침한다.
- 현행 코드에는 일부 수동 결정·보류·원본 충돌·파싱 오류·중복·취소 보호 필터가 있다. **이것이 모든 실거래에서 변경이 없다는 보증은 아니다.**

따라서 버튼 이름과 위치가 실제 쓰기 효과를 과소표현한다. 현행 구현 존재가 신규 UI에서 계속 노출해야 한다는 근거는 아니다. 운영 반영 여부는 \`docs/COST_V3_CURRENT_HANDOFF.md\`와 실제 배포 SHA로 별도 확인한다.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--122-제품-결정-및-범위"></a>
##### 12.2 제품 결정 및 범위

**확정 정책:** 일반 '지출 정리' 화면에는 '전체 지출 자동 정리' 버튼과 연계된 일괄 실행 안내를 **노출하지 않는다**. 일반 사용자의 주 흐름은 미정리 내역·보호 사유 확인, 건별 상세 검토, 기존 여행 변경/재검토로 유지한다. 단순 화면 조회(GET)는 어떠한 재분류·장부 기장·여행 변경도 유발하지 않아야 한다.

**유지 정책:** 이미 존재하는 카드 재분류/기장 기능을 즉시 삭제하거나 업무 규칙을 약화하지 않는다. 기존 정상 카드 수집 시점 자동화와 명시적 개별 수정 흐름은 그대로 유지한다. 일괄 재처리가 정말 필요한 경우에 한해 **별도 owner 전용 유지보수 경로**에서 실행하도록 분리한다.

**금지:** 버튼 숨김만으로 서버 POST를 안전한 관리 기능이라고 선언하지 않는다. 숨겨진 POST가 그대로 활성화되어 있다면, 기존 인증된 호출에 의해 장부/여행 배정이 계속 변경될 수 있음을 명시하고 아래 단계의 권한·안전 게이트를 구현한다. 다른 기존 자동 처리 기능을 무심코 비활성화해서는 안 된다.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--123-단계별-구현-티켓"></a>
##### 12.3 단계별 구현 티켓

**EXPENSE-BULK-AUDIT-01 (읽기 전용, 선행 필수)**

1. 실사용 라우트·버튼·스크립트·서버 핸들러와 모든 직접/간접 호출처를 검색한다. \`reclassify_pending()\` 및 카드 업로드 후 자동 분류와 이번 일괄 POST의 역할을 구분한다.
2. \`reclassify_cleanup()\`, \`CardFlow._classify()\`, \`_auto_record_locked()\`, \`assign_existing_local_expenses()\`의 변경 가능한 테이블·감사 로그·트랜잭션 경계·실패/부분 성공을 코드와 합성 테스트로 조사한다.
3. 현행 owner 인증, CSRF, 중복 요청, 재시도, 환불·취소 보호, 수동 여행 배정 보호, 비정상 응답의 범위를 정리한다.
4. 배포된 운영 동작은 운영 증거가 없으면 미검증으로 표시한다. 조사 단계에 실제 DB 읽기/쓰기, 운영 API 호출, 배포는 없다.

**EXPENSE-BULK-UI-01 (일반 화면에서 제거)**

1. \`render_expense_cleanup()\`의 버튼과 \`CLEANUP_SCRIPT\` 내 버튼 전용 클릭 처리 및 오해를 부르는 안내 문구를 일반 화면에서 제거한다. 남은 건별 처리와 다른 JS 핸들러는 유지한다.
2. '지출 정리' 건수, 사유별 분류, 상세 확인, 수동 여행 배정, 카드 원행 검색, 페이지네이션을 훼손하지 않는다.
3. 단순히 프런트만 숨겼다면 **일괄 POST는 여전히 호출 가능**하다는 점을 보고하고, 다음 관리 경로 보호가 완료되기 전에는 신규 링크나 우회 호출을 추가하지 않는다.
4. 사용자 경험 개선과 서버 측 행위 제한이 함께 계획·검증되지 않은 채 '안전하게 제거 완료'라고 표현하지 않는다.

**EXPENSE-BULK-MAINT-01 (관리자 유지보수 경로, 별도 변경 PR)**

1. owner만 접근 가능한 명확히 구분된 관리 화면/경로를 만든다. 기본 일반 '지출 정리' 내비게이션에 노출하지 않는다. 현재 서비스가 owner 단일 역할인지 먼저 조사하고, 허술한 '관리자' 개념을 새로 창작하지 않는다.
2. **미리보기(dry-run)가 반드시 읽기 전용**이 되게 만든다. 대상 카드 수, 장부 반영 예정 건수, 기존 장부 여행 재배정 예정 건수, 보류·건너뜀·오류 예상 건수, 영향받는 대상 ID/사유(민감정보 최소화)를 표시한다. 실제 처리 함수 호출 후 rollback하는 방식은 dry-run으로 인정하지 않는다. 외부 OTA API/워커와의 접촉 여부도 표시하고, 읽기 전용 보장이 불가능하면 실행 차단/HOLD한다.
3. 사용자에게 쓰기 범위를 명시적으로 확인받는다. '분류만'과 '장부 기록/여행 배정 포함'을 혼동하지 않도록 효과를 구분한다. 서버는 owner+CSRF+동의된 작업 범위+유효한 preview 토큰/버전(또는 동등한 최신성 검증)을 확인한다. 대상이 미리보기 이후 변경되면 실행을 거절하고 재미리보기를 요구한다.
4. 기존 \`POST /api/imports/reclassify-pending\`을 포함한 **모든 쓰기 진입점**을 조사해, 의도되지 않은 직접 호출/중복 클릭/재전송에 동일한 관리 게이트를 적용한다. 기존 호출 호환성이 깨지면 호출처와 마이그레이션을 함께 검증한다. 안전한 전환이 되기 전에는 새 관리 UI를 활성화하지 않는다.
5. 반복 요청으로 신규 장부 행·이중 비용·수동 배정 덮어쓰기가 생기지 않게 서버 측 멱등성·revision/기존 기장 보호·동시 실행 제어를 유지 또는 강화한다. 실패 시 부분 성공 건과 미처리 건을 구별하며, 임의로 이미 반영한 변경을 되돌리지 않는다.
6. 처리 시점의 작업 ID, 실행자, 시각, 변경 대상 ID, 변경 종류, 성공/실패 건수·사유를 비밀정보 없이 감사 가능하게 기록한다. 원문/개인정보/인증정보는 로그에 포함하지 않는다. '예상'과 '실제'를 구분해 보여준다.
7. 과거 원본, 결제 부호/통화, 중복/취소/환불, 충돌·보류, 이미 기장한 건, 사용자 수동 여행 확정, 실제 검증된 OTA 근거, Google 최종 정본/직접 쓰기 금지 정책은 현행 상위 계약을 그대로 준수한다.
8. 구현 후에만 관리 작업을 실행 가능하게 한다. 실제 운영 자료로 시험하지 않고 합성 fixture로 검증한다. 운영 전환/배포 및 운영 DB 재처리는 별도 사용자 승인 대상이다.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--125-시행-순서변경-권한"></a>
##### 12.5 시행 순서·변경 권한

- 순서: **EXPENSE-BULK-AUDIT-01 → EXPENSE-BULK-UI-01 → EXPENSE-BULK-MAINT-01**. AUDIT에서 확인한 현재 코드와 보호 규칙에 따라 파일을 최소화한다. 큰 자동화 함수의 불필요한 재작성은 금지.
- UI 제거와 유지보수 신규 기능은 각각 작은 PR로 나누며, 기존 운영 버전과 일시적으로 공존하는 엔드포인트의 위험을 PR 설명에 명시한다. 두 PR 사이에 오래 노출되는 쓰기 경계가 확인되면 서버 접근 제한을 UI 제거와 함께 먼저 구현하고 검증한다.
- 금융·인증·운영·Google 변경이 필요하거나 dry-run의 부작용 없는 구현이 불가능하면 **HOLD** 후 사용자 판단을 요청한다. UI 상 문제 제기가 곧 실제 DB 재처리 권한이 되지 않는다.
- 이 절은 **앞으로 구현할 제품 명세**이며, 작성만으로 버튼 제거·API 봉쇄·관리 화면 완성 또는 운영 반영을 주장하지 않는다.

#### 13. 우상단 해·초승달 단일 테마 선택 (2026-10-26 최신 확정)

> **최신 승인 우선:** 이전 §4.1, §4.5, §5 및 과거 검사·에이전트 계약에 적힌 '수동 테마 선택/저장 금지'는 **이 절이 대체**한다. 초기 시스템 자동 모드는 유지하되 사용자의 명시적 라이트/다크 선택을 허용한다. 현재 `main`에는 이 토글이 없으므로 **SPEC_APPROVED / CODE_NOT_IMPLEMENTED / NOT_DEPLOYED**다.

<a id="src-docs-card-all-transactions-and-ui-design-system-spec-v1-md--131-동작표시범위-theme-toggle-01"></a>
##### 13.1 동작·표시·범위 (THEME-TOGGLE-01)

1. **우상단 공통 헤더의 버튼 1개:** 모든 로그인 업무 화면에서 우상단에 작은 아이콘만 있는 테마 전환 버튼을 표시한다. 페이지별 중복 버튼, 별도 설정 패널, 드롭다운, 라벨이 보이는 토글 2개, 3단 선택 UI는 만들지 않는다. **버튼에는 해 또는 초승달 SVG 아이콘만 표시한다. 버튼 아래/옆에 '라이트 모드', '다크 모드', '클릭하면 전환' 등의 설명·캡션·상태 문구는 표시하지 않는다. 접근성 aria-label은 유지한다.** 공통 셸(`webapp/site_shell.py`)과 기본 장부(`webapp/ledger_design.py`)가 서로 다른 메뉴를 만드는 구조를 분석해 동일한 DOM 컨트롤과 스타일을 사용한다.
2. **현재 라이트 모드에는 해(`sun`) 아이콘**, 클릭하면 즉시 다크가 되며 **초승달(`moon`) 아이콘**으로 교체한다. 다크 상태에서 클릭하면 라이트·해로 돌아온다. 아이콘은 **현재 상태**를 나타내고 버튼의 접근 가능한 이름은 **다음 동작**을 나타낸다: 라이트에서 `aria-label="다크모드로 전환"`, 다크에서 `aria-label="라이트모드로 전환"`. 아이콘 자체는 `aria-hidden="true"`; 기존 공통 `ui_icons` 우선.
3. **최초 방문/미선택:** 저장된 설정이 없으면 `prefers-color-scheme`으로 현재 시스템 모드를 따른다. 사용자가 버튼을 클릭한 시점부터 `light` 또는 `dark`를 **localStorage의 단일 키**에 저장한다. 이후 새로고침·다른 내부 화면·같은 origin의 새 탭에서도 유지한다. 시스템 테마가 바뀌더라도 명시적 선택이 우선한다. 서버 DB·cookie·Google·로그 전송·계정별 API 저장은 없다.
4. **예외/초기화:** 저장값이 `light`/`dark`가 아니거나 삭제됐으면 시스템 기본값을 따른다. localStorage가 차단되거나 오류가 나도 JS 오류로 앱 전체를 망가뜨리지 않고 **현 탭의 모드 전환은 동작**해야 한다. 설정 초기화 버튼은 요청 범위가 아니므로 만들지 않는다.
5. **FOUC 방지·CSS 정합:** 초기 화면 표시 전에 공통 스크립트에서 명시적 모드를 적용하고 `html[data-theme="light|dark"]` 또는 이에 준하는 단일 루트 상태로 토큰을 제어한다. 기존 `@media(prefers-color-scheme:dark)` 변수보다 명시 선택이 우선해야 하므로, **시스템 다크 + 수동 라이트**, **시스템 라이트 + 수동 다크** 모두 body·`#nav`·폼·카드의 실제 계산 색상에 반영해야 한다. `--shell-*`, `--bg`, `--paper`, `--ink`의 기존 토큰을 재사용하고 페이지마다 하드코딩된 HEX를 늘리지 않는다.
6. **무새로고침/무부작용:** 클릭 후 테마만 즉시 바뀌고 여행/거래 선택, 입력 중 텍스트, 스크롤, 열린 사이드메뉴·모달, 항공권 후보 상태, 미저장 폼 값, API 요청·인증·CSRF는 변하지 않는다. 금융·Google·예약·운영 DB에 쓰지 않는다.
7. **모바일 포함:** 375/390/759/760/1280px, 200% 확대에서 우상단 위치를 유지하고 햄버거 메뉴/검색·작업 버튼과 겹치지 않는다. 터치 타깃 최소 44×44px, 아이콘 약 20~24px, Tab·Enter·Space 및 `:focus-visible` 지원. 배경·글씨·보조글씨·경고/포커스의 대비를 검사한다.

#### 14. 장부 화면 스크롤 시 전체 화면 이탈·하단 빈 영역 방지 (SCROLL-VIEWPORT-01, 2026-10-26)

> 사용자 제보 화면은 `0630_오제`의 거래 목록과 사이드메뉴가 일정 높이에서 함께 끝나고, 그 아래에 넓은 다크 배경이 보이는 상태다. 이는 **실제 브라우저 증상**이지만 캡처 한 장만으로 body 스크롤, 뷰포트 리사이즈, 확대, 특정 CSS 충돌 중 단일 원인은 확정되지 않는다. 이 PR은 우선 장부의 바깥 body 스크롤 연쇄를 차단하는 최소 코드 조치이며 실사용 브라우저 수락은 별도로 필요하다.

**코드 관측과 최소 변경**

- `webapp/ledger_design.py`: `.app`은 `height:100dvh`, `.nav`와 `.main`은 `overflow:auto`로 독립 스크롤을 선언했지만 바깥 `body` 스크롤은 명시적으로 차단하지 않았다. 브라우저에 따라 바깥 문서가 스크롤되면 메뉴와 콘텐츠가 함께 위로 이동할 수 있다.
- 장부 루트 `body:has(>.app)`에만 `overflow:hidden`을 적용하고, `.app`은 `100dvh`·`min-height:0`·`overflow:hidden`을 유지한다. 이 CSS는 **별도 standalone 페이지의 body를 일괄 봉쇄하지 않는다**.
- 세로 이동이 필요한 거래 내역은 `.main`, 긴 여행 목록은 `#nav`에만 스크롤이 생겨야 한다. 모바일 햄버거/내비게이션 drawer와 카드 상세 패널은 독립 스크롤을 유지한다. sticky 헤더·키보드/휠·터치 스크롤의 정상 사용을 보호한다.
- 만약 실제 사용자 환경에서 하단 빈 영역이 재현된다면 `document.scrollingElement.scrollTop`, `documentElement/body.scrollHeight`, `window.innerHeight`, `.app/#main/#nav`의 `getBoundingClientRect`, `visualViewport.height`를 함께 기록해 CSS 뷰포트 불일치나 상위 container 크기 문제를 분리한다. 고객정보는 수집하지 않는다.

<a id="src-docs-flight-booking-verification-spec-20261026-md--2-사용자-업무-흐름-단일-이름-검색부터-시작"></a>
#### 2. 사용자 업무 흐름 (단일 이름 검색부터 시작)

1. 좌측 메뉴명·페이지 타이틀을 **'항공권 예약 확인'**으로 일치시킨다. 기존 `/flight-passengers`는 북마크/기존 링크와 호환하여 새 `/flight-bookings`로 안전하게 이동시키거나, 사용자에게 보이는 이름만 변경해도 된다. 최종 정본 URL 하나를 선택하고 모든 내부 네비게이션/선택 표시/owner 인증 테스트를 갱신한다.
2. 첫 화면에는 **'탑승객 이름' 입력창 1개**와 **'예약 조회' 버튼 1개**만 필수 입력으로 둔다. 한글/영문 입력을 허용한다. 한글 이름은 *검증된 예약 정본의 한글·영문 성명 대응이 있는 경우에만* 영문 탑승자와 연결한다. 여권 영문명이나 로마자 변환을 임의 추정하지 않는다. 공백·대소문자·성/이름 순서 등 정규화는 근거가 충분한 경우에만. 이름 동명이인은 **모든 후보를 분리**하여 보여 주고 첫 번째 자동 선택 금지.
3. 검색 결과는 탑승객이 등장하는 **항공권 예약 단위 카드** 목록으로 묶는다. 한 사람의 왕복·여러 예약을 합치지 않고 예약번호/원본 출처/여정/예약 상태를 구분한다. 검색 결과에는 이름, 항공사/편명(원본에 있을 경우), 출발·도착(근거 있는 경우), 출발일·구간/예약번호(민감정보 접근 보호), 예약일/발권일/결제일(각각 실제 원본 의미 표시), 원본 최종 갱신/근거 출처, 취소·환불·충돌/동명이인 경고 등을 간결한 2단 카드로 제공한다. **확인된 필드만 표시**하며 항공권 확인 메일의 영문 이름만 존재한다면 '예약일 확인 불가'라고 표시한다.
4. 사용자가 결과 카드를 선택하면 **'항공권 예약 정보' → '연결된 카드 결제' → '미연결 카드 거래 후보'** 순서로 상세를 표시한다. 연결된 카드 거래가 검증된 결제/예약 관계를 통해 실제 식별된 경우에는 거래일/가맹점/승인금액/통화/승인번호/거래 유형/연결 출처/연결 상태와 관련 원본 이동 링크를 표시한다. 예약의 결제 증거가 없으면 '연결된 카드 결제 없음'을 구별한다. 과거 참가자 연결(수동) 상태는 상세의 보조 정보로만 유지한다.
5. **연결된 카드가 없는 경우:** 항공권의 명시·검증 예약일 또는 별도 예약일이 없을 때 승인된 `FIRST_RECEIVED` 기준일(같은 공급자·예약번호의 인증 메일 중 가장 이른 mailbox `internal_date`를 한국 날짜로 환산)에 해당하는 **모든 저장 카드 거래 원행**을 날짜 일치 후보 목록으로 제공한다. 최초 수신일 기준임을 표시하고 공급사의 원본 예약 생성일로 표현하지 않는다. 발권일·메일 발신자의 `Date`·결제일은 이 기준일로 대체하지 않는다. 가맹점이나 금액으로 사전 배제하지 않는다. 후보 행에는 승인일시·가맹점·원화 금액·외화 금액/통화·분류/기존 여행·취소·중복·기존 다른 예약 점유 상태·승인번호를 표시하며, 선택한 예약과의 거래 대조 후보일 뿐임을 명시한다.
6. **예약일/허용된 최초 수신일 기준 모두 불명확:** 전체 카드 원행을 무작위로 보여주지 않는다. 예약 날짜 근거를 확인할 수 없다는 안내와 별도 날짜 조회 기능(사용자가 지정한 날짜는 **필터**일 뿐 예약일이나 결제 연결의 확정이 아님을 밝힘)을 제공한다. 결제일·발권일·메일 발신자의 `Date`만 확인된 경우 이를 예약일 기준으로 둔갑시키지 않는다. 같은 날짜 후보 검색은 해당 증거의 날짜 종류를 정확히 표시한 **선택적 보조 탭**으로만 허용한다.
7. 연결된 카드가 일부만 있는 복수 결제·왕복/재발권 예약은 '연결된 카드'와 '추가 검토 후보'를 모두 보여 주되 **예약 전체가 완납/결제확정**이라고 단정하지 않는다. 환불·취소·재발행·동일 금액 복수 거래를 각각 구분한다.
8. 검색 및 펼치기는 **읽기 전용**이다. 실제 카드 연결/해제 기능은 기존 OTA 결제 검토의 owner·CSRF·근거 지문·revision·중복/점유/취소 보호 경로를 *검증해서 재사용하는 명시적 후속 작업*으로 분리한다. 이 화면의 새 GET에서 카드 연결·기장·원본 수정은 0건이어야 한다.

<a id="src-docs-flight-booking-verification-spec-20261026-md--3-기능-구현api-계약"></a>
#### 3. 기능 구현·API 계약

<a id="src-docs-flight-booking-verification-spec-20261026-md--flight-verify-data-01-데이터-출처와-관계-감사-선행-필수"></a>
##### FLIGHT-VERIFY-DATA-01: 데이터 출처와 관계 감사 (선행 필수)

- `passenger_index_for`의 항공권 인덱스에서 **booking_ref, surname/given_name, legs, source_digests, cancellation_status, conflict**의 실제 스키마를 확인하고, '예약일'의 신뢰 가능한 값과 의미가 존재하는지 확인한다.
- 연결 카드 판정에 필요한 기존 `ota_payment_review`의 저장된 **확정** 결제 링크, 예약/항공권 근거 및 카드 거래 ID의 실제 join 경로를 확인한다. 금액/날짜만 유사한 카드를 **연결됨**으로 오표시하지 않는다. OTA 예약 ID 중복·공급자 구분·원본 digest·추론과 수동 확정·반환/취소 관계를 함께 검사한다.
- `card_transactions.list_for_month`의 결제일·원행 조회 구조는 읽기 전용 재사용 가능. 필요한 경우 **같은 날짜 모든 거래**를 커서 페이지네이션하는 전용 함수 `list_for_day`로 분리한다. `per_page` 상한/총 건수/더보기 cursor 지원, `YYYY-MM-DD` ISO 값 엄격 검증. 같은 날짜가 1,000건이어도 앞부분만 '전체'라고 거짓 표시하지 않는다. 카드 원행 DB의 read-only 연결/권한을 유지한다.
- 검색 결과는 개인정보이므로 **owner 전용 + no-store**. 비로그인 401, viewer 403, 기능 비활성 404, 원본 동기화 stale는 별도 안내. 이름이나 예약번호·카드 원문을 로그/URL 분석 도구/브라우저 저장에 남기지 않는다. GET query 이름이 서버 액세스 로그에 노출될 수 있으면 POST 읽기 전용 API + CSRF로 이름을 본문 전달하거나 동등한 로그 최소화 방식을 검토한다.

<a id="src-docs-flight-booking-verification-spec-20261026-md--flight-verify-api-01-이름-단일-입력으로-예약-검색"></a>
##### FLIGHT-VERIFY-API-01: 이름 단일 입력으로 예약 검색

- 구현 엔드포인트: `POST /api/flight-passengers/name-search` (조회 전용이지만 실명 URL 노출 방지 목적), 입력 `{name:string}`. owner·CSRF와 서버측 검색 제한, 응답 `Cache-Control:no-store`, 결과 수 제한/페이징/정렬(최근 관련 여정 우선) 및 불완전 근거 상태 반환.
- `name` 외 필수 입력 없음. 최소 2자/최대 100자 등 합성 검증된 입력 제한을 적용하되 영문 짧은 합법 이름을 부당히 막지 않는다. 이름의 한국어 ↔ 영어 대응이 확인되지 않았다면 **'한글 이름으로 확인 가능한 예약 데이터 없음'**을 반환할 수 있어야 한다. 검색 0건 vs 검증된 원본 없음/동기화 실패/권한 차단 분리.
- 이름 매칭은 검증된 성·이름의 영숫자 토큰을 NFKC/casefold로 정규화하고 순서를 무시한다. 입력이 한 구성요소여도 그 토큰이 원본 이름의 **완전한 토큰과 일치**하면 검색한다. 부분 문자열, 로마자 변환, 원본에서 띄어 쓴 구성요소의 임의 결합은 하지 않는다. 따라서 새로고침된 검증 색인에 해당 완전 토큰이 없으면 정상적인 0건 결과이며, 색인 미사용/갱신 실패 상태와 구분해야 한다.
- 예시 응답 필드: `reservations:[{booking_key,booking_ref,passenger_names,airline,segments,reserved_on:{date,provenance,semantics},issued_on,paid_on,cancellation_status,source_status,card_link_count}]`. 실제 증명 가능한 필드만 사용. `booking_key`는 식별 가능하고 서버 검증 가능한 불투명 키, 기존 `booking_ref`만으로 다른 공급자/같은 번호가 합쳐지지 않게 한다.
- 예약 상세 조회도 동일 owner·세대·원본 digest 확인. 이름만으로 반환된 카드가 다른 사용자에게 노출되지 않도록 owner 판정을 매 요청 서버에서 수행한다.

<a id="src-docs-flight-booking-verification-spec-20261026-md--flight-verify-card-01-연결된-카드와-예약일의-카드-후보"></a>
##### FLIGHT-VERIFY-CARD-01: 연결된 카드와 예약일의 카드 후보

- '연결됨'은 저장된 동일 예약/결제 사건의 **명시적 링크** 또는 현행 OTA 보수적 계약이 인정하는 확정 관계만 포함한다. 메일 추측·카드 가맹점/금액 근사·참가자 이름 일치만으로 '연결됨'을 만들지 않는다. 항공권을 특정 OTA 결제 이벤트에 연결할 근거가 없으면 `LINK_NOT_VERIFIED`로 표시한다.
- 결제일·예약일은 다를 수 있다. 사용자가 요청한 기준은 **예약일 기준일 당일 카드 전체 내역**이다. 이 기준일은 명시된 예약일 또는 승인된 `FIRST_RECEIVED`(동일 공급자·예약번호의 인증 메일 중 가장 이른 mailbox `internal_date`를 한국 날짜로 환산)만 쓴다. 화면에 출처 의미를 표시하며 공급사 생성일로 오인시키지 않는다. 카드 승인일은 시차/국제 결제에 따라 경계 차이가 발생할 수 있다. ±1일 등 확장은 **명시적으로 선택한 필터**에만 허용하고 기본 임의 확대는 금지한다.
- `list_for_day`를 사용한다면 같은 날짜의 취소·환불·중복·이미 다른 예약에 연결된 원행도 빠짐없이 표시하고 **선택 가능 여부/보류 이유**로 구분한다. 전체 카드 데이터의 읽기 전용 투영이며 필드 누출·원본 수정을 금한다.
- 없는/미검증 예약일에는 카드 후보를 생성하지 않는다. 날짜 출처 검증/이용자 명시 필터를 분리하고, 확인되지 않은 링크를 영구 저장하지 않는다.

#### 4. 수락 기준 및 실행 순서

| AC | 검증 조건 |

| FLIGHT-BOOK-08 | 조회·검색·상세·후보 UI는 원본/Google/DB/운영 자료 **무쓰기**, owner+CSRF(이름 본문 검색)/no-store, 무로그 개인정보 보호. |
| FLIGHT-BOOK-09 | 375/390/759/760/1280px, light/dark 및 신규 테마 토글, 200% 확대, 키보드·스크린리더에서 메뉴와 화면이 정상이며 카드 상세·후보가 잘리지 않는다. |
| FLIGHT-BOOK-10 | 기존 참가자 연결 권한/검증/데이터/API 호환을 보존하되 주 메뉴에서는 더 이상 참가자 연결을 강제하지 않는다. 합성 테스트 PASS, 실예약 내역에서의 수락은 실제 증거 있을 때만 PASS. |

**개발 순서:** `FLIGHT-VERIFY-DATA-01`(read-only 조사) → `FLIGHT-VERIFY-API-01`(안전 검색) + `FLIGHT-VERIFY-CARD-01`(읽기 전용 조회) → `FLIGHT-VERIFY-UI-01`(반응형 UX/통합) → 독립 검증 → 작은 PR 병합/배포 승인. 실원본 근거 필드가 확인되지 않은 사항은 `HOLD`하되 나머지 범위를 안전하게 구현하고 `NOT_VERIFIED`를 기록한다.

**완료 상태:** 핵심 기능은 구현·운영 배포됐으며, 위 수락 증거와 남은 실제 기기 터치/브라우저 확대 수락을 구분한다. 이 문서의 규칙 변경만으로 카드 연결·기장·여행 배정 권한이 생기지 않는다. 현재 구현·검증·배포 상태는 상단의 2026-10-27 증거 및 연결된 운영 기록을 기준으로 한다.

지출 정리 화면에서 긴 목록 아래로 이동해도 여행 목록과 주요 화면 이동 메뉴에 접근한다. 금융 분류와 저장 동작은 바꾸지 않는다.

<a id="src-docs-expense-cleanup-navigation-spec-md--동작과-완료-조건"></a>
#### 동작과 완료 조건

- 데스크톱에서는 왼쪽 메뉴를 화면 높이 안에 유지하고, 긴 여행 목록은 메뉴 내부에서 스크롤한다. 본문은 독립적으로 스크롤할 수 있다.
- 작은 화면에서는 메뉴 열기 버튼이 본문 스크롤 중에도 상단에 남는다. 기존 메뉴 열기, 닫기, 배경 마스크와 키보드 접근을 유지한다.
- 문서 전체 스크롤과 본문 스크롤 중 실제 사용하는 경계를 확인하고 수정한다. 단순히 sticky 속성만 추가하지 않는다.
- 상단 고정 영역이 본문과 표 헤더, 모달을 가리지 않도록 높이와 겹침 순서를 조정한다. 가로 스크롤을 새로 만들지 않는다.
- 지출 정리 외 공유 레이아웃 소비 화면도 기존 탐색 동작을 유지한다.

<a id="src-docs-expense-cleanup-navigation-spec-md--검증"></a>
#### 검증

- 긴 합성 목록으로 데스크톱과 모바일에서 아래로 스크롤한 후 메뉴 접근과 열기/닫기를 확인한다. 브라우저 작업은 Aside REPL을 사용한다.
- 변경 CSS/HTML 계약의 표적 검사만 실행한다. 전체 회귀, 배포, 서비스 재시작과 운영 데이터 변경은 하지 않는다.

<a id="src-docs-design-cost-saas-ui-refresh-md--버튼과-아이콘-규칙"></a>
#### 버튼과 아이콘 규칙

1. 주요 동작은 녹색 채움, 보조 동작은 흰 배경과 얇은 테두리, 단순 이동은 투명 버튼으로 표시한다. 한 작업 영역에서 강조 버튼을 남발하지 않는다.
2. 버튼 문구 왼쪽에 16px 선형 SVG를 둔다. 사이드 메뉴는 18px, 표 헤더는 14~16px이다. 기본 SVG는 `viewBox="0 0 24 24"`, `fill="none"`, `stroke="currentColor"`, 둥근 선 끝과 모서리를 사용한다. 선 두께는 1.75~2px 중 하나로 통일한다.
3. 주요 작업은 아이콘과 한국어 문구를 함께 표시한다. 업로드·확정·복사·제외를 아이콘만으로 표현하지 않는다. 작은 닫기·메뉴 열기 버튼은 접근 가능한 이름을 반드시 제공한다.
4. 장식 아이콘은 `aria-hidden="true"`, `focusable="false"`, 클릭은 부모 버튼에 전달되도록 한다. 아이콘이 기존 버튼의 접근 가능한 이름을 바꾸지 않도록 한다.
5. 상태는 색상뿐 아니라 문구와 아이콘으로 구분한다. 확인 필요는 경고, 저장 완료는 체크, 연결 실패는 끊긴 연결, 동기화 중은 진행 상태를 사용한다.
6. 저장 중에는 버튼 폭과 문구 공간을 유지한다. 시각 변경 때문에 기존 중복 클릭 차단·재시도 동작을 제거하지 않는다.
7. 기존 버튼의 최소 높이를 줄이지 않는다. 모바일 터치 영역은 최소 44px이며 작은 SVG를 넣어도 클릭 영역은 축소하지 않는다.
8. 아이콘은 고정된 이름 목록으로만 렌더링한다. 사용자 원문이나 AI 응답을 SVG·HTML로 직접 삽입하지 않는다.

<a id="src-docs-design-cost-saas-ui-refresh-md--공통-사이드-메뉴와-화면-상단"></a>
##### 공통 사이드 메뉴와 화면 상단

- 홈·장부·카드·영수증·Google·예약·여행·계정 화면에서 같은 메뉴 구조·아이콘·글꼴·너비·간격을 사용한다. 화면별 CSS가 메뉴에 새어 들어가지 않게 한다.
- 현재 메뉴의 연한 녹색 배경과 명확한 선택 표시를 유지한다. 최근 여행·메뉴 스크롤 복구·접이식 메뉴·viewer의 제한된 여행 목록을 보존한다.
- PC 메뉴 너비는 기존 232px을 유지한다. 모바일은 기존 접이식 메뉴를 유지하고 메뉴 열기에 작은 아이콘을 넣는다.
- 화면 상단은 제목·짧은 설명·주요 작업을 한 묶음으로 정리한다. 홈·이동 버튼을 과도하게 강조하지 않고 실제 처리 동작을 먼저 보이게 한다.

<a id="src-docs-design-cost-saas-ui-refresh-md--전체-카드-내역"></a>
##### 전체 카드 내역

- 최신 요청대로 거래일·카드·상태의 이름 자체가 버튼이어야 한다. 별도 `select` 입력을 헤더 아래에 다시 넣지 않는다.
- 거래일에 작은 달력 또는 정렬 아이콘, 카드에 카드 아이콘, 상태에 필터 아이콘을 넣는다. 선택한 월·정렬 방향·상태를 옆의 작은 문구로 유지한다.
- 제목 버튼을 누르면 기존 선택 메뉴가 열리고 현재 조건이 체크로 구분된다. 화면 밖 잘림, Escape, 키보드 접근, 선택 후 조건 보존을 유지한다.
- 상단 카드 가져오기 버튼과 검색 버튼에 아이콘을 넣는다. 검색 입력·초기화·결과 건수·페이지 이동은 일관된 높이와 간격을 사용한다.
- PC 표의 정보 밀도와 모바일 개별 거래 카드 구성을 유지한다. 금액과 지급처를 장식 때문에 숨기지 않는다.

<a id="src-docs-design-cost-saas-ui-refresh-md--카드-검토영수증자연어-규칙"></a>
##### 카드 검토·영수증·자연어 규칙

- 업로드·수정·확정·복사·재시도 버튼의 시각 규칙을 통일한다.
- 자주 사용하는 동작을 먼저 보이게 하고 설명은 보조 문구로 정리한다. 의미가 다른 저장·확정·복사를 같은 성공 표시로 합치지 않는다.
- 오류·보류·중복 경고는 문구와 상태 아이콘을 함께 표시한다. 실제 OCR·AI 연결 상태를 디자인 변경으로 완료 상태처럼 바꾸지 않는다.
- 기존 파일 입력, 후보 수정값, 여행 선택, 요청 ID, 자연어 제안 승인과 화면 갱신 동작을 보존한다.

<a id="src-docs-design-cost-saas-ui-refresh-md--google여행-장부예약계정-화면"></a>
##### Google·여행 장부·예약·계정 화면

- 읽기 전용 장부, 연결 설정, 정본 선택을 기존 기능 그대로 정돈한다. 연결되지 않은 상태를 0원이나 성공 아이콘으로 표현하지 않는다.
- 여행의 검토 중 비용과 Google 확정 수치를 기존 의미대로 구분한다. 새로운 회계 합계를 만들지 않는다.
- 예약 연결과 계정 관리의 버튼·빈 화면·안내 영역에도 같은 시각 규칙을 적용한다. viewer에게 owner 버튼을 추가하지 않는다.

| 예약·여행·계정 화면 렌더러 | 필요한 버튼·상단·표시 스타일에 한정 |
| 작은 공통 아이콘 helper | 필요할 때 하나만 추가. 고정 SVG allowlist와 공통 CSS 사용 |
| 관련 UI 검사·라이선스 파일 | 실제 변경을 검증하는 데 필요한 최소 범위 |

전체 HTML 문자열을 정규식으로 뒤져 모든 버튼을 일괄 치환하거나 DOM의 `textContent`를 기준으로 기능을 추측해 아이콘을 붙이지 않는다. 서버 렌더링 지점과 명시적인 동적 버튼 생성 지점에 적용한다. 기존 이벤트 대상, ID, 이름, 폼 값, URL과 접근 가능한 이름을 보존한다.

<a id="src-docs-design-cost-saas-ui-refresh-md--작업-순서와-작성자"></a>
#### 작업 순서와 작성자

한 명의 구현자가 다음 순서로 진행한다. 같은 파일을 동시에 수정하지 않는다.

1. 작은 로컬 아이콘 집합·공통 버튼 규격을 마련한다.
2. 공통 메뉴와 전체 카드에 먼저 적용해 시각 방향과 모바일 조작을 확인한다.
3. 카드 검토·영수증·Google·여행·예약·계정의 기존 버튼에 확장한다.
4. 합성 브라우저 근거와 실제 diff를 검토하고 논리적 단위로 커밋·push한다.
5. 완료 범위와 미완료 화면, 정확한 테스트 명령·결과, 커밋을 기록한다. 코드 완료와 운영 미반영을 구분한다.


<a id="src-docs-design-cost-saas-ui-refresh-md--검증과-인수-기준"></a>
#### 검증과 인수 기준

문서 작성 세션에서는 코드 검사·빌드·운영 스모크·배포를 실행하지 않는다. 아래 검증은 구현자가 변경 후 수행한다.

- 실제 변경된 화면의 표적 검사를 실행한다. CSS·아이콘 때문에 전체 회귀나 운영 DB 검사를 반복하지 않는다.
- 공통 아이콘에 대한 검사는 작은 고정 SVG 집합·장식 속성·잘못된 이름 처리를 확인하는 범위로 한정한다.
- 공통 메뉴와 전체 카드: 기존 `test_site_shell_browser.py`, `test_card_catalog_browser.py`를 재사용해 375px·390px·1440px에서 진입·메뉴·헤더 선택·검색·조건 보존·가로 넘침을 확인한다. 검사에 없는 동일 화면·너비를 관성적으로 추가 반복하지 않는다.
- 카드·영수증의 변경된 버튼은 합성 DB로 저장·확정·복사 동작이 유지되는지 필요한 경로만 확인한다. 실제 자료로 시험 거래를 쓰지 않는다.
- 키보드로 버튼 진입·선택 메뉴 열기·Escape 닫기·포커스 표시를 확인한다. 아이콘 장식이 버튼 이름을 바꾸지 않는지 확인한다.
- 새 아이콘에 대한 외부 네트워크 요청이 없고, 아이콘 로딩 실패나 감소된 모션 설정에서도 문구와 업무 동작이 유지되어야 한다.
- 합성 데이터만 포함한 화면 캡처를 로컬에 남겨 스타일을 직접 확인한다. 자동 검사 통과만으로 시각 품질을 완료로 선언하지 않는다.
- 차이 검토에서 DB·API·금액·원본·권한·사용자 결정 코드에 영향이 있으면 범위를 되돌리거나 해당 위험을 별도로 검증한다. 보호 검사를 약화하지 않는다.

완료는 주요 화면의 아이콘·버튼·간격이 일관되고 기존 업무 조작이 유지되는 상태다. 전체 카드에서만 예쁘게 보이는 상태는 부분 완료다. 운영 배포는 이번 작업의 완료 조건에 포함하지 않으며 별도로 인계한다.

<a id="src-docs-design-icon-license-md--아이콘-출처와-라이선스-고지"></a>
### 아이콘 출처와 라이선스 고지

작성일: 2026-10-12

<a id="src-docs-design-icon-license-md--적용-범위"></a>
#### 적용 범위

COST 업무 화면의 버튼·메뉴에 쓰는 작은 선형 아이콘은 외부 요청·아이콘
폰트·전체 패키지 없이 `webapp/ui_icons.py`의 고정 목록으로만 렌더링한다.
사용자 원문이나 AI 응답을 SVG·HTML로 직접 삽입하지 않는다.

<a id="src-docs-design-icon-license-md--방향-참고와-라이선스"></a>
#### 방향 참고와 라이선스

- 시각 방향(24px viewBox, 채움 없음, 둥근 선 끝, 2px 선)은 Lucide 선형
  아이콘의 일반적인 관례를 참고했다. 참고 문서: https://lucide.dev/guide/
- `webapp/ui_icons.py`의 경로는 COST용으로 직접 작성한 단순 도형이며
  Lucide 공식 SVG를 복사하지 않았다. 따라서 특정 Lucide 버전·커밋의
  경로와 동일하다고 주장하지 않는다.
- 방향을 참고한 원 라이선스 고지를 보존한다.
  - Lucide: ISC License — https://lucide.dev/license
  - Lucide의 Feather 기반 아이콘: MIT License — https://lucide.dev/license
- 위 고지는 참고 방향의 조건을 유지하기 위한 기록이며, COST 저장소에
  제삼자 아이콘 자산이 들어왔다는 의미가 아니다. 공식 SVG를 그대로
  포함하게 되면 해당 시점에 정확한 출처·버전(또는 커밋)과 고지를 이
  문서에 함께 기록한다.

<a id="src-docs-design-icon-license-md--렌더링-규칙"></a>
#### 렌더링 규칙

- 기본 16px, 사이드 메뉴 18px, 표 헤더 14~16px을 사용한다.
- 장식 아이콘은 `aria-hidden="true"`, `focusable="false"`이며 클릭은
  부모 버튼에 전달된다. 기존 버튼의 접근 가능한 이름을 바꾸지 않는다.
- 허용되지 않은 이름은 렌더링하지 않고 빈 문자열을 돌려준다.
