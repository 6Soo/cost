# COST 관리자 UI/UX 종합 개선 실행 명세

- 작성일: 2026-11-05
- 상태: 구현·화면 검증 완료. 영향 기반 품질 검사와 별도 PR 제출 진행 중.
- 목적: 관리자가 데스크톱과 모바일에서 주요 업무를 이해하고 키보드를 포함한 다양한 입력 방식으로 처리할 수 있도록 기존 UI를 개선한다.
- 실행 요청: 현재 대화에서 승인된 관리자 UI/UX 개선. 과거 문서의 미완료 표시는 이 명세의 신규 작업으로 자동 편입하지 않는다.
- 완료 조건: 진단 범위와 결과, 변경 전후 비교, 실제 테스트와 최종 리뷰 근거를 포함한 별도 PR 제출. 운영 배포 여부는 PR 제출과 구분한다.

## 1. 보호 경계와 작업 환경

- 금융 데이터, 거래 처리·분류·환불·여행 배정 로직, 기존 API 계약과 데이터 구조를 바꾸지 않는다. 금액·원문·상태·근거를 가리거나 의미를 바꾸는 문구도 금지한다. Google 최종 장부 자동 쓰기는 금지한다.
- 운영 DB 변경, 실제 금융 분류·여행 배정 등의 쓰기는 승인 범위가 아니다. 화면 확인과 테스트에는 실제 고객 원본이나 자격증명 대신 별도 합성 데이터와 합성 세션을 사용한다. 접근 제어와 CSRF를 우회하거나 완화하지 않는다.
- 기존 미커밋·미추적 파일과 stash를 보존한다. 시작 시 `git status --short --branch`, HEAD, 기준 SHA와 작업 파일을 기록하고, 해당 변경을 임의로 되돌리거나 PR에 포함하지 않는다. 브랜치 생성만으로 기존 미커밋 변경이 분리되는 것은 아니므로 충돌 가능성을 확인한다. 실제 격리가 필요하면 별도 작업 공간을 사용하고 기존 변경을 건드리지 않는다.
- 기준 UI는 [화면·디자인 명세](ui.md)와 현재 사용자 결정을 따른다. 수동 테마는 우상단 해/초승달 아이콘 하나이며, 카드 목록은 모바일에서도 표를 유지하고 필요한 가로 스크롤은 표 내부에 둔다. 상태·출처, 예약 관계·금융 검증·실제 환급·Google 반영의 의미를 혼동하지 않는다.
- 개인정보와 비밀정보가 화면 캡처, 테스트 산출물, Git, PR에 들어가지 않도록 합성 값만 쓴다. 임시 산출물과 작업 공간은 소유권 및 보존 여부를 확인한 뒤 프로젝트 절차에 따라 정리한다.

## 2. 현재 코드와 진단 대상

관리자 화면은 Python에서 HTML을 생성하고 공통 셸과 CSS/JavaScript를 사용한다. 시작점은 다음과 같다. 실제 진단 시 라우트와 권한·기능 플래그를 다시 열거하고 빠진 업무 화면을 추가한다.

| 업무 영역 | 시작점 또는 근거 | 진단할 대표 흐름 |
| --- | --- | --- |
| 공통 셸 | `webapp/site_shell.py`, `webapp/ledger_design.py`, `webapp/static/css/site_shell.css`, `site_theme.css` | 메뉴, 여행 탐색, 테마, 초점, 권한별 메뉴, 좁은 화면 |
| 여행 장부 | `webapp/ledger_design.py`, `webapp/static/css/ledger_design.css`, `webapp/static/js/ledger_design.js` | 여행 선택, 수입·보험가입내역·지출, 거래 상세, 빈 여행 |
| 지출 정리 | `webapp/expense_workspace.py`, `webapp/static/css/expense_workspace.css`, `webapp/static/js/expense_workspace.js` | 필터, 목록, 상세, 검토 및 보호 상태 |
| 카드 전체 내역 | `webapp/cards_all.py`, `webapp/card_catalog.py`, `webapp/static/css/card_catalog.css` | 기간·검색·필터, 표, 상세, 취소·환불 표시 |
| OTA와 예약 | `webapp/ota_payment_review.py`, `webapp/ota_catalog.py`, `webapp/reserve_link_ui.py` | 목록·예약 근거·연결 상태·빈 결과·오류 |
| 영수증·항공·참가자 | `webapp/receipt_review.py`, `webapp/trip_flight_ui.py`, `webapp/participant_trip_panel.py` | 조회·상세·로딩·오류·권한 및 기능 비활성 |
| 여행·계정·권한 및 기타 관리자 화면 | 공통 메뉴와 실제 서버 라우트에서 확인 | 목록, 상세, 설정, 접근 불가와 복구 경로 |

각 화면은 실제 접근 가능한 역할, 데이터 유무와 기능 설정을 기록한다. 목록에 없는 화면을 발견하면 인벤토리에 포함한다. 실행할 수 없는 화면은 사유와 함께 미검증으로 남기며 전수 완료로 간주하지 않는다.

## 3. 실행 순서

### A. 발견과 기준선

1. 현재 Git 상태와 사용자 변경을 보존하고 PR 기준 SHA를 기록한다. 관련 `AGENTS.md`, 공통 셸·토큰·컴포넌트 및 화면별 기존 테스트를 확인한다.
2. `better-interface`와 해당 영역 소유 스킬 `better-accessibility`, `better-layout`, `better-writing`, `better-typography`, `better-colors`, `better-ui`를 읽고 적용한다. 기존 디자인 시스템과 업무 용어를 먼저 목록화한다.
3. [웹 개발 서버 안내](../../webapp/README.md)의 별도 `--data-root`, `--environment local-synthetic`, `--synthetic-sessions` 경로를 사용해 합성 환경을 구성한다. 운영 DB와 기존 데이터 디렉터리를 사용하지 않는다.
4. 화면 인벤토리를 기준으로 정상, 빈 결과, 로딩, 오류, 권한 제한 및 코드상 존재하는 예외 상태를 조사한다. 브라우저 작업은 `ego-browser` 스킬과 설치된 `ego-browser skill` 지침을 확인하고 같은 TaskSpace를 재사용한다.
5. 화면·상태·뷰포트·테마·합성 데이터 조건을 명시한 변경 전 캡처를 보관한다. 데스크톱과 모바일을 모두 포함하며, 가능한 경우 320·390·760·1440 CSS px, 200% 확대와 두 테마를 확인한다. 표 내부의 의도된 가로 스크롤은 데이터와 조작에 도달할 수 있는지 별도로 확인한다.

### B. 진단과 우선순위

문제마다 화면/상태, 재현 단계, 사용자 영향, 현재 동작과 근거 파일·줄, 수정 방향, 검증 방법을 기록한다. 시각적 주장에는 실제 렌더링 근거를 함께 남긴다. 측정하지 않은 대비값이나 확인하지 않은 결함을 사실로 쓰지 않는다.

| 우선순위 | 기준 |
| --- | --- |
| 높음 | 업무 차단, 내용·조작 불가, 거래 상태 오인, 데이터 손실 위험, 반복되는 접근성 실패. 이름 없는 조작, 키보드 경로·가시적 초점 부재, 내용 가림, 복구 안내 없는 오류 등 확인된 필수 접근성 문제 포함 |
| 중간 | 이해·효율·반응형 동작이나 일관성을 실질적으로 해치는 문제 |
| 낮음 | 업무 영향이 제한적인 개별 시각 완성도 문제 |

같은 심각도에서는 영향 화면 수와 공통 원인 해결 효과가 큰 순서로 정렬한다. 취향만 다른 기존 디자인은 결함으로 취급하지 않는다. 진단 결과와 미검증 항목을 구분해 기록한다.

### C. 구현

1. 공통 셸·토큰·기존 컴포넌트를 먼저 재사용한다. 레이아웃, 타이포그래피, 접근성, 문구를 우선 개선하고 필요한 경우 색상·시각 마감을 보완한다.
2. 기능별로 빈 상태와 오류에서 다음 행동이 보이게 하고, 실제 업무 상태와 권한에 맞는 명칭을 유지한다. 임의의 승인 대기 상태나 실제 환급·Google 반영 완료를 만들어 표시하지 않는다.
3. 네이티브 요소, 입력 라벨, 키보드 순서·초점, 대화상자의 초점 이동과 복귀, 상태 안내, 축소 동작 설정을 확인한다. API 요청·응답과 거래 의미를 바꾸지 않는다.
4. 변경은 공통 원인부터 화면별 순서로 나누고, 각 단계에서 영향 테스트와 인접 보호 경계를 실행한다. 사용자 미커밋 변경과 겹치는 파일은 별도 기준에서 작업해 기존 변경이 손실되거나 PR에 섞이지 않게 한다.

### D. 예외 상태와 스트레스 확인

- 사용자가 명시한 `state-machine`과 `break`를 사용한다. 두 스킬은 한 번에 한 컴포넌트를 대상으로 하므로 진단에서 영향이 큰 공통 탐색, 거래 목록·필터, 상세/대화상자 등 실제 컴포넌트를 선정해 각각 실행한다. 선택 이유와 제외한 대상을 기록한다.
- `state-machine`은 실제 코드에서 도달 가능한 로딩·빈 결과·오류·권한 등 상태만 합성 데이터로 재현한다. 없는 상태는 누락으로 기록하고 존재하는 것처럼 만들지 않는다.
- `break`는 실제 컴포넌트가 받을 수 있는 긴 명칭·금액·내용, 좁은 컨테이너 등 해당 컴포넌트에 가능한 시나리오를 사용한다. 합성 데이터만 주입하고 앱의 실제 스타일과 컴포넌트를 사용한다. 관찰한 현상과 미실행 조건을 구분한다.
- 각 스킬의 임시 화면은 해당 지침의 보존·정리 조건을 따른다. 운영 데이터나 외부 쓰기를 연결하지 않는다.

### E. 검증, 리뷰, PR

1. 같은 화면·상태·폭·테마에서 변경 후 화면을 기록해 기준선과 비교한다. 모바일과 데스크톱 모두 실측하고, 키보드로 주요 업무를 수행한다. 필요한 접근성 자동 검사와 수동 검사를 실행하며 실제 수행 범위를 남긴다.
2. 영향받은 테스트 파일 또는 `-k`를 지정해 실제 실행한다. 기존 사례로 `webapp/tests/test_common_design_completion.py`, `webapp/tests/test_card_review_layout_browser.py`, `webapp/tests/test_card_history_mobile.py`가 있으나 변경 범위에 맞춰 선택·추가한다. 금융 보호 경계에 직접 영향이 있으면 관련 통합 검사를 실행한다.
3. PR에 대해 `python tools/run_quality_checks.py --base origin/main --run`을 실행하고 검사 대상·결과·시작/종료 SHA와 JUnit·skip 결과를 기록한다. 필수 시나리오 skip이나 테스트 0건을 통과로 처리하지 않는다. 실패를 고친 뒤 해당 검사를 다시 실행한다.
4. 사용자가 명시한 `interface-review`로 PR의 정확한 기준과 전체 diff를 검토한다. 신규·회귀·기존 문제를 구분하고 해결 여부와 미검증 범위를 기록한다. 일반 코드 리뷰에서 금융·API 보호 경계와 테스트 결과도 확인한다.
5. 사용자 기존 변경을 제외한 커밋을 별도 브랜치에 만들고 별도 PR을 제출한다. PR에는 화면 인벤토리·우선순위 진단, 실제 변경, 전후 비교, 실행 명령과 결과, 미검증·차단 사항을 포함한다. 실제 PR 생성과 운영 배포는 서로 다른 사실로 보고한다.

## 4. 완료 판정 및 기록

| 요구사항 | 완료 증거 |
| --- | --- |
| 주요 화면 전수 진단 | 실제 라우트·역할·상태 인벤토리, 화면별 결과 및 미검증 사유 |
| 우선순위 | 심각도·영향·코드와 렌더링 근거가 있는 정렬 목록 |
| 디자인·접근성 개선 | 기존 자산 재사용 근거, 변경 파일과 해결된 항목 |
| 예외 상태 | 선택한 각 컴포넌트의 `state-machine`·`break` 실행 결과와 제외 범위 |
| 화면 비교 | 합성 환경의 동일 조건 전후 캡처, 모바일·데스크톱 및 테마별 결과 |
| 실제 테스트 | 명령·SHA·실행 건수·통과/실패/skip 및 보호 경계 결과 |
| 최종 리뷰·PR | `interface-review` 결과, 별도 PR 링크·커밋 및 남은 문제 |

각 항목은 실제 증거가 충족될 때만 완료로 표시한다. 자료나 권한 등으로 일부가 막히면 구체적 이유와 다음 행동을 기록하고 독립적인 작업은 계속한다. 테스트 결과 없이 전체 완료로 표시하지 않는다.
