# 웹 장부 에이전트 운영 명세

적용일: 2026-09-29. 사용자 결정: `D-WEB-AGENT-002`.
후속 역할 정정: `D-WEB-AGENT-003`이 아래 이전 역할 설명보다 우선한다.

## 현행 지속 실행과 의사결정 분리

- Astra Low가 지속 실행 컨트롤러이자 상태 관리자다. 작업표, 현재 phase, 워커 상태, ownership, 검증 증거와 미완료 항목을 관리하고 실제 위임·결과 회수·통합 실행·재시도를 수행한다. 공통 작업표와 통합 공간의 단독 작성자도 Astra다.
- GPT 5.6 Sol Web은 설계, 작업 분할, 우선순위, 워커 지시, 결과 검토, 충돌 해결처럼 높은 추론이 필요한 의사결정 단위로 직접 호출한다. 한 호출에는 해당 phase의 필요한 입력만 제공하고 판단 결과를 회수한 뒤 그 호출을 종료한다. 장시간 실행이나 프로젝트 상태 보관을 맡기지 않는다.
- Astra는 Sol의 의미 있는 설계·구현 선택을 임의 변경하지 않는다. 명세 충돌이나 새로운 아키텍처 판단이 생기면 압축된 증거와 선택지를 갖춰 Sol에 다시 질의한다. 일상적인 상태 조회·결과 수집·결정론적 검증은 Astra가 수행한다.
- Muse Spark 1.3 Free와 SpaceBunny Free는 Sol이 정한 분할에 따라 구현·환경설정을 병렬 수행한다. 파일·DB·외부 자원별 writer는 하나이며 가능한 경우 독립 worktree를 사용한다.
- 워커 전체 로그를 Sol에 보내지 않는다. Astra가 변경 파일, 핵심 변경, 테스트 결과, 실패 원인, 미해결 사항과 필요한 diff만 전달한다. Sol의 반환값에는 결정, 담당 파일, acceptance, 검증 범위, 다음 판단 조건을 포함한다.
- phase별로 `계획 → Sol 검토 → Muse/Bunny 병렬 구현 → Astra 결과 회수 → Sol 통합 검토 → 수정·검증`을 반복한다. 워커의 완료 주장만으로 완료 처리하지 않는다.
- 마지막에는 Sol의 전체 변경 architecture/integration review를 한 번 더 받는다. Astra가 저장소 상태, 실제 테스트 결과, acceptance와 미해결 항목 부재를 확인한 뒤에만 전체 완료를 판정한다. 명시적으로 추가 승인이 필요한 경우를 제외하고 이 루프를 계속한다.
- 아래 문서에서 Sol이 작업표·감시·통합 공간·상태·사용자 보고를 계속 관리한다는 설명은 Astra 담당으로 대체한다. Sol의 높은 추론 판단 역할은 유지한다. 장기 Sol 실행은 종료하고 짧은 판단 호출로 전환하며 기존 워커 결과는 보존한다.

이 문서는 관리·감독·지시와 구현·환경설정의 역할 및 결과 수용 절차를 정의한다. 제품 기능과 비용·일정 권위 규칙은 바꾸지 않는다. 역할 지정은 실제 모델 전환·인증·실행 성공을 의미하지 않는다.

## 2. 병렬 분할과 작성권

독립적인 작업 두 개가 준비되면 Muse와 SpaceBunny가 동시에 진행한다. 기본 예시는 Muse의 환경설정·운영 진입점 작업과 SpaceBunny의 장부·예약 로직 작업이다. 고정 전문분야가 아니며 실제 파일 의존성을 보고 Sol이 배정한다. 병렬 숫자를 채우려고 의존 작업이나 불필요한 감사를 만들지 않는다.

- 구현자별 Paseo workspace와 worktree, 브랜치, 합성 DB, 출력 경로, 테스트 포트를 분리한다. 기준 커밋과 필요한 미커밋 변경의 목록·해시를 맞춘다. 비밀값·원본 고객 자료는 전달하지 않는다.
- 같은 파일은 격리 공간에서도 동시에 변경하도록 배정하지 않는다. 공유 API·스키마·의존성 파일·시작 설정은 소유자를 먼저 정하고 소비자는 합의한 인터페이스나 합성 대역으로 작업한다. 소유자 결과 수용 뒤 의존 작업을 통합한다.
- 같은 외부 프로젝트·환경 변수 묶음·배포 대상·DB·브라우저 인증 세션에는 작성자가 한 명이다. worktree 분리는 외부 자원 격리가 아니다. 소유권이 불명확하면 해당 외부 쓰기만 보류한다.
- Astra가 Sol이 수용한 결과를 통합 작업 트리에 반영하는 단독 작성자를 맡는다. 실행 중인 구현자의 작업 트리에서 전체 파일을 일괄 스테이징하거나 통합·커밋하지 않는다. 확정된 산출물만 별도 통합 공간에 반영한다.
- 기존 SpaceBunny가 실행 중이면 중단·추가 프롬프트·작업공간 이동 없이 기존 범위를 먼저 확인한다. 기존 범위와 겹치지 않는 Muse 작업만 시작한다. 범위가 불명확하면 확인될 때까지 겹칠 가능성이 있는 작업은 배정하지 않는다. 다음 작업부터 격리 기준을 적용하며 재시작하지 않는다.
- 환경설정 담당 지정은 계정 생성·배포·운영 자료 변경·유료 결제의 새 승인이 아니다. 기존의 명시적 사용자 승인 범위를 작업표에 기록하고 그대로 활용한다. 이미 승인된 작업은 재질문하지 않는다.

## 3. 단일 작업표와 짧은 지시

Astra만 [구현 기록](WEB_LEDGER_IMPLEMENTATION_LOG.md)의 운영 작업표를 갱신한다. 구현자는 자신의 격리 공간에 결과를 제출하고 공통 문서를 동시에 수정하지 않는다. 기존 요구사항과 Muse 감사 5개를 이 표에 한 번 매핑하고 미해결 항목만 이어간다. 같은 목록을 새 계획 문서로 반복 복제하지 않는다.

각 행에는 다음을 기록한다.

```text
task_id / 요구사항 또는 finding_id:
목표 / 제외 범위 / 성공 조건:
담당 agent_id / 실제 provider·model / workspace·branch:
기준 commit / 필요한 로컬 변경 digest:
수정 허용 파일 / 외부 자원 단독 소유자 / 승인 근거:
선행 작업 / 합의한 인터페이스:
상태 / 마지막 산출물·시각 / 다음 동작:
결과 경로 / 변경 digest / 검증 명령·환경·결과·소요 시간:
통합 기준 / Sol 검토 결과 / 잔여 항목:
```

상태는 `준비 → 실행 중 → 결과 제출 → 검토 중 → 통합 완료`로 진행한다. 실패는 `수정 필요`, 외부 의존성은 `외부 조건 대기`, 모델·도구 불가는 `실행 불가`로 분리한다. `idle`과 테스트 통과 보고만으로 통합 완료로 바꾸지 않는다. 지시에는 담당 함수·관련 계약·합성 입력만 포함한다. 범위를 추가할 때는 새 항목과 의존성을 기록하며 실행 중인 지시를 덮어쓰지 않는다.

## 4. 감시·알림·재시도

- 기본은 완료 이벤트로 결과를 회수한다. 사용자에게 정상 실행·idle·재개 알림을 반복하지 않는다. 오류·판단 필요·중요한 결과·전체 완료는 Astra가 모아서 보고한다.
- 사용자 알림 억제가 필요한 호출은 `background=true`, `notifyOnFinish=false`를 사용한다. 이 설정을 쓰면 완료 회수 수단을 반드시 작업표에 둔다. 알림이 자동 도착한다고 가정하지 않는다.
- 기존 5분 감시 요구를 적용할 때 감시자는 Astra 하나만 둔다. 별도 감시 턴을 중복 시작하지 않는다. 한 주기에 상태를 한 번 확인하고, 상태 변화·오류·예정 결과 지연이 있을 때만 최근 활동을 읽는다. 같은 상태에서 상태·활동·목록 조회를 연달아 반복하지 않는다.
- 기존 heartbeat의 소유자·주기·대상을 확인한 뒤 재사용한다. 종료 확인 없이 새 heartbeat를 만들지 않는다. 다른 소유자의 감시를 제어할 수 없으면 중복 감시를 추가하지 않고 제약을 기록한다. 감시 종료는 전체 범위 수용 또는 사용자 지시에 따른다.
- `running`은 진척 증거가 아니다. 합의한 예상 시간과 마지막 산출물로 판단한다. 예상 시간을 넘기면 활동과 실행 명령을 한 번 조사하고, 같은 원인에는 같은 조사·재지시를 반복하지 않는다. 장시간 테스트라는 이유만으로 작업자를 교체하지 않는다.
- 도구 스키마·현재 실행 환경·명령 가용성을 먼저 확인한다. 잘못된 인자는 형식을 수정한 뒤 한 번 재호출한다. 일시적 읽기 오류는 같은 대상에서 최대 두 번 추가 시도한다. 반복 실패 시 오류 코드와 막힌 범위를 기록하고 독립 작업을 계속한다.
- 지원되지 않는 모델·인증 오류·보안 차단은 같은 호출 반복이나 다른 에이전트로 우회하지 않는다. 확인된 원인을 해결한 경우만 재시도한다. 외부 쓰기 timeout은 실제 반영 여부를 조회하며 `OUTCOME_UNKNOWN`이면 재전송하지 않는다. Agoda의 전용 제한은 별도로 그대로 적용한다.

## 5. 결과 회수와 검증

1. 구현자는 요구사항별 변경 파일, 패치 또는 커밋, 검사 명령·결과, 실패·생략·미검증, 외부 효과를 제출한다. 통과 수에는 기준 코드 digest와 실행 시각을 붙인다.
2. Astra가 결과를 저장하고 finding별 코드·테스트 근거를 대조해 압축한 결과와 필요한 diff를 Sol에 전달한다. Sol의 통합 검토 결정을 저장한다. 중복 지적은 한 항목으로 합치고 비적용 이유도 남긴다. 전체 결과를 회수하기 전에 archive하지 않는다.
3. 겹치지 않는 확정 변경을 순서대로 통합한다. 소유자 밖의 변경은 반환하고, 충돌은 지정 구현자 한 명이 해결한다. 결과 저장·대조·통합 또는 명시 보류까지 마친 뒤 작업자를 정리한다. 재사용 예정인 작업자는 유지한다.
4. 수정 중에는 해당 실패 재현과 영향받는 검사만 실행한다. 통합 후보가 고정된 뒤 관련 통합 검사와 전체 앱 검사를 한 번 수행한다. 코드·환경·실패 근거가 변하지 않으면 같은 전체 검사를 반복하지 않는다.
5. 간헐적 실패는 해당 테스트와 관련 순서·동시성 조건을 좁혀 반복하고 실패 횟수/시도 횟수를 기록한다. 필요성이 확인된 경우만 전체 반복 검사를 하며, 시작 전에 횟수와 종료 조건을 정한다. 몇 번 통과했다고 결함 부재를 단정하지 않는다.
6. 최신 통합 검증값은 구현 기록의 한 위치에만 기록하고 다른 문서는 링크한다. 과거 수치를 삭제하거나 현재 코드의 검증값으로 재사용하지 않는다. 합성 검증, 실제 로그인·연동, 운영 배포 완료는 구분한다.

## 6. 재개와 종료

압축·세션 이동 전후에는 작업표, 마지막 수용 결과, 실행 중 agent와 소유권, 다음 동작을 기준으로 재개한다. 명령을 보낼 예정이었다는 문장을 실행 증거로 사용하지 않는다. 전체 대화·저장소를 다시 읽지 않고 필요한 산출물만 확인한다.

전체 완료는 범위 안의 요구사항이 모두 수용되고, 통합 후보의 검증 근거와 사용자 흐름 증거가 있는 경우다. 외부 조건 때문에 남은 항목은 로컬 완료와 분리한다. 새로운 위험 근거 없이 전체 명세 감사를 재개하지 않는다. 문서 작성·모델 이름 지정·에이전트 생성 자체를 구현 완료로 세지 않는다.

## 7. 이번 규칙의 근거와 적용 상태
